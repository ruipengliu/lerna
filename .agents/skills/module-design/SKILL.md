# 模块详细设计

本 skill 集中定义本项目技术方案的设计、表达与交付审查要求，并提供从系统全景图展开模块的工作流程。默认读者为高级工程师，熟悉通用架构和技术机制。正文突出本项目的关键设计、决策依据和实现约束；特有或易混淆概念首次出现时简要定义。

将用户指定的全景图模块展开为可供实现和评审的技术方案，写入本项目架构文档。默认完成指定模块的设计文档及必要契约、示例；指定模块外的调整遵循第 2 步的提案与决策流程。运行代码的实现按用户另行指定的范围处理。

## 1. 定位模块与依据

| 依据 | 读取目的 |
| --- | --- |
| [架构入口](../../../docs/architecture/README.md) | 找到现有方案、目录及成熟度，确定新建还是补全现有文档 |
| [项目目标](../../../docs/architecture/goals.md) | 选出本模块承担的 C1–C9、A1–A4 及适用的 V1／V2 目标；区分建设目标与已具备能力 |
| [系统分工图](../../../docs/architecture/README.md#2-系统分工与事实归属) | 以总览内的 Mermaid 作为现行系统全景，确认模块、职责、事实归属及关键交互 |

按名称定位图中节点，读取分组、相连节点、边标签与箭头方向；有独立图时沿正文链接读取，按其格式检查源文件，必要时查看渲染或导出图。图中的逻辑职责与实际部署分别判断，连线只给出关键交互，完整契约还需查正文。

沿架构入口读取目标模块及直接邻接模块的相关章节，检索接口、状态、事实归属和待补契约。现行模块方案承载具体设计约束；与全景图不一致时，先区分抽象展开与真实职责冲突，需要跨模块调整的按第 2 步提出提案。正文没有依据的细节作为本次设计选择或假设说明。

默认使用现行文档。只有追溯某项决策或用户明确要求复用时，才按时间读取 [2026-09-26 归档](../../../docs/archive/architecture-2026-09-26/README.md)或[更早的 2026-09-22 归档](../../../docs/archive/architecture-2026-09-22/README.md)对应材料；历史接口、选型和“已确认”结论需重新对照当前目标与契约。

用户未指定模块、名称映射到多个不同范围或关键约束冲突时，给出候选范围与推荐，询问决定设计方向的信息，同时继续不依赖答案的资料核对。已有充分上下文时直接定位；默认聚焦指定模块，邻接模块只展开到完成交接所需的程度。

完成条件：能指出目标节点或分组、覆盖的目标、直接协作方、现有契约和文档落点；影响核心决策的缺口已显式提出，其余信息足以继续设计。

## 2. 确定边界与关键决策

先建立本模块的职责边界与最小闭环：

- 用一个具体场景说明请求从哪里来、模块产出什么、调用方凭什么判定成功；列明本模块保存和裁决的事实，以及依赖外部裁决的事项。
- 对每个直接交接列出发起方、处理方、输入输出、成功含义、持久责任及失败后的继续者。区分已有约定、本次补充和邻接模块仍须提供的能力。
- 从用户目标、已确认约束和现有契约出发，找出决定闭环能否成立的关键矛盾；发现错误前提、遗漏或更优路径时，给出有依据的建议，区分事实、假设与待决项。
- 先推演满足目标的最简单可行方案。新增模块、层次或概念须对应具体问题，说明现有职责为何不足，并通过删除、合并或复用检验其必要性。涉及接口拆分时，以调用方必须知道的契约为边界，内部实现细节留在模块内。
- 展开细则前，为决定方案形状的关键选择写出短论证：从项目事实与约束出发，对照最有竞争力的简单方案，说明推荐理由、适用边界、主要代价的承担者和触发场景，以及改变选择的条件。理由若只说明候选方案的共同前提，继续比较能区分它们的行为与成本；没有可信替代时说明约束依据即可。
- 选型未定时，根据本模块的实际约束作出选择；涉及外部技术能力、版本或性能依据时查一手资料并标注来源，历史方案仅作为候选。没有证据的容量参数标明估算前提。

短论证可先写在工作草稿，定稿时融入对应段落。遇到理由跳步、概念早于动机或代价抽象时，按问题读取[论证与表达对照](references/design-reasoning-examples.md)中的相关案例；案例提供分析方法，具体技术结论仍以现行契约为准。

文档重构保持已确认契约，超出本轮授权的设计变化列为建议。兼容设计以已发布契约或明确的共存要求为依据；无此约束的设计草案在本次授权范围内直接统一修订正文、契约与示例。

邻接契约缺失时，写清所需输入、输出和保证由谁提供，以及能力缺席时本模块等待、拒绝或降级的具体行为。

提出机制增删、合并或替代建议前，推演正常链路及最可能推翻设计的异常场景，核对谁发起、谁裁决、谁保存事实、何时可以确认成功、失败后由谁继续；以推演结果判断变更是否成立。

### 跨模块调整提案

全景图无法满足模块需求，或关联模块的职责、接口、状态与保证需要联动调整时，提出可供决策的具体提案：

- **问题与依据**：用正常链路或异常场景说明现有设计为何不足，以及维持现状的影响。
- **推荐变更**：列出调整前后的职责或行为、涉及的模块与文件，以及需要同步的图、契约、示例和索引；给出足以评审的具体改法。
- **取舍与验证**：说明可行替代方案、主要代价、对既有契约的影响和验证办法，明确需要用户决定的事项。

提案先在会话或指定模块的待决部分呈现。决策前保持指定模块外的内容不变，继续完成不依赖该决策的工作；本模块中依赖提案的设计标为条件方案，不将其写成已生效契约。

用户明确决定采用后，将决定及范围记入方案，按该范围修改指定模块外的内容并完成联动检查。同一会话已有明确决定且覆盖本次调整时直接执行；新增或超出已决策范围的变化另行提案。提案未采用时按现有边界收敛；无法满足的需求保留为明确缺口。

完成条件：正常闭环的每次交接都有明确责任方和成功依据；每项关键推荐都能指出支持它的事实或约束，有竞争方案时能解释为何在本场景下选用当前方案。尚不能成立的理由保留为假设或待决项，并给出验证路径；依赖缺口与跨模块待决项已标明，采用的提案有明确决策和修改范围。

## 3. 展开到可实现的机制

沿关键处理链细化设计。下表是覆盖检查，按模块适用性选择内容和篇幅；不适用项仅在容易引起误解时解释原因。

| 设计面 | 必须能从方案中判断的问题 |
| --- | --- |
| 对外契约 | 调用条件、输入输出、标识与关联、错误语义、取消／超时、重复调用及版本如何约定？复用哪个现有接口，哪些是新增提案？ |
| 内部流程 | 如何分配职责、调用依赖和作出裁决？核心算法或策略的输入、判定顺序、输出和有限执行条件是什么？ |
| 状态与存储 | 谁保存事实？状态转移由什么触发、受哪些条件约束？并发更新、原子提交、保留和清理如何保证后续责任可恢复？ |
| 异常与恢复 | 最可能推翻设计的失败、竞争或结果不明场景下，保留什么依据、由谁核对、何时重试或终止？缺少依赖时如何恢复推进？ |
| 授权与隔离 | 使用哪些主体、资源、用途和许可依据？哪里落实检查，权限变化如何影响在途工作？数据和资源消耗如何按用户隔离？ |
| 部署与容量 | 如何组装默认实现与依赖？适用的端云部署、离线或替换条件是什么？哪些队列、并发、时间与存储需要限额，过载时对外表现如何？ |
| 观测与验收 | 用哪些记录解释一次处理及其成本？如何用输入、故障注入和可观察结果验证关键保证？哪些结果仅能由未来运行实现证明？ |

跨模块异步交接需明确消息收到、业务接纳和效果确认各自的依据；涉及有副作用的操作时，推演“效果可能已发生但结果丢失”，落实原操作核对与重试条件。

决策分支应互斥或明确判定顺序，可同时成立的条件分别判断。

选一个贯穿正常流程的具体例子，再把最有挑战性的异常放回同一链路推演。为关键保证编写验证用例，至少交代前置条件、刺激或故障、预期可观察结果及对应目标。依赖人工处置时说明处置入口和允许动作，不能以“人工解决”省略契约。

完成条件：实现者无需自行决定关键职责、状态转移、交接原子边界和恢复策略；每项核心保证均有可观察的验证办法。尚缺证据的技术假设有验证路径，阻断实施的未决项明确标记。

## 4. 写入方案并联动现有文档

已有方案在原目录补全；没有方案时默认写入 `docs/architecture/<module-slug>/README.md`。指定的是已有方案中的子模块时，优先在所属方案扩展章节或文件，并从入口链接。篇幅确需拆分时，按连续阅读与实现查阅的需要拆分，入口保留完整主线。

正文通常沿“范围与分工 → 关键决策 → 正常处理链 → 关键机制与异常 → 契约查阅 → 验证与待决项”组织，按模块调整。先完成实质内容，再决定标题和文件划分，让读者看清问题、选择与行为的因果关系。多篇文档组成同一方案时，总览给出连续阅读路径。完整规则、字段和约束只在所属专题的一个权威位置定义，其他章节链接查阅。

组织正文与图表时：

- 决定机制是否成立的条件紧邻机制，完整字段、参数及异常清单集中查阅。已划定交付范围时，后续能力单列；当前机制尚未落实的依赖及缺失时的行为在入口说明。
- 主要通过图示表达模块关系、关键交接和状态变化，每张图聚焦一个问题。明确视角、边界及节点和连线的含义；同组分类使用同一维度，状态图固定建模对象，独立状态分别表达。沿用现有图示格式与风格；新增简单图优先使用 Markdown 内嵌 Mermaid，独立 HTML 仅在明确要求时生成。
- 段落围绕一个问题展开，主体与动作明确，相邻句自然承接；独立机制分段说明。配合图示时，文字补充职责、决策理由、边界与例外，避免逐句复述。解释非显然的机制时，先说明决定行为的事实，必要时用最小场景解释选择，再展开完整约束。
- 精简先判断信息是否必要、是否应在此处展开，再调整措辞；减少重复内容、无效层次和不必要概念，保留理解行为所需的解释。字段、接口和选项比较优先用表格，简单内容直接用短文。

在指定模块及已决策的联动范围内落实以下更新：

- 已有 Schema、示例或校验脚本时，同步本次契约改动；新增机器可读契约、伪代码或配置示例应解决具体的实现歧义，并标明是否可运行。
- 按实际影响更新架构入口、所属方案的阅读导航、邻接文档中的契约引用和缺口状态。模块职责或关键交互改变时，同步总览内的系统分工图及受影响的独立图；有导出图时一并更新。

发现范围外还需联动的内容时，补入提案，按第 2 步处理。待决提案集中记录，正文区分当前设计与条件方案。

完成条件：方案及已决策的联动修改已落盘，受影响的正文、图、契约与示例一致；架构入口可达或其索引更新已列入待决范围，设计完成与运行实现状态分别标注。

## 5. 审查与交付

对新增或实质改写的方案，先做独立读者复述。使用不继承讨论过程的审查上下文，仅提供需求、成稿和正文明确引用的必要依据，让审查者据正文简短复述问题、推荐、竞争方案的取舍和代价，并定位支持这些判断的段落。无法推出结论、需猜测前提或依赖作者补充解释时，指出具体缺口；审查者复述出的含义还须与需求和既有契约一致。缺少独立审查条件时，自行做相同核对并记录限制；纯措辞或查阅项修改按影响局部检查。

主设计根据复述结果补足论证或调整组织，再按影响范围对照图、正文、契约及示例，核对参与者、消息方向、状态与保证强度，明确标注未落实的机制。重点沿一次正常调用和最可能推翻设计的关键异常，跨文档检查从发起、裁决、事实保存、成功确认到恢复的责任链，确认新增依赖有提供方，新增状态或错误有调用方可执行的后续行为。可用时，将邻接契约一致性或异常推演交给另一审查者。推理与语义问题在相关范围内修正并复核，结构齐全不能代替正文依据。

用户指出一处问题后，归纳错误类型，检查本次范围及关联文档中的同类问题并一并修正。已有依据且在授权范围内的调整自主完成；范围外的变更按第 2 步处理，仅对影响关键决策的缺失信息提问，并附推荐。

检查 Markdown 链接及锚点、图示语法与实际渲染；契约发生变化时运行其现有校验。按影响选择验证，分别记录语义审查、静态检查、渲染检查和运行验证结果。工具或实现不具备时明确未验证项和影响，不将设计推演计作运行通过。

交付简述方案路径、关键决策、已执行的检查，以及仍需用户决策或后续实现验证的事项。若请求仅限某一阶段，交付该阶段产物；完整设计请求应落盘完整方案，未决项只限制依赖它的部分。

完成条件：读者无需依赖会话，就能从正文说明方案主线、关键取舍与限制，并判断异常后的行为，且理解与需求和契约一致；可判定的概念歧义、职责缺口和图文矛盾已解决，剩余缺口的影响与验证方式可查，交付说明与实际证据一致。

修改本 skill 的论证或审查流程时，用对照材料中的已知问题回放，再选择一篇未用于编写案例的文档局部试用。记录实际发现、修订和遗漏，并区分样例回放与独立试用；格式检查通过不能证明写作质量改善。
