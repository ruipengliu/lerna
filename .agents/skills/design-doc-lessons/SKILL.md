# 技术方案写作经验沉淀

将当前会话中有依据、可复用的写作经验融入项目根目录 `AGENTS.md` 的“方案设计文档”部分。普通方案编写与修改沿用现有指引；本流程在用户要求复盘、沉淀经验时使用。

流程：分析会话 → 筛选经验 → 输出草稿并等待确认 → 应用确认内容。用户要求的确认门约束 `AGENTS.md` 写入：确认前保持该文件不变，分析与草稿正常完成。

## 1. 分析会话

- 读取当前 `AGENTS.md`，以实际文件作为比较基线。使用 [writing-for-agents](../writing-for-agents/SKILL.md) 指导规则的组织与精简。
- 回顾可见会话中的用户纠正、明确偏好、已确认约束，以及文档修改暴露的问题和有效改法。必要时只读核对相关文档或 diff；文档现状用于核实事实，不单独证明用户偏好。
- 为候选经验保留简短依据，区分用户明确要求、已验证的问题与改进、助手推断。助手提出的建议及用户未回应的内容，仍按未确认处理。
- 说明影响结论的上下文缺失。仅凭可见内容继续分析，不编造历史反馈；只有缺失信息决定规则是否成立时才询问。

完成条件：每条候选经验都有可指出的会话依据，且事实、推断和待确认内容已分清。没有有效证据时说明原因，结束本次复盘。

## 2. 筛选与归并

按以下判定顺序处理候选经验：

1. **适用范围**：保留能改善本项目后续技术方案写作的经验。具体模块、字段、参数和一次性技术取舍留在原方案；仅记录其可迁移的分析或表达方法。其他工程经验不纳入本次修改。
2. **证据充分性**：推断、存在争议或适用条件尚不清楚的经验列为待讨论项。明确其成立条件后再拟成规则。
3. **已有覆盖**：比较含义而非字面。已覆盖的经验注明对应条款；执行时遗漏既有要求，应先判断措辞或触发条件是否确有缺口。
4. **增量价值**：有缺口时优先在原条款补充或合并，确属独立要求时再新增。若与现有要求冲突，列明冲突、依据和推荐处理，作为单独待决项。

把保留的经验写成可执行、可核对的指引，交代必要的适用条件和行为边界。用当前案例检查能否避免同类问题，再用一个适用条件不同的场景检查是否过度泛化。会话经过和论证留在分析中，长期规则只保留影响后续行为的内容。

完成条件：候选经验均已归入拟修改、已有覆盖、不纳入或待讨论；每项拟修改都能说明它比现有规则多解决了什么问题。没有值得修改的内容时，说明已有覆盖或证据不足，结束流程并保持文件原样。

## 3. 输出草稿并等待确认

在会话中交付以下内容，草稿无需另存文件：

- **分析摘要**：用简表列出拟修改项的编号、会话依据、可复用经验、现有条款与处理方式。对已有覆盖、不纳入和待讨论项简述原因。
- **准确草稿**：给出针对当前 `AGENTS.md` 的完整拟修改 diff，包含必要上下文，明确新增、替换或删除的实际文字；维持既有结构和风格。
- **待决项**：仅列影响规则成立或冲突处理的问题，并给出推荐。与之无关的草稿可单独确认。

请用户确认全部草稿或指定编号，并说明这是用户要求的“先草稿、确认后更新”流程。输出后结束本轮，等待回复；沉默、询问理由或仅要求改稿均不构成写入授权。

完成条件：用户已看到可直接应用的确切文字和修改位置。收到修订意见先改草稿；用户明确要求“按这些修改后写入”等指令时，可在其明确范围内应用，无需重复确认。

## 4. 应用确认内容

- 将用户回复对应到已展示的草稿，只应用明确批准的条目。部分确认时，其余条目继续保留为待定。
- 写入前重读 `AGENTS.md`。若期间的变化不影响已批准内容，调整定位后继续；若改变规则含义或产生冲突，仅将受影响部分重新出稿确认，保留其他工作。
- 在原条款中完成必要合并，保持无关内容与既有契约。若本次讨论要求改变具体技术设计，将其作为独立建议，不借经验沉淀修改方案文档。
- 复核实际 diff 是否限于确认范围，检查规则间的重复、冲突、过度泛化和 Markdown 格式；若新增指针，检查目标及触发条件。总结改动位置、已做检查和仍待确认的项目，不把静态检查说成行为效果已验证。

完成条件：实际变更与用户批准的文字及明确修订一致，未批准条目和无关内容保持原样。
