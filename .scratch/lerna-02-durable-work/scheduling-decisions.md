## 2. 可信装配与业务事实的最小来源

在 `internal/durableworkdemo` 的真实消费路径增加**演示调度策略及观察**，runtime 只存/调度有类型的责任；host/cmd 只注入和启动。adapter 实现消费方端口，不反向调用 host。规则纯计算仍只有 project，无需创建新阶段来冒充控制或核对业务。

采用宿主显式注入、校验且持久绑定的 fixture policy，按准确 owner + 对象身份选择。普通对象使用允许立即成功的默认策略；异常场景明确配置到特定测试对象，不能通过正文内容、ID 前缀、payload lane 或调用方自报权限偷偷选择。

当前闭合策略只需：

- 稳定策略 identity/version（或准确摘要）；Job 的内部 lane；有限执行时长、最大实际启动次数、基础/最大退避、等待复查间隔。
- 可选一个持久 gate 条件，见第 3 节。
- 可选有限的 fixture 临时失败次数；可选一个闭合的永久 fixture 拒绝分类。除此之外输出同样的准确 hash。不得接受任意代码、URL、表达式或用户定义重试规则。

首次接纳将该输入修订实际采用的策略绑定及绝对执行截止一起耐久保存。原 command 重传只取原决定，不重新挑选当前策略。新 input revision 可采用届时明确配置的策略，但不能覆写已领取旧 revision 的快照。未领取中间修订仍可按已批准最新投影语义合并。

lane 在同一对象的 project Job 首次创建时固定；现有 Job 不通过策略变更偷偷搬 lane。测试为三个 lane 使用三个明确绑定的对象集合。后续若真需要 lane 迁移，应单独说明在途配额转移，当前不做。

故意返回 transient/permanent 的 fixture 是有标记的测试处理器配置，用来验证真实耐久调度路径；不声称真实网络故障或凭一段 text 推导权限失败。权限测试还必须有实际的受信 worker 资格变化，不能只有“假装 forbidden”的分支。

## 3. 可检查等待、扫描与释放资源

最小等待谓词选择 **`gate_revision_at_least`**：保存准确同 owner gate identity、所需 revision、等待原因、下一次复查 due_at、该工作修订的绝对截止。gate 是演示 owner 的单调耐久事实，由受信 Host 测试控制 seam 提交推进；不是 Task WaitCondition，也不要求伪造 task_id。未知 owner、错 gate、回退 revision 拒绝。重复推进相同 revision 幂等。

gate predicate 的门槛固定在原工作修订策略中；重开读取实际 gate 事实，不能让内存 channel/callback 成为唯一条件。控制 seam 经明确受信装配才能使用，不能成为 record 用户可修改策略的后门。

worker 检查 gate 未满足时，短事务保存 waiting + 条件 + 正的下一次复查时间，释放 Claim、lane/tenant 槽、连接与事务后返回。检查满足后才进入实际处理；等待检查不算一次 project attempt。全部通知可以丢弃，由到期有界扫描重新检查。通知仅能使调度器较早查看 gate 的新事实，不能提前启动未来 due 的普通退避工作或代替持久条件。

调度器每次最多取有界 batch，空轮和未到期轮给出可信时钟的未来唤醒点；取“最早相关 due/lease/deadline”与有限 fallback 扫描周期的较早值。无工作时也必须停在 timer/取消等待，不能立即无界重扫。只查询未来 due 不得占有效 Claim。无通知、gate 改变、时钟到期及 context 退出均有真实可观察路径。

**无忙轮询/资源释放的观察**：内部 Host 调度观察至少能给出当前持久 wait/ref/due、是否持有有效 Claim、一次 scan/step 的有界结果及下一唤醒时间。用可控时钟驱动有限步，并在等待期间由另一个请求完成普通接纳/投影；可将连接池限定为一条连接或使用明确锁竞争对照，证明等待没有占长事务。可以使用测试时钟暴露的等待注册同步点证明 runner 已停在未来计时器，不用 SQL 调用次数、私有函数计数或长 sleep 充当证据。

## 4. 有限尝试、分类和关闭某个修订

处理者返回闭合的内部结果：成功投影、持久可检查等待、可安全有限重试、永久失败。runtime 不根据错误字符串猜分类。重试仅适用于本演示已知无外部副作用的 project；不推广为外部请求自动重发。

- `attempt_count` 按**原输入修订**记录，在领取后、真正处理开始前的短事务中核验资格并增加。仅领取、检查尚未满足 gate、等待配额不增加次数。开始确认丢失时查询该 Claim/启动记录，不重复给同一次启动加计数。
- 开始记录已提交后进程退出可以消耗一次尝试，即使无法证明 hash 实际计算过；重开不清零。epoch、续租和重复通知也不重置它。新的显式输入修订有自己的有限预算；旧 Claim 仍用旧修订快照，不能借新修订重置旧预算。具体用小的修订表还是当前/claimed 快照由实施者按实际代码选择。
- 有限临时失败 fixture 依据持久启动序号取结果，重开不从第一个临时失败重新开始。正常 fixture 达到预设有限临时失败次数后产生准确 hash；配置与最大尝试不匹配时到界明确关闭，不无限重试。
- 退避采用无随机抖动的确定性 `min(base × 2^(attempt-1), max_backoff)`，需溢出安全；base>0，max_backoff>=base，所有参数有有限上界。下一次 due 不越过执行 deadline；到 deadline 时保存到期关闭事实，不再开始 project。当前测试无需通用 jitter/策略插件。
- Schema、受信资格被撤销及不满足演示前态属于明确永久分类；临时 DB 不可用不能冒充永久业务失败。若连保存重试事实也失败，保留原持久责任，释放或等待租约接替后核对，仍受原绝对截止约束。
- 调用 context 取消/进程关闭不是“业务取消”。尽力通过有限短事务交回 Claim；无法确认则沿租约接替，不能直接记成功/永久失败。当前轮 context 截止、Claim lease、原工作执行 deadline 分开。

**完成修订不等于成功投影**：有限失败、到期或明确演示取消都需要保存绑定原 input_revision 的终止处理观察（种类、原因、策略/尝试依据）。`completed_revision` 表示该修订的处理责任已经以明确结果关闭，可在该事实同事务保存后推进；它不证明 hash 投影成功。只有成功处理观察带 `text_digest` 并推进成功投影的 input_revision；失败/取消不能伪造 hash 或抹掉先前真实成功观察。Host 观察必须同时区分“责任处理到哪一修订”和“成功投影到哪一修订”。Job 的 ready/leased/waiting/done 仍是工作状态，不新增假的 Task 终态。

若旧 Claim 关闭时已有更新 work_revision，记录旧结果后仍保留新责任 ready；不能把整个 Job done 或将新的等待/策略覆盖为旧值。已有新 revision 的预算/截止与旧完成严格隔离。

票 05 的“取消”用最小受信演示控制：准确对象 + 原输入修订的持久停止事实，重复同一控制幂等；不能取消猜测的未来所有修订。与完成竞争通过原 Claim/epoch/修订门禁，取消先胜则旧完成拒绝；成功先胜保留成功。后续显式新 record 形成新修订属于演示的新责任，不是 Task 复活。控制 seam 不修改固定 record 回执，不扩大公共方法清单。

## 5. lane、配额与可信配置

只有内部 `ordinary / control / reconciliation` 三个 lane。三者在本片都执行实际纯 project：标签来自可信策略，处理观察能验证准确 hash。control/reconciliation 名称只证明保留调度容量，不声称 Task 控制、外部核对、模型或财务服务已实现。

定义一个**当前同库调度池**：显式绑定同一个 PG DB/schema 集合或同一 SQLite 文件，列出允许的准确 OwnerRef/租户及每 lane 容量。跨 DB/跨设备全局配额不在本片范围。配额配置由 Host 启动/受信控制面解析校验并写入带 revision 的持久配置；所有 worker 在库中使用同一已生效版本，不接受每进程各自不同的 env 默认值。runtime/领域不自行读环境变量。

最小配置含 pool identity、成员范围、各 lane 并发上限/未结队列上限、每 tenant×lane 的并发配额、扫描 batch 上限、策略中的时间/尝试 bounds。control/reconciliation 的池并发与队列容量必须为正；普通池有单独有限容量。tenant 单 lane 为 0 可明确停其新启动，但不能删已有责任。小型验收可固定最多 64 个池成员、扫描 batch 1–64；实现不要构造无界全库候选列表。

pool 的协调计数/轮转是 runtime 调度事实，所属数据库集合及所有可调度成员必须由 Host 明确声明。可以在本库事务内协调这些共享容量及当前 owner 的 Job；这不授权读写其他 owner 的业务输入/结果，也不允许把不同 DB 偷放一个 Tx。现有 owner token 验证必须保留。实施者若选择独立 pool 协调行，应把这一声明范围写进 adapter 的存储职责，不能用任意 owner 绕过隔离。

领取限额以**有效 Claim 数**为准；PG 行锁/条件更新和 SQLite 单写事务必须真实保证它。持久配额预约与 Claim 同事务形成，释放/到期/取消也按同一绑定处理，不能只凭内存 semaphore。最简单可计算本 scope 内有效 Claim 计数；若使用计数器，必须处理崩溃和租约到期，不能产生永久漏槽。

池 worker 装配还应提供实际独立 lane 执行机会：普通 lane 全占用时，控制/核对仍有可运行 worker 槽，不能只有数据库标签而宿主用唯一 goroutine 卡在 ordinary 回调。单库短事务、有限连接等待及无长事务处理避免普通工作占满数据库连接阻断所有类别。

容量下调不回溯撤销已发生计算。最小规则：并发上限降至当前有效预约以下时配置更新明确拒绝，待 drain 后再改；队列上限可降低并形成现有超额积压，停止新增占位直到低于新上限，已有责任保留。任何配置变更都以准确 revision 条件应用，不默默让不同 worker 使用不同代。

## 6. 领取、执行入口和提交三处的检查

领取事务检查 due/state、owner/Job 绑定、当前 worker 允许的 owner/lane、有效配额和 Claim epoch，取得对应容量。不能先发 Claim 再异步扣容量。

实际处理入口在**开始 hash/fixture 处理前**再次检查：原 Claim 仍有效、epoch/claimed_revision 未变、未被演示取消、持久等待条件已满足、当前受信 worker 资格、原 deadline/尝试预算、有效 lane/tenant 预约。两次检查之间撤权、取消、改配额或租约到期，必须通过同步点让用例确实触发拒绝。合格处理才记录开始并消费 attempt。worker 资格是明确的受信 Host 操作员/worker allowlist，不是 record payload 或调用者任意 worker 字符串。

完成提交仍验证当前 Claim/epoch和停止门禁，才能写结果并交回容量。租约过期后旧进程即使仍在计算也不能提交。上述上限保证的是**受库约束的有效领取/启动资格**，不声称能强制杀死任意失联进程或把全部物理 CPU 工作精确限制在槽数内。project 是有限纯计算，ctx协作退出；后续外部目标仍需自己的门禁和未知效果协议。

等待、退避、永久关闭和显式取消释放有效预约。取消只关闭明确的原修订，pool reservation 的释放不能误释放其他 epoch 或新修订的 Claim。

## 7. 最小公平规则及可证明的界

选择每 pool×lane 的**持久公平轮转**，不实现通用优先级引擎：记录每个 tenant 的最近成功分配序号/轮转位置和就绪等待起点；考虑当前已获分配（配额 eligibility），从有可用额度且存在可领取工作的租户中轮转分配。相同轮转位置按最早就绪等待、稳定 tenant identity 排序。每次成功领取给该 tenant 写入递增分配序号，一次机会至多分配一个 Job，再开始下一机会；批量领取必须重复这一规则，不能给一个租户一口气拿走整批。

新加入/从无可领取工作变为可领取的 tenant 放到当前轮转尾部，不以归零计数持续插队。积累分配序号不会因进程重启清零。同 tenant 内按 due/等待起点/稳定 Job identity 有序取候选，扫描有上界且在竞争/跳过锁时推进游标；不能永远只看被锁住的第一页，使后面健康工作饥饿。

**验收界**：固定池成员数为 N（验收配置 N≤64），目标 tenant 持续满足 due、权限/预算和本 lane 空余额；其候选没有长期外部锁，数据库及 worker 健康并不断提供成功分配机会。在此有限竞争集内，目标 tenant 在最多 N 次该 lane 的成功轮转分配机会内取得一个 Claim。已有 Claim、等待配额、未到 due、被锁住或临时不可用期间不算“持续合格”；测试须明确这些前提，不能用它们掩盖实际健康 tenant 饥饿。

这个界是机会/轮次界，不是无条件墙钟 SLA。若没有任何槽释放，就没有成功机会；在另外声明处理/租约与扫描周期上界、时钟前进和服务可用后，才可推导时间上界。不能从 SKIP LOCKED 或运行若干秒没报错直接宣称公平。

Host 内部观察可暴露该调度合同的 lane、tenant、有效 Claim/额度、分配序号与等待事实；这是明示调度观察，不读取私有表或数私有函数调用。验收更要提交并独立读回健康对象的实际投影。ordinary 饱和与跨 tenant 竞争分别验证，避免一组带标签的空任务冒充两个不同保证。

## 8. 有限队列的准确接纳语义

队列容量统计未关闭的 Job 责任，包含 ready/leased/waiting/backoff，不只统计内存待发列表；closed/done 不占未结槽。容量校验与需要占位的新接纳共同事务，不能先回复 applied 后发现无法保存必要工作。

- 已有原命令先返回固定原决定，不受队列满或新配置影响。
- 同一已未结 Job 的新 revision 复用其一个队列位置，增加原 work_revision；不能因满额吞掉已提交的触发。
- 新对象/新 Job，或已 done Job 被新 record 重新触发，都会新增一个未结责任占位；若当前无额度，在修改输入/Job/receipt之前或同事务回滚后返回明确临时 Host backpressure/dependency_unavailable。没有固定新接纳决定，原身份可稍后重试；不能改成 budget_exhausted。
- 新命令已过期或业务前态不符仍按既有固定裁决处理，不能让“队列满”覆盖原键或永久前态判断。
- 任何已持久接纳的责任不得在队列缩容、进程内队列满或取消旧 Claim 时静默删除。活跃旧修订完成遇新修订，继续占有原未结位置，不先释放再丢新工作。

这与“新责任接纳前背压”和“不得静默忽略原 Job 新修订”一致：对 done Job 的新触发可以在接纳前明确背压，不能先接纳再忽略。

## 9. 两库验收与限制

05 最低共同 suite：无通知正常完成；未来 due 原 Claim 不产生且有未来唤醒；gate 未满足持久 waiting、其他工作/接纳仍能通过；推进 gate + 丢通知后到期继续；重开保持条件/attempt/due；有限 transient 后成功、永久拒绝、尝试耗尽、deadline 与明确取消均有正常对照；旧关闭不能覆盖新修订。使用 Host 观察和实际成功 hash，公共 command.get 原 applied/none 不变。

06 最低共同 suite：ordinary Claim 饱和但 control/reconciliation 实际 hash 可完成；两个以上 tenant 公平界；多 worker 竞争不能超有效 Claim 配额；领取后撤权/取消/到期以及正常允许处理的对照；等待释放槽；队列满新接纳原子背压、空出后原身份重试成功；满队列中的已未结 Job 新 revision 不丢；done Job 重触发正确占位；缩容保留已有责任；过期旧 worker 迟到完成拒绝且不释放新 epoch 的槽。

PostgreSQL 验证真实多连接/多 worker 的短事务锁序、并发容量与公平状态；SQLite 复用 02/04 实际跨进程单写排他范围，多个 worker 可以竞争同一受控 writer，但不能另开绕过协调的写 Host 冒称同一保证。重开后使用同一文件/库的真实状态验证，不以内存 fake 替代。需要的新等待/计数/公平列和索引创建真实向前迁移，不改已经发布的 v1/v2；07 原先 v1→v2 的独立升级范围和依赖不因此改为依赖06。

每个数据库记录当前配置、实际版本、有限时间、可信时钟来源、有限竞争假设与观察结果。PG正常使用数据库可信时间；SQLite使用单写owner可信时钟。测试控制时钟必须对参与同一竞争的进程一致，不能让各worker任意传 now抢 Claim。丢通知、取消、lease过期只证明本演示和本库资格，不能推导外部动作未发生。

不承诺跨库全局配额、任意故障下墙钟公平、进程物理终止、生产容量、真实授权/供应商账单或 Task 终态。本细化无需新ADR；正式05/06实施必须先等04/05各自退出，再由实施者以真实接口决定小端口、SQL和worker生命周期接法。

## 10. 并行迁移的整合约定

05 与07仍各只依赖04；06依赖05。并行工作树中的新迁移在整合前合并最新 integration，按已发布迁移之后的下一可用编号整合，必要时调整仅在该未发布分支新增的脚本编号及其新校验和。不得更改 integration 已发布脚本或 v1/v2 来源；调整后验证真实当前迁移和受影响升级。编号整合不是新增业务依赖，07不等待调度/配额行为作为验收前提。
