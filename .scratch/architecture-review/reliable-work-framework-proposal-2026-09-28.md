# 可靠接纳与持久工作框架：详细设计前的选择

状态：2026-09-28 用户已确认 Q1、Q2 均采用推荐项。本文保留选择依据；正式规则归[框架详细设计](../../docs/architecture/reliable-work.md)及[模块接入](../../docs/architecture/reliable-work.md#integration)，不声称已有运行实现。

## 1. 要解决的问题与已有边界

九个模块已经分别承担原命令接纳、持久工作、领取接替和事实归并。公共接口见[宿主装配](../../docs/architecture/deployment.md#4-默认宿主的装配与持久接口)，完整工作槽规则目前集中在 [Orchestrator 实现](../../docs/architecture/orchestrator/implementation.md#job-completion)。只让其他模块链接这一实现，仍须在各自代码中重复处理领取失效、新责任与旧完成竞争、提交后失答复等问题；但把业务成功和恢复判断一起抽取，又会改变现有保证。

此次补充的目标是统一可复用实现的契约和验收，让模块只补自己的业务键、事务参与者、处理步骤和完成条件。适用前提是所属 owner 能将业务记录、命令阶段和下一责任共同耐久提交；跨 owner 的步骤仍分别提交，并沿原命令恢复。

以下选择已有依据，无须重新设计：

| 已有约束 | 框架必须保持的含义 |
| --- | --- |
| 事实归各领域 owner，模块不等于服务 | 共用库可分别装入不同服务、数据库及工作池，不形成新的业务 owner 或调度服务 |
| 同提交域短事务；外部调用在事务外 | 框架不能包住模型、网络或设备调用重跑整个事务闭包 |
| 原 Command、业务对象与物理尝试分别有身份 | 重领和责任版本变化不能换原命令、重置尝试预算或推断效果未发生 |
| lease_epoch 与 work_revision 分别判断 | 前者约束本次领取，后者防止旧完成或旧退避覆盖新责任 |
| job 完成与领域成功独立 | 已持久交接责任可以结束本次 job；Task、Operation、发布或清理是否成功继续由领域规则裁决 |
| 已冻结公共协议允许独立实现替换 | 本轮框架属于参考宿主内部接口；不要求第三方采用相同表结构或公共运行库 |

## 2. 当前可独立决定的两个问题

### Q1：公共层提供到哪一层

**推荐提供可装配的接纳和有界工作模板。** 宿主共用实现负责原命令判重、事务结果分类、有限领取与调用槽、领取校验、责任槽回写以及观测断点；模块提供使用自己 repository 的事务步骤、外部 port 调用及恢复判断。领域可以先后执行多个短事务与外部步骤，框架不假设每项业务都只有一笔准备事务和一次调用。

竞争方案是只共用 transaction、command_store 和 job_store 原语，各模块继续实现自己的接纳和工作循环。它的公共接口更小，对模块改造较少；代价是领取失效、停止、提交未知等分支仍要在多个循环中实现并验收。推荐方案的代价由宿主维护者承担：需要定义清楚模板与领域回调的边界，并为特殊流程提供受约束的组合方式。若后续接入显示绝大多数模块无法复用工作循环，再收缩到原语，不增加大量按模块名称分支的通用模板。

模板只负责推动一次有限处理；是否发送、查询、等待、停止或重试由领域依据原事实决定。例如 Executor 准备后崩溃须先查询原操作，框架不得根据通用错误码自动再次调用驱动。

### Q2：工作存储统一到哪一层

**推荐统一逻辑 JobStore 契约，各提交域独立装配。** 共用领取、责任合并及条件回写算法，领域定义责任槽的业务键与关联；brain_job、execution_jobs 和其他模块记录由适配器承载。物理共表或分表不在本轮强制统一，继续按事务、隔离、访问路径与性能验收选择。

竞争方案是仅给出版本算法和测试，各模块独立实现工作存储接口。它允许模块更自由地组织持久记录，但难以让公共工作模板直接复用，领取和回写的一致性需要每个模块分别证明。推荐方案增加适配器接入成本，收益是同一组并发故障测试可覆盖全部适配器。不同存储无法兑现原子责任合并时，应拒绝宣称接入相同保证，不能把差异隐藏在适配器后。

两题相互独立：可以统一存储而保留模块自己的循环，也可以仅共享接纳模板、不共享具体工作循环。用户已确认两项均采用，正式设计按这一组合落实。

## 3. 推荐组合的职责划分

| 接口／参与者 | 共享实现承担 | 模块必须提供 |
| --- | --- | --- |
| transaction 与领域 repository | 固定提交域、短事务作用域、提交／冲突／提交未知分类；复用同一事务句柄 | 参与 repository、锁定顺序、当前资格、领域修订与业务约束；不得让插件取得任意表接口 |
| 原命令接纳模板 | 校验当前身份或方法规定的预认证依据后，按原服务、受信身份域与命令键判重，检查固定请求摘要及关闭索引；提交后才返回对应阶段 | 方法允许的回执阶段、准备记录、业务决定和下一责任；同步结束且无后续责任的命令不创建 job |
| job_store | 唯一责任槽、稳定槽键下的条件更新、责任版本递增与 due_at 提前、有限领取及条件结束／等待 | 是否新增责任、可否合并、需处理什么；责任槽业务键、关联原事实、到期依据及清理条件 |
| 有界工作模板 | 宿主生命周期、调用槽、领取与处理范围、停止信号、有限调度、通用观测 | 从原记录恢复当前阶段；调用领域 port；提交事实与下一责任；外部效果的安全重试判据 |
| 事实接收／归并入口 | 提供事务与幂等存储支持 | 原对象身份、可信来源、事实修订、单调性及终态约束；真实迟到事实独立于旧 worker 的领取资格接收 |
| 工作唤醒和恢复扫描 | 提交后可丢提示、到期有限扫描、未结责任审计 | 领域记录到责任槽的映射；补扫不能发明新的业务身份或替代正常责任共同提交 |

这里的“提交未知”只描述本地事务结果无法确认，不能自动转成外部 Effect=unknown 或 Task 失败。恢复仍查原命令或领域记录。事务闭包的重试也必须区分已确认回滚和无法确认提交。

原命令去重之外，领域仍检查业务身份唯一性。例如新 command_id 携带原 operation_id，不能建立第二项操作或绕过原决定。共同模板也不能按方法名称推断回执阶段：accepted、applied、rejected 的适用范围与成功含义继续由方法登记和领域规则决定。

接纳请求、持久工作和物理调用使用各自生命周期。已接纳工作不继承已断开请求的 context；发出停止信号不证明本地调用实际退出，释放调用槽前须观察退出。工作池继续为控制、撤权、收尾及清理保留容量；扩展宿主的最小诊断／停用入口不依赖尚未就绪的受管组件队列。

工作存储需暴露的逻辑操作包括：事务内合并责任、独立短事务领取、在领域提交事务内检查领取并结束／等待，以及有限扫描。确认后的内部接口、返回值和句柄约束见[正式接口](../../docs/architecture/reliable-work.md#interfaces)。

## 4. 各模块的接入位置与保留规则

| 模块与现有入口 | 接入的持久责任 | 必须留在模块内的裁决与例外 |
| --- | --- | --- |
| [Orchestrator](../../docs/architecture/orchestrator/implementation.md)：CommandHandler、TaskCoordinator、JobRunner | decide、dispatch、poll、verify、control、settle 等责任槽；任务／预算／意图／回执共同提交 | 祖先控制、行动准入、预算与条件核验；JobRunner 保留领域派发逻辑，完成 job 不等于完成 Task |
| [Brain](../../docs/architecture/brain/implementation.md)：DecisionStore、RecoveryWorker | 原 Decision 接纳、ModelCall 准备、发送门禁、产出保存和费用交回 | prepared 且无 send_started 的首次发送条件；已可能发送后的原调用查询、未知费用与能力分级；恢复产出不能重跑模型 |
| [Executor](../../docs/architecture/execution/implementation.md)：接纳、发送门禁与效果归并 | 原 Operation、attempt、查询／控制／费用交回工作 | 准备后崩溃按可能已发送核对；TaskGate、资源 control_epoch、实际入口隔离及驱动核对继续独立于 job lease_epoch |
| [Memory／内容](../../docs/architecture/memory/implementation.md)：MemoryWriter、MetadataStore 和各 Worker | 索引、提取、视图、关闭、reference_intent 与 copy_control_jobs | owner 变化序列、来源／copy 门禁、准确字节先耐久；跨库准备责任提交不等于 memory.create 已 applied；临时查询集合不变为持久业务队列 |
| [权限与隔离](../../docs/architecture/security/implementation.md)：GrantLedger、LeaseLedger、PairingController、RevocationWorker | 使用消费、撤销传播、结算及凭据相关责任 | 确认一次消费、祖先 Grant、额度与用途窗口；配对批准前在独立预认证会话域中处理，不能伪造已认证 tenant 来套业务模板 |
| [Agent 协作](../../docs/architecture/collaboration/implementation.md)：映射、创建及关闭用例 | 内部委派共同提交；外部原创建／查询／取消／结算责任 | 内部子任务共享父 Orchestrator 事务；外部接受未知不得创建第二个子任务；子任务结果、费用和关闭事实分别判断 |
| [应用与交互](../../docs/architecture/interaction/implementation.md)：交付、输入与应用消费 | 输入／应用事件转交、固定业务回执归并与呈现更新；原 Delivery 的传输责任仍归传输契约 | 业务消费和 Confirmation 一次消费仍归实际 consumer owner；消息送达、呈现和消费各有依据；查询分页及可丢 Change 提示不套持久命令接纳 |
| [扩展与宿主](../../docs/architecture/extensions/implementation.md)：安装、激活、恢复和实例管理 | 原安装／激活／迁移阶段及恢复责任 | 精确安装锁、当前批准、实例启动依据、探测与回退；活动指针不能证明当前进程已就绪 |
| [观测评测与改进](../../docs/architecture/evaluation/implementation.md)：RunCoordinator、ExposureLedger、ApprovalOwner、RolloutWorker／ReportSealer | 样本运行、取消、封存、暴露影响分页、批准／使用相关事实与工作 | 固定分母、尝试计数、原暴露门禁和批准状态；feedback_open、approval_check 等按实际持久语义接入，不凭名称当只读 |

统一依据是调用的事实与责任，不是方法名。例如某个 check 会产生使用资格记录，仍须领域事务；真正只读或可在短事务内终结的调用不承担额外异步排队成本。完整 Command／Query 分类与回执阶段沿用[共同契约](../../docs/architecture/contracts/README.md#2-标识命令和查询)及已有方法登记。

## 5. 已推演的关键反例

| 场景 | 框架必须保证 | 领域仍须回答 |
| --- | --- | --- |
| 接纳提交后答复丢失 | 原身份重投只查原阶段／决定；业务与后续责任不分离 | 哪个阶段代表方法已完成，尚未完成时继续哪项责任 |
| W1 过期后 W2 接替，W1 再返回 | 拒绝 W1 对受领取保护的业务与槽回写；不能靠责任版本相同恢复资格 | 真正的远端事实可由独立认证归并入口接收，不能丢弃已发生费用或效果 |
| W1 持有效领取时新责任 r+1 提交 | 新版本与提前 due_at 共同提交；旧 done／backoff 保留最新可领取责任 | 旧结果是否仍是可采用的原事实；新责任需要处理哪些对象 |
| 已向远端发送但结果未知 | 保留原工作及身份；接替和超时不触发无条件重发 | 原目标如何查询、何时有安全重试证据、未知期间保留哪些占用与费用 |
| Memory 已登记远端 copy，但本地未发布 | 准备与恢复责任先耐久，原命令继续可定位；不提前报告 applied | 继续发布的资格，关闭先到时如何拒绝并清理原持有关系 |
| 终态后有更高可信费用 | 原账务责任可随领域事务重开，版本与尝试预算不重置 | 累计差额与原计费来源的唯一性，禁止重开任务目标或使用资格 |

完整并发判定已有[责任槽实验](../../docs/architecture/validation/fault-experiments.md#job-merge)依据。本轮将补充可复用测试入口、故障屏障、各模块适配实例及所需观测事实，而不是仅列通用错误名称。
