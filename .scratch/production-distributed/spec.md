沿用已确认的 Go、端云统一 WSS、服务间 gRPC、同进程 Go interface。保留固定 Task Home、领域 owner、原命令恢复、未知效果核对和最小关闭身份；进程拆分不等于数据库提交域拆分。规模目标已有千万注册、百万日活、十万在线，不向用户重复索取。具体 TPS、连接倍率和恢复参数属于待验收假设。

用户已回复“接受建议”，确认以下生产、容灾和托管边界；本轮进入正文、契约与验证资产联动修订。

## 已采用的中间件收敛方向

以 PostgreSQL 承担每个稳定分区的业务事实、命令去重及持久工作责任，对象存储承担不可变正文和制品；连接入口与工作池从首个生产版本分别伸缩。多个租户共享经过测量的分区，避免每租户一库或每模块一套中间件。

先推演有界、带索引、按分区和工作类别批量领取的数据库 jobs；独立消息系统必须证明能够减少当前瓶颈及总体维护成本。Redis、Kafka、独立搜索／向量库和额外协调集群不因“海量用户”直接成为默认依赖，也不预先排除；正式选型须列出何时引入、停机时哪些功能可继续、权威数据是否保持唯一。

连接池优先复用经过验证的托管能力；需要独立 PgBouncer 时说明其部署可用性、连接预算及事务模式限制。服务发现复用既有平台和受信逻辑服务映射，避免另建一套业务注册中心。

并行审查对消息层给出两种竞争建议：保留 PostgreSQL jobs 加有界唤醒，或者加入成熟消息中间件承接跨实例通知及调度唤醒。最终选择须比较本项目需要自行维护的机制、吞吐及故障依赖；“没有中间件”和“少自研调度”都不能单独证明总体更简单。若采用 NATS／Redis，另核对其与已确认服务间 gRPC 边界的关系，消息不能替代领域调用的认证及接纳合同。

连接恢复的最小推荐为保留现有 EndpointChannel 外壳并增加内部受控重绑。网关拥有外部 connection_id，内部绑定另有身份；内部 Ready 不重复转发到客户端，旧流输出被隔离，在途原业务仍查询和核对。订阅只有证明连续才继续，否则发准确缺口；现有 snapshot_required 原因可能需要扩展。竞争方案是短 RPC 加独立推送路径，独立伸缩更彻底，但新增路由及推送契约，须证明收益。

## 官方依据核查

- [PostgreSQL LISTEN](https://www.postgresql.org/docs/18/sql-listen.html)：监听属于会话，断连清除；恢复必须先建立监听再扫描当前数据。由此不能把通知当持久队列。
- [PostgreSQL NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html)：通知队列耗尽会使含 NOTIFY 的事务在提交时失败。若选择它作可丢唤醒，应把业务提交与通知失败边界分开，并保留有界补扫。
- [PgBouncer 功能表](https://www.pgbouncer.org/features.html)：事务池不支持 LISTEN 和会话级锁；相关路径需独立会话或采用不依赖这些能力的机制。
- [Kubernetes 终止流程](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)与[端点终止](https://kubernetes.io/docs/tutorials/services/pods-and-endpoint-termination-flow/)：摘除新流量和完成旧连接是不同步骤；强制终止前有有限宽限期。不能把 readiness=false 等同于已有连接已经迁走。
- [PostgreSQL 日常清理](https://www.postgresql.org/docs/18/routine-vacuuming.html)：频繁更新的工作表必须计入 vacuum、索引和 IO 成本。

## 计划交付与验证

主线统一修改 README、technical-overview、deployment、decisions 与建设顺序；生产详设给出拓扑、数据边界、跨实例投递、实例恢复、发布与故障影响。中间件选择和数据布局可独立成专题，由总览连续链接。连接规则改变时，联动 gRPC／WSS 契约、Schema、示例及检查器；不能只改部署章节。

语义审查至少覆盖：提交后断线、工作者退出但旧发送继续、内部流重建、网关重启、全区故障、数据库切换、通知丢失、内容引用与 GC 并发、迁移中断和集中恢复。图示另做渲染审阅，链接与协议静态检查单独记录；没有实际服务和压测，不报告线上性能或可用性已达标。
