阅读路径：完整任务经过 → 模块职责与核心数据 → 各模块处理和恢复 → 共同契约、存储与部署 → 验收。总览已按用户选定的完整报告任务组织，九模块、专题、契约及验收索引已完成整合。

## 写作要求

每章先给读者能够推演的场景或问题，再解释选择、必要概念与正常链，随后展开字段、事务及异常。一个段落推进一个明确问题；表格用于同形记录、约束或状态，时序图用于交接和提交点，关系图须明确箭头及多重性含义。

写作者维护简短写作记录，注明开篇候选、选定路径、章节前置概念和首次引入概念。按已授权方式自主选择后续段落；每次写入前读取当前文件，保留其他人的修改。不要一次性铺开未解释的专有名词，也不要用泛化禁令替代可执行机制。

重要对象应具备身份范围、必要字段、关联及多重性、准确版本、不可变约束、写入负责方、状态迁移、持久提交和清理条件。重要流程应能对应到接口、读写记录、共同提交、后续责任、未知时查询及恢复、验收。

明确公共契约、默认参考实现、参数冻结条件和按需扩展。字段编码及必填性归同版 Schema，业务含义归所属模块。内部记录与响应投影不默认一一映射到物理表。确有缺项时补可落地映射；关键索引与事务条件要明确，容量优化和实际执行计划保留测量边界。

## 已识别问题与必须解决的整合项

1. Brain 的 request_input 提案表曾称持久 InputRequest 由交互创建；统一为实际业务负责方创建，任务澄清由原 Orchestrator 保存和消费，交互读取与转交。
2. Session、Message、完整原提交命令、待交付 outbox 和任务关联已有行为与恢复规则，交互 implementation 的记录目录须补完整承载、唯一约束和恢复映射。
3. ApprovalLease 的固定窗口、实例资格与持久分配应明确存放位置及约束，保持现行合同，不凭命名增加独立服务或表。
4. 命令、Job、租约、工作版本的通用规则收拢到公共框架，各模块保留其真实发送、效果和费用差异。
5. 核心数据、场景、模块详设、Schema、存储与用例建立逐项定位；所有正式本地链接和锚点应有效，正文不依赖 `.draft` 才能获得规范。
6. 原正文及研究中的默认路径、按需能力、未冻结的 G-01～05 等合同差异继续准确标识；不能为了“全文完整”承诺原本未设计的公共能力。
7. 更新 CONTEXT.md、相关 ADR 与有效导航到正式定义；研究和历史材料保持其日期及适用范围。
