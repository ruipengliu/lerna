# 未来与周期触发的应用调度边界

[任务推进](README.md) · [公共工作框架](../reliable-work.md#capacity) · [参考语义差异](../../research/agent-harness-comparison/core-model-semantic-coverage.md#sm-11)

Schedule 只在用户需要管理“未来何时发起什么工作”时启用，由宿主应用的调度能力保存；它不是 Task 的另一个状态，也不归 JobStore 裁决。一个 Schedule 可产生多个 Task，单个 Task 的结束不结束周期规则。本页给出可选能力的最小设计合同，尚无公共 Schedule 方法、Schema、运行 scheduler 或恢复实测。

## 1. 规则、触发与任务分别保存

| 记录／负责方 | 最小语义与生命周期 |
| --- | --- |
| Schedule／应用调度 owner | 稳定身份、规则修订、受信创建依据、准确输入模板与配置、时区、启停、有效期、错过及重叠策略；查询可区分下一计划时刻、已记录触发和交付缺口 |
| occurrence／同一调度 owner | 一次逻辑触发，固定 Schedule 及规则修订、规范计划时刻和必要的重复时间区分；保存原命令、准确载荷、发现选定的目标、接纳与交付责任，重领和重启不另造一次触发 |
| Task 或原输入／原业务 owner | 按既有方法接纳和去重；Task 拥有自己的目标、控制、期限、预算及完成依据。调度端保存关联，不写 Task 状态或代替输入消费 |
| Job／调度 owner 的本地 JobStore | 有限扫描、到期判定及原 occurrence 交付的处理责任；due_at 只是下次处理时刻，不替代用户时间规则 |

规则编辑按期望修订串行裁决。每个 occurrence 在生成时固定模板和配置，时间规则、模板和配置的编辑只影响尚未生成的触发；不能用新的目标正文覆盖一个答复未知的旧命令。停用与删除另按第 3 节封闭未发送触发。规则版本、时区和夏令时重复／缺失时刻的解释均可追溯，不能以 worker 本机时区解释同一规则。

启用配置必须选定错过触发时跳过还是有限补发、补发窗口与数量上限，以及前次任务未结束时跳过还是有界排队。首个实现宜采用跳过错过时刻、同一规则最多一个活动目标；更强并发须独立声明。不能恢复后无限补发，不能因领取失败重算出第二个同义 occurrence。

## 2. 从到期到接纳

1. 调度 owner 在短事务中核对当前规则修订、启用状态和时间策略，唯一地生成 occurrence，并保存准确输入、原命令及交付责任。新 Task 的目标选择遵守[固定路由](../../adr/0004-discovery-fixed-task-routing.md)：首次发送前固定原逻辑 Orchestrator，重试不跟随发现映射改投。
2. 发送前检查规则是否已阻止该项交付、输入当前来源与用途、准确配置、额度和期限。Schedule 存在只证明规则获准保存；执行所需 Grant 和真实入口的当前检查继续成立，不能从历史确认取得永久执行许可。
3. 交付者按固定命令调用原业务入口。答复丢失沿原命令查询；只有接收端持久接纳才能显示“任务已接纳”。查询不到但仍可能接纳时保留未知，不换 command_id 创建另一个 Task。
4. 接纳结果与 Task／输入关联在调度端共同保存。接收端与调度端不共享事务时，允许先接纳、后补关联；原 occurrence 的交付记录负责恢复这个间隙。Job 完成只证明本项交接已收束，不证明 Task 成功。

触发既有 Task 时必须明确业务含义：回答已存在的 InputRequest 可使用现有准确请求／修订合同，恢复目标沿原控制入口。任意聊天消息的 steering／follow-up 不属于现有输入合同，相关 Session 调度能力未交付时不能用一个自由文本定时消息冒充可消费输入。

## 3. 停用、取消与恢复

停用或删除规则先持久封闭新 occurrence，并阻止尚可证明未交给业务入口的触发继续发送。规则变更与发送准备在调度 owner 的相同裁决边界检查；已进入可能发送阶段的触发保留原查询责任，界面显示仍可能已经接纳。不能承诺停用与远端接纳跨库原子发生。

已接纳 Task 的取消另走原 Task 控制并核验适用权限；关闭 Schedule 不批量改写这些 Task。用户明确要求停止已发起工作时，调度端保存逐项原控制命令及未确认范围。未接纳项、接纳未知项和已接纳项分别报告，不能只返回“定时已关闭”掩盖在途工作。

恢复依据是规则、occurrence、原命令与回执。触发期限或授权已过时不开始新工作；已经可能发出的旧命令仍核对原接纳结果。原路由、接收记录或当前许可不可取得时保留缺口，不能移动到其他 Orchestrator 重建。正文清理不删除仍用于去重、取消或未决交付的最小关联，沿[长期保留决策](../../adr/0001-retain-closed-identities.md)处理。

## 4. 启用与验收

开放前须落实受信规则管理、规则修订与 occurrence 的唯一提交、准确时区语义、有限错过／重叠策略、当前权限、固定路由及原回执恢复。完整公共能力另行提交方法登记、Schema、示例与互操作检查，普通问答不承担这些记录或扫描。

主验收仍通过应用／SDK 观察：相同到期事件重复交付只产生一个已接纳目标；业务接纳后丢答复仍恢复原关联；规则编辑不改变旧目标；停用与发送竞争报告实际在途范围；暂停的 Task 不因时钟到期越权恢复；冷恢复和夏令时变化不会无限补发。上述为待运行场景，现有 JobStore 故障向量只能证明公共机制，不能代替调度行为验收。
