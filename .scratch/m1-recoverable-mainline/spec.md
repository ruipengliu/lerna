# M1 可恢复主线

Status: resolved

- 上游：项目目标第 11 节 M1 一行、分层与模块第 9 节"M1 最小切片"、各模块设计文档的"9 M1 范围"、ADR 0001（本地档）、ADR 0004（Go、Protobuf、SQLite）、开发规范
- 术语以项目目标第 3 节为准；规则编号（G、R、V、C）以项目目标和分层与模块为准；门禁条件编号（准入-n、开始-n、完成-n）以核心契约 2.6 为准

## 问题陈述

Lerna 目前只有设计文档，没有任何代码。设计的核心承诺是可靠性契约：结果未知不等于未发生（G1），完成需要证据（G2），先持久再确认（G3），先准入再执行（G4），出口全覆盖（G5），提议与裁决分离（G6），责任不随故障转移（G11）。这些不变量很难事后补回，所以第一个里程碑必须先做出一条**在故障下仍能正确恢复的主线**，而不是一个只在正常路径上跑通的 Agent 循环。

从使用者的角度，问题是：今天无法让一个 Agent 去调用 API 或写文件，并且相信它在超时、崩溃、回执丢失、取消竞争和迟到生效时既不重复执行，也不谎报成功。从开发者的角度，问题是：没有一个可运行的参考实现和一套可重复的故障测试，来证明设计成立，也没有骨架让后续里程碑在其上扩展。

## 解决方案

交付 M1 参考实现：一个单用户、单进程、用 SQLite 持久化（本地档）的 Lerna，打通"目标 → 提议 → 准入 → 执行 → 效果 → 核对 → 完成"主线。

- 用户通过命令行输入目标、确认授权、取消任务、查看任务状态、结果和遗留的未知效果。
- 默认推理经出口闸门调用模型，给出提议；核心裁决是否执行、是否完成。
- 执行适配器有三种：API、文件（受管理的本机目录），以及可注入故障的模拟 API（幂等、可查询、不可查询三类）。
- 所有出口（模型调用、API、文件）经出口闸门；每次实际发送之前，持久记录里已写明依据的条件版本、授权和预算。
- 虽然是单进程，事务域边界和跨域交接（R7 三步）按正式设计实现，不因同进程省略持久回执。
- 一套故障注入测试在每个持久化点前后注入崩溃和回执丢失，用持久记录和模拟目标实际收到的调用次数判定 V3 的故障行为部分和 V4（单进程和进程重启范围）达到 L2。

M1 只用于受控测试：使用合成数据，不接触真实个人数据，不开放第三方扩展，只运行经过审查的参考实现。M1 推迟的治理能力通过"不开放对应功能"来保证相关不变量不被违反，相关接口返回明确的"不支持"。

## 用户故事

### 输入、会话与任务

1. 作为用户，我想在命令行输入一个目标，以便 Lerna 为它创建任务并开始工作。
2. 作为用户，我想在提交目标时网络或进程出问题后重试同一命令，以便不会因此创建两个任务。
3. 作为用户，我想在输入已保存但任务尚未建立时进程崩溃，恢复后只看到一个任务，以便输入不丢失也不重复。
4. 作为用户，我想创建一个暂不关联任务的会话，以便先聊清楚再决定做什么。
5. 作为用户，我想在一个会话中先后发起多个任务，以便不必每次都新开会话。
6. 作为用户，我想在任务运行时修改目标或回答 Lerna 的问题，以便它基于最新信息继续。
7. 作为用户，我想在修改被接纳后，基于旧上下文的提议无法再执行，以便 Lerna 不按过时的理解行动。
8. 作为用户，我想用任务模板或显式条件列表说明"做到什么算完成"，以便完成判定有明确依据。
9. 作为用户，我想在目标超出模板时被请求澄清，以便不会由模型自行发明完成条件。
10. 作为用户，我想随时查看会话、任务的当前阶段和全量快照，以便知道它在做什么、在等什么。
11. 作为用户，我想在任务关闭后会话仍然保留，以便继续追问或发起新任务。
12. 作为用户，我想在请求分支或编辑历史时得到明确的"不支持"，以便知道 M1 的边界，而不是被静默覆盖。

### 授权与确认

13. 作为用户，我想对一个具体动作给出单次授权，以便只批准这一次执行。
14. 作为用户，我想给出有明确主体、资源、动作、范围和期限的持续授权，以便重复的低风险操作不必每次确认。
15. 作为用户，我想确认的内容是核心生成的动作描述，以便我确认的就是实际要执行的。
16. 作为用户，我想在动作参数改变后旧确认自动失效，以便确认不会被套用到不同的动作上。
17. 作为用户，我想确认回执丢失后重试，确认只被消费一次，以便不会因重试而多执行。
18. 作为用户，我想撤销一项授权后，依赖它的新准入立即被拒绝，以便撤销立即有效。
19. 作为用户，我想查询撤销的处理进度，以便知道已在进行中的出口是否已经停下。
20. 作为用户，我想在请求委派、组合授权或"读取自动包含保存"这类 M1 未实现的能力时被拒绝，以便权限不被暗中放宽。

### 推理与模型调用

21. 作为用户，我想 Lerna 用默认推理根据目标、条件和进展给出下一步提议，以便任务能自动推进。
22. 作为用户，我想推理的输出只是提议，是否执行由核心裁决，以便模型不能绕过授权和预算直接行动（G6）。
23. 作为用户，我想每次模型调用在发出前都经过准入和预算预留，以便模型费用也受控（G4、G5）。
24. 作为用户，我想推理进程崩溃后，重新运行时同一调用位置拿回原结果而不是再发一次，以便不重复计费。
25. 作为用户，我想模型调用超时后，原调用的未知状态和费用继续被核对，即使推理已重新请求，以便费用不会凭空消失。
26. 作为用户，我想在调用描述无法重现时得到"准备不可恢复"，由核心决定是否重新开始，以便已准入的载荷不被篡改。
27. 作为用户，我想推理不做隐式的自动重试、降级或模型回退，以便实际发送次数可预期。

### 执行：API 与文件

28. 作为用户，我想让 Lerna 调用一个按固定版本能力描述接入的 API，以便完成工具类任务（V3）。
29. 作为用户，我想 API 请求用确定性的参数编译和固定的幂等键，以便安全重发时目标能识别为同一请求。
30. 作为用户，我想 API 凭据以引用加受控注入的方式使用，以便推理和适配器看不到真实密钥。
31. 作为用户，我想遇到 429 时 Lerna 持久地等待并区分限流类别，而不是立即重发，以便不放大故障。
32. 作为用户，我想让 Lerna 读取受管理目录中的文件，以便基于文件内容工作。
33. 作为用户，我想让 Lerna 创建或替换受管理目录中的单个文件，并用版本检查防止覆盖他人修改，以便写入安全。
34. 作为用户，我想文件写入后被读回核验，以便"写成功"有证据。
35. 作为用户，我想追加写入和任意覆盖不被默认当作幂等，以便不会因重试而重复追加。
36. 作为用户，我想临时文件和中间资源被跟踪，以便失败后能找到并清理。

### 结果未知、核对与重发

37. 作为用户，我想一个结果无法确定的动作被明确标为"未知"，而不是失败或成功，以便我知道真实情况（G1）。
38. 作为用户，我想可查询的目标在结果未知时被核对，按证据确定效果，以便不靠猜测。
39. 作为用户，我想只有在确认未生效且原请求不会再迟到生效，或目标对同一尝试标识保证幂等时才重发，以便不重复扣款或重复写入。
40. 作为用户，我想既不可查询也不幂等的动作超时后一直保持"未知"并展示出来，以便我自己去核实，而不是被自动重试。
41. 作为用户，我想迟到生效的结果仍归原动作，以便不会被记成另一个新动作。
42. 作为用户，我想核对有持久调度、退避和上限，可以暂停和恢复，以便核对本身不失控。
43. 作为用户，我想超时、取消或进程替换都不会把一项动作改派给别的执行端点或改写成新任务，以便未知状态不被规避（G11）。

### 取消与竞争

44. 作为用户，我想取消任务后新的准入立即停止，以便 Lerna 不再开始新动作。
45. 作为用户，我想已准入但尚未发出的动作被封闭，以便取消真正阻止了它们。
46. 作为用户，我想取消与动作发出竞争时，界面准确显示已保存的控制和该动作的未知效果，以便不被误导为"已全部停止"。
47. 作为用户，我想取消后迟到的效果和费用仍被接纳和展示，以便账目完整（G10）。

### 完成与结果

48. 作为用户，我想任务只有在全部条件有证据、全部动作已收尾、本轮核验通过时才标记成功，以便"成功"可信（G2）。
49. 作为用户，我想完成核验被拒绝时看到具体缺口，Lerna 按缺口重新规划，以便任务继续推进而不是假装完成。
50. 作为用户，我想 Result 一旦固定就不再改变，并列出核验了什么，以便结果可审计。
51. 作为用户，我想任务可以非成功关闭并列出遗留的未知项，以便我知道哪些还需要人工核实。
52. 作为用户，我想关闭后补来的账单、动作结果仍可查，而 Result 不变，以便事后追溯。

### 预算与费用

53. 作为用户，我想为用户和当前任务设定明确的费用上限，以便控制花费。
54. 作为用户，我想每次调用按费用上界预留，用量回报后结清、释放未用部分，以便额度准确。
55. 作为用户，我想费用上界未知的调用不被准入，以便不会产生不可控费用。

58. 作为用户，我想迟到的账单被接纳并显示超支，以便看到真实花费。

### 持久性与恢复

59. 作为用户，我想 Lerna 在确认接下一项责任前已把记录写到本地档要求的持久程度，以便进程崩溃、重启或掉电后不丢责任（G3）。

## 实现决定

### 技术与部署

- Go 单一模块；公共契约用 Protobuf，buf 管理检查与生成；存储用 SQLite，满足本地档（ADR 0004、ADR 0001）。
- M1 以单进程运行：一个宿主程序装配全部核心模块、默认推理、三种执行适配器和命令行交互适配器。命令行与宿主之间为本地绑定，不实现网关。
- 事务域保持正式边界：裁决域（任务编排、会话、授权、预算在同一事务）、执行管理、内容治理、运行记录各为独立事务域。同一 SQLite 文件中也不得跨域共用事务写对方的私有记录；跨域交接一律按 R7 三步，回执丢失时查询原交接。
- 持久工作采用"自建有限模板"：命令回执、事务参与、待办工作（原子领取、有界租约、续租、领取代次、工作修订号）、接替 fencing。不引入通用工作流引擎，不扩展成通用重放框架。

### 模块与深度

按分层与模块第 9 节，摘要如下（各模块"9 M1 范围"为准）：

| 模块 | M1 做到 | 明确返回"不支持" |
| --- | --- | --- |
| 核心契约 | M1 涉及对象的完整 Protobuf 定义；四道门禁按核心契约 2.6 的编号条件实现 | — |
| 持久工作 | 语义完整，单一事务后端 | — |
| 任务编排 | 单用户；完整准入与完成门禁；有限计划长度 1、参数只允许具体值 | 子任务、外部 Agent 委派 |
| 会话 | 输入、确认、任务关联、持久回执与恢复 | 分支与历史编辑 |
| 授权 | 单次与持续授权、准入检查、不透明出口凭据、同域撤销；操作权利与处理目的两字段保留，处理目的只用"当前任务"，未知值拒绝 | 委派、组合多个来源、只读检索凭据 |
| 预算 | 单次费用上界的最小预留与结清；未知费用保留；迟到费用接纳 | 多维额度、退款、更正 |
| 执行管理 | 完整：接纳、尝试、三态效果、迟到可能性、核对、收尾依据、取消竞争 | — |
| 内容治理 | 来源、版本、派生关系；一个可信参考正文后端 | 删除、用途限制、记忆 |
| 运行记录 | 基础关联、按任务或动作查询、积压与缺口显示；OpenTelemetry 只定映射边界 | 外部上传、正文留存 |
| 出口闸门 | 覆盖模型、API、文件和辅助调用；P1–P8；禁用隐式重试与回退 | 设备、子进程出口；插件沙箱 |
| 推理 | 最简默认实现：每个提议请求最多一个调用位置，实际发送上限默认 1；确定性选择和裁剪，不做模型摘要 | 多次调用策略 |
| 记忆策略 | 不做 | 全部 |
| 执行适配器 | API、文件、模拟 API | GUI、外部 Agent |
| 交互适配器 | 命令行：目标、会话与任务查看、确认、取消、结果与未知效果 | 接管与交还 |
| 平台服务 | 不做 | 全部 |

### 关键接口与契约

- 交互适配器只通过公共契约命令与核心交互；每条命令带 `CommandIdentity`。同标识同内容返回原决定，同标识不同内容拒绝；"提交结果未知"必须可用原标识查询。
- 推理接口：核心登记提议请求和快照；推理每次模型调用由受信宿主封存完整调用描述后提交准入；"提议请求 + 调用位置"标识一次模型调用；同位置同描述返回原结果，同位置不同描述报冲突。
- 执行适配器必须声明效果、幂等、可查询等能力属性；执行管理只按声明和证据决定核对或安全重发。适配器只回报，不写效果（R3）。
- 出口闸门在实际 I/O 前执行开始门禁（P4，占用本次发送额度），在 P5 持久写下"可能已发出"之后才发送；没有 P5 持久化成功不得执行外部 I/O。
- 错误按核心契约 3.2 分类返回，不吞掉"提交结果未知""效果未知"。
- 所有持久记录和接口带用户范围；M1 只运行一个用户，错误身份被拒绝。

### 可测试性所需的结构（已确认的测试切面）

- **主切面：进程内装配。**用真实核心、SQLite、脚本化推理、模拟 API 和模拟模型供应商装配一个 harness。测试只通过公共契约命令驱动（提交目标、确认、取消、查询），断言持久记录和模拟目标实际收到的调用次数。生产宿主与测试 harness 共用同一装配代码，只替换推理和出口目标。
- **辅助切面一：持久化点崩溃钩子。**每个持久化点（出口的 P1–P8，各模块的持久点 n，以及 R7 交接的三步之间）提供命名的故障注入点，可配置为"提交前崩溃""提交后、回执前崩溃""回执丢失"。钩子只在故障构建标签下编译进来；生产构建不包含。崩溃后 harness 从同一 SQLite 文件重启。
- **辅助切面二：脚本化推理。**实现推理的公共接口，按脚本返回确定的提议和模型调用；它同样经过准入和出口闸门，模型请求发往模拟供应商。
- 模拟 API 与模拟模型供应商独立于被测进程的记录，崩溃后仍能报告真实的调用次数、请求标识和生效时间。

## 测试决定

- **好测试的标准：**只测外部行为。驱动用公共契约命令，判据是持久记录（任务、动作、尝试、效果、回执、预算、轨迹）和模拟目标实际收到的调用次数，不看函数返回值或内部状态。测试先行，先写会失败的测试。
- **规则标注：**每个测试函数上方用一行注释写明验证的规则，例如 `// 规则：G1、开始-2`。涉及出口、授权、预算或持久记录的包，每个包至少一个带标注的测试，`make check` 检查。
- **测试分层：**
  - 单元测试：与代码同目录，覆盖门禁条件、状态转换、能力声明解析等纯逻辑。
  - 一致性测试：持久工作的语义测试（同一事务后端接口）、执行适配器共同接口测试（API、文件、模拟 API 跑同一套用例）。
  - 故障注入测试：经主切面加辅助切面一，单独的构建标签和 `make test-fault`。
- **必须覆盖的故障矩阵（V4 单进程与进程重启范围）：**每个持久化点前后崩溃；准入、确认、交接、用量回报的回执丢失；取消与发送竞争（P4 前、P4 与 P5 之间、P5 之后）；迟到生效；不可查询且不幂等的超时；完成核验被拒绝后继续；推理崩溃后按调用位置恢复；旧工作者被接替后的写入被拒绝。
- **V3 的故障行为（模拟 API 上）：**幂等、可查询、不可查询三类各自在结果未知时的正确策略：不盲目重发；可查询的按证据核对；幂等的按原标识安全重发；都不满足的保持未知。
- **模块退出证据：**以各模块"9 M1 范围"列出的最低退出标准为验收清单，例如交互适配器的五项最小演示、会话的六项最低标准、执行管理的退出标准。
- **持久性：**在一个开发平台组合上验证本地档，包含掉电或等价的存储故障模型，结果列入平台准入表。
- **已有先例：**仓库尚无代码和测试。测试形式以设计文档中的测试要点为准：流程模型调用的"同一条执行历史"串联测试、各模块第 10 节的测试表。

## 不在范围内

- 记忆策略、只读检索凭据（R4 直连）、内容删除与用途限制、完整操作权利与处理目的（M2）。
- 多维额度、退款、更正、费用对账（M2）。
- 端侧部署、离线继续、重连核对、网关与 SDK、混合版本协商（M3）。
- 子任务、外部 Agent 适配器、扩展 SDK、插件沙箱、第二种可替换实现；GUI 适配器与用户接管（M4，可选）。
- 评测与自进化（M5）。
- 多用户隔离验证、容量、云端生产档、PostgreSQL 后端（M6；M1 只实现一个事务后端）。
- V1 联网问答、V3 的正确率与 API 覆盖规模统计；M1 不以"已接入多少 API 描述"宣称达成 10.1 的 API 指标。
- TypeScript SDK 和浏览器界面（M3 起）。
- 真实个人数据、第三方扩展、外部诊断上传。

## 补充说明

- **建议的实现顺序**（依赖关系，供拆工单参考）：骨架与工具链（Makefile、lint、buf）→ 核心契约 Protobuf → 持久工作与 SQLite 后端 → 裁决域（任务编排、会话、授权、预算）→ 执行管理与出口闸门 → 模拟 API 与 harness、崩溃钩子 → 文件与 API 适配器 → 内容治理与运行记录 → 默认推理与命令行 → V3、V4 故障矩阵。持久工作和 harness 越早可用，后续模块越能测试先行。
- **待验证事项：**核心契约 H1（Protobuf 在真实对象上的绑定覆盖、编解码和校验开销）；持久工作的"数据库队列能否承载 M1"；默认推理 H1（单次调用策略足以支撑 M1）。验证不通过时先改设计文档或 ADR，再改代码。
- **单进程不得成为捷径。**同进程部署也必须模拟域间回执丢失；不得因为同一个 SQLite 文件就跨域共用事务或省略回执。否则 M3 拆进程时故障语义需要全部重做。
- 设计文档是代码的上游。实现中发现规则缺失或冲突，先改对应设计文档并记录原因，再改代码。
