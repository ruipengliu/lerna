# 05: 准入：脚本化提议到动作意图交接

**What to build:** 脚本化推理对任务提出一次 API 调用的提议；任务编排在裁决域的一个事务中执行准入门禁（条件、预配置的持续授权、按单次费用上界的最小预留），写下动作意图和待办工作，再按 R7 三步交给执行管理持久接纳。用户能查询到已准入的动作及其依据。

**Blocked by:** 03（持久化点崩溃钩子与重启）、04（待办工作、租约与接替）

**Status:** resolved

- [x] 脚本化推理实现推理的公共接口，提议绑定快照中的条件版本、输入版本和控制版本
- [x] 准入门禁按核心契约 2.6 的编号条件实现；本工单涉及的条件各有带编号标注的测试（如"准入-n"）
- [x] 持久记录写明动作基于的条件版本、授权和预算（标注 G4）
- [x] 费用上界未知的调用不准入
- [x] 提议本身不产生任何执行；只有准入后的意图进入执行管理（标注 G6、R1）
- [x] R7：裁决域记下意图 → 执行管理持久接纳（P2）→ 裁决域记下回执；在三步之间分别崩溃和丢回执，恢复后查询原交接，不新建（标注 R7）
- [x] 同进程也不省略回执，不跨域共用事务

## Answer

- 公共推理端口位于 `contracts/reasoner`，`defaults/scripted` 只返回绑定快照的单步提议。可信条件接纳、不可变条件／快照／提议及历史查询由任务编排拥有；准入同时核验提议与原快照、当前任务的版本，不能把旧快照重新标为新依据。
- 根持续授权、每动作使用记录、USD_MICRO 用户／任务两级额度与预留分别由授权和预算模块写入。准入在一个裁决事务的业务保存点内调用各参与者；最后的内容或确认门禁拒绝时，回滚全部部分事实，仅保留不可变拒绝回执。提议消费、动作意图、固定执行域／端点、交接 outbox 和待办原子提交。
- R7 的三个提交点为 `tasks.admit`、`ledger.accept`、`tasks.handoff_receipt`。执行管理域独立保存原交接回执、ACCEPTED/OPEN 动作与执行待办；源域先查原身份再投递，保存对方原回执并核验当前领取后完成工作。启动恢复等待旧租约自然到期。此工单没有外部调用路径，目标计数为 0。
- 测试证据：`conformance/admission` 覆盖准入编号门禁、最后门禁原子回滚、原决定重放与冲突、旧快照重新绑定攻击、历史依据查询，以及两个独立连接下两个任务争用最后用户额度（仅一个获准）。`core/ledger` 验证未知／迟到可能性及上一轮已开始未收尾动作的阻断；尚属后续控制工单的状态在 `owner_state_test.go` 中明确作为所属域事实构造，断言仍走公开准入／查询接口。
- `conformance/fault/admission*_test.go` 覆盖全部六个新增持久化点的提交前崩溃、提交后崩溃和丢回执；R7 三腿恢复后保持原动作、授权使用、预留和两域待办不重复。接收方丢回执用例还验证恢复时 2 次查询、仅 1 次接纳调用。
- 通用工作完成／封闭不能丢弃未记接收方回执的交接，也不能封闭仍为 SUBMITTED 的目标决定责任；对应回归均先失败再通过，原有后端语义套件同步保留终态不得重开验证。
- 支持边界明确：逐动作确认尚未由 08 实现时按需拒绝；长期记忆、子任务、推理自报准备／收尾类别均拒绝；费用上界未知不准入；交接不结清或释放预留。后续工单按既有公共接口扩展，不依赖旁路布尔值。
- 验证：合并 21 的严格平台资格与同步屏障后，`make check` 通过（lint、协议格式／兼容／生成、race、全部故障矩阵、规则与生产依赖检查）。
