# 架构讲解深度讨论样稿

本原型用于决定开发者主文档讲到哪里。2026-10-03，用户确认采用下述推荐深度：正文保留足以解释机制的进程、数据、提交边界与失败条件，完整字段和算法细则通过直接链接查阅。决定见[主文档讲到哪里以及何时转向实现合同](../issues/02-explanation-depth.md#answer)。样稿仍是写作原型，不是新增实现合同，也不证明系统已经运行通过。

请先比较两种写法，再看推荐样稿。已有[写入机制图](diagram-layers.html#write-mechanism)和[恢复机制图](diagram-layers.html#recover-mechanism)与样稿配套，不另画一组简化图。

## 两种深度的区别

**概览写法：** 报告已保存但答复丢失时，系统按原操作查询结果。工作进程重启不会创建第二次写入；确认原效果后，系统继续读回核验和任务完成判断。

这段适合章节开头。它没有交代丢的是哪次答复、两端分别保存什么、新进程如何找到责任、何时能停止交回，也不足以解释为何查询成功还不能宣布任务完成。

**推荐写法：** 先固定故障发生的时点和部署，再沿原记录说明恢复。关键字段只在解释因果时出现，并在首次出现时说明用途。下面给出可直接阅读的短章。

## 样稿 报告写入成功后查询答复丢失

### 故障发生时两端知道什么

用户要求系统生成带来源的报告，保存到设备的指定目录，并核验保存结果。本例采用默认部署：云端 Orchestrator 负责 Task 的目标、行动准入和完成；设备 Executor 负责本机写入及效果记录。云端使用所属 PostgreSQL 分片，设备使用原 SQLite 执行账本，文件字节在受管文件根中。网络交接不把这三处存储合成一个事务。

这里的故障时点是：原 `execution.invoke` 已被接纳，云端也已保存接纳依据；设备随后完成写入，并将原操作的 `effect=applied` 及目标证据持久保存。云端调用 `execution.get` 查询原操作时，设备已保存待交回答复，但答复在途中丢失，云端 worker 随后退出。因此，设备已经知道“原写入发生了”，云端还缺这份最新事实。此时不能把“云端没有收到”写成“文件没有写入”。

Operation 表示一次行动及其持续核对责任；Attempt 表示其中一次物理尝试。worker 只是临时领取工作的进程。换 worker 不改变 Task 的逻辑负责方，也不新建 Operation 或写入 Attempt。

| 所在位置 | 此时保留的关键记录 | 为什么恢复需要它 |
| --- | --- | --- |
| 云端 Orchestrator 所属 PG | 原 Task、固定写入意图、原操作引用、执行命令接纳依据，以及尚未完成的效果核对 Job | 新 worker 能找到原操作和原 Executor，不从用户文字重新生成一次写入 |
| 设备 Executor 的 SQLite | 原 Operation、Attempt、效果及目标证据；待交回 Reply 和补传责任 | 网络失联不会删除已经发生的效果，设备可以继续交回原事实 |
| 原受管文件根及其 journal | 报告字节、原写入关联和恢复依据；journal 位置由装配明确 | 文件字节不能靠云端数据库恢复来推定；发生介质故障时仍需原目标证据 |

这里的 Job 是仍需履行的持久工作，通知仅用于提前唤醒 worker。通知、连接和进程消失，都不能把 Job 自动改成完成。记录细则见[数据归属和存储](../../../docs/architecture/data/storage.md)。

### 哪些步骤分别提交

写入前，Orchestrator 在一个 PG 短事务中保存固定意图、原执行命令、预算预留和派发责任，确认提交后才发送。Executor 在自己的库中保存接纳决定、Operation 和执行 Job，才返回命令回执。该回执的 `applied` 表示“承担执行责任的决定已提交”，还不表示文件已经写入。

实际写入前，执行宿主检查当前启动门禁，保存原 Attempt；资源负责方另须持久保存原在途记录与核对责任。文件写入在数据库事务之外进行。驱动利用原 journal、临时文件身份和目标证据判断效果，再由 Executor 在自己的事务中保存效果及后续责任。资源记录与执行账本可按声明装配共事务，也可分别提交，不能根据它们位于同一设备就推断为一个事务。

由此有三个不同的中断点：准备记录提交前不能发送；提交结果未知时先查原记录；目标可能已写入而效果记录尚未确定时，必须恢复原写入的证据。**本例处于效果记录已提交之后，只丢了后续查询答复。** 完整文件写入步骤和证据规则见[受管文件驱动](../../../docs/architecture/execution/README.md#5-受管文件驱动)，不在这里复制文件系统操作清单。

### 新 worker 怎样接续

1. 新 worker 从原 PG 领取效果核对 Job，取得新的领取代次。提交时仍须验证领取有效；旧 worker 即使后来恢复，也不能用过期领取更新受保护记录。新工作已经加入时，旧完成结果也不能覆盖它。
2. 新 worker 沿原 Executor 和原 `operation_id` 取得结果。设备可重交尚未确认的 Reply；云端也可发起新的查询，所查仍是原 Operation。查询身份与写入身份不同，新的查询不构成新的文件写入。
3. 云端先共同耐久保存收到的 Reply 与后续处理责任，再发送匹配该答复的 `ReplyAck`。这里的确认只表示答复已被耐久收到，允许设备释放对应的待交回副本；它不表示报告已核验或 Task 已完成。新查询的确认不能清掉旧交付中另一份尚未确认的 Reply。原答复的重交仍须核验当前披露权限，不能借恢复绕过撤权。
4. 云端按原事实的 owner、对象、修订及摘要核对并归并，在受领取保护的领域事务中共同保存合法事实、Task 的效果关联与后续 Job。相同事实不会重复推进；旧修订不能覆盖新投影。只有原责任已经完成或耐久交接，相关 Job 才能结束；否则保留等待或后续核对。

耐久收件和领域归并可以由不同短事务承担。若进程在两者之间退出，恢复必须继续处理原收件；不能把“已 Ack”当作领域处理完成。worker 并发规则见[Job 的字段和并发规则](../../../docs/architecture/runtime/README.md#3-job-的字段和并发规则)，交回规则见[双向 Delivery 与 Reply](../../../docs/architecture/protocol/README.md#7-双向delivery与reply)。

### 为什么还不能宣布报告完成

原操作的 `effect=applied` 证明报告曾按声明效果写入。文件随后可能被用户改动，因此它不能单独证明当前文件仍是所需版本。报告场景中的读回由另一个获准 Operation 执行，取得绑定路径、准确版本或摘要及观察时点的证据，不能用写驱动缓存冒充独立观察。

Orchestrator 还要根据当前目标核验来源支撑和所有必要条件，核对完整未结操作集合，并确认目标行动已封闭、没有未知或可能迟到的效果，才可提交固定 Result 与 Task 成功。费用结算仍可独立继续。准确完成规则见[完成事务](../../../docs/architecture/orchestrator/README.md#8-完成事务)。

### 如果丢失的是目标写入答复

若设备已经把请求交给文件系统或外部目标，却尚无足够证据判断效果，故障就落在另一条分支。Executor 必须结合原目标请求、journal 或独立观察核对；无法确定时保留 `unknown` 及迟到可能、必要资源限制和预留，不能因超时或暂时查不到而重写。

这也不是禁止一切重试。只读、目标实际支持原幂等键，以及已证实未发生且不会迟到，分别有不同恢复条件；当前权限和预算仍须有效。具体条件见[能力合同决定重试](../../../docs/architecture/execution/README.md#2-能力合同决定重试)。设备或原文件根不可访问时，系统报告等待或明确缺口，不能换空目录假装已经恢复。

保留原责任可以避免从一次失联直接产生第二次写入；代价是有些任务不能自动收束，核对记录与必要预留也不能立即清理。这是现行设计选择，不是已测得的恢复成功率。实现验收还须在相应故障点切断连接或终止进程，同时检查原账本、真实文件与实际写入次数，见[故障验收矩阵](../../../docs/architecture/validation/README.md#2-关键故障矩阵)。

## 主文档与合同的分界建议

主文档的停止点是读者能够解释“谁持有什么、怎样提交、失败后凭什么继续或等待”，并找到准确实现入口。删除一项细节若会改变读者对责任、原子性、权限或恢复结果的判断，该细节就必须留在正文；仅用于逐字段编码、SQL 实现或枚举全部组合的细节转向合同。不存在固定字数上限。

| 内容 | 主文档保留 | 转向现行合同 |
| --- | --- | --- |
| 对象与术语 | 首次出现解释用途，区分 Operation、Attempt、Job 和临时 worker | 完整字段、类型、全部生命周期枚举 |
| 接口 | 本场景的具体方法、输入指向哪份原记录、成功究竟说明什么 | 公共外壳、闭合 Schema、完整参数与错误码 |
| 数据与事务 | 真实位置、写入负责方、哪些记录共同提交、哪些跨库或介质交接 | DDL、索引、完整锁序、所有适配器方法 |
| 版本与并发 | 原对象身份、修订和领取代次为何影响续接；旧 worker 无权覆盖新事实 | CAS 字段全集、领取 SQL、所有竞争组合 |
| 恢复与例外 | 精确失败时点、可用证据、继续或等待的前提、无法证明时的行为 | 各驱动完整恢复算法、平台逐项验证步骤 |
| 理由与证据 | 已确认的理由和代价、适用限制及待验证收益就近说明 | 完整 ADR、研究细节、实验配置与原始结果 |

故障接管和滚动升级沿用同一深度：正文说明原库、旧写者隔离、兼容记录、接纳门禁及原责任如何续接；准确平台配置、发布命令和完整迁移协议链接合同。不能为了缩短主文档，把已采纳机制图所依赖的关键前提全部移走。

长期记忆、多 Agent、手机 GUI 等后续能力仍按既定范围说明接入位置、事实归属与约束，不在本轮提升到首阶段报告主线的同等篇幅。
