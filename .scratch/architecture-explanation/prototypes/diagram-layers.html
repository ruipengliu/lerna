概览只负责定位。关键流程继续展开到进程、持久记录、事务、网络交接和恢复入口。

本版图示组织方案已于 2026-10-03 获用户确认，作为正式架构讲解的写作依据。内容表达现有设计合同，不代表运行、恢复或容量已经验证。沿用现有文档配色与中文字体，不加载外部资源。

一 · 先认清职责

Brain 提建议，Orchestrator 作决定，Executor 对实际执行负责。

依据：职责总览；系统模型

省略与边界：图仅突出报告主线。费用、持久工作、扩展与评测另用邻近文字说明。Grant 管理许可；本人确认由实际业务负责方保存和消费。

将逻辑职责落实到实现

逻辑职责实际承载方式（默认部署）持久事实与越权边界
Orchestrator任务应用处理短命令；分类工作池执行持久工作。它们可更换实例。同一 Task 的目标、条件、OperationIntent、完整关系、Job 与 Result 归原 PG 分片。worker 不是 Task owner。

职责图只定位关系；下方时序中的实体记录、事务和恢复入口才解释机制。全量写入规则仍以原规范为准。

二 · 跟随一份报告走完主线

已接纳、已执行、条件通过、任务完成和用户收到，是不同的成功点。

依据：完整任务链路

省略与边界：“逐项准入与派发”压缩了检索、生成、保存与读回等阶段，不是一个批量接口。读取、写入、读回各为独立 Operation；每项均需适用的许可与入口检查。图未展开授权、内容发布、证据评估及费用收尾；模型、网络与文件操作都在数据库事务之外。

主线背后的数据与提交点

交接阶段提交什么、由谁推进成功点与中断后的入口
输入 → 接纳目标应用先保存原文与 Message / Submission / Command / Job；O 在自己的 PG 事务中保存 Task、目标版本、预算、回执与首 Job。两方各自提交。应用提交答复未知时查询原 submit command，不按相同文本新建 Task。
候选 → 条件 → 当前决策Brain 保存候选及来源；O 另一个事务接纳条件、推进目标版本、失效旧 Snapshot。后续 Job 才请求新决策。条件接纳不能顺便消费同轮行动提案；旧 Decision 不因 worker 重启变成当前提案。
行动准入 → 执行接纳O 的准入事务保存 OperationIntent、原 Command、预留、TaskOperation 与 dispatch Job。取得适用的原 UseReceipt 后才发送；E 另行保存 Operation / CommandReceipt / Job。invoke 回执 applied 是接纳成功。它不是 Operation.effect=applied，更不是 Task.succeeded。
执行 → 效果事实E 先耐久记录 Attempt 与核对责任，再过 StartBarrier 访问目标；后续本地事务记录证据与效果。外部效果在数据库事务之外。恢复查原 Attempt / 目标证据；超时不转换为 not_applied。
效果 → 读回 → 完成保存、读回分别是独立 Operation。O 核对当前条件版本、准确证据、GoalCoverage 和完整未结关系，才在原 PG 完成事务固定 Result 与后续交付 Job。报告写入成功只结束其中一个环节。正式完成、应用耐久接收与费用结清分别判断。

具体实现入口：任务链路 · 同一事务必须保存的记录 · Job 领取与恢复。

3.1 先看到丢失发生前的持久事实

图中数据库写箭头压缩了请求与确认提交。⑦ 文件写入明确位于这些短事务之间；任何一个数据库事务都不包住网络请求或文件副作用。

每个提交点具体留下什么

位置留下的事实与责任边界 / 失败处理
① TxO1 · 云端 PGOperationIntent + 原执行 Command + reservation + TaskOperation 完整关系 + dispatch Job；固定 executor_id / operation_id / intent_hash。此提交确认前不派发。UseReceipt 后来写派发记录，不回写不可变 Intent。
③ TxE1 · 设备 SQLite按原 command_id 与 operation_id 判重；接纳 Operation，保存 CommandReceipt 和执行 Job。这是 Executor 承担责任的成功点。④ 回执 applied 不等于目标效果 applied。发送方耐久接收后才结束命令交付责任，效果核对责任继续保留。
④a · 云端 PG保存原 invoke 的持久接纳依据；结束可结束的命令交付责任，保存或保留原 Operation 的效果核对 Job。收到了网络答复还不够；确认本方耐久接收后才确认相应 Reply。本图省略这次接纳 Reply 的匹配 Ack 帧，恢复图展开的是后续效果查询 Reply。
⑤ TxE2 · 设备 SQLite固定 Attempt、准确出口、使用依据、可能发送阶段及效果核对责任。Job 重领不新增 Attempt。提交未知先查原记录，不进入目标。
⑥ TxR · 文件资源账本原 file_owner 保存路径占用、原临时文件身份及耐久 journal；本例装配在同一设备库，仍是独立领域准备步骤。资源 owner 若独立部署，须另行原命令交接。不得据图合并成跨 owner 事务。
⑦–⑧ · 数据库事务外StartBarrier 核验 TaskGate、有限 UseReceipt、资源代次及期限。驱动同步临时字节、比较前版本、原子替换并同步目录。文件介质和账本不共同原子提交；驱动还需按 journal 阶段更新原记录。中间崩溃必须核对原 journal / 临时文件身份 / 前后版本，不能只靠相同摘要猜测。
⑨ TxE3 · 设备 SQLite归并原 Attempt / Operation 的 effect、may_apply_later、证据、准确结果与用量；保存需要的后续 Job。applied 是历史效果。仍有其他未知尝试时，不得因此填 may_apply_later=false。
⑪ · 设备 SQLite查询原 Operation 与分页 Attempt，持久保存匹配 delivery_id / request_digest 的 Reply。没有 ReplyAck 时保留交回责任。连接或普通日志不是恢复依据。
恢复⑤ TxO2 · 云端 PG按原来源身份与 source_revision 归并事实、维护 TaskOperation 与必要后续 Job；业务与 Job 同事务。检查 holder / lease_epoch / lease_until / observed_work_revision。旧领取失效不得写账本，新责任不能被旧 done 覆盖。

3.2 再看接替 worker 怎样继续

恢复图从原效果核对 Job 仍未结这一事实开始。效果确认后，还需独立读回报告并核验当前条件；这里不直接写 Task.succeeded。费用及其他未结责任也不随这次查询完成而消失。

不能混为一类的相邻故障

具体断点此时知道什么从哪里恢复
invoke 接纳答复丢失尚不能确认 Executor 是否承担责任。查原 command_id 的持久 CommandReceipt；命令去重不等于重做目标。
本例：效果查询答复丢失E 已存 applied，O 尚未获知；可能连查询 Reply 都待交回。原查询 Reply 按传输合同补传，或重新只读查询原 Operation。按来源修订归并；每份 Reply 只由自身匹配的 Ack 解除责任。
文件已写，E 尚未存效果就崩溃E 自己也可能 unknown。本机恢复处理器查询原 journal、目标证据与 Attempt；可用 execution.reconcile 提起原核对。该命令不能由调用者指定 effect。
设备或原文件根不可达不能证明未发生，也不能认为新空目录就是原目标。保留 unknown / may_apply_later 与资源限制，有限退避或转待处置；不换设备或 operation_id 重新写。
云端 worker 租约过期只说明其账本写入资格失效。新 worker 接原 Job；原设备入口仍由 TaskGate、设备代次与 OS 排他锁等机制约束，不能用 Job lease 代替资源隔离。

五 · 最后看它运行在哪里

默认部署把 Task 权威保存在云端；端侧 SQLite 保存本机执行与恢复事实。

依据：生产角色与故障域；存储与一致性

省略与边界：工作池与网关的连线标注业务交接，不假定未声明的传输协议。图省略云端 Executor、对象存储、平台服务、三可用区副本与端口；它们仍见原部署设计。未冻结的制品版本和副本数不在草图中虚构。端侧独立 Orchestrator 是另一种显式部署选择；云端任务断网后不会自动转成端侧可写任务。

拓扑之外，还要读出故障边界

位置 / 边界持久记录或约束进程失效后由谁恢复
网关 ↔ 应用 / 工作池 ↔ 端侧连接、binding 与原 logical_service_id 的路由；业务 owner 保留 Command / Delivery / Reply 责任。重连到原 owner；网关内存丢失不删除 Task 或 Operation。
云端 PG 分片Task、OperationIntent、TaskOperation、Job、Command 与 Result。原 owner 的新 worker 从未结 Job 领取；旧 epoch 不能回写。PG 写主恢复须满足旧主隔离与历史完整等条件。
设备 SQLite + 执行宿主Operation / Attempt、TaskGate、取消墓碑、资源代次、恢复 Job 与待交回 Reply。设备宿主先取得 OS 排他锁并恢复门禁、队列和未结记录，再开放实际入口。云 worker lease 不能替代设备隔离。
原文件介质准确临时文件、目标版本、持久 journal 关联及刷盘证据。原 file_owner 核对同一介质；数据库恢复不证明文件字节恢复。独立读回后才能提供当前成果证据。

六 · 突发故障：接回同一份任务历史

任务续接依赖原权威记录和未结责任。故障转移可以更换物理实例，但不能换一份业务历史继续写。

本例范围：默认云端部署中，一个 PG 写主或其可用区失效；候选仍可恢复同一逻辑分片。端侧 Executor 与文件介质独立存在。仅 worker 崩溃而数据库正常时，直接使用前文的原 Job 领取与效果核对流程，不需要数据库提升。

从“有健康实例”到“允许续接”的条件

阶段责任与恢复依据失败时必须保持的边界
① 先封新责任平台与服务 readiness 使新接纳、新目标发送暂停；已交给目标的动作仍可能发生。不能把封新入口解释为撤销已发送动作。取消、核对能否继续取决于权威库和实际入口是否可用。
②–④ 数据库接管数据库平台证明：旧主已隔离；候选属于同一历史并包含全部已确认提交；恢复第二耐久副本。应用消费这些证明，不靠 Job lease 选主。任何一项不能证明，保持不可写。连接池切换、DNS 更新或看到健康副本都不单独构成接管资格。
⑤ 路由回原 owner更新原逻辑服务 / 原分片到健康物理实例的路由。Task、命令去重、预算、墓碑和未结 Job 保持原身份。不改投当前“新 Task 默认 owner”，不建立同一 Task 的另一份可写副本。整地域灾备同样先隔离原地域。
⑥ 时间、格式与领取服务恢复进程核验存储格式、原控制与关闭记录、恢复处理器及可信时间。数据库提升后还需满足旧持有者隔离或安全等待条件，才续租 / 回收。不能因为新主可访问就立即复用旧槽位。领取或续租提交未知时先查询原 holder / epoch / 期限，不执行新动作。
⑦–⑧ 续接原任务新 worker 领取原 Job；提交未知查原 Command / 阶段；接纳未知查原 Receipt；效果未知查原 Operation / Attempt。合法原事实与后续 Job 在所属库事务中归并。查询不到或设备离线时保留等待与资源限制。旧 worker 迟到写入受 Claim 校验拒绝；可信迟到事实可走独立归并入口。
⑨ 分阶段恢复先开放获准查询、控制、关闭及原效果 / 费用核对；依赖、剩余配额和故障后容量满足，再开放新工作。不要求所有 unknown 清零才恢复无关任务；也不因单个任务恢复成功就宣称整个系统就绪。

“平台恢复机制”是数据库与基础设施的既有职责统称，不新增业务调度服务，也未指定某个选主产品。图中存储写与控制动作表示设计步骤，具体平台证明接口仍由生产实现落实。依据：数据库与内容恢复 · 可信时间与租约 · 原 owner 与物理放置 · 持久工作恢复。

7.1 worker：停止领取，不丢原责任

旧进程正常退出时，先以有效领取保存可保存的业务阶段和未结责任；新进程拿到新 Claim 后从这些记录继续。没有可验证的退出或领取释放时，按故障路径等待安全回收，不能并行重放已可能发送的动作。

7.1 的补充：接的是哪个业务阶段

中断时的阶段新节点读取的依据允许的后续动作
命令接纳未知原 owner、Command、请求摘要、CommandReceipt先查原接纳决定；不改 command_id、参数或目标后重新提交。
模型调用已经发出原 Decision、ModelCall.send_started、费用占用和核对 Job查原供应商调用；不能透明重新推理。供应商不可查询时保留未知与费用责任。

等待用户 / 设备 / 依赖原 InputRequest 或 waiting Job、条件版本与截止继续等待原输入或依赖变化；不占用常驻处理线程，也不把“等待”误记为已完成。

工作者的 Claim 只回答“谁可以推进并写账本”；真正的下一步由 Brain、Executor、Interaction 等原领域合同决定。所有阶段都沿原 Task 继续，不重启整项任务。

7.2 应用与网关：通道切换不改变 Task 身份

图中“网关池”和“任务应用池”包含多个进程；箭头已经注明执行动作的是旧实例还是新实例。身份服务分片一列包含其服务与所属存储，额度由身份 owner 裁决，不表示网关直接写其数据库。绑定更换与连接额度释放不在同一库事务中。认证、重连背压和有限重试折叠在握手步骤；它们失败时，原业务责任继续存在。

7.3 执行宿主：先证明入口安全，再恢复动作

“本机退出可证明”覆盖本地进程、驱动队列及子进程的隔离；它不证明已交给远端目标的请求不会迟到。新宿主恢复后仍要沿原 Attempt 核对，不能将未知改成未执行。只对门禁、许可、资源及依赖都满足的范围开放新工作。

切换点必须满足的条件条件不满足时
新实例加入前发布流程验证当前数据格式、原命令 Schema / profile、准确 InstallLock 与恢复处理器可用；准备实例不等于允许接业务。不兼容时暂停切换或进入已声明维护窗口，不能让新版本猜旧记录含义。
旧应用 / worker 退出应用停止新 RPC / 绑定，原短请求有界结束并重绑；worker 停止 Claim，按原领域阶段保存未结工作。已可能发送必须留核对责任。排空超时按故障处理。新 worker 只能在旧领取已合法释放、完成交接或满足安全回收条件后 Claim，不由发布器修改业务 Job 为 done。
连接在途与额度竞争绑定归原服务分片；连接额度归身份分片，各自提交。Reply 由接收方耐久保存并匹配 Ack；socket write 不是交付完成。新握手先到而旧额度未释放时，可暂拒并抖动重试；不得每个网关私自多发一份额度。旧绑定清理须条件匹配。
Executor 实际入口新设备宿主先取得 OS 排他锁，恢复 TaskGate、关闭墓碑、Attempt、资源代次、队列及补传 Job；多机接管还需设备 fence 或运维隔离。有冲突的未知外部效果时保持资源限制。原库、原文件根或旧实例隔离无法证明时，不能从新空库 / 空目录接管原身份。
继续扩批每批检查实际 readiness、原未结工作可恢复、连接重建和控制 / 核对容量，按已批准范围与观测门槛扩大。出现未知效果、恢复缺口或容量不足时停止扩批，保留原任务和责任，不通过重新提交任务掩盖问题。

7.4 新版本如何接住旧记录

兼容对象接续规则禁止的捷径
任务与工具版本旧任务默认继续准确原 InstallLock；旧效果 / 费用查询入口须保留，或由经合同验证的兼容接管器承担。“最新同名工具”不能重解释旧 Operation；原代码因安全问题停用且无合格接管器时，保留查询与明确恢复缺口。
数据库格式升级独立迁移命令执行 expand → 有界 backfill → 切换 → 观察 → contract；保存 migration_id、制品摘要、检查点及兼容范围。只有旧实例全退出、旧未结责任可恢复、回退保留期结束，才删除旧字段。不让每个启动副本竞相改表。
同版本实例重启适用扩展实例的 reopen 固定新 instance_id，核验旧实例隔离、当前批准、原格式及 readiness；不重跑已完成迁移。reopen 不等于新版本 activate，不继承旧实例的离线许可窗口，也不跳过 BindingHead 并发检查。
软件回退扩展版本回退属于新的激活：准确旧 InstallLock、独立旧批准、当前格式可读写及新实例 readiness 均须成立。回退不回滚 Task 历史，不抹除文件效果、撤权、一次消费或迟到账单。旧批准失效 / 格式不兼容则停用并报告缺口。

依据：连接、发布与排空 · Job 领取与条件提交 · 真实执行入口与宿主恢复 · 版本与在途工作 · 迁移与回退 · 独立迁移命令。

验证边界：本节解释现行设计，未证明生产故障转移或升级已通过验收。实际验收须覆盖提交未知、旧 worker 恢复、丢 Reply、旧绑定迟到、设备旧入口未退出、新旧格式并存和回退，并同时检查原记录、真实目标与实际出站次数；只看到新实例健康不能证明任务续接正确。
