## Question

哪些图最能支持所选章节结构，各张图应解释哪些关系、保留哪些边界？如何让读者分清“谁负责、保存什么、运行在哪里”，并理解跨模块箭头不自动代表网络调用或同一事务？

先检查已有职责图、数据图和时序能否直接复用或简化；只对确有理解缺口的地方制作草图。通过用户反馈决定图示数量、每图结论、角色命名、方向、边界和省略说明，不以图示数量作为完整性标准。

## Answer

采用“概览定位、关键场景展开机制”的图示方案。正式说明保留逻辑职责与默认物理部署的区别；关键场景必须把进程、持久记录、提交、外部效果与恢复入口联系起来。不能仅以业务流程箭头代替机制说明，也不能以“另有字段表”为由省略理解续接所需的数据关系。

### 图示内容与章节位置

| 图示 | 所在章节与回答的问题 | 必须保留的关键点 |
| --- | --- | --- |
| 逻辑职责概览 | 第二章：谁提案、谁裁决、谁执行？ | Brain、Orchestrator、Executor 的职责；配逻辑职责到运行角色、持久事实及越权边界的映射。逻辑方框不代表进程或数据库。 |
| 报告正常时序 | 第三章：研究报告怎样从输入走到交付？ | 分开接纳、效果、条件通过、Result 和交付；配阶段记录及提交点。保存与读回是独立 Operation。 |
| 写入与答复丢失详图 | 第四章：哪种答复在什么位置丢失？ | 原 worker、所属 PG、Executor 宿主、SQLite、文件介质；本地提交与事务外写入；本例丢失的是后续 execution.get 效果查询答复，invoke 接纳已确认。 |
| 接替 worker 恢复详图 | 第四章：进程退出后从哪里继续？ | 原 Job、新的合法 Claim、原 Operation 与版本化事实、持久接收及匹配 ReplyAck；不得换身份重写文件。 |
| 默认部署概览 | 第六章：职责装配在哪里，故障边界在哪里？ | 云端 Task 权威、端侧执行账本、工作池经网关到端侧的路径；配各存储与进程失效后的恢复责任。 |
| 数据库故障接管时序 | 第六章展开：PG 写主或可用区失效后如何续接？ | 旧主隔离、已确认历史、第二耐久副本、时间与领取资格、原 owner 路由；先恢复控制及核对，再按条件开放新工作。 |
| worker 滚动升级时序 | 第六章展开：计划内更换处理进程如何交接？ | 兼容预检、停止 Claim、持久保留阶段与未结责任、合法领取与 Guard；配不同业务阶段的恢复记录和动作。 |
| 应用与网关切换时序 | 第六章展开：连接切换怎样保持任务与交付连续？ | 应用升级优先内部重绑；网关升级触发外部重连。身份服务的连接额度与原服务的绑定分别裁决，原 Delivery / Reply 继续交付。 |
| Executor 宿主升级时序 | 第六章展开：如何避免新旧入口重复操作目标？ | 封新启动、原在途记录、本机进程和队列退出证明、OS 排他锁与资源隔离、恢复门禁及原 Attempt；本机退出不证明远端不会迟到。 |

第五章采用数据归属表，并回指已展示的提交点；不再为了凑图重复绘制全部字段与数据交接。故障接管、升级条件、任务中断阶段、新旧格式兼容与回退用表格补足精确规则。

当前原型共九张图。确认的是解释范围与机制深度，九张不是必须维持的数量指标；后续排版可以拆分或合并，但必须保留上述问题的答案，并保持与原规范一致。

### 表达与取舍

- 职责、正常链路与默认部署基于现有图和合同简化重排；新增恢复、故障接管与升级详图，用于补齐首版未能解释的数据、进程和边界。原型计划记录具体素材及省略项。
- 沿用现有文档的浅色底、青绿色节点与中文字体。采用静态 HTML 内联 SVG；窄屏图内滚动，配就近结论、图例、记录表和合同链接。
- 详图中的事务编号仅用于定位。各库独立提交，网络、模型与目标文件操作不被画成全局事务。平台恢复机制和发布流程表示既有平台或运维职责，不新增核心服务或 API。
- 明示示例装配和折叠内容：文件资源账本装配、网关路径、journal 中间阶段、身份服务内部调用，以及未展开的副本、端口、容量和平台产品。需要准确实现时直接跳转原合同。
- 旧任务、旧命令与旧效果保持原身份和版本语义；新进程、连接、Claim 或部署版本不能成为重执行整项任务的理由。兼容性不足、隔离无法证明或外部效果未知时，明确等待或报告缺口。
