## Question

在已选章节结构中，主文档需要哪些对象、接口和事务细节，才能让开发成员解释方案并找到实现入口，又不变成第二份规范？

以“报告已写入但回执丢失”为短章样例，对比不同讲解深度。请用户判断能否回答：系统知道什么、缺什么证据、谁继续核对、为什么不能直接重做，以及实现时去哪里查准确规则。由此决定术语首次引入方式、必要正文细节、例外的位置及链接边界。

## Answer

### 已确认的讲解深度

采用[讲解深度样稿](../prototypes/explanation-depth.md)中的推荐短章写法。概览段用于先说明结论，随后讲清进程、数据、分别提交的事务、恢复责任和失败条件。正文不以固定字数限长，也不以只讲业务步骤代替机制解释。

每个关键场景先固定部署与故障时点，再说明各方知道什么、缺什么、原记录在哪里，以及哪个负责方据什么继续或等待。正文必须区分命令接纳、目标效果、答复收到、当前成果核验与 Task 完成，不能把它们压缩成一个“成功”。

### 正文保留与引用边界

| 内容 | 正文必须保留 | 通过直接链接查阅 |
| --- | --- | --- |
| 对象和术语 | 首次出现解释用途及相近概念的区别；如 Operation、Attempt、Job 与临时 worker | 完整字段、类型和全部生命周期枚举 |
| 接口 | 场景实际使用的方法、输入指向的原记录，以及返回成功能证明什么 | 公共外壳、闭合 Schema、完整参数与错误码 |
| 数据和事务 | 真实存储位置、写入负责方、共同提交的记录及跨库或介质交接 | DDL、索引、完整锁序和适配器接口 |
| 版本与并发 | 稳定身份、修订和领取代次如何约束续接；旧 worker 无权覆盖新事实 | 完整 CAS、领取 SQL 和所有竞争组合 |
| 恢复和例外 | 精确中断点、可用证据、继续或等待的前提、无法证明时的处理 | 各驱动完整恢复算法及平台验证步骤 |
| 理由和依据 | 已确认理由、代价、适用限制和待验证收益紧邻机制 | 完整 ADR、研究材料、实验配置和结果 |

判断一项细节是否保留的规则是：删除它若会改变读者对责任、原子性、权限或恢复结果的理解，就必须留在正文。仅为逐字段编码、SQL 实现或枚举组合服务的内容转向合同。链接应直接指向对应规则，不让读者重新遍历整个文档树。

故障接管和滚动升级采用相同深度，保留原库、旧写者隔离、格式兼容、接纳门禁和原责任续接的前提；平台配置、发布命令及完整迁移协议链接合同。长期记忆、多 Agent、手机 GUI 等后续能力仍按既定范围说明接入位置、事实归属和约束。

### 样稿与来源

样稿固定的故障是：invoke 接纳已确认，设备 Executor 已持久保存写入 applied，随后 execution.get 查询答复丢失，云端 worker 退出。它沿已采纳机制图说明新领取、原操作查询、耐久收件与后续责任、匹配 ReplyAck、事实归并、独立读回和完成核验。目标效果本身仍未知另列分支，不能从前一种情形推导所有故障都可自动恢复。

原型的[来源与样稿核对](../prototypes/explanation-depth.md#来源与样稿核对)逐项链接执行、持久工作、共同协议、Orchestrator 与验证合同。完整字段和规则仍由这些原合同维护；本决定没有新增或修改接口、授权、事务与恢复保证。
