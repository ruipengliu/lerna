# 生产可操作性只读审查

范围：持续过载、工作与控制传播、配额及凭据换版、恢复处置、SLO。只检查当前设计是否闭合，不把尚待压测的参数作为设计缺口；未修改方案正文。

## OPS-01（P2）请求 SLO 的去重口径不能覆盖查询，恢复后的成功也缺少固定判定窗口

**位置与依据**：`docs/architecture/deployment-production.md:230` 规定逻辑请求统一按原 `command_id` 计一次，`:234` 又将权威查询单列为 ≥99.9% 可用性目标。`docs/architecture/contracts/transport.md:93` 规定 `request_id` 只关联当前连接，query 和 receipt_lookup 不创建业务命令；`:108` 已规定每次请求自首次收到起最多 5 秒，后续仍可查原身份。`docs/architecture/contracts/schemas/protocol.schema.json:4054` 的 Query 只有 method、target_id、payload（`:4099` 为完整必填集合），没有通用 command_id；`:4272` 的 ReceiptLookup.command_id 是被查询命令的身份，并不是本次查询的身份。

**具体异常轨迹**：应用短时不可用，一次 `task.read` 在原请求期限内失败；客户端重连后用新的 request_id 成功读到状态。若按 command_id 聚合，第一次查询没有合法聚合键；若按 request_id 聚合则得到两个请求；若按“最终读成功”计一次又可能抹掉首次超时。反过来，同一任务取消命令在不同时间被多次 receipt_lookup，按被查 command_id 去重会把独立的可用／不可用观察折成一次。因此，同一故障在不同实现中可能获得不同的权威查询可用性和请求延迟，现有 99.9% 验收无法复现。命令已经提交、客户端在 5 秒内未收到确定结果、稍后查询成功时，也需要区分账本成功和本次接口及时可用。

**最小补充**：在生产 §4.2 固定指标对象及观察截止。建议接口可用性／延迟按客户端可观察的一次调用及原 5 秒期限统计，重试调用另有尝试计数；命令业务接纳另按 command_id 去重，但后续原回执恢复不能追改首次调用的超时结果。普通 query 与每次 receipt_lookup 按调用统计，不按被查询的业务对象折叠。若坚持合并客户端自动重试，应由 SDK／测量器持有一次用户操作的观测关联并冻结总期限，明确跨重连关联规则即可，无须给领域 Query 新造业务身份。为避免成功重试冲淡故障，保留已要求的失败时段指标，并说明与请求指标分别判定。

**代价归属**：网关／客户端 SDK 和观测实现承担双口径关联、固定截止与聚合成本；验收维护者承担故障样本核对。这里不要求新增中间件或更改领域恢复协议。

**是否需用户关键决策**：不需要。现有 99.9%、5 秒请求期限及 RTO 目标足以确定口径；属于使已确认目标可执行的补充。若希望另行承诺“用户重试后最终成功率”，应作为不同指标命名，不能替代当前接口目标。

## 已核对且未列为缺口

- 持续过载及积压不能无限延期：生产 §5.2～5.4 已规定到达／完成速率、剩余容量、mu>lambda 排空条件、类与租户配额、控制／收尾专用余量、持久队列上限、接纳前 overloaded；PROD-03、16 已覆盖验证。参数尚待实测不是遗漏。
- 跨分区总配额换版：生产 §5.3 已规定串行配置版本、先降旧份额并确认再增新份额、失联不回收、版本不清零计数，且已明确闲置和运维调整成本。
- 凭据及内部绑定轮换：transport §2～3 与 gRPC 已规定当前身份复核、JWS 新旧 key 过渡和失窃处理、原凭据期限、30 分钟内部委托更新，不应再泛列“没有密钥轮换”。
- 发布与事故恢复：生产 §4.3、§6 已规定有界启动恢复、依赖失败不触发整体重启、分角色排空、兼容回填与回退边界，以及跨可用区恢复的证据条件。
- 反复崩溃的 job：runtime 已保存尝试数并规定有限调度及尝试耗尽后的保留责任；本次未将“缺少毒作业机制”列为确定缺口。实现和专项测试应核对领取后异常退出也消耗持久尝试／退避预算，但仅凭当前抽象程度不足以断言必然无界。

本审查为文档语义核对，没有运行压测或故障注入；不宣称任何 SLO 已通过。
