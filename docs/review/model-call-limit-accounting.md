# R4-03 模型调用位置上限与实际发送上限必须分开

| 日期 | 修订说明 |
| --- | --- |
| 2026-10-04 | 第四轮评审：核对调用位置恢复与实际调用次数约束。 |

- 状态：评审建议，未采纳
- 优先级：P2
- 解决阶段：M1 单位置调用接口定稿之前
- 涉及：G4、G5、G10；推理接口、任务编排、执行管理、预算
- 基线：`0a21f22`

R3-04 的“提议请求 + 调用位置”能够区分恢复原结果与新的采样。剩余问题是同一个 `limits` 同时表示位置数量和物理调用次数。安全重发可以不增加调用位置，却增加一次实际发送；这两个上限不能共用一个计数值。

## 1 文档事实

| 位置 | 已写规则 |
| --- | --- |
| [推理接口 2.1](../architecture/ports/reasoner/README.md#21-上下文快照) | `limits` 包含“实际模型调用次数上限”。 |
| [推理接口 2.2](../architecture/ports/reasoner/README.md#22-提议请求) | `model_operation_refs[]` 按调用位置索引，位置分配、次数占用和动作关联在同一事务完成，数量不超过 `limits`。 |
| [推理接口 3](../architecture/ports/reasoner/README.md#3-接口) | 已有位置重复请求不占新次数；实际模型调用按可能单独收费的供应商请求计数，重试也分别计数。 |
| [第三轮处理记录 R3-04](archive/round-3/disposition.md#r3-04-模型调用按提议请求--调用位置恢复) | 明确“次数上限按位置计数”，同时要求物理安全重发和新采样分别记录。 |
| [预算 4.1、4.2](../architecture/core/budget/README.md#41-准入执行与结算) | 出口核验调用次数约束；安全重发如另行计费，需要新的计费关联和预算容量。 |

分别记录次数和费用是必要条件，但文档还须说明各次发送具体扣哪个上限、在哪个事务扣减。

## 2 事件顺序与推断

1. 提议请求 R 的 `limits` 中调用上限为 1。位置 0 被准入，位置数量变为 1。
2. 原发送进入可能发送窗口后丢失响应。
3. 假设测试目标提供已验证的幂等保证，执行管理按 G1 允许沿用原尝试重发；预算还有第二次请求的费用容量。
4. 第二次发送仍属于位置 0。位置数量为 1，实际供应商请求数量为 2。

**推断：**按位置上限解释，重发没有超限；按 2.1 的实际调用上限解释，重发超限。满足金额上限不能解决独立的调用次数限制。这个反例不假设任意模型供应商支持幂等，只需一个明确声明该能力的模拟目标。

反方向也有分歧：若实现把“返回已有位置结果”当作新的物理调用次数占用，进程恢复可能在上限耗尽时拿不到原结果，与 R3-04 的恢复承诺冲突。

## 3 具体修改方案

建议在请求限制中明确两个独立维度，名字可在协议定稿时确定：

| 维度 | 计数和写入规则 |
| --- | --- |
| 逻辑调用位置上限 | 新位置与模型动作准入时占用；查询或重取已有位置结果不占用。M1 固定最多 1 个位置。 |
| 实际发送上限 | 每次新发送身份在获得出口开始资格前占用；包括执行管理批准的安全重发。同一发送身份查询或重投回执不重复占用。 |

预算维护调用次数维度的额度，执行管理维护每次发送身份，任务编排保存位置关联。继续使用现有写入方，不新建计数服务。

建议在 P4 所属裁决事务中绑定本次发送的次数占用、预算依据与开始回执。P4 回执丢失时查询原发送，不再次扣减。进入可能发送窗口后，未查清的发送继续占用次数；只有权威证明没有发送且不能再发送时，才按明确规则释放未使用的占用。

M1 可以把两个上限都设为 1。需要物理重发时，核心必须事先分配额外的实际发送额度；G1 的重发许可只证明效果安全，不自动扩大次数或金额。以后开放多位置时，两类上限仍分别核验。

## 5 验收场景

- 1 个位置、1 次发送额度，原发送未知：即使 G1 允许重发，也必须因次数不足等待。
- 1 个位置、2 次发送额度，安全重发成功：位置仍为 1，发送为 2，实际计费来源分别保存。
- 额度耗尽后重取位置 0 的已有结果：内容许可有效时返回，不新增发送或扣减。
- P4 提交后丢回执、两个工作者重复提交同一发送：只占一次次数，恢复不产生额外发送。
- 以后开放两个位置并发请求最后一份发送额度：最多一个获得开始资格。

本项是计数契约冲突；没有声称现有运行发生过超限。
