# 命令身份还没有贯穿存储、会话和交互接口


上一轮的命令身份调整尚未全量落实。核心契约、网关和持久工作已经统一为四元组，存储设计、会话和交互接口却还给出不同的范围。建议在 M1 的表结构和 SDK 协议固定之前完成这项修订；否则上游的正确类型仍可能被下游的唯一约束截断。

---

定位：[核心契约 §3.1](../architecture/core/contracts/README.md)第 188 行规定 `CommandIdentity = (user_id, issuer_id, target_domain_id, command_id)`；第 411 行还要求不同 issuer 的同名命令互不覆盖。但[数据与存储 §2.2](../architecture/topics/data-and-storage.md)第 76 行仍写“同域同用户同标识只有一个决定”；[会话 §2.1](../architecture/core/sessions/README.md)第 57 行要求 `command_id` 在用户范围唯一；[交互接口 §2.1、§3.1](../architecture/ports/interaction/README.md)的事件、回执和查询仍自行列命令标识，查询没有完整的 issuer 与目标域绑定。

同一用户的手机 issuer A 和电脑 issuer B 向同一域提交 `command_id=42`。按核心契约它们是两条合法独立命令；按存储表的约束，第二条会冲突，或者错误返回第一条回执。UUID 降低偶发碰撞概率，不能消除协议语义冲突，更不能成为省略命名空间的理由。

---

修改方案：下游统一引用 `CommandIdentity`，不再定义替代的简写主键。存储唯一约束、回执查询、客户端待发索引、本地回显合并、显式前驱依赖、跨域交接映射和退役记录都要保留完整身份。路由可以帮助定位目标域，但不能改变历史命令的域身份；主体认证可以验证 issuer 的使用权，但不能把多个 issuer 默默合并成一个。

同一设备有多个主体或同一用户使用多个 SDK 时，`command_id` 只需在所属命名空间内满足生成约定。会话对外查询也接收完整身份；如果产品支持“查另一个端点的命令”，另行核验查询权限，不能靠伪装成那个 issuer。端点代次封存与 issuer 退役之间定义明确映射，不要沿用两个彼此独立的清理边界。

顺带同步交互回执的类型：受理、业务决定和查询状态直接使用核心契约，再映射为显示文案。不要把 UI 的“待决定／已应用”反向当成另一套协议枚举。这个修订是完成既有决定，不需要新建 ADR 或推翻上一轮的身份选择。

---

[Matrix v1.18 的事务标识规则](https://spec.matrix.org/v1.18/client-server-api/#transaction-identifiers)把重传身份绑定到明确的客户端作用域，刷新认证令牌不改变原作用域。它支持“身份范围必须贯穿恢复”的判断；本项目采用四元组是自己的选择，不必复制 Matrix 的具体范围。

验收覆盖同用户不同 issuer 同名命令、同 issuer 同名同载荷重投、同 issuer 同名异载荷、不同目标域、凭据轮换后的查询、旧 issuer 退役后的重传。除了核心单测，还必须经过存储唯一约束和 SDK 待发记录这两处，确保端到端都得到一致结果。增加文档或契约检查，禁止下游重新写出缺字段的命令键。


定位复核补充：数据与存储中“同域同用户同标识”的命令回执约束位于第 **75** 行，上文的第 76 行是下一条待办工作记录。这里需要修改的是命令回执的身份与唯一约束。
