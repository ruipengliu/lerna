# 被拒绝但仍在等待的核验轮次，也必须能释放冻结

第三轮评审点 R3-02，优先级 P1，建议在 M1 实现前修订。第二轮给 `VERIFYING` 增加 `SUPERSEDED`，修复了核验进行中被新输入替代的路径；但 `REJECTED` 仍可能持有冻结，现有替代转换没有覆盖它。

---

定位：[任务编排 §2.4](../architecture/core/tasks/README.md#24-状态)第 135 行把“核验轮次被替代”的前态限定为 `VERIFYING`；[§4.7](../architecture/core/tasks/README.md#47-完成门禁)第 313 行先把目标未达成的轮次写为 `REJECTED`，只有控制、版本、未知效果和封闭条件全部满足时才解除冻结，否则等待或非成功关闭。两条规则组合后，存在已经拒绝、仍持有冻结、又无法进入被替代转换的状态。

§4.7 已经声明拒绝或被替代后必须有合法后续路径。本意见保留这一活性要求，补的是能实际满足它的状态转换。

---

反例不依赖丢失通知：轮次 n 固定了清单，发现附录尚未生成，同时另一个已开始动作仍有阻断性的未知效果。轮次被记为 `REJECTED`，因为未知未消除而保留冻结。随后用户修改要求，输入版本和控制代次递增；n 已不是 `VERIFYING`，按明确列出的转换不会变成 `SUPERSEDED`，冻结仍属于 n。后来未知效果被合法核对清楚，n 的“拒绝后继续”又因版本不匹配无法执行。新的目标准入被旧冻结阻断。

“等待依赖”在依赖恢复后有后继；上述历史中依赖已经恢复，卡住的是冻结的归属和释放规则。仅增加扫描或重试次数不能修复它。

---

建议将核验结论与冻结的处置分别表达。轮次可以保留不可变的 `REJECTED` 结论；只要它仍持有冻结，就必须有一项持久的后续处置责任。无需为了释放冻结而把已经拒绝的历史改写成另一种核验结论。

对持有冻结的 n，定义两个幂等的处理路径：

- 等待条件改善且版本仍匹配：在同一事务中释放 n 的冻结、登记下一次规划；继续所需的条件不满足时保留明确等待及唤醒来源。
- 输入、条件或控制变化使 n 不再适用于当前任务：无论 n 是 `VERIFYING` 还是已经 `REJECTED`，都在该变更事务中按冻结归属条件写入，解除 n 对当前任务的阻塞，并按当前控制保存后续工作。历史上的拒绝结论和旧清单封闭责任继续保留。

第二条只解除核验冻结。用户暂停仍有效，取消只推进收尾；未知效果仍由普通目标准入门禁阻止，已封闭动作永不重开。不能把“释放冻结”实现成“所有阻塞已经解除”。

也可以规定 `REJECTED` 事务总是立即释放冻结，把未知等待完全交回任务的普通等待集合。这种方案更少状态，但必须同步改写现有“本轮封闭确认后才继续”的规则，并证明新准入仍被旧动作的不确定性正确阻断。推荐先采用按冻结归属处理的修补，改动范围较小。

---

修改落点：任务编排 §2.4、§4.5、§4.7、§5 与测试表；核心契约的轮次状态说明。持久工作的工作目的键使用轮次和处置目的，保证重复唤醒只产生一次继续决定。完成处置后旧工作不能释放后来轮次的冻结。

验收包含：`VERIFYING → REJECTED且等待 → 输入变更 → 未知消除`；将输入变更替换为暂停后恢复、条件变更；封闭回执晚到、重复到达和处置事务崩溃。授权、预算和控制均允许且未知已消除后，任务必须能进入新规划或明确的非成功结果，不能仍被 n 冻结。另检查旧 n 的迟到处置不能解除 n+1 的冻结。

这是按现行状态转换作出的纸面反例，不是已经运行实现或形式化工具得到的验证结果。
