## X-01 无外部效果的动作结果未知后永远无法收尾

**文档事实**

- [核心契约 2.6](../architecture/core/contracts/README.md#26-四道门禁)"收尾的两条路径"：`SETTLED` 要求派发已封闭、迟到可能性为 `RULED_OUT`、没有未处理的证据冲突；可能已发出的动作只能凭"可信出口固定的原始观察，由受信解释规则判定"。
- [核心契约 2.4](../architecture/core/contracts/README.md#24-能力声明)：迟到终局的缺省值是"无法证明"。
- 完成-6：全部已准入动作都已 `SETTLED`。[任务编排 2.1](../architecture/core/tasks/README.md) 的动作清单"包括模型调用、辅助调用和收尾调用"。
- [流程：模型调用 5](../architecture/flows/model-call.md)：模型响应超时，"效果按未知处理"。
- [执行管理 4.2](../architecture/core/ledger/README.md#42-结果未知后由能力组合决定策略) 第一行允许"无外部效果，且重复读取安全"的动作重发；但重发不改变原尝试的迟到可能性。
- [分层与模块 8.2](../architecture/layers.md#82-故障时谁负责)：推理调用超时，"可以重新请求提议"。

**问题**

一次模型调用在 P5 之后超时，或一次只读 API 查询（例如"查询余票"）响应丢失，原尝试就停在 `UNKNOWN`、`MAY_OCCUR`。模型供应商和多数只读接口不提供"按请求证明终局"的手段（待验证，属于[核心契约 H4、H5](../architecture/core/contracts/README.md#8-待定事项)），所以它永远无法收尾，完成-6 永远不成立：**任务只能非成功关闭**。模型超时是常见故障，这会让 V4 中的"超时后继续完成"无法达成，也和分层 8.2"可以重新请求提议"的意图冲突。

对这类动作，"迟到"影响的只有费用和已经发生的数据外发：费用由预算继续承担（预留不释放），外发由内容治理按接收方登记（G9）。它们不会再改变外部世界，阻止任务成功没有对应的不变量收益。

**建议**

在核心契约中为"外部效果 = 无"的能力规定收尾口径（建议方案）：

1. 能力声明的"外部效果"维度为"无外部效果"且有验证证据时，迟到可能性只约束费用和外发记录。派发封闭、费用责任已由预算接纳（预留保持到结清）、外发接收方已登记，即可 `SETTLED`；效果可以保持 `UNKNOWN`，Result 必须披露"结果未取得，费用待结"。
2. 未声明或无证据的仍按"改变外部世界"处理，保持现行严格规则。
3. 同时修正重试门禁公式，补上"无外部效果且重复读取安全"一支（现在只在执行管理 4.2 出现，见[逐篇 CT-04](per-doc-core.md#核心契约)）。

备选：维持现行定义，并在 M1 验收中明确"任何模型调用超时后任务都不能成功"。不建议，这等于让最常见的故障决定任务结局。

**落点**：核心契约 2.4、2.5、2.6；执行管理 2.3、4.2；流程：模型调用 5；推理接口 5；任务编排 4.7。

**验收场景**：模拟模型供应商对一次请求"已计费、响应丢失、不可查询"；推理用新调用位置继续并给出完成提议。任务能以 `SUCCEEDED` 关闭，Result 列出该调用的未知结果和待结费用，预算预留在账单到达前不释放。对照组：一个"改变外部世界、不可查询"的动作超时后，任务仍不能成功。

## X-02 "阻断性未知效果"没有定义

**文档事实**

- 准入-5："没有阻断性的未知效果"（[核心契约 2.6](../architecture/core/contracts/README.md#26-四道门禁)），没有定义"阻断性"。全仓只有[整体方案](../architecture/overview.md)、核心契约和[任务编排](../architecture/core/tasks/README.md)使用这个词。
- [任务编排 4.3](../architecture/core/tasks/README.md#43-有限计划)："任何一个有外部效果的步骤结果未知时，默认停止本任务后续的目标行动……这条规则适用于所有目标准入"。
- 准备类准入只跳过准入-3，仍检查准入-5；收尾类跳过准入-5。

**问题**

实现者要自行回答五个问题：范围是本任务、本任务加祖先和子任务，还是同一用户的全部任务；无外部效果的未知是否算；"默认"能否被模板或用户覆盖、由谁覆盖；准备类准入（解释新输入的模型调用）是否会被阻断；拒绝时返回什么错误码。最坏的读法是"任何未知都阻断、准备类也受阻"：一次模型超时之后，连解释用户澄清所需的模型调用都无法准入，任务只能等待一个永远不会到来的核对结果，与 X-01 叠加成死锁。

**建议**

在核心契约 2.6 的准入-5 下写出判定式（建议）：

- 范围：本任务，以及尚未关闭、结果尚未汇总给本任务的子任务；不跨任务；
- 对象：能力声明"可能改变外部世界"、效果为 `UNKNOWN` 的动作，加上被拒绝轮次中"开始核验前已取得开始回执、尚未收尾"的动作；
- 无外部效果的未知（见 X-01）不阻断；
- 准备类准入不受"无外部效果"的未知阻断；是否受"有外部效果"的未知阻断，写明结论和理由；
- 拒绝时返回专门的错误码（见 X-10）。

任务编排 4.3 的"默认"二字删除，或写明唯一的覆盖途径。

**落点**：核心契约 2.6、3.2；任务编排 4.2、4.3、4.7；整体方案 2.2。

**验收场景**：模型调用超时、效果未知之后，下一次准备类模型调用和普通行动都能准入；付款动作效果未知时，新的目标动作被拒绝并返回专门的错误码，核对查询（收尾类）仍能准入；另一个任务不受影响。

## X-03 P4 与 P5 的先后在多篇文档中写反或缺失

**文档事实**

权威顺序见[出口闸门 4.1](../architecture/core/egress/README.md#41-正常调用)和[核心契约 2.6](../architecture/core/contracts/README.md#26-四道门禁)：P4 在裁决域核验并返回开始回执，**之后**执行管理在 P5 写下 `DISPATCH_POSSIBLE`，再发生 I/O。下列位置与之不符：

| 位置 | 现行写法 |
| --- | --- |
| [核心契约 4](../architecture/core/contracts/README.md#4-关键流程) 第 7 步 | "持久点 7 执行管理：保存尝试并标记 `DISPATCH_POSSIBLE`；出口闸门在 P4 核验……后调用"：P5 写在 P4 之前 |
| [持久工作 4.5](../architecture/core/durable/README.md) | "登记尝试：……并标记 `DISPATCH_POSSIBLE`"，下一行才"再核验一次当前的出口前提" |
| [执行管理 4.1](../architecture/core/ledger/README.md) | "开放出口"一步只写"出口闸门检查当前凭据、派发控制和重发安全条件"，没有 P4；第 3 节"开放出口"接口的错误包含"授权失效、预算不足"，像是执行管理自己检查 |
| [数据与存储 4.1](../architecture/topics/data-and-storage.md#41-准入交接与执行) 第 7 步 | "出口核验条件、当前权限和端点"与"保存尝试和可能已发出"写在同一步（D5），没有说明 P4 在裁决域 |
| [部署 3](../architecture/topics/deployment.md) | 接口"核验出口并登记尝试（授权、执行管理、出口闸门）"把裁决域的 P4 和执行管理的登记合成一个接口 |

**问题**

照前两处实现，会先写 `DISPATCH_POSSIBLE` 再请求 P4。P4 一旦因取消、撤销或控制代次被拒绝，动作已经是 `UNKNOWN`，只能走外部终局核验，用不上内部封闭证明；[执行管理 2.3](../architecture/core/ledger/README.md#23-收尾依据)"P4 已返回开始回执、P5 尚未成立时……可以走内部路径"的设计也失去意义。取消与发送的竞争（M1 退出标准之一）因此会把本可收尾的动作变成长期未知。

**建议**

以出口闸门 4.1 为唯一来源，上表各处改为引用它，不再复述顺序；执行管理第 3 节的"开放出口"改名为 P5 对应的接口，输入必须包含开始回执，错误中删去由 P4 负责的授权和预算项。

**落点**：核心契约 4；持久工作 4.5；执行管理 3、4.1；数据与存储 4.1；部署 3。

**验收场景**：在 P4 之前取消，尝试阶段停在 `REGISTERED`，效果 `NOT_APPLIED`、迟到可能性 `RULED_OUT`，原执行管理负责方能出具内部封闭证明；在 P4 之后、P5 之前取消并由执行端点确认封闭胜出，结果相同；P5 之后取消，保持未知并进入核对。

## X-04 默认部署下离线开始已准入动作与 P4 在裁决域执行相矛盾

**文档事实**

- 开始门禁"每次开始发送前在**裁决域**再检查一次"，开始-2 比较控制代次，开始-5 由预算占用发送额度（[核心契约 2.6](../architecture/core/contracts/README.md#26-四道门禁)）。默认部署中裁决域在云端（[分层与模块 10](../architecture/layers.md#10-部署映射)）。
- 下列文档却写明端侧断网时，已准入、尚未开始的动作在"本地能证明当前授权仍然有效"时可以启动：[分层与模块 8.2](../architecture/layers.md#82-故障时谁负责)"端侧断网"一行、[执行管理 4.5](../architecture/core/ledger/README.md#45-端侧补传与云端对账) 第 2 步、[部署](../architecture/topics/deployment.md)开头"离线继续的边界"和 [4.2](../architecture/topics/deployment.md#42-断网与重连)"新出口检查"、[预算 4.5](../architecture/core/budget/README.md) 离线分配（"端侧出口闸门只接受这组既有动作；每次本地消费前原子记录尝试和消费序号"）、[项目目标 C5](../architecture/project-goals.md#c5-任务运行与端云协同) 验收要点"本地能证明当前授权有效的步骤可以离线继续"。
- [授权 4.5](../architecture/core/grants/README.md#45-撤销与出口的竞争离线) 的离线表反而写明：只有"完整的裁决域和必要事实从创建时起就归本地持有"才能继续。

**问题**

在默认部署下，控制代次和发送额度都只在云端裁决域里，端侧永远无法在本地完成 P4，所以"离线开始已准入的动作"实际上不可能发生。几篇文档（含层级 0 的 C5 验收要点）给出的承诺不成立，预算的离线分配设计也没有可用的路径。M3 的实现者面对两种互斥的读法：要么照字面在端侧做一个本地 P4（会破坏控制代次围栏和撤销语义），要么照契约离线时一律不开始。

**建议**

建议采用"默认部署离线时不开始任何新发送"：

1. 层级 0 先改：C5 验收要点改为"已经开始的本机动作离线继续记录和核对；尚未开始的动作，只有在端侧独立持有任务的部署中才能离线开始"；
2. 分层 8.2、执行管理 4.5、部署 4.2 按同一口径修改，引用授权 4.5 的离线表；
3. 预算 4.5 的离线分配要么移到"端侧独立持有任务"方案下，要么删除；
4. 如果确有"先在线取得开始资格、离线后再发送"的需求，另写 ADR 设计"预取的开始资格"，并写明它与控制代次围栏、撤销两阶段的关系。不建议在 M3 默认引入。

**落点**：项目目标 C5；分层与模块 8.2；执行管理 4.5；部署开头与 4.2；预算 4.5；授权 4.5（作为权威位置）。

**验收场景（M3）**：动作已准入、尚未开始时端侧断网，期间云端撤销授权；断网期间动作不发送；重连后 P4 拒绝。对照：断网时已经过 P5 的动作继续记录，重连后补传并核对。

## X-05 内容控制元数据是否属于裁决域事务，表述不一

**文档事实**

- [分层与模块 4](../architecture/layers.md#4-核心)："内容治理的控制元数据与裁决域**同处一个事务设施**"；[数据与存储 1.1](../architecture/topics/data-and-storage.md#11-事实归属与事务域)"与裁决域同一事务设施"。
- [存储归属图](../architecture/assets/storage-domains.svg)写"参与同一事务"，[行动主线图](../architecture/assets/system-boundaries.svg)写"内容控制元数据加入同一事务"。
- 准入-6、准入-10、开始-4 都在裁决域事务中检查内容和记忆（[核心契约 2.6](../architecture/core/contracts/README.md#26-四道门禁)）。
- 但[内容治理](../architecture/core/content/README.md)多处写"内容域"：4.1 第 3 步"在内容域持久写入暂存登记"、4.2 第 1 步"在内容域预登记"、M1 范围"内容登记、派生产物和回执按正式的 R7 实现"；[会话 4.1](../architecture/core/sessions/README.md#41-输入的记录与任务接纳) 第 2 步"内容治理持久接纳；跨域交接按 R7"；[交互适配器 4.1](../architecture/ports/interaction/README.md) 第 4 步"跨内容治理域的交接按 R7"。
- 术语表没有"事务设施"，也没有"内容域"。

**问题**

"同一事务设施"可以读成"同一个数据库、各自开事务"，也可以读成"加入裁决域的同一事务"。两种读法对实现影响很大：前者要求内容登记按 R7 进出，准入事务读取内容状态时与撤回之间没有串行保证；后者要求内容控制写入与准入共用一个事务上下文。M1 的功能规格（`.scratch/m1-recoverable-mainline/spec.md` 的"事务域保持正式边界"一段）已把内容治理列为与裁决域并列的独立事务域，说明分歧已经进入实现计划。

**建议**

建议在分层与模块 4 明确（并在术语表增加"事务域"条目）：

- 内容治理的**控制元数据和记忆记录**属于裁决域事务域，通过内部接口加入裁决域的唯一事务上下文；
- 内容正文、索引和派生存储不在其中，按 R7 交接；
- 来自其他事务域（执行管理回报的证据、会话收到的附件）的内容登记，按 R7 交给裁决域，由内容模块在裁决域事务中写入；
- 删去"内容域"一词，或定义为"裁决域中由内容模块写入的那部分事实"。

如果最终选择"独立事务域"，就必须改写准入-6、准入-10、开始-4 的实现方式，并给出内容治理 3"联合使用检查"中读取围栏的完整协议，代价明显更高。

**落点**：项目目标第 3 节（新增术语）；分层与模块 4；数据与存储 1.1；内容治理 1、4.1、4.2、9；会话 4.1；交互适配器 4.1；两张 SVG。

**验收场景**：准入事务读取内容可用状态时，并发提交该内容的撤回；只有两种结果——撤回先提交则准入被拒，准入先提交则 P4 因开始-4 拒绝发送。执行管理回报的工具结果，按 R7 交接后才成为可用内容。

## X-06 核心模块之间的代码依赖与内部接口位置没有定义

**文档事实**

- [分层与模块 R6、11](../architecture/layers.md#11-代码组织)：核心模块"依赖公共契约和自己声明的内部接口"；"模块私有代码放在 `core/<模块>/internal/`，由编译器阻止其他模块导入"；`platform` "只使用 `core` 的公开接口"。
- [开发规范 3](../development.md#3-依赖规则)：`core/<模块>/` 可以依赖"`contracts/`、标准库、本模块声明的内部接口"；`infra/` 可以依赖"`core/` 声明的内部接口"。
- [ADR 0003](../adr/0003-replacement-classes-and-assembly.md) 第 4 条："裁决域只创建一个事务上下文，各模块通过内部接口加入"。
- 准入事务中，任务编排要调用授权的"核验并占用"、预算的"准入内检查与预留"、会话的"消费确认"、内容的使用检查（[任务编排 4.2](../architecture/core/tasks/README.md#42-准入)）。

**问题**

1. "内部接口"（ADR 0003 的概念）与 Go 的 `internal/` 目录同名不同义。如果内部接口声明在 `core/<模块>/internal/` 下，`infra/` 无法导入，也就无法实现它；
2. 共享的事务上下文类型由哪个包声明，骨架里没有对应目录；
3. 按开发规范 3 的字面，`core/tasks` 不能依赖 `core/grants`，任务编排就无法在同一事务中调用授权。可行的做法有两种（任务编排导入其他模块的导出 API；或任务编排声明端口、由其他模块实现、`cmd/` 装配），规范没有选；
4. `platform` 可以用的"`core` 的公开接口"和"公共契约"是什么关系，没有说明。

这些是 M1 第一张工单（骨架与 depguard 规则）的直接输入，不定就会在代码里各自发明。

**建议**

在开发规范 2、3 补一节"核心模块的包结构"，建议：

- `core/<模块>/`：模块的导出 API 和它声明、要求受信实现提供的接口（即 ADR 0003 的"内部接口"，在 Go 中是导出的接口类型）；
- `core/<模块>/internal/`：实现细节；
- 裁决域的事务上下文由一个专门的包声明（例如放在 `core/durable/`，或新增目录并先改文档规范的骨架）；
- 核心模块之间允许的导入方向列成表（例如任务编排可以导入授权、预算、会话、内容的导出 API，反向不允许，禁止成环），并写进 depguard 规则；
- 说明 `platform` 能导入哪些 `core` 包。

ADR 0003 中"内部接口"一词加注，说明它与 Go `internal/` 的区别。

**落点**：开发规范 2、3；分层与模块 11；ADR 0003（加注）。

**验收场景**：按新规则写一个骨架：`infra/sqlite` 实现任务编排声明的存储接口；任务编排在一个事务上下文中依次调用授权、预算、会话、内容的检查；任一核心模块导入其他模块的 `internal/` 时编译失败，违反方向表时 `make lint` 失败。

## X-07 任务模板与条件核验规则没有设计归属

**文档事实**

- M1 的条件集"只支持任务模板和显式条件列表，模板外的任务请用户澄清"（[任务编排 9](../architecture/core/tasks/README.md)）；"可以客观核验"的条件"由核心按固定规则判断"（任务编排 2.2）；受信任务模板"把义务类型与核验规则的能力绑定"。
- [推理接口 8](../architecture/ports/reasoner/README.md) 把"条件核验约定"列为待定。
- 没有文档说明模板和核验规则由谁编写、怎样审查和发布、用什么表达、属于哪类实现（核心裁决语义、受信实现还是配置），用户给出的"显式条件列表"又怎样绑定核验规则（用户不会写规则）。

**问题**

完成门禁的完成-5 依赖"合格证据"，M1 的 S2 示例需要"文件内容核验"和"消息发送证据"两类规则。没有规则清单和归属，M1 要么把规则硬编码在任务编排里（成为未经设计的核心语义），要么接受模型生成的规则（违反任务编排 2.2"不得注册恒真的规则"）。它与执行管理的"受信解释规则"性质相同，后者已在 [ADR 0003](../adr/0003-replacement-classes-and-assembly.md) 之后归入受信实现。

**建议**

在任务编排 2.2 后新增一小节（或写一篇 ADR）：

- 核验规则归入受信实现，与受信解释规则同类：随受审查的版本发布，第三方不能自带；
- M1 内置一份有限的规则目录，例如"文件存在且摘要等于"、"按查询接口核对目标对象状态"、"用户对绑定条件版本的评价"；
- 显式条件列表的每一项必须从目录中选择规则，否则视为需要用户评价的条件；
- 任务模板是随版本发布的受审查配置，写明模板的版本化和匹配方式。

**落点**：任务编排 2.2、9；推理接口 8；分层与模块的受信实现表；X-08 的代码位置。

## X-08 受信组件在代码骨架中没有位置

**文档事实**

- 受信宿主"捕获全部实际读取，核验任务的必要事实没有被裁掉，由受审查的供应商编码实现生成完整、固定的调用描述"（[任务编排 4.1](../architecture/core/tasks/README.md#41-创建任务与请求推理) 第 5 步、[推理接口 3](../architecture/ports/reasoner/README.md)）。
- 受信解释规则"属于受信实现……可以是核心支持的受限声明，也可以是经审查发布的实现"（[执行管理 2.3](../architecture/core/ledger/README.md#23-收尾依据)）；M1 的参考适配器"解析逻辑按受信规则审查"。

**问题**

**建议**

**落点**：开发规范 2、3；分层与模块 2 的三类替换资格表；推理接口 3；执行管理 2.3。

## X-12 P4 与预算的出口关联重复，安全重发的金额没有来源

**文档事实**

- [预算 2.4](../architecture/core/budget/README.md)：预留"已预留 → 可能计费"的条件是"出口前接纳了原执行尝试和出口关联"；4.1 第 3 步"执行前记录尝试、出口调用和预算绑定……预算接纳绑定后保存回执"。
- 预算 4.1 第 4 步：P4 占用一次发送额度，"与开始回执同事务绑定"。
- 预算 4.2："同一动作的安全重发如果会另外产生调用费，必须有新的出口计费关联和预算容量"。M1 预留是"按单次调用的费用上界"（预算 9），重发时"核心事先分配额外的发送额度"（[推理接口 2.1](../architecture/ports/reasoner/README.md#21-上下文快照)）只说次数。

**问题**

1. 每次发送前有两次进入裁决域的步骤：执行管理按 R7 把"出口关联"交给预算，再请求 P4。两者是否同一事务、哪个在前，没有规定；
2. 预算 2.4 的状态图没有"可能计费 → 未使用封闭"一条：出口关联已登记、P4 随后被拒绝时，预留无法释放；
3. 安全重发的金额从哪里预留没有规定：准入时只预留了一次调用的上界，P4 只占次数。

**建议**

把"出口关联登记"并入 P4 的同一裁决事务：P4 同时占用发送额度、登记出口关联、在需要时为本次发送追加金额预留；P4 被拒绝则什么都不登记。状态图补上 P4 拒绝或内部封闭证明后的释放路径。准入时的费用上界写明覆盖几次发送，或写明重发的追加预留规则。

**落点**：预算 2.4、4.1、4.2；核心契约开始-5；出口闸门 4.1。

**文档事实**

- [会话 2.3](../architecture/core/sessions/README.md)："输入请求声明答案是否会改变任务依据"；[任务编排 2.2](../architecture/core/tasks/README.md#22-条件证据与提议)："输入请求已由核心声明它不影响依据，接纳事务同时把 `bound_input_version` 推进到新版本，不进入处理门禁"。
- 输入请求来自推理的"向用户提问"提议（[推理接口 2.3](../architecture/ports/reasoner/README.md)），推理是不受信的可替换部分。

**问题**

没有写明"核心声明"依据什么。如果直接采用推理在提问时给出的标记，被提示注入控制的推理可以把关键问题（例如"发给谁"）标成"不改变依据"，用户的回答就会绕过输入处理门禁，旧的条件集立即适用，[任务编排 2.2](../architecture/core/tasks/README.md#22-条件证据与提议) 要防止的"答案被悄悄忽略"重新出现。

**建议**

写明规则：缺省视为"会改变任务依据"；只有受信模板或核心规则（例如只用于澄清措辞、不绑定任何条件字段的问题）才能声明"不改变"；推理的标记只能把问题标得更严格。

**落点**：会话 2.3；任务编排 2.2；推理接口 2.3。

## X-15 可信基础设施 I/O 能否承载业务载荷，表述冲突

**文档事实**

- 术语表"出口"：可信基础设施 I/O"只能使用固定身份和固定目标，不得承载扩展发起的请求"（[项目目标 3](../architecture/project-goals.md#3-核心术语)）；分层 R2 同义。
- [网关与 SDK 1](../architecture/platform/gateway/README.md)："端云之间的核心契约通信，包括握手、心跳、流控和命令回执，属于可信基础设施 I/O……**不得承载业务载荷**"。
- 端云之间的 R7 交接（动作意图及其参数、执行管理补传的事实、用户命令）本身就是业务载荷。

**问题**

按网关的写法，R7 交接和用户命令都不能走可信基础设施 I/O，只能当作出口经出口闸门，这又与"核心模块之间的交接属于可信基础设施 I/O"（持久工作 4.3）冲突。同步端侧内容时由谁做同步许可检查（出口闸门，还是 R7 发送方）也随之不清。

**建议**

以术语表为准，把网关的限制改为"不得承载扩展发起的请求和未经同步许可检查的内容正文"；写明端侧内容随 R7 上行时，由发送方在交接前调用内容治理的同步检查。

**落点**：网关与 SDK 1；必要时在项目目标第 3 节"出口"条目补一句。

## X-16 "必须写 ADR"的决定大量积压，文档状态没有采纳标准

**文档事实**

各模块"取舍"一节都以"正式采纳前必须写成 ADR"结尾，合计 80 余项（核心契约 3、持久工作 2、执行管理 4、任务编排 4、授权 4、预算 4、会话 3、内容治理 4、运行记录 5、出口闸门 4、推理 4、记忆 4、执行接口 4、交互接口 3、四个适配器 6、三项平台服务 10、四个专题 15）。现有 ADR 4 篇。[文档索引](../architecture/README.md#2-文档索引)中全部模块、流程和专题文档都是"草稿"。

**问题**

开发规范要求"代码只实现设计文档写明的规则"。没有规定"草稿"文档能否作为 M1 编码依据，也没有规定哪些 ADR 是 M1 的前置条件，"必须写 ADR"就会被整体忽略，或者阻塞全部编码。很多条目彼此重叠（例如"尝试标识的语义"出现在执行管理、执行接口两处）。

**建议**

1. 汇总一张 ADR 待办表（建议放在文档索引或文档规范），去重后按里程碑排序。M1 前建议只写真正难以撤回的几项，例如：全局标识与 UUIDv7、命令回执的保留、尝试标识与收尾依据、完成核验的封闭协议、授权消费的时机、计费来源身份；
2. 其余条目改写为"设计已在本文确定，变更时补 ADR"，删去"正式采纳前必须"的措辞；
3. 在文档规范中写明状态转为"已采纳"的条件，以及 M1 编码前哪些文档必须是"已采纳"。

**落点**：文档规范 1、6；文档索引；各模块"取舍"一节的末句。

## X-19 SQLite 驱动与内置版本没有选定

**文档事实**

- [数据与存储 5.4](../architecture/topics/data-and-storage.md#54-持久档位)：端侧固定的 SQLite 构建"必须包含"3.51.3 的 WAL 修复；平台准入表记录"SQLite 构建与 VFS"；每条写连接打开时核验实际设置，macOS 需要 `fullfsync=ON`。
- [ADR 0004](../adr/0004-language-and-stack.md) 和[开发规范](../development.md) 只写"SQLite"，没有选驱动。

**问题**

Go 访问 SQLite 有几类驱动：cgo 绑定（随驱动编译 SQLite 源码）、纯 Go 转译、基于 WASM 的实现（待验证各自的现状）。它们决定内置 SQLite 的版本能否固定到包含 3.51.3 的修复、`fullfsync` 等 pragma 是否生效、`make test -race` 和交叉编译的方式，以及 M3 能否复用到手机端。这是 M1 持久性验收（本地档、平台准入表）的直接前提。

**建议**

在 ADR 0004 增补（或另写 ADR）：选定的驱动、内置 SQLite 版本的固定方式、迁移工具；平台准入表增加"驱动与内置 SQLite 版本"字段。

**落点**：ADR 0004；数据与存储 5.4；开发规范 1。

## X-20 手机端执行部分的语言决定影响一致性测试的架构

**文档事实**

- [ADR 0004](../adr/0004-language-and-stack.md)：手机端执行部分的语言"未定，M3 前决定"；考虑过 Rust"便于将来嵌入手机端"。
- 端侧要部署执行管理、出口闸门和持久工作（[部署 2.2](../architecture/topics/deployment.md)），它们属于核心，"核心裁决语义只随受审查的版本发布"（[分层与模块 2](../architecture/layers.md#2-划分原则)）。
- [开发规范 5](../development.md#5-测试)：一致性测试放在 Go 的 `conformance/`；M1 规格的测试主切面是"进程内装配"。

**问题**

如果手机端不用 Go（例如 Kotlin、Swift 或 Rust），执行管理的故障语义就有第二份实现，必须通过同一套故障注入。M1 的测试如果全部是 Go 进程内调用，M3 就无法复用。

**建议**

在 ADR 0004 写明约束：手机端优先复用 Go 核心（例如以库的形式嵌入，可行性待验证）；如果不复用，执行管理和出口闸门的一致性测试必须能通过公共契约以黑盒方式驱动。M1 的测试 harness 据此至少把"通过公共契约命令驱动、断言持久记录与模拟目标"这一层与进程内装配分开。

**落点**：ADR 0004；开发规范 5；文档规范 2 的 `verification/`。
