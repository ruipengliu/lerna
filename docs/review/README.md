## 1 结论

12 条意见中，11 条指出的问题经核对属实，1 条是性能优化提议。

| 决定 | 条数 | 编号 |
| --- | --- | --- |
| 采纳 | 6 | RV1、RV2、RV3、RV6、RV8、RV9 |
| 采纳，按本文简化 | 3 | RV4（合并 RV5）、RV7、RV10 |
| 部分采纳 | 1 | RV11 |
| 暂不采纳，保留为候选 | 1 | RV12 |

原意见揭示的问题可归为两类：

1. **状态模型互相矛盾或走不通**（RV1、RV2、RV3、RV6）：两篇文档对同一对象给出不同定义，或者状态机里缺少一条必要的转换。照文档实现，开发者会得出不同结果，甚至出现无路可走的状态。
2. **承诺大于机制**（RV4、RV5、RV7、RV8、RV10、RV11）：文档宣称了某项保证，但给出的机制只能覆盖其中一部分。例如单机同步提交被说成满足"承受可用区故障"。

由第 2 类得出一条贯穿全局的调整原则：**每项保证都必须写明覆盖范围；范围外的情况如实报告，不暗中降级。**这条原则已写入[整体方案第 1 节](../architecture/overview.md#1-结论先行)。

处理时遵循三条取舍：

- 能用现有记录解决的，不新建一套事实（例如用云端已有的开始回执检测端侧回滚）；
- 两个方案都可行时，M1 先选实现面更小的一个，另一个记为候选；
- 原意见中需要实测才能判断收益的部分，不在测量前采纳。

## 3 逐项处理

每项按"核对结果 → 决定和理由 → 调整后的方案 → 落点"组织。

### RV1 命令身份统一为一个类型

**核对结果。**[核心契约 3.1](../architecture/core/contracts/README.md#31-命令回执查询通知与错误)的幂等范围是 `(user_id, issuer_id, target_domain_id, command_id)`；[网关 2](../architecture/platform/gateway/README.md#2-对象与状态)写成"用户 + 接纳责任域 + command_id"，并声称两者一致。两个调用者用同一个 `command_id` 时，按网关文档实现会互相覆盖。

**决定：采纳。**这是协议的直接矛盾，必须在冻结 SDK 协议前修正。

**调整后的方案。**

- 核心契约定义唯一的 `CommandIdentity`，即上述四元组。提交、查询、回执、交接、SDK 待发记录和退役记录都引用它，各文档不再自行列字段。
- `issuer_id` 由认证得到的主体决定，核心核验该主体是否有权使用这个命名空间；不得采信正文自报的值。
- 刷新令牌、重连、更换网关、重启进程、轮换密钥，都不改变原命令的 `issuer_id`。
- 已退役的命名空间不得分配给新的安装实例。
- 跨域交接时，源域以自己的固定服务命名空间创建目标命令，并保存源命令到目标命令的映射。

**落点：**核心契约 3.1；网关 2、3、4.1；持久工作 2.1 改为引用该类型。

### RV2 命令的"已受理"和"已决定"分开表达

**核对结果。**[持久工作 2.1](../architecture/core/durable/README.md#21-命令回执)只允许"不存在 → 已接受/已拒绝"，且决定永不改变。[网关 4.1](../architecture/platform/gateway/README.md#41-用户命令的持久交接)却允许异步命令在 P2 先返回接纳回执、P4 再做决定。若把 P2 的回执当作决定，P4 发现预算不足时就无法拒绝。

**决定：采纳，在原意见基础上简化。**原意见提出新增 `CommandSubmission` 和 `CommandDecision` 两类记录。本文改为**同一条命令记录增加一个"已受理"阶段**，效果相同，少一类对象。

**调整后的方案。**

- 命令记录的状态改为：
  - 同步命令：`不存在 → 已接受 / 已拒绝`（一个事务）；
  - 异步命令：`不存在 → 已受理 → 已接受 / 已拒绝`。
- "已受理"表示系统已承担给出决定的责任，**不是业务决定**。决定字段只写一次，写入后不变。
- 回执分两种：受理回执和决定回执。业务上的 `ACCEPTED`/`REJECTED` 只出现在决定回执中，不与受理状态共用一个枚举。
- 查询结果有五种：尚未发现、已受理待决定、已有决定、已退役、无法查询。"尚未发现"不证明未提交。
- 只有确定的业务原因才写"已拒绝"。暂时不可达、复制待核实不得写成拒绝。
- 界面可显示"已提交，等待核验"；只有决定回执为接受后，才显示"已准入"。

**落点：**核心契约 3.1 的回执与查询；持久工作 2.1 的状态转换；网关 4.1 的 P2/P4 和 SDK 查询。M1 只实现同步路径时，契约也必须先定义好异步阶段，避免以后改协议。

### RV3 授权的有效性与次数消耗分开

**核对结果。**[授权 2.3](../architecture/core/grants/README.md#23-授权使用记录)规定"次数耗尽只禁止新的准入，已经绑定的动作仍要检查撤销"。但[授权 2.5](../architecture/core/grants/README.md#25-状态)和[核心契约 2.5](../architecture/core/contracts/README.md#25-状态模型)把 `CONSUMED` 写成与 `REVOKED` 并列的终态。一次性授权被占用后，用户撤销它，状态机里没有合法转换。

**决定：采纳。**正文意图正确，状态模型没有表达出来。M1 的付款逐次确认就会用到一次性授权。

**调整后的方案。**

| 维度 | 表达方式 |
| --- | --- |
| 控制状态 | 只有 `ACTIVE`、`REVOKED`；撤销另有完成状态 `PENDING → COMPLETE` |
| 时间有效性 | 按权威时间与有效期计算，不写成状态 |
| 剩余次数 | 由使用池的上限和已占用记录计算，不写成状态 |

界面可以显示"已用完""已过期"，但它们是计算出的展示值，不是控制状态。任何时候都可以撤销。

两种核验分开定义：

| 核验 | 必须检查 |
| --- | --- |
| 新准入 | 授权链有效、未过期、用途匹配、**还有剩余次数**；原子建立使用记录 |
| 已准入动作的出口 | 存在与该动作精确匹配的使用记录；授权链未撤销、未过期；任务控制允许。**不再要求剩余次数** |

**落点：**核心契约 2.5；授权 2.3、2.5 和凭据签发前置条件；出口闸门的核验步骤。

### RV4 持久性按部署档位声明（合并 RV5）

**核对结果。**[G3](../architecture/project-goals.md#4-不变量)要求持久记录承受主机故障和单可用区故障。[数据与存储 5.4](../architecture/topics/data-and-storage.md#54-持久档位)给 M1 和端侧账本用的本地同步提交不覆盖设备永久丢失，却称"与 G3 一致"。RV5 进一步指出：SQLite 的 `synchronous=FULL` 在 macOS 上不会自动启用 `F_FULLFSYNC`，设备缓存可能未刷新。

**决定：采纳原意见的第一条路线（部署档位），并把 RV5 并入。**第二条路线要求端侧每次确认前同步到另一个故障域，会使离线执行失效，与 M3 的离线目标冲突，不采纳。

**调整后的方案。**

G3 改为：**确认或执行前，记录必须达到所声明的持久档位。**档位如下：

| 档位 | 覆盖 | 不覆盖 | 用于 |
| --- | --- | --- | --- |
| 本地档 | 进程崩溃、重启、掉电（以经过验证的平台组合为限） | 存储介质永久丢失 | M1、开发环境、端侧账本 |
| 云端生产档 | 以上全部，加主机和单个可用区永久丢失 | 多个可用区同时丢失 | 云端生产的权威记录 |

- 档位是部署配置，写入负责域配置和接纳回执。客户端不得通过请求降级；副本失联时不得临时降档。
- 端侧账本的介质永久丢失后，云端显示"设备记录不可恢复，效果未知"，保留原负责方，不重发。这守住 G1，但不算满足 G3 的云端生产档。
- 本地档的"掉电"覆盖只对**平台准入表**中列出的组合成立。准入表由部署层维护，数据库和文件适配器共用，记录 OS、文件系统、SQLite 构建与 VFS、同步配置、实际使用的屏障原语和验证证据。
- 每条写连接打开时核验实际设置。macOS 默认 VFS 下，候选配置为 `journal_mode=WAL`、`synchronous=FULL`、`fullfsync=ON`。核验失败或平台未经验证时，不开放依赖掉电保证的能力。
- 杀进程测试通过不得记作掉电验收通过。

原意见要求在 M1 就验证多个平台。本文简化为：**M1 只验证开发和测试用的一个平台组合；端侧平台在 M3 逐个加入准入表。**

**落点：**项目目标 G3、第 11 节 M1 和 M6 的退出标准（改动已采纳文档，负责人已确认，见 [ADR 0001](../adr/0001-durability-profiles.md)）；数据与存储 5.4、9；持久工作 6；部署的故障矩阵；文件适配器 4.1、8。

### RV6 完成核验被拒绝后，任务可以继续

**核对结果。**[任务编排 4.7](../architecture/core/tasks/README.md#47-完成门禁)第一阶段先"封闭新的目标准入和子任务创建"，第二阶段才核验。核验发现目标确实未达成（例如附录还没写）时，唯一出口是"以收尾用途准入核对动作"，而收尾用途不得推进目标。任务因此卡死，只能非成功关闭。

**决定：采纳，状态数比原意见少。**原意见设计了四个核验状态。本文只区分"任务冻结"与"动作封闭"，用轮次表达其余内容。

**调整后的方案。**

- 每次完成核验是一个**核验轮次**，带单调递增的轮次号，绑定冻结时的条件版本、输入版本、控制代次和动作清单。
- 开始核验时：
  - **任务层面**只是暂时冻结新的目标准入；
  - **动作层面**对清单中尚未开始的意图发出封闭。封闭只针对清单里的这些动作，永久有效，不覆盖以后的新动作。
- 核验结果有三种：
  1. 通过：原子保存核验记录，以 `SUCCEEDED` 关闭；
  2. 缺证据：保留本轮，以收尾用途准入观察动作，取得证据后重新核验（与现有规则相同）；
  3. 目标未达成：保存逐项缺口，结束本轮。若任务仍开放、版本一致、没有阻断性的未知效果，就在**一个事务**中解除任务冻结、递增规划代次、登记新的提议请求。
- 补齐缺口必须创建新动作，重新检查授权、预算和确认。不得恢复已封闭的旧动作，不得复用已消费的确认。
- 取消、暂停、条件修改与"继续"通过预期版本竞争，用户控制优先。迟到的旧封闭回执只影响旧清单。

另增一条**有前提的活性断言**：依赖恢复、授权和预算有效、无用户停止、无阻断性未知时，被拒绝的核验必须最终进入"重新规划""明确等待"或"非成功关闭"之一，不得无原因地停在冻结状态。这条思路推广到全部恢复流程，见第 4 节。

**落点：**任务编排 2.1 状态表、3.2 接口、4.7；动作账本 2.2 的封闭范围改为"按清单"。

### RV7 端侧账本恢复前先检测回滚

**核对结果。**[部署](../architecture/topics/deployment.md)定义了"账本连续性标识"，但标识存在账本里，会随账本快照一起回退；字段级判据仍是待定事项。Android 默认自动备份会包含应用数据库，所以系统自动还原是常见路径，不只是人工运维。

**决定：采纳，按本文简化。**原意见提出了五项措施。本文保留可在 M3 落实的四项，把"独立的单调见证"改为明确的能力边界。

**调整后的方案。**

1. **启动状态。**端侧账本启动时处于"待验证"，通过后才"允许恢复"，发现问题则进入"恢复隔离"。领取工作、P4 开始和 P5 出口都必须先检查启动状态。
2. **复用云端回执作为见证。**重连时，对比云端已记录的开始回执与本地记录。云端有、本地没有，说明本地倒退：该尝试视为未知，停止该范围内的新发送，转入核对。不新建跨模块账本。
3. **备份与迁移默认隔离。**账本和端点绑定密钥排除在平台云备份和设备迁移之外（Android 用数据提取规则配置）。任何导入的备份都进入恢复隔离。
4. **能力边界。**离线期间、没有云端见证时，无法检测同一设备上的快照回退。文档明确写出这一边界：此类部署不承诺回滚检测，也不得用"连续性检查通过"之类的布尔值掩盖。

**落点：**核心契约（连续性判据字段）；部署 2.3、4.2、8；动作账本 4.5；数据与存储 5.3。

### RV8 受管理文件：覆盖前先交接前驱证据

**核对结果。**[文件适配器 4.2](../architecture/adapters/file.md#42-受管理的版本布局)称提交指针能证明"原动作是否提交"。但动作 A 发布后、账本保存回报前崩溃，写者 B 随后发布，指针只剩 B，A 是否发布过就无法证明。

**决定：采纳原意见的较小方案（串行交接）。**提交链方案允许更高并发，但需要历史遍历和回收，M1 不需要。

**调整后的方案。**

- 写者在稳定锁内读取当前提交。覆盖前，确认该提交的发布证据已被账本持久接纳。
- 前驱没有回报时，先核对并补交前驱证据。账本不可用或核对未完成时，**阻止该目标的覆盖**。
- 代价：账本不可用期间，同一目标不能写入。这是有意的取舍，写入文件接口说明。
- 孤立的不可变对象（未被指针引用）不得判为已发布。不得通过重新发布 A 覆盖 B 来"核对"。

**落点：**文件适配器 3、4.1、4.2、5。

### RV9 授权区分"操作权利"和"处理目的"

**核对结果。**[核心契约](../architecture/core/contracts/README.md)和[授权 2.1](../architecture/core/grants/README.md)的 `purposes[]` 只有读取、保存、同步、行动四值；[运行记录 4.6](../architecture/core/trace/README.md)和[评测与进化](../architecture/platform/eval/README.md)却要求区分诊断、评测、生成改进。同一主体读取同一份记录，用于诊断和用于生成 Skill，四值集合无法区分。

**决定：采纳独立字段方案。**原意见的备选方案（把目的编进动作名，如 `trace.read_for_diagnosis`）会让动作数量随目的成倍增加，不采纳。

**调整后的方案。**

- 术语拆分：原"用途"改称**操作权利**（读取、保存、同步、行动）；新增**处理目的**（为什么处理这份数据）。字段为 `use_rights[]` 和 `processing_purposes[]`。
- 首批处理目的：当前任务、个性化、诊断、评测、生成改进。目的集合带语义版本。
- 缺省不等于全部；新增的目的不自动包含在旧授权中。
- 委派只能缩小目的集合；派生内容的目的上限取全部输入的交集，交集为空时不发布。
- 处理目的由受信的任务编排或平台工作流绑定，在读取、模型调用、派生发布和导出时核验。扩展或推理不能靠改参数获得新目的。

**落点：**项目目标第 3 节术语和 G8（改动已采纳文档，负责人已确认，见 [ADR 0002](../adr/0002-processing-purposes.md)）；核心契约 Grant 与凭据；授权 2.1、2.2；内容治理的用途上限与派生交集；运行记录 4.6。

### RV10 不可信扩展：每次调用用干净实例

**核对结果。**[扩展清单](../architecture/platform/extensions/README.md)允许"私有状态"，只禁止共享可变状态。插件第一次读取私密内容 A 后留在内存，第二次只读公开内容 B 却用 A 改写输出；宿主只看到 B 的读取，来源登记漏掉 A。

**决定：采纳原意见的基线方案。**备选的"宿主累计实例来源集合"会扩大删除扇出、需要并发串行化，等实测证明干净实例成本不可接受时再议。

**调整后的方案。**

- 每个不可信计算工作使用新的隔离实例。可以复用编译产物，不得复用接触过用户内容的可变内存。
- 跨调用的状态只能作为派生产物交还核心，登记完整来源；下一次通过受控读取重新载入。
- 扩展清单的"私有状态模式"只允许两种：调用结束即销毁；由核心管理的显式状态引用。
- 生成登记增加宿主分配的实例标识；输入清单由宿主生成，插件只能补充，不能减少。

**落点：**扩展管理清单与就绪契约；内容治理的生成登记；记忆接口；安全专题。M1 的默认实现属于可信边界，不受影响。

### RV11 完成门禁的覆盖边界

**核对结果。**G2 证明的是"已登记的必要条件都有证据"。如果初始条件漏抽了一项，或者核验规则只检查"文件存在"，后续证据链全部真实，结论仍然错误。

**决定：部分采纳。**问题成立，但从自然语言到条件的完整性无法用机制证明。原意见要求为每个输入片段建立覆盖映射记录；这类记录本身仍由模型抽取，会制造"已证明完整"的错觉，而实现成本很高，因此**不采纳覆盖映射记录**。采纳以下四项：

1. **写明 G2 的保证边界。**核心证明的是"已接纳的条件都有证据"，不证明条件集完整表达了用户意图。
2. **条件集要先被接纳。**条件集处于"整理中"时，不得据此判定成功。
3. **削弱核验规则与删除条件同权。**把核验规则换成证据强度更弱的规则，需要与删除必要条件相同的可信依据。推理不得注册恒真的核验规则。
4. **结果透明。**Result 列出本次核验了哪些条件、各用什么规则，并标出由模型整理的条件。用户能直接看到"系统检查了什么"。

M1 只支持任务模板和显式条件列表，模板外的任务请用户澄清。评测平台以原始用户请求作为独立评分输入，不只按被测 Agent 抽出的条件评分。

**落点：**项目目标 G2 的说明（措辞补充，不改规则）；任务编排 2.2、4.1、4.7；评测与进化。

### RV12 同库事务折叠：暂不采纳

**核对结果。**[持久工作 4.3](../architecture/core/durable/README.md#43-跨域交接r7)要求同一数据库内的跨域交接也保留三次独立提交。原意见建议允许同库时合并为一次事务。原意见自己也说明：这不是缺陷，收益未经测量，不应成为 M1 阻塞项。

**决定：暂不采纳，保留为 M6 候选。**理由：

- 引入两种交接实现，故障测试矩阵翻倍，与 M1"先做出一条能恢复的主线"相反；
- 统一 R7 是[分层与模块](../architecture/layers.md)已采纳的取舍，换来"拆分部署时故障语义不变"；
- 没有基准数据，无法判断三次提交是否是瓶颈。

**重新评估的触发条件：**M6 容量测试显示交接提交在尾延迟或写入量中占主要比例。届时按原意见第 5–7 段的方法比较两种装配，先写 ADR 再改实现。

原意见中"用小状态模型检查交接与恢复的活性"一项与本优化无关，予以采纳，见第 4 节。
