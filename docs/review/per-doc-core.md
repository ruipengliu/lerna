## 出口闸门

文档：[core/egress/README.md](../architecture/core/egress/README.md)

结论：P1–P8 的持久化点、P4 作为执行开始的排序点、禁止隐藏重试、DNS 与 SSRF 的处理都清楚，是其他文档的权威来源。需要把"出口执行"的状态对应到契约枚举，并写明非模型动作在 P4 比较的是什么。

| 编号 | 优先级 | 位置 | 意见 | 建议 |
| --- | --- | --- | --- | --- |
| EG-01 | P2 | 第 2 节状态表 | "出口执行：已接纳 → 待核验 → 开始已记录 → 可能已发出 → 回报已持久 / 待核对"是一套新状态，与契约的尝试阶段（`REGISTERED → DISPATCH_POSSIBLE → OBSERVED`）不对应；同一节又说"出口闸门不拥有新的事实"，读者无法判断这些状态由谁保存 | 写明每个状态对应哪个负责方的哪个字段（例如"开始已记录"是裁决域的开始回执，"可能已发出"是尝试阶段 `DISPATCH_POSSIBLE`），或改为展示值 |
| EG-02 | P2 | 2 出口凭据 | 绑定尝试和发送序号，与授权的签发时机矛盾 | 见 X-11 |
| EG-03 | P2 | 4.1 第 3–4 步 | 第 3 步"适配器构造受约束的调用描述"发生在准入之后，P4 再核验"描述……是否与准入一致"。模型调用在准入前已封存描述，可以逐字比较；API 和文件动作准入时只固定了参数（执行管理有 `request_digest`），适配器之后生成的请求与准入怎样比较没有写 | 写明非模型动作在准入时固定的是哪种规范化表示，适配器生成的请求怎样映射回去比较；做不到逐字节一致的协议，写明允许的转换（2 中"允许的协议转换版本"） |
| EG-04 | P3 | 4.1 两张时序图 | 第一张由出口闸门向裁决域请求开始，第二张（取消竞争）由"执行管理（执行端点）"请求 | 统一参与者 |
| EG-05 | P3 | 4.5 | 插件沙箱首选 Wasmtime，没有考虑 Go 宿主的选择 | 见 X-18 |

相关跨文档意见：X-03、X-11、X-12、X-16、X-18。
