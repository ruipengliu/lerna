# 持久接纳与业务决定需要两个明确的回执契约

建议把“接下处理责任”和“作出业务决定”在公共契约中分成两类不可混淆的记录。现有异步流程需要前者，持久工作只定义后者。优先级高：开发者按两篇文档分别实现，会对同一个 ACCEPTED 得出不同含义。

---

定位：[持久工作第 2.1 节](../architecture/core/durable/README.md#21-命令回执)第 57 行只允许“不存在→已接受/已拒绝”，原决定永不改变；第 4.1 节要求业务决定、回执与业务修改同事务。[网关与 SDK 第 4.1 节](../architecture/platform/gateway/README.md#41-用户命令的持久交接)第 92–97 行允许 P2 先记录命令和待办、返回接纳回执，P4 随后才做业务决定。[核心契约第 3.1 节](../architecture/core/contracts/README.md#31-命令回执查询通知与错误)的回执只定义 ACCEPTED/REJECTED，没有区分这两个阶段的类型。

---

反例：异步提交一个尚未核验预算的准入命令，P2 返回 ACCEPTED；P4 发现预算不足。如果把 P2 的回执当作持久工作的原决定，就不能再拒绝，重投也只会返回已经接受；如果把它改成 REJECTED，又违反原决定不可变。另一种实现会另建后台命令，但目前缺少后台命令与原命令、查询状态之间的固定映射。问题在于缺类型和迁移规则，并非说异步受理本身不成立。

---

修改方案：公共协议增加 CommandSubmission 与 CommandDecision 两种事实。Submission 保存完整命令身份、指纹、输入引用、接纳时刻和业务处理待办，表示“系统已承担给出决定的责任”；Decision 保存唯一且不可变的接受/拒绝决定、稳定错误码与结果引用。Submission 的处理视图可从 PENDING 到 DECIDED，但决定本身不变。同步命令在一个事务中写齐两种记录；异步命令 P2 写 Submission 与待办，P4 原子写 Decision、业务事实和后续交接。两种路径使用同一命令身份，不分配新的外部动作身份。

重复投递只校验身份和指纹，返回已有 Submission 以及可用的 Decision，不再创建待办。后台工作按原 Submission 身份推进，领取代次只控制当前工作者。P4 遇到确定的业务拒绝才固定 Decision；暂时不可达、复制待核实不能被伪装成永久拒绝。用户在 P2 与 P4 之间撤销权限时，P4 检查当前事实并拒绝新的行动，保留当初接纳处理责任的事实。

---

SDK 查询返回一个有明确变体的结果：尚未发现、已接纳待决定、已有决定、已退役，另列无法查询；“尚未发现”仍不证明未提交。UI 可以显示“已提交，等待核验”，只有对应的准入 Decision 接受后才显示“已准入”。快照和通知只投影这些记录，不产生第三套事实。原来的业务 ACCEPTED 可以保留名称，但必须被包在 Decision 类型中，不能与受理状态共用一个无上下文枚举。

---

改动落点：contracts 的对象表、回执和错误模型，durable 的状态与执行命令接口，gateway 的 P2/P4、SDK 查询及恢复；sessions 如采用异步接纳也引用同一协议。验收在 P2 后、P4 前反复崩溃；等待期间改变授权、预算和条件；并发重投原命令；验证最多一个 Submission、一个最终 Decision、一组合法业务效果，拒绝不被早先的“已接纳”覆盖。

---

一手依据：[RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)明确区分已接受处理与处理完成，且处理时可能不被允许，并建议提供状态查询入口。它不替 Lerna 规定持久性；上面的双记录方案是为闭合现有 P2/P4 流程提出的设计建议。（2026-10-04 核查。）
