# 第三轮架构评审

本轮任务是：在第二轮调整完成后重新审核 `docs/architecture`，查缺补漏，必要时提出更好的整体方案；每个评审点附修改方案，按 writing-fragments 分别保存。现有第二轮的十篇意见、一篇分层分析、总览和处理记录，共 13 个文件，已经移到 [archive/round-2](../round-2/README.md)；第一轮保留在 [archive/round-1](../round-1/README.md)。归档正文保持原样，只调整相对链接，并同步改址现行架构与 ADR 中的历史引用。

评审基线是提交 `cadd519`（第二轮决定已写入设计文档）。以下六项是新的评审建议，尚未成为架构决定；本轮没有替用户改写正式方案。文中触发场景是对设计契约的事件顺序推演，不是已有运行实现的缺陷复现报告。

---

整体判断：继续采用现有的核心与可替换部分划分。任务、会话、授权、预算以及参与裁决的内容控制元数据共处一个事务设施，动作账本靠近执行端点，跨域按 R7 交接，方向合理。ADR 0003 已经补齐“必须受信”与“可以替换”的区别，现在没有足够依据推翻这些边界或再拆一组服务。

本轮最重要的三个问题发生在状态转换的交界：新输入已经接纳，但条件依据尚未处理；核验已经拒绝，但仍持有冻结；父任务控制已经变化，但子动作尚未开始。它们都不能仅靠最新版本号、异步通知或重试解决。

---

更好的整体修订方向，是把已经分散定义的资格检查组织成少量明确的内部入口，并由原事实写入方维护规则：

- 任务编排判断输入是否已处理、条件是否适用于当前输入、当前任务及祖先是否允许推进；
- 内容模块判断治理许可与语义依据是否仍适用于这一次使用；
- 准入记录固定当时采用的准确依据，P4 与发布、完成事务按当前事实重新检查；
- 每个等待都保存负责对象、唤醒依据和失效后的处置路径，不能只有一个阻塞状态；
- 原始观察、策略解释和核心裁决保留各自的来源，恢复时仍能判断哪条路径可信。

这些入口是现有模块内部的代码组织建议，不是新增在线授权中心或通用规则服务；调用同一个判定逻辑，也不意味着跨数据库自动获得原子性。局部事实在现有事务内裁决，跨域仍按现有协议保留等待与未知。无需把所有业务对象塞进统一状态机，也无需为这六项引入新的数据库。

M1 可以先把“输入修改—模型准备—单次调用—动作—核验拒绝—恢复”做成一条可检查的执行历史；M2 加入记忆纠正，M4 加入祖先控制与第三方证据。相比继续增加抽象层，这样更能检验当前模块边界是否足够清楚。

---

`docs/research` 中的输入生命周期、工程切片、记忆投影与调用恢复材料用于比较思路，没有作为正式规范直接引用，也没有复制其旧对象模型或默认技术栈。外部调研回到原始资料：Temporal 的消息处理与重放、PostgreSQL 的事务隔离、W3C PROV-DM，以及 MCP 的工具信任边界。采用的具体结论与来源链接放在对应评审点中；本项目的修改建议与外部系统的现有保证分开表述。

仍保留几个已经明确的开放条件，不在本轮重复计为新缺陷：跨权威域联合使用围栏在验证前拒绝开放；云端生产档须先完成安全接管协议；平台持久性须有对应平台的验证；未知外部效果不能靠任务重建或人工接受风险抹去；M1 仅用于受控测试，不宣称完整的个人数据治理。

本轮的证据范围是设计交叉检查、事件顺序推演和原始资料核对。链接与文档格式检查只能保证文档可用，不能证明架构具备分布式正确性。上述验收场景须在实现阶段落成故障注入和状态机测试。
