# 子任务的执行开始必须检查祖先的控制依据

第三轮评审点 R3-03，优先级 P1，开放 M4 内部委派前必须补齐；M1 定义准入与开始凭据时建议预留这种依据。祖先控制已经进入子任务的准入检查，但尚未明确进入已准入动作的执行开始检查。

---

定位：[任务编排 §2.3、§4.6](../../../architecture/core/tasks/README.md)保存子任务创建时的父条件版本和父控制代次，要求“子任务的每次准入都检查祖先的控制范围”。[出口闸门 §2、§4.1](../../../architecture/core/egress/README.md)则只列动作所属任务的条件和控制版本，P4 比较该动作准入时的控制代次与当前值。[任务编排 §4.5](../../../architecture/core/tasks/README.md#45-条件变更暂停与取消)在条件变化时标出相关子任务，但新增的输入变更规则没有明确同样处理子树。

授权模块检查全部祖先授权，是另一条正确的保护。父任务暂停、取消或改目标，不必同时撤销一份仍可供其他任务使用的持续授权，因此授权链检查不能替代任务祖先的控制检查。

---

父任务 P 委派 C，C 已准入“发送报告”，但还没到 P4。用户先取消 P，取消已在裁决域持久成立，向 C 的封闭传播暂时延迟。C 自己的控制代次没变，授权仍有效，动作又已经过了“子任务每次准入”的检查。如果 P4 只检查 C，它仍可建立开始回执。

更隐蔽的是 P 修改要求后仍为 `ACTIVE`：即使给 P4 加上“祖先没有暂停或取消”，也无法识别 C 的动作依据的是旧父条件。父任务暂停后恢复同样会重新变为 `ACTIVE`，旧子动作不能因此自动复活。

---

建议在子任务的授权委派关系之外，固定它依赖的任务祖先及控制依据。在动作准入时保存准确的祖先任务引用和代次，P4 在同一个裁决事务中验证：当前祖先仍允许这种推进，且动作绑定的祖先控制依据仍有效。既有子任务关系已经限制深度，M4 可以先按有限祖先链读取，不需要同步更新整棵子树。

父级输入修改、条件变更、暂停和取消，都使依赖旧代次、尚未开始的子孙目标动作不能取得新的开始回执。通知继续用于推动封闭与收尾，不承担正确性。P4 先成立的动作保留原责任；父控制先成立的动作被拒绝。父控制与子 P4 必须使用能共同排序的事务检查，不能各自读一份缓存后比较。

恢复或重新允许某个子任务继续，需要核心在当前父条件和控制依据下明确重新裁决其推进范围。不得只把旧动作凭据的父代次改成当前值；旧动作不变，新目标推进重新准入。核对、取消和费用确认按当前控制以受限的收尾用途准入，仍可关联旧父子关系。

M4 现有方案把同一用户父子任务放在同一裁决域，足以支持这项检查。将来若开放跨裁决域内部委派，需要单独的开始授权协议；在此之前明确不支持，不引入全局锁服务。外部 Agent 仍遵守其已声明的停止能力，不承诺控制已进入远端的每个内部动作。

---

修改落点：任务编排 §2.3、§4.5、§4.6；核心契约的准入依据和精确引用；出口闸门 P4；授权出口核验的任务控制依赖；委派故障测试。遵循现有唯一写入方和联合裁决事务，不改变 ADR 0003。

验收至少覆盖：子动作准入后父取消、父修改、父暂停后恢复，全部把传播通知延迟到子 P4 之后；再交换父变更和子 P4 的提交顺序。前一种顺序必须拒绝旧动作，后一种顺序保留已开始责任。增加祖孙三层、控制变化后重新准入、旧工作者恢复和收尾查询正例。测试既检查状态，也检查实际出口次数。

这个缺口与第二轮 R2-02 同属“准入后依据变化”，但对象不同：第二轮已经修复同一任务输入变化，本项补足的是任务祖先链。

---

[PostgreSQL 18 的可串行化隔离](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)约束事务的并发执行，并不替应用补上遗漏的业务读取。因此，P4 的事务若没有核验相关祖先，即使数据库隔离级别正确，也不会凭空得到上述父子控制保证；将祖先依据纳入同一检查，是本项目需要补充的业务规则。
