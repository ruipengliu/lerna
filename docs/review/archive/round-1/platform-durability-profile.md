# 把端侧持久性落实到平台与同步屏障


本轮评审要求每项判断附修改方案。这里的判断是：端侧的 `WAL + synchronous=FULL` 可以作为配置起点，但尚不能单独支撑“支持的平台都能承受掉电”的实现承诺。需要补上平台、SQLite VFS、同步原语和失败处理的共同契约；不能把名称中的 `FULL` 理解成所有层都已经执行了最强的持久化屏障。

---

具体定位：[持久工作 6](../../../architecture/core/durable/README.md#6-不变量落实)在“持久性的范围”中指定端侧 SQLite WAL 和 `synchronous=FULL`；[数据与存储 5.4](../../../architecture/topics/data-and-storage.md#54-持久级别)把本地同步提交的覆盖范围写为进程崩溃、重启和掉电；[文件适配器 4.1](../../../architecture/adapters/file.md#41-普通文件的发布)以同步临时文件、替换、同步目录实现持久发布。[文件适配器 8](../../../architecture/adapters/file.md#8-待定事项)已经要求验证文件系统和设备实际履行同步承诺，因此不能说文档忽略了存储故障；缺口是数据库和文件两条路径还没有共同的平台准入表，也没有明确指出 macOS 下的两个 `FULL` 含义不同。

SQLite 官方区分了两个控制量：`PRAGMA synchronous` 决定何时调用 VFS 的 `xSync`；`SQLITE_SYNC_NORMAL` 与 `SQLITE_SYNC_FULL` 决定同步方式，在默认实现中后者才涉及 macOS 的 full sync。`PRAGMA fullfsync` 是另一个设置，默认关闭。参见 [SQLite 同步标志](https://sqlite.org/c3ref/c_sync_dataonly.html)、[fullfsync 配置](https://sqlite.org/pragma.html#pragma_fullfsync)。所以“已经设置 synchronous=FULL”不是“已经启用 F_FULLFSYNC”的证据。

Apple 的归档系统手册说明，普通 `fsync` 可以只把数据推送到设备缓存，掉电仍可能丢失或乱序；`F_FULLFSYNC` 要求设备刷新缓存。该手册揭示的是需要验证的平台语义，不能替代对当前 OS、文件系统和设备组合的认证。参见 [Apple fsync 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html)。

---

反例：账本先记录 P5，SQLite 返回提交成功，闸门发出非幂等操作；设备缓存尚未真正持久时掉电。若这个平台组合只执行了普通 `fsync`，恢复后可能没有 P5，而外部效果已经发生。同一动作由此丢失恢复依据。文件路径也有对应问题：临时文件和目录操作都返回了正常同步结果，却不一定满足被声明的掉电范围。这里只论证存在不满足承诺的合法配置，不声称所有 macOS 设备都必然丢失提交。

---

建议增加一份“端侧存储能力档案”，由部署层选定，数据库和文件适配器引用同一档案。最少记录 OS 与版本、文件系统与挂载范围、SQLite 构建及 VFS、事务同步配置、实际屏障原语、目录同步支持、覆盖的故障和对应验证证据。进程崩溃恢复、主机掉电恢复和设备永久丢失要分别声明；后两者不能从进程重启测试推导。

对于采用默认 Unix VFS 的 macOS 路径，把 `journal_mode=WAL`、每条写连接的 `synchronous=FULL` 与 `fullfsync=ON` 作为严格掉电档的候选配置，并验证实际执行路径；不能只检查设置值，因为 VFS 或底层系统可能不提供等价屏障。其他平台按原生机制验证，不机械复制 macOS 参数。文件适配器也必须选用该平台相应的同步屏障并逐项处理错误；不能把 Linux 的函数返回约定当作跨平台实现本身。

启动时读取并校验每条写连接的实际设置。连接池新增连接、迁移脚本和库替换后也要核验；不允许某条恢复连接以默认配置写入关键责任。屏障不可用、同步错误或平台组合未经验证时，不开放依赖严格掉电保证的能力。若只提供较小的故障范围，必须在上游目标允许的前提下显式声明，不能在下游悄悄降级。

这个修改不是要求所有场景都选最昂贵的同步方式。它让每种确认的成功语义有具体实现和证据：严格档承担屏障成本，其他档只能承诺自己的范围。SQLite 也明确提醒，数据库只能依赖系统与硬件对同步操作的报告；把配置设对并不能证明任意设备都诚实履约。参见 [SQLite 数据损坏说明](https://www.sqlite.org/howtocorrupt.html#_failure_to_sync)。

---

验收增加三层证据：先检查实际构建、VFS 和所有写连接设置；再用故障注入观察 P5 提交和文件发布是否确实调用所要求的同步路径，并模拟屏障失败；最后对声明支持的组合执行掉电或等价存储故障模型测试。重点覆盖 P5 确认后立即掉电、文件替换后目录同步失败、WAL 检查点与提交交错、连接重建漏设参数。断言是：声明范围内已确认的责任仍可恢复，未达到屏障不得开放出口；单纯杀进程通过不得被计为掉电验收通过。
