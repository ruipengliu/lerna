# 让原文件提交在后续覆盖后仍可核对


本轮评审允许提出更好的整体方案，也要求给出具体改法。受管理文件的“不可变对象 + 原子提交指针”值得保留，但建议补上历史可达性约束：指针能证明当前发布，不能单独证明曾经被后续版本覆盖的原尝试。此项属于恢复能力与承诺范围的补齐，不等同于断言现有方案必然重复写文件。

---

具体定位：[文件适配器 4.2](../../../architecture/adapters/file.md#42-受管理的版本布局)说明提交指针包含动作标识、目标版本、对象引用和摘要，并据此认为恢复时能查询原动作是否提交；[文件适配器 3](../../../architecture/adapters/file.md#3-接口)允许“查询原尝试”返回历史已清理；[文件适配器 4.1](../../../architecture/adapters/file.md#41-普通文件的发布)第 7 步才让账本持久接纳发布证据。现有规定已要求账本保存回报，也要求未知时不得再次覆盖，因此正常收到持久回报的动作有账本兜底。需要补齐的是“发布已发生、账本尚未保存回报”这一窗口，不能默认该窗口已经被可变指针消除。

反例：A 发布提交指针后崩溃，未留下账本回报；锁随进程退出而释放。另一个合法写者 B 取得同一资源锁，基于当时的当前版本发布 B，指针随即只剩 B。恢复 A 时，磁盘上即使还保留 A 的不可变内容对象，也只能证明内容曾经准备好，无法仅凭对象存在判断 A 是否真正发布。当前指针、参数摘要和原动作的内容对象都可能同时正确，但关于“是否发布过 A”的证据仍然缺失。文档要求稳定锁和版本检查，却未要求 B 在覆盖前补持久 A 的证据，也未定义指针包含可验证的前驱链。

这是对当前发布流程的推导，不是第三方工具的经验类比。作为机制参照，Git 将当前引用更新和引用变更日志分开定义：引用可被新值替换，reflog 另存旧值与新值；其文档也明确要求日志追加失败时引用更新失败。该事实支持“当前值与历史证据是两件事”，不意味着直接使用 Git 就获得本设计的掉电保证。参见 [Git update-ref 官方手册](https://www.kernel.org/pub/software/scm/git/docs/git-update-ref.html)。

---

M1 建议优先采用较小的修改：同一受管理目标的写者在稳定锁内读取当前提交身份，覆盖之前确认该提交的发布证据已被账本持久接纳；如果前驱没有回报，先核对并补交前驱证据。核对尚未完成或账本不可用时，阻止该目标的后继覆盖。这样单一指针始终保留最后一个尚未完成证据交接的提交，已有账本负责历史，不再引入第二套效果事实库。需要把这个阻塞条件写入文件接口和恢复流程，并明确会牺牲同一目标在账本不可用期间的写入可用性。

如果未来需要在前驱核对未完成时继续发布，则采用持久提交链：每个不可变提交对象保存原尝试、目标身份、版本、内容引用和前驱提交身份；所有对象与必要目录先完成同步，再在锁和期望版本保护下原子推进唯一 HEAD，并同步 HEAD 所在目录。恢复时，只把从有效 HEAD 可达的提交视为发布证据；孤立的准备对象不构成提交证明。后继提交必须保留前驱可达性，直到前驱证据已可靠交给账本。单纯多写一份 `committed=true` 文件会新增双写窗口，不是解决办法。

两条方案可以择一：M1 的串行交接更小；提交链允许更多并发恢复，但带来历史遍历与回收成本。不建议一开始同时实现。若暂不补齐任何一种机制，就收缩 4.2 的表述：只有当前仍保留原提交身份，或账本已有原提交证据时，才承诺可归因查询；其他情况继续保持未知，不声称已消除这类窗口。

---

历史回收也必须与责任交接关联。正文、不可变内容对象和最小提交身份分别治理；允许删除正文，不意味着可以在未知动作仍依赖证据时按 TTL 删除最后的提交依据。采用串行交接时，账本持久接纳后才能允许覆盖指针；采用提交链时，剪枝前必须证明受影响提交的证据已被账本接纳，或明确降低可查询范围并保留未知。不得为了“保证历史”无限保存不获准保留的正文；最小元数据的用途与保留依据仍归内容治理约束。

验收新增 A 发布后、账本回报前崩溃，随后 B 再发布；连续 A/B/C 覆盖；A 只生成对象但未推进 HEAD；推进 HEAD 后同步失败；账本接纳成功但确认丢失；未知 A 遇到历史清理。采用 M1 方案时，B 必须在 A 的证据持久接纳之前受阻；采用提交链时，A 必须仍可从当前 HEAD 证明历史发布。所有方案都必须拒绝把孤立准备对象判为已发布，也不得通过重新发布 A 覆盖 B 来“核对”。
