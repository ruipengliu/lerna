# 模块和协议扩展需要一份可执行的注册与验收契约

用户追问：“模块与协议扩展范式是否明确，可扩展性是否有保证？”第二轮 R2-10，建议 P2：在 M1 固定最小注册格式与单版本基线，在 M3 混合版本和 M4 第三方扩展开放前分别补齐协商与互操作验收。现行设计已有安全的扩展方向，但尚不能凭文档承诺跨版本扩展已经得到验证。

---

已有规则必须保留。[分层 §5—§7](../../../architecture/layers.md)限定四类扩展接口和依赖方向；[扩展管理 §4.1、§4.3](../../../architecture/platform/extensions/README.md)规定安装、隔离、就绪、核心接纳、灰度与回滚；[核心契约 §7.5、§7.6](../../../architecture/core/contracts/README.md)规定单一权威结构定义、必需语义、编号保留和历史 Schema；[持久工作 §2.1、§2.2](../../../architecture/core/durable/README.md)已经要求保留原指纹比较规则与旧工作解释能力。因此不能把缺口说成“没有版本”“没有恢复”或“没有兼容测试要求”。

尚未固定的是把这些规则连起来的可执行资料：扩展类别与准入清单、方法与特性的注册结构、能力依赖、协商结果怎样绑定到具体请求、兼容矩阵，以及哪些测试结果允许对外声明支持。现行架构中的 Protobuf 仍是待绑定验证的首选，混合版本窗口仍是待验证项；研究目录的 Schema 与原型不能直接充当当前契约的发布产物。

---

修改方案首先区分三种扩展路径，不能把“新增模块”都理解为加载插件。

| 扩展路径 | 必须提交与验证 | 允许改变的范围 |
| --- | --- | --- |
| 在既有接口增加或替换实现 | 固定实现与能力定义、参数与结果结构、效果和费用声明、权限上限、状态格式、恢复与清理合同、平台探针和一致性证据 | 新工具、新推理策略、新检索算法、新交互呈现；不新增事实裁决权 |
| 新增核心业务模块或受信基础设施实现 | 负责事实、身份、状态转换、内部接口、原子事务范围、交接、未知结果、保留和恢复、依赖及部署位置 | 经代码审查和正式发布增加职责；涉及既有决定时更新架构或 ADR，不接受插件注册任意核心处理函数 |
| 扩展公共协议语义 | 版本化方法／特性定义、输入输出 Schema、缺失与未知规则、必需能力、指纹投影、错误与恢复、持久格式及兼容证据 | 经统一契约发布增加可协商能力；不能以任意 JSON、脚本或未登记字段绕过准入 |

例如新增日历读取能力，可以实现既有执行接口并登记能力，无需给 Task 增加“正在读日历”的专属状态。新增一种授权消费方式则会影响核心准入、指纹和持久状态，必须走受审查的语义变更，不能装作普通工具参数。

---

在现有发布清单和能力声明上补一份受控注册契约，不新建在线全局注册服务。Schema 继续只有一个权威来源；注册记录引用其准确版本和摘要，不复制字段定义。最低内容如下：

| 项目 | 要回答的问题 |
| --- | --- |
| 身份与命名空间 | 哪个接口、方法或特性，由谁维护；稳定标识如何防冲突；版本和摘要如何定位 |
| 结构与语义 | 输入、输出、错误、存在性、缺省、枚举与状态；哪些字段只用于展示，哪些影响决定 |
| 接纳与恢复 | 原 CommandIdentity、成功提交集合、查询入口、未知处理、来源回报去重、旧处理器的保留要求 |
| 安全与费用 | 操作权利、处理目的、实际出口、来源传播、费用上界；所需特性与依赖 |
| 兼容性 | 可接收、可解释、可执行、可恢复的版本范围分别是什么；哪些组合只允许受限读取 |
| 生命周期 | 停止新调用、撤销、排空、迁移、回滚、卸载、旧责任恢复和清理的规则 |
| 验收证据 | 测试套件与版本、平台、目标系统、生成工具、运行库、正反例与已知限制 |

这些字段按扩展类别引用已有记录，不要求每个插件填写无关能力。支持方法与实现权限仍分别检查：发现一个能力，只证明它可被描述；安装和协商成功都不授予业务授权。

---

协议协商必须落到可复核的判定规则。发布版本仍按现有核心、契约、SDK 同版管理；特性标识用于声明各端实现的子集，不意味着各模块开始独立发布所有协议版本。

建议协商结果固定双方身份、契约版本、定义清单摘要、可用方法及必需特性、方向性限制和资源上限。重连重新协商；旧命令保留原契约、Schema、指纹版本和原身份，不因连接升级而改写。接收处理器每次检查实际请求是否落在支持范围内，不只依赖网关曾握手成功。

`must_understand` 不能仅由发送者自由填写。接收方对已知的精确 Schema 和方法，从受控定义确定最低必需特性及字段条件，再核验请求声明与协商结果。发送者遗漏安全特性时拒绝；Schema 本身未知时，不猜哪些字段安全，停止业务执行。能够受限保存或透明转发未知信息的路径必须另行声明；它不能据此签发开始许可。

反例是新协议增加“仅允许发送给指定账户”的约束。旧读端即使能解码其他字段，也不能忽略该约束继续发送；发送方少写一个 `must_understand` 也不能使它变成旧式无约束请求。网关、JSON 转换、SDK 再编码都须保持原语义绑定，不能通过丢字段获得兼容。现行规范已经要求拒绝这种降级，注册契约要使检测条件可实现、可测试。

这不是要求所有新增展示字段都强制升级全部客户端。只有受控定义明确其不影响决定、权限、效果、费用和恢复时，才可允许忽略或受限展示；新增枚举、方法和关键字段分别给出行为，不能共用一个“未知就跳过”的开关。

---

兼容性至少有四层：格式能够传输、业务语义能正确解释、持久记录能恢复、具体实现仍有资格运行。前三层通过也不能重新启用已被安全隔离的旧插件。需要处理它留下的责任时，通过仍可信的解析、原账本、查询或人工证据继续核对；无法恢复就显式受阻，不为追求可用性运行不可信代码。

[Protobuf 未知字段说明](https://protobuf.dev/programming-guides/proto3/#unknowns)指出二进制未知字段可能在 JSON 转换或逐字段复制时丢失；[ProtoJSON 文档](https://protobuf.dev/programming-guides/json/)也明确其兼容性与二进制不同。因此结构差异检查需要覆盖每种实际传输路径，不能只用一次二进制往返证明 SDK 兼容。[MCP 2025-11-25 生命周期规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)把版本和能力协商放在初始化阶段；本项目还必须补原命令、授权、持久责任和实际出口约束，不能从支持 MCP 推导这些保证已经成立。

---

把扩展验收作为开放能力的条件，最小验证矩阵如下。这里的“旧”和“新”必须填入准确版本、生成工具和配置，不是永久承诺任意 N 与 N−1 都兼容。

| 测试 | 通过条件 |
| --- | --- |
| 同一接口的第二种独立实现 | 通过共同语义与故障用例；切换无需改任务、授权和账本的业务规则 |
| 旧写新读、新写旧读 | 支持的组合语义一致；不支持的组合明确拒绝，不能静默扩权 |
| 新发端—旧网关—新执行端 | 必需字段与语义绑定不丢失；不能保留时阻断路径 |
| 未知必需特性、未知枚举、遗漏声明 | 不产生新动作或错误默认；错误可定位缺少的能力 |
| 升级时仍有旧命令、待办、未知动作和费用 | 原身份、比较规则与恢复责任保持；旧回执可在当前权限下查询 |
| 新状态写入后回滚 | 已声明支持的旧读端可安全恢复；不支持则阻止回滚或限定为受阻恢复，不恢复旧数据库 |
| 停用、卸载、撤权与迟到回报交错 | 停新调用，仍接纳合法原责任回报；不删除最后恢复依据 |
| 错误实现主动丢字段、换键重发或自动重试 | 一致性套件能够发现反例，避免只验证“好实现通过” |

行为兼容测试不能全部由插件自带；平台维护共同测试与独立的目标效果记录。模拟目标适合稳定重现故障，真实平台探针验证实际出口与隔离，两类证据分开声明。Schema diff 和生成物可重复检查是必要条件，但不足以证明行为兼容。

---

实施顺序：M1 固定现行对象与最小方法的权威结构定义、注册记录、原指纹与单版本正反例；M3 加真实端云协商、转码与混合版本恢复；M4 加四类接口的第二实现、沙箱与安装全生命周期验证。研究中的协议原型可作为反例设计材料，按当前身份与状态重写后再纳入。

修改落点为核心契约的定义清单／兼容检查／版本章节、网关协商输出、扩展安装与就绪门禁、SDK 恢复规则及 conformance。与 R2-08 的公共契约和内部接口划分配套，不新建能绕过核心的通用插件总线。

最终可以对明确的接口、能力、平台和版本组合声明可扩展性，并列出验收证据。不能承诺任意未来模块、任意协议变化都无须改核心。可扩展性的合理目标是：既有语义内增加实现的成本受控，增加新语义的影响可定位，不支持的组合安全拒绝，旧责任持续可恢复。
