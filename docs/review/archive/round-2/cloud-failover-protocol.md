# 云端安全接管需要落成可验收的部署协议

用户追问：“分布式问题是否有考虑？”现有设计已经明确同域事务、跨域交接、领取隔离、外部未知效果和分区时严格等待。这里补充的是第二轮 R2-07：建议按 P1 管理的云端生产准入项，在启用云端生产档和自动接管前完成；不要求 M1 的单进程本地档先建设高可用集群。

这是部署协议尚未定型的缺口，不是已经发现业务契约允许双主。现有规范要求遇到不能证明的情况停止，因此不能把下述反例描述成符合现有规范的合法执行，也不能声称运行中的系统已出现故障。

---

定位：[部署 §4.4](../../../architecture/topics/deployment.md#44-云端进程和可用区故障)要求安全提升、隔离旧主，并明确三个可用区加同步复制不足以证明安全；[数据与存储 §5.2、§5.4](../../../architecture/topics/data-and-storage.md)要求停止降档、核验复制屏障；[ADR 0001](../../../adr/0001-durability-profiles.md)承诺云端生产档承受单可用区永久丢失。这些要求正确，但尚未绑定一个具体的高可用实现、版本、同步成员变更规则、旧主隔离方式和开放出口的验收证据。

需要防止的错误实现：A 主库、B 同步副本、C 落后副本各在一个可用区。A、B 已保存准入和开始记录，用户已收到成功回执。A 所在可用区丢失后，若运维仅按“C 健康、能连通”提升 C，便可能丢失已确认责任；即使 B 尚存，也没有理由提升缺记录的 C。另一个反例是 A 仅与协调服务断开，却仍能服务旧数据库连接；新主开放后，如果只更新路由而没有隔离 A，两个存储就可能各自接受裁决。

这两条历史检验的是接管资格与旧主隔离。业务工作者的领取代次只能保护其所访问的权威存储，不能让已经分叉的两套存储重新成为一个权威。

---

修改方案：保留 PostgreSQL 与单用户裁决共置，选定一种高可用实现，将下列规则写成部署协议和 ADR。可以使用经验证的托管服务，也可以评估 PostgreSQL、Patroni 与共识协调服务的组合；这里没有直接采纳某一产品。

1. 固定数据库、高可用管理器、协调服务的版本和拓扑。写清数据副本跨可用区的分布，以及协调服务失去多数成员时谁停止新写入。协调服务只管理存储领导资格，不成为任务、预算或授权的第二个事实来源。
2. 定义同步成员资格与变更顺序。新成员追平并取得协议规定的资格之前，不得承担原成员的持久性承诺；失去足够副本时停止关键确认和派发。副本数量要与故障域分布共同核验，不能把同一可用区的两个副本算成跨区保障。
3. 定义提升资格。候选必须通过所选高可用协议证明包含已确认责任；不能把“当前可见节点里日志位置最大”当成充分证据。比较日志位置还须核验时间线和历史连续性。证据不足则等待原节点或恢复可验证的副本，人工提升也不得绕过这一条件继续自动行动。
4. 定义旧主隔离。采用所选平台支持并验收过的关机、存储访问隔离或等价机制；说明它如何覆盖已有连接与暂停后恢复的进程。只改 DNS、摘除负载均衡地址、撤掉调度租约均不足。隔离尚未证实时，不开放新主的业务推进。
5. 分别核验当前写入资格与每条责任的持久屏障。连接到当前主库不等于某一条本地可见记录已复制；查询回执、outbox 派发、P4 开始回执与云端账本的 P5 均须遵守各自记录的持久档位。复用存储专题已有的复制水位或同步提交屏障要求，明确实现接口、超时结果及故障后的重新核验方式。
6. 新主恢复后，先验证时间线、同步配置、路由和权威记录，再开放新推进。已有开始记录的动作按原尝试恢复；已进入可能发送窗口的动作继续核对。隔离旧主不会撤回此前已经发往目标系统的请求，也不能消除迟到效果。

首版可以选择较保守的候选范围和人工审批的接管操作，接受更多停写。人工操作仍执行相同的证明和隔离步骤，不把操作者点击“提升”视为安全证明。自动化程度与安全条件是两件事。

---

[PostgreSQL 17 故障提升文档](https://www.postgresql.org/docs/17/warm-standby-failover.html)明确要求防止旧主恢复成第二个主库，并说明 PostgreSQL 本身不提供完整的故障检测与接管系统。[Patroni 4.1.5 复制模式文档](https://patroni.readthedocs.io/en/latest/replication_modes.html)区分了限制提升候选与要求每次提交保有同步副本：普通同步模式在没有合适副本时仍可能接受只保存在主库的写入，严格模式才禁止自动关闭同步要求；即便严格模式，取消复制等待后仍可能读到尚未复制的事务。[Patroni watchdog 文档](https://patroni.readthedocs.io/en/latest/watchdog.html)还专门处理管理进程无法及时停库的情况，包括进程暂停、崩溃和关库过慢，并说明看门狗时序配置的限制。

这些资料说明不能把一个“开启同步复制”的开关当成完整证明。它们是候选方案的依据，不构成本项目已通过验收的证据；实际采用时固定版本和配置，不以 latest 页面作为运行时契约。

---

修改落点为部署 §4.4、数据与存储 §3.2／§5.2／§5.4、持久工作的确认与派发边界，以及云端生产验收清单。新增的高可用 ADR 细化 ADR 0001，不改变其故障范围，也不扩大为跨地域灾难下的自动恢复承诺。

验收必须记录可检查的执行历史：原命令身份、事务结果、持久屏障证据、领导资格、数据库时间线、隔离结果、P4/P5 记录、目标系统实际接收的请求与最终效果。不能只记录“集群恢复、服务返回 200”。

| 注入历史 | 必须观察到的结果 |
| --- | --- |
| 主可用区永久丢失，另一个候选落后 | 仅合格候选可提升；已确认责任保留，不能证明则停止 |
| 主库与协调服务分区，但旧客户端连接仍可用 | 不出现两个可接受新裁决的权威；提升前的隔离证据可查 |
| 高可用管理进程暂停，数据库继续运行 | 隔离机制仍满足协议；做不到就不能宣称自动接管安全 |
| 同步成员更换期间崩溃或断网 | 不出现临时降档后仍确认或派发的窗口 |
| 本地提交、复制未确认，取消等待，消费者读到待办 | 派发等待持久屏障；超时不被解释为未提交 |
| 旧工作者在 P5 之后暂停，接管完成后恢复 | 新工作者不重复非幂等发送；旧请求迟到时仍归入原尝试 |
| 接管后旧主重新上线、连接池仍持有旧连接 | 旧主不得恢复权威写入；连接失效不会生成新的业务命令身份 |

验证安全之后再测恢复时间、积压消化和取消命令的延迟。先证明责任不丢、效果不被盲目重复，再给出可用性指标。
