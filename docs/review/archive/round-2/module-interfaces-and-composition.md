# 模块划分需要区分裁决权、替换资格与代码依赖

第二轮 R2-08，建议 P2，在 M1 代码骨架和扩展接口固定前处理。分层方向可以保留，但“核心不可替换、其余可替换”和“只依赖核心契约”不足以直接指导代码组织。需要明确各模块的内部接口、受信基础设施适配和装配入口，否则容易把所有结构塞进一个公共契约包，或者在落地时留下大量未说明的例外。

---

定位：[分层 §2](../../../architecture/layers.md)第 20 行用“实现写错是否破坏不变量”判断是否属于核心；§7 的 R6 与 §11 第 232 行规定 core、defaults、adapters 只依赖 contracts。与此同时，[任务编排](../../../architecture/core/tasks/README.md)第 17 行要求通过模块接口共享事务上下文，[存储](../../../architecture/topics/data-and-storage.md)要求 PostgreSQL 和 SQLite 分别实现正式的提交与恢复语义。现有目录没有明确这些基础设施实现、内部事务接口与装配代码的位置。

“写错会破坏不变量”能提醒哪些实现必须受信，却不能单独决定哪些实现可替换。存储适配实现出错可以丢失责任，但 PostgreSQL 与 SQLite 仍需要不同实现；受审查的出口基本操作也可能因平台不同而替换。反过来，第三方执行适配器可替换，也不意味着其能力声明和回报天然可信。第三方替换权、受审查实现的替换能力、事实裁决权是三个不同问题。

这不是断言现有文档禁止所有数据库适配，而是要求把目前需要实现者自行补出的规则写清。

---

修改方案：保留唯一事实写入方，并用四张对应表表达架构：事实归属、代码依赖、运行调用、部署与信任隔离。运行时 A 向 B 请求、B 再回报 A，不自动构成编译依赖环；两个模块共用数据库事务，也不意味着可以互写私有表。

将替换规则明确为三类：核心裁决语义随受审查版本发布，不能由第三方改变；存储、时钟、密钥和受控出口原语属于受信实现，通过专项契约和平台验证后可以替换；推理、记忆算法和受限工具适配器可以由第三方提供，但只能使用其被授予的接口和能力。P1 用于识别必须受控的裁决与执行约束，不再推导“受信实现都不可替换”。

契约分为公共契约与内部接口。公共契约只包含跨进程命令、稳定引用、扩展接口与需要版本协商的载荷；事务对象、存储访问、锁顺序、平台时钟等内部接口归使用它们的模块或受信运行支撑，不自动进入 SDK。仍可同仓库、同版发布，无需立即拆成多个发布包。

建议的代码关系如下，目录名称只是候选，实施前需显式修订已采纳的 layers R6：

```text
contracts/public       命令、引用、扩展接口、线协议
core/<module>          事实处理器与本模块内部接口
runtime                持久命令/工作模板、提交结果与事务协作
infrastructure         PG、SQLite、可信时钟、密钥及平台实现
defaults               经审查的默认策略
plugins                受限第三方实现，仅接公开扩展接口
application            装配入口，连接具体实现与模块接口
platform               网关、发布、评测与诊断投影
```

`core` 不导入 SQL 驱动、网络框架或插件实现；基础设施实现核心或运行支撑要求的内部接口；装配入口可以知道具体实现，但不写业务规则。各模块之间只使用声明过的接口。禁止通用的 `GetTable/ExecuteSQL` 或万能事件总线绕过事实写入方；也不要求每条记录都生成一层只有转发作用的 Repository。

裁决域只创建一个事务上下文，绑定同一用户、同一物理数据库事务和对应持久档位。任务、会话、授权、预算及参与检查的内容控制元数据通过自己的内部接口加入它。不能由四个 Repository 各自开事务，再把“四次成功”拼成一次准入。远程接口不接受本地事务句柄；跨域交接保留 R7。

---

接口的收敛应围绕完整责任，而不是减少文档框的数量。任务的准入接口隐藏授权检查、确认消费、预算预留和待办登记的顺序；执行的受信协调入口隐藏账本准备、P4/P5 与回报恢复的顺序；内容的发布接口隐藏登记、正文准备、条件发布与孤儿清理。它们各自调用已有写入方，不取得第二份事实，也不要求部署成三个服务。

如果新增入口只是要求调用者按顺序调用五个旧方法，它没有减少复杂性，就不应增加这一层。接口真正需要承担的是：输入哪个原身份、成功固定了哪些事实、未知之后查哪里，以及在内部完整维持这些约束。

[Cockburn 的原始 Ports and Adapters 文章](https://alistair.cockburn.us/hexagonal-architecture)把应用与 UI、数据库等技术实现分离，并通过相同的应用接口接入测试。这支持显式定义基础设施接口与装配关系；本文提出的事务共置、受信级别和三类责任入口，则由本项目自己的不变量推导，并非该模式自动提供的保证。

---

验收以三次替换和两条故障历史判断接口是否足够集中：更换模型编码实现不改预算与账本规则；更换检索排序不改记忆纠正与删除事实；在声明支持的部署范围内更换存储实现，不改业务处理器，且各自通过持久性合同。编译检查要拒绝领域导入驱动、插件导入内部存储接口、平台直接更新任务私有记录。

再验证“确认消费后预算失败”和“派发提交成功但回执丢失”：前者整个裁决回滚，后者沿原身份恢复。测试从公开的业务入口触发，不在测试里重写一遍内部调用顺序。内存实现可以验证流程，但不能证明数据库隔离、掉电持久性和平台出口隔离。
