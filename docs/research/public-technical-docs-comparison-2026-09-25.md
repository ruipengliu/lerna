# 公开技术文档与大脑设计文档的对照

调研日期：2026-09-25。阅读作者或项目官方材料的相关完整章节，对照本仓库当前大脑文档。本次只新增研究笔记，不修改设计契约。

这里的“优秀”有明确判断依据：能否让读者理解问题如何产生、为什么选择当前方案、代价是什么，以及什么条件下保证不成立。所选材料包括设计提案、论文和实现解释，不能把不同文体当作统一模板，也不能把成熟系统已有的实现证据算成纯粹的写作优势。

当前大脑文档已经有问题引入、处理链、故障示例和证据边界。差距主要在几个关键处：方案理由仍可能跳过竞争性选择，重要解释有时晚于字段和约束，正常使用成本没有异常规则那么具体。以下按这些问题对照。

## Go：从“需要某种机制”推进到“为什么选择这种机制”

[Go 类型参数提案](https://github.com/golang/proposal/blob/master/design/43651-type-parameters.md#constraints)的 Constraints 章节从泛型函数无法确定某类型是否有 String 方法讲起，再比较延迟检查和从函数体推导约束，说明内部实现变化可能破坏远处调用者，才推出显式约束。No parameterized methods 一节则分析多种实现路径的代价后划定边界。这里分析的是 2021 年提案，不把它当现行语言规范。

对照[大脑总览“为什么把决策切成单轮”](../architecture/brain-system/README.md#decisions)，第 10—14 行从工具执行后答复丢失引出核心准入，理由成立，但尚未充分比较“保留大脑工具循环，每次调用仍由核心准入”。集中准入、每轮只返回一个有界批次、每轮至多一次物理生成，是相关但不同的决定。前一项的理由不能自动证明后两项必要。

这暴露的是论证缺口，不足以判定现有设计错误。下一次修订应明确替代方案需要保存什么状态、由谁恢复、如何响应控制变化，再比较额外复杂度与跨轮交接成本。只有这些差异确实成立，推荐才有说服力。没有实现数据的部分应列为待验证判断。

## SQLite：先让读者能推演，再补齐实现细节

[Atomic Commit In SQLite](https://www.sqlite.org/atomiccommit.html)先限定为 rollback 模式并交代硬件假设，再沿单文件提交展开。第 3.7、3.11 和 4.1 节把日志持久化、提交点和断电恢复连起来；完整扇区等细节留到第 6 节补充。它通过同一过程的前后状态解释保证，读者可以判断在某个时点中断会发生什么。文中含历史实现细节，不适合直接作为今天所有 SQLite 配置的运行指南。

对照[调用发送契约](../architecture/brain-system/contracts-and-runtime.md#call-handoff)，第 160 行已经解释“先保存可能发送标记，会出现占额却尚未发送；恢复者仍不补发”。这条因果关系很好，但它出现在身份规则、时序图、授权集合和提交边界表之后。读者较晚才看到这一设计最重要的代价。

可以先用两个崩溃点说明问题：保存标记后、真正发送前崩溃；已经发送、返回前崩溃。恢复者如果不能可靠区分二者，补发就可能重复生成。再说明现方案如何保守处理，最后展开表格。这样保留全部字段，但让读者知道为什么需要它们。

## Raft：让替代方案真正参与论证

[Raft 扩展论文](https://raft.github.io/raft.pdf#page=6) §5.2 沿着选举失败展开：同时竞选会分票，再次同步竞选可能继续失败，于是用随机超时打散竞争。作者还解释为何放弃候选者排名：高排名节点失败后，低排名节点何时重新参选又产生可用性问题，补规则继续引入边角情况。读者看到选择如何减少问题，而不仅看到“更简单”的结论。

对照[总览第 14 行](../architecture/brain-system/README.md#decisions)，现稿已解释单轮决策的代价，但同一段继续装入计划复用、单次生成、修复交回核心、逐步准入。它覆盖了规则，尚未逐一交代这些选择如何解决前一个问题。值得学习的是围绕一个矛盾收束一段，并用最有竞争力的替代方案暴露代价。

边界：论文 §5.4 明说前面的选举与复制机制仍不足以保证安全，再用旧日志节点当选的反例引出限制。不能把前面的简化解释独立当作实现规范；图 2 与后续安全章节承担完整性。这里的可读性依赖分层和明确补全，不依赖省略条件。

## AWS：每条约束回答刚出现的疑问

[Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 的 “Reducing client complexity” 先提出按参数识别重复，再用“用户也可能想创建两台相同实例”否定它，因而引出调用者提供请求身份；“Same client request ID, different intent” 再解释同键异参为何报错。抽象规则前有明确的意图冲突。

对照[接口文档 §4](../architecture/brain-system/contracts-and-runtime.md#call-handoff)，第 115—117 行先列两套身份和不可变绑定，理由到后文才逐渐展开。当前规则有价值，但读者需要自己推回：请求身份承载同一次意图，参数只能用于检查意图有没有改变。可先讲清这句话，再展开字段及冲突行为，查阅表无需删除。

边界：AWS 在 “Late arriving requests” 和结尾明确讨论记录保留成本及严格契约的实现代价，且服务需求不同。文章以降低调用者复杂度为目标；本项目面对未提供幂等保证的外部模型，不能据此直接改为自动重试。应借鉴其论证顺序，并保留本项目的外部事实边界。

## React：把代价写成使用者会遇到的事

[Hooks RFC 的 Drawbacks](https://github.com/reactjs/rfcs/blob/main/text/0068-react-hooks.md#drawbacks)把限制落到具体工作：增加提前返回可能需要调整 Hook 位置，闭包可能捕获旧状态，两种组件方式并存增加学习负担。代价的承担者和触发条件都清楚。其 Alternatives 主要列举选择，比较并不充分，因此也不应整体照搬。

大脑总览第 14 行说单轮设计会增加经过核心的次数，第 57 行说明接入可能需要目标解释和验证规则，已经承认成本。还应继续说明正常任务怎样承担它们。例如，连续 GUI 操作需要反复观察并进入新一轮决策；延迟由哪些交接贡献，需要测量。接入一个新能力究竟只补声明，还是必须写任务策略和验证器，也应以实际样例给出工作量。当前缺少实测，不能写成确定的性能退化或人日估算。

这与异常契约不是同一类信息。我们目前对失败后的责任描述较具体，对正常接入和使用的负担较抽象；后者也会决定方案是否值得采用。

## 一段可以直接看出差异的示范

原文[接口与模型运行第 160 行](../architecture/brain-system/contracts-and-runtime.md#call-handoff)已经把保守发送的理由写出来，但将多个判断压在了一起。下面只示范调整解释顺序，不作为本次对设计正文的修改：

> 适配器先保存“可能已发送”，再向供应方发起请求。若进程恰好在两步之间崩溃，记录会显示可能在途，实际请求却还没有发出。恢复者无法仅凭这条记录区分它与“已经发出、尚未收到结果”的情况，因此不能补发原调用。
>
> 这个选择避免恢复过程造成重复生成，也可能让未实际发送的调用继续占用预算和容量。物理占位凭可信未启动或终结证据释放，预算预留依据用量证据单独结算；证据缺失时，分别保留对应占用。

这段没有减少关键条件。变化是先给读者一个可想象的时点，再说明信息缺口、决定和代价。完整的资格检查与记录字段仍应留在契约表中。

## 对后续写作的明确建议

优先补单轮边界的竞争方案比较；它涉及设计依据，不能当作纯措辞调整。其次把未知发送的两种崩溃状态提前，让表格成为已经理解的机制的查阅入口。最后用一个真实接入和一个连续交互任务测成本，再决定默认保证是否划算。

应保留现稿已经做好的部分：建议、准入、执行事实和完成分别确认；未知费用与过程单独保存；设计材料和运行证据分开报告。优秀文档同样需要这些细节，只是不会要求读者在尚不理解问题时先记住全部规则。

核查范围：阅读所引原始材料的相关章节，并逐段核对本地总览、决策、接口与验证文档。外部材料的运行实现未复现；没有据此改变本项目的协议、保证或性能承诺。本地行号以本次调研时文件为准，链接使用现有章节锚点。
