## 1. 推荐先验证一个交接机制

可以用形式化方法把当前方案提炼成精确的状态、动作、前提和性质，再检验这些规则是否一致。推荐先用 **TLA+ 与 TLC 检查两个提交域之间的一项持久责任交接**：发起方保存责任，接收方持久接管，确认可能丢失，任一进程可能崩溃。这个问题贯穿任务、消息、执行、委派和发布管理，范围小且直接对应本项目最重要的恢复保证。[项目交接规则](../architecture/endpoint-communication/message-contract.md#handoff)

Lean 不必同时引入。等某条规则稳定，确实需要对任意参数、任意长度推导作一般性证明时，再比较 Lean 或 TLAPS 的证明投入。以下取舍是结合本项目的建议，并非官方性能或工期承诺。

| 工作 | 产物与用途 | 可以声称的结论 |
| --- | --- | --- |
| 结构化总结 | 列清对象、权威、状态、动作、交接点、性质与环境假设 | 概念更明确，便于评审；还没有验证性质 |
| TLA+ 规格＋TLC | 对一个有限模型实例探索可达状态，检查已配置的性质并找反例 | 在该模型、参数、配置及工具检查范围内的结果 |
| Lean 或 TLAPS 证明 | 从明确的定义与假设推导定理，检查证明义务 | 形式定理在其逻辑与假设下成立；可覆盖无限状态或一般参数，取决于定理本身 |
| 实现关联与运行验证 | 将数据库提交、消息、门禁和故障对应到模型动作；验证适配器及真实效果 | 补充模型之外的实现与环境证据，不能由前几项自动取得 |

TLA+ 官方将其定位为代码层之上的精确模型；写出模型并不排除实现中的编码错误。Lean 官方也明确区分“一个形式命题有有效证明”和“该命题表达了预期含义”。因此，把 Markdown 改写成 TLA+ 或 Lean 文件不等于证明原方案正确。[TLA+ 高层视角](https://lamport.azurewebsites.net/tla/high-level-view.html)、[Lean 证明验证](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)

## 2. TLA+、PlusCal、TLC 与 TLAPS 各做什么

TLA+ 以状态序列描述系统行为。状态变量记录关注的事实；`Init` 定义初始状态，`Next` 由允许发生的动作组成，动作关联变更前后的状态。安全性质约束不能发生的坏事，其中不变量要求每个可达状态都满足条件；活性性质要求某件事最终发生。`Init` 和 `Next` 只定义允许的变化，不会自动保证调度器一定执行某一步，活性通常还需要适用的公平性或环境进展假设。[TLA+ 状态机与性质](https://lamport.azurewebsites.net/tla/high-level-view.html)

本项目适合把“数据库提交”“确认送达”“崩溃”“恢复扫描”“取得当前资格”“外部动作发生”建成不同动作。模型中的全局状态是分析视角，不要求实际系统存在一个全局数据库或协调器。真正属于同一本地事务的变化才合为一个原子动作；若把跨模块交接合成一步，就会删掉最需要检查的失败窗口。

| 工具／语言 | 已核实能力 | 本项目使用边界 |
| --- | --- | --- |
| TLA+ | 直接定义状态、动作与时序性质 | 推荐用于明确跨模块边界、未知状态和故障交错 |
| PlusCal | 用接近程序的语法描述并发与非确定算法，翻译为 TLA+ | 适合顺序较清楚的参与方流程；标签形成的原子步骤仍须对应真实提交边界 |
| TLC | 显式状态模型检查与模拟，支持安全和活性检查 | 先用小参数的完整状态探索查设计反例，不把随机模拟当作穷尽检查 |
| TLAPS | 机械检查 TLA+ 证明，组织证明义务并调用后端验证器 | 需要一般性不变量或精化证明时可评估；不必为了证明再换一套规格语言 |

能力来源：[TLA+ 官方工具说明](https://lamport.azurewebsites.net/tla/tools.html)、[PlusCal 官方介绍](https://lamport.azurewebsites.net/tla/high-level-view.html)、[TLAPS 官方仓库](https://github.com/tlaplus/tlapm)。TLAPS 旧主页对时序推理的描述与当前仓库所列 LS4 后端存在年代差异，本篇不据旧页断言其完全不能处理活性；也不承诺任意活性证明都能自动完成。采用时应固定工具版本与所需证明片段。

### TLC 通过说明什么

对能够完整探索的有限状态模型，TLC 可检查所有可达状态及相关行为图；这不同于只枚举固定长度的几条执行轨迹。需要固定节点数、操作数、消息容量等参数，并确保时间、序号、历史和重试计数不会继续造成无限状态。活性检查仍受模型中的公平性及环境假设约束。[TLC 官方文档](https://docs.tlapl.us/using%3Atlc%3Astart)、[官方模型配置说明](https://learning.tlapl.us/intro/tlc-config/)

“通过”必须记录规格版本、配置、参数范围、启用的性质、状态／动作约束、完成状态及检查统计。某性质只在规格中定义但未启用检查，不能算已验证。随机模拟、提前停止或只完成部分探索，只能报告已探索范围未发现反例；三个节点的结果不能直接推广到任意节点数。为压缩空间添加的约束可能排除真正的故障，应解释它们为何不删掉待检查场景。[官方配置说明](https://learning.tlapl.us/intro/tlc-config/)、[TLC 运行模式](https://dl.tlapl.us/tlatoolbox/branches/1.7.1/doc/model/tlc-options-page.html)

TLC 结果还依赖工具实现及状态存储、约简等配置。它不是一份 Lean 内核检查的证明证书。这里需要的是可重现、边界明确的设计检查，不宜将“有限模型未发现反例”写成“生产系统已被数学证明”。[TLC 状态探索与指纹说明](https://dl.tlapl.us/tlatoolbox/branches/1.7.1/doc/model/tlc-options-page.html)

## 3. Lean 可以证明什么

Lean 可以定义状态结构、转移关系、可达状态与执行轨迹，再证明初始条件成立、每种合法转移保持某性质，从而得到所有可达状态满足性质。归纳类型与归纳证明足以表达这类基础结构，所以不能把 Lean 限定为只能证明静态公式、不能描述并发；并发交错可以进入转移关系。这个应用方式是基于官方类型和归纳机制的推论，并非 Lean 自带本项目分布式运行语义。[Lean 归纳类型](https://lean-lang.org/theorem_proving_in_lean4/Inductive-Types/)

对于当前方案，Lean 较适合候选规则包括：预算分配及结算保持守恒、授权委派始终收缩、重复应用同一回执不改变结果、版本比较或规范化函数满足指定代数性质。证明应明确量化范围和前提，例如“提供方累计用量合法且所有账本转移遵守规则时，父子份额不会被重复分配”。不能把“预算永不超卖”直接当作公理，再宣称证明了预算机制。

Lean 的一般性证明通常需要编写辅助不变量、归纳步骤及环境假设；用其直接搜索交付与崩溃组合也需要额外建模或可执行检查层。对本仓库当前的协议竞态问题，先用 TLC 获取具体反例通常更直接；对已稳定的纯规则进行一般性证明，Lean 的投入更容易界定。这里是方法与工作量判断，不是“Lean 不能处理并发”或“TLA+ 只能做有限模型”。TLA+ 还有 TLAPS 证明路线。[TLA+ 工具分工](https://lamport.azurewebsites.net/tla/tools.html)、[Lean 证明与内核机制](https://lean-lang.org/faq/)

### 证明的前提和可信边界

Lean 的证明脚本通常产生由内核检查的证明项，但结论始终依赖形式命题、定义和所用公理。`sorry`／`admit` 是未完成证明的占位，相关定理会依赖 `sorryAx`；额外声明的公理可能直接引入错误前提。应对最终定理运行 `#print axioms`，审查传递依赖，区分标准逻辑公理、未完成证明和项目新增假设。使用原生求值证明时还会扩大可信计算范围，应单独记录。[Lean 公理](https://lean-lang.org/doc/reference/latest/Axioms/)

即便没有 `sorry`，也须复核定理是否保留了需要证明的全部约束，前提是否不可满足、是否把目标性质藏进假设。导入依赖和符号定义影响定理实际含义；工具通过不负责判断定义是否忠实于设计。固定工具链、依赖和可复现检查是交付的一部分，本轮没有执行这些检查。[Lean 证明验证](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)

## 4. 本项目优先建模的对象

以下是建模建议，保留现行方案的事实归属和成功含义，不新增运行时模块。

| 顺序 | 最小范围与关键动作 | 主要性质及异常 |
| --- | --- | --- |
| 1 | 两个提交域的一项责任交接：发起方保存 Work、接收方提交接管记录、发送确认、原方记账、双方崩溃与恢复 | 已接纳且未完成的责任始终有持久承担者；重复交接不新建同一责任；提交成功而确认丢失仍可继续。不能将两次提交和确认合为一个动作 |
| 2 | 同任务取消与派发准备竞争，再接入原执行操作和迟到事实 | 取消屏障建立后不再产生／准备新目标工作；已准备项保留核对责任；获准迟到结果和费用仍被接收，取消终态不被复活 |
| 3 | owner、工作领取及实际资源门禁 | 只有当前有效资格可创建新责任；租约失效、连接断开不自动证明旧实例不能作用于资源 |
| 4 | 恢复快照、同步切点、连续变化与逐行为门禁 | 撤权或取消不落入快照／订阅之间的空档；旧轮次、旧 owner 的证明不能开门；事实接收和新行动分别判断 |
| 5 | 父子预算预留、累计用量、重复／迟到账单、最终封账 | 不双重分配或重复结算，未知费用不释放；适合 TLC 检查交错，规则稳定后可另作一般性证明 |
| 6 | 版本引用登记、排空、撤回与清理 | 先登记保留资格才使用；新引用已封闭且原责任核清才回收；回退代码不回滚授权、预算和已发生效果 |

对应现有契约：[两处持久交接](../architecture/endpoint-communication/message-contract.md#handoff)、[派发与领取](../architecture/task-kernel/decision-and-work.md)、[取消及迟到事实](../architecture/endpoint-communication/recovery-and-control.md#cancel)、[活动所有者](../architecture/endpoint-communication/delivery-and-recovery.md#recovery)、[恢复切点](../architecture/endpoint-communication/recovery-and-control.md#resume)、[父子预算](../architecture/agent-coordination/delegation.md#results)、[引用与回收](../architecture/extensions-and-runtime/contracts.md#storage)。

### 首个模型的关键假设

首个模型保留双方各自的持久记录与易失内存，允许确认丢失、重复交接和任意持久提交前后崩溃。数据库的原子与耐久提交先作为显式存储假设；提交结果未知是调用方的知识状态，不能让实际已提交记录随调用方超时一起消失。正常链应能释放发起方责任；接收方提交后立即崩溃、确认丢失等异常则应保留至少一方的持久责任。若模型将一次发送直接等同持久接纳，这项检查没有覆盖项目问题。

纳入执行后，须用不同变量表示**外部实际发生的效果**和**系统已知的执行／效果事实**。允许外部动作已经发生，但本地仍为 unknown；禁止由“没有成功记录”推导“实际未执行”。现行协议不保证任意外部动作恰好一次，模型也不能凭去重表创造这一保证。应验证的是未知时不自动重做、旧工作者不获新启动资格，以及责任与预算不被抹除。[执行恢复边界](../architecture/endpoint-communication/recovery-and-control.md#retry)

活性先使用有条件命题：当权威持续可达、权限和相关前提持续有效、存储可写、资源与重试额度足够，且适用工作得到公平调度时，交接最终推进。永久断网、权限撤销或有限预算耗尽时，不要求最终成功；应另检查责任仍可查询，按既定规则停止主动消耗并保存缺口。公平性不能冒充网络最终恢复或远端停止的证据。[有限工作规则](../architecture/endpoint-communication/delivery-and-recovery.md#scheduling)

## 5. 如何关联模型、文档与实现

**精化**是用更具体的规格实现较抽象的规格：在规定的状态映射下，具体规格的行为满足抽象规格。TLA+ 可将其表达为规格之间的蕴含；映射本身也是待审查内容，不能通过把所有实现动作映射为“不变”而得到没有实际意义的结论。[Lamport 精化说明](https://lamport.azurewebsites.net/tla/proving-safety.pdf)、[精化映射的语义](https://www.microsoft.com/en-us/research/publication/the-existence-of-refinement-mappings/)

本项目先维护轻量映射：每个模型动作对应文档的提交边界和实现入口，每个不变量对应已确认契约，每个环境假设对应提供方要求或运行测试。对首个交接模型至少区分“领域保存发送责任”“接收方耐久接管”“确认到达”“发起方完成交接记账”。这有助于发现实现遗漏，但映射表、轨迹对照和测试本身不是完整精化证明。

要把形式结论提升到生产实现，需要进一步说明实现语言及存储／消息／资源接口的语义，证明或验证具体步骤如何保持模型关系。把外部数据库抽象为原子提交，不会证明数据库配置耐久；把受信资源入口抽象为不可绕过，不会证明沙箱、设备或第三方接口实际满足这个条件。此类假设仍按[现有系统验证](../architecture/validation.md)取得故障注入与平台证据。

可交付的最小验证包应包含：建模问题与排除范围、状态／动作映射、环境假设、待检性质、固定配置、实际运行记录，以及反例如何修正或解释。TLC 与 Lean 可分别使用；没有必要为同一阶段同时维护两份完整系统形式化副本。
