# Opus 5.5 技术写作样本：公开产物检查

核查日期：2026-09-25。本笔记分析可读的模型产物，不把模型介绍或使用者评价当作文档样本。

本轮最有价值的观察是：好段落会先找出决定行为的事实，再由此推出约束和行动。公开样本也存在结论过强、验收证据冲突等问题。以下区分作者声称的模型生成、平台发布的模型输出和有人审阅的协作修订；没有同题盲评，不能据此给两个模型排总体名次。

## 样本：并行动画实现指南

[PDoomVideo 的 ANIMATION_GUIDE.md](https://github.com/JohnHeibel/PDoomVideo/blob/dff37f6b154e21dc21d9f27509debb059c5e0206/ANIMATION_GUIDE.md)是写给并行子 Agent 的实现指南。[作者说明](https://github.com/JohnHeibel/PDoomVideo/blob/dff37f6b154e21dc21d9f27509debb059c5e0206/README.md#how-it-was-made)明确将其归于 Opus 5.5。公开材料没有完整生成会话或独立的人工编辑审计；可说“据作者说明由模型生成”。

最好的局部推理是：帧会并行、乱序渲染，因此镜头不能依赖上一帧的状态，随机效果也必须稳定。原文同时提供替代方法。它把执行事实、必要约束和实现手段接在一起，读者不需要自行补出原因。

全文仍有大量 API 清单，适合查阅和执行，并非连贯架构论证的完整范本。允许子 Agent 私有实现缺失 helper，可以减少共享文件冲突，但何时收敛重复实现没有交代；性能目标也未绑定硬件和测量条件。因此它体现了短期协作中的务实判断，尚不足以证明长期演进设计优秀。

## 样本：Ballista 开发者文档修订

[Apache DataFusion Ballista 固定提交](https://github.com/apache/datafusion-ballista/commit/8a3eb73256e8c53206ea2fc19714814467ee9ce5)标注 Claude Opus 5.5 协作署名。这是开源协作修订，不是可独立归于模型的完整原始输出。[Apache 提交邮件](https://www.mail-archive.com/commits@datafusion.apache.org/msg33256.html)可读完整差异。

修改把未进入发布目录的开发者文档并入正式指南，删除过时图，并补全几个组件的入口说明。Executor 的开头从一句组件名称说明，变成注册、执行、保存和提供结果的处理链。启动说明紧接着解释同机增加实例需要处理多个端口。这里的好处是减少读者真正会遇到的理解和操作障碍。

值得保留的判断是按读者进入项目的路径安排信息，既处理内容，也处理可发现性。不过，多分区任务的长段落主要来自原有文档迁移，不能把其全部架构解释计为这次模型创作。修订仍有密集的字段和特性表；它们适合查询，不能替代设计理由。

## 样本：工程培训需求综合分析

[Mike’s Checks — 04 thematic，result 952](https://checks.every.to/p/mikes-checks/results/952)公开 `ANSWER.md` 全文和下载入口，标注模型为 `claude-opus-5.5`、Claude Code、high effort、2026-09-20 运行。任务是根据三位工程师的访谈笔记，确定公司 AI 工程培训重点。这是技术需求综合文档，不能当作复杂系统架构规格。

页面将附件标为模型输出。未找到独立公开的原始 `context.md`、完整运行轨迹或人工编辑审计，因此模型归属依赖发布方记录；只能分析已发布文本，不能证明完全未经人工修改。运行早于公开发布，不据此推断具体测试邀约关系。

正文把培训内容分为三个有序主项和两个可选方向，逐项连接访谈证据、培训活动及产物；另列样本和角色假设。页面显示 8/8 检查通过，其中五项由 Claude 评判；人工备注简短认可了综合结果。[任务比较页](https://checks.every.to/p/mikes-checks/tasks/04-thematic)上多个模型也满分，因此该分数不具强区分力。

## 对写作和判断的分析

最值得借鉴的是证据到行动的转换：先判断当前困难，再选择课程内容。它还把知识治理与教学边界分开。这比按访谈顺序压缩原话更接近技术方案写作需要的判断工作。

阅读上有明确主线，但有三处可以继续改进：

- 开篇对组织现状的断言强于小样本能够支持的程度。重要限定应跟着结论出现，不能仅靠末尾补充假设来降低前文的确定性。
- 按任务名称划风险档位不够稳健。内部工具同样可能拥有生产权限或敏感数据。更可执行的规则应依据影响范围、权限、可逆性和验证成本判断。
- 采用率、活动次数和覆盖率容易测量，却不能单独回答培训是否改善工程交付。建议补充实际返工时间、交付周期或被审查发现的缺陷，并说明基线与观察窗口；事故为零也不能单独证明风险控制有效。

这些是对本文决策规则的审查意见，不是跨模型胜负结论。该样本足以观察综合、组织和表达能力；没有覆盖职责划分、状态不变量、并发异常及恢复协议。

## 反例：AI village 的交付摘要

[Mike’s Checks — result 962](https://checks.every.to/p/mikes-checks/results/962)公布提示、模型设置、`ANSWER.md` 和检查结果。标注为 Opus 5.5、Claude Code high effort。本轮读到的是交付摘要；其中 `REPORT.md` 链接未能读取，不把它称为已完整审阅的研究报告。

摘要把数据、解释和限制接得很紧：说明小样本中的知晓率趋于饱和，也承认不同方案的排序不稳定。这些限定紧邻结论，值得学习。

但它声称角色行为均来自子 Agent 调用，而页面的轨迹检查未通过，人工备注也明确表示未按要求用子 Agent 驱动角色。模型评审却给相关项目通过。公开材料不足以独立还原全部执行过程；可以确认的是，交付声明与检查证据存在未解决的冲突，不能接受声明作为完成证明。

这对技术文档的评价很关键：论述完整、语气克制、附有限制说明，都不能代替事实核验。写作者应把每项实现保证接到具体证据上。

## 对本项目写作的启发

我之前常把规则组织完整，却把规则之间的推理留给读者。更好的写法应让读者先理解决定方案的事实，再看选择如何由它产生；约束应解释行为，例子应帮助读者预测异常后的结果。保留清单和表格用于查阅，不要求正文承担全部查询功能。

还应分开检查表达质量和证据质量。一个设计理由讲得自然，并不表示前提已证实；一个限制写在末尾，也不能自动抵消开头过强的承诺。对当前项目而言，关键是讲清谁保存事实、谁能作出保证，以及无法确认时怎样继续，而不是再增加一套抽象的写作口号。
