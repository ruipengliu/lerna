# 保证前提与尚未闭合的边界

[入口](README.md) · [来源与覆盖](coverage.md)

本版沿用已确认决定，不把接口意图当作实现证明，也不因一处正文没有展开就认定设计缺失。下面区分需要补充的设计、公共合同、平台证据和已经明确的适用范围；它们要求的下一步不同。

## 1. 有限窗口：入口执行机制仍需交付

**性质：平台前提与实现缺口。** [ClockAdapter](deployment.md#clock-adapter) 已定义 ε、ρ、κ 及旧信任代次失效规则，逻辑上没有忽略暂停。但草案没有选定并验证检查到实际发送／披露间隔的约束机制，也没有证明 Mac、Linux、容器与 VM 各自允许哪些暂停。

关键反例是在最后一次期限检查后暂停线程，过期后直接恢复到发送指令。重复检查、续约线程和一般 SIGSTOP 测试都不足以单独排除它。工程需确定真实入口及恢复屏障，再用对应平台故障实验证明上界；做不到的平台关闭依赖该保证的路径。本版没有用新的系统调用或进程模型替代这个待选实现。

<a id="revision-progress"></a>
## 2. Task 总修订：账务变化后的续行分支待补齐

**性质：控制流细则尚未闭合，尚不足以断言必然死锁。** 当前提案准入比较完整 Task 修订；迟到账单也推进该修订；进展判断中的语义输入又不把单纯账务变化当作新任务信息。这三个选择分别有理由，但交汇处需要明确续行责任。

例子是 Brain 根据 r=10 推理，账务归并推进到 r=11，随后原提案因 stale_snapshot 失效。已有方案要求重组快照；还需说明由谁再次驱动、怎样对待原推理费用、是否消耗无进展额度，以及持续账单更新时如何终止或等待。

本版在[任务控制](task-control.md#accounting-revision)保留完整修订门禁，没有引入新“语义修订”字段，也没有规定免费重推理。实施前补一条可执行状态路径及确定反例，再决定是否需要改变门禁或计数规则。

<a id="result-contract"></a>
## 3. 公共结果：完成标签与当前资格的表达范围有限

**性质：已知语义范围及公共合同缺口。** verified 表达必要条件的确定性通过，目标覆盖仍可能是语义判断；两者并非形式矛盾。风险在于调用方只展示一个标签，使用户以为任意自然语言目标已被确定性证明。

现有 Result 有 conditions 与 limitations，但没有完整的结构化目标覆盖对应物。成功后的判断缺陷也不改写历史 Result；默认宿主可提供诊断，公共 task.result 尚未提供附加缺陷说明的完整查询合同。

本版要求呈现时说明依据范围，并把历史结果与当前适用性分开。公共表达仍需一起决定字段或读取路径、授权、版本和一致性用例；跨域缺陷还要明确可信导入及时效。没有增加未经确认的新接口，也没有承诺远端瞬时缺陷一致性。

## 4. 文件保存：受管目录是产品范围

**性质：已经明确的保证前提，不是遗漏。** 默认 journal 依赖受控根、排除旁路写者与硬链接别名、句柄相对访问、原子替换和持久化。它能够在这些条件下解释原写入，不覆盖一般编辑器共同写入的任意目录或未经验证的网络盘。

需要决定的是后续产品是否支持普通用户目录、哪些驱动可承诺何种恢复，以及安装时如何检验和告知用户。本版从入口就说明受管目录，不把普通桌面工作流悄然包含进首装验收。生产跨区账本也不等于目标文件根跨区接管。

## 5. 持久工作：模板收益要由真实接入证明

**性质：工程机制与抽象成本待验证。** 共用接纳、Claim、Raise／Finish 的理由充分，新责任不被旧完成覆盖也是必要规则。当前接口声明仍留下 handler 的业务锁、外部阶段、独立迟到事实与恢复扫描职责。

需要用 Task 与 Operation 两条真实路径检查：受限 repository 是否防止越权写表，领取失效能否回滚全部受保护写入，提交未知是否确实按原键恢复，以及 handler 是否仍大量重复机械故障代码。可用公共模板承担的约束应放进模板；领域效果判断继续留在 owner。多数模块绕过时按 ADR 收窄，不能把“有公共接口”直接当成已降低复杂度的证据。

## 6. 首装：信任链已说明，承载实现尚未形成

**性质：交付依赖。** 最小宿主、受信 conformance 导入、本机预检、本人确认与有限 compatibility 批准构成无循环首装链；不要求先运行完整改善系统。原稿已解释这一点，本版将其前移。

真正交付仍需要可信发行材料、报告验证器、批准 owner、持久确认及准确实例自检。失败时保留管理和诊断，不能用“内置”跳过批准或让插件自证可信。第三方首装需要的精确导入与管理范围按现有协议和内部接口分别实现，不能仅凭流程图宣称互操作完成。

## 7. 后续能力：先补合同，再开放入口

**性质：明确延后，不能计入当前公共能力。** 线性 Session 可在宿主内部组织；通用消息排队／steering、历史分支、Schedule、跨父复用子会话、交互代码的 host-call 和执行环境管理仍有各自合同待补。

它们共同需要准确提交身份、输入归属、冲突与控制范围，细节并不相同。Schedule 还需选择错过触发和重叠策略；复用环境要证明旧计算停止及实例隔离；分支只选择历史，不能回滚外部世界。现有 105 个领域方法不自动覆盖这些应用名词。

## 8. 质量和规模：目标与实测必须分别呈现

**性质：缺少运行证据，部分参数尚待冻结。** API 广度、90%／95% 质量、百万 DAU、RPO／RTO 和有限许可窗口都是验收目标或试验配置。模型费用上界与查询能力、验证器校准、两种数据库竞争、文件介质、设备隔离及公司平台都须实际取证。

B1／B2、分层决策、渐进发现、程序化工具及委派是可比较策略，不因文档包含它们就成为默认启用能力。费用无可信上限时，只有满足已经规定的本地 estimate 例外才可启用；本版没有替选定供应方默认作出这个选择。

后续决定应先写清适用场景、反例和可观察退出条件，再与 Schema、ADR 和运行证据共同更新。当前正文能指导实现和比较，不能替这些未完成工作作出通过结论。
