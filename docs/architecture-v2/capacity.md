# 容量与运行指标

容量评审分别测稳态、高峰、损失一个可用区及带持续流量的积压恢复，使用同一业务构成和明确的计数口径。下列数字是建模输入或验收目标；实际结果统一记录在 [review](review.md)。部署与故障前提归[deployment](deployment.md)。

## 负载模型

任务到达率与连接数分别展开，不能用总 API QPS、空闲 socket 或 CPU 利用率代表整条任务链。

| 输入 | 初始值 | 推导 |
| --- | --- | --- |
| 日活用户、每天任务数 | 100 万、每人 5 个 | 每天 500 万任务，平均约 57.9 新任务／秒 |
| 峰均比 | 5 | 高峰约 290 新任务／秒 |
| 每任务模型调用与平均占用 | 4 次、8 秒 | 高峰约 1,160 调用／秒、9,280 在途 |
| 任务平均活跃时间 | 300 秒 | 稳态峰值约 87,000 活跃任务，运行／排队／等用户／等依赖分别报告 |
| 每任务业务提交 | 20 次建模下界 | 约 5,800 提交／秒，领取、续约、授权、控制和恢复另计 |
| 每任务内容 | 200 KiB | 每天约 0.95 TiB 原始内容，30 天约 28.6 TiB |
| 在线用户与提示 | 10 万、每人每 10 秒一次 | 10,000 原始提示／秒，再按订阅扇出 |
| 独立压力场景 | 500 新任务／秒，持续 15 分钟 | 45 万新任务；按同假设至少 10,000 业务提交／秒，约 15 万活跃任务和 16,000 模型在途 |

连接按 `C=U×a×b` 计算：U 为在线用户，a 为每用户活跃会话／设备数，b 为每会话平均逻辑服务连接数。初始 `U=100,000、a=2、b=1`，另测 a×b 的 2 倍和 4 倍。

| 倍率 | WSS 数 | 每 30 秒心跳组／秒 | 60 秒全重连平均握手／秒 | 每连接单向 4 MiB 全排满 |
| --- | --- | --- | --- | --- |
| 1 | 200,000 | 约 6,667 | 约 3,333 | 781.25 GiB |
| 2 | 400,000 | 约 13,333 | 约 6,667 | 1,562.5 GiB |
| 4 | 800,000 | 约 26,667 | 约 13,333 | 3,125 GiB |

排满值只说明逐连接上限相加不可作为内存预算；进程、租户和分片还要限制总额。20 万连接每条最多 32 个在途关联有 640 万项的理论上限，另计 TLS、HTTP/2、订阅、队列和运行时内存，按实际驻留分布测量。

内部 30 分钟委托轮换在 20 万连接下约产生 111 次建流／秒；若每连接两个订阅、每快照三页，仅均匀轮换就约 667 次额外分页／秒。应用故障主要放大内部绑定与快照，网关故障额外放大外部认证与额度，集中切网还可能叠加旧额度未释放。

## 计量与验收目标

调用可用性、命令接纳和最终任务结果保留独立分母。采样器按固定租户、负载和一个月窗口报告请求及失败时段，初始每 5 秒用隔离验收租户探测接纳、控制和权威查询。

| 计量对象 | 样本和截止 | 恢复后的处理 |
| --- | --- | --- |
| 接口调用 | 每次 command、query、receipt_lookup 单独计数；调用方发起至确定答复，最多 5 秒或其更早截止 | 超时仍记失败；内部重绑不增加外部样本，重连后新调用另计 |
| 命令接纳 | 按原服务、租户和 command_id 去重，固定首次时间与接纳期限 | 查得已提交可补充接纳事实，不修改首次接口超时 |
| 失败时段 | 固定采样间隔和探测流程 | 缺失探测记未观测，不填成功；同时报告采样误差 |
| 最终任务结果 | 原 Task 和冻结条件 | 完成依据、效果、费用及残留分别报告 |

系统过载、依赖故障和内部错误计入接口不可用。预先约定的权限或额度拒绝单列，不能故障后改分母。成功调用的延迟分布与超时数量同时报告。

| 指标 | 初始验收目标 |
| --- | --- |
| 接纳、控制提交、权威查询可用性 | 各自 ≥99.9% |
| 同地域接纳／控制提交 | p95≤300 ms，另观测 p99≤1 s，包含复制及本方依赖 |
| 控制／核对 job 领取等待 | p99≤2 s |
| 普通可运行 job 等待 | p95≤5 s |
| 健康在线入口控制传播 | p99≤5 s，实际停止另计 |
| 单应用故障内部重绑 | p99≤5 s，外部 WSS 保持比例另报 |
| 单区账本恢复 | 按[部署保证与限制](deployment.md#保证与限制)判断 RPO 和 RTO |

## 故障剩余容量与扩容

无状态池按损失一个区后仍可兑现的吞吐定副本数。若负载 L、单副本实测容量 C、利用率上限 U、损失比例 f，则 `N≥ceil(L/(C×U×(1−f)))`；三区均布以 f=1/3 试验。数据库提升后的写容量、设备串行能力和提供方配额单独测量。

积压 B、持续到达率 λ、故障后处理率 μ 满足 μ>λ 才能排空，估算耗时 `B/(μ−λ)`。例如 60 秒积累 17,400 个任务，恢复净余量 145/s 仍需约 120 秒。控制和收尾使用自己的保留池，不等待普通积压排空。

| 瓶颈证据 | 调整方向 |
| --- | --- |
| CPU 或连接入口饱和，数据库尚有余量 | 增对应进程池，同时限制单网关故障影响面 |
| 热行、WAL、锁或连接等待主导 | 降同键并发、缩短事务、有限批量；实测后增加承接新任务的 Orchestrator 分片 |
| 提供方／设备限流 | 限制准入和有限等待，增加 worker 无法扩大目标容量 |
| μ≤λ、最老责任持续增长或提交延迟超标 | 限新接纳，准备新分片和份额，验证恢复净余量 |

每次调节有上限与冷却期。记录全部事务而非只数业务调用，连接池总额包括所有实例、LISTEN、管理和恢复预留。长期存储含正文、WAL、索引、副本、备份与重建空间；每天 500 万任务一年仅任务身份约 18.25 亿个，命令和操作另计。最小记录增量按 `365×(N_cmd+N_close)×B_record` 估算，单条实际占用实测。

## 初始运行限额

限额由原 owner 跨副本共享，任何重启、换版或重新领取都不重置原累计计数。

| 资源 | 初始值 | 满额行为 |
| --- | --- | --- |
| 每用户活跃任务／模型在途 | 16／4 | 有界排队或等待 |
| 每用户待处理任务 | 100 | 接纳前 overloaded |
| 每任务决策轮／每轮补上下文 | 100／3 | 按策略等用户调整或结束 |
| 内部委派深度／活跃子数 | 4／8 | 拒绝新委派，原子任务继续收尾 |
| 单步安全重试 | 最多两次额外尝试 | 原效果核对或失败，不能重做未知非幂等动作 |
| 控制、核对、收尾 | 每分片非零工作和连接预留 | 普通任务不能借用至耗尽 |

## 保证与限制

本页 SLO 是冻结环境下的验收目标，不是任意负载的服务 SLA。明确等用户、设备、预算和提供方的业务等待单列；平台不能调度不应伪装成业务等待。控制到达、入口停止和原效果核清是不同时间点。

质量与 API 覆盖归[验收规则](validation/README.md)，不能从接口可用性推导。新增中间件的改选条件归[部署取舍](deployment.md#取舍)；容量实验失败不能单独证明必须采用某个 MQ 或缓存。
