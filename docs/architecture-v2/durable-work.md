# 持久工作：保存事实时，也保存下一项责任

[入口](README.md) · [任务推进](task-control.md) · [部署与恢复](deployment.md)

最常见的恢复错误不是队列暂时不可用，而是业务已经提交，下一项工作还只存在内存里。公共框架要解决这个缝隙：在同一 owner 的事务中保存原命令、领域事实和下一责任，再由有界 worker 继续。

它还统一处理一个容易遗漏的竞争：worker 正准备把任务标为 done，新账单或新控制已经到达。作业版本让旧完成无法覆盖新责任。

## 1. 三种身份各自回答一个问题

| 身份 | 回答的问题 | 不承担的判断 |
| --- | --- | --- |
| Command | 这是不是已经接纳过的同一请求 | 外部效果是否实现 |
| Job | 这个 owner 还有哪项持久责任 | 目标是否成功、动作是否可重试 |
| Claim | 当前哪次领取可以回写这份工作 | 远端旧动作是否已经停止 |

Job 按领域给出的稳定业务键合并，包含 `work_revision`、到期时间和 ready／leased／waiting／done 状态。Claim 固定 job_id、holder_id、lease_epoch 与领取时的 observed_work_revision。进程重启使用新 holder，续约不改变领取观察值。

这些是内部运行库接口语义，当前不是可编译 SDK，也不是新的公共 RPC。第三方组件只需兑现公开业务合同，不必使用同一库。

## 2. 框架应当消除什么重复代码

接纳模板负责认证后的原键查找、规范摘要比较、事务组织和合法回执保存；工作循环负责有限容量、领取、续约、受限事务与条件回写。领域处理器仍须说明原事实是什么、下一步能做什么、何时算责任完成。

| 框架必须提供的机械约束 | 调用方仍须给出的领域依据 |
| --- | --- |
| Tx 绑定 owner、身份域和已装配 repository，禁止逃逸与嵌套假事务 | 哪些业务对象需要共同锁定，如何判断授权与状态 |
| Command 唯一键及同键摘要检查，回执阶段符合方法登记 | 接纳／拒绝条件、业务对象的唯一映射 |
| Raise／Hint 的版本与到期更新 | 什么是新责任，什么只是重复事实或提示 |
| 固定 Claim、实际时间检查、Guard／Finish 同事务生效 | 返回事实是否可信，责任是否已完成或已持久交接 |
| 领取前容量预留、有限处理和到期发现 | 外部调用的发送边界、重试、核对和停止条件 |

只给调用方一组低层 API，还不能证明减少了重复实现。首轮应让 Task 推进和 Operation 执行真正使用公共接纳及工作模板，再检查哪些规则仍靠每个 handler 手写。repository 能力限制、锁序约束、panic 和提交未知的机械保护需要实现与反例；当前文档没有把它们当作已有编译器保证。

## 3. 接纳事务只处理本地事实

入口先检查身份、方法、路由、结构和容量，再按 `(tenant_id, logical_service_id, command_id)` 查原键。已有终结回执返回固定决定；只有最小去重记录时返回 `gone` 或摘要冲突；没有记录才检查首次接纳期限并运行领域逻辑。

同一 Tx 提交业务决定、回执以及确有必要的 jobs。不能留下没有继续责任的命令占位。跨库准备先保存准确准备阶段和原外部命令，再在事务外调用；若方法只允许 applied／rejected，内部准备不能自行新增公开 accepted 阶段。有限请求等待结束后按传输超时返回，原后台工作继续，调用方查原命令。

事务结果有三种实际意义：确认提交才能对外确认决定；确认回滚且只是数据库竞争时，可在有限预算内重跑纯本地闭包；提交未知先查原命令或业务阶段。提交未知不等于业务失败，也不允许释放未知预留。

加锁依次经过原命令键、领域规定的业务锁，最后稳定排序的 Job 行锁。需要共同裁决的领域对象先全部声明并锁定，取得 Job 锁后不再寻找新业务锁。隐式外键和唯一索引锁仍须由数据库实验检验，接口调用顺序本身不足以证明无死锁。

## 4. 一轮工作如何组织

工作循环先预留实际处理容量，再有限领取到期 jobs。领取只锁作业，提交后才载入领域输入。领取提交未知时，适配器以提交前保存的候选 Claim 查询确认；查不到可信原领取就不处理，不能重新拼造观察版本。

以派发文件操作为例，handler 读取原 Operation 和当前控制，在短事务内保存原发送准备；事务外调用原执行端；最后在另一个短事务内验证领取、合并合法事实、保存核对或结果交接责任。每个阶段恢复都查询原命令和操作，不因 handler 返回 error 就重跑外部动作。

一轮可在步骤和时间预算内完成多个这样的短阶段。长期等待保存依赖和 due_at 后退出，不长期占用 goroutine。后台 context 属于宿主与业务责任，不能继承已经断开的接纳请求。

续约未知时仍以此前已确认截止为最迟依据。停止信号或超时不能证明调用已经退出，物理容量只有确认实际退出才释放。跨端执行和模型提供方的未知物理并发分别按原领域保留。

## 5. Raise 与 Finish 共同防止丢掉新责任

`Raise` 与新领域事实共同提交，增加 work_revision 并提前 due_at；已完成或等待的 job 重新 ready，正在 leased 的 job 保持同一持有者。重复通知不增加责任：`Hint` 只提前已有未结 job，不创建、不重开 done，也不推进版本。

worker 回写时使用原 Claim，不能把 observed_work_revision 刷新到当前值：

| 条件 | 本次事务结果 |
| --- | --- |
| 领取身份、代次或实际截止已失效 | 所有受保护的领域和 Job 写入回滚 |
| 领取有效，当前版本大于领取观察值 | 可保存仍合法的原事实，但释放为 ready，保留新责任的较早到期 |
| 领取有效且版本相同，已完成或持久交接本次全部责任 | 写 done |
| 领取有效且版本相同，需要等待 | 保存具体依赖及有限到期，写 waiting |
| 当前版本小于观察值或字段不可能成立 | 拒绝并报告适配器或数据异常 |

假设 W1 领到 r=4，迟到账单事务保存 r=5。W1 随后完成 r=4，只能留下 ready；若 W1 先完成，新账单再把 done 重开为 ready。两种顺序都由同一 Job 行上的事务互斥实现。W1 自己的事务先 Raise 再 Finish，也必须看见新增版本。

Guard 和 Finish 使用实际裁决时的数据库时间，不能使用排队前或长事务开始时的时间。handler 的 `return nil` 不会自动 Finish(done)，panic 也不会变成业务完成。

## 6. 领取失效后仍可能收到真实事实

旧 worker 失去 Claim 后不能写自己的进度。但远端返回可能确实证明原动作发生过，丢掉它也不正确。原 owner 可通过独立事实入口核对来源、原业务身份和单调修订，再由新的领域事务归并效果与费用、建立下一责任。不能独立核验的结果只作为查询线索。

持续观察关联在建立时就保存责任，追平一次后以 waiting 继续，直到该关联生命周期结束。否则一个 done job 不能依赖可丢提示发现后来的变化。账单来源的 outbox 则在每次新费用修订时建立新责任，两者按领域含义选择，不能用一个通用轮询器替代。

到期扫描是工作发现依据；通知仅缩短等待。另有领域 Reconcile 按原业务键分页修复遗漏责任，不制造新外部动作身份。控制、收尾和核对保留容量，普通工作按用户公平限流，避免高负载时最需要恢复的工作得不到执行。

## 7. 公共层不吸收业务状态机

同一 JobStore 可服务任务推进、费用交回、内容清理和评测环境封闭，但这些处理器的 done 含义不同。未知副作用是否可重试、报告能否发布、设备是否真正停止，仍由所属 owner 裁决。

实现采用共同事务和 JobStore，是因为同库提交可以消除责任缝隙；独立 owner 仍通过原 Command 与可查询回执交接。如果实际两条主路径频繁绕过模板，应先收窄公共接口，而非增加可配置业务流程语言。此取舍遵循 [ADR-0009](../adr/0009-reliable-work-framework.md)，准确内部接口见[原持久工作方案](../architecture/.draft/reliable-work.md)。
