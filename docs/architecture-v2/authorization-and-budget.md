# 授权与预算：一次行动需要哪些独立依据

[入口](README.md) · [执行](execution.md) · [部署与恢复](deployment.md)

任务已经被接纳，不代表它可以把本地报告交给任意模型，或让任意设备创建提醒。安全模块回答当前主体能否为明确用途使用准确资源，并记录真实消费；Orchestrator 仍负责这一行动是否属于当前任务。

## 1. 权限围绕资源、用途和接收方收窄

认证确定租户和主体，不能信任请求正文自报身份。Grant 明确资源范围、动作、用途、接收方、期限、次数及费用上限。`read`、`process`、`store`、`sync`、`disclose`、`act`、`manage` 分别成立；读取网页的许可不自动允许长期保存、发给模型或公开。

资源类型由受信规范化器解释。文件路径解析到获准根内的准确资源，URL 范围约束实际连接与重定向，设备使用绑定稳定资源身份。模型文本或 hook 的允许意见不能代替规范化和当前 Grant 检查。

委派的每一维都必须是父权限的子集，并可核对唯一父链。若多份 Grant 各自允许不同接收方，不能拼成一份原来不存在的对外披露许可。

同 owner 的多项必要授权可在一个事务内共同占用。跨 owner 没有原子占用：部分成功仍需保存已消费事实，只有全部必要依据有效后才行动。可证明没有启动的占用按既有结算规则收束；不凭跨库失败把已消费次数倒回。

## 2. 查询许可与消费许可分开

`grant.check` 只回答当前条件，不能作为稍后发送的永久凭证。`grant.use` 以固定 use_id 和意图摘要消费，检查当前父链与余额并保存有限启动回执。答复丢失先查询原 use；同 use 重投返回原截止时间，不获得新窗口。

物理启动前仍要检查回执期限、已知撤回、任务控制、资源代次与来源状态。模型调用、内容处理等使用也要有准确业务身份，不要求为每一种使用额外创建 Executor Operation。

撤回先在原 owner 阻止新使用，再传播到持有端。持有端一旦知道撤回即停止新启动；尚未收到时，原有限回执窗口内仍可能启动。初始远端窗口为待测的 30 秒上限配置，并受原授权与部署限制；它不是已测出的全球撤回时延。

窗口成立依赖[可信时间及入口执行机制](deployment.md#clock-adapter)。本版保留其平台前提，不能仅靠调用一次“检查当前时间”便声称暂停的线程一定不会迟到发送。

## 3. 预算既约束启动，也记录已经发生的费用

Task 保存任务预算，Grant owner 保存权限和使用余额，供应方或执行 owner 保存原计费事实。它们有不同职责；一个费用出现在多个投影中不能被多次计入任务。

默认只有可信费用上限才能预留后启动。声明 `cost_bound=strict` 是接入合同，需要供应方或驱动证据，不能从参数中存在 max_cost 就推导出硬上限。

`estimate` 是受限例外：原 Orchestrator 与费用 Grant owner 必须位于同一受信本地事务范围，能直接检查 Task 内用户接受估算风险的记录，且所有必要 Grant 均无相应费用单位的硬 limit。公开 policy_ref、跨域缓存或“当前在线”不足以证明同意。跨 Orchestrator allocation 和离线租约坚持 strict。

实际支出 12、预留估算 10 时，账本记录 12，并停止同范围新计费，不能把费用截成 10。费用未知时保留预留，不能按超时填零；已释放的授权额度不因迟到账单而重新开放。

### 迟到账单由三方完成交接

假设报告已经交付，模型供应方后来把原调用费用从 10 更正为 12：

1. **费用来源 owner** 保存更高累计用量，并在同一事务建立交回 outbox。它沿原 Task 与原来源身份调用 `task.billing_reconcile`，直到收到 Orchestrator 已持久保存核对责任的 JobAck。
2. **Orchestrator** 把 JobAck 对应的核对工作保存下来，随后主动读取原来源。它验证原任务绑定、来源修订和准入时固定的唯一计费来源，再归并差额 2；通知里的金额不直接入账。
3. **Grant owner** 沿原使用结算真实累计额。原 use、Task 终态和已释放占用的历史保持，超额与退款按各自事实处理。

每个来源上调修订有独立 outbox 身份。交付命令的期限耗尽后，可为同一费用修订建立新的投递尝试；Orchestrator 按来源业务键去重，不能再扣一次。它先读到更高修订时，后来到达的旧修订只确认已有事实；同修订异摘要才冲突。

任务完成、操作关闭和旧 job 完成均不删除这项责任。没有可信账单更正截止期时，保留最小计费身份、累计账与查询入口。关于费用推进 Task 总修订后如何处理在途模型提案，见[尚待闭合的续行分支](task-control.md#accounting-revision)。

## 4. 离线额度需要事先分配

离线端不能凭缓存 Grant 自行扣远端余额。原 owner 先预留一次额度，固定设备实例及其本地账本；端上在这份额度内记录使用，重连后结算。租约到期只关闭新使用，未有可信关闭与用量证据前不归还余额。

有效期取 Grant、来源、设备与部署限制中的最小值。远端离线续用默认关闭；初始方案仅支持连续进程生命周期内使用分配。重启、可信时间丢失或恢复旧快照后，先在线核对；不能复用旧实例租约。

重连先读取当前设备撤销和内容关闭事实，再恢复上传、同步或新工作。迟到费用仍归原租约。全本地 owner 可直接核验本地权威账本，这是另一种拓扑，不是缓存远端授权的离线模式。

## 5. 用户确认固定到原业务决定

权限授予、发布批准和结果验收都不能由模型伪造一个按钮完成。实际 owner 保存 Confirmation，绑定准确原命令、意图、挑战及预期主体；受信入口认证用户，业务事务核对并一次消费。

两台设备并发回答，只能有一个固定决定。批准后再点“拒绝”不会撤回既有授权；撤回是独立管理操作。更换候选、目标或请求修订时，旧确认不能套到新内容上。

需要预览时，受信 Renderer 取得并呈现准确材料才启用依赖按钮。`preview_refs` 只表达回答针对哪些版本，本身不是已下载或已阅读证明；业务端仍检查版本、覆盖、当前来源与用途。任意第三方客户端更强的呈现证明不在现行合同中。

## 6. 身份和隔离从宿主入口落实

本地管理 Web 使用受控会话、Origin／CSRF 防护和受保护的传输与 cookie 设置。设备配对区分有限期 device code 与给用户的 code，认证批准后才允许一次领取；配对撤销推进凭据代次，重新配对产生新实例，不继承旧实例未结清额度。

WSS 建连认证不覆盖整条长连接，每条消息仍检查当前身份与权限。正文撤权时关闭披露，但用户若仍有取消或删除权，应可通过最小管理元数据行使这些权利。

同租户与跨租户都需要队列公平性、物理并发、费用、字节和存储上限；不能通过开多个 Orchestrator 绕过同一用户限额。控制和核对保留容量，避免普通任务挤占停止旧工作的通道。

原生插件在受信进程内运行时属于可信代码。若允许不可信代码，必须有通过验收的实际隔离边界；类型接口、包签名和静态审查本身不构成运行沙箱。准确 Grant 字段、错误和配对流程仍见[原安全契约](../architecture/.draft/security/README.md)及[实现说明](../architecture/.draft/security/implementation.md)。
