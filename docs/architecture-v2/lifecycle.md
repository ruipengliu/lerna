# 装配与生命周期：从一台空机器到当前可用实例

[入口](README.md) · [评测与发布](evaluation.md) · [部署与恢复](deployment.md)

一个包下载完、评测通过、用户批准、节点运行起来，是四项不同事实。Extensions 把精确制品装进宿主，Evaluation 决定某个候选可以在哪些目标启用；实际业务入口还要确认当前实例已经就绪。

## 1. 默认装配保持简单

受信内置组件随 Go 宿主构建，通过进程内接口装配；更新这类代码需排空并重启。需要独立安装和切换的可执行扩展使用受控子进程或服务。默认不采用 Go plugin 动态装载，也不先建设插件市场或全局依赖解析服务。

InstallLock 固定制品、完整依赖、配置、平台与数据格式。任务引用准确清单，运行中不再按“最新包”解析。Brain、Memory 和 Executor 可独立替换，但替换必须保持原协议、效果与恢复语义。

Skill 是版本化操作材料，Agent 配置指定模型、Skill 与允许能力。可读的 Skill 不自动成为可信指令，安装也不自动授予用户文件、模型披露或设备操作权限。普通调用只引用已就绪组合，不逐次建立安装和发布对象。

## 2. 首装依赖的信任根先于业务组件

干净机器先启动受信最小宿主，提供身份、制品核验、有限批准、管理诊断和恢复。它不依赖尚未获准的 Brain 或插件自行批准自己，也不要求完整改善实验系统已经运行。

首装链如下：

1. 核验发行来源、实际制品及依赖摘要，取得绑定准确平台和配置范围的契约符合性报告。
2. 通过受信 ReportSealer 导入端口验证随包报告；保留原构建环境与运行来源，另存本机差异预检。
3. 形成唯一 InstallLock。用户或获准维护者通过批准 owner 的确认入口决定，确认与本机有限目标的 compatibility 批准在同一业务事务消费。
4. 以固定 activation_id、空旧版清单和 `expected_generation=0` 接纳首次激活，完成实际装载、自检与入口开放。

有效随包材料与本地批准允许离线首装。材料缺失则先做 compatibility_check 或保持诊断，不存在绕过证据的默认开发开关。conformance 只说明契约符合，没有旧基线时不虚构改善成绩。

这条链消除了“先安装评测组件才能批准首装”的循环；它仍依赖可信发行、报告签名核验、批准 owner 与本机预检的真实实现。它们属于首个工程切片，尚不是仓库已有的可运行安装器。

## 3. 核验的是实际装载字节

制品在独立暂存目录展开，限制字节、数量与深度，拒绝路径逃逸、越界链接和未声明入口。默认使用预构建制品，不执行下载包中的安装脚本。

PackageVerifier 检查取得字节、展开文件及完整依赖；清单发布后不可就地覆盖。装载入口从受管不可变目录读取准确文件，平台权限与句柄要防止核验后替换。摘要证明字节对应，来源信任仍需独立证据。

制品字节先持久化，再提交可用记录和 InstallLock。任务、操作、迁移和回退在使用前登记 LockReference；跨库预登记后结果未知，引用仍保留。清理先封闭新引用入口，再核对所有持有者及引用修订。失联不能归并成零引用。

## 4. 切换默认先排空旧绑定

激活接纳保存目标、新旧清单、批准、预期代际和下一 job。同一目标通过预期代际竞争，只有一个切换可以提交。

排空先停止向旧绑定接纳相关新工作，再等待已有责任到可交接边界。活动任务的准确清单保持，旧 Operation 仍用原驱动核对。HTTP 超时、UI 显示完成或旧进程被杀，都不能证明原责任消失。

期限到而效果、费用或格式仍无法交接，激活进入 blocked，明确阻塞引用。这可能让升级等待很久，是默认排空换取简单一致性的代价。只有明确声明并验证状态、资源与格式隔离的无状态实现，才可让旧任务留在旧实例，同时给新任务开放新版本。

迁移有唯一步骤身份、检查点、可读格式范围及幂等或可核验恢复条件。字节重写形成新不可变版本，映射逐批提交。不可恢复的迁移不执行；不可逆格式变化要在批准前说明，不能事后把“切回旧代码”称为完整回退。

## 5. 当前实例就绪不能借用历史激活成功

| 记录 | 表达的事实 | 何时改变 |
| --- | --- | --- |
| Activation 的历史启动依据 | 原激活曾基于什么清单和批准提交 | 历史依据保持 |
| ActiveBinding | 当前目标使用哪个清单及活动代际 | 新激活推进代际 |
| InstanceReadiness | 这个进程实例实际装载、自检和获准启动的事实 | 每次实例重建重新取得 |

装配先在不可见的局部注册集合构造实例与 handler，有界初始化和自检。自检不能偷偷启动计费模型或外部效果；确需真实资源时先有相应许可、预算和原操作记录。

随后短事务核对准确配置、当前实例、批准和预期代际，保存活动绑定及 readiness。提交并确认实际装载后，路由才发布 handler。数据库与内存指针之间无法原子提交，缝隙中的崩溃应导致暂不可用，不能开放没有依据的实例。

配置 A 初始化时被配置 B 替换，A 的完成或清理只能处理自己的暂存实例，不能使 B ready 或卸载 B。读取端也检查当前实例租约；进程突然退出、旧 ready 行尚未更新时，不能继续返回旧的 `ready=true`。

重启沿原 ActiveBinding 装载新实例，取得绑定本次 instance 的新 reopen 启动依据。它不推进活动 generation，也不重跑迁移。原 activation 解释历史切换，新 readiness 解释现在是否可用。

## 6. 批准窗口与业务许可分别成立

全本地共库可以把当前批准检查与启动登记放进同一事务，不伪造远端使用回执。远端以固定 use_id 调用 `evaluation.approval_check`，绑定准确 activation、reopen 或 work，取得有限 start_before；同 use 查询不续期。实际启动还要检查当前窗口与已知撤回。

已有激活实例只有显式得到 approval_lease，才可在固定 continue_until 内离线续用。离线租约不允许激活新版本或扩批，重启也不继承旧实例租约。每项业务的 Grant、来源和任务控制仍要各自满足。

## 7. 停用与回退按实际结果报告

安全停用封闭新入口，旧受信实现可保留受限核对能力；若代码本身不再可信，停止运行并报告查询缺口，不能为取得一个“排空成功”继续执行它。

自动回退使用**独立旧版批准**。批准新版时固定精确 rollback_lock 和同 owner 的旧批准引用，核对其目标、期限及自身报告；回退时再次检查当前有效性、代码信任和旧版能否读取当前格式。缺一项就只停用并报告恢复缺口。

条件成立后建立新的回退 activation，使用旧版批准取得启动依据。撤回新版不撤回或复活旧批准；数据、权限、费用和外部效果也不回滚。逐目标报告新版停止、旧版恢复及残留责任，不用一个 rollback=true 掩盖差异。

## 8. 渐进发现只在总收益成立时采用

小目录可直接加载准确声明，大目录可 search 后 describe，Skill 可先读用途和适用条件，再按需要加载正文。缓存键包含准确版本与查询范围，实际使用仍检查当前权限、来源、依赖和 ready；目录不可达时，独立可核验的原准确绑定才可继续。

选择诊断记录未召回、同名歧义、加载过晚、实际采用及未使用原因。减少目录 token 只是中间指标；额外搜索、加载、模型回合及维护成本都计入任务实验。没有净收益或存在关键类别退化时保留原策略。
