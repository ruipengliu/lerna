# 事实归属与关键选择

[入口](README.md) · 前一篇：[任务经过](task-journey.md)

任务链中最重要的接口不是“谁调用谁”，而是“返回以后确认了什么”。Orchestrator 可以确认已准入写入，Executor 可以确认已接纳操作，只有相应目标证据才能支持写入效果；任务是否完成还要结合其他必要条件。这些区别决定记录、事务和恢复边界。

## 一项事实有一个裁决位置

owner 表示固定的逻辑负责方。它保存原事实、处理并发竞争，并提供查询与恢复入口。缓存和聚合视图可以复制必要投影，但不能据此改变原负责方的决定。

| 事实 | 裁决与保存者 | 其他参与者取得什么 |
| --- | --- | --- |
| Task 的目标、控制、行动准入和完成 | 原 Orchestrator | 当前任务、原回执、固定结果与缺口 |
| 固定输入的一轮提案和模型用量 | Brain | Decision、提案、调用事实和费用 |
| 原操作的接纳、尝试、效果 | Executor；实际资源入口由资源 owner 控制 | Operation、目标凭据、观察及未决事项 |
| 准确内容、来源与记忆版本 | Content／Memory owner | 版本引用、获准字节、查询范围和当前可用性 |
| 许可使用与结算 | Grant owner | 原使用回执及累计结算事实 |
| 输入或本人确认是否消费 | 实际业务 owner | 一次消费决定与其业务结果 |
| 组件活动版本与实例就绪 | 扩展宿主；批准资格由批准 owner 裁决 | 安装清单、活动代际、当前 readiness 与残留责任 |

Confirmation 随消费它的业务决定提交。即使共用确认代码，也没有一个可以替所有数据库原子消费确认的中心。

## 四种边界不要混在一起

**模块**组织代码规则，**owner**限定事实裁决，**进程**决定故障与隔离，**本地事务**决定哪些更新能共同提交。四者可以重合，也可以不同。

同一 Orchestrator 内，任务、祖先控制、预算及派发责任需要共同判断，保留在同一本地事务范围。生产把命令入口和工作者拆为多个进程，它们仍使用同一份权威任务存储。Brain、Memory、Executor 可以独立替换或远端部署，跨库之后各自保存接纳及后续责任。

同库本身不授予跨模块任意写权限。需要共同提交时，宿主装配受限事务参与者；网络、模型、工具和人工等待均在短事务之外。对象存储先保存字节、数据库再发布引用，也有自己的中断和孤立内容清理责任。

## 对象随问题出现

普通请求用六组对象组织。这里的“组”帮助应用理解职责，不减少原契约中的独立消费、保留和恢复义务。

| 对象 | 为什么保留它 | 身份与生命周期 |
| --- | --- | --- |
| Session | 一段对话可涉及多个目标，需要保存消息及其任务关联 | 应用管理；归档和窗口关闭独立于 Task |
| Task | 一个目标需要跨模型轮次、输入和操作持续推进 | 原 Orchestrator 固定；终态后仍有原效果和账务收尾 |
| Decision | 需要解释某份提案依据什么、花了多少，以及是否可能已请求模型 | 固定输入和配置；含 0 或 1 次物理模型请求 |
| Operation | 一个行动可能多次传送、经历多个合法尝试，效果仍须归于原意图 | Orchestrator 保存意图，Executor 保存接纳及效果；接替不换身份 |
| Content | 同一报告要供模型、核验、写入和呈现引用 | owner、content_id、version、hash 固定字节；当前用途另行核验 |
| Grant | 许可可能跨任务存在，并且有独立撤销、消费和费用责任 | 原授权 owner 裁决；撤销不抹除既有使用 |

Requirement、覆盖记录、Snapshot、候选消费、OperationIntent、预算和 Result 通过 Task 组织。ModelCall、Proposal、Attempt、Effect 和用量归相应 Decision／Operation。它们可以使用类型化字段或关联表，物理布局由查询与并发决定。

InputRequest、InputSubmission、Confirmation、Surface、授权使用及内容副本具有独立消费或清理责任，不能随会话正文或父 Task 级联消失。列表、摘要、进度和回合视图可以重建；已经用于某次 Decision 的输入版本则必须固定。

Command、Job 和 Claim 属于共同工作机制。Command 标识一次业务裁决；Job 保存某个对象仍待履行的责任；Claim 是一次有限领取。一个 Job 结束，可能只表示已把责任交给下一作业，并不等于任务成功。

## 保留哪些取舍

| 选择 | 获得什么 | 承担什么，以及何时重评 |
| --- | --- | --- |
| 每 Task 固定逻辑 Orchestrator | 一套目标、预算与控制裁决，可由共享账本的进程接替 | 原端失联时依赖任务等待；需要跨端自动接管时，先证明旧端隔离、在途效果及权限预算交接 |
| Brain 一轮提案，Orchestrator 管循环 | 推进和恢复进度集中，提案不能直接取得行动权 | 多轮交接增加延迟；有限计划和规则续行可优化，须保留同等准入与恢复 |
| 同域短事务，跨域持久命令 | 已保存决定有明确继续者，避免隐含分布式原子性 | 原命令、回执、核对和未知预留形成存储与读取成本 |
| PostgreSQL 保存事实与 Job | 业务变化和工作发现可共同提交，初期少一套持久中间件 | 数据库承担扫描、索引、清理与故障积压；出现实测瓶颈后再评估消息或缓存系统 |
| 长期最小去重与终态记录 | 清理正文后仍能拒绝旧请求复活 | 存储和备份持续增长；要求全部身份物理删除时，需另评身份代际及不可延长期限合同 |
| 通用 assessed，强保证另行收紧 | 普通开放任务不必先为所有质量判断建立校准体系 | 未校准范围须披露；高影响用途依固定独立证据准入 |
| 默认受信组件与静态装配 | 普通任务不依赖动态插件控制面 | 任意原生代码的隔离要逐平台证明；接口约束不能构成恶意代码沙箱 |

这些选择分别落实在现有 ADR 中，完整对应见[来源与覆盖](coverage.md#adr-map)。v2 没有用较短的说法取消其中的成本。

## 不变量与实现自由

实现可以改变表名、索引、工作池和内部组件组合，但以下行为需要保持：原命令不因重传换义；合法决定与后续责任共同保存；旧控制和旧领取不能覆盖新事实；未知效果有可定位的继续者；成功只能依据当前适用的证据；当前权限在实际使用位置成立。

这不意味着每个模块都要建独立数据库、每个字段都要一次事务，或每条消息都要一个新对象。反过来，把多个页面合成一张界面，也不能合并接纳、效果和完成的含义。

目前尚未由接口和运行实验充分证明的保证集中在[边界清单](open-boundaries.md)。具体失败恢复从[持久工作](durable-work.md)进入，实际平台约束从[部署](deployment.md)进入。
