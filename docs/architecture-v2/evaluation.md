# 评测与发布：怎样证明一次改进值得启用

[入口](README.md) · [任务完成判断](verification.md) · [装配与生命周期](lifecycle.md)

一次任务通过条件，并不证明某个新模型或 Skill 普遍更好。生产日志可以发现退化，却混合了不同目标、用户和环境。Evaluation 用固定计划、隔离环境和独立取证比较候选；发布批准再限定可以实际启用的范围。

普通任务的 ConditionResult 仍归原 Orchestrator。用户纠正记忆沿 Memory 管理，不要求每条偏好都成为发布实验。只有使用评测与发布能力时，才创建这里的独立记录。

## 1. 诊断先定位问题，实验再验证改进

恢复需要的命令、效果和授权事实不可采样丢失。Trace 可以采样，须声明缺失；通用日志默认不复制提示词、正文或截图。获准诊断使用准确受控内容引用，指标使用有界标签。

失败沿处理链归因：目标遗漏、检索没召回、上下文裁剪、参数或准入、传输恢复、工具语义、完成判断都可能是原因。记录最早可证实问题、后续影响和仍未知部分，证据不足保留“归因未知”。例如包装器漏页不能只算模型回答错误，写入成功但答复丢失也不能计为工具未执行。

选择候选时尽量一次改变一个因素，固定模型、环境、数据、权限和预算；有单项证据后再测组合。模型调用更少、上下文更短，不自动说明最终质量或总成本更好。

## 2. 开发、选择与正式确认使用不同数据

开发集用于调试，selection 用于比较并选择候选，holdout 用于候选固定后的正式确认。样本按来源任务组隔离，改写、派生材料和重复种子不能装作独立新样本。哈希能找相同字节，不能单独证明来源独立。

所有候选与尝试先登记，包含失败、取消和未形成报告的尝试。一个 release_request_id 固定一个准确候选、一份正式计划和一个未暴露 holdout；三者绑定和数据占用共同提交。运行中断不会把该子集退回成“未使用”。

还需要约束整个 improvement_id 的选择过程。首次正式计划前，受信维护者固定候选范围、正式尝试上限、停止规则和比较方法。默认一次正式确认；若计划多次确认，在任何 holdout 反馈开放前就须规定适用的多重比较或序贯方法。换申请名或新的数据集不重置同一改进过程的历史。

## 3. 计划固定分母，恢复固定原样本

EvaluationPlan 固定样本、种子、基线与候选清单、环境、判定器、预算、重试、停止及失败口径，同时声明主要改善量和各类退化界限。修改产生新计划，不能改原申请的绑定。

一份计划只接纳一个逻辑 EvaluationRun。SampleRun 固定 `(sample_id, arm)`，Attempt 只是该位置的有限尝试；重启或重试不增加独立样本数。基线与候选从相同冻结初始状态运行，各有隔离环境，不共用已被前一臂修改的设备或记忆。

环境提供方按预存的 environment_key 准备准确样本臂。它须提供 prepare、start_sample、inspect、observe_truth、seal、destroy 的可恢复语义；准备和样本启动核验有限许可。候选只访问任务观察与动作，独立判定器通过受保护只读通道取得真值，候选不能读取答案或更改评分配置。

样本完成后先封闭新动作并处理允许的在途责任，再取最终真值。效果未知时沿原操作核对，不能为取得可评分结果重复未知写入。取消整个 run 会为所有已创建及创建未知的环境保存 seal 责任，费用与清理在总期限之后继续。

双方任务启动前的环境预检失败记 invalid 并留下必需覆盖缺口；启动后的基础设施故障按未成功留在分母。未知、超限及候选异常也按冻结口径保留，不能删除坏样本提高成功率。整次实验无效条件必须事先规定。

## 4. 报告分别回答三个问题

| 判断 | 所需依据 |
| --- | --- |
| 固定样本上的比例是否达到目标 | 完整分母、真实目标达成及冻结的失败口径 |
| 是否通过适用统计验收 | 抽样总体、相关结构、样本量、选择与停止方法 |
| 相对基线是否改善 | 成对结果、最小实用改善、关键类别退化、全部成本与时延 |

方法或样本不足可以报告固定集合比例，但统计或改善门槛为 inconclusive，不能补成 pass。主观判断固定评估模型、提示与不确定性；第二判定器的分歧是敏感性证据，不能运行后挑有利分数，也不自动成为真值。

成本包含失败分支、等待、汇总、清理和迟到账单。Skill、记忆、模板的构建维护成本另列，并按事先声明复用次数计算摊销区间，不能假定无限复用。账单未结或差异不确定时不宣称省费。

普通 compatibility_check 只产出 conformance 和 compatibility 批准；首装无需旧基线。改善失败后不得原地自动降为兼容通过，另起明确兼容申请仍保留原尝试历史。

## 5. 反馈开放本身就是需要保存的事件

正式报告封存前，普通读取只提供进度和准备故障，不泄露逐例答案或成绩。`evaluation.feedback_open` 先保存主体、范围、来源组和暴露事实，再返回内容；答复丢失仍视为已暴露。

正常封存后开放反馈不撤销该报告自身，但同来源组中尚未封存的其他正式计划会受影响。通过其他路径泄露也可由受信维护者登记；发现早期泄露时，原报告保持不可变，当前证据资格失效并说明原因。

关键竞争发生在“暴露已登记、影响扫描尚未跑完”之间。正式计划、新样本与重试、封存、改善批准、启动和扩批都直接核对原暴露及来源组事实，不能只信可能滞后的 PlanEligibility 投影。分页扫描负责逐项关闭环境和传播撤回，不承担同步放行判断。

已签发有限启动窗口或离线租约仍可能允许未收到撤回的目标行动。保留逐目标未确认范围，原环境继续收尾。系统不能从“撤回已接纳”推导所有远端已经停止。

## 6. 报告通过之后，还要批准和实际激活

受信批准固定候选、报告、有限目标、批次、观察窗口、退出阈值、期限与精确回退引用。模型和候选没有自批权。扩大目标、更换候选或降低阈值需要新批准。

发布 job 为每个目标建立唯一 activation_id。只有本批各目标实际绑定且 ready，观察窗口和最小样本均满足，才进入下一批。节点离线、激活未知或样本不足时等待或停止，不能按管理命令 applied 宣称整批成功。

达到退出阈值时先停止扩批并停用新版。旧版恢复沿[独立旧批准和当前格式检查](lifecycle.md)，没有有效依据就报告恢复缺口。Rollout.finished 只说明有限批次执行和观察完成，不解除活动节点的当前批准、撤回和原效果责任。

验证器也使用此证据链。普通开放质量 assessed 可在基础契约及范围审查后启用并披露尚未专项校准；高影响用途按 TaskPolicy 要求专项证据。正常停用与已确认判断缺陷不同，后者通过[任务完成门禁](verification.md)约束活动任务，历史 Result 不被重写。

精确评测计划、报告和批准字段见[原评测契约](../architecture/.draft/evaluation/README.md)。部分管理设计接口的精确公共请求尚未冻结，按[现有方法登记](protocol.md)声明可用范围，不能仅凭这一章宣称第三方发布互操作已完成。
