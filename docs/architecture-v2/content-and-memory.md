# 内容与长期记忆：保存材料不等于取得使用权

[入口](README.md) · [Brain 与上下文](brain.md) · [授权与预算](authorization-and-budget.md)

任务比较软件版本时会产生原始网页、引用片段、报告、截图与验证报告。这些材料首先是 Content：准确字节、版本和来源。只有确实需要跨任务复用、并取得相应用途许可的材料，才进入长期 Memory。

这个区分让首个任务链无需部署完整记忆系统，也避免将“为了当前任务读到”扩大为“永久记住、同步到云端并用于其他任务”。

## 1. ContentRef 固定读到哪一份材料

Content owner 保存内容身份、版本、摘要、来源边和治理状态。业务记录引用准确 ContentRef，不能用一个可变文件路径或最新版本指针代替当时的输入。派生内容绑定实际处理过的来源集合；即使摘要不再含原文，来源约束也不会自动消失。

保存时先提交字节，再把业务引用与后续责任共同提交。中断留下的无引用内容可回收，但回收必须与建立新引用互斥，不能删除正在被接纳的成果。存储正文、读取、处理、复制、披露是不同用途，各自检查许可。

关闭来源先阻止新使用，再持续清理受管副本。关闭 Content 不可逆，物理清理分别报告待完成、已完成和残留未知；一条“删除成功”不能掩盖失联设备仍持有字节。备份恢复也须先同步当前关闭事实，再开放使用，不能把旧备份当成重新授权。

## 2. Memory 保存可以独立管理的跨任务记录

每个记忆库只有一个权威 owner。记录分为 fact、preference、inference、experience；类型帮助解释材料，不证明真实性。用户可以独立查看、纠正、限制和删除 Memory，无需先创建一个 Task。

创建记录与索引工作共同提交。替换固定预期修订；旧修订退出当前检索，依赖它的记录标为待复核。获准历史读取可以保留旧证据，不能把旧值继续混作当前事实。纠正也不能删掉派生材料曾用过的来源关系。

默认提取流程产生待确认候选，除非已有明确的有限预授权。终结后的自动提取以原任务、终态修订和提取策略版本去重，沿原任务的准确输入及结果形成候选。失败、取消或效果未知不能被提取成“成功经验”；本地限定材料也不能因提取而进入远端模型或云端库。

本地私有库与云端库可以由不同 owner 管理。它们不是一份离线多主记录；离线端可创建属于自己的新记录，随后显式合并，不能覆盖原 owner 的旧修订。

## 3. 先划定可处理范围，再检索和排名

搜索整个库后过滤输出，会让未授权材料参与排名或模型处理。因此查询先依据认证主体、范围、用途、接收方与来源状态形成允许处理的集合，再执行检索。

默认 B0 是可解释的字面基线：ASCII 大小写折叠、Unicode 字面匹配，多词项按 OR 命中，再按匹配词数、范围具体程度、观察时间及稳定 ID 排序。索引是可重建投影，权威记录和已提交变更序列才是恢复依据。检查点必须覆盖连续提交范围，不能把数据库序号的空洞当作已处理。

索引落后时，有界补扫权威增量；超过行数、字节或时间预算就返回缺口。查询不是重建索引的入口，也不能因索引陈旧假装没有记录。

一次查询冻结有限的 `(memory_id, revision)` 集合和顺序。每页再检查当前权限、来源与记录状态：失效项跳过，不泄露受限标识；新记录留给新查询。游标按已扫描位置前进，因此空页仍可能有下一页。部分覆盖、变化与未扫描范围明确返回，跨库查询也分别保留各库游标和缺口。

管理列表读取最小元数据，可让用户在无正文读取权时仍行使删除或限制权。它与内容检索的目的不同。

## 4. 更好的召回先作为可比较候选

当前默认与优化提案分开交付：

| 配置 | 要解决的问题 | 额外责任 |
| --- | --- | --- |
| B0 字面基线 | 给出无模型依赖、能回放的起点 | 明确字面召回局限 |
| B1 中文词法候选 | 中文、混合语言和短词的覆盖 | 固定二元组与 ASCII 词元规则，验证否定、ID 和代码反例 |
| B2 混合候选 | 同义表达的召回 | 合法本地嵌入、独立索引水位、向量保存与清理、质量与资源证据 |

B2 首轮提案在已有 PostgreSQL 上对获准有限集合做精确向量计算，再与词法结果按固定 RRF 参数融合。筛选条件必须在候选处理前生效；只有 SQL 中存在 tenant 条件并不足以证明这一点。排序分数不表示事实置信度。

词法和向量分别保存连续覆盖水位。向量缺失时可返回带缺口的词法结果，不能把词法补扫称为补齐语义召回。查询创建后发生的降级要记录；不能临时改称它原本就是 B1。

本地编码器固定模型和 tokenizer，禁用网络与隐式持久缓存；每次真实计算都计入处理许可和资源预算。IndexWorker 在事务外计算，取得有效领取和当前来源检查后提交投影；查询编码只在当前有界处理内暂存。旧计算尚未证实结束时仍占物理容量。缺少这套装配证据，B2 保持关闭。

## 5. 冲突需要保留证据，不能靠新近程度消解

结构化正文的候选格式应保留主语、否定、适用范围、观察时间、有效时间和来源，未知时间不得用提取时刻补齐。两条记录看似矛盾时，先核对是否同一对象、是否有绑定旧修订的明确纠正、适用时间和范围是否重叠，再判断语义冲突。

可选的一跳关系扩展只解析正文已明确声明的冲突伙伴与适用前提。每个扩展项仍独立核验处理许可，并消耗同一总预算。关系投影与内容来源边用途不同，不能把推断关联写成真实来源；没有发现关系也不证明不存在冲突。

这些结构化内容、关联扩展和读时整理仍属于优化候选。默认不会按使用频率自动遗忘权威记录，也没有完备的结构化 as-of 查询合同。需要更多事实推断时，把证据和缺口交给任务，计算成本沿原决策和授权记录。

## 6. 同步传的是受控视图

记忆策略区分 `local_only`、受控远端处理和受管复制。本地限定同样约束派生摘要、向量和布尔结论，不能只检查正文是否上传。

同步先用 `memory.view.open` 固定一致切点和有限对象，再接续 Memory 变化。接收端把记录、墓碑、必要处理工作和游标共同提交，之后才能确认接收。变化序列断裂时停用旧视图并重新取得快照。

这个视图覆盖的是指定切点和已接续变化。Grant 扩大可能让旧记录新近可见，却不会制造 Memory 修改事件；权限范围扩大后需要新视图，不能把旧游标耗尽解释为当前全部可见内容。

复制前向内容 owner 登记副本；登记与来源关闭互斥，避免清理扫描漏掉刚建立的持有者。镜像读取仍须核验原 owner 当前状态，镜像不是离线权威转移。设备镜像票据固定接收方预分配位置、原 Content 与发送方，不能用任意上传路径逃过副本治理。

副本持有者可通过受限控制查询取得关闭状态；该入口不返回正文或下载地址，也不新建普通 Grant。清理完成据实际载体逐项确认。记录限制、副本清理与仍可保留的最小审计身份各自表达，避免把清理过程变成重新披露受限内容的理由。

实现可以把 RecordStore、ContentStore、查询集合、视图、索引和副本治理放在同一宿主。边界依据事实归属划分，不要求各自独立部署。准确字段和查询规则见[原记忆契约](../architecture/.draft/memory/README.md)；候选配额与实验矩阵保留在[优化方案](../architecture/.draft/memory/optimization-plan.md)及[验证计划](../architecture/.draft/memory/validation.md)。
