# 29：协作移交 Task Owner

同一 task_ref 的源端进入 PREPARING 后冻结业务推进；目标准备检查点但没有任务执行权。源端确认旧执行端不能再启动动作后，在单次 Runtime 事务中保存 SEALED 和唯一签名激活 Outbox。目标校验同一请求、双方、epoch、版本和检查点摘要后原子激活 epoch+1。没有跨库事务，也没有失联后自动抢占。

## 接入与信任边界

宿主通过 `Service.Handoffs` 安装 Ed25519 私钥、逻辑拥有者到公钥的映射、当前 `Policy` 和 `Isolated` 检查。每个管理边界还检查本地当前 `task.handoff` 权限与任务主体。Policy 必须核验双方当前授权、身份映射、必要恢复内容可获得，以及允许处理、披露和保存；引用不等于内容已可恢复。不能把示例的允许策略用于未受信数据。Isolated 必须覆盖所有能启动旧执行的端点，包括离线资格；不能用心跳超时、数据库封存或连接断开代替隔离证据。回调必须遵守带期限的 context。

实际动作仍经过 `execution.Core.CheckExecution` 和 `WorkPort.GuardExecution`。冻结检查还覆盖领取、续租、生成、控制、输入更新和委派的 RunStore 写入；无关任务继续运行。已经启动的动作并不因封存消失：原执行权威保留账本，执行报告按原 qualification/operation/revision 入冻结转交队列，新拥有者核对。未受理的控制/输入明确返回可恢复错误，调用方保留原请求，不伪造已接纳回执。

调用顺序为 Begin → Export → Prepare → Seal → Activate。按持久保存的原请求与 Status 恢复；封存提交未知时不能发送调用失败产生的材料，只能核对原 SEALED 决定。重复激活不增加 epoch。封存后目标永远不可达也不能 Abort。未封存可 Abort；若对端已准备，用源端 `Aborted` 签名证明调用 `DiscardPrepared`，再开始新的移交操作。旧撤销证明不能撤销已激活目标。目标可以继续同样协议移交到新的拥有者；参考实现保留旧拥有者墓碑并拒绝覆盖已有任务，未提供回迁覆盖旧墓碑的管理流程。

WebSocket 双方协商 `task.handoff.v1`，宿主安装 `Binding.Handoffs` 和接收事实所用的 `HandoffWorker`。prepare、activate、facts、discard 和原接纳窗口核对复用现有 mTLS、当前披露、分块、消息关联及有限 I/O。移交材料自带双方签名关系；传输成功不是封存证明。参考接入由宿主显式重试每一步，没有无限后台投递循环。

## 检查点、接纳及父子责任

检查点复制完整 RunSnapshot 与本任务提交、提交请求、控制、输入更新记录，以及原操作接纳与窗口水位。包含工作、未知效果关联、控制进展、等待项、生成预算、委派预留、父子关系和路由。摘要针对已保存的确切 JSON 字节；重试直接使用该字节串。执行私钥、授权发行秘密、其他任务及独立内容/记忆权威不复制。激活清除旧租期并增加工作 generation，保留原执行关联；旧资格不变成新执行许可。

既有原操作精确导入，未知外来操作不能被目标本地新窗口接纳。开放原窗口中的新请求由目标 `OriginalRequest`、原权威 `ValidateOriginal`、目标 `ImportOriginal` 验证；不导出 HMAC 秘密。导入的身份绑定原任务，Submit、Control、Update、Delegation 和新 Handoff 都检查作用域。该证明仅预留身份，具体业务仍检查当前权限、版本、期限与预算。原权威不可达时等待，关闭原窗口的首次接纳被拒绝；移交不延长窗口或授权。连续移交保留既有操作，尚未接纳的新原始请求仍需能联系其原发行权威。

父任务迁移不重建子任务或派发新额度。目标 `Route` 将激活证明与新父节点的精确认证 presentation 绑定；子端 `WithParentRoutes` / `FollowParent` 校验来源、epoch、签名和当前路由策略，持久保存 ParentRoute。宿主用 `Peer.WithParentRoute` 联系原子端。新 peer 无证明被拒绝；旧 peer 的 Lookup、Report、Cancel 以及 Accept 重放都受当前路由约束。原子任务、原 signed leaf 和运行预算责任不变。

## 恢复与有限资源

普通重启只适用于持久存储未回滚、身份与执行端排他的情况。已知旧备份、回滚或克隆必须用 `Service.Quarantine` 进入隔离；只有 `VerifyRecovery` 的外部排他权威核验通过，宿主才使用返回的服务。恢复期间宿主须隔离整个旧运行环境。任意代码绕过隔离入口、复制签名密钥或使用被攻破宿主，不在保证范围；较旧 SQLite 中的自述状态不能证明唯一权威。

检查点最多 2 MiB，签名正文最多 3 MiB；WS 编码后的单请求/回复另限 1 MiB，所以网络有效检查点上限更小，超限明确拒绝。每次检查点最多 1024 个操作，每库最多 10000 个导入操作、32 个原权威水位；历史移交最多 32 项，每移交最多 32 条迟到报告，执行报告每操作 revision 1–32。任务表、现有 8 MiB RuntimeData、委派和模型预算限制继续生效。I/O 配置为 1 毫秒至 5 秒。回调须遵守超时，调用次数由宿主有限编排。

Status 和事实转交检查持久检查点及每个保留报告修订的当前披露策略，旧版本不会因新版本覆盖而漏检。迟到报告转交成功后仍保留原队列，重复交付按原身份去重；容量耗尽拒绝新接纳并保留旧义务。`DrainAborted` 可在安全取消后核对冻结期间已收事实。历史/队列未实现自动压缩；达到上限需可证明完成义务的后续管理流程，不能随意删除未结算记录。

## 验证

入口：`sh scripts/verify-handoff.sh`；原始输出在 `build/handoff`，持久结果见 [验证报告](evidence/29-handoff-report.json) 和 [双轴审查](29-handoff-review.md)。脚本固定 Go 1.26.1 / protoc 36.1，检查依赖、生成一致性、构建、静态检查、竞态移交测试、受影响回归，并将 answer profile 与票前提交的失败集合比较。比较通过不表示 answer profile 通过。

真实证据包括独立 SQLite、五个持久窗口各两次真实子进程退出 80、本机 mTLS WebSocket、实际执行入口和独立动作目标计数。提交前失败、提交后未知由存储包装器注入，属于模拟事务故障；重复投递模拟回包丢失后的恢复，不冒称真实公网丢包。执行目标为确定性任务夹具，时钟、业务内容和策略条件受控；没有真实模型供应商、生产外部工具、宿主时钟修改或自动故障接管实验。

最终专项竞态测试 11 个通过事件（含子测试）；受影响回归的唯一失败为 `TestGRPCBoundedConcurrentStreams` 收据超时。票前版本另跑 10 次失败 4 次（两次同样超时、两次 EOF），当前版本 10 次失败 1 次（EOF）；记录为既有不稳定，不声称全部回归通过或两种症状根因完全一致。answer 当前及票前均保留相同 46 个失败身份。验证脚本如遇这些失败仍非零退出，报告不覆盖原始失败状态。
