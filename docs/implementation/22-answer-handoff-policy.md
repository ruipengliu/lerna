# 22 票答案交接不得恢复来源权限

原22票要求原材料及个性化来源的用途、位置、期限和披露限制在生成及交付时继续生效。代码审计发现 publishResearchAnswer 在创建答案上下文后调用 Policy.Replace，重新授予所有参考网页与内联任务目标的权限，并刷新期限。这会覆盖行动结束后发生的撤权或策略收紧。

反例通过真实 Core、SDK、HTTP 获取与 SQLite 行动链路到达答案交接点，再撤销来源策略。旧代码改变了策略 Revision，测试失败（0.720s）。修复后，公开参考宿主仅在初始化策略时配置内联 task-goal；答案交接不再写策略，网页规则继续沿用初始化时的期限，不因进入答案阶段延长。

测试核对策略版本保持、模型调用数为零、任务未完成且没有结果。交接撤权、单页查询计量、本地协议模型调用边界撤权与证据答案发布/恢复的 race 组合通过（14.216s），vet/diff通过。没有读取.env、调用外部模型或修改预算。

这解决同一运行内答案交接的越权重置。参考宿主的存储重开仍重新安装固定公开规则；生产级动态策略持久化与恢复配置仍待实现，不能把本修复扩展为跨进程策略持久化已完成。多来源64条预算失败及原22票其他条件仍保留。

普通可回答/不足/获取失败及对应答案存储重开的正向race组合通过（18.100s），表明初始化策略仍支持原公开路径。Standards与Spec独立增量静态审查均无actionable findings；两轴未另跑测试，不替代最终整票审查。

后续已接入当前来源规则的SQLite持久化：参考宿主恢复不再安装默认规则，缺失或损坏策略明确拒绝。跨实例、重开撤权及版本保持证据见 `22-source-policy-recovery.md`。上述固定重装限制属于修复前检查点；通用生产配置迁移和策略历史审计仍未覆盖。

继续审计发现：页面上下文检查不能替代原任务目标权限检查。仅撤销 task-goal 规则、保留网页规则时，旧答案接线仍调用模型（calls=1，反例0.812s）。新增 researchAnswerInput，将原 ContentAccess.Validate 与页面上下文组合，并同时接入模型和发布端口。原目标及 InputRefs 在组装、模型调用边界及发布前继续验证，必要的原输入 GET 沿原任务计量。

goal_revoked_only 的独立 race 回归通过（2.612s），核对模型零调用、策略版本不变且没有发布结果。原单失败路径必要观察下界从53增加到57，原64上限保持；随后该单例连续5次race通过（19.541s）。Standards与Spec增量静态审查均无新增可操作发现，未替代完整22票审查。首次搜索的独立间歇故障与期限修复见 `22-retention-scope-recovery.md`。

后续核对发布端口发现重复：Port.Commit 本来已经通过 ContentAccess.Validate 检查当前 Core 快照中的原目标和输入，传入 controlledInput 会在同一边界再 GET 一次原输入。模型仍使用 controlledInput；发布端口改为接收页面 input，保留“端口检查原输入 → 页面检查 → 原输出 LOOKUP → Core 提交”的顺序，恢复最终也进入同一端口。

真实固定回放反例先失败（1.888s，总查询56/Content48/Outcome2），去除重复后为55/47/2；没有HTTP定时观察造成的计数波动。HTTP单失败路径必要下界相应为56、Content48，原64上限不变。新计量用例、目标撤权、原账本计量及证据答案实际进程恢复的race组合通过（22.254s）。Standards和Spec增量静态审查均无新增可操作发现。这个单次节省不能证明多来源预算或整票验收已通过。
