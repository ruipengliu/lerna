# 22 票搜索披露检查的查询计量增量

本增量继续原 22 票查询计量范围；不改变原 64 条查询、模型、网络上限，也不代表完整计量或整票验收完成。

searchprivacy 在网络处理/披露位置重新读取原执行输入，再与 Call.Input 比较；这种真实 Content 数据读取不能归为 Core 控制核对。WithQueries 为可信宿主提供绑定视图，Check 以原 execution.Request 的完整 ActionBinding 调用 ChargeExecutionQuery，不加载最新 Worker 或建立新额度。每次 GET/READ 在 I/O 前计费；底层权限、用途、实际处理位置和完整性检查保持。

长度表仍只共享有界长度，每次 READ 都实际进行。未配置任务查询端口的基础 profile 保留原行为；研究 bindSearchActionHost 在端口非空时必须接入。此变更不覆盖获取/搜索驱动 Acquirer.Recover 的 Outcome 和证据读取，也不放宽取消后的内容访问权限。

## 真实路径证据

在真实 Core、Content、SQLite、SDK 和获取驱动外增加委托仪表：接纳后的 Start 先进行两次真实 searchprivacy.Check，再调用原驱动；没有替换业务结果。反例先得到 4 次原执行观察而非预期 7 次，运行失败（1.159s）。接入后，原 4 次执行观察与隐私首次 GET/READ、第二次 READ 共 7 次，运行通过（0.972s）。行动结算后旧请求不得访问 Content 或消耗当前工作资格的额度，另以实际 Content 调用仪表断言。

该用例、原搜索处理位置检查以及真实搜索进程恢复的 race 组合通过（9.536s）。研究冻结组合已启动，结果待记录；不能沿用接入前的绿色冻结报告声称当前完整路径通过。

此前完整相关 race 会话 30063 在本增量之前编译；它只覆盖此前批次。当前增量尚待独立双轴审查与最终相关验证，尚未提交。


## 研究组合的实际结果

接入后的冻结组合失败（31.176s）：HTTP/回放冲突、两种部分失败及冲突答案重开再次触及 64/64，不能沿用之前的通过结论。单页失败实际为 Outcome 2、总查询 52，新增六条 Content 观察。旧精确计数 46 已不适用；网络等待的 WatchGuard 还可能产生额外实际读取，计量用例改为检查最少 52、总上限 64、Content 与总数的八条差额及两条 Outcome，不能把耗时轮询写成固定计数。独立 SDK 用例仍精确断言两次隐私检查的三条观察。

当前研究边界已接入但原预算内组合尚未通过，获取驱动内部读取仍未计量。后续需要继续审计重复观察及恢复调用路径；不得增加原上限、把业务读取藏入控制核对或关闭披露检查来获得绿色结果。

Standards 与 Spec 独立增量静态审查均无 actionable findings；两者未另跑测试，且明确保留组合预算失败及未计量驱动入口，不替代最终整票审查。


## 被拒绝的实际读取不退款

真实 SDK 委托用例增加输入不一致分支：隐私 Guard 先读取原受控输入，再因 Call.Input 不同而拒绝；之后仍以原合法调用进行两次复查并执行真实获取。原执行四次观察、被拒绝检查的 GET/READ 与两次成功 READ 共八次，均保留在原 Core 账本。正常分支仍为七次；旧资格拒绝发生在 Content I/O 前。两个分支 race 通过（3.869s）。这项补充未改变生产逻辑，也不改变前述冻结组合预算失败。
