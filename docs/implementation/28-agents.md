# 28：内部 Agent 子任务委派

父任务通过有限 Brain 提案委派子任务，在自己的 RunStore 原子保存预算预留和待发意图；接收方使用自己的任务权威接纳。父端核对来源、Schema、效果、用量及目标证据后才结束责任关系。没有跨存储原子事务，也不以传输回执或子任务的 COMPLETED 标签替代父目标核验。

## 接入

`brain.NewDelegations` 选择 `harness_delegation_v1`，复用既有生成预留、当前上下文校验、受控输出保存和用量结算。只允许上下文中 `internal-agent` 候选；模型不能指定操作身份。宿主读取保存的有限提案，经 `PrepareDelegation` 分配操作身份，再调用 `WorkPort.Delegations(...).Admit`。恢复已准入提案时读取 RunSnapshot，不重新生成或替换原操作。

`DelegationPort` 必须绑定当前输入/结果处理与保存策略。`ChildPort` 必须绑定当前子授权策略、受信证据观察器及本地控制操作发行器。检查区分 accept、execute、delegate、disclose；工作领取、续租、模型请求、后代委派及实际工具启动均检查子权限。`execution.Core.CheckExecution` 是实际启动必经门禁，不依赖可选 StartGuard。普通任务不增加子权限 I/O，普通远程能力调用仍可直接运行。

授权与运行预算分别核算。`ChildGrant` 是受信宿主接口，须用持久保存的原始 `GrantAuthority.Mutate(DERIVE)` 请求幂等取得收缩授权，不得每次核对重新签发新额度。已有授权权威负责收缩、接收方、位置、期限和额度检查。参考 `SignedChildPolicy` 使用绑定完整委派摘要的 single 叶子授权；叶子明确禁止继续委派。需要更深协作的宿主必须绑定允许后代且检查原授权深度的策略；运行时同时检查祖先、深度和子预算，不会因配置较大而扩权。

双方协商 `task.delegation.v1`，宿主用 `ChildPort.BindPeer` 将逻辑任务拥有者映射到精确认证节点，并安装 `Binding.Children`。accept 传完整意图；lookup、report、cancel 只传 `ChildReference`，包含父任务、拥有者、epoch、原操作、目标 Agent 及摘要，不重传目标正文、输入、Schema 或授权材料。已有 WebSocket 负责 mTLS、当前披露、队列、分块、消息关联和 I/O 限制。这里依靠父意图与子接纳账本恢复，不把可靠消息回执当作跨任务提交证明。

## 状态、预算与控制

每个父任务支持一个最多 16 项的有限批次，可表达并行分支和本批次内的成功依赖。可见环、缺失依赖、超深祖先、超额预算及超期输入被拒绝。待发、已发送、活动、冲突、验收通过、失败、停止及明确未发送分别持久保留。调度轮转避免一个未知分支饿死独立分支；必需失败只阻断依赖它成功的工作，不能改写为可选。

子身份由来源拥有者和原操作确定；改变父任务、epoch、目标或预算属于原操作语义冲突，不能创建第二个子任务。发送前持久记录尝试。回包丢失后先按原关联查询，至多三次接纳尝试。取消未知接纳时，子端原子保存拒绝迟到接纳的关闭记录，或控制已存在的子任务。

用量未知或关键效果未知保留 CONFLICT、额度和并发占用。只有确认终止且用量已知，才结算已消耗部分并释放其余预留；明确未发送的分支可释放运行预留。正常核对与取消处置各有独立持久计数，正常额度耗尽不会耗掉取消资源；处置额度也耗尽时保持 WAITING，不伪造停止。

子报告有独立持久修订及原任务版本，保留来源、可见证据、覆盖、未解决事项、效果和消耗。同修订异内容、错关联、旧修订不能覆盖当前事实；新观察保留旧报告历史。处理前和提交前检查当前策略。父端用受信独立核验器作判断，不按多数或最后返回者裁决。

`PublishResults` 先检查全部历史报告的当前策略，再让保存回调接收任务和报告集合，不暴露原始委派授权材料。通过既有 SubmitUpdate 追加带提交主体与报告来源的事实，保留原操作和版本去重。输入追加沿用原有失效规则，宿主确认旧决策已返回后重新领取、核验父目标。`Approve` 保存独立目标证据；`Complete` 发布已治理的报告引用。目标或输入在批准后改变会使旧批准失效。所有终态路径共享所辖子任务处置门槛，父取消也必须等自身工作及子任务实际处置。

## 上限和已验证组合

构造边界：批次 1–16，深度 1–8，并发 1–4 且不大于批次；正常/处置检查各 1–64；单次 I/O 1 毫秒–5 秒。每子最多三次提交尝试。输入及结果各 16 KiB，输入/结果 Schema 各 8 KiB，证据、来源、覆盖及单项未知说明各 1 KiB，未知说明最多 16 项；WS 请求/响应另限 64 KiB。任务总表、操作表、模型预算及 8 MiB RuntimeData 上限继续生效。参考测试主要使用 4 子、深度 3、并发 2、16 或 32 次检查和 1 秒 I/O。

验证覆盖完整三子图（两并行、一依赖）的 Brain→Core→接纳→核验→SubmitUpdate→父完成；并发预算、必需失败隔离、策略拒绝、取消未知效果、独立取消额度、超限和环；父预留与子接纳分别真实进程退出 79；真实 mTLS 客户端接纳后退出 78、重启后关联同一子任务和同一派生额度；授权撤销后已接纳工具不得启动。SQLite、真实进程和真实本机网络实际运行；时间/业务数据/模型为可控合成夹具，没有调用真实模型供应商或修改宿主系统时钟。

执行入口：`sh scripts/verify-agents.sh`。原始结果在 `build/agents`，持久记录见 [验证报告](evidence/28-agents-report.json) 和 [审查记录](28-agents-review.md)。脚本单独比较 answer profile 在本票与冻结前提交的已知失败集合，比较通过不表示该 profile 通过。报告逐项列出成功、失败和基线复验，不将未执行的完整多 Agent 质量评测、其他平台、任意外部 Agent 协议、长期后台守护或真实模型质量写成通过。
