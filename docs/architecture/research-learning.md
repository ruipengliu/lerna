# Agent 能力与评估研究依据

本文面向 Lerna 架构设计者与能力组件开发者，回答一个问题：近期 Agent 研究中，哪些机制值得形成稳定接口，哪些仍应作为可替换策略，通过实验选择？

**设计建议是：稳定任务控制、证据、预算和权限语义；让上下文构造、记忆组织、规划与协作策略独立演进。** 长上下文、递归推理、多 Agent 和自动积累经验都有适用条件，不能直接写成所有任务的默认路径。

调研截止日期为 **2026-10-03**。本文选择八项一手研究，核对论文版本、提交日期、研究范围及作者提供的实现入口。本文是设计依据，不是接口规范；标为“设计推断”的内容是 Lerna 的选择，不能视为论文已经验证的结论。本次未复现论文实验，也未验证任何实现已经满足 Lerna 的可靠性或安全要求。

## 2. 记忆应保存证据，并支持多种上下文构造策略

### R1：把环境经验纳入记忆评估

**研究事实。** LongMemEval-V2 从历史操作轨迹中评估静态状态、动态变化、工作流程、环境陷阱和问题前提。它比较检索式记忆与通过代码工具收集证据的方式，后者在所测任务中表现更好，也带来更高延迟。研究对象是定制 Web 环境中的经验问答。[论文方法与实验](https://arxiv.org/html/2605.12493v1)

**适用限制。** 找到回答问题所需的历史证据，不等于能够正确执行下一次操作；问答结果也不能证明跨租户隔离、遗忘和恢复语义正确。

**设计推断。** Memory 建议区分原始观察、带时间的事实与经过验证的操作经验，并保留来源关联。ContextCompiler（上下文构造器）根据当前任务生成有界的证据包，供决策引擎使用。它可以先检索摘要，再回读原始材料；某种知识图谱或向量库不应成为框架唯一允许的内部表示。

**验证方式。** 用同一历史材料分别测试事实更新、过期流程、错误问题前提和证据缺失。除最终答案外，检查检索结果是否包含正确时间和可追踪来源。

### R2：长上下文与提取式记忆需要按使用模式比较

**研究事实。** 该研究在三个记忆基准中比较基于 Mem0 的事实提取方案与长上下文模型。长上下文在部分事实回忆任务中更好；提取式记忆的前期写入成本与后续查询成本结构不同。论文还将提示缓存纳入成本分析。[论文](https://arxiv.org/abs/2603.04814v1)

**适用限制。** 结果依赖所选模型、提取方案、历史长度、查询次数和价格。论文中的成本拐点不能直接用作 Lerna 的路由阈值。

**设计推断。** 短历史可直接组装上下文；长历史或反复访问的材料可使用检索与分层压缩。Memory 建议保留在访问与保留策略允许范围内的原始证据，使摘要损失能够被发现和补救。是否抽取、何时整理、如何检索应当分别可配置。

**验证方式。** 在相同模型与数据上比较全文、混合检索、事实提取三组，报告首次写入和多轮查询的累计成本、遗漏率、时效性与延迟。

### R3：支持按需读取材料，递归只是其中一种策略

**研究事实。** RLM 将长输入放入外部环境，由模型通过程序检查、分解材料，并可对子片段递归调用模型。论文考察长上下文任务；[作者实现](https://github.com/alexzhang13/rlm)提供可扩展推理引擎与不同执行环境。[论文](https://arxiv.org/abs/2512.24601v3)

**适用限制。** 长材料处理能力不等于任务恢复能力。作者仓库的默认 REPL 可以在宿主进程执行代码，不能把“提供 REPL”视为“已经形成安全隔离”。仓库说明另有隔离执行环境。[实现说明](https://github.com/alexzhang13/rlm#repl-environments)

**设计推断。** 框架建议用可授权的材料引用传递大文件，提供查询和分段读取能力。编程读取、递归调用和多候选推理作为可选策略，由 Executor 的隔离环境执行。子调用计入根任务预算，并受深度、并发、时间和材料访问范围约束。

**验证方式。** 在相同预算下比较检索、全文输入和程序化读取；另行注入超时、恶意材料、递归不终止与沙箱退出，检查预算和权限是否仍由运行框架强制执行。

## 3. 经验、规划与协作应当可选择、可撤回

### R4：积累经验时保留结构化增量与版本

**研究事实。** ACE 将上下文组织为持续演进的操作经验集合，通过生成、反思、整理三个环节进行增量更新，减少反复全文改写造成的信息丢失。论文包含离线与在线上下文适应；作者提供[实现仓库](https://github.com/ace-agent/ace)。[论文](https://arxiv.org/abs/2510.04618v3)

**适用限制。** 运行反馈不天然等于正确标签。该机制不能证明经验在新环境中仍有效，也不能替代权限、代码发布或插件供应链管理。

**设计推断。** Lerna 建议将经验写入分为候选、验证和发布。每条经验记录来源、适用环境、验证结果和版本；任务固定所用版本，后续更正可追踪。经验更新不得修改框架授权规则，也不得自动发布可执行插件。自动整理可以异步执行，但是否启用新经验应由明确策略控制。

**验证方式。** 对比无经验、直接自我反思写入、经验证后发布三组，专门测量错误经验传播、环境变化后的失效和回滚效果。

### R5：让决策引擎感知预算，让框架执行预算

**研究事实。** BATS 向 Agent 持续提供剩余工具预算，并据此调整探索、规划和验证；成本比较同时统计模型与工具消耗。主体实验集中于搜索任务，论文将多维资源约束和更准确的资源分配列为局限与后续方向。作者提供[实现仓库](https://github.com/google-research/budget-aware-agent)。[论文方法与局限](https://arxiv.org/html/2511.17006v2)

**适用限制。** 预算提示能帮助策略选择，却不是资金或调用次数的硬约束。检索问答中的继续探索，也不能直接推广为有外部副作用的再次执行。

**设计推断。** 每次决策输入建议携带剩余预算与截止时间。预算服务负责调用前预留、执行后结算；决策引擎只能提出资源使用建议。完成核验需要保留资源；资源不足时返回部分结果或等待决策，不能将“预算用尽”转换为“任务成功”。

**验证方式。** 在相同硬预算下比较固定步数、仅预算提示、预算提示加验证策略，观察有效结果、重复检索、核验完成率及实际支出。

### R6：多 Agent 是任务策略，不是默认部署方式

**研究事实。** 该研究控制工具、提示和计算条件，对单 Agent 与独立、集中、分散、混合协作进行比较。结果随任务结构变化：可分解任务可能受益，强顺序依赖任务可能因协调和错误传播受损。本文采用 v3；早期版本的实验规模与摘要数字不同。[论文](https://arxiv.org/abs/2512.08296v3)

**适用限制。** 研究中的拓扑偏好不构成普遍阈值；运行于不同进程的框架组件，也不等于多个独立推理 Agent。

**设计推断。** 默认建议由一个任务控制者组织决策。只有子问题能独立验收、证据可合并且预算允许时，才分派并行子任务。子任务返回结果、证据和不确定性，由父任务核验；共享可变资源的行动不能依靠自然语言协商解决冲突。

**验证方式。** 按“资料可独立搜集”“必须顺序操作”“共同修改同一资源”分组，比较单 Agent、并行研究加集中核验两种模式，统计结果质量、总成本、协调延迟及冲突。

## 4. 评估对象应是完整运行系统

### R7：固定并记录模型与框架组合

**研究事实。** 该论文通过方差分解分析多个 Agent 榜单，区分“固定模型与框架组合的排名”与“底层模型排名”。研究指出，增加相似任务不一定能消除框架覆盖不足导致的不确定性。作者也说明，排名稳定不代表评估目标本身有效。[论文与局限](https://arxiv.org/html/2610.00651v1)

**适用限制。** 这是截止日期附近发表的预印本；结论依赖所采样的榜单、模型和框架范围，本文将其用于实验设计，不把拟合结果作为生产质量保证。

**设计推断。** 每次评估建议固定模型版本、策略版本、插件版本、工具环境、数据快照、预算和评分器。报告整体完成率之外，还要报告证据正确性、错误外部效果、恢复结果、成本与延迟。框架正确性、模型质量和业务效果分别判定。

**验证方式。** 对同一任务做配对重复运行；替换模型和策略时一次只改变目标变量。报告样本数量、离散程度、失败类型及适用场景，避免只展示最好的一次结果。

### R8：同时检查任务效用与攻击结果

**研究事实。** AgentDojo 提供可扩展环境，在工具返回的不可信数据中加入攻击内容，并评估正常任务与攻击目标。它支持扩展任务、攻击和防御，作者发布了[开源实现](https://github.com/ethz-spylab/agentdojo)。[论文](https://arxiv.org/abs/2406.13352v3)

**适用限制。** 通过有限攻击集不能证明不存在提示注入；一味拒绝工具使用也可能降低攻击成功率，却使正常任务无法完成。本文保留该较早工作作为可扩展测试方法，而不把它称为最新防御方案。

**设计推断。** 外部材料与授权指令需要不同的来源标记。读取材料不得扩大权限；执行入口独立检查实际目标资源与授权范围。生成代码使用受限执行环境。测试同时度量正常任务成功率、错误阻断率与未经授权的实际效果。

**验证方式。** 将恶意指令放入网页、文件、工具回执和历史记忆，覆盖跨用户读取、外发数据、权限提升与重复副作用；检查行动记录和外部状态，不能仅检查模型是否口头拒绝。

## 5. 对架构接口的建议

以下是综合研究后的设计推断，具体字段与强制约束由本目录的架构契约定义。

| 需要稳定的边界 | 建议保留的语义 | 不宜提前固定的实现 |
| --- | --- | --- |
| Memory 与上下文构造 | 来源、时间、访问范围、版本、删除与失效传播；能回读获准访问的原始证据 | 单一向量数据库、知识图谱或摘要算法 |
| 决策引擎与任务控制 | 有界输入、预算快照、结构化提案、提案依据与使用的版本 | 某一种提示模板、推理链或搜索树 |
| 父任务与子任务 | 子目标、验收条件、材料范围、预算、取消关系和返回证据 | 固定 Agent 数量或所有任务使用相同拓扑 |
| Executor 与外部环境 | 明确效果、隔离范围、实际用量、结果不确定时的查询途径 | 把任意超时处理成可安全重试 |
| 经验更新与发布 | 候选来源、验证结果、适用范围、版本和撤回 | 从一次模型自评直接更新全局策略 |
| 评估与发布 | 可重现配置、配对对照、正确性检查、质量及成本结果 | 单一模型评分或公开榜单名次 |

## 6. 优先实施的对照实验

实验先使用可重置环境与无外部副作用的任务。涉及写操作的故障与攻击测试使用隔离的模拟服务。下表是实验计划，本次文档工作未执行这些实验。

| 实验 | 保持不变的条件 | 比较变量 | 用于作出什么决定 |
| --- | --- | --- | --- |
| 研究报告上下文 | 相同模型、资料快照、问题与总预算 | 全文、混合检索、程序化读取 | 默认上下文策略及切换条件 |
| 长期经验 | 相同历史轨迹与后续任务 | 无经验、直接写入、验证后发布 | 经验发布是否值得增加成本 |
| 规划预算 | 相同工具及硬预算 | 固定步数、预算感知、预算感知加核验 | 如何分配探索与核验资源 |
| 协作模式 | 相同问题、模型与总资源上限 | 单 Agent、并行分工加集中核验 | 哪类任务可以默认并行 |
| 完成判断 | 相同候选结果与真实环境状态 | 模型自评、规则核验、规则加独立评估 | 错误完成与过度拒绝的边界 |
| 故障与攻击 | 相同业务目标和授权 | 注入位置、故障时机、组件实现 | 可靠性约束能否跨策略成立 |

建议先跑小样本找出流程错误，再确定场景分层、重复次数与所需统计精度。验收阈值由目标应用的成本和错误容忍度确定，必须在查看最终测试集结果前锁定。调参数据与验收数据分离；无法重复或无法核验的结果单独报告。

采用新策略的依据应当是：在指定场景与资源范围内，改善可核验的任务结果，并继续满足权限、预算、恢复和效果约束。论文和开源实现为这个判断提供候选机制，Lerna 的真实实验负责验证是否采用。
