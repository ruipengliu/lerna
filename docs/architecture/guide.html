Harness 架构讲解

Harness 接纳用户目标，组织模型和工具持续推进任务，并根据证据决定是否完成。它把三个职责分开：Brain 提出下一步，Orchestrator 决定是否准入及是否完成，Executor 执行并记录实际效果。 进程中断后，接替者从原记录继续；如果效果仍未知，系统保留核对责任，不能直接再做一次。

本文面向参与实现和评审的开发者。读者需要了解数据库事务、API 和基本权限控制。本文帮助你沿一项任务确认各模块的职责、每次交接保存的记录、失败后的恢复入口，并找到准确的实现合同。

全文采用同一个例子：比较两个软件版本，取得来源，生成报告，保存到设备指定目录，再读回核验。 先看完整架构，再看正常流程、异常恢复、数据和部署。字段、状态机和接口细则直接链接各模块规范，本文不另建一套合同。

设计状态：本文解释现行目标设计。内核、SDK、跨可用区恢复及模型质量仍必须按开发准备度和验收合同逐项验证。本文的图示不是运行证据；真实开发者试读也尚未开展。

约束用语：“必须／不得”表示强制要求；“建议／不建议”表示默认选择，偏离时需说明影响；“可选”表示可以不提供，但提供后必须遵守相应合同。本文不采用 RFC 英文大写关键词的正式语义。

1 项目目标与首阶段范围

首阶段要让公司内部的个人智能应用团队接入一个可独立运行的框架。应用可以提交目标、补充要求、查看进展、暂停或取消任务，并取得有依据的结果。项目同时保留面向外部开发者的开源交付要求。

研究报告任务用于验证这一条完整流程：系统取得实际来源，生成满足要求的报告，保存文件，再独立读回并核验。模型生成了流畅文字、工具返回成功、界面显示完成，分别只说明其中一部分事实。

首阶段交付 后续阶段按需开放
可运行内核、必要默认组件与 SDK、示例界面、真实应用接入 跨任务个性化、复杂多 Agent 协作、完整离线任务、手机 GUI、受控自进化
上下文与进展持久化、授权、费用记录、效果核对、故障恢复 各能力所需的新增授权、资源管理、评测和发布机制

项目首先验证任务执行的可靠性：长任务能否持续推进，进程中断后能否恢复，效果未知时是否会重复执行。规划、长期记忆和多 Agent 的收益需要另外做对照实验；接入体验需要真实应用接入来验证。

范围限制：缩小首阶段功能范围，不减少授权、恢复和效果证据要求。第一次生产上线仍必须满足已定的分布式部署条件。首阶段与最终覆盖目标分别验收，完整范围见项目目标。

2 模块职责与完整架构

任务（Task）表示一个用户目标及其推进责任。任务从应用进入，由 Orchestrator 承担目标责任。Brain 只能提出建议；Orchestrator 结合当前目标、权限和预算决定是否准入；Executor 还必须在实际执行入口检查一次，再访问目标。只有 Orchestrator 可以裁决 Task 完成。

图中的框表示逻辑职责。一个框不要求对应一个微服务，一条连线也不指定 RPC 或数据库事务。第六章再说明这些职责运行在哪些进程中。

模块或职责 在报告任务中负责什么 必须保留的边界
Interaction 应用交互 保存原输入，组织对话，呈现进展、输入请求与结果 关闭窗口不取消任务；界面展示不等于本人确认
Orchestrator 任务编排器 保存目标与条件，固定决策输入，准入行动，处理控制，裁决完成 不得把模型提案或执行回执直接当作完成证明
Brain 大脑 选择本轮所需材料，提出条件候选、行动或完成建议 不得改权威目标、扩大权限或自行重发结果未知的模型调用
Executor 执行器 接纳已准入意图，检查实际入口，保存尝试、效果、证据和用量 接纳请求不等于产生效果；取消回执不证明外部动作已停
Content 内容管理 保存准确版本的字节、来源及副本责任 材料进入上下文，不自动获得长期保存许可
Memory 长期记忆 管理获准跨任务保存与复用的记忆 保存、检索和再次使用必须遵守各自许可与保留规则
授权与业务确认 Grant 表示受范围、期限和额度约束的授权许可；业务负责方保存并消费本人对准确请求的可信确认（Confirmation） 插件声明、普通回答和模型同意不得扩大权限
持久工作与结算 各负责方保存未结工作及真实费用 调度器不裁决领域成功；任务终态不删除费用核对责任
扩展与评测 管理准确版本、评测依据及发布资格 评测分数不替代权限、效果核验或发布批准

负责方与工作进程不同。 负责方（owner）是有权维护某类事实的逻辑主体；工作进程（worker）只是临时领取工作的一次进程实例。一个 Task 始终归同一个 Orchestrator，但可以由不同应用副本和 worker 服务。进程退出不转移目标、预算或完成裁决权。

为什么这样划分：Brain、Executor 和 Memory 可以分别替换。替换 Brain 改变提出建议的方法，替换 Executor 改变访问目标的方法，替换 Memory 改变记忆组织与检索的方法。替换后的实现仍必须遵守同一套身份、权限、效果和恢复合同。完整边界见系统模型和扩展合同。

3 报告任务的正常流程

报告任务依次建立五类事实：输入已保存、目标已接纳、行动已获准、效果已核实、当前目标已满足。以下流程分别说明谁保存这些事实，以及交接失败后从哪里继续。

3.1 保存输入与接纳目标

应用保存输入和 Orchestrator 接纳目标是两次提交，必须分别判断是否成功。

  1. 应用保存输入。 Interaction 保存原文与附件的准确内容引用，并记录消息（Message）、输入提交记录（Submission）、原提交命令和投递工作。Session 用于组织对话及关联任务；Task 承担具体目标。关闭 Session 不终止 Task。
  2. 应用固定原提交。 首次发送前，应用保存原 task.submit 命令及目标 Orchestrator。Command 是一次业务裁决的请求身份，重复发送仍指向同一次裁决。
  3. Orchestrator 接纳目标。 原 Orchestrator 在所属数据库事务中检查是否重复，共同保存 Task、目标版本、预算、回执和首项工作，再返回结果。

答复丢失时：应用必须凭原命令查询固定的 Orchestrator，不得按相似文本另建 Task。

设计取舍：固定路由避免每次提交再增加一项跨分片写入，但调用方必须持久保存未决提交。本地记录完全丢失、受信目录也无法定位时，不保证自动找回；调用方也不得任意改投另一负责方。依据见固定 Task 路由 ADR。

3.2 把要求变成可核验条件

Orchestrator 必须把完整目标对应到具体条件，并确认这些条件覆盖原目标，才开放依赖它们的普通目标行动。

任务条件（Requirement）用于判断目标是否满足。本例中的条件包括：报告覆盖指定比较维度，重要事实有实际取得的来源支持，文件保存在准确位置，且独立读回一致。判断规则与允许使用的证据由合同和任务策略固定，模型不得为便于完成而删除硬要求。

版本范围或来源要求不明确时，系统先保留完整原目标，通过已登记模板或 Brain 提出候选，再用原输入请求向用户澄清。必要歧义未解决时，依赖它的目标动作不得开始。

候选条件由 Orchestrator 校验并接纳。条件实质变化时，它在一个短事务中保存新条件版本和目标版本，并使同一提案中的行动与完成建议失效。下一轮决策必须使用新快照。相同条件不产生额外修订。

设计取舍：先接纳条件可以避免沿旧条件执行行动；发生实际条件变化时，代价是增加一轮决策的费用与延迟。条件列表非空仍不证明覆盖完整，系统还必须检查原目标与条件的对应关系。规则和理由见条件提炼和条件优先 ADR。

3.3 取得来源并生成报告

Orchestrator 为一次判断固定身份和输入，再让 Brain 提出下一步。Snapshot 是本轮目标、控制、条件、已知事实、未结效果和获准材料的准确快照；Decision 是基于该快照的一次判断。提案返回后，Orchestrator 还必须检查它是否符合当前事实，不能只看生成时的快照。

搜索和正文获取属于执行能力，每项读取都必须经过行动准入。搜索摘要只能帮助选择来源，不能冒充已经取得全文。读取结果必须说明实际取得的内容、来源、观察或获取时间、覆盖范围和缺口。

后续决策通过 Content 引用准确版本的正文、截图等材料。Content 不是任意填写的 URL；权限、用途和外发限制仍适用于这份内容。

Brain 生成报告时保存原提案与用量，并在必要内容可查询后完成该 Decision。模型调用同样受输入用途、外发权限、费用和输出发布规则约束。

调用未知时：每个 Decision 至多一次物理模型请求。发送阶段已经保存后，Brain 不得透明重试。供应商无法查询原调用时，系统保留结果未知和费用占用；是否建立后续 Decision，由固定任务策略 TaskPolicy 决定。

设计取舍：这一限制明确了调用与费用的恢复身份，也可能使部分判断无法自动取得结果。它不是由统一授权必然推导出的唯一方案，本文也没有验证它能降低净成本。具体规则见Brain 的模型调用合同。

3.4 准入行动与实际执行

假设报告已经生成，下一步是保存文件。这个行动先经过云端准入，再经过设备实际入口检查；两次检查负责不同的边界。

云端准入。 Orchestrator 固定最终路径、内容版本、能力及具体实现绑定。它在准入事务中核对当前目标、控制、授权、预算和资源冲突。通过后共同保存不可变行动意图 OperationIntent、原执行命令、预算预留、完整操作关联和派发 Job。

Job 是负责方尚需履行的持久工作。它与业务记录共同提交，因此派发进程退出后，接替者仍能找到待办事项。

Executor 接纳。 Operation 表示一次有界行动及其持续核对责任。Orchestrator 保存“准许做什么”的意图，Executor 保存“实际做了什么”的事实。双方通过原操作身份关联，各自在所属数据库提交。Executor 接纳 execution.invoke 时保存 Operation 和执行工作，再返回命令回执。

跨负责方使用授权时，若需取得有限授权使用凭据 UseReceipt，派发方必须先取得适用凭据再发送。凭据保存在派发记录中，不回写不可变意图。部分授权已经消费而后续交接失败时，不得擅自恢复一次性许可。

实际入口检查。 执行宿主先保存原 Attempt 和必要的在途核对责任。Attempt 表示一次物理尝试，网络重传和 Job 重领本身不产生新的 Attempt。宿主随后通过受信入口 StartBarrier 检查任务控制门禁 TaskGate、许可窗口、资源代次、版本资格和期限，满足条件后才访问目标。

TaskGate 保存原 Orchestrator 的控制事实，只约束本机启动，不授予设备修改目标的权力。网络请求和文件写入都在数据库事务之外；数据库回滚无法撤销已经交给目标的动作。

两个 applied 的含义不同：命令回执的 applied 表示接纳决定已提交；Operation.effect=applied 表示声明效果已有目标证据。接纳成功不能证明文件已写入。

实现细则见统一行动准入与真实执行入口。

3.5 保存核验与完成裁决

文件写入成功只证明原声明效果发生。文件随后可能被用户修改，所以本报告场景还需要独立的读回 Operation，取得准确路径、版本或摘要以及观察时点。写驱动自己的缓存不能冒充独立读回。

报告的来源支撑、内容要求和保存结果分别形成当前条件的核验依据。完成一次评估不等于条件通过；条件通过也必须绑定当前目标和准确成果。

对于普通开放质量，系统可以按已定的 assessed 路径使用评估结果，并明示其限制。这里的 assessed 表示已经按适用规则评估，不表示判断已取得专项准确性保证。准确范围见证据分级 ADR。

Orchestrator 在原 Task 数据库中裁决完成，必须核验：

  1. 条件覆盖完整原目标，所有必要条件均已满足，证据适用于当前目标与准确成果。
  2. 完整的未结效果和子任务集合符合完成要求，不能仅凭客户端一页列表推断“没有剩余工作”。
  3. 全部已准入目标操作均已封闭新的目标尝试，没有未知或可能迟到的效果。

这些检查通过后，Orchestrator 在完成事务中共同固定 Result、Task 成功状态和后续交付责任。Result 是本次任务固定的正式结果。准确门禁见完成事务。

Result 先成为固定的业务事实，内容导出、应用接收与用户看到结果随后分别发生。导出失败沿原 Result 继续，不重做整项报告。Task 终态也不删除迟到账单、预留核对和清理责任。

观察到的成功点 能确认什么 还不能确认什么
原命令回执 applied 该方法的决定已持久提交 文件已写入或所有目标已满足
Operation.effect=applied 声明效果已有目标证据 当前文件仍是该版本，或没有其他迟到效果
独立读回与条件判断通过 相应观察和条件具有准确依据 其他必要条件及完整收尾集合均已满足
Task 成功与固定 Result 当前目标通过完整完成门禁 用户已经收到，或后续账单不会更正
答复确认（ReplyAck）或应用持久接收 对应答复或交付被耐久收到 用户已经阅读、理解或认可内容

上述交接的逐阶段记录见端到端时序。

4 目标变化与异常恢复

以下分支分别从同一报告任务的不同位置发生，不把所有故障拼成一条执行。恢复先定位原责任与当前事实，再决定继续、等待或停止新工作。

4.1 用户补充要求

用户可能在报告生成期间增加比较维度。应用需要分清这是修改当前目标、回答当前问题，还是提交另一个目标；三者不能都当作新消息直接交给模型。

对当前目标的有效修订由原 Orchestrator 接纳并推进目标与控制版本。旧 Snapshot 下的提案不能被重新标成当前提案，旧目标不能继续准入新行动。已经发生的效果、费用与来源关系仍保留并核对；复用旧成果也要按新条件重新确认适用性。输入与分支规则见应用交互，控制和修订规则见Orchestrator。

4.2 报告已写入但查询答复丢失

本例只需要取回原效果事实，不需要再次写入文件。 Executor 已经保存 effect=applied，云端没有收到最新查询答复；这与 Executor 自己也不知道是否写入的故障不同。

本例假设原 invoke 接纳已由双方确认，云端 PostgreSQL（简称 PG）、设备 SQLite 和原文件介质仍完整。设备写入报告并保存效果证据后，云端调用 execution.get。设备保存了待交回答复 Reply，但答复在网络中丢失，云端 worker 随后退出。

4.2.1 先定位已保存的事实

云端保存原写入意图和效果核对 Job；设备保存实际执行与答复记录；文件介质保存报告字节。三处分别承担责任，云端未收到答复不会将设备已有的 applied 改成 unknown。

⑦–⑧ · 数据库事务外 StartBarrier 核验 TaskGate、有限 UseReceipt、资源代次及期限。驱动同步临时字节、比较前版本、原子替换并同步目录。 文件介质和账本不共同原子提交；驱动还需按 journal 阶段更新原记录。中间崩溃必须核对原 journal / 临时文件身份 / 前后版本，不能只靠相同摘要猜测。
⑨ TxE3 · 设备 SQLite 归并原 Attempt 与 Operation 的效果、迟到可能（may_apply_later）、证据、准确结果和用量，保存必要的后续 Job。 applied 是历史效果。仍有其他未知尝试时，不得因此填 may_apply_later=false。
⑪ · 设备 SQLite 查询原 Operation 与分页 Attempt，持久保存匹配 delivery_id / request_digest 的 Reply。 没有 ReplyAck 时保留交回责任。连接或普通日志不是恢复依据。

4.2.2 接替者取回原答复并归并事实

  1. 领取原工作。 新 worker 从原 PG 领取效果核对 Job，取得新的领取代次。一次领取称为 Claim，绑定领取进程、代次与期限。旧 worker 恢复后，不得用过期领取更新受保护记录。
  2. 查询原操作。 新 worker 沿原 Executor 和 operation_id 取得结果。设备可以重交未确认的 Reply，云端也可以另发只读查询。查询身份可以改变，执行身份不变，因此不会新增文件写入。
  3. 确认持久收件。 云端共同持久保存 Reply 和后续处理责任，才发送匹配该答复的 ReplyAck。每份 Reply 只能由自己的确认解除交回责任；新查询的确认不得清除另一份旧答复。设备重交时仍必须核验当前披露权限。
  4. 归并事实并留下后续工作。 云端按原来源负责方、对象、修订和摘要核对事实。在领取仍有效的领域事务中，共同保存合法事实、Task 的效果关联和必要 Job。重复事实不得重复推进，旧修订不得覆盖新投影。责任已完成或已持久交接后，才结束相应 Job。

耐久收件与领域归并可以分成两个短事务。若进程在两者之间退出，接替者必须从原收件及后续责任继续；ReplyAck 不表示领域处理已经完成。领取失效的旧 worker 无权恢复自己的写入资格，但可信迟到结果可以经独立事实归并入口提交。

确认历史写入后，任务还必须独立读回报告并核验当前条件。ReplyAck 只证明对应答复被持久收到，不授权 Executor 将 Task 改成成功。

合同入口：Job 并发与条件提交、双向交回、事实归并。

4.3 目标效果本身仍未知

另一种故障发生得更早：请求可能已经交给文件系统或外部目标，Executor 却没有足够证据判断效果。此时需要按原目标请求、原 Attempt、journal 或独立观察核对。暂时查不到、超时或空读回，都不能证明没有发生，更不能证明以后不会迟到。

能力的效果类型 原操作再次发送需要的依据
只读 准确能力及真实出口确实不产生目标业务写效果，当前权限、预算与资源限制仍满足；新的读取是新的观察及可能收费尝试
目标支持幂等 目标实际识别原幂等键，其作用域和保留期覆盖恢复窗口，业务输入保持不变
没有幂等保证 已证实原效果未发生，而且不会迟到，当前授权等条件也允许有限重试

这三类条件来自能力合同。更换 operation_id、参数或执行端不构成安全恢复。不能证明时保留 unknown、迟到可能及必要的资源和预算限制；自动核对耗尽后转低频核对或明确待处置，原记录不会因此消失。

保留未知可以避免由一次失联直接产生第二次非幂等效果，代价是部分任务不能自动收束，预留和核对记录不能立即释放。这是设计取舍，不是框架已经实现任意第三方恰好一次的保证。更多依据见为何保留未知效果。

4.4 用户暂停或取消

暂停停止新的决策、评估和行动，原效果、费用、控制和清理仍继续核对；已有充分证据时，暂停状态也不必阻止符合合同的完成。取消则终结目标推进，但不能撤回已经进入外部目标的动作。

因此，界面可能需要同时显示“取消已保存”和“写入结果仍在核对”。若原写入后来被证实发生，Operation 可以补充 applied，Task 仍保持 cancelled。删除刚写出的文件属于新的有后果行动，需要新的授权、意图和效果证据，不能偷偷当作回滚。

取消先于 invoke 到达时，Executor 也要保存原 operation_id 的关闭记录，防止迟到请求重新启动。关闭身份、Task 终态和控制记录不能因清理正文而一并删除。见取消与迟到效果和最小关闭身份 ADR。

4.5 设备失联或进程退出

默认云端 Task 的权威在原 PG 分片，设备 SQLite 保存本机执行、门禁和补传记录。断网后，设备只可继续原准入及有限许可窗口允许的工作与收尾，不能根据缓存修改云端目标、准入新目标动作或裁决完成。重连沿原操作补传，云端根据当前目标核验事实。

仅 worker 退出而数据库正常时，另一个 worker 通过合法领取续接原 Job；它不创建新 Task，也不自动增加一次目标尝试。执行宿主退出还涉及真实入口、驱动队列和设备资源隔离，不能只靠云端 Job 租约判断安全。数据库或可用区失效又是另一层故障，需要部署接管条件。

端侧可以显式运行独立 Orchestrator，但只有首次提交就归它的自有 Task 才在设备上维护目标权威。它不是云端任务断网后的自动接管方式。见可选端侧部署。

5 数据归属与事务边界

前面的流程涉及许多记录，但不需要让每条记录变成一个新服务。先按“谁能改变这份事实”归类，再决定存储与进程装配。

5.1 事实归属与存储位置

先确定谁有权维护事实，再确定存储位置。 下表汇总前文对象；不同对象共用进程或数据库，并不自动取得相互写入的权限。

对象或记录组 负责维护的事实 默认存储与引用边界
Session 与输入投递 Interaction 保存消息、分支、Submission 和原投递关系 应用所属库；关联 Task 不取得其完成权威
Task 原 Orchestrator 保存目标、条件、控制、预算、当前事实投影和 Result 固定 Orchestrator 所属 PG 分片；应用与设备只在权限内展示或引用
Decision Orchestrator 固定输入及派发意图，Brain 保存判断、模型调用、提案和用量 两方各写自己的记录；采纳仍由 Orchestrator 裁决

这些是逻辑分组，不限制物理表数量。准确字段、关系和生命周期见整体数据设计；物理落位、索引与介质边界见存储与一致性。

5.2 为什么事实与工作要共同提交

如果接纳 Task 的记录已保存，而后续工作只在内存或可丢通知中，进程退出就可能使任务无人推进。反过来，若先派发工作再提交准入，未获准行动就可能进入目标。

同一负责方必须按合同声明，在同一数据库事务中提交业务变化、命令回执和必要 Job。确认提交后，才进行外部交接。

Job 保存责任的位置和当前阶段，通知只是提前唤醒已有工作。Claim 记录领取进程的启动身份、领取代次和期限；新事实还会推进工作修订。领取保证“当前谁可以受保护地写账本”，工作修订防止“旧处理结束”覆盖后来新增的责任。处理函数成功返回，并不足以把 Job 标成 done；负责方还必须确认原责任已完成或已持久交接。

设计取舍：公共模板统一接纳、领取与条件提交，各领域仍决定下一步、重试条件和完成条件。这样可以减少重复编写故障分支，但宿主需要维护存储适配和共用故障套件；数据库也要承担领取、扫描及历史记录增长的成本。

当前选择由 PG 保存工作责任，避免再引入一套工作流责任与重放规则。这是工程选择，本文没有验证它比其他工作流方案更快或更便宜。见共用工作模板 ADR和PG 责任主线的依据。

5.3 本地原子性与跨方交接

默认 Orchestrator 将 Task、条件、目标版本、预算、Result、控制，以及共同裁决的授权、确认和证据门禁装配在所属同一 PG 分片。Memory、Content、Executor 可以有独立负责方。处于同一个进程、主机或 PG 集群，不自动意味着共享一个事务。

跨负责方的交接分别提交：

  1. 发送方保存原命令、准确输入和交付责任。
  2. 接收方持久保存接纳决定及后续责任。
  3. 发送方保存对方的持久回执，并保留必要的后续核对工作。

中间结果可以暂时未知，但未结工作必须有负责方。确认未提交的纯数据库闭包可以有限重试；提交结果未知时先查原键，不能立即发送外部请求或释放未知预留。规则见提交未知与跨 owner 交接。

对象字节也有独立边界。Content 先写准确不可变字节并验证介质条件，再提交可发布引用；字节存在不等于已发布。发布失败留下的孤儿字节有原清理责任，不能用一个数据库回滚假设它们已消失。

5.4 什么可以重建，什么必须保留

展示汇总、检索索引和部分缓存可以从准确来源重建。重建时必须保留版本、水位、权限和缺口信息；索引滞后或分页未完，不能替代完成门禁所需的完整内部关系。

原命令身份、未结效果、控制与撤权、关闭墓碑、一次消费以及尚未结清费用，不能因为“可以再算一遍”而删除。旧备份缺少最近的撤权或外部效果历史时，只能安全诊断，不能用旧 allowed 或空表重开动作。正文清理与最小关闭身份保留分别处理，存储代价要按实际增长验收。见保留与恢复。

6.1 默认部署与开发装配

默认生产部署在单地域三个可用区。云端 PG 保存 Task 的权威记录，设备 SQLite 保存本机执行和恢复记录。在线进程分为 WSS 网关、任务应用、分类工作池和执行宿主，管理与评测执行另设隔离边界。

开发可以使用单进程调试或本机 PostgreSQL 多进程装配，不依赖公司平台先行建成。但第一次生产上线仍要满足角色分工、耐久、隔离与跨可用区恢复要求。本机验证不能代替这些证据。见生产分布式 ADR、生产角色与故障域和工程装配。

6.2 协议与 SDK 怎样保存恢复身份

端云统一使用 WSS；独立服务间使用 gRPC，同进程可以直接调用 Go 接口。领域 JSON 合同放在传输外壳内，传输换连接或换进程不改变原命令含义。

Command 表达一次业务改变，首次发送前固定原目标、参数、期限与摘要；重复传输返回原决定，同键异内容拒绝。Query 读取当前允许披露的事实，不建立永久命令墓碑；查询失败不能替业务作出新的决定。

SDK 的责任因此不止发送 HTTP 或 WebSocket 帧。它需要保存原命令和固定 owner，处理接纳未知，恢复准确查询与订阅，并区分未接纳错误和已经存在的业务责任。浏览器可在 IndexedDB 保存未决提交，但它不持有 Task 完成权威。

设备方向的交接使用 Delivery 与 Reply。Reply 绑定原交付和请求摘要，在匹配 Ack 前由端点保留；网关转发成功和 socket write 均不等于业务 owner 已耐久收到。应用还要将 Result 与原输入分支关联，避免旧分支输出污染新界面。共同字段、错误和方法成功点见方法实现合同，通道和订阅见共同协议。

6.3 数据库故障接管怎样恢复原任务

接管可以更换物理实例，但必须延续原业务历史。 本节讨论 PG 写主或其可用区失效，候选副本仍能恢复同一逻辑分片的情况。只有 worker 退出而数据库正常时，直接领取原 Job 即可，无必须数据库提升。

平台和服务封闭新入口 暂停新接纳与新目标发送；已经交给目标的动作仍可能发生 不得将封新入口解释为撤销已发送动作；控制与核对能否继续取决于原库和实际入口是否可用

新 worker 续接原责任 合法领取原 Job，沿原命令查接纳、沿原 Operation 和 Attempt 查效果，并共同保存合法事实与后续工作 依赖不可达时保留等待和资源限制；旧领取不得回写，可信迟到事实走独立归并入口
服务分阶段开放 先开放获准查询、控制、关闭及原效果和费用核对；依赖、配额与故障后容量满足后再开放新工作 不要求所有 unknown 清零才恢复无关任务；单个任务恢复也不证明全系统就绪

应用消费平台提供的隔离与耐久证明；Job 租约不负责数据库选主。图中的“平台恢复机制”表示现有数据库及基础设施职责，不增加业务调度服务，也未指定选主产品。具体证明接口需要生产实现落实。

设计取舍与待验证目标：同步提交和备用容量有实际成本。既定目标是在单可用区故障下，云端 PG 已确认账本不丢失，即恢复点目标 RPO=0；控制与权威查询在 60 秒内恢复，即恢复时间目标 RTO≤60 秒。这些是运行验收目标，本文没有测得这些结果。

PG 恢复不证明设备或文件字节已经恢复。原文件根不可达时，系统继续限制该根的冲突新动作，但无必须阻止无关任务恢复。整地域灾备也必须先隔离原地域，不得把旧备份当作当前业务历史直接重启。

具体条件见数据库与内容恢复和可信时间。

6.4 滚动升级按角色交接

发布流程决定何时让旧实例退出，原业务记录和执行门禁决定新实例能接什么工作。发布流程不得把未结 Job 改成 done，也不得通过重新提交用户目标掩盖恢复缺口。

切换前必须验证新实例能读取当前格式、识别原命令合同，并具备准确版本与恢复处理器。不兼容时，暂停切换或进入已声明维护窗口。以下发布动作仅是运维步骤示意，不新增核心 API。

6.4.1 worker 从原阶段继续

旧 worker 先停止领取新工作，在领取仍有效时保存可保存的业务阶段与未结责任。新 worker 取得合法新 Claim 后，从原阶段继续。

排空超时按故障处理。无法证明旧进程退出或领取已释放时，必须等待安全回收条件，不得并行重放可能已经发送的动作。

中断阶段 接替者读取什么 允许继续什么
命令接纳未知 原 owner、Command、请求摘要与 CommandReceipt 查询原接纳决定，不换参数、命令或负责方重投
模型已到可能发送阶段 原 Decision、ModelCall 发送阶段、费用占用和核对 Job 查询原调用；供应商不可查询时保留未知，不透明重新推理
工具可能已产生效果 原 Operation、Attempt、目标键、journal 及证据 核对原效果和迟到可能，不因换进程新增目标尝试
等待用户、设备或依赖 原 InputRequest、waiting Job、条件版本与期限 继续等待原依赖，不占用常驻线程，不将等待记为完成
Result 已固定但交付未确认 原 Result、输入分支和交付记录 续交同一结果，不重新执行报告任务
目标或控制已更新 当前修订、旧 Snapshot 和消费记录 按当前修订推进；旧提案保留审计和费用，不恢复行动资格

6.4.2 应用与网关分别切换连接

应用退出时，优先由网关重建内部服务绑定，端云 socket 可以保留。网关退出时，外部连接需要重连。两种切换都必须按原身份恢复业务决定、Delivery 和 Reply，隔离旧绑定输出；订阅连续性无法证明时，重新取得快照。

连接额度由身份负责方裁决，业务绑定归原服务分片，二者分别提交。新握手先到、旧额度尚未释放时，可以暂拒并有限重试；网关不得私自增加额度。旧绑定清理也必须匹配原身份与条件。

设计取舍：优先内部重绑可以减少普通服务发布引发的外部握手，但增加绑定状态和快照恢复流量。保留 socket 只说明连接未断，不能证明业务处理毫无中断。见生产发布与重连。

6.4.3 执行宿主先隔离旧入口

执行宿主升级时，先封闭新的实际启动，保存原在途操作和核对责任，再证明旧本机进程、驱动队列及子进程已退出或被隔离。

新宿主取得操作系统排他锁后，恢复原 TaskGate、关闭记录、资源代次、Attempt、队列和补传工作。只有门禁、许可、资源及依赖都满足的范围，才能开放入口。多机接管还需要目标自身的隔离机制或运维证明，云端 Claim 到期不能代替设备隔离。

本机退出只证明本地入口受控。已经交给远端目标的请求仍可能迟到，新宿主必须继续核对原效果。原库、原文件根或旧入口隔离无法证明时，不得从新空库或空目录接管原身份。具体要求见执行系统。

继续扩批的条件：每批检查实际服务就绪状态、原未结工作的可恢复性、连接重建以及控制和核对容量。出现恢复缺口或容量不足时停止扩批，保留原任务及责任。

6.5 新版本怎样接住旧记录

版本兼容必须覆盖原命令、数据格式和未结责任。InstallLock 是固定制品、依赖、配置与平台约束的安装清单；能力名称相同，不表示两个版本可以互相解释原操作。

变更类型 接续条件与动作 失败处理与限制
旧任务使用工具 默认继续准确的原 InstallLock；保留原效果和费用查询入口，或由通过合同验证的兼容接管器承担 原代码不可信且没有合格接管器时，停用原代码，保留账本查询和明确的效果核对缺口
数据库格式升级 独立管理命令执行扩展结构、有界回填、切换、观察、收缩；保存迁移身份、制品摘要及检查点 旧实例全部退出、旧未结责任可恢复、回退保留期结束后，才删除旧字段；不得让每个启动副本竞相改表
同版本实例重启 适用扩展实例通过 reopen 固定新实例身份，核验旧实例隔离、当前批准、原格式及就绪状态 不重跑已完成迁移，不继承旧离线许可窗口，也不跳过当前绑定的并发检查
软件版本回退 回退是一次新的激活，需要准确旧 InstallLock、独立旧批准、当前格式可读写和新实例就绪 旧批准失效、不可核验或格式不兼容时停用并报告缺口；不得回滚 Task 历史、撤权、一次消费或外部效果

设计取舍：提前维护旧批准和格式兼容依据，需要额外的发布与验证工作，换取故障时可用的回退路径。安装包仍在，并不代表旧版本当前获准或可以读取新格式。

详细要求见版本与在途工作、存储迁移和独立旧版批准 ADR。

7 后续能力的接入位置

后续能力复用同一条“目标 → 准入 → 执行 → 事实 → 核验”主线，同时增加各自的持久身份和前提。它们的接入位置需要现在明确，但不全部成为首阶段报告任务的前置条件。

能力 接在现有主线哪里 新增或必须保留的边界
长期记忆与个性化 Memory 从获准来源提取候选，在独立保存许可下建立跨任务记忆；Brain 检索适用内容 读取、保存、再次使用分别获准；保留准确来源、时间和固定保留期限。索引与摘要不能绕过关闭和撤权
多 Agent 协作 Orchestrator 通过有界委派固定子目标、控制和预算；内部与外部 Agent 采用相应交接 内部子任务与外部独立运行时的责任不同；原创建未知不得换替身重复创建或分配预算
GUI 与手机操作 Executor 以设备、资源代次和准确观察执行有界动作 观察后一次动作，再观察和核验；本人接管封闭旧入口，在途未知仍需核对。模拟设备通过不代表真机平台已支持

周期与未来任务 Interaction 的 Schedule 形成有身份的 Occurrence，再提交普通 Task 实际启动重新检查来源、许可和预算；时区、错过及重叠规则明确，重启不任意补跑
受控改进 候选改进先进入独立评测（EvaluationRun），再经发布批准及版本激活 评测使用冻结样本和独立依据；测试成绩不授予权限，不允许靠重复正式尝试挑最好结果

各能力分别见内容与记忆、Agent 协作、执行系统、应用交互、评测与改进。

对研究和开源实现的借鉴，重点是发现机制与失败边界。它们可以启发上下文压缩、能力选择、记忆组织和有限计划，但不直接证明本项目的召回、费用或成功率改善。已批准 ADR、现行合同和待验证选择的区别见设计取舍与研究依据。

8 实现入口与验证方法

8.1 先实现一条可恢复闭环

按工程实现顺序和开发准备度选择首阶段开放范围。先建立原命令、回执、Job/Claim 与真实存储适配，再接输入目标、决策和执行，最后把独立核验、Result、交付与收尾接齐。不要先开放外部副作用，再补恢复身份。

开发者选择一条报告请求，必须能指出每个事务的原身份、输入、共同写入的记录、外部交接和下一项工作。字段或物理表如何拆分可以是实现选择，唯一负责方、门禁、原子提交集合和未结责任不能自行改变。

当前机器 Schema 仅覆盖形式化子集。正式开放方法之前，还必须完成同版闭合 Schema、方法登记、SDK 与正反例；文档列出方法名不等于完整公开协议已实现。

8.3 分清文档检查与运行验收

文档检查确认图文、示例、字段引用和限定条件一致。状态模型检查只覆盖所声明的原子步骤与有限性质。实际存储、驱动、SDK、多进程和跨可用区故障必须另行实验；真实模型任务质量、费用与耗时还需要固定任务集和测量方法。

例如验证查询答复丢失，不能只观察 UI 最终显示成功。实验必须固定故障点，同时检查原两端账本、真实文件、实际出站和写入次数、后续读回以及费用责任。故障接管和升级还要加入旧 worker 恢复、旧绑定晚到、原设备入口未退出和新旧格式并存。刺激与预期见关键故障矩阵。

文档链接可在仓库根目录运行以下检查；它不验证远程来源在线有效，也不执行系统恢复：

python3 docs/architecture/validation/check_links.py

正式结果必须绑定实现版本、配置、故障域和样本范围。RPO/RTO、容量和任务质量目标均不能由链接检查或图示通过来宣布达标。
