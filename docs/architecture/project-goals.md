## 1 定位

一个开源、长期维护的**个人 Agent Harness，围绕一份可靠性契约构建**。它的核心持有任务、授权、预算、动作效果和内容来源的记录，保证这些规则在端云分布式部署、插件替换和各种故障下依然成立。推理、记忆策略和各类执行适配器接在核心上，可以替换。

在这个 Harness 之上，应用可以让 AI 在用户授权范围内完成问答、工具操作、长时间任务以及端云和多 Agent 协作，并且在任何时刻都能说清楚做了什么、做成了什么、还有什么不确定。

项目的重点不是让 Agent 更聪明，而是让 Agent 做的事**可靠、可查、可恢复、不越权**。"聪明"的部分，也就是推理和记忆策略，能够随着模型和算法进步自由替换；"可靠"的部分是项目本身，不开放替换。分布式部署和插件机制是实现这些目标的手段，不是目标本身。

## 2 要解决的问题

### 2.1 Agent 能动手之后，真正的难点在后果

模型调用工具已经是成熟能力。一旦 Agent 开始改变外部世界，下面这些问题就绕不过去：

| 问题 | 典型后果 |
| --- | --- |
| **结果未知** | 付款请求发出后连接断开。当成"没执行"去重试，可能扣两次款；当成"已执行"去收尾，可能根本没付 |
| **完成靠声明** | 模型说"已完成"、接口返回 200，就被记为成功，实际目标没有达成 |
| **中断后接不上** | 进程重启、换机器、手机断网后，系统不知道哪些动作已经发出、哪些还没收尾，只能重来或放弃 |
| **权限悄悄扩大** | 插件、Skill、子 Agent、自动生成的改进继承了调用者的全部权限，甚至更多 |
| **记忆删不干净** | 用户删除或撤回的信息仍留在历史版本、索引、摘要里，继续影响后续回答 |
| **费用算不清** | 重试、取消、迟到的账单让同一笔消耗被重复计算或漏算 |
| **取消不等于停止** | 用户点了取消，界面显示已停止，但已经进入外部系统的动作仍然可能完成 |

### 2.2 调研结论

我们对五个开源 Agent Harness（Codex、Pi、DeepSeek Harness、Prime Agent、Crush）的关键源码，以及 Mem0、LangGraph、Graphiti、memU 等记忆库做了只读核对。主要发现：

- **名字不代表语义。** Prime Agent 的定时任务拿锁失败后仍然运行，状态写入错误被忽略；Crush 一个标为"必须送达"的通知通道，在 50ms 后仍可能丢弃通知。保证必须由行为和测试证明，而不是靠命名。
- **一条出口漏管，整条保障失效。** DeepSeek Harness 的发送前检查点只覆盖关联了 Session 的路径；没有 Session 的调用和嵌套工具会绕过它。所有对外出口，包括摘要、标题生成这类辅助调用，都必须走同一套准入和记账。
- **删除和过期的语义各不相同。** Mem0 的删除可能保留历史值；LangGraph 默认在读取时延长过期时间，过期数据是否被过滤还取决于配置和后端。项目不得把底层库的"删除""过期"直接当作对用户的承诺。
- **值得借鉴的做法。** Pi 恢复任务时只把原记录重新挂上，不会自动再发模型或工具调用；对于效果待定的动作，它同时检查保存时和当前的"可安全重放"声明。先弄清楚原来的责任，再决定能否继续执行。

这些项目都能分布式部署，也都支持某种插件。它们在模型循环、上下文管理和工具组织上各有可借鉴之处，但没有一个把"效果、权限和费用在故障与并发下仍可追溯、可恢复"作为整体目标。这是本项目要填补的空缺。

## 3 核心术语

后续文档和代码统一使用以下概念。具体字段和状态机由设计文档定义，但含义不得偏离这里。

| 术语 | 含义 |
| --- | --- |
| 用户 | 数据、任务、授权和费用的隔离单位 |
| 端点 | 用户的一台设备或一个运行环境（手机、电脑、云端执行宿主） |
| 核心（Core） | 持有并裁决任务、授权、预算、动作效果和内容来源等事实的部分。裁决语义不开放第三方替换，只能通过代码审查修改；存储、时钟等受信实现可以按专项契约替换（[ADR 0003](../adr/0003-replacement-classes-and-assembly.md)） |
| 裁决域 | 任务编排、会话、授权、预算所在的事务域，按用户分片。准入、确认消费和完成关闭都在它的一个事务里裁决 |
| 负责方 | 持有某类事实的逻辑归属，例如一个任务的负责裁决域、一个动作的负责账本。负责方从创建起不变；运行它的进程可以替换 |
| 可替换部分 | 产生判断或连接外部世界的部分：推理、记忆策略、执行适配器、交互适配器。通过固定接口接入核心 |
| 任务（Task） | 用户交给系统的一个目标及其全部后果。有唯一负责方，从创建到关闭不转移。委派出去的子目标也是任务（子任务） |
| 条件（Requirement） | 判断任务是否完成的具体条件。有版本，条件改变后基于旧版本的提议作废 |
| 条件集接纳 | 条件集可以用于裁决的前提：来自任务模板、用户的显式列表或用户确认。接纳时记下已处理到的输入版本；会改变任务依据的输入处理之前，条件集暂不适用 |
| 核验轮次 | 一次完成核验。开始时暂时冻结新的目标准入，并永久封闭清单中尚未开始的动作；以通过、拒绝或被替代结束，三种结束都释放冻结 |
| 推理（Reasoner） | 理解任务、制定和调整计划、选择工具或 Agent、综合回答的可替换部分。它只给出提议，不做裁决。这里指 Agent 的思考环节，不是模型推理服务（inference） |
| 提议（Proposal） | 推理基于给定材料给出的下一步建议，例如做什么、调用哪个工具、任务是否已完成。只是提议，不是授权，也不是完成证明 |
| 会话（Session） | 独立于任务存在的交互记录，承载用户输入、确认以及它们与任务的关联 |
| 确认（Confirmation） | 用户对一个具体事项的明确回应。只能被消费一次；界面显示过不等于用户已确认 |
| 命令 | 发给核心、要求改变状态的请求。由用户、调用者命名空间、目标域和命令标识四者共同标识；同一命令只产生一个决定。异步命令先"受理"，再"决定"，受理不是决定 |
| 动作（Operation） | 一次已准入、会影响外部世界的行动，例如 API 调用、文件写入或 GUI 点击。模型调用同样作为动作准入和记账 |
| 准入 | 核心在裁决域的一个事务里，确认一项动作现在可以成立，并固定它的依据（条件、输入、控制、授权、预算、确认）。准入不等于已经执行 |
| 门禁 | 动作和任务必须依次通过的四道检查：准入、开始（出口 P4）、重试、完成。各自的条件以核心契约为准 |
| 控制代次 | 任务的"开始资格围栏"。暂停、恢复、取消、条件变更、会改变依据的输入、开始完成核验都会递增它；准入后代次变了的动作不得开始。与规划代次、领取代次、撤销代次是不同的计数 |
| 开始回执 | 出口 P4 通过后的持久记录，表示"允许开始"。它不证明请求已经发出；写下"可能已发出"（出口 P5）之后，才按可能已发生处理 |
| 执行尝试（Attempt） | 对一个动作的一次具体执行，有稳定标识。结果未知时，重发沿用同一标识，不得换新标识绕过未知 |
| 效果（Effect） | 动作的实际结果，至少分为**已生效**、**未生效**、**未知**。未知必须保留，直到被证实 |
| 核对（Reconciliation） | 对效果未知的动作，向目标系统查询或观察以确定实际结果的过程 |
| 迟到可能性 | 已经可能发出的请求，以后是否还会产生或改变外部效果。只有明确证明才能排除，不能由超时、租约过期或取消推断 |
| 收尾（Settled） | 动作的派发已封闭、迟到可能性已排除、没有未处理的证据冲突。从未发出的动作凭原账本的内部封闭证明收尾；可能已发出的，凭可信出口固定的原始观察和受信解释规则收尾 |
| 原始观察 | 可信出口在实际 I/O 处固定的外部响应和观察。执行适配器只能引用它们、提交自己的解释，不能把自造的内容登记成原始观察 |
| 出口（Egress） | 数据或指令离开 Lerna 受控范围，或可能产生外部效果或费用的调用。核心自身的持久化和核心模块之间的交接属于可信基础设施 I/O，不算出口，但只能使用固定身份和固定目标，不得承载扩展发起的请求 |
| 受控持有方 | Lerna 自己控制的存储、索引、缓存、备份和端点。与之相对的外部接收方包括模型供应商、外部 Agent、第三方服务和消息收件人 |
| 最小责任记录 | 为满足 G1–G3、G10、G11 必须保留的记录，例如标识、状态、时间、费用和完整性摘要，不含内容正文。删除内容时它不随之删除，但有独立的用途限制和保存期限 |
| 授权（Grant） | 谁、对什么资源、可以做什么、为什么目的、在什么范围和期限内。可以单次，也可以持续 |
| 操作权利 | 授权允许对数据做的操作：读取、保存、同步、行动。原称"用途" |
| 处理目的 | 授权允许处理数据的理由，例如当前任务、个性化、诊断、评测、生成改进。与操作权利是两个独立维度 |
| 持久档位 | 部署声明的持久记录所覆盖的故障集合。本地档覆盖进程崩溃、重启和经过验证的掉电；云端生产档另外覆盖主机和单个可用区永久丢失 |
| 账本连续性 | 端侧账本没有被回退或复制成另一份。账本自身的记录不能证明它，必须用账本之外的见证（例如云端已记录的开始回执）核对；无法证明时进入恢复隔离 |
| 内容（Content） | 系统读取或产生的原始数据，带来源、版本、操作权利和处理目的的上限以及派生关系 |
| 记忆（Memory） | 从内容中提炼、可以跨任务使用的信息，区分事实、偏好、推断和经验 |
| 记忆记录 | 内容模块中记录"当前采纳哪一版记忆、依据是什么、与哪些版本冲突或替代"的权威记录。记忆策略只提候选，不能改写它 |
| 当前依据与历史视图 | 使用记忆的两种方式。当前依据把记忆当作现在的事实，记忆被纠正后随即失效；历史视图读取某个时间点的记录，仍受当前授权和删除状态约束 |
| 调用位置 | 一次提议请求中某次模型调用的稳定序号。推理重启后按同一位置拿回原结果，不重复发送；新位置才是一次新的采样 |
| 预算（Budget） | 可以消耗的模型、工具和外部费用上限，以及实际用量记录 |
| 结果（Result） | 任务关闭时固定下来的结论，包括达成情况、证据和遗留的不确定项 |
| 扩展 | 插件、Skill 和外部 Agent 等第三方接入物，需要声明能力、版本、依赖和所需权限 |

## 4 不变量

不变量是在任何实现、任何部署、任何故障下都必须成立的规则。每条都必须能写成测试，建议故障注入测试优先覆盖这些规则。

| 编号 | 规则 |
| --- | --- |
| G1 未知不等于未发生 | 无法确认结果的动作记为"未知"。只有经目标系统证实没有执行并且原请求不会再迟到生效，或目标系统对同一尝试标识保证幂等时，才能重试。只查到"当前不存在"不足以证明未执行 |
| G2 完成需要证据 | 任务只有在全部必要条件都有证据满足，并且全部已准入的动作都已收尾（效果确定，或确定不会再迟到生效）时，才能标记成功。任务也可以非成功关闭；非成功关闭可以遗留未知项，但动作账本的核对责任和预算的结算责任不因任务关闭而结束。条件集被接纳后才能支撑成功；把核验规则换成证据更弱的规则，与删除必要条件需要同样的可信依据。G2 保证"已接纳的条件都有证据"，不保证条件集完整表达了用户意图；Result 必须列出核验了哪些条件，供用户判断 |
| G3 先持久再确认 | 系统确认接下一项责任或开始执行前，记录必须达到所声明的持久档位。内存队列、通知、连接状态和函数返回值都不算凭据。云端生产的权威记录必须采用云端生产档（承受进程崩溃、主机和单个可用区永久丢失）；端侧和本地部署采用本地档，不覆盖存储介质永久丢失。档位由部署配置固定，不得由请求降级，也不得因副本失联临时降档。超出档位的故障发生后，系统停止推进并保留未知，不从旧快照猜测继续 |
| G4 先准入再执行 | 每个动作执行前，持久记录中必须写明它基于哪个条件版本、哪项授权、哪笔预算，模型调用也不例外；执行端点在实际出口处再核验一次 |
| G5 出口全覆盖 | 所有对外出口，包括模型调用、工具调用、网络请求、文件和设备操作，以及摘要生成等辅助调用，都必须经过同一套准入和记账，不得有旁路。核心自身的持久化和模块间交接属于可信基础设施 I/O，不计为出口，但不得被用来承载其他请求 |
| G6 提议与裁决分离 | 推理的输出只是提议。是否行动、是否完成，由核心根据记录裁决 |
| G7 权限只收缩 | 委派给子任务、子 Agent、插件、Skill 的权限，以及自进化产物的权限，不得超出来源。任何组件都不得自行扩大权限 |
| G8 操作和目的分别授权 | 读取、保存、同步和行动这四种操作权利分别授权；处理目的（例如诊断、评测）另行授权，缺省不等于全部，派生内容的目的上限取全部输入的交集。读过不代表可以保存，为诊断读取不代表可以为评测读取，以前可用不代表现在可用；每次使用时都要检查当前授权。无法证明当前授权有效时（例如端点与授权负责方失联），停止依赖该授权的新使用，已经开始的动作继续记录和核对。撤销分两个阶段：撤销被接纳后立即拒绝新的准入和凭据；各执行端点确认停止后，撤销才算完成。界面如实展示所处阶段 |
| G9 删除可验证 | 用户删除或撤回信息后，原始内容、索引、派生记忆和缓存都必须停止使用。受控持有方必须能验证清理已完成；已发送给外部接收方的副本，按其支持的能力请求删除，并如实报告清理状态。标记为严格删除的数据，不得发给无法验证删除的接收方。最小责任记录不随内容删除 |
| G10 费用只计一次 | 每个实际计费来源只计一次。取消或关闭任务不会抹掉已经产生的费用 |
| G11 责任不随故障转移 | 超时、取消、断线或进程替换，都不会把一项动作改派给其他执行端点，或改写成新任务来规避未知状态 |
| G12 用户隔离 | 不同用户之间的数据访问、任务运行和资源消耗互相隔离，一个用户的故障或负载不得影响其他用户的正确性 |

由此得出一条行为准则：**宁可停下等待，不可猜测前进。**前提无法证明时，系统说明具体缺什么，关闭依赖该前提的新行动，并把状态如实告诉用户。代价是有些任务无法自动收尾，这是有意的取舍。

## 5 目标冲突时的优先顺序

不变量是硬约束，不参与取舍。满足不变量之后，目标之间发生冲突时按以下顺序决定：

1. **用户控制与隐私**：用户能看到、能停下、能删除，端侧隐私数据不外流
2. **故障后可恢复、可诊断**：任何中断后都能从记录接续，并能查清发生了什么
3. **任务效果**：回答正确率、任务成功率
4. **延迟与成本**
5. **扩展和替换的便利**

例如，为了降低延迟，可以让推理一次提交一个有限计划，由核心一次准入多步；但不得为了省一次往返，让推理直接调用执行适配器，因为那会破坏 G4–G6。

## 6 用户与典型场景

**使用者。** 一类是用本项目构建个人智能应用的开发者，另一类是使用这些应用的个人用户。一个用户可以拥有多台设备、多个任务和多个 Agent。

下列场景用于检验设计是否完整。每个模块设计都必须说明它在相关场景中承担什么职责。

| 场景 | 描述 | 主要考验 |
| --- | --- | --- |
| S1 个性化联网问答 | 用户问"适合我下周出差的航班有哪些"，系统检索实时信息，结合用户偏好作答并给出来源 | C2、C3、V1、G8 |
| S2 多步工具操作 | "把本周会议纪要整理成文档，发给项目组"，涉及读取、生成、写文件、发消息 | C1、C4、V3、G1、G2、G4 |
| S3 手机 GUI 操作 | 在一个没有 API 的应用中完成设置修改，中途用户接管，再交还给系统 | C4、C7 |
| S4 长时间任务与断网 | 持续数天的跟踪任务，期间手机多次离线、云端进程重启 | C5、V4、G3、G11 |
| S5 多 Agent 委派 | 主任务把子目标委派给内部或外部 Agent，过程中取消 | C5、C6、G7 |

## 7 能力要求

每项能力列出要求和验收要点。验收要点是测试计划的最低覆盖范围，不是完整用例。

### C1 任务理解与规划

结合目标、用户约束、上下文和可用能力制定计划，选择工具或 Agent，拆分和委派工作；根据实际反馈调整后续步骤，综合出回答，并提出完成判断。完成与否由核心按 G2 裁决。

验收要点：信息不足、行动失败或结果不明时，明确说明当前判断和缺口，不编造完成；条件变更后，基于旧条件的提议不会被执行。

### C2 上下文、记忆与个性化

为当前任务组织目标、进展、工具结果、证据和记忆。长期记忆的来源包括用户提供、授权接入和交互提取，区分事实、偏好、推断和任务经验，并保留来源、时间、置信度和适用范围。支持端云结合：重要的隐私数据可以只留在端侧，原始数据、索引、派生记忆和返回结果分别遵守各自的存储、处理和同步策略。

验收要点：个性化信息在适用的任务中实际改变了结果；删除或撤回后不再被使用；端侧专有数据不会出现在云端存储或日志中。

### C3 信息获取与证据处理

通过可替换的搜索和内容获取能力，从声明支持且已授权的信息源取得实际内容，记录来源和获取时间。

验收要点：回答依据来自实际取得的内容，引用能支撑结论；检索失败、证据不足和来源冲突时，有明确表达。

### C4 工具调用与设备操作

执行工具、设备或外部系统上的动作，提供环境观察、调用反馈和实际结果。API 是主要路径；GUI 用于没有合适 API 的应用，以及作为兜底。工具和设备必须声明支持的能力、适用条件，以及能否幂等、能否查询结果。

验收要点：分别报告"是否执行"和"效果是否确认"，无法确认时保留未知；请求已发出或节点已连接，不得作为完成依据；GUI 操作遵循"观察 → 动作 → 再观察 → 核验"。

### C5 任务运行与端云协同

持久保存任务状态和执行记录，提供调度、超时、重试、取消和恢复，支持即时问答和长时间任务。根据节点能力和用户策略分配工作。委派给内部 Agent 的工作以子任务表达；外部 Agent 以执行适配器的方式接入。两者都受同一套授权、预算和完成规则约束。

验收要点：本地能证明当前授权有效的步骤可以离线继续；依赖云端当前授权或失联节点的步骤会等待；重连后先核对授权、任务状态和执行结果，再决定下一步；可能已产生外部效果的动作，先核对再决定是否重试；取消父任务时，子任务和外部 Agent 的处理状态如实呈现。

### C6 扩展接入与协议互操作

通过共同接口和 SDK 接入插件（可安装、可替换的组件或适配器）、Skill（用户自定义的操作知识和流程）、Agent（内部 Agent 的生命周期由本项目管理，外部 Agent 保留独立运行时）。共同接口覆盖任务协作、能力调用、记忆访问、端云连接，以及端侧 UI 的呈现、用户事件、输入请求和交互结果；UI 可以关联任务，也可以独立存在，不绑定具体界面框架。

验收要点：扩展声明能力、版本、依赖和所需权限；安装、替换和回滚有兼容性验证；扩展只能实现可替换部分的接口，不得进入核心，也不得绕过 G4、G5、G7。

### C7 授权与用户控制

统一表达主体、资源、动作、范围和有效期，支持单次和持续授权。核心负责授权检查，执行端点在出口处落实行动权限。用户可以查看、纠正和删除信息，限制用途，中断任务，接管设备。运行记录的使用也受授权和用途限制。

验收要点：委派后的权限只收缩；撤销授权后，依赖它的新动作停止；界面如实展示"取消已保存，部分动作结果仍在核对"这类中间状态。

### C8 运行观测与能力评测

关联跨端任务、工具调用、授权和结果记录，支持运行诊断。提供可复用的测试集、基线比较和评测结果，衡量质量、耗时和成本。

验收要点：契约符合性和任务实际效果分开记录；每个评测结果都能追溯到测试环境、实现版本、测试集和测量方法；除本次测试任务必需的输入外，参考答案、评分材料、其他正式运行的轨迹和诊断都不会进入被评测对象的训练、提示或候选生成过程。

### C9 受控自进化

从运行经验中提出改进，经过隔离评测后发布，持续监测效果，支持回滚，并保留来源、产物版本和评测依据。

| 改进对象 | 生效方式 |
| --- | --- |
| 记忆 | 授权范围内的常规更新可以自动生效；声称效果改善时需要评测证据 |
| Skill、执行策略、Agent 配置 | 通过评测后逐步启用 |
| 插件与核心代码 | 只生成可审查的补丁，由维护者确认后发布 |

验收要点：用改进前后的基线比较证明效果提升；评测结果不扩大发布权限；自进化不得降低评测门槛；回滚后旧版本可以正常运行。

## 8 系统边界

| 编号 | 要求 |
| --- | --- |
| A1 核心与可替换部分 | 持有并裁决事实的部分组成核心：任务、会话、授权、预算、动作账本、内容治理、运行记录，以及让它们可恢复的持久工作和出口闸门。产生判断或连接外部的部分可以替换：推理、记忆策略、执行适配器、交互适配器。一类事实只有一个写入方 |
| A2 独立替换 | 每个可替换部分都有可用的默认实现，并且可以单独替换；替换后第 4 节的不变量仍然成立。核心不开放替换，只能通过代码审查修改 |
| A3 端云部署 | 核心和可替换部分都可以部署在端侧、云端或两者之间。事实的归属不随部署位置变化，也不随故障转移 |
| A4 共同契约 | 模块、节点和扩展遵守同一套接口和授权规则，明确输入、输出、错误和权限限制，并通过一致性测试验证 |

**明确不做：**

- 不以通用分布式框架或通用插件平台为目标。分布式部署和插件机制只服务于本文的目标。
- 不承诺对任意第三方系统"恰好执行一次"。目标系统不支持幂等或结果查询时，只能保留未知状态。
- 不承诺取消可以撤回已经发生的效果。取消只是停止新的推进。
- 不提供自动补偿。撤销已经发生的动作，本身就是一个新动作，必须重新准入和授权。
- 不训练基础模型，也不以提升模型本身的能力为目标。
- 不把模拟设备上的验收通过，等同于真实手机平台已经受支持。

## 10 验收目标

### 10.1 量化目标

| 维度 | 目标 |
| --- | --- |
| 最终服务规模 | 千万注册用户、百万日活用户、十万同时在线 |
| API 覆盖 | 支持 1000 个以上 API 的准确调用 |
| 首次调用正确率 | ≥ 90% |
| 有限重试后的任务成功率 | ≥ 95% |

这些是目标值，尚未实测。API 接入数量和调用效果分别验收；在线规模必须结合任务吞吐、活跃任务数、模型并发和存储负载一起验证。

### 10.2 专项验收

**V1 联网问答。** 验收答案正确性、引用对结论的支撑程度和信息时效，以及检索失败、证据不足和来源冲突时的行为。个性化信息的使用必须符合 C2 和 C7。

**V2（已撤销）。**原为"手机 GUI 操作"专项。GUI 不是关键能力，它的正确性由 C4 的验收要点和 GUI 适配器的测试要点覆盖，不再单独做专项验收。编号不复用。

**V3 API 工具调用。** 验收 10.1 中与 API 有关的目标：在固定的 API 集合上，分别统计首次调用正确率和有限重试后的任务成功率；用幂等、可查询、不可查询三类可注入故障的模拟 API，验证结果未知时不盲目重发、按能力声明核对或安全重发；API 覆盖规模按能力声明和抽样一致性测试统计。参考验收使用模拟 API，它们必须记录实际收到的请求和产生的效果；接入真实 API 后，另行声明并验证支持范围。

**V4 结果未知与恢复。** 验收可靠性契约本身：在每个持久化点前后注入崩溃和回执丢失，验证结果未知后不盲目重发、取消与执行的竞争结果、迟到效果的接纳、断网重连后的核对，以及端侧账本回滚的检测。对应场景 S7 和 S4。判据是持久记录和目标实际收到的调用次数，不是接口返回值。

### 10.3 成熟度等级

每项能力分别记录目标等级、实际等级、验证结果和已知边界。

| 等级 | 完成标准 |
| --- | --- |
| L1 契约定义 | 职责、输入输出、可观察行为、错误、权限和能力声明都有明确约定 |
| L2 参考实现可用 | 参考实现可以运行，验证结果可以重复 |
| L3 替换与互操作 | 不同实现遵守同一接口，通过适用的跨组件、跨节点或 Agent 协作验证 |
| L4 异常恢复与治理 | 适用的失败处理、恢复、权限和用户控制经过验证；自进化另外必须验证发布和回滚 |

验收只认运行证据。文档写完、图画完、静态检查通过，都不代表能力已经达成。场景演示通过，也不得替代各项能力的独立验收。

## 11 建议的开发顺序

以下顺序依据依赖关系提出，供规划参考，可以调整，但调整时必须说明原因。原则是**先做出一条能在故障下正确恢复的主线，再扩展能力的广度**，因为不变量很难事后补回。各阶段涉及的模块和深度见[分层与模块](layers.md#9-m1-最小切片)。

| 阶段 | 目标 | 主要覆盖 | 退出标准 |
| --- | --- | --- | --- |
| M1 可恢复主线 | 单用户；核心的最小可用版本；默认推理；API 和文件适配器。打通"目标 → 提议 → 准入 → 执行 → 效果 → 核对 → 完成" | C1、C4（API）、C5、G1–G6、G11 | V3 的故障行为部分在模拟 API 上达到 L2；V4 在单进程和进程重启范围内达到 L2，含回执丢失、进程重启、取消与执行竞争、迟到效果、结果不可查询的动作、完成核验被拒绝后继续；持久性按本地档在一个开发平台组合上验证（含掉电或等价的存储故障模型）；基础运行记录可查 |
| M2 授权、预算与记忆 | 完整的授权模型、预算预留与结算、内容治理的删除与用途限制、默认记忆策略、用户控制 | C2、C3、C7、G7–G10 | V1 达到 L2；删除和撤回可验证；费用对账无重复、无遗漏 |
| M3 端云 | 端侧部署核心的执行部分、离线继续、重连核对 | C5（端云）、A3 | V4 的端云部分达到 L2，断网和重连场景（S4）通过；支持的端侧平台列入平台准入表；系统自动还原和备份导入的回滚场景通过；混合版本的协议协商、转码和恢复按兼容矩阵验收，不支持的组合安全拒绝 |
| M4 协作与扩展 | 子任务委派、外部 Agent 适配器、扩展 SDK、可替换部分的第二种实现；可选交付：手机 GUI 适配器和用户接管，可作为第二种执行适配器 | C5（协作）、C6、A2、A4；C4（GUI，可选） | 至少一个可替换部分有第二种实现并通过一致性测试（L3）；S5 通过；GUI 适配器为可选交付，不进入退出标准；对外声明支持的扩展接口、版本和平台组合都附注册记录和兼容验收证据 |
| M5 评测与自进化 | 评测套件、基线比较、受控发布和回滚 | C8、C9 | S8 场景完整通过，含回滚 |
| M6 规模与生产 | 多用户隔离、容量和故障域验证 | G12、10.1 量化目标 | 规模和成功率目标有实测数据支撑（L4），其中 V3 的正确率和 API 覆盖规模、V4 的云端接管演练达到 L4；云端生产档在销毁主机和单个可用区的演练中通过；开放云端生产档之前，高可用实现、提升资格和旧主隔离已写成 ADR 并通过接管故障历史验收（见[部署 4.4](topics/deployment.md#44-云端进程和可用区故障)） |

运行记录和基础观测（C8 的一部分）从 M1 起就要具备，否则后续阶段无法诊断问题。

**分阶段不等于豁免不变量。**每个阶段只开放已经满足相关不变量的功能，尚未实现的治理能力通过"不开放对应功能"来保证不被违反。具体地，M1 只用于受控测试：不接触真实个人数据，不开放第三方扩展，只运行经过审查的参考实现。面向真实用户之前，至少要完成 M2 的授权、内容治理和预算能力，以及出口沙箱。

## 12 如何使用本文

**技术设计文档**：[分层与模块](layers.md)是各模块设计的直接上游。每篇模块设计在开头列出它负责满足的能力（C）、边界（A）和不变量（G），说明在相关场景（S）中承担的职责，并对每条不变量给出实现方式和验证方法。

**测试**：用例标注对应的 C、A、G、V 编号。不变量测试优先写成故障注入测试。

**代码开发**：功能变更说明影响哪些编号；涉及外部出口、授权、预算或持久记录的变更，必须附带对应不变量的测试。

**修改本文**：目标、不变量或边界变化时，在修订表中记录日期和原因，并检查受影响的设计文档和测试。
