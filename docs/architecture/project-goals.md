本文说明项目要做什么、为什么要做、做到什么程度才算达成。它不规定技术方案。模块设计、协议和部署见[架构草稿](../research/architecture/README.md)；两者冲突时，目标与范围以本文为准，实现细节以草稿为准。

## 1 一句话定位

一个开源、长期维护的**个人 Agent Harness**：让 AI 在用户授权的范围内替用户做事，并且能证明自己做了什么、做成了什么、还有什么不确定。

## 2 要解决的问题

### 2.1 Agent 已经能动手，但结果不可信

模型调用工具的能力已经普遍可用。问题出在动手之后：

- **结果未知。** 请求发出后超时或断线，外部系统可能已执行，也可能没有。按"没执行"重试，可能扣两次款或写两次文件；按"已执行"收尾，可能什么都没发生。
- **完成靠声明。** 模型说"已完成"，或者请求返回了 200，经常被直接当成任务成功。
- **中断后无法接续。** 进程重启、换机器、断网重连之后，系统不知道哪些工作还没收尾，只能从头再来或者丢掉。
- **权限会悄悄扩大。** 插件、Skill、子 Agent、自动生成的改进，经常继承甚至超出调用者的权限。
- **记忆删不干净。** 用户删除或撤回的信息，仍然留在历史版本、索引或派生摘要里，并继续影响回答。
- **费用算不清。** 重试、取消、迟到的账单，会让同一笔消耗被重复计算或漏算。

### 2.2 调研印证了这些不是假想问题

我们只读核对了 Codex、Pi、DeepSeek Harness、Prime Agent、Crush 五个开源 Harness 的关键源码，以及 Mem0、LangGraph、Graphiti、memU 等记忆库，记录在[调研目录](../research/README.md)。几个有代表性的发现：

- Prime Agent 的定时任务拿锁失败后仍然运行，状态写入出错也会被忽略；Crush 标为"必须送达"的通知在 50ms 后可能被丢弃。**代码里的名字不能代表实际的持久语义。**
- DeepSeek Harness 只在关联了 Session 的路径上设置发送前检查点，没有 Session 的调用和嵌套工具会绕过它。**只要有一条出口没被管住，整条保障就不成立。**
- Mem0 的删除可能保留历史值；LangGraph 的过期时间默认会被读取操作延长。**记忆库的"删除"和"过期"不等于用户期望的删除和过期。**
- Pi 的恢复入口只重新挂上原记录，不会自动再发模型或工具调用；遇到效果待定的操作，会同时检查保存时和当前的"可安全重放"声明。**这是值得借鉴的做法：先弄清楚原来的责任，再决定能不能继续执行。**

这些项目各有长处，但没有一个把"真实效果、权限、费用在故障下仍然可追溯"作为整体目标。这正是本项目要补的空缺。

### 2.3 我们不重复解决的问题

Agent 的规划能力、模型质量、工具数量，已有大量项目在推进。本项目把大脑、记忆、执行都做成可替换的组件，借用业界最好的实现，自己专注于把它们可靠地连起来。

## 3 核心主张

系统在任何时刻都必须能分别回答五个问题：

1. **用户想要什么**：目标和完成条件有版本。条件变了，基于旧条件的行动建议随之作废。
2. **现在允许做什么**：授权明确到主体、资源、动作、范围和有效期，只能收缩，不能扩大。
3. **实际做了什么**："已决定""已发出""效果已确认"是三件不同的事，分开记录。
4. **还有什么不知道**：无法确认的效果标记为未知，先核对再决定是否重试，绝不把"不知道"当成"没发生"。
5. **凭什么说完成**：全部必要条件满足、全部可能产生效果的动作都已收尾，才能宣布成功。

这五个问题不能压缩成一个 running/done 状态。由此得出三条贯穿全系统的原则：

- **大脑只提议，内核做裁决，执行端记录事实。** 模型的输出不是授权，也不是成功证明。
- **能恢复的才算接下了。** 每项已接受的责任都必须能从持久记录恢复；内存队列、通知、socket 都不算数。
- **宁可停下等待，不可猜测前进。** 前提无法证明时，系统说明缺什么，并关闭依赖该前提的新行动。代价是有些任务不能自动收尾，这是有意的取舍。

## 4 交付物与用户

**面向谁。** 构建个人智能应用的开发者，以及最终使用这些应用的个人用户。同一个用户可以有多台设备、多个任务、多个 Agent；不同用户之间的数据、任务和资源必须隔离。

**交付什么。**

| 交付物 | 说明 |
| --- | --- |
| 架构规范与共同协议 | 定义任务、操作、授权、内容、费用等核心对象，以及模块之间的接口 |
| 可运行内核 | 任务生命周期、调度、授权检查、运行记录、故障恢复 |
| 三系统默认实现 | 记忆、大脑、执行各一套可用的参考实现，均可独立替换 |
| 扩展 SDK | 接入插件、Skill、内外部 Agent 和各种端侧 UI |
| 一致性测试 | 验证任何实现是否遵守共同合同，包括故障和恢复场景 |

## 5 能力范围

| 编号 | 能力 | 关键要求 |
| --- | --- | --- |
| C1 | 规划与决策 | 根据目标、约束和反馈制定和调整计划；信息不足或结果不明时明确说明缺口 |
| C2 | 上下文、记忆与个性化 | 区分事实、偏好、推断和经验，保留来源与时间；个性化要真正影响结果；隐私数据可以只留在端侧 |
| C3 | 信息获取与证据 | 从授权的信息源取得实际内容，标注来源和时间；明确报告证据不足和来源冲突 |
| C4 | 工具与设备操作 | API 优先，GUI 兜底；分别报告"是否执行"和"效果是否确认" |
| C5 | 持久任务与端云协同 | 持久保存任务状态，支持超时、重试、取消、恢复和长时间任务；本地条件满足时可以离线继续 |
| C6 | 扩展与互操作 | 通过共同接口接入插件、Skill、Agent 和 UI，带能力、版本和依赖声明 |
| C7 | 授权与用户控制 | 用户可以查看、纠正、删除、限制用途、中断任务、接管设备；读取不等于获得长期保存权 |
| C8 | 观测与评测 | 跨端关联运行记录；提供可复用的测试集和基线比较，分别衡量合同符合性和任务实际效果 |
| C9 | 受控自进化 | 改进先隔离评测再逐步发布，可监测、可回滚；评测结果不扩大发布权限 |

C9 按改进对象分级生效：授权范围内的常规记忆更新可以自动生效；Skill、执行策略、Agent 配置须通过评测后逐步启用；插件和内核代码只生成补丁，由维护者审查后发布。

## 6 系统边界

| 编号 | 要求 |
| --- | --- |
| A1 逻辑分工 | 记忆管信息和经验，大脑管规划决策，执行管行动和反馈；内核提供任务、调度、授权和运行记录等公共保障 |
| A2 独立替换 | 三系统各有默认实现，可以单独替换；替换后任务、授权和运行规则仍然成立 |
| A3 端云部署 | 三系统可以部署在端侧、云端或两者之间，职责不绑定位置 |
| A4 共同契约 | 所有模块、节点和扩展遵守同一套接口与授权规则，并通过一致性测试验证 |

**明确不做的事：**

- 不承诺对任意第三方系统"恰好执行一次"；目标系统不支持幂等或查询时，只能保留未知。
- 不承诺取消能撤回已经发生的效果；取消只停止新的推进。
- 不提供自动补偿；撤销一个已发生的动作本身就是新动作，需要重新授权。
- 不把模拟设备上的通过当成真实手机平台已受支持。

## 7 怎样算达成

### 7.1 量化目标

| 维度 | 目标 |
| --- | --- |
| 服务规模 | 千万注册用户、百万日活、十万同时在线 |
| API 覆盖 | 1000 个以上 API 可以准确调用 |
| 首次调用正确率 | ≥ 90% |
| 有限重试后任务成功率 | ≥ 95% |

以上是目标值，目前都没有实测。规模还须结合任务吞吐、活跃任务、模型并发和存储负载一起验证；API 数量和调用效果分开验收。

### 7.2 专项验收

- **V1 联网问答**：答案正确，引用确实支撑结论，信息有时效；检索失败、证据不足、来源冲突时行为正确。
- **V2 手机 GUI 操作**：完整覆盖"观察 → 动作 → 再观察 → 核验"，包括点击、滑动、输入、返回、中断和用户接管。参考验收使用多个有状态的模拟设备，不要求真机。

### 7.3 成熟度等级

每项能力分别记录目标等级、实际等级和已知边界：

| 等级 | 标准 |
| --- | --- |
| L1 合同定义 | 职责、输入输出、错误、权限和可观察行为有明确约定 |
| L2 参考实现可用 | 参考实现可以运行，验证结果可以重复 |
| L3 替换与互操作 | 不同实现遵守同一接口，通过跨组件、跨节点或 Agent 协作验证 |
| L4 异常恢复与治理 | 失败处理、恢复、权限和用户控制经过验证；自进化另须验证发布和回滚 |

验收只认运行证据。文档写了、图画了、链接检查通过了，都不等于能力已达成。
