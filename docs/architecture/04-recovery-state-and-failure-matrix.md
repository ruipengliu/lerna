# 恢复状态与故障检查表

状态：依据用户已确认的[端云恢复方案](04-edge-cloud-and-recovery.md)整理的实现契约。未实现状态机，也未执行故障注入；表中的结果均为验收要求。

## 任务状态转换

状态转换由当前拥有者校验，以预期状态版本提交。任务可以存在多条并行分支；有可推进分支时保持 RUNNING，仅全部可调度工作都受阻时进入 WAITING。等待原因按分支和目标保留，不因其他分支继续执行而丢失。

| 当前状态 | 触发与前置条件 | 结果 |
| --- | --- | --- |
| 不存在 | Submit 经授权且操作身份首次受理，状态/回执/待处理工作原子提交。 | QUEUED；重复 Submit 返回已有 task_ref。 |
| QUEUED | 控制意图允许运行，拥有者及 Worker 资格有效，至少一项工作可执行。 | RUNNING。 |
| QUEUED / RUNNING | 没有可继续的工作，等待输入、依赖、授权或效果核对。 | WAITING，并记录全部有效等待原因。 |
| WAITING | 相关前置条件已满足，控制意图仍为 RUN，具备合法领取资格。 | QUEUED 或 RUNNING，保留尚未满足的其他分支等待原因。 |
| 任意非终态 | PAUSE 已受理。 | 停止发起新工作；已开始工作按能力处理。仍有在途工作时可以 RUNNING，停稳后 WAITING，控制进展标注已落实。 |
| WAITING 且已暂停 | 明确的恢复请求受理，其他等待条件已核对。 | 将控制意图改为 RUN，重新判断是否可调度；不直接清空全部等待原因。 |
| 任意非终态 | CANCEL 已受理。 | 控制意图为 CANCEL，停止新工作并传播取消；主状态依据在途工作与核对情况保持 RUNNING 或 WAITING。 |
| 任意非终态 | 必需工作及结果满足目标，完成提交先赢得并发版本检查。 | COMPLETED；迟到取消返回“任务已完成”，不改写事实。 |
| 任意非终态 | 已确认无法完成目标，必要在途处置已完成，关键效果无待核对事项。 | FAILED，记录失败和已发生的效果。 |
| 任意非终态且取消处理中 | 需停止的工作已停止或处置完成，关键效果已核对。 | CANCELLED，保留副作用及取消落实结果。 |
| COMPLETED / FAILED / CANCELLED | 迟到回复、重复请求、重启或控制消息。 | 不重开任务；合法重复查询返回既有结果，新的工作创建新任务。 |

CANCEL 已先持久化时，调度不得继续追加完成目标所需的新动作。若取消生效前既有工作已完成，拥有者核对实际完成证据后可记录 COMPLETED，并将取消请求标注为未能阻止完成；若关键动作结果未知，则等待核对，不靠消息到达顺序编造终态。

PAUSE/CANCEL 不是运行错误；未知效果不是已确认失败。取消指令自身可能因权限或不支持而被拒绝，不能覆盖成目标任务 CANCELLED。超时也先检查在途效果，再决定失败或核对等待。

## 所有权与 Worker 前置条件

任务拥有者记录至少包含 task_ref、owner_ref、owner_epoch、state_version、管理阶段及可选移交目标和检查点引用。owner_epoch 是任务已有身份的单调世代，不随网络重连递增，不与 task_ref 或 operation_id 混用。

管理阶段使用 ACTIVE、PREPARING、SEALED；目标准备中的记录不能提交业务状态。移交成功后的目标以新世代 ACTIVE 运行；源端保留 SEALED 记录及指向新拥有者的路由，不能把源端副本误作为新的 ACTIVE。

| 提交或动作 | 必须校验 |
| --- | --- |
| 任务状态更新 | 当前 owner_ref、owner_epoch、预期 state_version 与适用管理阶段。 |
| Worker 领取/续租 | 任务允许调度、工作仍可领取；领取代次及有效期在同一运行持久化单元更新。 |
| Worker 驱动新动作 | 当前工作领取凭据及适用授权；执行端检查来源、期限与已知失效状态。 |
| Worker 回传并推进状态 | 所有权前置条件与当前领取代次同时有效。旧 Worker 不可直接推进状态。 |
| 迟到执行结果 | 先作为带来源事实登记；由当前拥有者核对 operation_id 和实际效果后决定是否更新。 |
| 消费输入或取消 | 当前授权、操作去重、目标和等待项/控制状态；不能只凭消息送达改写任务。 |

以上校验包含在 RunStore 的受约束原子变更中；调用者不能先查询资格再无条件写入。监督逻辑处理用户意图与 Worker 提交可以有不同的必要凭据，但都不得绕过当前拥有者和状态版本检查。

执行凭据仅允许其声明的已有动作范围，不授予任意延长、派生新动作或再次委派的权限。任务移交需要停止源端发出新凭据，并确定旧执行端不再有资格启动新动作。若端侧暂不可达，只能在适用的有限资格已可证明失效后继续，不能用本地时钟猜测未知执行端已停止。

## 协作移交的故障窗口

移交针对一个任务，其子任务继续由各自拥有者管理。父任务迁移须转移委派关系和结果路由，不自动迁移或取消所有子任务。

| 窗口 | 持久化证据 | 恢复规则 |
| --- | --- | --- |
| 源端尚未准备 | 旧世代 ACTIVE。 | 原拥有者正常恢复，其他节点不得自行接管。 |
| 源端已 PREPARING，目标未准备 | 源端停止新调度并记录目标。 | 核对既有动作；可继续准备，也可在确认尚未封存及未发激活凭据后取消本次准备。 |
| 目标已准备，源端未封存 | 目标保存检查点版本与内容摘要，仍不具执行权。 | 源端可以继续移交或安全取消准备；目标不得因超时自激活。 |
| 源端正在封存，提交结果未知 | 同一原子提交包含 SEALED、唯一目标、新世代及激活 Outbox。 | 按原 change_id 查明提交结果；未查明前既不发激活凭据，也不恢复源端调度。 |
| 源端已 SEALED，激活消息未送达 | 源端旧世代永久停用，Outbox 中仍有可补发凭据。 | 补发至原目标；源端不因等待过久回到 ACTIVE。 |
| 目标收到激活，激活提交结果未知 | 目标按唯一移交内容幂等提交新 ACTIVE。 | 先核对持久化结果，未确认前不启动 Worker。 |
| 目标已 ACTIVE，回执丢失 | 目标新世代持久化，源端仍 SEALED。 | 重复激活返回同一结果，源端更新路由；不再次增加世代。 |
| 源端封存后目标永久不可达 | 不能证明目标未激活或已经失效。 | 参考实现保持待处理；故障接管需额外排他性机制，不提供“强制点一下即安全”的路径。 |

激活凭据绑定任务、源/目标拥有者、旧/新世代及确切检查点版本和摘要，并通过受信来源验证。源端只对一个目标产生一次有效激活决定。目标必须匹配已准备状态；源端封存时若任务版本已经变化，应重新准备一致检查点，不能激活旧快照。

冻结业务提交期间的迟到结果保存于可恢复收件记录；封存后转交目标，由目标核对。源端不能在目标准备后悄悄更新权威状态而不更新检查点。检查点摘要针对明确的保存字节计算，不依赖 Protobuf 任意重新编码天然得到相同字节。

参考故障模型覆盖持久状态未回滚的进程/网络故障。备份恢复、存储回滚或节点身份并行克隆不能当作普通重启；这些场景必须隔离新调度并核对所有权。若生产 Adapter 声明支持它们，须提供对应隔离证据及测试，不能仅恢复一个更旧的 SQLite 文件后直接运行。

## Inbox、操作与 Outbox 原子边界

| 阶段 | 持久化内容 | 崩溃后的检查点 |
| --- | --- | --- |
| 发送准备 | 操作意图/任务变更与待发消息共同提交。 | 无 Outbox 记录不代表可以重建一次新业务动作；按原变更及操作核对。 |
| 接收 | 原 message_id、来源作用域、载荷指纹、流位置、未处理标记。 | 已持久化即可回复 PERSISTED；重启扫描未处理记录。 |
| 同一运行存储内处理 | 操作登记/去重、状态更新、等待项变化、Inbox 消费标记和回复 Outbox 原子提交。 | 不出现已消费但状态没变，或状态已变但漏掉回复的组合。 |
| 不同存储模块处理 | 用同一 operation_id 幂等转交目标模块，再核对其受理/结果。 | 目标已受理但转交记录未落盘时，可查询/重复转交原操作，不能新建操作。 |
| 回复发送 | 从 Outbox 投递，接收方完成自己的持久化确认。 | 回执丢失可重发原消息，不产生新的业务回复内容。 |
| 清理 | 已满足交付及恢复义务，或已显式结束恢复窗口；操作核对记录按独立生命周期保留。 | 队列容量不足不授权直接清理未履约记录。 |

单独的 PERSISTED 回执不需要递归持久化确认；它丢失后可从接收记录重建。可靠流序号仅为可靠、需恢复的消息分配，临时事件、心跳和无需重放的回执不占用同一可靠序号空间，避免形成无法补齐的假缺口。

接收方确认的是按发送方向的持久化连续前缀。出现序号缺口时可暂存有界乱序消息并要求补投，不能越过缺口推进累计确认。过期缺口转入快照/操作核对；关闭旧流并记录恢复边界后再建立新流位置，不能假装原序列连续。

## 接纳窗口与记录清理

操作身份仍作为一个不透明 operation_id 对调用者呈现，其内部绑定受信作用域、接纳世代和随机部分；生成与验证通过协议 SDK/端口完成。无须额外公开一套全局窗口实体。

| 情况 | 处理 |
| --- | --- |
| 无既有操作，窗口有效且身份、业务期限和授权有效 | 首次受理并持久化操作身份及结果查询依据。 |
| 同一操作已受理，窗口仍有效或已关闭 | 当前授权允许时返回保留的原记录，必要时继续核对；不得再次首次执行。 |
| 无既有操作，所属窗口已关闭 | 返回过期/不再接纳，不能把查不到记录当作未执行。 |
| operation_id 被换到另一个窗口 | 身份与窗口绑定校验失败；主动创建新 ID 表示新业务意图，不能由传输重试自动完成。 |
| 长任务尚在运行，但接纳窗口结束 | 禁止在旧窗口新建操作；已有任务继续受自己的授权、期限及恢复义务约束。 |
| 旧窗口操作明细准备清理 | 先持久化关闭水位，确认无剩余恢复义务，再清理明细；不能反序。 |
| 拥有者迁移 | 随检查点移交适用的关闭水位、仍开放的窗口和已有操作记录，不能重置历史。 |

接纳窗口与离线执行授权不同：窗口决定能否首次接收一个业务操作，授权决定能否执行其动作。两者的过期时间不能隐式互相替代。具体签发与可信时间由授权分册实现；时间可信度不足时停止接纳依赖该时间判断的新动作。

窗口范围应绑定实际受理的模块/权威作用域。转发或 UI Adapter 不改变被转交逻辑操作的身份；真正派生的新操作使用目标模块可接受的窗口并保留父操作引用。旧接纳信息的管理记录必须在清理后仍足以拒绝旧 ID，不能通过重建连接把关闭水位归零。

## 局部恢复与 UI 顺序

每个需要恢复的任务、操作和流分别具备恢复进度。节点启动可先开放健康的无关能力；恢复受影响对象时遵循：认证与资格核对、消息保留范围核对、业务操作核对、有效等待项/界面状态恢复，再开放相关调度。

| UI 情形 | 恢复行为 |
| --- | --- |
| 窗口关闭后任务仍在运行 | 恢复新窗口呈现，不重新创建任务。 |
| 表单提交完成但 UI 未收到回执 | 按原 operation_id 查询并展示原结果；不得因重连再提交一次新操作。 |
| 两端以不同操作回答同一等待项 | 目标模块原子校验等待项版本；其余提交获得已处理/冲突结果。 |
| 旧等待项已撤销或期限已过 | 对新输入明确拒绝；不能自动绑定到新等待点。 |
| 独立 UI 不关联任务 | 根据其处理模块、操作和等待项恢复，不伪造 task_ref。 |
| 补丁基版本不符或末次临时增量丢失 | 通过快照或版本核对恢复；不能只等待下一条增量恰好到达。 |
| 旧 surface / 旧连接的消息迟到 | 校验路由和世代；可以保留必要业务结果证据，但不重新打开失效界面。 |

## 故障注入验收清单

使用同机多进程、独立本地持久化和多个模拟端执行以下测试。表格是计划，不是通过记录。

- 两个 Worker 同时领取、续租与提交，只有有效代次能推进状态；旧 Worker 的外部效果仍可核对。
- 在准备、封存、激活及回执每个移交窗口杀进程/丢包；不存在两个可调度拥有者。
- 源端封存后目标不可达，保持待处理而不是自动恢复源端执行。
- Inbox 持久化后、业务处理前重启；操作最终被处理且不会消失在 PERSISTED 回执之后。
- 跨独立存储转交已受理但本地标记失败，按原 operation_id 恢复，不能重复写入记忆或提交输入。
- 动作已发生但结果未落盘、取消和完成并发，终态与效果证据一致。
- 乱序、重复、断流、补投窗口及接纳窗口过期，不越过缺口确认，也不复活旧操作。
- 在关闭窗口水位与清理明细之间崩溃，恢复后仍拒绝已关闭窗口的首次接纳。
- 有界队列耗尽时重要消息不静默丢失，无关任务及 UI 仍按各自可用性运行。
- 离线授权到期、远端撤销尚未送达、可信时间异常，执行行为符合声明的离线模式。
- 多 UI 端、多 surface、无任务交互、迟到输入及版本缺口分别验证。

## 后续分册输入

记忆分册需给出独立存储幂等及查询契约、删除与恢复记录保留的协调规则；授权分册需落实拥有者/执行凭据、接纳窗口、离线授权及可信时间；扩展与评测分册需把可选自动接管、备份恢复支持及上述故障矩阵记录为实际能力，不从默认流程推导额外保证。
