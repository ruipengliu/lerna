# 持久运行与协议互操作研究

本文为 Lerna 的任务运行、能力扩展和跨系统协作提供外部证据。主要结论是：**持久执行可以保存控制进展，但外部效果核对、业务完成判断和授权有效性仍需框架明确承担。** 决策循环、会话历史、持久工作和远端任务是相关而不同的对象，建议分别建模。

研究日期为 **2026 年 10 月 3 日**。范围包括官方工程文档、正式协议及两篇近期预印本；已读取原文，不以搜索摘要作为机制依据。动态文档没有稳定发布日期时，以访问日标注。本次研究不声称覆盖全部最新成果，也没有实际运行以下项目或复现论文实验。表中的“建议”均为面向 Lerna 的推断，不代表来源作者的主张。

## 架构取舍建议

以下是基于上述证据的设计建议，须由后续实现验证。

**优先定义共同语义，再选持久引擎。** 稳定接口至少要表达目标版本、操作身份、实际效果、取消意图、等待条件和完成证据。底层可采用数据库驱动的持久工作或现有工作流引擎。选择标准包括端侧资源成本、云端运维、版本迁移和事务边界；不能仅凭已有 agent 集成就认定适合全部部署位置。

**让决策插件提出计划，让任务控制器承担准入和完成责任。** 插件可以使用图执行、代码循环或专用搜索策略。它们必须在共同边界输出提案及其输入依据。任务控制器检查提案是否仍适用，再交给执行组件产生效果。

**将外部不确定性作为显式结果。** 网络超时不能被统一解释成失败。执行组件需要声明安全重复执行、可核对或不可核对等能力。不可核对的未知效果必须进入受控处理路径，并向用户说明不确定性。

**保持本地任务与远端委托的双重身份。** 外部协议负责互通；本地任务负责最终验收。一次本地行动可以关联远端任务句柄，但两者的状态、权限和保留期限不能合并。远端过期或失联时，本地仍需保留已知事实与待处理责任。

## 验证与选型顺序

先制作一个包含人工等待、外部写入和远端委托的最小任务。对“执行前、效果提交后、结果落库前、取消传播中”四个位置逐一注入故障，再比较候选持久引擎。选择前需得到以下可检查的证据：

1. 恢复后任务仍引用相同目标、操作身份与组件版本。
2. 可幂等动作不产生重复效果；不可幂等动作的未知结果不会被自动重做。
3. 取消请求有明确接纳点，已发生效果与尚未停止工作被分别报告。
4. 远端完成、协议成功和本地任务完成被分别验证。
5. 替换决策实现、MCP 版本或远端代理后，共同任务规则仍通过同一组合同测试。

本轮交付为设计证据和实验建议；上述实验均未执行。
