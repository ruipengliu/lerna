# 端云部署与故障域

| 日期 | 修订说明 |
| --- | --- |
| 2026-10-04 | 初版：进程角色、端侧部署、可用区与故障域、断网与重连、云端故障接替、发布与升级兼容、在线规模的估算方法。 |

- 状态：草稿
- 负责满足：C5、A3、A4、G3、G4、G11、G12；协同 C2、C4、C6–C8
- 涉及场景：S1–S8，重点 S3、S4、S6、S7
- 上游：[项目目标](../project-goals.md)、[分层与模块](../layers.md#10-部署映射)、[网关与 SDK](../platform/gateway/README.md)、[数据与存储](data-and-storage.md)

本专题规定模块放在哪里、怎样隔离和接替、哪些连接可以恢复、升级之后怎样继续承担原来的责任。它不新增业务裁决者，事实的写入方保持[分层与模块](../layers.md)的划分。

推荐方案：

- **默认由云端持有任务**，端侧持有本机动作账本和出口闸门；
- 生产云端**单地域、三个可用区、同步持久提交、按用户分片**；
- **离线继续的边界**是"已准入，并且出口处仍能证明当前前提有效"；做不到就等待；
- 端侧独立持有任务是创建任务时就选定的另一种部署方案，**断线不会自动触发**它；
- 发布按用户组、宿主和故障域分批；新的安全语义必须显式协商，旧端不理解就停止新动作，但仍能处理原有责任。

有三种误用要特别防止：

1. 把租约到期解释为"旧动作没有发生"；
2. 把消息送达、连接恢复或系统作业重跑解释为"责任已经接续"；
3. 把"协议可以解析"解释为"旧端理解新的授权和效果规则"。

## 1 职责与边界

### 1.1 事实与部署位置

| 事实或行为 | 负责方 | 部署要求 |
| --- | --- | --- |
| 任务、条件、控制、Result | 任务编排 | 默认在云端；一个任务从创建到关闭不转移 |
| 消息与确认 | 会话 | 与裁决域同一事务域 |
| 授权、撤销、凭据依据 | 授权 | 与裁决域同一事务域；端侧不能凭缓存自行扩权 |
| 预算与实际用量 | 预算 | 与裁决域同一事务域；出口的用量经持久交接回报 |
| 动作、尝试、效果、迟到可能 | 动作账本 | 靠近对应的执行端；本机动作由本机账本负责 |
| 内容的用途、来源、删除和清理进度 | 内容治理 | 按数据策略部署在端侧或云端；同步需要单独授权 |
| 命令回执、待办、领取 | 持久工作 | 随事实负责方部署 |
| 对外访问 | 出口闸门 | 在每个真实出口处落实，不持有独立的效果事实 |
| 连接、重连、传输 | 网关与 SDK | 路由和搬运命令与回执，不裁决效果或完成 |
| 产物的发布和回退 | 部署管理、扩展管理 | 核心产物经代码审查；扩展只进入可替换接口 |

### 1.2 三种身份不要混淆

| 身份 | 含义 | 能否变化 |
| --- | --- | --- |
| **任务负责方** | 固定的逻辑事实归属 | 不变 |
| **执行端点** | 动作准入时指定的设备或运行环境 | 不变 |
| **工作者进程** | 当前运行的实例 | 可以替换 |

云端在另一台物理主机上恢复成"原执行端点"，必须证明身份、账本、所需的文件或环境状态、出口约束都是连续的。不能把任意执行池统称为同一个端点，来掩盖实际的改派。

## 2 对象与状态

### 2.1 进程角色

**M1** 全部在同一个进程里运行（见第 9 节）。**生产**按伸缩、信任和故障边界划分进程，而不是每个逻辑模块一个进程：

| 角色 | 部署内容 | 伸缩与隔离依据 |
| --- | --- | --- |
| 接入进程 | 网关、连接恢复、传输限流 | 连接数、握手、消息流量 |
| 裁决进程 | 任务编排、会话、授权、预算，以及对应的持久工作 | 按用户分片；准入保持单事务 |
| 云端执行宿主 | 云端动作账本、出口闸门、执行适配器宿主 | 动作量和核对量；第三方适配器隔离运行 |
| 推理工作进程 | 推理及其受控调用 | 活跃工作量；恢复依据由核心提供 |
| 内容进程 | 内容治理、存储访问、记忆策略宿主 | 内容和检索负载；可替换策略不能直接写治理事实 |

**进程数量不决定事实写入方的数量。**多个进程可以接替同一模块的工作，但不能各自持有可能冲突的任务、授权或效果事实。不推荐"每个逻辑模块一个进程"：拆开任务、会话、授权、预算会让准入变成跨域协调，个人场景下得不偿失。

### 2.2 端侧部署

| 项目 | 手机 | 电脑 |
| --- | --- | --- |
| 最小内容 | 本机账本、出口闸门、本机适配器、恢复客户端；使用本机内容时部署内容治理 | 同左，可以增加本地推理和记忆策略 |
| 宿主方式 | 在应用里运行；系统的后台任务提供恢复机会 | 可以作为用户服务运行；交互适配器可以单独退出 |
| 运行约束 | 运行窗口、电量、温度、内存、平台权限 | 休眠、用户注销、资源限制、设备权限 |
| 持久存储 | 未收尾的责任、回报和回执**不能被当作缓存淘汰** | 同左；多进程需要正确协调本机写入 |
| 资源不足 | 停止新接纳和新出口，优先保留恢复记录 | 同左 |

**手机上不能承诺常驻进程。**Apple 的后台任务由系统调度，iOS/iPadOS 26 的持续处理任务要求用户主动触发并显示进度，资源紧张时仍可能被终止（[WWDC 2025](https://developer.apple.com/videos/play/wwdc2025/227/)）。Apple 的后台推送不保证送达（[后台推送](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)）；Android 的 Doze 会暂停网络、推迟作业（[Doze](https://developer.android.com/training/monitoring-device-state/doze-standby)），AndroidX 的 `Worker` 被抢占后重跑会创建新实例（[Worker 源码](https://android.googlesource.com/platform/frameworks/support/+/cbf5ea2a1e5a7e5999144c2cb7f170802046e1c9/work/work-runtime/src/main/java/androidx/work/Worker.kt)）。所以手机部署围绕**有限的运行机会**恢复：推送只提示"去查询"，系统作业只唤醒本机账本，作业重跑不能直接重发有副作用的调用。

端侧的存储配置见[数据与存储](data-and-storage.md#54-持久级别)。端侧专有内容、索引、派生记忆和结果分别检查同步权限；云端裁决需要的证据如果不允许同步，就等待允许的核验方式，**"设备在线"不能当作完成证据**。

### 2.3 部署相关的字段

完整业务对象由各核心模块定义，这里只补充部署需要的字段：

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 任务 | 用户、任务、负责方、条件版本、控制版本 | 负责方固定；物理路由变化不改写归属 |
| 动作意图 | 动作、任务、条件版本、授权、预算、执行端点、参数、出口期限、所需的语义能力 | 执行端点固定；重试不能修改载荷 |
| 端点身份与能力 | 用户、端点、身份绑定版本、**账本连续性标识**、支持的契约、能力和格式 | 鉴权由授权负责；网关观察到的在线状态不承担责任 |
| 同步进度 | 数据类别、连续序号、已持久接纳的序号、清理回执 | 按每条流分别维护；不能用一个连接游标覆盖全部事实 |
| 发布记录 | 产物摘要、契约和持久格式版本、适配器版本、发布批次、**最低可回退版本**、验证依据 | 已有的尝试保留原版本引用；发布不改变任务或效果 |

### 2.4 故障域

| 范围 | 隔离与恢复要求 |
| --- | --- |
| 工作者进程 | 同一负责方接替；旧领取不能覆盖新记录 |
| 执行宿主或设备 | 保留固定的执行端点；恢复它的账本和环境，或等待、核对 |
| 可用区 | 权威记录跨区持久提交；剩余可用区预留容量 |
| 用户或用户组 | 队列、并发、存储访问和资源配额隔离 |
| 发布批次 | 一个批次不能覆盖全部故障域；异常时停止扩大 |
| 共享依赖 | 身份、DNS、模型供应商、发布和恢复入口单独纳入故障测试 |

**多可用区隔离不了同时发布的同一个缺陷。**Cloudflare 2019-07-02 的故障中，一条快速全球分发的 WAF 规则耗尽了 CPU，缺少分阶段发布是复盘列出的原因之一（[复盘](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/)）。代码、配置、适配器规则和扩展都要分批发布。

## 3 接口

所有持久命令携带用户身份、命令标识、契约版本和载荷摘要；用户身份取自可信的鉴权结果，并与载荷里的用户字段核对。

| 接口（负责方） | 成功含义 | 主要错误 | 幂等 |
| --- | --- | --- | --- |
| 端点握手（网关、授权） | 身份和协议匹配，返回可用契约和连接模式；**不承接业务责任** | 身份无效、版本不兼容、能力不足 | 可重复 |
| 提交交接（接收方持久工作和事实模块） | 持久接纳或持久拒绝 | 载荷冲突、版本失效、权限不足、存储不可用 | 同标识同载荷返回原决定 |
| 查询原交接（持久工作） | 原决定和接纳引用，或"当前未发现" | 无权、权威存储不可用 | 只读；**未发现不证明外部未执行** |
| 核验出口并登记尝试（授权、动作账本、出口闸门） | 当前前提核验通过，开始记录已持久；只准许对应的出口，不代表效果已生效 | 授权未知或失效、控制版本过期、预算不足、旧领取、无法持久化 | 重复请求不会产生第二份出口许可 |
| 提交观察和用量（动作账本、预算、内容治理） | 回报已持久接纳；效果和费用由各自写入方裁决 | 证据不支持、载荷冲突、来源不可信 | 回报按标识去重，费用按计费来源去重 |
| 同步控制与治理（任务编排、授权、内容治理） | 当前版本、撤销与删除记录、清理回执已在接收方持久落实 | 序号缺口、版本冲突、无法清理、端点不可达 | 按对象和版本幂等 |
| 排空与恢复宿主（持久工作、部署管理） | 已停止新工作并保存状态；或新版本已恢复 | 格式不兼容、账本不连续、旧写入方未隔离 | 重复执行不改写业务对象 |

**撤销与出口开始要有明确的先后。**出口核验和开始登记是受核心控制的一次开始动作（[出口闸门 4.1](../core/egress/README.md#41-正常调用) 的执行开始排序点）。开始记录成立后，动作按"可能在途"处理；撤销阻止之后的开始，但不能承诺撤回已经开始的效果。不能用一次旧的授权查询代替当前的出口核验。

通知只携带最少的标识和查询提示，允许丢失、重复和乱序。传输层的确认也不是责任证明：RabbitMQ 的发布确认和消费者确认覆盖不同链路，彼此独立（[RabbitMQ 3.13 确认语义](https://www.rabbitmq.com/docs/3.13/confirms)）。

## 4 关键流程

### 4.1 正常路径

正常的准入、交接和执行路径见[数据与存储 4.1](data-and-storage.md#41-准入交接与执行)。部署层面要注意一点：**实际出口与外部系统之间通常没有共同事务。**即使崩溃发生在实际发送之前，接替者也只能看到"可能已发出"，必须按 G1 恢复。

### 4.2 断网与重连

| 阶段 | 行为 |
| --- | --- |
| 断网前 | 每个已接纳的动作有独立记录；有限的计划不能只保存一份笼统的授权 |
| 断网中 | 保存本机观察、用量和待传回报；云端持有任务时，端侧**不产生新准入** |
| 新出口检查 | 当前前提能由本机的权威记录证明时才推进；依赖失联的云端记录就等待 |
| 重连鉴权 | 验证端点身份、账本连续性和版本；先进入受限的同步模式 |
| 控制核对 | 优先核对授权、任务控制、条件和内容撤回；相关步骤保持冻结 |
| 回报接纳 | 按当前允许的用途传递证据、费用和清理回执；不丢弃真实的迟到效果 |
| 收敛 | 查询原交接，补齐序号缺口；未知效果继续核对 |
| 恢复推进 | 所需前提重新可证明后，由任务编排决定下一步 |

**为什么"已准入"不够。**设想两种情形：断网后，云端"没有撤权"和"已经撤权"。端侧观察到的完全一样，无法区分。因此：

- 云端持有、可以撤销的授权，在失联时不能仅凭缓存或签名有效期启动新出口；
- 条件变更、取消状态、内容撤回如果也由云端裁决，同样如此；
- 缩短有效期只能缩小看不见的窗口，不能实现窗口内的即时撤销；
- 只有当前前提都能由本机的权威记录验证、且已有的准入仍然有效时，才能安全地离线执行。

这就是[项目目标 C5](../project-goals.md#c5-任务运行与端云协同) 的"严格等待"原则。撤回的内容不能因为"正在恢复"而继续使用或上传；确需保留的最小责任标识和费用事实应有独立的用途依据。

### 4.3 两种离线方案

| 比较项 | 默认：只执行已准入的步骤 | 备选：端侧独立持有任务 |
| --- | --- | --- |
| 任务负责方 | 云端，从创建到关闭不变 | 端侧，从创建到关闭不变 |
| 端侧部署 | 动作账本、出口闸门、本机适配器、必要的内容治理 | 完整的裁决域、持久工作、账本、出口和可用的推理 |
| 离线能力 | 不能新准入；只推进前提仍可证明有效的已有动作 | 可以在本地提议、准入、执行、核对和完成 |
| 授权与预算 | 使用原准入记录；出口仍检查当前授权；失联时不能用缓存代替 | 相关事实必须由端侧裁决域**唯一**持有；其他端通过命令访问 |
| 多设备 | 其他设备可以访问云端任务；原设备的动作不因失联而改派 | 其他设备依赖持有任务的端点；该端点失联时等待 |
| 故障恢复 | 云端任务等待原账本回报；端侧恢复原尝试 | 恢复完整的本地核心；云端不能自动接管 |

端侧独立方案应当是"该用户的裁决事实由指定端点唯一持有"的完整部署，**不能复制一份云端的预算和授权各自裁决**。是否支持这一方案，见[项目目标 13](../project-goals.md#13-待定事项)。

### 4.4 云端进程和可用区故障

1. 剩余的存储先证明自己有安全写入的资格；不能证明就停止新裁决；
2. 同一负责方的工作者领取原工作，更新并持久保存领取代次；
3. 按原记录区分：尚未接纳、已经接纳、可能已发出、效果未知；
4. 可能已发出的动作先核对；原执行环境无法恢复时等待；
5. 连接重新建立不触发动作重派；
6. 补传和核对受限速保护，控制命令保留专门的资源额度。

**租约到期只改变领取资格。**etcd 的锁也只是把"创建修订号"作为事务比较条件，保护 etcd 内部的更新（[mutex.go，v3.5.15](https://github.com/etcd-io/etcd/blob/9a5533382d84999e4e79642e1ec0f8bfa9b70ba8/client/v3/concurrency/mutex.go#L150)）。它不能证明旧进程已经停止外部调用，不能作为重发动作或改派执行端的依据。

**可用区故障时，正确性和可用性分开承诺。**PostgreSQL 默认是异步流复制，提升副本可能丢失已确认的事务；官方要求隔离旧主，防止双主（[故障提升](https://www.postgresql.org/docs/17/warm-standby-failover.html)）。"三个可用区 + 同步复制"本身还不足以证明提升是安全的：必须验证被提升的副本包含全部已确认记录，并阻止旧主继续写入。无法证明时停止新裁决，**不能为了恢复服务而从旧快照继续准入**。分片调整同样要保留原命令回执、责任记录、授权版本和删除记录，路由更新不能让两个存储同时成为同一事实的写入方。

**剩余可用区要预留余量。**AWS 建议预先配置能承受可用区损失的容量，不依赖故障时临时扩容（[静态稳定性](https://docs.aws.amazon.com/wellarchitected/2024-06-27/framework/rel_withstand_component_failures_static_stability.html)）。编排平台只管放置：Kubernetes 的拓扑分散约束控制副本分布，但 PDB 防不了非自愿中断（[拓扑分散](https://v1-34.docs.kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/)、[中断](https://v1-34.docs.kubernetes.io/docs/concepts/workloads/pods/disruptions/)）。副本数、故障域分布、升级中断预算和数据正确性要分别验证。

### 4.5 发布、升级与回退

| 阶段 | 行为 |
| --- | --- |
| 准备 | 记录产物、格式和契约版本；验证新旧组合、恢复和回退 |
| 扩展读取能力 | 先部署"能读新旧两种格式、仍写旧格式"的版本 |
| 灰度 | 按用户组、宿主和故障域逐批发布；分别观察契约错误和任务效果 |
| 排空 | 停止新领取或新出口；保存全部待办、尝试和回报；未知的动作可以留着继续核对，不能改写成新动作 |
| 启用新语义 | 只对声明支持的端点启用；旧端保持兼容功能，或只回报原有责任 |
| 启用新写法 | 确认所有相关的读者都已就绪，明确最低可回退版本 |
| 回退 | 恢复兼容的旧产物，保留全部业务记录；**不能用恢复旧数据库快照来回退代码** |
| 清理旧格式 | 旧记录完成迁移、旧责任能继续处理之后再清理，不按发布日期决定 |

"先让所有读者理解新格式，再启用新写法"是 AWS 的部署实践（[回滚安全](https://d1.awsstatic.com/builderslibrary/pdfs/ensuring-rollback-safety-during-deployments.pdf)）。Protobuf 的文档也提醒，线格式上安全的变更仍可能破坏应用语义，未知字段可能在 JSON 转换或逐字段重建时丢失（[proto3 指南](https://github.com/protocolbuffers/protocolbuffers.github.io/blob/689caf34961fbf2b3c72d2bb671414f716a5a720/content/programming-guides/proto3.md)）。所以兼容分四项分别管理：

| 项目 | 要求 |
| --- | --- |
| 传输与消息格式 | 双向可解析；中转不能丢弃关键字段 |
| 裁决语义 | 必须理解所要求的授权、条件和效果规则 |
| 持久记录 | 新程序能读旧记录；允许回退的旧程序能读回退时已有的记录 |
| 执行适配器 | 原尝试的参数、副作用声明和证据解释可以追溯 |

**未知的授权约束、未知的效果枚举值、不支持的证据格式，都不能按宽松的默认值执行。**新增的安全语义必须显式协商。"只支持当前版和上一版"可以作为新动作的接入窗口，但不能据此丢弃旧责任的回报：未收尾的责任可能比版本窗口更长。

适配器替换时，原尝试的声明快照不能被覆盖。能否安全重发，要同时检查原声明、当前实现和目标系统的实际保证；目标的幂等窗口已失效的，重新核对。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 发送方持久工作、接收方事实模块 | 查询原交接并保存原回执；标识、载荷和目标不变 |
| 进程崩溃 | 原事实模块和持久工作 | 从持久待办接替；已有开始记录的按"可能已发出"处理，先核对 |
| 重复请求 | 接收方持久工作 | 同标识同载荷返回原决定；不同载荷报冲突；重复的观察不重复计费 |
| 并发冲突 | 裁决域、账本、持久工作 | 原子检查对象版本和领取代次；旧提议作废；过期工作者不能覆盖权威状态 |
| 依赖不可用 | 依赖它的核心模块 | 保存等待原因；停止依赖该前提的新行动；恢复后查询原请求 |
| 迟到结果 | 原动作账本、预算、任务编排 | 持久接纳证据和真实用量；旧进程只能回报，不能直接覆盖状态 |
| 端侧断线 | 本机账本、网关与 SDK | 保留待传记录；等待新准入和无法证明的授权；重连按 4.2 核对 |
| 设备存储满或写入失败 | 本机持久工作、账本 | 接纳前拒绝；出口前无法登记就不发出；已发出的保留原开始记录，恢复后核对 |
| 手机被系统终止、电脑休眠 | 本机账本和宿主 | 下次运行从记录恢复；不依赖退出回调 |
| 单可用区丢失 | 存储与部署运维、核心模块 | 安全接替或停止新写；剩余可用区限速恢复，保持原责任 |
| 旧进程暂停后恢复 | 持久工作、出口闸门、账本 | 拒绝旧的权威写入；不假定旧请求已消失 |
| 设备重装、恢复过期备份 | 原账本、授权、部署运维 | 验证账本连续性；无法证明就冻结原责任，**新安装不能冒充原账本重发** |
| 撤权或删除时端点失联 | 授权、内容治理 | 在线的持有方停止使用；失联方的清理显示为待处理，不声明全部清理完成 |
| 版本不兼容 | 核心契约、部署或扩展管理 | 拒绝不理解的新行动；保留处理原责任的回报和核对路径 |

对于不可查询、非幂等的目标，效果未知可能长期无法自动收尾。这是 G1 的要求，不能用超时清理或重新派发来规避。

## 6 不变量落实

| 不变量 | 怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 尝试持久登记后崩溃，按可能已发出恢复；是否重发由账本决定 | 发送前后丢回执、终止进程，检查实际效果和重发次数 |
| G2 | 连接、接纳、回报成功都不直接关闭任务；核验权威账本的收尾状态 | 隐藏证据、延迟效果、断开原端点，成功关闭必须被拒 |
| G3 | R7 三处持久记录；网关和通知不代替接纳 | 每个持久化点前后崩溃 |
| G4 | 原意图包含条件、授权和预算；真实出口检查当前前提 | 旧版本、撤权、预算不足、失联都不能启动出口 |
| G5 | 网络、模型、嵌入、文件、设备出口都受闸门控制；扩展没有直接出口 | 在各宿主上尝试绕过 |
| G6 | 推理进程只能提出提议和证据 | 推理直接执行、伪造完成、写核心记录都失败 |
| G7 | 端点、进程、扩展凭据按能力和用户范围限定；升级不扩权 | 升级新增的权限在授权前不可用 |
| G8 | 本地使用和同步分别检查；失联时不把缓存当作当前授权 | 读取、保存、同步、行动四类撤销，以及分区期间的使用 |
| G9 | 治理记录和清理进度持久保存；旧缓存和旧快照不能重新启用内容 | 多端删除、离线端重连、旧备份恢复 |
| G10 | 按实际计费来源唯一结算；不用动作标识吞掉真实的重复收费 | 重复账单、取消后账单、迟到更正、同一动作的多次真实收费 |
| G11 | 任务负责方和执行端点固定，只替换工作者 | 断线、超时、可用区故障、升级后归属和尝试标识不变 |
| G12 | 用户身份贯穿存储键、凭据、队列和配额；重负载用户受限 | 跨用户标识注入、路由错误、单用户洪峰、费用归属 |

R7 在同进程和跨进程部署下使用相同的故障测试；R2 通过出口覆盖验证；R3 通过写入权限验证；R6 通过构建依赖检查。

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 默认云端持有任务 | 集中管理多设备、长任务和用户级裁决事实 | 新准入依赖云端；失联时能推进的范围有限 |
| 端侧持有本机账本和出口 | 本机事实靠近真实执行，隐私数据可留在本机 | 端侧需要可靠的存储和恢复 |
| 三可用区同步持久提交 | 单区故障后已确认的责任仍在 | 跨区延迟、备用容量、运维成本 |
| 前提无法证明时等待 | 保持 G4、G8，不靠缓存猜测 | 离线体验受限 |
| 保留旧责任的兼容路径 | 升级后仍能核对原动作 | 旧格式的支持期可能长于新功能的支持窗口 |
| 控制和恢复分别配额 | 补传时仍能保存取消和撤销 | 调度和容量模型更复杂 |

比较过的方案：

| 问题 | 方案 | 结论 |
| --- | --- | --- |
| 可用区 | 单可用区 | 适合开发和早期部署，不能宣称可用区容灾 |
| | 多可用区异步主备 | 从落后副本继续裁决会丢失已确认的责任；只能作副本和灾备，不能默认自动接替写入 |
| | **三可用区同步持久提交** | 生产默认 |
| | 多地域强一致 | M6 之后有地域恢复需求时再评估 |
| 端侧内容 | 端侧只做交互 | 本机文件、设备和端侧专有内容难以满足 C2、C4、C5；可作为无本机能力的客户端 |
| | **端侧部署核心的执行部分** | 默认 |
| | 端侧部署完整核心 | 作为明确选择的独立部署方案 |
| 升级 | 云端和全部端点同时升级 | 离线端和长任务难以同步 |
| | **契约版本 + 语义能力协商 + 持久格式迁移** | 采用 |
| 端云传输 | **HTTPS 命令/查询 + 可选长连接**；双向 RPC 流；持久消息系统 | 起步优先评估第一种（便于弱网恢复）；任何传输都执行 R7 |
| 工作通知 | **持久待办扫描为恢复依据**，消息提示作加速 | 采用 |
| 云端存储 | PostgreSQL 同步复制；共识复制的事务存储 | 见[数据与存储](data-and-storage.md#72-比较过的方案) |

用户分片、任务负责方固定、执行端点连续性的判据、生产提交和故障提升的保证，都是难以撤回的决定，正式采纳时应分别写成 ADR。

## 8 待定事项

### 8.1 在线规模的估算方法

以下数字**只用于展示方法**，不是吞吐结论。稳定系统中的平均在途数量可以用 Little 定律 `L = λW` 估算（[Little，1961](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383)），但它不保证尾延迟和突发。

假设十万在线用户、每人一条连接、2% 的用户同时有任务、活跃用户每秒 0.02 个任务、每任务 3 次模型调用和 5 个其他动作、模型调用平均在途 8 秒、每动作 6 次持久提交、每任务另加 3 次：

| 资源 | 估算式 | 示例 |
| --- | --- | --- |
| 连接数 | 用户 × 每人连接数 | 100,000 |
| 心跳 | 连接数 ÷ 周期 | 30 秒周期约 3,333 次/秒 |
| 连接内存 | 连接数 × 单连接内存 | 64 KiB/连接约 6.1 GiB，另计运行时和缓冲 |
| 任务到达率 | 用户 × 活跃比例 × 每人到达率 | 40 任务/秒 |
| 模型调用 | 任务率 × 3 | 120 次/秒，平均在途约 960 |
| 全部动作 | 任务率 × 8 | 320 动作/秒 |
| 持久提交 | 动作率 × 6 + 任务率 × 3 | 约 2,040 次/秒，另计内容、控制、核对、费用更正 |
| 模型令牌 | 调用率 × 每次令牌 | 输入 2,000、输出 400 时，分别约 24 万、4.8 万令牌/秒 |
| 单区重连 | 丢失连接数 ÷ 恢复窗口 | 丢失三分之一、分散到 60 秒，约 556 次握手/秒 |

只看业务 QPS 会漏掉连接维持和建立的成本，多层重试还会放大负载（[Google SRE 第 21 章](https://sre.google/sre-book/handling-overload/)）。所以连接、握手、业务、核对和补传分别计算；传输恢复集中退避，副作用重试由动作账本按 G1 决定。逻辑提交次数不等于磁盘同步次数，要分别测量提交延迟、日志字节、同步复制和存储吞吐。

每个资源池的实例数取各约束的最大值：

```text
实例数 ≥ max(连接需求 / 单实例连接容量,
             CPU 需求 / 单实例 CPU,
             内存需求 / 单实例可用内存,
             网络需求 / 单实例网络,
             持久写需求 / 单实例持久写容量)
```

三个可用区均匀承载、要求损失一个区后利用率不超过 `u` 时：`总能力 ≥ 峰值需求 × 1.5 / u`。例如 `u = 60%`，总能力至少是峰值的 2.5 倍，另计升级时退出的实例。恢复积压另算：`补传完成时间 ≥ 积压量 / (恢复处理能力 − 正常到达率)`，分母必须为正。连接握手、效果回报、控制命令、内容同步使用不同的额度，避免补传耗尽取消和撤销的通道。

## 9 M1 范围

M1 可以全部同进程运行。部署专题在 M1 首先要保证：**以后拆进程时，故障语义不需要重做**。

| 范围 | M1 实现 | 推迟 |
| --- | --- | --- |
| 进程与存储 | 单用户、单进程；裁决域和账本域显式分开 | 生产进程池、用户分片、跨区复制：M6 |
| 持久工作 | 完整的命令去重、回执、待办、领取和过期写入保护 | 不能推迟 |
| 跨域交接 | 同进程也实现 R7 的意图、接纳、回执，并分别提供查询 | 不能用内存调用代替 |
| 版本字段 | 持久记录包含契约、格式和适配器版本；不兼容时停止恢复 | 端云协商：M3；扩展发布：M4 |
| 平台服务 | 不实现网关、扩展管理和评测 | 分别在 M3、M4、M5 |
| 端侧与离线 | 本地运行可以验证恢复；不声明已完成端云离线协同 | 端云、离线、重连和 V2：M3 |

M1 的退出证据：回执丢失、进程重启、取消与执行竞争、迟到效果、不可查询的动作都通过测试，并且能从基础运行记录解释每个恢复决定。M1 **不宣称**端云协同、多可用区或十万在线已经达成，也只用于受控测试。

## 10 测试要点

所有用例通过公开接口操作，并用目标系统独立记录的真实效果验证，不只检查核心自己报告的状态。

| 用例 | 必须成立 | 对应 |
| --- | --- | --- |
| 准入提交后丢回复，重复原命令 | 同一个决定、同一个动作；确认不被重复消费 | G3、G4 |
| 账本接纳后丢回执，重启双方 | 查询原交接即可恢复，没有新责任 | G3、G11、R7 |
| 出口开始登记后、实际调用前终止 | 不按崩溃位置猜测"未执行"；按原尝试恢复 | G1、G11 |
| 外部已生效、回报保存前终止 | 先核对；不可查询的非幂等目标保持未知 | G1、G2 |
| 暂停旧进程到领取过期，新进程接替后再恢复旧进程 | 旧的权威写入被拒；旧请求可能迟到，但不触发重复动作 | G1、G11 |
| 在准入、接纳、开始登记、发送各位置取消 | 顺序可解释；未开始的封闭；在途的继续核对 | C7、G2、G11 |
| 云端撤权，端侧尚未收到 | 缺少当前授权证明时停止新出口 | G4、G8 |
| 删除后重连，或恢复旧快照、旧索引 | 内容不复活；清理未确认时不显示完成 | C2、G9 |
| 手机后台窗口结束、通知丢失、Doze、内存压力终止 | 责任不丢；唤醒后恢复原账本，不直接重发 | C5、G3、G11 |
| 磁盘满、同步写失败、内存限额 | 没持久化就不确认，无法登记就不发出 | G3、G4 |
| 新安装试图继续旧端点的动作 | 没有连续性证明就冻结原责任，不改派 | G11 |
| 损失一个可用区；旧主仍存活；尝试提升落后副本 | 已确认记录不丢；只有安全的一侧能写，否则停止新写 | G3、G11 |
| 未知授权字段、未知效果枚举、经 JSON 中转 | 安全语义不降级；旧责任仍能回报和核对 | A4、G4 |
| 新格式写入后回退；迁移中断；旧程序恢复未知动作 | 业务事实不回退；最低可回退版本生效 | C6、G1、G11 |
| 插件直接访问网络、文件、设备；辅助模型调用绕过 | 全部旁路被阻止并可诊断 | G5、R2、R5 |
| 跨用户标识、错误路由、单用户洪峰 | 数据、费用和授权不串用户；重负载用户被限制 | G12 |
| 十万连接加真实业务；单区丢失 + 补传 + 取消；过载后回落 | 正确性保持；控制命令能持久保存；积压能消化 | C5、C8、G12 |

分阶段执行：M1 覆盖主线持久化点和动作故障；M2 加入治理和结算；M3 验证端云和手机；M4 验证替换与扩展；M6 验证容量、用户隔离和故障域。
