**核心记录提供可以恢复的事实依据；指标、日志和追踪提供诊断视图。**用户看到的"发生了什么"取自负责方的记录，不依赖遥测是否完整。

本专题回答四个跨模块的问题：各类信号怎样分工；怎样向用户和开发者解释现状；怎样测量服务质量而不让指标"变好看"；怎样告警和排查。关联记录本身的字段、接纳流程和 OpenTelemetry 投影见[运行记录](../core/trace/README.md)，这里不重复。

有几种做法必须防止：

| 反例 | 为什么危险 | 防线 |
| --- | --- | --- |
| 从日志或 span 恢复动作 | 采样、队列和进程故障会让记录缺失 | 从动作账本恢复，诊断信号只补充解释 |
| 以 HTTP 200 标记完成 | 接收成功不等于实际效果，还可能是部分拒绝 | 完成判断只读 G2 所需的证据 |
| 用"进入次数 − 退出次数"维护积压 | 丢事件、重复事件、重启都会让计数漂移 | 用账本快照或可以重建的投影计算 |
| 只统计已经结束的核对 | 长期未解决的动作被排除，指标反而变好 | 时长分布和未完成积压一起报告 |
| 只在 Collector 里脱敏 | 敏感信息已经进入 SDK、队列或本地文件 | 在来源端先做字段白名单 |
| 遥测上传自行重试 | OTLP 本身不证明幂等 | 由动作账本依据接收方能力决定 |
| 告警被确认就认为故障恢复 | 确认通知不改变动作效果 | 告警、故障状态和效果分别处理 |

## 1 职责与边界

观测与诊断不新增裁决模块，也不新增可替换的核心。关联查询、诊断投影和告警规则的求值归入运行记录的实现；权限、内容策略和动作效果仍由原负责方持有。

| 负责方 | 本专题对它的要求 | 分界 |
| --- | --- | --- |
| 任务编排 | 提供条件版本、准入决定、阻塞原因、控制状态、完成门禁和 Result 引用 | 观测不得修改任务状态或重做完成裁决 |
| 会话 | 提供用户输入、确认、取消请求和任务关联 | 显示或通知不算用户确认 |
| 动作账本 | 提供执行尝试、效果、核对进展、迟到生效的可能 | 日志和追踪不得写效果 |
| 授权、预算 | 提供当前许可、拒绝原因、用量和结算状态 | 诊断模式不扩权；指标不结算费用 |
| 内容治理 | 管理诊断内容的来源、用途、位置、保留、派生和清理 | 运行记录没有隐私豁免 |
| 运行记录 | 持久关联、授权查询、解释视图、可重建的统计和诊断信息 | 不成为业务事实的第二个写入方 |
| 持久工作 | 管理关联交接和诊断任务的回执、领取和恢复 | 不用内存通知承担责任 |
| 出口闸门 | 覆盖遥测上传、诊断包上传和外部告警通知 | 抑制递归埋点不得绕过 R2 |
| 交互适配器 | 展示当前事实、证据、缺口和可选的下一步 | 不从界面连接状态推断任务完成 |

可替换部分通过核心契约提交有限的诊断信息，不得提交有裁决效力的状态；核心契约不包含第三方 SDK 的对象（R6）。

## 2 对象与状态

### 2.1 信号分工

| 数据 | 回答什么问题 | 完整性要求 |
| --- | --- | --- |
| 核心事实 | 接下了什么责任；动作效果是什么；任务能否成功 | 必须持久，由负责方写入 |
| 运行记录（基础关联） | 哪个任务、提议、授权、动作和费用互相关联 | **不可采样**，可以恢复 |
| 指标 | 多快、多大、积压多少、是否饱和 | 明确统计口径、覆盖范围和缺失 |
| 日志 | 某个局部步骤出现了什么可诊断的情况 | 结构化、有额度；允许明确报告丢失 |
| 追踪 | 时间花在哪里；调用和异步步骤怎样关联 | 可以采样；不得当作完整的责任历史 |

这种分工的依据：Dapper 以低开销、广覆盖为目标，靠采样和公共库埋点实现追踪，主要服务开发和运维诊断（[Dapper](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/)）。OpenTelemetry 的 SDK 在采样决定为 `DROP` 时丢弃 span 的属性和事件，批处理队列满时也会丢 span（[追踪 SDK，v1.51.0](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.51.0/specification/trace/sdk.md)）。所以**"没有执行 span"不能证明"动作没发生"**，出错的追踪也不保证存在。

**长任务不用一个持续数天的 span。**任务标识保持稳定，每次准入、执行尝试、核对查询和恢复活动各用一条短追踪，通过关联引用和 Span Links 连接（[Links](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.51.0/specification/overview.md#links-between-spans)）。恢复后追踪可以重新开始，但任务、动作和尝试的标识不变（G11）。

### 2.2 诊断对象

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 诊断条目 | 信号类型、受控事件码、关联引用、有限的属性、采样信息、丢失信息、是否事后重建 | 没有裁决效力；持久化时登记内容来源和派生 |
| 采集配置 | 配置版本、范围、许可引用、内容策略、允许的字段、采样率、资源额度、有效期 | 配置不得自行授予许可；每次使用检查当前授权 |
| 用户解释视图 | 任务状态、条件与证据、请求发出情况、效果、迟到可能、阻塞原因、费用状态、可选的下一步 | 每项结论附负责方和版本；证据不可读时如实标注 |
| SLI 定义 | 版本、事件集合、开始与结束条件、合格规则、窗口、范围、缺失和时钟处理 | 定义改变后不得和历史数据混算 |
| 统计投影 | 来源版本、处理游标、去重信息、统计值、覆盖范围、更新时间 | 可以重建；不得裁决任务或动作 |
| 导出清单 | 批次和交接标识、内容引用、用途、目标、许可、预算、导出任务和动作 | 一个批次只包含同一授权和隔离范围的数据 |
| 告警记录 | 规则版本、范围、证据、评估时间、资料完整度、状态、通知动作 | 通知回执不代表故障解决 |

解释要区分**任务关闭时固定的 Result** 和**后来核对得到的当前效果**：迟到的结果更新动作账本，解释里追加展示，不改写旧 Result。

### 2.3 状态

| 对象 | 状态 |
| --- | --- |
| 关联查询的完整度 | 完整 / 存在缺口 / 来源暂不可用；来源恢复后补齐 |
| 可选的诊断条目 | 可采集 → 已缓冲 / 已保存 / 因策略丢弃 / 因额度丢弃 |
| 导出进度 | 待派发 → 派发中 → 回执已证实 / 部分回执 / 效果未知（效果由动作账本写入） |
| 告警 | 正常 → 待观察 → 触发 → 恢复；资料不足时保留之前的状态并标明盲区 |

"部分回执"只记录已知的计数，不得把每条诊断数据逐一标为已接纳。

## 3 接口

关联的接纳和查询接口见[运行记录 3](../core/trace/README.md#3-接口)。本专题补充：

| 接口 | 成功含义 | 错误 | 幂等 |
| --- | --- | --- | --- |
| 查询解释 | 读到了声明范围内的事实、解释、完整度和更新时间 | 无权、来源不可用、证据不可读 | 无副作用 |
| 提交诊断条目 | `已缓冲`、`已保存`，或明确的丢弃原因；**缓冲不代表持久成功** | 字段被禁止、策略过期、额度、格式不支持 | 有稳定标识时去重；没有标识的重复必须反映在覆盖信息里 |
| 设置采集配置 | 配置已持久；**不代表许可已扩大** | 授权不足、版本冲突 | 原命令去重 |
| 创建诊断包或导出任务 | 本地包的持久清单，或导出任务的回执；远端是否完成另查动作效果 | 内容不可用、权限不足、预算不足、目标能力不满足 | 同命令固定清单 |

共同要求：超时不解释为命令未提交；查询不泄露其他用户的对象是否存在；后端不可用时返回缺失和陈旧程度，**不得返回"未知积压为零"**；"已缓冲""目标已接受""目标已持久接纳""清理已完成"用不同的回执字段。

## 4 关键流程

### 4.1 生成用户解释

1. 检查当前的读取授权和用途；
2. 读取任务编排的任务、控制和 Result；
3. 按关联引用读取动作账本、授权、预算和允许访问的证据；
4. 检查引用版本和因果关联；无法形成完整视图时标注缺口，**不宣称取得了跨事务域的原子快照**；
5. 用确定性模板生成说明，保留事实、证据、未知项、阻塞原因和下一步；
6. 保存解释或诊断包时，作为派生内容登记；单次读取不自动授予保存权限。

用户解释和开发者诊断回答不同的问题：

| 视图 | 必须回答 | 数据来源 |
| --- | --- | --- |
| 用户解释 | 系统接下了什么；哪些请求已发出；效果确认到什么程度；为什么在等；费用是否待确认；用户可以做什么 | 当前核心事实和授权可读的证据 |
| 开发者诊断 | 哪个版本、哪个步骤、哪次尝试出了问题；交接是否完成；时间和资源花在哪里；哪些数据缺失 | 核心关联，加上授权范围内的日志、追踪和资源测量 |

用户解释的例子：

> 取消已保存。此前有一项请求已经发出，目标是否执行尚未证实，系统仍在核对。目标暂时无法访问，下一次查询还没有完成，因此目前不能确认全部动作已停止，也不能安全地重试这项请求。

开发者视图可以同时列出"目标已处理但回执丢失""目标还没处理"等假设，但必须标为假设。**不让推理直接总结日志并给出状态**，那样容易违反 G1、G2、G6；以后可以用推理改善措辞，但状态、证据引用和未知项保持原结构，生成过程本身也遵守 G4、G5、G8、G10。

### 4.2 指标与追踪

- 核心事实提交后生成与责任相关的统计；投影的处理游标和统计更新原子提交，重复事件不重复计数；
- 定期用负责方的快照校验积压，重建发生漂移的投影；
- 陈旧、丢失、采样和基数超限的信息随诊断输出一起展示；
- **用户、任务、动作标识、完整 URL、文件路径不作为全局指标标签。**Prometheus 官方反对把无界集合放进标签；直方图可以跨实例聚合，预计算的分位数通常不能（[标签](https://github.com/prometheus/docs/blob/533c220d60b95b77af8098c92fbce29690b0f3bc/content/docs/practices/naming.md)、[直方图](https://github.com/prometheus/docs/blob/533c220d60b95b77af8098c92fbce29690b0f3bc/content/docs/practices/histograms.md)）。个例分析通过授权查询完成。

**采样策略：**基础关联全量；诊断追踪按固定比例头部采样；需要时开启有期限、有额度的定向诊断。尾部采样需要先缓冲数据，对长任务尤其不合适，不作为默认。定向诊断恢复不了之前已经丢弃的 span，事后查询必须读核心记录，并区分"实时采集"和"事后重建"。

### 4.3 SLI 与 SLO

**不变量是硬约束，不设允许违约的错误预算。**服务质量的 SLO 单独定义。以下数值都是**待验证的假设**，不是上游目标，也不是生产承诺：

| 指标 | 测量口径 | 初始候选目标 |
| --- | --- | --- |
| 准入延迟 | 原准入命令进入核心，到准入或拒绝决定持久提交；包括排队和提交，不包括推理和用户确认的等待 | 30 天内 99% ≤ 100 ms（本地）；云端 ≤ 500 ms |
| 准入可用性 | 合格的原命令中，按时得到确定决定的比例；正确的授权拒绝算正常决定 | 99.9% |
| 未知效果积压 | 从账本快照计算：总数、可核对数、不可查询数、年龄分桶、最长年龄 | 可核对类超过 5 分钟的比例 ≤ 1%；样本少时逐个评估 |
| 核对启动时延 | 动作具备核对条件，到首次实际发出查询；持久领取不算发出查询 | 99% ≤ 30 秒 |
| 核对完成时长 | 首次未知，到效果确定且满足收尾条件；包括依赖故障的等待 | 可查询类 99% ≤ 5 分钟 |
| 解释更新时延 | 负责方提交新事实，到在线交互端能读到对应版本 | 本地 99% ≤ 1 秒；跨端 ≤ 5 秒 |
| 关联交接延迟 | 来源事实提交，到运行记录持久接纳 | 99% ≤ 5 秒 |
| 可选观测的开销 | 与保留同样核心可靠性记录的基线比较 | 额外 CPU ≤ 5%，准入 p99 增量 ≤ 10% |

**计数规则：**

1. 原命令、原动作只计一次，网络重传不扩大分母；
2. 到期仍未得到决定或未完成核对的对象，计为未按时完成；**不得只统计已结束的样本**。例如 100 个未知动作中，90 个在 1 秒内核对完成、10 个始终没解决：只看完成样本，尾延迟很好看；按全部动作计算，按时解决率只有 90%；
3. 核对完成 SLO 的适用范围在动作进入未知时固定，不得在故障后改成"不覆盖"来改善结果；
4. 撤回、取消、断网和目标故障分别展示原因，总等待时长保留；
5. 不可查询、不幂等的动作不承诺自动确定效果，但要持续展示责任和未知项；
6. 无样本、采集缺失、时钟无法判定分别报告，**都不算健康**；
7. 不跨端直接相减未经校验的时间戳；同一进程内用单调时钟，跨重启的年龄结合持久时间和误差范围；
8. 任务效果、契约符合性、耗时和费用分别报告（C8）。

服务响应、任务效果和契约符合性分开记录。Google SRE 区分面向症状的监测和内部诊断，并指出 HTTP 200 也可能对应错误的结果（[SRE 第 6 章](https://sre.google/sre-book/monitoring-distributed-systems/)）；接口成功率不得代替 C4、G2。

### 4.4 告警与排查

| 类别 | 触发 | 首要处理 |
| --- | --- | --- |
| 契约异常 | 核心发现没有准入的尝试、错误的完成、责任记录缺失 | 负责方停止依赖错误前提的新推进，保留现场 |
| 未知效果风险 | 动作账本出现未知，或超过按能力定义的年龄阈值 | 查原动作、目标能力、最近一次核对、当前授权 |
| 服务质量下降 | 准入、核对或解释的 SLO 消耗错误预算 | 查排队、存储、执行宿主和目标依赖 |
| 观测盲区 | 来源陈旧、关联积压、丢弃或基数超限 | 恢复观测，期间明确显示"无法判定" |
| 内容清理积压 | 内容治理仍有未确认的持有方 | 阻止继续使用，逐个核实持有方 |

**低流量和高流量用不同的规则。**多窗口、多燃烧率告警适合高流量服务：`燃烧率 = 窗口内未达标比例 / (1 − SLO)`，可以从"1 小时和 5 分钟同时超过 14.4 倍""6 小时和 30 分钟同时超过 6 倍"开始验证。但低流量会放大单次失败的比例，合成流量也可能掩盖真实用户的问题（[SRE Workbook 第 5 章](https://sre.google/workbook/alerting-on-slos/)）。个人场景优先用逐个动作的风险、积压年龄和独立探针，不得为了减少通知而掩盖未知效果。

告警只提出检查或操作建议；实际的核对、取消、补偿和配置变更仍通过负责方的接口和授权执行。

**排查顺序：**

1. 确认用户、任务、负责方和诊断授权；
2. 查看核心的当前事实，确认是否可能已产生外部效果；
3. 检查观测完整度和来源版本；
4. 沿原命令、交接、准入、尝试、出口、效果和核对定位缺口；
5. 比较实现版本、配置、依赖和资源变化，提出可验证的假设；
6. 通过负责方执行有授权的核对或修复；
7. 用负责方的记录验证恢复——**告警消失不能单独证明恢复**。

### 4.5 遥测的隐私与清理

| 数据 | 默认处理 |
| --- | --- |
| 状态码、受控的错误类别、耗时、实现版本 | 在允许保存的范围内采集，有额度和保留期 |
| 用户、任务、动作、端点和追踪标识 | 作为受控的关联信息；跨端传输必须有同步授权 |
| 提示、工具参数、结果正文、截图 | 默认不进入日志或 span，通过内容引用查询 |
| 异常文字、网络响应正文、文件路径、配置 | 来源端白名单过滤；不得让无约束的字符串自动进入遥测 |
| 出口凭据、密钥、令牌 | 不记录 |
| 与用户相关的统计和诊断包 | 登记派生关系，支持停止使用、删除和验证 |

几个需要注意的来源事实：

- OpenTelemetry 的 GenAI 语义约定把输入、输出、工具参数和结果设为显式开启的内容属性，但**内容上传钩子可以独立于这些开关和采样运行**（[GenAI spans，v1.38.0](https://github.com/open-telemetry/semantic-conventions/blob/v1.38.0/docs/gen-ai/gen-ai-spans.md)）。只关闭提示属性不够，上传钩子、异常文字和其他出口都要治理；
- W3C Trace Context 禁止在 `traceparent`、`tracestate` 里放个人或敏感信息，并指出关联请求本身就可能带来隐私风险（[Trace Context](https://www.w3.org/TR/2021/REC-trace-context-1-20211123/#privacy-considerations)）。追踪标识用随机值，标识及其关联关系仍受用途、同步和访问限制；散列或替换后的标识仍可能关联到同一用户，继续视为受控数据；
- Prometheus 的删除接口使用墓碑，数据可能继续留在磁盘等待清理（[删除接口](https://github.com/prometheus/prometheus/blob/804c49d58f3f3784c77c9c8ec17c9062092cae27/docs/querying/api.md#delete-series)）。**后端返回"删除成功"不足以证明 G9 的清理完成**；没有可验证清理能力的后端，不接收受治理的诊断数据。

清理流程与[运行记录 4.5](../core/trace/README.md#45-保留撤回与删除) 一致：先停止使用，再清理日志、追踪、队列、索引、解释缓存、诊断包和受影响的统计；持有方完成实际清理后回报（"收到清理通知"不是完成）；离线持有方未确认时保持"清理未完成"；恢复备份或收到迟到的诊断数据时，先检查当前治理状态。"已经聚合"不得自动成为删除豁免：保留受治理的贡献以便重算，或删除受影响的聚合。

### 4.6 远端导出

**OTLP 的回执不是持久接纳回执。**OTLP 只规定客户端与服务端之间的单跳交付，回执丢失后重发可能产生重复（[OTLP v1.7.0](https://github.com/open-telemetry/opentelemetry-proto/blob/v1.7.0/docs/specification.md#request-acknowledgements)）；部分成功仍返回 200，客户端不能重试原请求（[部分成功](https://github.com/open-telemetry/opentelemetry-proto/blob/v1.7.0/docs/specification.md#partial-success-1)）。Collector 的内存队列在入队成功后就可以返回，不等后端保存（[queue_sender.go](https://github.com/open-telemetry/opentelemetry-collector/blob/c87bda5bd0c3f8b18dbef08f6029361f35d58bc4/exporter/exporterhelper/internal/queue_sender.go#L187)）；文件存储扩展默认 `FSync=false`（[factory.go](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/994853d135dced340df40e762a6443a20cf00def/extension/storage/filestorage/factory.go#L51)）。"开启了磁盘队列"不足以证明不丢数据。

因此远端导出按普通的对外动作处理：

- 导出由事先创建、归属明确的诊断任务负责；不得事后把原业务的未知动作改派给它；
- 保存导出清单和意图，再经准入、动作账本和出口闸门执行；实际出口检查当前授权、内容策略和预算；
- 目标支持稳定的批次去重和查询时，按原交接恢复；部分成功时解析响应正文，不重试原批次；回执丢失且目标既不幂等也不可查询时，保持未知；
- 导出本身产生的准入、尝试、费用和基础关联照常持久记录，但不再进入同一条导出流，避免递归；
- 本地核心事务存储的写入属于可信基础设施 I/O；主动的远端导出和外部通知都是出口。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 原业务回执丢失 | 原命令负责方、持久工作 | 查询原命令；不用日志猜测，不提交新责任 |
| 关联接纳回执丢失 | 来源负责方、运行记录 | 查询原交接；同标识重发被去重 |
| 导出回执丢失 | 动作账本 | 查原导出动作；目标无幂等或查询能力时保留未知 |
| 进程崩溃 | 持久工作、原事实负责方 | 接替者恢复原待办和原责任；运行记录从来源补齐关联 |
| 可选的诊断缓冲丢失 | 采集实现 | 报告诊断缺失；核心事实和责任不变 |
| 重复、乱序的关联 | 运行记录 | 去重，按来源版本处理；旧投影不覆盖新事实 |
| 核心存储不可用 | 原事实负责方 | 不确认新责任；解释返回"无法判定"，不得返回零积压 |
| 遥测后端不可用 | 采集实现、导出任务 | 限额、降级、报告缺失；基础关联保留；重试由账本决定 |
| 迟到的结果 | 动作账本、预算 | 按原动作、尝试和计费来源接纳；解释展示新事实，不改写固定的 Result |
| 迟到的日志或旧导出 | 内容治理、运行记录 | 校验当前治理状态和来源版本；删除后拒绝复活 |
| 端侧断网 | 端侧原负责方 | 保留本机记录；观测不接管任务；重连后先检查当前授权再补传 |
| 删除与导出竞争 | 内容治理、授权、出口闸门 | 尚未发出的导出被阻断；已发出的按实际效果处理并跟踪远端清理 |

## 6 不变量落实

观测负责支撑和如实呈现，不替代原模块的保证。

| 不变量 | 怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 效果只读账本；缺少遥测不解释为未发生；导出重试也检查目标能力 | 丢弃全部追踪，原动作仍然未知，不被不安全地重试 |
| G2 | "成功"只呈现任务编排的门禁结果；证据缺失和未知动作显式展示 | HTTP 成功、日志成功、推理声明都不得改变任务状态 |
| G3 | 关联意图随来源事务提交；接纳回执持久化后才返回 | 在来源提交、关联接纳、回执记录前后杀进程和丢回执 |
| G4 | 诊断上传和通知同样绑定条件、授权和预算，并在实际出口复核 | 未准入的导出、旧许可、预算不足都被拒绝 |
| G5 | 覆盖 exporter、上传钩子、通知和辅助调用；抑制递归只影响可选诊断 | 捕获所有外部调用，核验每次都有有效的出口凭据 |
| G6 | 用户状态来自核心事实；推理最多改善措辞 | 注入伪造的"已完成"诊断文本，状态不变 |
| G7 | 诊断范围受来源许可约束；扩展不得开启越权的内容采集 | 子任务、插件或诊断配置扩大范围时被拒绝 |
| G8 | 读取、保存、同步和导出分别检查当前许可 | 允许读取但禁止保存或同步时，相应操作失败 |
| G9 | 诊断派生物登记并清理；旧数据和恢复的备份不得复活 | 删除覆盖队列、视图、诊断包、索引、聚合和迟到数据 |
| G10 | 费用只取预算记录；遥测计数不充当账单；导出费用也记账 | 重复 span、重复用量回报不重复计费；迟到账单仍可见 |
| G11 | 任务和动作标识跨恢复稳定；追踪可以变化 | 取消、断网、重启后，未知动作仍由原负责方承担 |
| G12 | 授权查询、队列、额度和导出范围按用户隔离 | 越权查询和混合导出被拒绝；单用户日志洪泛不影响其他用户 |

运行中"没有发现违规"和一致性测试"已覆盖并通过"分开记录；**绿色的仪表盘不能证明不变量成立**。

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 基础关联不可采样，诊断遥测可以降级 | 故障后仍能解释责任和效果 | 承担持久关联和恢复的成本 |
| 用户解释采用确定性结构 | 可追溯、低延迟、容易验证 | 不追求自由生成的丰富叙述 |
| 端侧内容默认留在端侧，远端只同步获授权的数据 | 符合 C2、G8、G9 | 云端诊断可能有明确的缺口 |
| 不把各种标识作为指标标签 | 控制基数和资源 | 个例分析要通过授权查询 |
| 不可查询的未知动作不承诺收敛时限 | 保持 G1、G11 | 部分任务要等人工提供证据 |
| 没有清理能力的后端不接收受治理数据 | 避免无法履行 G9 | 限制部分观测产品的接入 |
| 遥测出口走完整的准入 | 保持 G4、G5、G10 | 比 SDK 自动上传复杂 |

比较过的方案：

| 问题 | 方案 | 结论 |
| --- | --- | --- |
| 事实与信号 | 日志或追踪作为唯一记录 | 排除：缺失会破坏 G1、G3、G11 |
| | 把完整业务状态同步复制到观测后端 | 不建议：形成第二个事实写入方，增加 G8、G9 风险 |
| | **核心持有事实，运行记录保存关联，遥测生成诊断视图** | 采用 |
| 关联的可靠性 | 业务提交后直接发日志 | 只用于可选诊断：存在丢失窗口 |
| | 业务等待远端遥测后端确认 | 排除：把核心可用性绑定到诊断依赖上 |
| | **负责方事务内保存关联和待交接工作，再按 R7 交给运行记录** | 采用 |
| SLO 来源 | 只统计网络状态和返回码 | 作辅助 |
| | 从采样追踪估算全部 SLO | 不建议：未完成和未采样的动作会消失 |
| | **负责方记录计算责任相关的 SLI，运行时测量资源和局部耗时** | 采用 |
| 隐私控制 | Collector 后置黑名单脱敏 | 排除为主要防线 |
| | **来源端字段白名单 + 内容治理 + 当前授权 + 派生清理** | 采用 |
| 存储 | **关联、回执、游标放核心事务存储，诊断视图可重建** | M1 首选 |
| | 诊断数据放受治理的本地分段文件 | 端侧低资源环境可选 |
| | 另设日志、时序和追踪后端 | M6 规模化时的候选；后端必须满足访问、用途、清理和隔离要求 |
| 远端协议 | **本地核心查询接口** | M1 首选 |
| | 普通 OTLP 接收端 | 诊断互操作时有条件采用 |
| | **R7 持久交接接口承接，再映射到 OTLP** | 跨端可靠交接时采用 |

基础关联的持久职责、远端观测的接收契约、用户相关聚合的清理方式，正式采纳前必须写成 ADR。

## 8 待定事项

| 事项 | 验证或决定方式 |
| --- | --- |
| 候选 SLO 数值是否适合个人场景 | 固定负载、实现版本和故障比例，测量本地与云端的分布；在 `verification/capacity.md` 中固定事件集合、阈值、缺失和时钟口径 |
| 基础关联与可选诊断的存储开销 | 测量每个任务的记录数、大小、保留期和积压上限 |
| 候选后端能否查询 Links、清理派生数据、隔离用户 | 后端一致性测试，不看产品功能名称 |
| 统计投影的重建时间 | 全量恢复、游标回退和重复事件实验 |
| 时钟误差能否支持跨重启的年龄告警 | 注入时钟前跳、后跳和长期离线 |
| 远端的接纳、最终保存和清理回执能否明确区分 | 固定接收端协议，做故障注入 |
| 统计聚合何时算脱离了可识别内容 | 与[内容治理](../core/content/README.md)共同确定哪些统计仍属派生内容 |

## 9 M1 范围

M1 实现**本地、可恢复的基础观测**，不需要 Collector、独立的观测平台或远端导出。

| 内容 | M1 做到 | 推迟 |
| --- | --- | --- |
| 关联 | 任务、条件、提议、授权、预算、动作、尝试、效果、核对、Result 的基础引用和版本；R7 交接、去重、按原回执查询、崩溃恢复 | 子任务和外部 Agent 的关联：M4 |
| 用户解释 | 本地查询或最简界面；展示未知、取消已保存、核对等待和证据缺口 | 丰富界面和端云呈现：M3 |
| 开发者诊断 | 受控错误码、来源版本、实现版本、交接和尝试链 | 全功能日志检索和追踪后端：按需 |
| 指标 | 准入耗时、未知数量和年龄、核对进展、关联积压、诊断丢弃和陈旧程度 | 多用户 SLO 和生产燃烧率告警：M6 |
| 追踪 | 可选的本地短活动耗时 | 跨端 Links 和完整的追踪互操作：M3–M4 |
| 隐私 | 默认不复制正文、提示、参数、截图和凭据；持久派生物记录来源 | 完整用途细分和删除传播：M2 |
| 告警 | 本地的风险和盲区状态，给出排查指引 | 外部通知和远端诊断包：具备授权和出口契约之后 |

M1 不为了"预备诊断"而采集大量原始内容。M1 的退出证据至少包括：

- 重启后能查到原任务、原动作、原尝试和未完成的交接；
- **遥测全部丢失时**，未知效果、责任归属和完成门禁仍然正确；
- 取消与执行竞争、迟到结果、不可查询动作的解释与核心记录一致；
- 指标明确覆盖未完成的对象，缺失不显示为零；
- 所有实际出口（包括辅助调用）遵守 G4、G5；
- 测试报告附环境、版本、故障点和测量口径；文档本身不算验收证据。

## 10 测试要点

| 用例 | 必须成立 | 对应 |
| --- | --- | --- |
| 在来源事务提交前后中断 | 未提交不确认责任；已提交可以按原命令恢复 | G3（M1） |
| 关联接纳后丢回执，重发原交接 | 只接纳一次；来源可以查询并记录回执 | G3、R7（M1） |
| 在准入、尝试、出口、效果和核对各点杀进程 | 原标识和负责方不变；可能已发出的动作不变成"未执行" | G1、G11（M1） |
| 采样率为零、队列满、采集实现失效 | 核心效果和完成门禁不受影响；诊断明确显示缺失 | G1、G2、C8（M1） |
| 重发命令、事件、回执；同键不同内容 | 同内容去重，不同内容报冲突，统计不翻倍 | G3、A4（M1） |
| 新版本先到、旧版本后到 | 投影不回退；原 Result 不被改写；新效果可见 | G2、G11（M1） |
| 取消分别早于、晚于实际出口 | 如实区分已封闭、已发出、未知、仍在核对 | G1、G2、C7（M1） |
| 目标已执行，但短期查询返回"不存在" | 达到目标声明的证明条件前继续保持未知 | G1、C4（M1） |
| 重复用量、重复 span、关闭后的账单 | 展示预算的唯一计费结果；迟到费用不消失 | G10（M1 基础，M2 完整） |
| 100 个动作中 90 个快速完成、10 个不结束 | 不得报告全部达标；积压和超时的分母覆盖未结束的对象 | C8（M1） |
| 时钟前跳、后跳、重启、补传 | 不产生负的耗时；顺序取来源版本，年龄标明误差 | C5、C8（M1/M3） |
| 大量随机标识、URL、错误文字 | 不产生无界的指标标签；超限和分组缺失可见 | G12（M1 基础，M6 容量） |
| 内容上传钩子、异常正文、编码后的敏感属性 | 未授权内容进不了队列、持久文件或外部出口 | G5、G8、C2（M1 基础，M2 完整） |
| 导出排队后撤权，或在实际出口前失效 | 当前核验失败就阻断；已发出的如实处理 | G4、G8（M2–M3） |
| 删除后补传旧 span、恢复备份、重建索引 | 停止使用；派生物全部清理；旧版本不复活 | G9（M2–M3） |
| OTLP 接收后、后端保存前崩溃；200 部分成功 | 不声称最终持久；不重试部分成功的原批次 | G1、G3（远端接入阶段） |
| 伪造来源、其他用户的标识或追踪标识 | 不接纳伪造的事实，不泄露对象是否存在，不产生混合导出 | G7、G12、R3（M1 基础，M6 完整） |
| 一个用户持续制造日志和诊断请求 | 该用户的额度生效，其他用户的记录和裁决正确 | G12（M6） |
| 停止采集、重复通知、用户确认告警 | 失联不当作恢复；确认通知不改变动作效果 | G1、C7、C8（M1 起） |

默认实现和替换实现都通过同一公开接口验证，不只测采集实现的内部函数。
