扩展管理负责第三方接入物（插件、Skill、外部 Agent）的安装和发布：包的身份与版本、依赖、来源验证、就绪检查、发布计划、灰度和回滚。

它有一条清晰的边界：**扩展管理持有"装了什么、检查过什么、发布到哪里"的事实；但"能不能用于准入"由核心决定。**扩展声明的权限上限由授权持有，核心当前可以使用哪些实现由任务编排持有，每个动作实际使用了哪个实现由动作账本固定。平台事实不得直接改变准入资格。

本设计的要点：

- **不可变的扩展包、固定的依赖、隔离的安装**；安装器不运行包自带的任意生命周期脚本；
- **就绪检查有证据**：检查实际加载的字节、接口、出口封闭性和恢复能力；证据绑定环境和宿主实例；
- **安装不是授权**：生效的权限是"来源授权 ∩ 安装声明的上限 ∩ 具体调用的凭据"；
- **第三方可执行代码必须在真正的隔离环境中运行**，所有出口受控；
- **灰度和回滚保留旧动作的实现绑定**：回滚是新的发布代次指向旧包，不恢复旧数据库，也不撤回已发生的效果。

五个判断彼此独立：**来源可信、版本兼容、运行就绪、当前授权有效、动作效果确定。**任何一个都不能推出其他几个。

## 1 职责与边界

| 事实或行为 | 唯一负责方 | 扩展管理承担的工作 |
| --- | --- | --- |
| 包的身份、版本、依赖、来源验证、检查证据、发布计划 | 扩展管理 | 持久记录并提供查询；本身不开放插件替换 |
| 命令回执、待办工作、领取与租约 | 持久工作 | 使用其公共接口 |
| 当前可供准入的实现视图 | 任务编排 | 提交候选实现和证据；不得直接改任务状态 |
| 扩展的权限上限、实际授权、撤销 | 授权 | 提交声明，请求受限的授权；安装记录只保存引用 |
| 执行尝试、效果、核对、迟到结果 | 动作账本 | 提供固定的实现引用和恢复资源 |
| 下载、文件、进程、网络和设备出口 | 出口闸门和对应的执行适配器 | 安装、探针和扩展调用都走受控出口 |
| Skill 正文、个人配置、缓存、派生数据、删除 | 内容治理 | 保存内容引用，登记持有方和清理范围 |
| 用量、评测结果、运行诊断 | 预算、评测与进化、运行记录 | 关联其记录，不自行计费或认定质量提升 |

扩展只能接入四个位置：推理、记忆策略、执行适配器、交互适配器。插件声明实现其中一个或多个接口，每个接口独立验证。Skill 是操作知识和流程内容，由核心组织进推理上下文，不成为新的裁决者。外部 Agent 经执行适配器接入。扩展之间的能力调用经核心中转（R4 的只读检索除外）。第三方交互适配器的事件不得自行产生授权；确认必须绑定核心记录的具体请求。

## 2 对象与状态

### 2.1 扩展清单

| 字段 | 含义与约束 |
| --- | --- |
| 清单模式版本 | 决定解析和检查规则；不支持的安全必需语义拒绝安装 |
| 扩展标识、发布者 | 稳定的身份；显示名称不用于路由；发布者与预期的签名身份、来源命名空间对应 |
| 类别 | 插件、Skill、外部 Agent |
| 版本 | 用于兼容和展示；**同一版本、不同摘要**视为不同的产物，阻止自动替换 |
| 实现的接口 | 接口标识、契约版本范围、必需功能；只接受四类可替换部分 |
| 能力 | 能力标识、描述、输入输出模式摘要、适用条件；执行能力按[核心契约的五个维度](../../core/contracts/README.md#24-能力声明)声明，未声明的按最保守处理 |
| 依赖 | 区分随包的库、运行环境依赖、经核心使用的能力依赖；必需或可选，版本要求 |
| 所需权限 | 主体、资源、动作、范围、用途和期限的**上限**；读取、保存、同步、行动分开 |
| 运行条件 | 支持的端点环境、所需的沙箱功能、资源上限和入口 |
| 资源清单 | 正文、脚本、配置模式和其他资源的相对路径、摘要、大小、是否可执行 |
| 私有状态模式 | 只允许两种：**调用结束即销毁**；**由核心管理的显式状态引用**（状态作为派生产物交还核心，登记来源，下次通过受控读取载入）。另记格式版本、保留规则、能否跨版本读取。声明其他模式或不声明的扩展不得接触受限内容 |
| 来源和验证材料 | 源码提交、签名、来源证明、SBOM、许可证等的引用；引用本身不构成可信的结论 |

包摘要放在外层的包记录和签名证明中，避免"清单包含自身摘要"的循环。签名覆盖确定的包字节；解析出的关键字段必须与这些字节一致。

### 2.2 持久记录

| 对象 | 关键字段 | 写入方 |
| --- | --- | --- |
| 扩展包 | 身份、版本、包摘要、清单摘要、固定的依赖组合、内容引用、来源材料引用 | 扩展管理 |
| 来源检查 | 包摘要、检查规则版本、信任根版本、预期和实际的签名身份、证明结果、证据 | 扩展管理 |
| 安装 | 用户、端点、扩展、包摘要、安装位置、安装动作引用、阶段 | 扩展管理 |
| 就绪检查 | 安装、宿主实例、包与环境摘要、契约测试集版本、工具定义摘要、状态模式、结果、证据、有效期 | 扩展管理 |
| 发布 | 原包和目标包及依赖组合、分组范围、目标代次、预期原代次、检查和评测引用、核心与端点的回执、阶段 | 扩展管理 |
| 权限上限 | 用户、安装、包摘要、声明权限摘要、撤销版本 | **授权** |
| 核心接纳 | 用户、端点、接口、发布代次、可用实现引用、允许的使用范围、阻止原因 | **任务编排** |
| 动作的实现快照 | 原动作和尝试、端点、安装引用、包和依赖摘要、契约版本、能力定义、恢复声明 | **动作账本** |

后三类是**核心的记录**；扩展管理只保存回执和引用，不取得第二个写入权。

### 2.3 状态

| 对象 | 正常转换 | 失败与特殊状态 |
| --- | --- | --- |
| 包检查 | 待检查 → 检查通过 | 拒绝；等待依赖；等待可信的时间或来源材料 |
| 安装 | 已接纳 → 获取中 → 暂存完成 → 安装完成 | 等待核对、失败；效果未知由动作账本记录 |
| 就绪检查 | 未检查 → 检查中 → 通过 | 不通过、证据不足、已失效 |
| 发布 | 已接纳 → 准备中 → 等待核心接纳 → 灰度中 → 已发布 | 暂停、中止、等待回执或核对 |
| 旧安装 | 服务新动作 → 停止接收新动作 → 保留核对能力 → 可以清理 | 隔离；存在未知动作时不得因超时直接清理 |
| 卸载 | 已接纳 → 停止新使用 → 等待责任收尾和内容清理 → 卸载完成 | 部分完成、等待核对 |

- **安装完成**只证明指定的包已在端点按计划装好；
- **检查通过**只证明在指定版本、环境和检查规则下证据成立；
- **允许新动作使用**还要求核心接纳、当前授权有效、预算和任务条件满足；
- 就绪证据绑定环境和宿主实例：重启、工具定义变化、依赖变化或相关策略变化后，要重新判断是否仍有效；
- 正常升级时停止旧版本接收新动作，但保留已准入动作的绑定；安全隔离则另外阻止尚未发出的相关出口。

## 3 接口

所有改变状态的命令包含用户、请求主体、命令标识、请求摘要、预期代次和相关的授权引用；持久工作按原命令返回同一决定。

| 接口 | 输入 | 成功含义 | 主要错误 |
| --- | --- | --- | --- |
| 规划变更 | 已取得的来源内容、目标摘要、端点、变更类型、当前环境和规则版本 | 计划、固定的依赖组合、权限差异、兼容结果；**只是规划，不承担执行责任** | 清单无效、依赖冲突、目标不兼容、来源不足 |
| 提交变更 | 命令标识、计划及其摘要、预期代次、授权和预算引用；类型为安装、发布、停用、回滚、卸载 | 持久回执和变更标识；表示已接下责任 | 无权、计划已失效、并发冲突、资源不足 |
| 请求就绪检查 | 命令标识、安装引用、环境摘要、检查规则、测试用途的授权 | 检查责任已持久接纳 | 包不完整、环境不支持、没有测试授权 |
| 报告安装或检查的观察 | 工作标识、宿主身份、领取代次、序号、实际摘要、证据引用 | 观察已保存；**不代表效果或任务完成已被裁决** | 身份不符、证据无效；过期的报告记为历史观察，不覆盖当前状态 |
| 向核心提交实现视图 | 发布标识、目标代次、预期原代次、固定的实现和权限上限引用、有效的检查证据 | 核心接纳回执或拒绝；只表示核心保存了这个视图 | 代次冲突、证据失效、接口越界、权限声明不符 |
| 查询状态、订阅通知 | 用户范围、记录标识或位置 | 持久状态、回执、阻止原因、待核对的动作引用 | 通知可能重复；缺口通过查询补齐 |

各类变更的完成证据：

| 变更 | 完成证据 |
| --- | --- |
| 安装 | 端点保存并重新核验了包和依赖的摘要；相关的安装动作已收尾 |
| 发布 | 指定范围内核心的接纳与端点的观察一致，所需的检查仍有效；离线端点单独显示为待处理 |
| 停用 | 核心已阻止新的使用；已发出的动作仍列出核对状态 |
| 回滚 | 新的发布代次指向指定的旧包并已被接纳；原动作记录仍完整 |
| 卸载 | 新使用已停止、可执行资源已验证移除、内容清理完成；遗留的动作责任如实说明 |

管理任务是否成功，仍由任务编排按 G2 裁决。接口返回"已接纳"不得显示为"安装成功"。

## 4 关键流程

### 4.1 安装与就绪

| 步骤 | 处理 | 持久化点 |
| --- | --- | --- |
| 1 | 验证变更请求，创建原命令回执、安装意图和关联的管理任务 | **I1** 扩展域意图和持久工作回执 |
| 2 | 获取来源元数据、包和证明材料；下载、文件写入和必要的进程操作都经过核心准入和出口闸门 | **I2** 核心准入、动作账本的尝试；内容治理登记来源 |
| 3 | 核对包摘要、发布者身份、来源证明、SBOM 和更新元数据；固定全部依赖 | **I3** 包记录、检查记录、依赖组合 |
| 4 | 在用户和安装专属的位置暂存；限制解压大小、文件数和路径，拒绝越界链接和特殊文件；安装完成前核验实际字节 | **I4** 端点动作的接纳和效果证据 |
| 5 | 在没有业务权限的隔离环境中启动；检查接口、资源限制、出口封闭性、恢复能力、私有状态模式，以及宿主能否为每个计算工作提供干净实例 | **I5** 就绪检查记录和证据 |
| 6 | 请求授权模块登记声明的上限；取得实际授权是另一个独立的过程 | **I6** 授权记录 |
| 7 | 把固定的实现视图和检查证据提交给核心，核心验证后接纳 | **I7** 核心接纳记录和交接回执 |
| 8 | 查询核心和端点的最终观察，更新管理视图；管理任务按 G2 收尾 | **I8** 发布观察和核心的 Result |

跨域步骤都遵守 R7。包必须先完整落盘或进入持久的包仓库，然后才能提交引用它的可用记录。

**就绪检查**包括：宿主实际加载的字节与清单一致，不接受插件自报的版本；必需的能力和依赖确实存在，缺少可选依赖不会扩大其余能力；不能直连网络、读取宿主凭据、写入未授权的文件或调用其他扩展；执行适配器能返回 G1 所需的效果类别，幂等和核对能力有针对目标系统的依据；超时、崩溃、重复回报、撤权和删除的行为符合契约；MCP 按明确支持的协议版本检查协商行为，发现的工具定义与批准的快照一致。探针**不得为了验证可用性而执行真实的付款或发送消息**；确需有副作用的检查，必须使用独立的测试任务、受限的资源、授权和预算。

**为什么必须真正隔离。**VS Code 官方说明，扩展宿主拥有 VS Code 本身的权限，可以访问文件、网络、启动进程（[扩展运行时安全](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)）。进程隔离可以改善稳定性，但同一操作系统用户下的普通子进程不是权限边界。首批选择能证明出口受控的操作系统沙箱或受限运行时（如 WebAssembly，见[出口闸门 4.5](../../core/egress/README.md#45-插件沙箱m4)）；不支持所需隔离的端点不得标为就绪。

**清单和输入模式代替不了执行处的资源检查。**官方的 Git MCP 服务器曾先后出现参数注入、未验证配置的仓库边界、`git_add` 接受 `../` 路径等问题（[GHSA-9xwc-hfwc-8w59](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-9xwc-hfwc-8w59)、[GHSA-j22h-9j4x-23w5](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-j22h-9j4x-23w5)、[GHSA-vjqx-cfc4-9h6v](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-vjqx-cfc4-9h6v)）；修复版本在未配置允许的仓库时，仍会跳过仓库边界检查（[修复源码](https://github.com/modelcontextprotocol/servers/blob/862e717ff714987bd5577318df09858e14883863/src/git/src/mcp_server_git/server.py)）。所以修复代码是否启用、部署配置是否正确，也必须进入就绪证据，不得只凭"版本已修复"就启用。

### 4.2 Skill 的格式与加载

Skill 保持 Agent Skills 的标准格式：`SKILL.md` 使用 YAML 前置元数据加 Markdown 正文，必需字段是 `name` 和 `description`，可以包含脚本、引用和资源，`allowed-tools` 是实验字段（[Agent Skills 规范](https://github.com/agentskills/agentskills/blob/69ef37e9424c0a7ea9dd2293b559e43ec8176379/docs/specification.mdx)）。版本、依赖和权限由外层的 Lerna 清单补足。

| 环节 | 做法 |
| --- | --- |
| 导入 | 正文和全部引用的资源进入不可变的包 |
| 解析 | 限制大小和解析深度；拒绝重复的关键字段、危险的 YAML 构造和无法解释的权限语法 |
| 发现 | 只展示已被接纳、当前可以使用的 Skill 元数据；描述同样视为第三方内容 |
| 加载 | 核心固定 Skill 的包摘要和内容版本；先提供名称和描述，需要时再取正文和资源 |
| 权限 | `allowed-tools` 最多形成**更窄**的工具限制；不得创建授权，也不得扩大外层的权限上限 |
| 引用 | 相对路径只能指向固定包内的资源；远程引用必须作为受控的获取动作重新处理 |
| 脚本 | **加载 Skill 不执行脚本**；脚本运行要形成提议，经准入后在受限的执行环境中运行 |
| 更新 | 文件内容变化生成新版本；已固定的任务上下文不热替换 |
| 删除和撤回 | 内容治理让引用失效，清理正文、派生摘要、缓存和使用中的上下文；必要时销毁隔离实例 |

不会自动信任工作区里新出现的 Skill。结构化包装和提示注入检测只能缓解推理的偏移，安全保证来自 G4–G8，而不依赖模型遵守 Skill 里写的约束。

### 4.3 灰度与回滚

1. **准备候选版本**：安装、就绪检查、状态兼容检查都已完成；发布计划固定目标包、依赖、范围和停止条件；
2. **保存发布意图**：按预期代次条件更新，写入新代次和待办；
3. **核心接纳**：按 R7 交接。灰度按稳定的用户或端点分组，每个任务和动作记录实际选用的版本；不采用"每次调用随机选版本"，那样一个任务会混用版本，难以复核；
4. **观察灰度**：契约违规和效果质量分开记录；质量、耗时、费用和未知效果的比例都来自核心记录和评测证据；
5. **扩大范围**：只有证据满足预先固定的条件才推进；**证据不足就暂停**；候选不得修改评测门槛。Argo Rollouts 区分分析结果的成功、失败和无法下结论，对"无法下结论"暂停（[Argo Rollouts 1.8.3](https://github.com/argoproj/argo-rollouts/blob/v1.8.3/docs/features/analysis.md)），这里采用同样的原则；
6. **回滚**：重新核验旧包当前是否仍可用，创建一个更高的发布代次指向旧包，再走核心接纳；不恢复旧数据库，也不降低更新元数据的版本；
7. **保留原责任**：已准入的动作继续按原端点、包、能力定义和尝试标识处理；回滚后的版本不会重新执行它们；
8. **清理旧安装**：停止新使用后，取得核心关于引用和动作收尾的持久证据，再清理可执行资源。

正常回滚不撤回已发生的效果；需要补偿时，由用户目标形成新的动作并重新准入。按 C9，自动生成的 Skill 和配置必须经评测和受控发布；自动生成的插件代码只能形成可审查的补丁，维护者确认发布后才进入安装流程。

### 4.4 供应链检查

| 检查 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 摘要 | 下载的字节没有变 | 摘要来源被攻陷时无效 |
| 发布者签名 | 来源身份。Sigstore 验证要求约束签名身份和发行者，并核对产物摘要（[Sigstore](https://docs.sigstore.dev/cosign/verifying/verify/)） | 代码没有恶意 |
| 来源证明（SLSA） | 怎样构建的：构建者、输入和产物（[SLSA 1.2](https://slsa.dev/spec/v1.2/build-provenance)） | 代码没有恶意 |
| SBOM（SPDX、CycloneDX） | 资产追踪、漏洞影响分析、清理范围 | 不代替安装时的依赖锁定，也不意味着清单完整 |
| 更新元数据（TUF） | 防止回滚、冻结、元数据混配和密钥泄露攻击，使用不同的签名角色、阈值、版本和有效期（[TUF 1.0.31](https://theupdateframework.github.io/specification/v1.0.31/index.html)） | — |

公共的自动更新源采用"签名 + 来源证明 + SBOM + 安全的更新元数据"。用户自己编写的 Skill 可以使用明确接受、固定了摘要的本地来源，但仍执行同样的授权、隔离和内容治理规则。"签名有效"不得直接转换为"允许执行"：微软在 2025 年报告当年已从 Marketplace 移除了 110 个恶意扩展，并介绍了发布后重新扫描和阻止的机制（[Marketplace 安全与信任](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)）。签名、扫描、权限批准和运行隔离是四种不同的检查。MCP Registry 同样只是发现来源，不是信任根，也不是安全审核结论（[Registry](https://modelcontextprotocol.io/registry/about)）；启动参数按数组处理，不交给 shell 拼接。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 持久工作、扩展管理、跨域接收方 | 查询原命令或交接标识；不新建安装、发布或动作 |
| 管理进程崩溃 | 持久工作、扩展管理 | 新工作者从持久的意图、阶段和回执继续；领取代次防止旧工作者覆盖结果 |
| 安装宿主或插件崩溃 | 动作账本、端点宿主 | 查询实际的包状态和原尝试；可能已有外部效果时保持未知，先核对 |
| 重复请求 | 持久工作、各记录写入方 | 同命令同摘要返回同一决定，不同摘要拒绝 |
| 安装、升级、回滚并发 | 扩展管理、任务编排 | 对发布代次做条件更新，依赖组合一起固定；竞争失败的计划重新规划 |
| 依赖或来源不可用 | 扩展管理 | 等待或拒绝；保持已核验的旧版本；不临时换用最新版、未知镜像，也不扩大权限 |
| 授权或核心不可用 | 授权、任务编排、出口闸门 | 无法证明前提时，停止新的启用和出口 |
| 迟到的就绪报告 | 扩展管理 | 保存到对应的旧检查记录；不得让已停用的版本重新成为当前版本 |
| 迟到的动作结果或费用 | 动作账本、预算 | 仍关联原动作和实际计费来源；不因回滚或取消而丢弃 |
| 签名身份被撤销、包被发现恶意 | 来源检查、授权、核心、宿主 | 阻止新使用，隔离相关实例，保留动作账本；旧包不得凭历史检查结果继续执行 |
| 删除时扩展不回报 | 内容治理、宿主 | 阻止使用，销毁相关实例，验证受控存储已清理；**不接受恶意插件自报"已删除"** |
| 清理中崩溃 | 扩展管理、内容治理、端点动作账本 | 从清理意图核对实际资源；未完成的保持可查，不提前确认卸载完成 |

## 6 不变量落实

| 不变量 | 本模块怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 安装的副作用和插件的业务动作都由动作账本处理；超时不转为未生效；回滚保留原恢复声明 | 发出请求后丢回报，然后升级，检查是否仍用原动作核对，有无无依据的重试 |
| G2 | 管理成功要求明确的安装或发布证据；未知动作不会被卸载或回滚抹掉 | 插件返回成功，但实际的包有误或目标没变，不得据此完成 |
| G3 | 意图、接纳、回执和核心接纳分别持久化；通知只用于唤醒 | 在 I1–I8 前后崩溃 |
| G4 | 下载、安装写入、启动、探针、模型和工具调用都有准入；出口再次核验 | 缺条件版本、授权或预算引用的调用全部被拒绝 |
| G5 | 沙箱限制直接的系统出口，受控接口核验凭据；启动和辅助检查也受管 | 插件直接联网、读文件、起进程、访问设备、调用辅助模型，都没有旁路 |
| G6 | Skill 和推理只提供内容和提议；插件只回报；管理平台不写任务终态或效果 | 提交伪造的完成、授权和效果记录，都被拒绝 |
| G7 | 生效权限不超过"来源授权 ∩ 安装声明上限 ∩ 具体调用凭据"；新版本扩大声明时不继承旧批准 | 子 Agent、Skill 脚本、升级后新增的权限试图越权，被拒绝 |
| G8 | Skill 的加载、保存、同步、评测和行动分别检查当前用途授权 | 只有读取权限时试图保存或同步；撤销后使用旧上下文 |
| G9 | 私人内容和派生物登记；缓存和实例纳入清理；不依赖插件单方面的回报。删除要求优先于"可能需要回滚" | 删除后从索引、缓存、旧版本、日志和活动实例中检索 |
| G10 | 所有用量进入预算；回滚、重试和取消不删除费用 | 重复、乱序和迟到的计费回报 |
| G11 | 动作固定原端点和实现快照；故障、升级、卸载都不产生替代动作 | 未知动作期间替换插件或重启宿主，标识和负责方不变 |
| G12 | 安装和配置按用户隔离；隔离实例、凭据、缓存和额度都带用户范围 | 跨用户读取和负载攻击 |

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 包、资源和依赖都固定 | 安装、恢复和评测都可追溯 | 存储增加；不能直接热加载工作区的变化 |
| 不可信代码隔离，所有出口受控 | 安全不依赖插件自律 | 部分现有插件无法原样运行，需要适配 |
| 不可信扩展每次用干净实例，状态显式交还核心 | 宿主记录的输入清单就是完整来源；读过私密内容的内存不会进入下一轮输出 | 每次实例化的成本；跨调用状态要经核心登记和受控读取。备选的"宿主累计实例来源集合"会扩大删除扇出并要求串行化并发调用，实测证明干净实例成本不可接受时再议（[评审 RV10](../../../review/archive/round-1/README.md#rv10-不可信扩展每次调用用干净实例)） |
| 核心接纳与平台安装分开 | 权限和准入事实仍满足 A1、R3 | 增加跨域回执和中间状态 |
| 旧动作固定实现，旧版本保留核对能力 | 升级不会制造重复效果或丢失责任 | 多版本并存，资源长期保留 |
| 默认不做破坏性的状态迁移 | 回滚可用，记录不丢 | 扩展作者需要设计状态兼容或隔离 |
| 证据不足就暂停灰度 | 不猜测发布成功 | 个人场景样本小，可能难以自动扩大范围 |

被否决：自由文本的清单（无法可靠检查能力和权限）；通过执行入口自省来发现能力（发现时已经执行了不可信代码）；启动时解析最新版本的依赖（恢复和回滚不可重复）；继承安装者的全部权限（违反 G7）；与核心同进程运行插件（无法约束恶意插件）；覆盖当前目录并执行安装脚本（崩溃后出现混合版本）；原地降级并恢复旧数据库（可能丢失新记录或迟到的结果）。

第三方代码的强制隔离边界、核心实现接纳记录的归属、旧动作版本的保留规则、公共更新源的信任根管理，正式采纳前必须写成 ADR。

## 8 待定事项

| 事项 | 验证或决定方法 |
| --- | --- |
| 首批端点能否限制文件、网络、进程、凭据和设备出口 | 分平台构造恶意插件，测试实际的系统调用和逃逸路径；失败的端点不得标为就绪 |
| 多版本隔离的启动、内存和存储开销是否适合个人部署 | 分别对推理、执行适配器和脚本测量，不以空插件的启动速度代替 |
| 干净实例的成本和隔离是否达标 | 以 Wasmtime 为例，可复用预编译模块和 InstancePre、每次新建 Store（[快速实例化](https://docs.wasmtime.dev/examples-fast-instantiation.html)）；测量实例化延迟，并验证宿主缓存、临时文件、共享内存和继承句柄都不跨实例 |
| 协议兼容和模式检查能否覆盖主要的行为变化 | 用两种独立实现做跨版本恢复和一致性测试 |
| 保留恢复资源是否会造成不可接受的长期占用 | 模拟长期未知的动作；额度不足时拒绝新安装，不删除未收尾的责任 |
| 支持哪些 MCP 协议版本和哪些反向请求 | 明确版本列表，逐版检查；服务器默认不得自行发起模型调用、工具调用或委派 |
| 信任根、发布者身份更换、漏洞阻止和离线检查的策略 | 确定维护者和用户各自的权限、可信时间来源和重新检查的触发条件 |
| SBOM 接受哪种格式、完整性要求和漏洞例外期限 | 比较 SPDX 和 CycloneDX 的工具链；缺失的信息明确显示 |

### 8.1 扩展路径与兼容验收

新增能力先判断属于哪条路径（定义见[核心契约 7.6](../../core/contracts/README.md#76-版本同版发布加兼容窗口)）：在既有接口增加实现、新增核心或受信模块、扩展公共协议语义。本模块只管理第一条路径的安装和发布；后两条经代码审查和统一契约发布，插件不能注册核心处理函数。

执行适配器要区分两类产物：普通插件可以提供协议解析、候选字段提取和易用性包装；按目标系统解释终局语义的**受信解释规则**属于受信实现（[ADR 0003](../../../adr/0003-replacement-classes-and-assembly.md)），需要独立审查和发布，不能随普通插件一起安装生效。插件包里自带的"终局验证器"不取得裁决权（见[动作账本 2.3](../../core/ledger/README.md#23-收尾依据)）。

注册记录在现有发布清单和能力声明上补齐，不新建在线的全局注册服务；Schema 只有一个权威来源，注册记录引用其准确版本和摘要。M3 定型时至少回答：

| 项目 | 要回答的问题 |
| --- | --- |
| 身份 | 哪个接口、方法或特性，由谁维护；稳定标识怎样防冲突 |
| 结构与语义 | 输入、输出、错误、缺省、枚举；哪些字段只用于展示，哪些影响决定 |
| 接纳与恢复 | 原 `CommandIdentity`、成功提交的记录集合、查询入口、未知处理、旧处理器的保留要求 |
| 安全与费用 | 操作权利、处理目的、实际出口、来源传播、费用上界、必需特性 |
| 兼容性 | 可接收、可解释、可执行、可恢复的版本范围分别是什么 |
| 生命周期 | 停止新调用、撤销、排空、回滚、卸载、旧责任恢复和清理 |
| 验收证据 | 测试套件与版本、平台、目标系统、生成工具、运行库、正反例与已知限制 |

协商结果固定双方身份、契约版本、定义清单摘要、可用方法和必需特性。重连重新协商；旧命令保留原契约、Schema、指纹版本和原身份。接收方每次按实际请求检查是否在支持范围内，不只依赖握手时成功过。安装和协商成功都不授予业务授权。

兼容性分四层：格式能传输、语义能正确解释、持久记录能恢复、具体实现仍有资格运行。前三层通过也不能重新启用已被安全隔离的旧插件。开放能力前通过以下验收，"旧""新"必须填入准确版本，不是对任意 N 与 N−1 的永久承诺：

| 测试 | 通过条件 | 阶段 |
| --- | --- | --- |
| 同一接口的第二种独立实现 | 通过共同的语义和故障用例；切换不改任务、授权和账本的业务规则 | M4 |
| 旧写新读、新写旧读 | 支持的组合语义一致；不支持的组合明确拒绝，不静默扩权 | M3 |
| 新发端—旧网关—新执行端 | 必需字段与语义绑定不丢失；不能保留时阻断路径 | M3 |
| 未知必需特性、未知枚举、遗漏声明 | 不产生新动作或错误默认；错误能定位缺少的能力 | M3 |
| 升级时仍有旧命令、待办、未知动作和费用 | 原身份、比较规则和恢复责任保持 | M3 |
| 新状态写入后回滚 | 已声明支持的旧读端可安全恢复；不支持就阻止回滚或限定为受阻恢复 | M4 |
| 停用、卸载、撤权与迟到回报交错 | 停止新调用，仍接纳合法原责任的回报；不删除最后的恢复依据 | M4 |
| 错误实现丢字段、换键重发或自动重试 | 一致性套件能发现反例，不只验证"好实现通过" | M4 |

行为兼容测试不能全部由插件自带；平台维护共同测试和独立的目标效果记录。二进制、JSON 和 SDK 再编码的路径分别验证：Protobuf 的未知字段在 JSON 转换或逐字段复制时可能丢失（[未知字段](https://protobuf.dev/programming-guides/proto3/#unknowns)）。

## 9 M1 范围

**M1 不实现扩展管理平台。**M1 只运行项目维护的默认实现。必要的预留是：在核心契约和运行记录中准确记录实现版本、能力和恢复声明，每个动作固定实际使用的实现；恢复动作时不得换版本重发。M4 实现基本的安装、兼容检查、扩展 SDK、第二种实现和一致性验证，以及插件沙箱和干净实例；M5 实现完整的受控评测和灰度自动推进。M1 的恢复测试通过，不代表第三方扩展的安全已经达成。

## 10 测试要点

| 用例 | 必须成立 | 对应 |
| --- | --- | --- |
| 在 I1–I8 的每个持久化点前后注入崩溃和回执丢失 | 已确认的责任不丢；恢复时查询原交接；不重复产生副作用 | G1、G3、G11、R7 |
| 插件动作已发出但回报丢失，随后升级、回滚或卸载 | 原动作仍是未知；端点和实现快照不变；新版本不重发 | G1、G2、G11 |
| 撤权与准入、出口并发 | 撤权后依赖旧权限的新出口无法通过；已发出的结果仍如实核对 | G4、G7、G8 |
| 恶意插件直接读文件、联网、起进程、访问设备和模型服务 | 全部被实际的隔离边界阻止，或进入受控的准入和记账 | G5、R2、R5 |
| 并发的升级、回滚、依赖更新；租约过期后的工作者继续回报 | 只有有效代次能推进当前状态；旧报告不覆盖；依赖组合不混配 | G3、G11、A4 |
| 签名有效但身份不符；摘要不符；旧的更新元数据重放；元数据混配 | 拒绝候选；回滚不降低信任根或元数据版本 | C6、A4 |
| 解压路径越界、符号链接、特殊文件、压缩炸弹；以 `-` 开头的命令行参数 | 没有越界写入，没有参数注入；资源消耗受限 | G5、G12 |
| MCP 重连或工具变化通知后，名称、描述或模式改变 | 新定义产生新的快照；旧批准不得覆盖；原动作的查询保留原定义 | G1、G7、C6 |
| 插件声称幂等或只读，但模拟目标产生了副作用 | 不凭声明授予安全重试资格；实际效果由核心记录 | G1、G6、C4 |
| 删除或撤回私人 Skill，插件拒绝清理并仍有缓存 | 立即停止使用；实例和存储的清理可以验证；旧版本无法恢复被删内容 | G8、G9、S6 |
| Skill 里包含伪造的完成、扩大权限、自动安装依赖或嵌套的工具指令 | 这些指令无法修改核心事实或绕过准入 | G4–G7、R1、R4 |
| 灰度指标缺失、样本不足、契约测试失败 | 暂停或中止；不当作成功，也不自行降低门槛 | C8、C9、S8 |
| 新版本写入私有状态后回滚，旧版本无法读取 | 发布前阻止不兼容的路径，或证明隔离和兼容机制可用 | C6、C9 |
| 未知动作仍引用旧安装，同时运行清理 | 清理不删除责任记录，不错误移除必要的恢复资源 | G1、G11 |
| 确定性的恶意插件：第一轮读私密内容 A 存一个字节，第二轮只读公开内容 B，把该字节放进正文、URL 路径或参数分支 | 新实例取不到旧字节；插件假报缓存已清空、实例池复用、并发调用互读状态、崩溃后恢复旧状态都无法带入 A。对照：只载入 B 的干净实例能完成获准的公开输出 | G7、G8、G9 |

再加一个通过公共接口运行的随机状态序列测试，交错安装、检查、启用、撤权、取消、回滚、崩溃和迟到的报告，持续检查三个性质：每项已接纳的责任始终有记录和负责方；每次实际出口都能追溯到有效的准入和实际的实现；任何版本切换都不会把未知效果变成"未生效"或"成功"。
