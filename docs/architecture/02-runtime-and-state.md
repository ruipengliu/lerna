# Go 内核与本地持久化

状态：本分册的模块职责、运行存储接口与替换验证方案已由用户确认。本文为技术设计，尚无实现或测试结果。

决策依据：[确定 Go 内核模块与本地持久化 Interface](../../.scratch/harness-technical-design/issues/05-kernel-stack.md)。约束见 [设计输入与硬约束](00-design-constraints.md)，机制证据见 [持久运行机制与存储研究](../research/harness-durable-runtime-options.md)。

## 设计范围

本分册确定任务运行的责任归属、持久化组织方式、Go Module 的调用及部署方式，以及原子提交和替换测试契约。端云所有权转移协议、记忆同步数据模型和插件发布规范由对应分册继续设计。

## 已确认的基础方案

| 设计方面 | 已采纳方案 | 主要代价与替代方案 |
| --- | --- | --- |
| 任务状态权威 | Go 内核持有任务状态机，负责调度、取消、重试准入和恢复；大脑提出行动，执行系统报告事实。外部运行框架通过 Adapter 或受委派任务接入。 | 项目需要自行维护状态机与恢复机制。另一条路线是让工作流引擎实现完整的任务运行契约，Harness 提供接口和策略；这会增加引擎适配及部署约束。 |
| 持久化模型 | 保存可直接恢复的当前状态，并追加执行记录；状态更新、对应记录和待处理工作在同一事务提交。日志用于追溯和诊断，不要求仅靠完整事件历史重建全部任务。 | 需确保当前状态与记录一致，并维护数据迁移。另一条路线是完整事件溯源：以事件为权威、状态为可重建投影，承担事件版本及重放兼容成本。 |
| 集成与部署 | 核心提供可嵌入业务的 Go 库，由独立启动入口组装参考实现；默认进程内调用，远程 Adapter 经同一行为契约接入。单机同时提供多进程验证形态。 | 需验证进程内外两种调用的错误、取消及授权语义。另一条路线是所有模块一开始都经本地 RPC 调用，以更多序列化和启动管理换取统一网络调用路径。 |

任务运行不依赖具体大脑、数据库或工作流框架的内部类型。实现可以更换，但本分册规定的生命周期和提交语义必须保持。

## Module 职责与依赖

下表按职责定义 Module；具体 Go 包路径随契约分册确定。模块不等同于独立的 `go.mod`、进程或运行节点。

| Module | 对调用者提供的 Interface | 留在 Implementation 内的责任 |
| --- | --- | --- |
| 任务运行 | 提交任务、查询进展、请求取消、提交决策或执行事实。 | 校验状态转换、推进任务、安排工作、执行重试及恢复策略。 |
| 运行存储 | 读取恢复状态，按预期版本原子提交状态变更、关联记录及待处理工作。 | SQLite 表、SQL、锁和事务实现；将持久化错误转换为契约错误。 |
| 大脑 | 接收受控任务上下文，输出决策或委派请求。 | 模型供应商、推理循环及大脑内部检查点。 |
| 记忆 | 按授权访问和更新长期信息。 | 存储、检索和索引；长期记忆事务与运行事务分别设计。 |
| 执行 | 声明能力、执行动作、观察和核对效果，处理取消与接管。 | 设备驱动、模拟设备状态及外部系统连接。 |
| 授权 | 对请求给出允许、拒绝或需要用户参与的判定及其依据。 | 规则实现和授权材料读取；执行端仍需落实准入。 |
| 连接 | 交付已关联的协议消息，报告连接及交付状态。 | 网络建立、编码、重连和传输错误；不自行决定任务完成。 |
| 启动组装 | 根据配置构建依赖并管理启动、关闭。 | 选择 SQLite、具体大脑、模拟设备等 Adapter；核心模块不反向依赖启动入口。 |

运行存储不暴露通用 SQL 或数据库连接给调用者，也不把全部模块的数据放进一个万能存储接口。记忆、证据及产物可以采用各自的存储契约；共享一个开发期数据库文件不意味着共享模块内部表。

## 恢复路径示例

用“模拟设备动作发生后，回执尚未记录便重启”说明恢复契约：

1. 内核先持久化动作意图、稳定调用标识和待处理工作，再交给执行系统。
2. 执行系统按调用标识保留接收记录，在授权有效的条件下执行动作。
3. 模拟设备状态已经改变，但完成回执丢失；恢复时只能判定结果尚未确认。
4. 内核通过执行 Interface 请求核对；可确认效果则记录事实并推进任务，无法确认则保留待处理状态。
5. 重试准入依据动作能力、已知事实和授权决定，不能仅因超时重新发出动作。

数据库提交与外部设备动作不属于同一事务。稳定调用标识和去重记录也不单独构成动作恰好执行一次的保证。进程内调用同样需要此恢复路径，不能依靠函数返回值作为唯一执行记录。

## 运行接口与替换契约

本节行为契约已确认。方法和类型名称用于说明设计，不是已经发布的 Go SDK；完整消息字段与版本编码由协议分册定义。

### 任务级原子存储接口

运行存储接受一个任务的原子变更，包含预期版本、新运行状态、执行记录增量和待处理工作变更。调用者不用自行协调多张表或管理数据库事务。记忆访问和设备动作不纳入该事务；跨任务协作通过持久化工作关联，具体协议另行设计。

```go
// 类型字段及完整错误编码由契约分册定义。
// 每次提交针对一个任务；ChangeID 在该任务内稳定标识一次变更。
type RunStore interface {
    Load(ctx context.Context, taskID TaskID) (RunSnapshot, error)
    Commit(ctx context.Context, change RunChange) (CommitReceipt, error)
    LookupCommit(ctx context.Context, taskID TaskID, changeID ChangeID) (CommitStatus, error)
    ListRecoverable(ctx context.Context, query RecoveryQuery) (RunPage, error)
}
```

- `Load` 返回该实现的权威当前状态及版本。持久化实现须以已提交的持久状态为准，不能将未落盘缓存当作已提交状态。
- `Commit` 在一个原子提交中更新运行状态、追加执行记录、增删或推进待处理工作，同时写入变更回执。成功时返回已提交版本。声明耐久性的实现必须已完成持久化，不得在仅进入内存队列时报告提交成功；内存参考实现仅提供明确标注的临时状态语义。
- 相同变更标识和内容的重复提交返回同一结果；相同标识配不同内容明确拒绝。去重判定先于旧版本冲突判定，避免成功提交的重试被误判为新的竞争更新。
- 提交除状态版本外，还须按调用角色原子校验拥有者及其世代；Worker 推进状态另须满足当前领取代次。条件和失败路径见 [恢复检查表](04-recovery-state-and-failure-matrix.md)，不能先读资格后无条件写入。
- 预期版本不匹配时返回冲突，调用者重新读取并重新决策；不能不检查新状态便重放外部动作。新任务创建也通过明确的“不存在”前置条件防止重复创建。
- 提交超时或断连可能意味着结果未知。调用者通过 `LookupCommit` 核对，必要时以同一变更标识重试；一次未查到回执不证明旧请求永远不会提交。
- 回执与去重信息的保留窗口必须写入契约，至少覆盖仍允许重试和恢复的任务生命周期；清理后不可静默将旧提交当作新提交。敏感载荷删除策略由后续数据与授权设计明确。
- 错误表达同时包含原因和结果确定性：无效请求、版本冲突与持久化结果未知不能合并为可盲目重试的通用错误。
- `ListRecoverable` 支持有界分页，查询结果仅为候选；处理前仍须核对版本和适用执行资格。

将核心数据类型、对外入口与必要的扩展契约放在可导入的 Go 包中；消费依赖的模块声明其所需 Interface，Adapter 实现它。SQLite 类型不出现在这些包的公开参数、返回值或错误中。具体包路径与 Schema 随契约分册确定。

### 调度机制与生命周期规则

调度拆成两个职责：可替换的策略负责从合格工作中选择先后顺序，可替换的 Worker 机制负责唤醒和处理工作。内核始终决定状态能否转换、是否允许重试、何时响应取消和授权是否足够。

待处理工作与任务变更共同持久化，领取、续租及完成确认通过受约束的工作存储 Interface 更新。默认 SQLite Adapter 实现运行存储及工作存储，两者属于同一运行持久化单元；替换时必须一并保持原子性契约。不能把任务更新写入一个库、待处理工作仅发往另一个队列后，就宣称满足原子提交要求。

调度器在调用方看来可以替换，但不拥有另一份任务终态。多 Worker 的竞争通过存储版本和领取凭据约束；旧 Worker 的提交必须可被拒绝。具体拥有者管理、凭据世代和过期动作处置见 [端云恢复方案](04-edge-cloud-and-recovery.md)。

运行存储或工作存储暂不可用时不发起新的外部动作；已发出的动作仍可能发生，需要后续核对。Go 的 `context.Context` 用于限制当前调用等待，不代替持久化的任务取消请求，也不能证明外部动作已停止。

默认进程内调用与远程 Adapter 共用行为契约，分别记录传输能力和故障表现。公开任务入口不允许调用者直接写入任意终态；外部 Agent 报告由内核校验后转换为 Harness 任务事实。

### 契约替换与耐久性验证

开发期提供 SQLite 持久化 Adapter 和内存参考 Adapter，共跑基础状态、版本冲突、重复提交及错误契约套件。内存参考实现用于验证核心没有绑定 SQL，只用于测试或显式临时运行，不作为完整部署默认值。

进程重启、故障恢复及持久化验收必须使用 SQLite 文件。内存实现不声明通过耐久性要求，其状态在进程结束后丢失也不能被包装为任务恢复成功。

这组实现可提供基础存储接口替换证据，但不能单独宣称“不同持久化后端已完成互换验收”。已确认在 M3 引入 bbolt 第二持久后端并通过同一耐久性套件；具体路线见 [专项与实施分册](11-specialized-validation-and-handoff.md)，不强制开发期引入外部数据库服务。同机多进程调用独立验证远程 Adapter，其通过也不能代替后端替换证据。

## 验证责任

以下是必须提供的验证证据，尚无实现或测试结果。

| 验证项 | 应观察到的证据 |
| --- | --- |
| 原子提交 | 注入提交前、提交中、提交后的故障，不出现新任务状态配旧执行记录或缺失待处理工作的组合。 |
| 并发更新 | 相同预期版本的竞争更新最多一个成功；另一方显式获知冲突并重新读取。 |
| 重复提交及结果不明 | 同一变更重试不会重复追加工作；提交回执丢失后可按标识核对结果。 |
| 进程重启 | 使用 SQLite 文件关闭并重启进程，恢复任务、执行记录和待处理工作；内存替身不能提供此证据。 |
| 实现替换 | 同一行为套件用于不同 Adapter，分别标注持久化、并发和跨进程能力，禁止将内存实现通过基础测试等同于耐久性达标。 |
| 调用位置替换 | 本地调用与同机多进程调用得到兼容结果，覆盖超时、取消、授权拒绝和回执丢失。 |
| 大脑替换 | 更换大脑后可读取受控上下文并提出决策，既有任务状态和执行记录不随之丢失。 |

第二个持久化后端的 M3 验证节点、共同耐久性套件及双向停写迁移已由 [能力里程碑](11-milestones-and-validation.md) 明确。本方案不引入新的开发期外部基础设施依赖。
