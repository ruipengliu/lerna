# 设计决策与可见行为

[总览](README.md) · [任务运行](orchestrator/README.md) · [共同契约](contracts/README.md) · [验收](validation/README.md)

本页固定会影响产品行为、保证范围和实施成本的选择。它是决策索引；完整状态、字段和异常规则仍归所属模块。替换实现可以改变内部组织，不能静默改变这些行为。当前协议尚未发布，任何调整都须同时修改正文、机器契约及验证用例。

## 1. 默认实现与权威范围

| 决策 | 采用的行为及依据 | 代价、竞争方案与改选条件 |
| --- | --- | --- |
| D-01 同提交域短事务，跨域持久命令 | 生产从首版采用分布式进程池；同一提交域的 Task、jobs 和适用许可使用共同提交，跨域以原命令、回执及查询恢复。单体只作开发调试，进程拆分不要求拆开必要事务 | 多进程共享权威库仍有数据库容量与热键限制；跨库不能沿用共库原子性。消息中间件可加速唤醒，不能替代领域保存工作与核对责任 |
| D-02 每任务固定 Orchestrator | 同一用户可有多个 Orchestrator，单个任务始终只有一个裁决方；本地独立任务不因另一个云任务失联而无法接纳 | 跨 Orchestrator 的共享额度预分配、资源 owner 及目录聚合增加协调成本。单用户统一 Orchestrator 更简单，适合不需要多端独立接纳的装配；不自动迁移已有任务 |
| D-03 普通模型 API 按可兑现能力分级 | 本地调用槽、发起速率、费用与远端物理并发分别声明；普通 API 可以接入，但没有提供方证据时不承诺远端物理并发硬上限 | 保留所有未知调用的物理占位更保守，可能因缺少终结查询而长期停收。需要远端硬上限的部署只采用具备可验证终结或执行上界的后端，不通过超时回收伪造保证 |

规则归属：[本地事务](orchestrator/README.md)、[命令恢复](contracts/README.md)、[跨 Orchestrator 额度](orchestrator/README.md#budget)、[模型资源保证](brain/README.md)、[部署与容量](deployment.md)。D-01 减少的是通用交付状态，不免除任何领域保存未决操作及后续工作的责任。

## 2. 任务与用户控制

| 决策 | 用户可观察的行为 | 主要取舍与不可突破的边界 |
| --- | --- | --- |
| D-04 活动任务可以修订目标 | `task.revise` 保存新 goal_revision；未启动的旧工作失效，已经可能产生的效果沿原身份核对；终态后修改目标另建任务 | 比每次修改都建新任务更连贯，但须处理旧效果与新目标冲突。修订不能抹去费用、授权使用、操作身份或已有副作用 |
| D-05 暂停阻止新目标工作，既有证据可以完成 | 暂停后不再发起新决策、评估和行动；此前行动已产生且全部条件已核实的任务仍可 succeeded | 将暂停解释为“必须恢复才能发布成功”更保守，但会把已具备的事实人为停留在未完成状态。界面必须说明暂停边界及远端待确认项，不能显示全局瞬时停止 |
| D-06 完成依据显式分级 | Result 区分 verified、assessed、user_accepted；混合条件按必要条件中的最弱依据标记 | 通用任务不必预装每一类目标的专用验证器，但自然语言质量判断不能宣称机械保证。用户验收只替代允许的质量判断，不能覆盖未知外部效果 |
| D-07 取消先到也封闭迟到启动 | Executor 对尚未见过的原操作持久保存取消墓碑；较旧控制不覆盖较新门禁，终态不能重开 | 执行端承担 TaskGate、墓碑和恢复窗口的保留成本。仅在原调用出现后补发取消无法提供相同乱序保证，不能声明为等价实现 |

任务状态、有效祖先控制、完成条件及修订规则以[任务编排器](orchestrator/README.md#state)为准；执行端可确认的停止范围以[执行设计](execution/README.md)为准。控制命令的持久回执与远端实际生效是两个检查点。

## 3. 验收数字与改善证据

| 决策 | 固定口径 | 代价与适用边界 |
| --- | --- | --- |
| D-08 API 按语义业务操作计数 | 提供方和语义业务操作确定唯一计数身份；主版本、驱动、实例和账号记录覆盖情况，不重复增加数量 | 版本升级不能用于凑足 1000 项；只有语义不同、具有独立声明及验收用例的业务操作才形成新项 |
| D-09 比例目标与统计门禁分别报告 | 首次调用正确率至少 90%、有限重试任务成功率至少 95%；正式推断还采用预先声明的 95% 区间下界门禁 | 比仅观察样本比例更严格，通常需要更高比例或更多独立样本。固定穷举集只说明该集合，相关样本和重复种子不能人为扩大有效样本量；统计方法与适用条件按[验收规则](validation/README.md#metrics)冻结 |
| D-10 改善须有未被反馈污染的证据 | 候选、数据分区、尝试历史和反馈暴露均登记；整体策略预先限定正式尝试与停止规则，不能换申请或分区反复挑选最好一次报告 | 维护新的未暴露保留数据有成本；默认仅一次正式确认，多次确认需事先规定整体推断方法。只有探索性结果时可继续研发，不能据此通过正式改善发布门禁 |

D-09 是附加的验收选择，不重命名项目的 90%／95% 比例指标，也不意味着任何有限测试能保证任意任务的成功率。统计门槛不替代权限、重复副作用、数据隔离及来源规则。D-10 的登记、判定及发布交接以[评测设计](evaluation/README.md)为准。

## 4. 修改时需要联动的检查

| 影响范围 | 必须一起核对 |
| --- | --- |
| D-01／D-02 | 接纳答复丢失、原服务路由、跨 Orchestrator 额度封账、共享设备互斥；不能只改部署图 |
| D-03 | 调用身份、未知费用、物理终结证据、池级熔断；分别声明本地和远端保证 |
| D-04 至 D-07 | Task、ControlSnapshot、TaskGate、输入及成果版本；同一正常链和控制乱序反例；机器契约中允许的状态及关联 |
| D-08 至 D-10 | API 清单、样本计划、分母、候选与暴露记录、评测报告和发布门禁；历史结果保留原口径，不能换规则重写结论 |

实现尚未提供的能力维持所属模块规定的等待或拒绝行为。设计审查、机器契约校验、故障运行与质量／容量验收分别记录在[交付审查](review.md)，不互相替代。

## 5. 详细设计中确认的保留与引导规则

| 决策 | 采用的行为及依据 | 代价与改选条件 |
| --- | --- | --- |
| D-11 长期保留最小关闭身份 | 用户确认保留最小命令去重、操作取消与任务终结记录。取消先到时没有原请求的最晚接纳依据，不能靠固定 TTL 证明迟到请求已经失效；完整回执删除后仍须区分 gone 与 not_found | 权威账本和备份承担持续增长的最小索引，正文及敏感数据独立清理。必须物理删除全部身份时，需要另定可验证代际或不可延长的接纳期限；当前不引入这项协议成本 |
| D-12 兼容发布与改善发布使用不同证据 | 沿用普通兼容发布可只验证契约的约定，首装由受信最小宿主核对精确制品与兼容证据并保存本地批准；宣称改善的发布另受保留评测、统计及实用改善门禁约束 | 首个可分发制品也须有可核查的契约证据，缺失时停留在管理／诊断入口。失败的改善发布不得自动转为兼容发布绕过原申请；本轮不增加无报告开发模式 |
| D-13 历史激活与当前实例开放分别保存 | 激活证明某次版本切换已发生；重启后新实例须重新取得当前批准与就绪依据，不能更新原 activation_use_id 来伪造同一次启动 | 多保存一项当前实例依据。远端依赖不可用时等待开放；全本地共库直接核验。只看持久活动指针无法证明进程已就绪，不是等价替代 |

D-11 的长期决定另记于根域 ADR；实现规则集中在[共同保留语义](contracts/README.md)和[执行机制](execution/implementation.md)。D-12／D-13 的完整状态和字段归[评测机制](evaluation/implementation.md)与[扩展机制](extensions/implementation.md)。关闭记录不会使原任务重新运行，实例重新开放也不会重复执行原激活、格式迁移或外部动作。

## 6. 实现语言与通信绑定

| 决策 | 采用的行为及依据 | 代价与改选条件 |
| --- | --- | --- |
| D-14 Go 核心、端云 WSS、服务间 gRPC | 云服务、本地宿主和默认组件采用 Go；浏览器、CLI 和设备主动建立 WSS，双向承载命令、回复和推送；独立服务采用 gRPC，同进程 interface 保持共同事务 | 接入层承担连接、流控、认证续期及重连；不因使用 gRPC 就拆成九个服务。浏览器或设备传输边界确有新约束时再增加绑定 |
| D-15 Protobuf 外壳复用严格 JSON | 领域方法继续以现有 Schema 和 JCS 为权威，RPC 外壳固定在 .proto；不为同一字段维护第二套解释 | 保留 JSON 编码和运行时校验成本；只有测量证明该成本成为瓶颈，才另行定义完整 typed Protobuf 映射及兼容配置 |

集成取舍见 [ADR-0002](../adr/0002-go-wss-grpc.md)，实现约束集中在[部署](deployment.md)、[WSS](contracts/transport.md)和[gRPC](contracts/grpc.md)。交付检查须覆盖已提交命令断线、ReplyAck 丢失、旧凭据长连接、慢端与控制竞争、服务 deadline／取消、网关排空与集中重连；连接成功不能代替业务成功。

## 7. 生产分布式与基础设施

| 决策 | 采用的行为及依据 | 代价与改选条件 |
| --- | --- | --- |
| D-16 生产多可用区，托管优先 | 独立网关、应用与工作池跨三个可用区部署；单区已确认账本 RPO=0，控制／查询 RTO 目标≤60秒。托管数据库、对象存储和现有容器平台优先，不绑定厂商 | 同步写等待和故障剩余容量增加成本，平台仍须证明旧主隔离和完整提升。地域灾难使用异地灾备；要求跨地域自动写入时重开持久方案与延迟取舍 |
| D-17 外连接与内部实例生命周期分开 | 存活网关保持 WSS，内部流重新认证并受控绑定原服务，原命令查询恢复；网关退出、当前身份失效或内部恢复超限时结束所属外连接 | 网关维护有界请求和绑定状态，内部重绑保守触发订阅快照。若流数量或快照成本成为瓶颈，再评估短 RPC 与独立推送通道；不能静默丢提示 |
| D-18 收敛权威存储与持久工作 | PostgreSQL 保存分区事实、去重与 jobs，对象存储保存准确版本字节；默认数据库批扫、可丢通知唤醒。额外缓存／消息／索引按明确瓶颈引入 | 数据库承担领取、索引维护和恢复 IO，必须在单区故障及长期历史规模下压测。外部消息系统的收益须超过其发布、重投、容量和运维成本，不能仅凭用户数决定 |

记录见 [ADR-0003](../adr/0003-production-distributed.md)。完整拓扑、重启与发布程序归[生产部署](deployment-production.md)，数据布局和中间件比较归[存储专题](storage-and-middleware.md)。首阶段就在生产形态验证跨进程交接；可用性、性能和容灾数字均为待运行验收目标。

## 8. 收敛重复定义与派生状态

2026-09-27 用户确认下列四项消融建议。协议尚未发布，本轮统一修订正文、字段及用例，不增加旧字段或旧枚举的共存路径。

| 决策 | 采用的行为及依据 | 代价与改选条件 |
| --- | --- | --- |
| D-19 表单结构由业务请求唯一提供 | Surface input 块只引用准确 request_ref，Renderer 通过既有 request_read 读取业务 owner 的 Schema；省去快照副本及两份结构的兼容校验 | owner 不可达或请求修订过期时输入不可用，沿原等待／刷新规则处理。确需多种输入表达模型时，再定义显式映射；单纯标签差异不产生另一份字段约束 |
| D-20 连接内请求使用递增序号 | 客户端在实际发送 request 时分配 request_seq；网关保存最高已见序号及有限在途关联，包括后续返回 Error 的新请求。内部重绑保留序号，外连接另起命名空间 | 客户端须通过共同写循环编号，控制优先排队不能先编号后重排。去掉历史 ID 集合及 10000 次请求轮换；业务原身份、在途和字节限额保持。需要同连接乱序接纳新序号时才重评关联机制 |
| D-21 委派阶段为只读投影 | Delegation.phase 按同一已提交修订的创建、映射、未决责任及 Closure 生成，不再单独保存阶段状态机；工作由具体责任及 jobs 驱动 | 查询须读取一致事实并按明确优先级生成摘要；公开字段不一定含全部推导依据。持久 Closure 及清理后最小关闭记录继续保留。只有阶段本身产生独立业务决定时才另建状态 |
| D-22 离线租约合并开放阶段 | OfflineLease 使用 open／closed／reconciled；是否已知发生使用及累计用量从原使用账本读取，省去 allocated→in_use 的派生迁移 | open 不证明未使用或可以返还额度；首次消费仍与门禁检查、扣额共同提交。只有首次使用改变期限、费用或撤回资格时，才重新区分开放阶段 |

完整规则归[输入结构](interaction/implementation.md#21-输入-schema-子集)、[连接请求](contracts/transport.md#4-双向请求与主动交付)、[委派投影](collaboration/README.md)及[离线租约](security/README.md#offline)。逐项核对旧请求版本、错误响应后复用序号、内部重绑、创建未知、取消与费用迟到、首次使用与关闭竞争；运行步骤见[消融后的恢复验证](validation/fault-experiments.md#ablation-followup)。可执行计划、异步索引、冻结查询集合及 Task 总修订门禁维持原设计。
