# 四类请求的数据流程与提交边界

[默认应用入口](application-workflow.md) · [核心数据模型](core-data-model.md) · [参考项目读写对照](../../research/agent-harness-comparison/data-flow-io-comparison.md)

本页把六组核心对象落实到四条默认流程，说明读取哪些事实、保存哪些责任、何处可以共事务。它是当前设计的组织说明；原成功与恢复规则仍归各领域模块。本项目没有运行存储适配器，以下“阶段”不等于一条 SQL、一次事务或一次磁盘写入。

<a id="scenarios"></a>
## 1. 固定场景与计数口径

| 场景 | 本页固定的正常路径 | 不混入基线的工作 |
| --- | --- | --- |
| A：直接回答 | 暖 Session 中的新目标创建一个 Task；一个有模型的 Decision，零工具 Operation；既有条件可用本地确定规则核验 | 标题生成、压缩、模型质量评估、澄清、重试 |
| B：读后回答 | 新 Task；第一 Decision 提出读取现有短文本文件，原只读 Operation 返回后，第二 Decision 形成回答 | 文件历史索引、额外搜索、插件发现、工具内部未声明的请求 |
| C：冷恢复 | 在 A、B 或 D 的指定断点退出，重开原 Session；比较终点为历史、原关联及未决责任已恢复可查询，尚未发起新的模型请求 | 恢复后续行单独计量，不混入历史研究 C 的冷打开数值；重新打开不创建新目标，新增用户工作另记 |
| D：保存后读回 | 新 Task 的目标含生成报告、保存、独立读回与最终说明；第一 Decision 形成报告并提出保存，第二 Decision 在保存事实归并后提出读取，第三 Decision 形成最终说明；两次 Operation | 此处特意固定三次模型请求以便回放，不宣称是最少轮数；有限计划或确定性续行的另一实现另列计量 |

A、B、D 都选择消息正文 Content 引用、稳定模型与工具配置、无子任务／记忆提取／自动改善。每个 Decision 至多一次物理模型请求；本例没有额外规则 Decision。任务条件若需要新增评估行动，按其实际 Decision／Operation／Content／许可另计，不能为了符合表中轮数而跳过必要核验。D 的保存与读取必须分别获准；只把原写入参数回传不算读回。

| 计量项 | 如何记录 |
| --- | --- |
| 逻辑记录 | 记录创建／修订了哪些原对象与子记录；一份准确正文可被多处引用 |
| 数据读取 | 区分元数据／当前资格／准确字节／外部目标；有界批读和当前投影可以合并实际查询 |
| 持久阶段 | 记录业务必须已保存才能继续的点；一个阶段可写多条记录，合并须满足下文条件 |
| SQL／追加、事务、flush／sync、字节、物理 IO | 由实际适配器分别测量；不能从阶段数或 ContentRef 数推算 |
| 增量 | 初始化、恢复、辅助模型调用、权限补齐、流呈现和迟到结算各自附表，不折进暖路径平均数掩盖 |

<a id="scenario-a"></a>
## 2. A：直接回答

应用只操作提交、查询、读取成果。Task 统一组织目标、条件和结果，Brain 统一管理固定输入、调用及提案；无需对内部记录分别 CRUD。

| 阶段 | 对象与读取 | 保存的权威事实及后续责任 | 下一步成立条件 |
| --- | --- | --- | --- |
| A0 准备原提交 | Session 消息、准确目标 Content、受信路由与政策 | 内容 owner 保存准确字节及内容元数据；宿主保存原 Command、逻辑 Orchestrator、消息关联与交付责任 | 内容发布成功、原命令可恢复后才首发；消息保存不表示 Task 已创建 |
| A1 接纳 Task | 原命令去重、目标引用、当前主体及预算限制 | Task、目标与条件、预算、原回执、首个推进 job 在本域事务共同提交 | task.submit 的 applied 返回原 Task；Session 补关联可延后恢复 |
| A2 固定一轮输入 | 当前 Task／control／goal_revision、必要获准历史、准确内容与配置 | 保存本轮固定输入引用、decision_id、预算预留和原派发责任 | 旧快照或不可取必需内容不能发给 Brain；Session 全历史不自动成为输入 |
| A3 Brain 接纳与调用 | 原 decision_id／输入摘要、准确内容、全部来源与当前用途、固定模型配置 | 分别完成接纳，ModelCall 准备，包含最终编码依据的 send_started，输出终态四个基本持久阶段；许可原使用与正文发布见下文 | 发送门禁后仅发一次固定请求；completed 只证明提案已保存 |
| A4 Task 消费与核验 | `brain.get` 原提案和用量；当前目标修订、控制、条件与证据 | 本域一次消费原 Decision；归并费用、条件选择和下一责任。条件确有变化时先修订目标，旧提案余部失效 | 只有全部必要条件、目标覆盖及完成门禁满足，才进入成功裁决 |
| A5 固定结果 | 准确成果 Content、当前有效 ConditionResult、未结效果与费用事实 | 固定 Result、Task 终态、关闭新目标工作及必须保留的收尾责任共同提交 | Result 可从 task.result 查询；正文按当前权限另取 |
| A6 呈现 | 原 task.read／task.result、获准成果字节 | Session 保存原提交到答复的关联；Surface 发布带原来源修订的快照 | 正式提示在对应事实可读后发送，提示丢失可以重读 |

A4 与 A5 在全部依据已取得、无需新的外部处理且处于同一 Task 事务范围时可以共同裁决。不能先写成功再异步补必需证据。Result 已固定后迟到费用或证据缺陷沿原对象追加收尾／说明，不改写原结果或重开目标。

Brain 的四个阶段遵守[接纳与发送](brain/implementation.md#32-接纳事务)。ModelCall 准备与 send_started 是两个提交点，不能因共库合成一个发送后日志。生成正文另有固定 publication、字节保存与准确引用提交：外部 `content.put` 不放进数据库事务，已存字节失去答复时按原保存身份核对，不重新推理。无新字节时复用准确 ContentRef，不能按 token 创建 publication。

<a id="scenario-b"></a>
## 3. B：读取文件后回答

B 复用 A0～A3；首次提案消费后进入下列行动段，再以原 Task 进入第二轮 A2～A6。文件正文的业务读取与 Harness 自身元数据读取分开记录。

| 阶段 | 对象与读取 | 保存的权威事实及后续责任 | 合并或阻断条件 |
| --- | --- | --- | --- |
| B1 准入读取 | 原 Decision、当前 Task、准确 Capability／Binding、参数及所需用途 | Orchestrator 在消费原提案的事务中保存 operation_id、固定 OperationIntent、预留与原 Invoke 派发 job | 同一准入决定不按 Intent／预算／Job 分别提交；目标修订已变则本提案失效 |
| B2 接纳原操作 | Executor 核对原 Invoke、TaskGate、取消索引、绑定和容量 | Operation、原回执与执行责任共同提交 | execution.invoke 的 applied 表示接纳，尚不能当作读取成功；跨负责方答复丢失查原 Operation |
| B3 准备与实际读取 | 当前使用回执、控制、资源和安装资格；资源入口再次核对范围 | 准备事务保存 Attempt、原目标关联与核对责任；实际入口保存其适用门禁／占用事实 | 准备提交后才跨实际入口；资源 owner 不同则保留各自提交。文件读取在事务外，计为一笔业务读 |
| B4 归并原结果 | 读取返回字节及来源、完整性、原 Operation／Attempt、用量 | Executor 保存准确结果引用、效果／观察事实、费用、后续核对责任及适用 Finish | 先发布获准结果字节再引用；空文件、截断、失败与未知分别表达，不用显示摘要替换原结果 |
| B5 Task 归并并续行 | `execution.get` 的原身份与修订；当前 Task、条件、预算 | 本域按原来源修订去重，归并事实／账单，保存下一 Decision 的推进责任 | 通知只唤醒查询；完整输入在下一 A2 固定，不能让工具回调绕过 Task 准入直接调用模型 |
| B6 第二轮与完成 | 只把本轮获准文件内容和当前事实加入输入 | 第二个 Decision 沿 A3；随后 A4～A6 判断和呈现 | “模型已经回答”仍不是 Task 完成依据 |

Executor 每个正常 Operation 有接纳、Attempt 准备、原结果归并三个基本持久阶段，实际资源入口／占用等责任另计。与 Brain 不同，Executor 准备后崩溃而无法证明未交接时已须按可能发送处理；即使此例是只读工具，也按准确能力的重复与费用合同决定能否再次读取。规则见[Executor 公共接入](execution/implementation.md#reliable-work-integration)和[实际入口](execution/implementation.md#31-启动准备)。

<a id="scenario-c"></a>
## 4. C：冷恢复原工作及后续续行

冷恢复先取得当前认证、原负责方及只读／恢复资格，读取原宿主命令、Session 关联与业务记录；新动作接纳须另满足[就绪条件](deployment.md#recovery-readiness)。恢复不扫描聊天文本猜测“最后一句在做什么”，也不把 active 直接解释为可以调用模型。

与[历史研究 C](../../research/agent-harness-comparison/data-flow-io-comparison.md#1-统一场景与计数口径)比较时，**重建阶段**止于历史、原关联和未决责任恢复可查询、具体缺口可见，且尚未发起新的模型请求。此后按原控制、当前许可、预算及宿主就绪条件继续原工作，属于**恢复后续行**。下表同时列出两段的恢复规则；合法原首次模型发送等续行动作归入后段，按[CM-03](validation/core-model-scenarios.md#cm-03)分别记录。

| 断点 | 必需读取 | 条件写入与后续动作（分段计量） | 必须保持的身份与结果 |
| --- | --- | --- | --- |
| Task 创建后，Session 关联回写前 | 原服务的命令回执、返回 Task、原消息关联 | 补同一 Task 关联与交付完成记录；回执未知继续有界查询 | 一个 submit_command_id 对原 Task，不另建 Task |
| 结构化回答 queued／sending | `interaction.input_read`、原目标回执、准确请求与消费状态 | queued 原规则转交或撤回；sending 查固定目标命令并保存原消费投影 | 原 input_id／request_id／target_command_id；sending 不因超时变 withdrawn |
| Brain 已准备但无 send_started | 原 Decision／ModelCall、固定输入、当前控制与许可 | 恢复领取与门禁按原事务保存；恢复后续行在原身份上重新检查后允许原首次发送 | 不创建第二个 ModelCall，不把恢复当新预算 |
| Brain 已有 send_started，结果未知 | 原供应方调用标识与原 Decision、费用事实 | 查原调用；不可查则保存 provider_result_unknown、等待／收尾责任，不透明重发 | 原 Decision／ModelCall 保留，用户能看到不确定性 |
| 文件写入后，Executor 答复丢失 | 原 Operation／Attempt、准确目标键、可用目标证据和当前控制 | 查询／核对原效果，去重归并并更新原 Task；无依据则保留 unknown | 已可能写入不能换 operation_id 重写，Task 取消也继续核对 |
| Task 已终态，原账单或效果晚到 | 原 Task 终态与原收费／Operation 修订 | 归并原来源差额和必要收尾，不准入新的目标行动 | 固定 Result／取消决定不变，费用与效果仍可解释 |
| 仅 Surface 或本端缓存丢失 | 原 Surface／Task／InputSubmission、当前可读 Content | 重建投影及本端呈现；来源已关闭则呈现缺口 | 零新增模型与工具调用；旧输出不能覆盖另一 Task |

读取原对象、接替 Claim、必要续约、保存新查询事实和恢复投影都可能增加存储操作；只读远端查询也可能计费。C 的两段分别记录查询次数、目标观察、恢复提交与字节，不把它们填成固定零次，也不按每条旧消息计一次重放写入。恢复后续行的模型／工具请求、效果核对和收尾不混入重建计数，也不与 A／B／D 的剩余工作重复相加。原数据不足、负责方不可达或权限已撤回时，保留具体缺口及获准恢复入口，不能通过更换身份消除未知。

<a id="scenario-d"></a>
## 5. D：生成报告、保存文件并独立读回

D 采用第 1 节固定的三轮回放：生成／保存，提出读回，读回后答复。该选择让不同实现的模型次数明确；未来使用已冻结有限 Plan 自动提出下一行动时，应另报其实际 Decision 数，不把少一轮推理误记为少保存一份外部效果。

| 阶段 | 对象与读取 | 持久事实及下一步 | 不能省略的依据 |
| --- | --- | --- | --- |
| D0 建立条件并生成报告 | A0～A3；读取用户指定目录、准确目标与配置 | 第一 Decision 发布准确报告 Content；Task 固定所需保存与读回条件 | 条件不足时按原规则澄清／修订，新增轮次另计 |
| D1 准入并保存 | 读取准确报告版本、规范化路径、绑定、Grant；按 B1～B4 执行写 Operation | 原 Intent 固定字节／目标，Executor 保存写入的尝试、效果、目标证据与费用 | 文件系统／远端目标写发生在事务外；写回执与实际目标效果分别表达 |
| D2 归并保存事实 | `execution.get` 原写操作与当前 Task；记录已发生效果或 unknown | Task 去重归并写事实；正常已核实写入后建立第二 Decision，由其提出读回 | 未知写入走 C 的原操作核对；不为取得“成功”而另造相同写操作 |
| D3 准入并读回 | 当前目标版本／观察条件、原报告 hash、读权限及准确读取能力 | 第二个 Operation 从实际目标独立读取；保存读回 Content、来源／目标身份和完整性 | 读回不能只读取 Brain 缓存或原写入参数；工具显示文本不代替原字节 |
| D4 核验准确成果 | 原写 Effect、独立读回事实、目标修订、报告版本与条件规则 | Task 保存或选择与准确成果绑定的 ConditionResult；第三 Decision 形成目标所要求的最终说明 Content，原提案消费后才进入 D5，费用沿原调用记录 | 路径、版本、hash 或内容不符合条件时保留缺口；历史 applied 不随用户后改文件而改成未写 |
| D5 固定结果与恢复入口 | 当前全部必要条件、目标覆盖、未决责任；A5～A6 | Result 引用报告及完成依据；Session 关联原 Task 和答复 | 答复中的“已保存”不能替代目标证据，Task 成功不承诺文件永远不变 |

声明写入幂等、可核对或可安全重试的能力必须有对应目标合同。存储报告 Content 成功不等于用户指定文件已保存；文件写成功也不等于报告 Content 当前仍允许披露。保存、读回、条件通过三者保持独立事实，应用用一个结果视图呈现它们。

<a id="transaction-boundaries"></a>
## 6. 可合并的事务与必须保留的屏障

单进程开发装配允许已声明的参与者共享受限事务句柄。生产保持固定逻辑 Orchestrator、各自本地事实和工作责任；同库本身不能授权跨模块任意写入，同进程也不代表所有内容和目标都位于同一事务。

| 相邻记录或步骤 | 可以共同提交的范围 | 必须保留的边界 |
| --- | --- | --- |
| Session 消息、原 Command、交付 outbox | 应用自身的一次本地事务 | 跨库 Task 接纳后再补关联；原命令查询承担中断恢复 |
| InputSubmission 与原请求消费 | 已装配的同宿主共库交互／业务参与者可共享受限 Tx | 分库时分别提交转交与消费，原目标命令及 queued／sending 竞争仍保留 |
| Task 接纳、目标、预算、回执、首 job | 同一次 Orchestrator 接纳事务 | 准确目标字节先保存；不等待外部存储或调用在事务内完成 |
| Task 的固定输入派发与本地 Brain 接纳 | 仅已声明共用受限 Tx 的本地参与者 | 独立 Brain 保存自身接纳，调用方保留派发／原回执恢复；模型准备与 send_started 仍分开 |
| Task 消费、预留、OperationIntent 与 dispatch job | 同一次行动准入事务 | 远端 Executor 接纳有独立事实；不会因一个组合视图就获得跨库原子性 |
| Executor 接纳、准备或结果阶段的各自子记录 | 阶段内部的领域事实、费用及 Raise／Finish 按原锁序共同提交 | 接纳、Attempt 准备和目标结果有时序依赖；准备提交后才交实际入口，资源 owner 的门禁按其责任保留 |
| 同域 Grant 使用与实际启动登记 | 既有合同允许的同一受信本地事务范围 | 独立 Grant owner 必须沿固定 use_id 裁决／查询，不能先发送后补许可或承诺跨 owner 即时撤权 |
| Task 事实归并、核验选择与 Result | 全部证据已取得且本轮可合法完成时，使用同一 Task 事务 | 新核验行动、正文发布或远端查询在事务外；需要结果后再决定的提交不能预先成功 |
| 生成正文、Content 元数据与引用 | 字节耐久后，符合内容协议的本地元数据可共同提交 | 对象存储／原内容 owner 与领域库不假装原子；保留原 publication／上传命令与孤立内容清理 |
| 正式 Surface 快照与变化提示责任 | Surface owner 本地事务 | 提示实际发送在提交后；provisional 片段不逐 token 提交，也不取得正式结果资格 |

同一物理事实只保留一份权威正文，必要引用、控制与消费记录仍在各负责方保存。可重建投影可以从原对象批读或增量更新，但已用于 Decision 的准确输入不可用“当前最新视图”替换。合并事务的目标是共同裁决必要记录，不是让一个长期事务跨越模型、工具、网络和用户等待。

<a id="measurement"></a>
## 7. 如何核对收敛效果

在上述固定条件下，A／B／D 分别有 1／2／3 个模型 Decision，0／1／2 个工具 Operation。按现行设计对应 Brain 域 4／8／12 个基本持久阶段，以及 Executor 域 0／3／6 个基本持久阶段；**这不是请求总事务数，更不是 SQL 或 fsync 总数。** 正文发布、Task、原授权使用、资源入口、领取、正式呈现、合法合并和迟到结算都需要在实际适配器中单列。

附加工作使用同一归属：标题、摘要、修复等推理各有自己的 Decision；查原调用和效果的恢复不得伪装为新推理；实际使用裁决可能写库，不能计成纯缓存读。已有当前投影可以减少历史读取，静态小目录无需每轮动态发现，未启用长期记忆、协作和发布不创建对应对象。

C 按第 4 节的重建终点与恢复后续行分别列账。与历史研究比较只取重建段；需要评估恢复至任务继续或完成的总成本时，再明确附加后段及其终点。

后续运行记录至少固定输入、历史、目标初态、模型回放、工具绑定、输出分块、存储装配及断点。比较正常／恢复路径的实际调用、逻辑记录、字节、SQL、事务与 sync，再判断事务合并或正文复用是否降低成本。验收沿[应用入口](application-workflow.md#entry-points)，使用[HAR 场景](validation/harness-scenarios.md)及各模块现有向量；当前仅交付可检查的流程设计，不登记运行通过或性能下降比例。
