执行适配器把 Lerna 和外部世界连起来：把动作翻译成目标系统的协议，调用它，然后**如实回报**看到了什么。它可以对效果提出主张，但**不得写效果**，也不得自行决定重试；效果由执行管理裁决，任务是否完成由任务编排裁决。

本接口的核心约定：

- **三个行为接口**：执行、查询、观察，共用一种回报和证据格式；
- **能力按具体能力声明**，分维度表达外部效果、幂等、查询、迟到终局和计费，并附验证依据；未声明或无依据的维度一律按最保守的取值处理；
- 超时、断线、取消和"查无记录"，都**不能单独证明未生效**；
- 每获得一次核心的发送许可，**最多发送一次**有副作用的业务调用。适配器、SDK、代理和认证中间件都不得自行重发。

## 1 职责与边界

| 负责方 | 负责的内容 | 与执行适配器的分界 |
| --- | --- | --- |
| 执行适配器 | 能力声明；协议转换；参数检查；执行、查询、观察；对原始观察的解释 | 可以提出效果主张，不得写核心的效果或任务状态。原始观察由可信出口固定，适配器只能引用它们并提交派生解释 |
| 执行管理 | 尝试标识、原参数、执行端点、发送记录、效果、核对、重发决定和收尾 | 效果的唯一写入方（R3） |
| 出口闸门 | 在实际出口核验凭据、发送许可、授权和资源范围，关联用量 | 适配器所有的网络、文件和设备访问都经过这里（R2） |
| 任务编排 | 条件版本、准入、取消和完成门禁 | 推理选择工具仍然只是提议，执行必须经 R1 |
| 内容治理 | 证据内容的来源、版本、用途、派生和清理 | 适配器不建立脱离治理的结果缓存 |
| 预算、运行记录 | 实际计费来源、关联轨迹 | 适配器回报，不自行结算或改写记录 |
| 扩展管理 | 版本、兼容性、验证范围和启用状态 | **安装成功不自动获得幂等、可查询等保证** |

共同约束：

1. 核心可见的对象和接口定义属于核心契约；核心不依赖具体适配器（R6）；
2. 适配器无权自主推进任务、扩大权限、重试有副作用的调用或自动补偿；
3. 适配器丢失内存状态后，核心仍能找到原动作、尝试、目标和恢复依据；
4. 同一执行端点内替换进程或工作者，不改变责任归属；不得把未知的动作改派到另一个端点重新执行；
5. 普通的网络返回不构成 G3 的持久接纳确认。

## 2 对象

### 2.1 能力声明

声明**按具体能力**提供，不得给整个适配器贴一个"幂等"的标签。五个基本维度沿用[核心契约](../../core/contracts/README.md#24-能力声明)，这里补充适配器需要额外声明的内容：

| 字段组 | 必须包含 | 缺省或无依据时的处理 |
| --- | --- | --- |
| 身份与版本 | 适配器标识、实现版本、契约版本、声明摘要；目标协议和目标版本范围 | 版本不兼容就拒绝执行 |
| 能力 | 能力标识、输入和输出结构、允许的参数范围 | 未知能力拒绝 |
| 适用条件 | 目标账户、资源范围、部署环境、依赖、并发条件、有效期 | 无法确认条件时不使用强保证 |
| 权限与用途 | 执行、查询、观察各自需要的权限；读取、保存、同步的限制 | 不从执行授权推出其他用途的授权 |
| 外部效果 | 是否只读；可能创建、修改、删除、发送或触发哪些效果；是否可能部分生效 | 视为有副作用，且不是原子的 |
| 幂等 | 无 / 目标原生去重 / 有条件的效果幂等；外部键怎样映射、作用范围、参数匹配规则、保留期 | 不采信 |
| 结果查询 | 按尝试标识 / 仅按目标回执 / 资源观察 / 不支持；可见性延迟、保留期、能否证明终局 | 不可查询 |
| 观察 | 支持的环境或资源、版本和完整性信息、读回方式 | GUI 能力没有观察就不合格 |
| 计费 | 计费方式、用量来源、是否会迟到、更正、重复计费的可能 | 计费且上界未知 |
| 验证依据 | 测试集版本、目标版本、运行配置、验证时间、已知限制 | 超出验证范围的调用按保守处理 |

"只读"只限定业务效果；只读调用仍可能产生用量和审计记录，要按 G5、G10 处理。

**使用强保证的规则**：原尝试保存的声明、当前实现的声明、当前的适用条件、有效的验证依据，必须**共同**支持这次恢复。升级、回滚或目标变化，不得追溯地增强旧尝试的保证；保证收缩时，停止自动重发。

为什么不能直接相信协议层的提示：MCP 的工具注解规范明确说明注解只是提示，不能保证忠实描述行为，并且默认取最保守的值：`readOnlyHint=false`、`destructiveHint=true`、`idempotentHint=false`、`openWorldHint=true`（[MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)、[schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/38c84e9f93ad191d9eb26d92b945d17bd0efcaf3/schema/2025-11-25/schema.ts#L1166-L1220)）。HTTP 也一样：RFC 9110 中幂等只指"重复请求的预期效果相同"，不要求响应相同，也不排除日志等附带行为；HTTP 202 只表示已接收处理，处理尚未完成（[RFC 9110 §9.2、§15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)）。所以 HTTP 方法、状态码和 MCP 注解只能辅助解释，不得代替对目标系统的核实。

### 2.2 执行输入

| 字段组 | 内容与约束 |
| --- | --- |
| 关联 | 用户、任务、动作、尝试标识、条件版本 |
| 绑定 | 原执行端点、适配器和声明的版本、能力、目标系统和目标账户 |
| 参数 | 固定的参数或不可变的内容引用；摘要用于检查一致性；会影响效果的默认值、随机值在第一次发送前固定 |
| 准入依据 | 持久准入记录、授权、预算依据的引用 |
| 出口上下文 | 当前有效的凭据、本次发送的序号、工作者版本、期限 |
| 前置条件 | 目标资源版本、观察引用或设备控制版本；不支持的条件要明确拒绝或降低保证 |

出口凭据可以更新，但不得借更新凭据改变目标账户、资源范围、参数或原责任。

### 2.3 回报与证据

执行、查询、观察使用统一的外层格式：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 契约版本、回报标识、产生方及实现版本 |
| 关联 | 用户、任务、动作、尝试、本次发送；目标的回执和业务标识 |
| 来源与时间 | 实际取得内容的来源和时间；可用时附目标版本、序号和读取区间 |
| 执行情况 | 未执行 / 已受理 / 进行中 / 已结束 / 未知；原始状态码、错误类别、诊断 |
| 效果主张 | 已生效 / 未生效 / 未知；明确这个主张覆盖哪些资源和效果 |
| 终局依据 | 哪项证据证明目标处理已结束，或证明不会再迟到生效；必须引用可信出口登记的原始观察。适配器给出的终局依据只是候选，强结论由受信解释规则判定 |
| 内容引用 | 不可变的内容版本、摘要、来源、派生关系、用途和端侧保留要求 |
| 用量 | 计费来源标识、数值、单位、暂估或更正版本 |

| 证据种类 | 必须包含 | 能证明什么 |
| --- | --- | --- |
| 执行回报 | 目标回执、执行阶段、原始响应、终局语义 | 按目标约定解释后的执行事实；受理回执通常只证明"已受理" |
| 观察结果 | 观察范围、实际内容、时间、版本、完整性；GUI 还包括页面和控制状态 | 某一时刻看到的状态 |
| 读回 | 资源身份、实际值或摘要、资源版本、读取来源；与原尝试的关联方式 | 条件是否满足；关联充分时，可以进一步核对这个动作的效果 |

关键限制：

- "资源当前符合预期"可以支持某个条件，但不一定证明是原尝试造成了这个状态；
- 当前值不符合预期，也不能证明原尝试从未生效：它可能生效之后被别人改了；
- 部分生效必须逐项报告，不得包装成全部成功或全部未生效；
- 截图、文本和结构化结果都是内容，适配器不得在日志或缓存里另存不受治理的副本；
- 核心同时保存适配器的主张和自己的裁决，不会把主张直接写成权威的效果。

### 2.4 适配器需要支持表达的状态

适配器只回报，但共同接口必须能表达以下核心状态（定义见[执行管理](../../core/ledger/README.md#22-状态维度)）：出口情况（待出口、可能已发出、出口已封闭）；效果（未知、已生效、未生效）；迟到可能性（可能、已排除；缺少证据时默认"可能"）。

| 事件 | 状态变化 |
| --- | --- |
| 准备实际发送 | **先持久记录"可能已发出"**，再访问外部 |
| 收到受理回执 | 记录"已受理"；效果通常仍未知 |
| 超时、断线、工作者崩溃 | 保持未知，进入核对；不转为未生效 |
| 拿到覆盖充分的效果证据 | 执行管理裁决已生效或未生效 |
| 查无记录、记录过期 | 保持未知，除非同时拿到适用的终局证明 |
| 出口已封闭，且能证明尚未发出 | 只有原执行管理负责方的内部封闭证明能证明"尚未发出"（[执行管理 2.3](../../core/ledger/README.md#23-收尾依据)），适配器的自报不算；证明成立后可以裁决为未生效并收尾 |
| 收到迟到的结果 | 追加证据，由原执行管理负责方重新裁决；已取消的任务不会因此恢复推进 |

## 3 接口

| 接口 | 输入 | 输出 | 成功含义 | 幂等性 |
| --- | --- | --- | --- | --- |
| **执行**（尝试标识，参数，执行上下文） | 2.2 的执行输入 | 执行回报和证据；可以是"进行中"或"未知" | 这次调用拿到了有效的回报；**不等于任务完成，也不构成持久接纳确认** | 业务效果是否幂等取决于声明；核心只在允许时才重新调用 |
| **查询**（尝试标识，查询上下文） | 原尝试，以及核心保存的目标关联信息；当前的读取凭据 | 查询证据、进行中、查无记录、记录已过期或不支持 | 拿到一次查询结果；不保证效果已确定 | **查询不得重新执行原动作**；结果可能随时间变化；费用另记 |
| **观察**（范围，观察上下文） | 用户、端点、资源或设备范围；读取凭据；可选的原尝试关联 | 观察或读回证据 | 拿到声明范围内的实际内容 | 不得改变业务状态 |

细则：

1. 所有实现都提供查询接口；不具备查询能力时明确返回"不支持"，不得伪造"未生效"；
2. 观察是可选接口：GUI 必须有；API 和文件可以用它提供资源读回；
3. 同一尝试标识对应不同的参数、目标或能力时，拒绝；拒绝这次请求并不消除原尝试的未知状态；
4. 查询、观察、获取结果资源和各种辅助请求，也都经过出口闸门，有持久的访问记录、当前授权和用量关联；
5. 错误诊断和效果分开返回。不能提供充分证明的超时、异常、取消或依赖错误，效果就是未知；
6. **不提供通用的 `retryable=true`。**适配器可以回报目标建议的等待时间，但重试许可由核心判断。AWS Well-Architected 把多层重试、无上限的重试、未验证 SDK 行为都列为反例，建议在单一层控制重试（[AWS 2023](https://docs.aws.amazon.com/wellarchitected/2023-04-10/framework/rel_mitigate_interaction_failure_limit_retries.html)）。

**异步回报**：适配器通过核心提供的回报入口提交同样格式的证据；核心持久接纳后才确认，重复回报按回报标识去重。回报的重投不得触发目标动作，进度通知也不得成为唯一的恢复依据。

**发送链路必须整体检查。**只检查适配器自己的代码不够：stripe-python v12.0.0 的 HTTP 层有受 `max_network_retries` 控制的重试循环，请求构造会在未提供幂等键时为 POST 生成随机键（[HTTP 实现](https://github.com/stripe/stripe-python/blob/v12.0.0/stripe/_http_client.py#L182-L201)、[请求构造](https://github.com/stripe/stripe-python/blob/v12.0.0/stripe/_api_requestor.py#L500-L506)）；MCP TypeScript SDK 1.25.0 在某些认证流程完成后会再次发送原消息（[streamableHttp.ts](https://github.com/modelcontextprotocol/typescript-sdk/blob/2b20ca95735e82a2ba7c47c9bd303057601b7f8e/src/client/streamableHttp.ts#L489-L548)）。必须显式传入核心保存的标识，关闭 SDK 的自动重试，并在实际出口计数验证。

### 3.1 与 MCP 的桥接

MCP 提供工具发现、调用和结构化结果的互操作格式，但缺少 Lerna 的责任、准入和效果语义，所以不直接作为核心契约，而是桥接为 Lerna 的执行适配器。普通的 MCP 工具可以接入，但没有经过验证的强保证时，一律采用保守声明。

| MCP 能力 | 在 Lerna 中的映射与限制 |
| --- | --- |
| `tools/list`、输入输出 Schema | 转成版本化的能力描述，保存实际的声明快照；列表变化后必须重新核验，不改变旧尝试的绑定 |
| `tools/call` | 映射为"执行"；调用只能由执行管理发起，推理不得直接调用 |
| JSON-RPC 请求 ID | 只用于消息关联；Lerna 的尝试标识独立持久保存。MCP 规定请求 ID 在同一会话内不能复用（[基本协议](https://modelcontextprotocol.io/specification/2025-11-25/basic#requests)） |
| `annotations` | 作为待核验的提示，不直接授予安全重发的许可 |
| `content`、`structuredContent`、`isError` | 保存为证据和诊断；不直接映射为任务完成或未生效。通过 `outputSchema` 校验的成功文本，仍可能没有实际效果 |
| 资源读取或观察工具 | 经当前读取授权和出口闸门执行，转成观察或读回证据 |
| Tasks（实验特性） | 保存尝试与目标 Task ID 的关联，按目标的保证解释状态和结果；它不等同于 Lerna 的任务 |
| SSE 恢复 | 允许用 `Last-Event-ID` 恢复原消息流；不得因此重新发送有副作用的 `tools/call` |
| 取消和超时 | 只是停止等待或请求停止；原动作的核对责任保留 |

MCP Tasks 改善了长时间调用的查询能力，但它有几个限制：Task ID 由接收方生成，创建回报一旦丢失，查询标识也就丢了；有效的取消必须先进入 `cancelled`，**即使执行随后继续完成**也保持这个状态；取消后可以立即删除，TTL 到期后任何状态的任务和结果都可以删除（[Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)）。所以 `cancelled`、已过期和"Task 不存在"都不是"未生效"或"不会迟到"的证明。MCP 的普通取消通知也可能被忽略，规范建议发送方忽略之后到达的响应（[取消](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)），而 Lerna 必须独立地归集这些迟到的证据，不得把"停止等待"当作"动作结束"。

增强接入时，可以要求目标支持调用方的业务标识和查询接口。但把尝试标识放进 `_meta`，并不会自动让目标支持去重；这种行为必须有明确的约定和验证。认证必须在有副作用的调用之前完成；认证挑战不得授权 SDK 自行扩大权限或重新发送。

## 4 关键流程

正常执行的持久化点见[出口闸门 4.1](../../core/egress/README.md#41-正常调用)；结果未知之后的恢复策略见[执行管理 4.2](../../core/ledger/README.md#42-结果未知后由能力组合决定策略)。适配器在其中的职责：

1. 收到执行请求时，校验参数、目标和声明版本与原尝试一致；
2. 只在出口闸门放行后进行**一次**调用；
3. 拿到回报后，把原始响应、读回和用量整理成统一格式提交。原始观察由可信出口在实际 I/O 处登记，适配器只引用它们，不能把自己生成的内容登记成原始观察；
4. 被要求查询时，按声明的关联方式查询原尝试，不重新执行；
5. 被要求观察时，只读取，不改变业务状态。

**GUI 适配器**执行"观察 → 一次动作 → 再观察"，所有访问都经过出口闸门；设备被用户接管或控制代次改变后，旧的发送许可失效；核验由核心依据证据完成。**用户取消**时，未发出的尝试封闭出口，已发出的继续核对；向目标发送取消请求本身是一个经过准入的动作，取消回报不得自动关闭原动作。**外部 Agent** 把一次委派表达为一个长时间运行的动作，接入前必须明确其权限范围、预算约束、结果关联和取消语义；只接受远程 Agent 的自我声明，不足以证明 G7。

**证据的信任边界。**宿主能确认"这份内容由插件生成"，不能确认"这些字节由目标系统在这次查询中返回"。所以第三方适配器可以做协议解析、提取候选字段、包装易用性，但"未生效""不会再迟到生效"这类强结论，只能由执行管理判定：从未开放出口的动作用原执行管理负责方的内部封闭证明，可能已发送的动作按受信解释规则基于原始观察判定。适配器不能提交"从未发送"的声明来代替内部封闭证明（见[执行管理 2.3](../../core/ledger/README.md#23-收尾依据)）。受信解释规则属于受信实现，经审查发布；普通插件不能通过自带"终局验证器"取得裁决权。没有受信解释规则的能力，按最保守的能力处理。三种职责要分开：**观察采集**由可信出口完成；**普通解析和解释建议**可以由第三方适配器提供；**终局解释**由受信解释规则完成。M1 只运行受审查的参考适配器，但从 M1 起受信解释规则就有独立的装配和审查身份（代码位置见[开发规范 2](../../../development.md#2-目录骨架)），替换普通适配器不会替换终局规则；开放第三方执行适配器（M4）前，这一划分必须经过验证。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 任务编排、原执行管理负责方 | 核心交接按原标识查询，不新建责任；外部回执丢失则按声明的方式核对；没有可用的关联方式时保持未知 |
| 进程崩溃 | 持久工作、原执行管理负责方 | 接替的工作者读取持久记录；"可能已发出"之后按可能已发送处理；之前的，也要先封闭旧工作者的出口，才能确认尚未发送 |
| 重复请求 | 持久工作、执行管理、出口闸门 | 核心命令去重，检查参数绑定；重复投递不会自动获得新的发送许可；允许的重发必须单独持久决定 |
| 并发冲突 | 执行管理、出口闸门、目标系统 | 核心拒绝过期的工作者；适用时使用目标的版本前置条件。重发收到版本冲突，不能证明之前那次没有生效 |
| 依赖不可用 | 执行管理 | 暂停执行或核对；明确没越过出口的失败只说明这一次没发；不覆盖原尝试已有的未知状态 |
| 迟到的结果 | 原执行管理负责方、预算 | 归入原尝试，去重后重新裁决；不因工作者租约过期而丢弃真实证据；不恢复已取消的任务 |
| 授权撤销 | 授权、出口闸门 | 停止相关的新出口；核对也必须有当前的读取授权；没有查询权限时保持未知 |
| 记录过期或查询返回不存在 | 执行管理 | 不认定为未生效；依据目标的保证判断是否还有核对路径 |
| 适配器升级或回滚 | 扩展管理、执行管理 | 保留旧声明和目标关联；新实现只在兼容范围内接续原责任，否则等待 |
| 宣称已终局之后仍迟到生效 | 执行管理、扩展管理 | 记为契约违反，停止采信该能力的强保证，核查受影响的动作；原证据和 Result 保留审计记录 |

## 6 不变量落实

| 不变量 | 本接口怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 未知被独立表达；只有目标的查询证明或适用的幂等保证才支持重发 | 丢回报、弱查询、迟到请求、幂等期限过期后，核对真实效果的次数 |
| G2 | 执行情况、效果和终局依据分开；证据写明覆盖范围；适配器不得写任务终态 | 受理回执、部分生效、伪造的成功文本、过期的读回，都无法通过完成门禁 |
| G3 | 核心持久接纳后才确认；证据先持久可访问再确认；恢复不依赖通知 | 在各持久化点前后崩溃，已确认的责任都能找回 |
| G4 | 绑定条件、授权和预算；每次实际出口再核验 | 条件改变、撤权、额度不足、旧工作者发送，都被拒绝 |
| G5 | 执行、查询、观察、认证、获取结果和辅助访问全部经过出口闸门 | 拦截网络、文件和设备访问，核对每次访问的核心记录 |
| G6 | 推理只提交提议；发送和完成由核心裁决 | 直接调用执行接口、伪造完成声明都无效 |
| G7 | 能力所需的权限不超过已获的授权；不自动扩大认证范围 | 越界资源、替换账户、增加权限、嵌套调用都被拒绝 |
| G8 | 执行、读取、保存和同步分别约束；每次访问检查当前授权 | 只有执行权限无法读取或保存；撤销后缓存和读回不得继续使用 |
| G9 | 证据和派生缓存登记到内容治理，支持停止使用和清理回报 | 删除后搜索所有存储、缓存和日志副本 |
| G10 | 实际计费来源单独关联；发送、查询、观察可以各自产生用量 | 重复、迟到、更正的用量都不重复计数；取消不抹掉费用 |
| G11 | 尝试、目标和执行端点固定；进程接替不改派责任 | 重启、断线和取消之后，不存在借新标识重新执行的旁路 |
| G12 | 用户身份绑定凭据、尝试、证据和目标账户；执行资源有上限 | 跨用户的标识、内容引用和账户访问被拒绝 |

## 7 取舍

| 问题 | 选择 | 被否决的方案及理由 |
| --- | --- | --- |
| 接口形状 | 执行、查询、观察三个接口，共用证据格式 | 只有同步执行、返回成功或失败：无法表达未知和核对；每类适配器各定义一套完整的工作流协议：会复制核心的职责 |
| 副作用怎样表达 | 分维度声明，附适用条件 | 四选一的枚举：表达不了"幂等且可查询"；按 HTTP 方法或 MCP 注解自动推断：强保证依赖不充分 |
| 尝试标识 | 同一尝试保持标识，每次发送另有序号 | 每次发送生成新标识：丢失原责任的关联；用参数摘要作为标识：会把用户有意的两次相同动作合并 |
| 证据格式 | 结构化回报 + 原始证据引用 + 覆盖范围 | 只有布尔值、状态码和文本：无法验证 G2 |
| 重试和取消 | 执行管理决定，出口闸门逐次核验 | 适配器和 SDK 自行重试：难以落实 G4、G10、G11 |
| 怎样采信声明 | 核实目标约定 + 独立一致性测试 + 版本绑定 + 运行时检测 | 安装时直接相信自我声明：声明错了就破坏 G1、G2、G7 |

在适配器外面包一层本地去重缓存，并不能给任意第三方调用增加"恰好一次"的保证。RIFL 实现恰好一次，需要请求的唯一标识、**与状态变更原子持久化**的完成记录、重试能找到原记录，以及安全的记录回收（[RIFL §3–4](https://web.stanford.edu/~ouster/cgi-bin/papers/rifl.pdf)）。强幂等声明必须追溯到实际产生效果的目标系统。

尝试身份的语义、核心对事实的归属、证据与内容治理的关系、强声明的信任前提，正式采纳前必须写成 ADR。

## 8 待定事项

| 假设 | 验证方法 | 不成立时 |
| --- | --- | --- |
| 首批目标支持按调用方标识核对 | 核实固定版本的约定；丢失创建回报后再查询 | 降为"只能按回执查询"或"不可查询" |
| SDK、HTTP 库、代理和认证路径可以禁止有副作用的重发 | 在实际出口计数，注入断线、401、403、重定向、连接重建 | 更换或改造发送实现；做不到就不启用 |
| 目标的保留期覆盖核对和重发的窗口 | 测试边界、长期离线和延迟的请求 | 到期之前停止重发；到期之后保持未知 |
| 查询能提供"终局不存在"的证明 | 延迟原请求，让查询先返回，再放出原请求 | 证明失败时，"不存在"只作为弱观察 |
| 证据保存和调用开销可以接受 | 测量持久写入、读回、查询延迟和证据体积 | 优化批量登记和通知，保持事实语义不变 |

## 9 M1 范围

| M1 必须实现 | 最低深度 |
| --- | --- |
| 执行与查询的共同约定 | 完整定义标识、参数绑定、错误、未知和证据；不支持查询时明确回报 |
| 版本化声明 | 五个维度齐全，缺省保守；保存首次执行时的声明 |
| API 参考适配器 | 对明确的目标约定提供经过验证的能力；通用的请求能力采用保守声明 |
| 文件参考适配器 | 明确允许的文件操作和故障范围；写入回报与实际读回分开；追加不得默认声明为幂等 |
| 故障模拟 API | 覆盖"幂等""可查询但不幂等""不可查询也不幂等"三类；查询可以滞后，效果可以迟到 |
| 出口全覆盖 | 包括模型调用和适配器的查询、观察、辅助请求；参考实现没有隐式的有副作用重试 |
| 一致性测试入口 | 同一套测试同时用于参考实现和将来的第三方实现，验证实际行为 |

M1 不必实现完整的 MCP 桥接或实验性的 Tasks 支持；但如果第一个 API 后端选的是 MCP，它的发送、超时和证据行为同样必须通过 M1 的测试。M1 只运行经过审查的参考适配器；插件沙箱实现之前，不得宣布任意第三方适配器已满足 A2、G5、G7。

| --- | --- | --- |
| 完整的用途限制、删除传播、预算结算 | M2 | 来源、派生、用途、用量标识和更正字段 |

## 10 测试要点

测试以**独立的目标**为事实依据：记录真实的业务效果、收到的业务请求、目标的状态和用量。仅断言适配器返回了"幂等"或"成功"，不能验证声明的真实性。

### 10.1 声明一致性

| 声明 | 关键用例 | 通过标准 |
| --- | --- | --- |
| 只读 | 覆盖正常、错误、超时、取消路径，对比业务状态 | 没有声明范围之外的业务变更；用量仍有记录 |
| 目标幂等 | 串行和并发重复原标识；丢回报后重发；目标重启 | 在声明范围内不产生额外的业务效果 |
| 参数绑定 | 原标识改变参数、账户、资源或能力 | 新请求被拒绝；原记录和未知状态保留 |
| 幂等保留期 | 期限前后重发；长期离线；迟到的请求 | 核心不在已失效的保证上自动重发 |
| 按尝试查询 | 丢弃创建回报、重启适配器后按原标识查询 | 不依赖已丢失的回执，仍能关联到真实的目标结果 |
| 终局未生效 | 查询先返回"不存在"，然后再放出被延迟的原请求 | 声称"终局未生效"时，原请求确实不可能随后生效 |
| 观察或读回 | 错误的资源、旧版本、不完整的页面、被其他主体修改 | 证据如实声明范围和版本，不伪造因果关联 |
| 不自行重试 | 注入超时、断线、认证挑战、重定向和代理错误 | 每个核心发送许可只对应一次有副作用的业务调用 |
| 版本兼容 | 升级、回滚、修改声明或运行配置 | 旧尝试的保证不会被追溯增强；超出验证范围的按保守处理 |

### 10.2 故障注入

| 用例 | 必须检查 | 对应 |
| --- | --- | --- |
| 在各持久化点前后分别崩溃 | 已确认的责任存在；目标可能已生效时保持未知；恢复时没有旁路发送 | G1、G3、G11 |
| 伪造或嫁接的终局证据：Schema 正确的伪造终局、把另一次调用的真实响应嫁接到本次、跨账户证据、篡改取得时间、把旧查询当作当前终局 | 核心拒绝强结论，保持未知；真实的迟到观察仍被接纳；替换普通适配器后，原始观察和受信规则仍能支持原动作核对 | G1、G2、G6 |
| 目标生效后丢弃回报 | 幂等目标只产生一个效果；不幂等目标先核对或停下 | G1 |
| 查询滞后，原请求迟到 | "不存在"的回报不触发重复的副作用 | G1、G2 |
| 成功回报丢失，之后目标资源被别人修改 | 当前资源状态不能否定原动作曾经生效；条件必须重新核验 | G1、G2 |
| 取消与发送竞争 | 未发出的动作被封闭后，旧工作者无法发出；已发出的继续核对 | G4、G11 |
| 第一次写入成功，重发遇到版本冲突 | 不把第二次的冲突解释为第一次没生效 | G1 |
| 批量目标部分生效后报错 | 不回报为全部未生效或全部成功；保留部分证据 | G1、G2 |
| MCP SSE 断开后恢复 | GET 消息恢复与 POST 工具调用分别计数，没有自行重发 | G1、G5 |
| MCP Task 创建回报丢失、取消后完成、TTL 删除 | 没有可用的关联或终局证明时保持未知 | G1、G2、G11 |
| 重复、乱序、迟到的用量回报 | 实际计费来源只计一次；更正可追溯；取消不删除费用 | G10 |
| 撤权、删除、跨用户访问 | 出口和内容使用被阻止；缓存无法绕过治理 | G7–G9、G12 |

每次通过都记录实现版本、目标版本、SDK 版本、运行配置、测试集、随机种子和原始的目标记录。**发现一个反例，就足以否定对应的强声明**；任何相关前提改变后都要重新验证。
