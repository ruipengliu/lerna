默认推理是推理接口的一个参考实现。它的目标不是追求最高的任务质量，而是**在可靠性约束下提供一个足够好、行为可预测、容易验证的基线**；更强的策略可以作为替换实现，通过同一套一致性测试接入。

## 1 求解策略

默认实现采用**短的观察驱动策略，附带有限计划**：

- 每次提议请求至多发出一次直接的模型请求；
- 本地做确定性的解析和校验；
- **不内置**模型驱动的自动修复、评审、降级或工具执行循环；
- 需要观察结果才能决定下一步时，返回一个单步行动，等任务编排带着新的进展再来请求。

| 候选策略 | 特点 | 结论 |
| --- | --- | --- |
| **短观察驱动，附有限计划** | 核心每轮提供真实进展，错误的影响范围小 | 默认采用；往返较多 |
| 先生成完整计划，再按计划执行 | 稳定任务可以省调用；环境变化时需要失效和重新规划 | 作为后续可选策略 |
| 多样本、评审或多模型求解 | 部分任务质量可能更高；每次调用都要准入，恢复和预算更复杂 | 必须实测成本收益后再引入 |

ReAct 交替进行推理、行动和观察，但它并不普遍优于纯推理：在 HotpotQA 上 ReAct 的 EM 为 27.4，CoT 为 29.4；作者记录的失败包括重复同样的思考或行动、无信息的搜索导致难以恢复（[ReAct §3.3](https://arxiv.org/html/2210.03629v3)）。所以循环由核心限制和记录，"继续思考"不算进展。

## 2 模型视图的组装

模型视图按以下层次组织，从上到下优先级降低：

| 层次 | 内容 | 裁剪规则 |
| --- | --- | --- |
| 必须保留 | 当前目标、必要条件及其版本、控制状态、**未知的效果**、未决的确认、当前的缺口 | 超过输入限制就返回错误，**不得通过摘要删掉** |
| 当前依据 | 最近的相关观察、证据引用、动作回报 | 保留来源、时间和效果类别；大段正文可以换成允许补读的引用 |
| 最近交互 | 最近完整的用户输入和工具交互 | 不留下无法解释的半对"调用—回报" |
| 历史视图 | 有来源的摘要、已裁决提议的概览、明确的省略区间 | 可以替换或重建；不得覆盖核心事实 |

长上下文和摘要都不得代替完整的条件、效果和证据记录。Lost in the Middle 的研究在其评测的模型和任务中发现，相关信息位于长上下文中间时表现下降（[论文](https://arxiv.org/abs/2307.03172v3)）；Anthropic 也指出过于激进的压缩可能丢掉后来才变得重要的细节（[上下文工程实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。这就是"必须保留"一层存在的原因。

M1 只使用**确定性的选择和裁剪**，不做模型摘要。M2 引入模型摘要时，摘要由核心作为独立的辅助工作调度：单独准入，登记全部父内容和用量。推理不得把摘要调用藏在一次提议请求里，也不得直接要求记忆策略写入摘要。完整历史的保留受保存授权和期限限制，不得以"恢复需要"为由无限保存。

供应商提供的会话状态和压缩结果（例如 OpenAI 的压缩输出包含不透明的加密条目，见[压缩文档](https://developers.openai.com/api/docs/guides/compaction)）只能作为**可以丢弃的性能优化**。因为无法逐条检查其中的内容，它依赖的任何内容一旦被删除或撤回，整份状态必须失效。

## 3 能力的渐进暴露

千级规模的 API 不建议一次全量放进上下文。Anthropic 的工程报告指出，全量加载工具定义会增加上下文消耗，并导致选错工具和参数错误，名称相近的工具尤其明显（[Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)）；其中的评测数字是厂商自己的，不得直接作为 Lerna 的预期指标。

默认实现的做法：

1. 核心先按用户隔离、环境可用性、版本和可发现范围，固定能力目录；
2. 模型最初得到**目录概览**和少量候选能力的完整参数约定；
3. 需要更多详情时，推理返回"上下文不足"和候选引用，由核心在**同一目录版本**中补充材料，然后发起新的请求；**不在内部偷偷续跑模型循环**；
4. 目录版本变化后，旧的候选必须重新验证；
5. 模型只能提议已经拿到参数约定的能力；未知的标识和过期的 Schema 被拒绝。

目录概览必须保留发现遗漏能力的途径，不得把候选集合当成全部可用的能力。发现能力不等于获得行动授权；工具对自己的描述（例如"只读""幂等"）也不得自动获得核心的信任（[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)）。

## 4 状态

默认实现可以保留进程内的缓存（例如已构造的模型视图、候选能力详情），但它们全部可以丢弃：缓存命中时仍检查当前授权和内容的有效性；进程重启后从核心记录重建。不要求重建后的输出和原来相同，只要求权威事实和行为约束相同。

## 5 待验证假设

| 假设 | 验证方法 |
| --- | --- |
| H1：单次调用的默认策略足以支撑 M1 | 与允许有限次额外求解的策略比较任务成功率、首次提议正确率、调用次数和费用 |
| H2：有限计划能减少往返，且不增加失效的行动 | 分别在稳定和动态环境中测试，记录重新规划、未执行的步骤和错误准入 |
| H3：渐进暴露适合千级 API | 用名称相近、跨类别的能力和被漏选的候选，测量发现的召回率和最终的参数正确率 |
| H4：分层的历史视图优于固定的消息窗口 | 在长任务中注入旧条件、未知效果和迟到的证据，比较遗漏、重复行动和完成误判 |
| H5：新的推理实例能从核心快照恢复质量 | 让原会话和全新实例分别接续同一核心状态，比较行为的正确性，不要求措辞相同 |

所有实验按 C8 固定测试集、实现版本、模型标识、提示版本和测量方法；契约符合性和任务质量分别计分。
