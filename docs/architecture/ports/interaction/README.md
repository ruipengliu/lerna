- 状态：草稿
- 负责满足：C6、C7 的交互部分；协同 C1、C4、C5、C8
- 涉及场景：S1–S7；S8 只负责呈现评测、发布和回滚请求
- 上游：[项目目标](../../project-goals.md)、[分层与模块](../../layers.md)、[核心契约](../../core/contracts/README.md)、[会话](../../core/sessions/README.md)

交互适配器负责**呈现**和**收集**：把核心的状态呈现给用户，把用户的意图收集回来交给核心。会话、任务编排、授权和动作账本分别持有并裁决对应的事实；交互适配器只是一扇窗。

本接口由三部分组成：

1. **核心状态视图**：当前授权范围内、按维度分开的会话、任务、控制、效果和结果；
2. **用户事件**：带明确主体、目标和关联标识的输入、确认、取消、接管、交还；
3. **持久回执**：每个事件对应一份核心持久记录的回执，可按原标识查询。

界面的描述协议和传输协议都可以替换，但责任记录和裁决语义保持不变。连接成功、消息送达、界面已显示，都不得成为责任凭据。端到端原则早就指出：消息到达目标主机的回执，不能证明目标应用已经执行了请求，应用需要自己的处理确认（[Saltzer、Reed、Clark，1984](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf)）。

## 1 职责与边界

| 事项 | 事实负责方 | 交互适配器的职责 |
| --- | --- | --- |
| 输入顺序、消息、确认回应、任务关联 | 会话 | 收集事件，准确标明目标和请求关联 |
| 任务控制、条件、准入、Result | 任务编排 | 呈现核心状态；不自行宣布成功或停止 |
| 授权范围、当前有效性、设备控制权代次 | 授权 | 呈现具体范围；不把确认当成通用权限 |
| 执行尝试、效果、核对、端侧停止的落实 | 动作账本 | 呈现已知事实、未知项和来源的更新程度 |
| 命令回执、交接意图、待办工作 | 持久工作 | 按原标识查询和恢复；内存队列不算凭据 |
| 内容保存、用途、派生、删除 | 内容治理 | 使用内容引用；落实缓存的停止使用和清理 |
| 连接、重连和传输 | 网关与 SDK（M1 为本地绑定） | 报告连接情况，不据此推断业务状态 |
| 布局、输入控件、本地草稿 | 交互适配器 | 可以替换；草稿要与核心记录明确区分显示 |

约束：

1. 只使用公开的命令和查询，不依赖核心内部实现，也不直接写核心的表（R3、R6）；
2. 界面里的工具调用、扩展请求不得直接调用执行适配器，必须先变成用户事件或提议，由核心裁决（R1、R4）；
3. 远程媒体、链接动作、嵌入内容发起的调用等外部访问，都经过出口闸门；UI 描述不得提供任意的网络访问能力（R2）；
4. **安全确认由受审查的宿主呈现和提交。**第三方的交互适配器和扩展内容只能提供内容描述，保留来源标识，不得覆盖安全确认区域、持有确认提交凭据，也不得自称具备安全确认能力；
5. 会话和 UI 可以不关联任务（C6）；这时任务标识为空，不得隐式地产生任何动作权限；
6. 不负责自动补偿。取消或接管之后的撤销动作是新动作，必须重新授权和准入。

第 4 条是信任边界的一部分。恶意的界面可以向用户展示假数据、伪造点击；协议摘要只能绑定"提交了什么内容"，不能证明"屏幕上显示了什么"或"用户真的理解了"。MCP Apps 规格也承认，即使放在隔离的 iframe 中并施加 CSP，嵌入内容仍然可能误导用户（[MCP Apps 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/5373f01d6f55114ec0a3eb9c864fea6f233589bc/specification/2026-01-26/apps.mdx)）。

## 2 对象与状态

### 2.1 记录

| 记录 | 关键字段 | 含义与约束 |
| --- | --- | --- |
| 适配器声明 | 实现标识、版本、契约版本、依赖；支持的事件、UI 描述配置、最大负载；所需权限 | 用于兼容性和替换验证；不支持接管或安全确认时必须明确声明；声明不授予权限 |
| 用户事件 | [`CommandIdentity`](../../core/contracts/README.md#31-命令回执查询通知与错误)（用户、`issuer_id`、目标域、`command_id`）、事件种类；用户、端点、调用主体；会话、任务、设备资源、输入请求的引用；条件版本、确认版本、控制代次；正文或内容引用、字段用途；客户端时间 | 一次用户意图，重传不改变标识。用户身份来自认证绑定，不相信客户端填写的用户标识。目标必须明确，不得默认投递给"最近打开的任务"。客户端时间只用于展示，不用于裁决多端的全局顺序 |
| 命令回执 | `CommandIdentity`；核心契约的受理回执或决定回执（`SUBMITTED`、`ACCEPTED`、`REJECTED`），界面再映射为"已提交，等待核验""已应用""已拒绝"等文案，文案不是另一套协议枚举；持久接纳引用；保存了什么事实及其版本、关联对象；后续待办、错误和恢复建议 | 必须说清楚保存了什么，例如"取消控制已保存"，不得只返回一个没有业务含义的"成功" |
| 确认请求 | 请求标识和版本；事项类型（`GRANT_ISSUANCE` 签发授权，或 `OPERATION_ADMISSION` 动作准入）；所属用户、会话，动作准入时还有任务；条件版本、提议引用、动作集合摘要；动作、资源、接收方、范围、期限、预算上限；规范化规则版本、内容摘要、到期时间；回应、回应主体、消费记录 | 由核心创建并保存；关键数据是结构化的，不得只靠模型生成的说明文字；回应和消费分别记录 |
| 状态视图 | 视图范围、版本、授权策略版本；各来源（会话、任务、账本等）的版本和更新点；任务状态、控制状态、停止的落实情况；动作效果、核对状态、可能迟到生效；覆盖完整性、失联的来源、未知项数量；Result 引用、证据、遗留的不确定项；输入请求、确认请求、UI 描述、内容引用 | 用户权限范围内的只读投影。不声称跨事务域存在一个全局原子快照；缺少账本回报时，未知项数量可以是"未知"，**不得计成零**；只有核心的 Result 能支撑"任务成功"的展示 |
| 视图更新 | 流标识、流代次、续传游标、基础版本、目标版本 | 顺序只在声明的流内有效，不得解释为所有核心事实的全局顺序 |

规范化摘要只是绑定内容的技术手段，不能证明用户确实看过屏幕。两种确认的呈现不同：签发授权的确认展示被授予的持续范围（资源、操作、处理目的、期限），动作准入的确认展示这一次具体操作的关键数据。两者都必须由受审查的宿主呈现和提交。

### 2.2 状态

交互状态分维度表达，不合并成一个"运行、取消、完成"的枚举：

| 维度 | 转换 | 允许转换的依据 |
| --- | --- | --- |
| 本端投递 | 未保存 → 本端意图已保存 → 核心回执未知 → 核心已持久接纳 | 对应的持久记录；发送函数返回了不算 |
| 命令决定 | 已受理（异步命令）→ 已接受 / 已拒绝 | 原命令的核心决定回执；重复请求不产生第二个决定 |
| 确认 | 待回应 → 已回应 → 已消费 | 回应由会话保存；消费按事项类型在裁决域的授权签发事务或准入事务中完成 |
| 确认失效 | 待回应或已回应 → 过期 / 被替代 / 失效 | 请求到期；条件或关键内容变化；当前授权不再满足 |
| 视图同步 | 取快照 → 同步中 → 已追平 | 快照和更新都成功应用；**在线不等于已追平** |
| 视图失同步 | 任何同步状态 → 失同步 → 重新取快照 | 缺口、基础版本不符、解析或应用失败、游标过期 |
| 接管 | 系统控制 → 接管请求已保存 → 等待端点停止 → 用户控制 | 端点持久回报：旧的自动操作入口已封闭 |
| 交还 | 用户控制 → 交还请求已保存 → 重新观察与核验 → 系统控制 | 新的观察、当前授权、正确的控制代次、任务控制检查 |

第一个有效的确认回应通过原子检查确定。不同端点的"同意"和"拒绝"竞争时，必须有一个可以查询的结果，另一方不得覆盖它。已同意但尚未消费的请求仍然可能失效。用户控制的是**设备资源**，不是任务的责任归属：接管和交还都不迁移任务或已有动作的负责方（G11）。

### 2.3 必须如实呈现的中间状态

| 核心事实 | 允许的文案 | 必须避免的推断 |
| --- | --- | --- |
| 只有本端的持久意图 | "取消请求已在本机保存，尚未确认被接纳" | 已取消、系统已停止 |
| 核心已保存取消控制 | "取消已保存，已停止新的准入" | 所有已准入或已发出的动作都没执行 |
| 仍有未知效果 | "取消已保存，部分动作结果仍在核对" | 未生效、费用为零 |
| 端点失联 | "端点未回报停止情况，已有动作可能继续产生效果" | 未知项为零 |
| 用户已回应确认 | "确认已保存，等待准入检查" | 已授权全部动作、已经执行 |
| 核心固定了成功的 Result | "任务成功"，附条件证据和结果引用 | 根据模型文本或交互流结束就推出成功 |

已生效的动作、已发生的费用和后续的核对始终可见，取消不得把它们从历史里抹掉。

取消只是一个请求。Temporal SDK v1.33.0 中 `WaitForCancellation` 默认关闭，调用方可能已经收到取消结果，而活动本身还没有结束（[activity.go](https://github.com/temporalio/sdk-go/blob/a85ce600f6272b3fc11fa112f822b6990cd7cd1e/internal/activity.go#L125)）。所以"取消已保存""执行端点已停止新操作""已有动作的效果已确定"要分别呈现。

## 3 接口

核心提供公开的命令、查询和订阅；交互适配器接收视图、输出事件。接口的机器定义属于核心契约。

### 3.1 通用接口

| 接口 | 输入 | 成功含义 | 主要错误 |
| --- | --- | --- | --- |
| 协商能力 | 契约版本、适配器声明 | 确定可用的事件和描述配置；不授予业务权限 | 版本不兼容、能力不足 |
| 呈现视图 | 核心状态视图 | 呈现报告，只表示渲染情况 | 不支持的描述、非法结构、失同步 |
| 提交用户事件 | 完整事件和认证绑定 | 原命令回执；成功含义由具体事件决定 | 无权、版本冲突、请求过期、标识冲突 |
| 查询命令回执 | 原 `CommandIdentity` | 核心契约的五种查询结果之一：尚未发现、已受理待决定、已有决定、已退役、无法查询 | 无权（含冒用其他 `issuer_id`） |
| 查询状态视图 | 范围、可选的最低来源版本 | 当前授权下的快照、来源版本和续传游标 | 部分来源不可用、尚未追平 |
| 订阅视图更新 | 范围、游标、描述配置 | 可以重复到达的有序更新，或明确的重置要求 | 游标过期、权限变化、消费过慢、流代次变化 |

查询原命令时暂时没有记录，不得据此新建命令，仍按原标识重传。**回执查询是恢复责任的路径，状态流是呈现的路径**，两者分开。

### 3.2 用户事件

| 事件 | 必要输入 | "已应用"的准确含义 | 并发与幂等 |
| --- | --- | --- | --- |
| 输入 | 会话、可选的任务或输入请求、内容 | 会话已保存输入顺序和投递责任；任务仍在创建时明确返回这个阶段 | 同一命令只有一条输入；不同命令的相同文本是两次输入 |
| 确认 | 请求标识、请求版本、内容摘要、回应选项 | 会话已保存有效的回应；**不表示确认已在准入中被消费** | 同命令返回原结果；同一请求的不同回应不得覆盖第一个有效回应 |
| 取消 | 明确的任务标识 | 任务编排已保存取消控制，关闭新的准入 | 不依赖无关的进展版本；重复取消返回已保存的控制状态 |
| 接管 | 设备资源、当前控制代次、相关任务 | 控制意图已保存；执行端点的停止另有回报 | 按设备资源检查代次，不迁移动作 |
| 交还 | 设备资源、用户控制代次、交还范围 | 交还意图已保存；恢复自动操作要先完成重新观察和核验 | 旧代次拒绝；失联或超时不会自动交还 |

普通文字输入里的"好""继续"不得自动转成安全确认事件。命令行界面同样必须有明确的确认请求和动作范围。

### 3.3 错误与重试

| 错误类别 | 能否按原标识恢复 | 处理 |
| --- | --- | --- |
| 传输失败、回执未知、决定仍在处理 | 能 | 查询原回执或重传原事件，不改变负载 |
| 条件、确认或控制版本冲突 | 原请求不能改写 | 获取当前对象；用户需要重新表达意图时生成新命令 |
| 请求过期、确认失效 | 不能继续原确认 | 核心创建新请求，重新呈现 |
| 同标识不同负载 | 不能 | 拒绝并保留原记录 |
| 当前授权无法证明 | 不能继续依赖该授权 | 停下来，说明缺什么 |
| 回执已过保留期 | 不能重新执行旧请求 | 返回可查询的对象关联，或明确说明不可恢复 |

顺序是：先认证，再查用户范围内的去重记录，新请求才检查当前前置条件。已经决定的命令不会因为后来的条件变化而被重新裁决。

## 4 关键流程

### 4.1 输入与任务创建

| 步骤 | 处理 | 持久化点 |
| --- | --- | --- |
| 1 | 收集明确的目标和关联，显示"尚未提交" | 不作接纳承诺 |
| 2 | 需要跨事务域投递时，先保存完整的 `CommandIdentity`、投递意图和允许保存的内容 | **P1** 发送侧持久工作 |
| 3 | 核心认证、去重；会话保存输入和后续处理责任 | **P2** 裁决域：会话、命令记录、待办 |
| 4 | 正文和附件登记来源和版本；跨内容治理域的交接按 R7 | **P3** 内容治理 |
| 5 | 任务编排创建任务和初始条件，会话关联该任务 | **P4** 裁决域事务 |
| 6 | 返回准确的阶段和原命令回执 | 回执对应已有的持久记录 |
| 7 | 发送侧记下回执，按内容策略清理投递缓存 | **P5** 发送侧回执 |

步骤 3 之后已接下输入责任，但步骤 5 尚未完成时，显示"输入已保存，任务创建中"。

### 4.2 确认与准入

1. 任务编排固定条件版本和待执行的内容，会话保存确认请求和关键字段；
2. 受审查的宿主从**结构化字段**呈现动作、资源、接收方、范围、期限、预算和不可撤回的后果；
3. 用户主动回应。宿主提交确认事件，核心重新校验主体、当前请求、摘要和到期时间，保存回应和命令决定；
4. 准入时，在裁决域的一个事务中检查当前条件、授权、预算和确认范围，消费确认，写下动作意图和待办；
5. 动作账本按 R7 接纳意图；
6. 视图分别呈现"确认已保存""动作已准入""执行与效果"。

任何关键参数变化都会生成新的请求版本，旧确认失效。界面提前展示过请求，也不得跳过第 3 步。

| 确认界面的约束 | 原因 |
| --- | --- |
| 关键字段来自核心固定的记录；模型的说明只是补充，并标明来源 | 防止提议文字代替实际的授权范围 |
| 接收方、金额、路径、范围等关键差异必须可以辨认 | 防止截断、相似名称或默认值误导 |
| 没有默认同意、没有倒计时同意，不因"已展示"而确认 | 用户必须主动产生事件 |
| 扩展内容不得覆盖确认区域、提交凭据或确认事件入口 | 减少伪造宿主确认的途径 |
| 所有入口使用同样的请求绑定和消费规则 | 防止旧接口、快捷键或通知上的动作绕过检查 |

这些约束对应 OWASP 交易授权指南的要求：用户能识别并确认关键交易数据，验证数据由服务端生成和保存，修改后旧确认失效，执行前检查授权，确认凭据限时且每个操作唯一（[OWASP](https://github.com/OWASP/CheatSheetSeries/blob/6b6a66bae11c9e001c3576bcc3de55cc0dc5e449/cheatsheets/Transaction_Authorization_Cheat_Sheet.md)）。

### 4.3 取消与未知效果

1. 用户提交取消；还没取得核心决定时，界面保持"等待确认接纳"；
2. 任务编排持久保存取消控制，关闭新的准入，创建处理已准入动作的待办；
3. 已准入但未发出的动作由动作账本封闭；已发出的继续记录效果和核对；
4. 视图发布取消决定，同时保留端点的落实情况、未知效果和可能迟到的项目；
5. 迟到的效果和用量继续关联原动作、原任务。

取消回执只能证明第 2 步完成，不能提前证明第 3 步全部完成。既不可查询也不幂等的动作保持未知，不会因为用户再点一次取消而重试。

### 4.4 多端同步

1. 从核心取得快照，以及与快照一致的续传游标；
2. 从这个游标开始接收更新；重复的更新可以忽略，缺口和版本不符必须显式处理；
3. 更新成功应用之后才推进游标；持久缓存和游标原子提交；
4. 增量应用失败、历史过期或权限范围变化时，停止使用旧的同步基线，重新取快照；
5. 收到命令决定后，建立"最低事实版本"的要求：旧快照不得把"取消已保存"覆盖回"仍在运行"；还没追平时显示"决定已保存，状态更新中"；
6. 多端输入的顺序由会话的接纳顺序决定，客户端时钟只用于展示；
7. 跨域的视图保留来源版本和缺失情况；界面不得根据混合的快照自行重新计算任务是否成功。

失同步时，确认、交还等依赖当前对象的控件暂停提交；取消仍可按明确的任务标识提交，由核心按当前状态裁决。

快照必须附带续传位置，避免"查询之后、订阅之前"的空隙。Kubernetes client-go 的 Reflector 就是先取 LIST 的版本、再从该版本 WATCH，历史版本不可用时重新 LIST（[reflector.go](https://github.com/kubernetes/client-go/blob/3aa3c77983ce87f8702329ea44d366cb16a04fd1/tools/cache/reflector.go#L398)）。但同一个 Reflector 在 `Store.Add/Update/Delete` 失败后仍会推进同步版本（[reflector.go#L900](https://github.com/kubernetes/client-go/blob/3aa3c77983ce87f8702329ea44d366cb16a04fd1/tools/cache/reflector.go#L900)），这对可重建的缓存可以接受，但如果 Lerna 持久保存视图缓存还照搬这种做法，就会跳过未应用的更新，所以第 3 步要求缓存和游标一起提交。AG-UI 1.0.1 的 reducer 应用增量失败时只记警告、保留旧状态，没有自动请求全量恢复（[apply/default.ts](https://github.com/ag-ui-protocol/ag-ui/blob/ec9f4fa68b950d0b440087cd94530c0815b81115/sdks/typescript/packages/client/src/apply/default.ts#L681)），这也是本设计要求"增量失败即进入明确的失同步状态"的原因。

Matrix 用事务标识区分新请求和重传，本地回显和远端回显可能交错，需要按标识合并（[Matrix v1.18](https://spec.matrix.org/v1.18/client-server-api/#local-echo)）。"本机待提交"和"核心已保存"必须是两个不同的状态；事件流先于请求回执到达时，也只能形成一条输入记录。

### 4.5 接管与交还

1. 任务编排保存接管意图；授权关闭相关设备资源的新自动操作权限，推进控制代次；
2. 端侧动作账本落实停止要求，出口拒绝旧代次，并持久回报封闭情况；
3. 只有端点能证明旧的自动操作不会再进入设备出口时，才呈现"接管已落实"；已有的外部效果仍可能待核对；
4. 用户交还后，保存交还意图；
5. 执行适配器重新观察，证据经动作账本回报，核心检查当前授权、条件和控制代次；
6. 核验通过后，恢复允许的推进。

用户在断网的端点上直接接管时，端点先限制本机的自动操作并记录事实，重连后补交原控制事件。这种本地限制只能**收缩**权限，不得自行恢复云端的权限。

### 4.6 通知

核心持久保存待处理事项；推送只用来提示"有新状态，请同步"。RFC 8030 规定推送服务返回 201 只表示已接受投递，不表示用户端已收到，而且消息有保留期限（[RFC 8030 §5](https://www.rfc-editor.org/rfc/rfc8030.html#section-5)）。推送回执、已读回执都不得代替核心接纳、用户确认或效果证据。点击通知只定位到当前对象，然后重新读取状态和确认请求；旧通知不得直接消费确认。

### 4.7 外部 UI 协议的分层组合

| 层次 | 选择 | 用途与限制 |
| --- | --- | --- |
| 基础 | **Lerna 自己的小型语义描述**：状态、消息、字段、内容引用、输入请求、确认引用 | 核心状态和安全确认保持固定语义，容易做符合性验证；支持命令行、原生界面和 Web |
| 声明式表单 | A2UI 的受限配置 | 适合更丰富的表单。但 A2UI 的双向绑定会先修改客户端的数据，用户事件才向创建方发送数据（[A2UI v0.9.1](https://github.com/a2ui-project/a2ui/blob/1444719acd8833eeb5e70529c7ac47bc50b7390c/specification/v0_9_1/docs/a2ui_protocol.md)），所以本地表单变化不得称为"已保存"，整个表单回传时必须逐字段检查用途 |
| 事件交换 | AG-UI | 可以交换事件和状态，但必须补上 Lerna 的持久回执、条件版本绑定、授权检查和确认消费；交互运行结束不得映射为任务成功 |
| 受限嵌入 | MCP Apps / MCP-UI | 适合专用的工具界面，需要逐个宿主验证。MCP Apps SDK v1.1.2 的 `AppBridge` 在传入 MCP client 时会自动转发界面发出的 `tools/call`（[app-bridge.ts](https://github.com/modelcontextprotocol/ext-apps/blob/5373f01d6f55114ec0a3eb9c864fea6f233589bc/src/app-bridge.ts#L1470)），Lerna 必须拦截这类调用，转成用户事件或提议，否则会绕过 G4、G5、R4 |

这几层不互斥，也都不是核心的事实格式。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式与界面行为 |
| --- | --- | --- |
| 回执丢失 | 发送侧持久工作或 SDK；核心持久工作 | 用原标识查询或重传原事件，显示"核心回执未知"；不新建任务或命令 |
| 适配器或客户端崩溃 | 发送侧持久工作、适配器 | 重新加载未完成的投递和回执，再取核心快照；没有持久保存的草稿不承诺恢复 |
| 核心进程崩溃 | 持久工作和各事实写入方 | 恢复已提交的命令、决定和待办；未提交的事务不产生"已保存"回执 |
| 重复请求 | 核心持久工作、会话 | 同标识同负载恢复原请求，不同负载拒绝；视图按输入或完整的 `CommandIdentity` 合并回显 |
| 两端的确认冲突 | 会话、任务编排 | 第一个有效回应生效；确认最多被一个准入消费；另一端读取冲突结果并刷新 |
| 确认与条件修改、授权撤销、取消竞争 | 裁决域 | 按事务顺序检查；回应先保存不保证之后能准入；条件或授权失效就不得消费 |
| 取消与执行竞争 | 任务编排、原动作账本、出口闸门 | 停止新的准入；未发出的动作按记录封闭；已发出或无法判断是否发出的，保留核对责任 |
| 执行端点失联 | 原动作账本；任务编排汇总 | 显示停止的落实情况和效果未知；不改派同一个动作 |
| 状态流断线、游标过期、增量失败 | 网关或 SDK、适配器 | 重连或重新取快照；应用失败的更新不推进游标；"在线"不当作追平的证据 |
| 迟到的执行结果或费用 | 原动作账本、预算 | 关联原动作和任务，继续核对和计费；取消不抹掉费用 |
| 旧端点迟到的确认或交还 | 会话、授权、任务编排 | 校验当前的请求、条件和控制代次；失效就拒绝，不自动转成新的确认 |
| 删除时端点离线 | 内容治理、端点上的缓存持有方 | 跟踪清理进度，不提前宣称全端清理完成；无法证明当前用途权限的缓存停止使用 |

## 6 不变量落实

| 不变量 | 本接口怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 未知效果、缺失的回报和可能迟到的项目分别显示；不由超时推出未生效 | 请求发出后断线、端点失联、迟到的成功，界面始终保留未知 |
| G2 | 成功的展示只依据核心的 Result；交互流结束和模型声明都不产生成功 | 必要条件缺证据或动作未收尾时发送"已完成"文本，界面不显示核心成功 |
| G3 | 本机意图、核心接纳、决定和展示分别表达；回执引用持久记录 | 在各持久化点前后崩溃并丢回执，不丢责任，也不出现虚假的"已保存" |
| G4 | 确认绑定事项类型、条件和动作内容，按类型在授权签发或准入事务中消费，出口处再检查 | 替换参数、使用旧确认、撤回与准入竞争，非法动作都发不出去 |
| G5 | UI 中的工具调用、媒体、链接和嵌入内容都无法形成旁路 | 拦截直接的网络、设备访问和 SDK 自动转发，都被拒绝或进入核心路径 |
| G6 | 提议内容与核心事实分开；适配器没有裁决状态的入口 | 模型伪造成功、授权或取消声明，都无法改变核心状态 |
| G7 | 确认范围明确，事件主体可信；扩展没有自授权限的能力 | 修改用户、资源、范围或事件种类，核心拒绝越权 |
| G8 | 发布、读取、缓存、同步分别检查当前用途；整表单回传必须有字段级授权 | 撤回同步或保存权限后，相关字段不再发布或使用 |
| G9 | 内容引用可以失效；缓存纳入派生和清理跟踪；去重记录不保存被删除的正文 | 删除后检查本地缓存、日志、附件、描述和回放路径 |
| G10 | 只展示预算的记录，不按消息数累加费用；迟到的费用保持关联 | 重复用量回报、取消后到达的账单，显示与核心结算一致 |
| G11 | 命令、任务、动作的标识跨恢复稳定；接管和断线不迁移责任 | 替换客户端、执行进程、断线重连后，未知动作仍归原负责方 |
| G12 | 所有查询、游标、回执、内容和本地缓存按用户隔离；慢端点使用有界缓冲 | 伪造对象标识、复用他人游标、切换用户后读缓存、慢消费压力测试 |

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 语义契约在内，协议转换在外 | 替换适配器时事实语义保持稳定 | 需要维护映射和一致性测试 |
| 状态分维度 | 准确呈现控制和未知效果 | 界面文案和字段更多 |
| 持久确认、一次消费 | 并发、重放和条件变更都有确定的行为 | 多了持久写入；暂时不可用时需要等待 |
| 以快照作为恢复基础 | 流或通知完全丢失也能恢复 | 大快照需要分页、过滤和容量验证 |
| 接管要等端侧证据 | 不把控制意图误报为物理停止 | 失联时无法立即宣布接管完成 |
| 敏感缓存在无法核验权限时停用 | 保守地落实 G8、G9 | 部分离线查看能力受限 |
| 回执与呈现流分开 | 慢客户端不会阻塞核心的责任处理 | 客户端要处理"回执先于视图到达" |

被否决的方案：用聊天消息流直接驱动界面（容易把模型声明、流结束和按钮点击当成事实）；会话级的"用户已同意"标志（无法绑定条件和范围，容易重放和扩权）；签名或限时的确认令牌、服务端不保存消费状态（有效期内仍可重放）；多端复制状态并用"最后写入获胜"或 CRDT 合并（会破坏确认消费、预算和任务控制的唯一裁决，只适合草稿）；按心跳或租约过期判定用户接管（超时不能证明旧执行者已停止）。

确认的绑定方式、设备控制代次、回执的保留策略，正式采纳前必须写成 ADR。

## 8 待定事项

| 假设 | 验证方式 | 验证前的处理 |
| --- | --- | --- |
| 受审查的宿主能在各种界面上完整呈现关键确认字段 | 窄屏、命令行、辅助技术和恶意描述的测试 | 不认可缺少安全确认能力的实现 |
| 最小的语义描述足以覆盖默认交互 | 用 S2、S7 和独立会话验证 | M1 保留纯文本和明确的选择 |
| 用户能理解"取消已保存，效果仍在核对" | 用户理解测试 | 不把"文案正确"等同于"用户理解" |
| 每用户一个发布序列能满足常态负载 | 高频输出、多端和慢消费的容量测试 | 有界缓冲；过载时明确要求重新取快照 |
| 游标窗口和回执保留期的合理取值 | 结合 S4 的离线周期、存储量和恢复时间测量 | 不承诺长期离线后一定能增量恢复 |
| 设备的停止回报能准确界定旧的操作入口 | 用模拟设备和实际执行宿主做故障注入 | 缺少证据就保持等待或未知 |

## 9 M1 范围

M1 实现命令行或最简界面即可，但责任和恢复语义必须完整。

| 项目 | M1 实现 | 推迟 |
| --- | --- | --- |
| 默认交互 | 输入目标、查看会话和任务、明确确认、取消、查看结果和未知效果 | 丰富的布局、嵌入 HTML |
| 契约 | 完整的 `CommandIdentity`、核心契约的回执和查询类型、确认绑定（含事项类型）、来源关联 | 外部协议转换、完整的扩展 SDK：M4 |
| 持久恢复 | 核心去重、回执查询、待办恢复；必要的跨域交接按 R7 | 生产的端云网关：M3 |
| 状态查询 | 全量快照和明确的阶段；可以用轮询 | 多端实时流、大规模推送 |
| 确认 | 单次和持续授权的具体范围；回应与消费分开；按事项类型在授权签发或准入事务中只消费一次 | 委派和完整的用途模型：M2 |
| 取消 | 取消已保存、新准入停止、已有动作核对中、迟到的效果和费用 | 子任务和外部 Agent 的取消：M4 |
| 接管与交还 | 契约预留；默认实现明确返回"不支持" | GUI 和端侧落实：M3 |

M1 的最小验收演示：

1. 输入已持久保存、任务尚未建立时崩溃，恢复后只创建一个任务；
2. 确认回执丢失，恢复后只消费一次；
3. 取消与动作发出竞争，界面准确显示已保存的控制和未知效果；
4. 既不可查询也不幂等的动作超时，一直保持未知；
5. 动作迟到生效，结果仍归原动作，已发生的费用仍可查。

## 10 测试要点

测试同时检查**核心的持久事实、实际的出口行为和用户看到的表达**，不得只检查接口返回码。

| 优先级 | 用例 | 必须满足 | 对应 |
| --- | --- | --- | --- |
| P0 | 在发送意图、核心提交、返回回执、保存回执之间逐点崩溃 | 恢复原命令；最多一条输入、一个任务；没有虚假的"已保存" | G3、G11、R7 |
| P0 | 回执丢失；事件流和回执分别先到，重复到达 | 只回显一条输入；同一个决定；文本相同的不同命令仍分别保留 | C6、G3 |
| P0 | 同标识不同负载；令牌轮换、重连、适配器重启后重传 | 不同负载被拒绝；连接变化不产生新命令 | G3、A2 |
| P0 | 两端同时同意，或同意与拒绝竞争 | 第一个有效回应生效；确认最多被消费一次 | C7、G4 |
| P0 | 展示之后替换接收方、金额、资源、条件或预算范围 | 旧确认失效；替换后的动作无法准入 | G4、G7 |
| P0 | 确认与撤销授权、修改条件、取消并发 | 结果符合事务顺序；回应已保存不得绕过准入 | G4、G8 |
| P0 | 取消分别发生在准入前、准入后、发出前、发出后 | 新准入停止；已发出的责任保留；不推出"未生效" | G1、G3、G11 |
| P0 | 端点离线且有已发出的动作；迟到的结果和账单 | 未知和费用保持关联；不改派，不重复计费 | G1、G10、G11 |
| P0 | 模型输出"已完成"、协议流结束，但条件缺证据 | 不显示核心成功，说明缺口 | G2、G6 |
| P0 | 禁用所有通知，或通知重复、过期、乱序 | 靠查询仍能恢复；点击旧通知无法执行旧确认 | G3、C7 |
| P0 | UI 直接发起工具调用、远程媒体或链接访问 | 没有出口凭据的路径被拒绝；合法的请求进入核心 | G4、G5、R2、R4 |
| P1 | 快照之后、订阅之前发生确认消费或取消 | 快照和续传不遗漏变更 | C5、A4 |
| P1 | 增量应用失败、缓存提交失败、游标先写后崩溃 | 不跳过未应用的更新；失同步后重新取快照 | A4、G3 |
| P1 | 新的取消回执之后到达一个旧的"运行中"快照；账本来源缺失 | 已知的决定不倒退；缺失不计成零 | C7、G1 |
| P1 | 接管时旧工作者迟到、端点失联；交还时观察已过期 | 旧代次无法进入出口；没有证据不宣布恢复 | S3、G4、G11 |
| P1 | 确认字段被截断、相似字符、恶意 HTML、终端控制序列、隐藏的默认值 | 关键数据可以辨认；扩展无法伪造或覆盖宿主的确认 | C7、A4 |
| P1 | 复用他人的游标、回执、内容标识；切换用户后读缓存 | 拒绝跨用户访问；缓存和负载隔离 | G12 |
