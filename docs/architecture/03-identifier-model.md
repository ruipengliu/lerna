# 标识模型简化评估

状态：用户已明确同意修改，本方案作为后续 Schema、SDK 和端云恢复设计的标识基线。尚无协议实现或运行验证。

本次评估针对[原生接口与消息目录](03-contract-message-catalog.md)的标识设计，目标是减少身份和关联关系，同时保持任务、去重、核对及恢复语义。结论已同步到消息目录，尚无协议实现或运行验证。

## 结论

采用以下两组合并：执行类操作用 `operation_id` 作为调用身份，替代单独的 `invocation_id`；应用请求使用 `message_id` 关联响应，取消独立的 `request_id`。同时将连接与追踪信息移到适用的上下文，把交互标识保留在确实需要它的操作载荷中。

ID 不必一一对应独立领域对象、表或服务。应区分业务对象的身份、持久化日志的键、关联引用与暂态上下文。本次减少两种独立身份，不承诺减少所有记录：操作回执、执行状态、收发日志和提交记录各自提供不同保障。

## 逐项判断

| 原标识 | 处理 | 保留的语义及理由 |
| --- | --- | --- |
| task_ref | 保留业务对象身份。 | 一个任务涉及多个操作，任务和操作完成时间不同。 |
| invocation_id + operation_id | 合并为 operation_id。 | 能力调用是执行类操作；受理、执行进展、核对和结果使用同一身份。操作类型不同不需要再分配一套 ID。 |
| request_id + message_id | 合并为 message_id。 | 请求是一种应用消息；回复通过 reply_to 指向请求消息。传输发送尝试在本地日志/追踪中记录即可。 |
| change_id | 保留，但只属于内核存储。 | 一次操作可产生受理、启动、完成等多次原子提交，不能与操作身份一一对应。 |
| interaction_id | 按需保留，放入等待项及响应操作载荷。 | 一个任务可同时或先后等待多项输入；仅有任务 ID 无法阻止迟到回复匹配错误等待点。 |
| stream_id / seq | 保留为流和游标元数据。 | 用于顺序、缺口、补读和流量额度；不强制生成新的业务实体。 |
| connection_id | 保留在连接/协商上下文。 | 新连接与旧连接必须能区分，但无须每条应用消息重复携带。 |
| trace_id | 可选追踪上下文。 | 不影响任务身份、去重和授权，不成为业务查询的必需键。 |
| causation_id | 改为可选 causation_ref。 | 引用已有消息或操作，不再分配“因果对象”的新身份。 |

`reply_to`、`target_operation_ref`、`causation_ref` 都是已有对象的引用，不引出同名实体或新的 ID 生成机制。存在多个前因时，因果信息可以记录引用集合，不能用一个伪造的因果 ID 掩盖关系。

## 最小对象关系

- Task 管理目标及进展，关联零到多个 Operation；独立工具或记忆操作可以没有 Task。
- Operation 标识一次逻辑变更意图，包含不可变的种类、目标和语义输入。执行类 Operation 持有执行进展及效果证据；取消和输入提交是另外的 Operation。
- 一次 Operation 可以关联多个 Message 和多个内部 Change。两类记录生命周期分别由协议和存储契约管理。
- 等待项绑定受控处理模块，可关联任务或操作，也可服务独立 UI 交互，具有稳定 interaction_id；提交输入是引用该等待项的另一操作，不能用输入提交 ID 代替等待项身份。
- Stream 与 Connection 属于通信上下文，Trace 属于诊断上下文；它们不是 Task 的替代身份。

这里的 Operation 是统一的身份语义，不要求所有能力共享一个巨大结构或万能服务。工具执行、记忆更新仍由各自 Module 管理；可共用操作回执接口，并按种类保存专有状态。能力调用不再重复建立彼此独立的“请求操作”和“调用实体”身份。

## 合并成立的条件

### 操作身份

在一个命名空间内分配唯一 operation_id，类型、目标、业务期限及语义载荷固定；相同 ID 配不同类型或载荷返回身份冲突。身份去重不再靠更换方法名或认证主体产生一个新作用域。操作身份由发起方在有效接纳窗口内生成并由当前权威核验；内部绑定窗口世代，但对调用者仍是一个不透明 ID，不因转发节点不同而另建命名空间内的同名操作。接收端仍须先核对认证主体对该操作的访问和执行权限，不能因为猜中 ID 就返回结果或重放动作。

查询和核对执行类操作使用其 OperationRef，不再另存 invocation_id。取消操作使用自己的 operation_id，并以 target_operation_ref 指向原执行操作；两个操作的结果分别记录。新的业务动作使用新 operation_id；底层传输重试或内部重试策略在原操作内记录尝试信息。

一条执行指令跨节点转发时保留原操作引用和原始发起身份的受信关联，重新执行适用的授权检查。若委派产生新的目标或新的能力动作，则创建新的操作并记录父子引用；不能仅因网络转发多一跳就变更业务身份，也不能用父操作 ID 吞掉真实的子操作。

### 消息身份

消息原样补发保留 message_id；业务查询、新响应、新事件或重新构造的请求使用新 message_id。新请求若仍表示相同逻辑变更，则保留 operation_id。这样同时覆盖“同一消息重复投递”和“不同消息携带同一操作”两种情况。

响应的 reply_to 指向请求 message_id，持久化回执同样指向已接收的消息。一个请求可以产生受理、进展及最终结果等多条消息，每条消息各有身份；接收方不能只按 reply_to 去重全部回复。

gRPC unary 已有本次 RPC 的响应关联时，可由绑定层使用原有调用上下文；需要跨连接补投或查询的业务意图仍保留 operation_id。WebSocket 多路并发需显式使用 message_id/reply_to。应用层不强制再生成一个请求尝试实体。

### 记录保留

执行类操作身份及结果核对记录覆盖完整调用恢复期，不能在受理回执过期时一起删除；合并身份不等于将长任务执行状态降为短期幂等缓存。消息去重记录、操作记录、等待项和内部提交回执分别执行各自保留契约。

消息记录已过期但操作仍存在时，新的请求消息仍能通过 operation_id 查到原操作。相关操作核对记录也已过期时必须显式报告边界，不能把迟到的旧请求默认为新动作。窗口关闭水位先于明细清理持久化，以便清理后继续拒绝旧操作首次接纳；具体流程见 [恢复检查表](04-recovery-state-and-failure-matrix.md)。

## 反例检查

| 情形 | 简化后的表达 | 不丢失的语义 |
| --- | --- | --- |
| 点击已发生但回执丢失 | 重投消息 M1，或发新查询 M2，均关联操作 O1。 | 不新建点击身份，仍按 O1 核对效果。 |
| 同一操作两次请求尝试 | M1 和 M2 各自关联响应，携带相同 O1。 | 消息去重和业务去重分别成立。 |
| 取消与完成竞态 | O2 取消 O1；取消受理不修改 O1 已发生事实。 | 保留两项操作及各自结果。 |
| 一次调用多次状态提交 | O1 关联 C1、C2、C3。 | 同一提交重复写与不同阶段写入可区分。 |
| 一个任务两个输入等待点 | I1、I2 各自被输入操作引用。 | 迟到回复或并发回复不会误推进另一等待点。 |
| 同一逻辑消息改走另一条流 | 消息身份不变，流位置按恢复契约处理。 | 不强迫消息身份等同原流序号，仍能查重。 |
| 重连后旧连接仍有迟到数据 | 新旧连接上下文分别校验，操作身份保持。 | 身份简化不把连接新旧判定交给业务 ID。 |

这些是设计推演，不是已执行的分布式测试。端云恢复设计须将它们加入故障用例。

## 不采用的进一步合并

不把 `operation_id` 与 `message_id` 合并：一个操作需要多条消息，重试查询与最终事件也有各自的关联需求。

不把 `message_id` 简单替换为 `stream_id + seq`：gRPC unary 不天然具有逻辑流游标，路由或补投位置也可能变化。要采用这种编码必须额外固定持久日志与流身份，现在会增加限制。

不把 `interaction_id` 简单替换为任务版本：不同等待点可并存，任务其他状态更新也可能改变版本；除非明确限制只存在一个等待点，否则语义不等价。

不把 `change_id` 与任务状态版本合并：预期版本用来发现竞争，change_id 用来核对某次提交。把两者强行合并会令提交结果未知时的恢复含义发生变化。

外部 MCP、A2A 的标准字段不随本次原生协议简化而删除；Adapter 将其远端身份映射为本地 OperationRef 和 MessageRef，保留实现所需的版本与服务器作用域。

## UI 扩展沿用此身份模型

端侧 UI 不另设 ui_task_id、ui_request_id 或 ui_event_id。正式用户动作使用 operation_id，呈现消息使用 message_id，等待输入使用 interaction_id。surface_ref 和 component_key 只提供作用域内的界面定位，revision 表示界面状态版本；多窗口需要区分定位，不意味着每个控件都成为独立业务实体。详见 [UI 交互契约](03-ui-interaction-contracts.md)。
