# 文档规范

| 日期 | 修订说明 |
| --- | --- |
| 2026-10-04 | 从 `README.md` 拆出：文档层级、目录骨架、命名、写作与链接规则、模块设计模板、M1 文档清单。内容未改，此前的修订记录见 [README](README.md)。 |

本文写给编写和评审设计文档的人，规定文档放在哪里、叫什么、写什么，以及文档之间以什么为准。新增、移动文档或变更状态时，按本文归置，并同步更新 [README](README.md#2-文档索引) 中的文档索引。

文字表达方面的通用要求（读者、结构、术语、约束用语、图示）见仓库根目录的 `CLAUDE.md`；本文只规定本目录特有的规则。

## 1 文档层级

文档按上下游排列，下游不得改变上游的结论。下游发现上游有问题时，先修改上游并记录原因，再改下游。

| 层级 | 文档 | 回答的问题 |
| --- | --- | --- |
| 0 目标 | [项目目标](project-goals.md) | 做什么、为什么、做到什么程度算完成；术语、不变量、能力和验收 |
| 1 划分 | [分层与模块](layers.md) | 有哪些模块，各自负责什么事实，谁可以调用谁 |
| 2 决定 | `docs/adr/` | 难以撤回、需要单独记录理由的具体决定 |
| 3 设计 | 本目录下的模块、流程和专题文档 | 每个模块怎样满足上游要求：对象、接口、流程、故障处理 |
| 4 合同 | `protocol/` | 机器可读的接口定义和 Schema，与代码同版本发布 |
| 5 验证 | `verification/` | 怎样证明设计成立：测试矩阵、故障注入、专项验收、容量 |

[整体方案](overview.md)不属于上述层级。它用一个端到端场景解释各模块怎样配合，供开发者入门；它不新增或修改任何要求，与上游冲突时以上游为准。

本目录之外的文档：

| 位置 | 用途 | 与本目录的关系 |
| --- | --- | --- |
| `docs/adr/` | 架构决定记录 | 层级 2；模块设计中做出的难以撤回的决定，另写一篇 ADR |
| `docs/research/` | 调研、比较和来源 | 不是规范。设计文档需要其中的结论时，重写进正文，不链接为依据 |
| `docs/archive/` | 已废弃的旧方案 | 不是规范，不链接 |
| `.scratch/` | 功能规格和实现工单 | 实现层面的拆分；工单引用设计文档，设计文档不引用工单 |

## 2 目录骨架

模块目录与 [分层与模块](layers.md#11-代码组织) 中的代码目录一一对应，便于从代码找到设计，也便于从设计找到代码。唯一的例外是 `ports/`：可替换部分的接口定义在代码中属于 `contracts/`，默认实现在 `defaults/` 或 `adapters/`，文档则把接口约定和默认实现设计集中放在 `ports/<部分>/`。

```
docs/architecture/

├── layers.md                 层级 1：分层与模块
├── overview.md               整体方案：解释性入口，不新增要求

├── core/                     核心模块，一个模块一个目录
│   ├── contracts/            核心契约

│   ├── sessions/             会话
```

骨架中列出的目录和文件都是预留位置。**不提前创建空目录或占位文件**，开始写哪个文档时再建对应的目录。骨架之外需要新增位置时，先修改本文。

### 2.1 各目录放什么

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `core/<模块>/` | 该模块负责的事实、对象、接口、流程、故障处理 | 其他模块的内部设计；跨多个模块的流程 |
| `ports/<部分>/` | 接口约定（`README.md`）和默认实现设计（`default.md`） | 某个具体适配器的细节 |
| `adapters/` | 具体适配器：对接的系统、效果与幂等等属性声明、故障表现 | 执行适配器的共同接口，那属于 `ports/executor/` |
| `platform/<服务>/` | 平台服务的设计 | 任务裁决逻辑 |
| `topics/` | 跨三个以上模块、不归属任何单一模块的主题 | 只涉及一两个模块的内容，放进对应模块 |
| `flows/` | 一个场景从头到尾经过哪些模块、在哪里持久化、故障后从哪里恢复 | 模块内部细节，只链接到模块文档 |
| `protocol/` | 机器可读的定义文件及其说明 | 设计理由，那属于模块文档或 ADR |
| `verification/` | 验证方法、测试矩阵、通过标准 | 测试结果；结果属于实施报告 |
| `assets/` | 图的源文件和导出文件，同名并存 | 只有导出图、没有源文件的图 |

## 3 模块目录的内部结构

每个模块目录从一个 `README.md` 开始。只有在以下情况才拆分出单独文件：

- 正文超过约 400 行
- 字段表、状态机等参考材料很长，影响正文阅读

拆分后的常用文件名：

| 文件 | 内容 |
| --- | --- |
| `README.md` | 模块设计正文，必需 |
| `records.md` | 对象字段和状态的完整定义 |
| `recovery.md` | 故障与恢复的详细分析 |
| `default.md` | 仅 `ports/` 下使用：默认实现的设计 |

## 4 命名规则

- 目录名和文件名使用英文小写，单词之间用短横线，例如 `fault-injection.md`。正文使用中文。
- 模块目录名与代码目录名保持一致。代码目录改名时，文档目录同步改名。
- 流程文档以场景编号开头，例如 `s7-unknown-payment.md`，与[项目目标](project-goals.md#6-用户与典型场景)中的 S1–S8 对应；没有对应场景的流程，用描述性名称。
- ADR 使用四位编号加短横线标题，例如 `docs/adr/0001-shard-by-user.md`，编号只增不复用。
- 图的源文件和导出文件同名，例如 `assets/admission-flow.dot` 与 `assets/admission-flow.svg`。能用 Mermaid 写在正文里的图，优先写在正文里。

## 5 写作与链接规则

**每篇设计文档必须独立可读。**读者不需要打开调研或归档文档就能理解设计和理由。需要用到调研结论时，把结论和必要的事实重写进正文；引用外部事实时，链接到固定版本的一手来源。

**只链接现行文档。**设计文档可以链接本目录、`docs/adr/` 和外部一手来源；不链接 `docs/research/`、`docs/archive/` 和 `.scratch/` 作为依据。

**术语统一。**术语以[项目目标](project-goals.md#3-核心术语)第 3 节为准。需要新术语时，先加到那里，再在设计文档中使用。

**编号可追溯。**设计文档引用目标时使用编号：能力 C1–C9、边界 A1–A4、不变量 G1–G12、场景 S1–S8、专项验收 V1–V2、依赖规则 R1–R7。

**状态如实。**设计文档描述的是目标设计，不代表已经实现或验证。任何"已达成""已验证"的说法都必须附上运行证据。

**修订有记录。**每篇文档开头保留修订表，记录日期和改动原因。

**整体方案随上游同步。**修改 `layers.md`、核心模块的职责或主线流程时，同步检查[整体方案](overview.md)。整体方案只描述机制之间的关系并链接上游，不复制字段表和状态枚举，以减少过时的内容。

## 6 模块设计模板

新建模块设计文档时复制以下结构。某节确实不适用时保留标题并写明原因，不要删除。

```markdown
# <模块名>

| 日期 | 修订说明 |
| --- | --- |
| YYYY-MM-DD | 初版 |

- 状态：草稿 / 评审中 / 已采纳 / 已替代
- 负责满足：C?、A?、G?
- 涉及场景：S?
- 上游：项目目标、分层与模块，以及相关 ADR

## 1 职责与边界

负责哪些事实；明确不负责什么；与相邻模块的分界。

## 2 对象与状态

核心对象、关键字段、状态及状态转换。完整字段表较长时拆到 records.md。

## 3 接口

对外提供的命令、查询和通知。每个接口写明：输入、输出、成功意味着什么、
可能的错误、是否幂等。

## 4 关键流程

正常路径的处理步骤，标出每一步在哪里持久化。

## 5 故障与恢复

逐项列出：回执丢失、进程崩溃、重复请求、并发冲突、依赖不可用、迟到结果。
每项写明负责方和恢复方式。

## 6 不变量落实

| 不变量 | 本模块怎样保证 | 怎样验证 |
| --- | --- | --- |
| G? | | |

## 7 取舍

考虑过的备选方案，以及选择和放弃的理由。难以撤回的决定另写 ADR。

## 8 待定事项

## 9 M1 范围

M1 做到什么程度，哪些推迟到哪个阶段。

## 10 测试要点

最关键的一致性测试和故障注入用例。

## 参考资料

外部一手来源，注明版本或访问日期。
```

流程文档（`flows/`）使用简化结构：场景描述、参与模块、逐步时序（标出每一步的持久化点）、每一步的故障与恢复、对应不变量。

## 7 M1 需要的文档

按[项目目标](project-goals.md#11-建议的开发顺序)，M1 开发前至少需要下列文档，建议按顺序编写：

| 顺序 | 文档 | 理由 |
| --- | --- | --- |
| 1 | `core/contracts/` | 其他所有模块都依赖核心对象的定义 |
| 2 | `core/durable/` | 所有模块的持久化和接替都依赖它 |
| 3 | `core/ledger/` | M1 的核心价值：未知效果与核对 |
| 4 | `core/tasks/` | 准入和完成门禁 |
| 5 | `core/grants/`、`core/budget/`、`core/sessions/` | 裁决域的其余部分，M1 只需最小版本 |
| 6 | `core/egress/` | 出口全覆盖 |
| 7 | `core/content/`、`core/trace/` | M1 只记录来源、派生关系和基础轨迹 |
| 8 | `ports/reasoner/`、`ports/executor/`、`ports/interaction/` | 推理、执行适配器和交互适配器的接口；M1 的确认、取消和中间状态呈现依赖交互接口 |
| 9 | `adapters/api.md`、`adapters/file.md` | M1 的两个适配器 |
| 10 | `flows/s2-multi-step-tools.md`、`flows/s7-unknown-payment.md` | 用两个场景串起全部模块 |
| 11 | `topics/data-and-storage.md` | 事务域、按用户分片和存储选择 |
| 12 | `verification/conformance.md`、`verification/fault-injection.md` | M1 的退出标准 |
