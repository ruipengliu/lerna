本文写给编写和评审设计文档的人，规定文档放在哪里、叫什么、写什么，以及文档之间以什么为准。新增、移动文档或变更状态时，按本文归置，并同步更新 [README](README.md#2-文档索引) 中的文档索引。

本文同时规定本目录的写作规则（第 5 节），包括读者、结构、术语、约束用语和图示。

## 1 文档层级

文档按上下游排列，下游不得改变上游的结论。下游发现上游有问题时，先修改上游并记录原因，再改下游。

| 层级 | 文档 | 回答的问题 |
| --- | --- | --- |
| 0 目标 | [项目目标](project-goals.md) | 做什么、为什么、做到什么程度算完成；术语、不变量、能力和验收 |
| 1 划分 | [分层与模块](layers.md) | 有哪些模块，各自负责什么事实，谁可以调用谁 |
| 2 决定 | `docs/adr/` | 难以撤回、需要单独记录理由的具体决定 |
| 3 设计 | 本目录下的模块、流程和专题文档 | 每个模块怎样满足上游要求：对象、接口、流程、故障处理 |
| 4 合同 | 仓库根的 `contracts/proto/`；说明放本目录 `protocol/` | 机器可读的接口定义（Protobuf），与代码同版本发布 |
| 5 验证 | `verification/` | 怎样证明设计成立：测试矩阵、故障注入、专项验收、容量 |

[整体方案](overview.md)不属于上述层级。它用一个端到端场景解释各模块怎样配合，供开发者入门；它不新增或修改任何要求，与上游冲突时以上游为准。

**文档状态。**"草稿"表示设计可以评审、尚未承诺；"评审中"表示有未处理的评审意见；"已采纳"表示可以作为实现依据；"已替代"表示由另一篇文档取代。一篇设计文档转为"已采纳"需要同时满足：针对它的 P1、P2 评审意见已经处理；第 8 节待办表中阶段为"M1 前"（或它所在的更早阶段）且涉及它的 ADR 已写成。M1 编码以第 7 节所列文档为依据：这些文档在上述条件满足后转为"已采纳"；尚未满足时，只有已经处理过评审意见的章节可以先用于编码，并在工单中注明。

本目录之外的文档：

| 位置 | 用途 | 与本目录的关系 |
| --- | --- | --- |
| `docs/adr/` | 架构决定记录 | 层级 2；模块设计中做出的难以撤回的决定，另写一篇 ADR |
| `docs/development.md` | 开发规范：代码目录、依赖检查、测试、提交 | 不是设计文档；代码只实现设计文档写明的规则，冲突时以设计文档为准 |
| `docs/implementation/` | 实施报告、实际验收结果及其原始数据 | 不是设计依据；按里程碑归档环境、受测版本、日志与限制，不能改变上游通过标准 |
| `docs/research/` | 调研、比较和来源 | 不是规范。设计文档需要其中的结论时，重写进正文，不链接为依据 |
| `docs/archive/` | 已废弃的旧方案 | 不是规范，不链接 |
| `.scratch/` | 功能规格和实现工单 | 实现层面的拆分；工单引用设计文档，设计文档不引用工单 |

## 2 目录骨架

模块目录与 [分层与模块](layers.md#11-代码组织) 中的代码目录一一对应，便于从代码找到设计，也便于从设计找到代码。唯一的例外是 `ports/`：可替换部分的接口定义在代码中属于 `contracts/`，默认实现在 `defaults/` 或 `adapters/`，文档则把接口约定和默认实现设计集中放在 `ports/<部分>/`。

骨架中列出的目录和文件都是预留位置。**不提前创建空目录或占位文件**，开始写哪个文档时再建对应的目录。骨架之外需要新增位置时，先修改本文。

### 2.1 各目录放什么

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `core/<模块>/` | 该模块负责的事实、对象、接口、流程、故障处理 | 其他模块的内部设计；跨多个模块的流程 |
| `ports/<部分>/` | 接口约定（`README.md`）和默认实现设计（`default.md`） | 某个具体适配器的细节 |
| `adapters/` | 具体适配器：对接的系统、效果与幂等等属性声明、故障表现 | 执行适配器的共同接口，那属于 `ports/executor/` |
| `platform/<服务>/` | 平台服务的设计 | 任务裁决逻辑 |
| `topics/` | 跨三个以上模块、不归属任何单一模块的主题 | 只涉及一两个模块的内容，放进对应模块 |
| `flows/` | 一个场景从头到尾经过哪些模块、在哪里持久化、故障后从哪里恢复 | 模块内部细节，只链接到模块文档 |
| `protocol/` | 协议说明：消息怎样组合、版本与兼容规则，链接到 `contracts/proto/` 中的定义 | 定义文件本身，只放在 `contracts/proto/`；设计理由，那属于模块文档或 ADR |
| `verification/` | 验证方法、测试矩阵、通过标准 | 测试结果；结果属于实施报告 |
| `assets/` | 图的源文件和导出文件，同名并存 | 只有导出图、没有源文件的图 |

验证文档可以链接对应实施报告，供读者查找实际结果；这个链接是证据导航，不把报告提升为设计依据。`docs/implementation/m1/` 保存 M1 当前报告及数据，`history/` 保存被后续测量替代的原件。原 H1 和本地档文档同时包含方法与结果，与本表的目录分工不符；拆分时先保存原字节和来源版本，再将方法留在 `verification/`、结果放实施报告。历史数据不得标为新 Schema 或新平台的测量。新增最终验收报告也遵守这一分工。

## 3 模块目录的内部结构

每个模块目录从一个 `README.md` 开始。只有在以下情况才拆分出单独文件：

- 正文超过约 400 行
- 字段表、状态机等参考材料很长，影响正文阅读

拆分后的常用文件名：

| 文件 | 内容 |
| --- | --- |
| `README.md` | 模块设计正文，必需 |
| `records.md` | 对象字段和状态的完整定义 |
| `recovery.md` | 故障与恢复的详细分析 |
| `default.md` | 仅 `ports/` 下使用：默认实现的设计 |

## 4 命名规则

- 目录名和文件名使用英文小写，单词之间用短横线，例如 `fault-injection.md`。正文使用中文。
- 模块目录名与代码目录名保持一致。代码目录改名时，文档目录同步改名。
- 流程文档以场景编号开头，例如 `s7-unknown-payment.md`，与[项目目标](project-goals.md#6-用户与典型场景)中的 S1–S8 对应；没有对应场景的流程，用描述性名称。
- ADR 使用四位编号加短横线标题，例如 `docs/adr/0001-shard-by-user.md`，编号只增不复用。
- 图的源文件和导出文件同名，例如 `assets/admission-flow.dot` 与 `assets/admission-flow.svg`。能用 Mermaid 写在正文里的图，优先写在正文里。

## 5 写作与链接规则

**每篇设计文档必须独立可读。**读者不需要打开调研或归档文档就能理解设计和理由。需要用到调研结论时，把结论和必要的事实重写进正文；引用外部事实时，链接到固定版本的一手来源。

**只链接现行文档。**设计文档可以链接本目录、`docs/adr/` 和外部一手来源；不链接 `docs/research/`、`docs/archive/` 和 `.scratch/` 作为依据。

**术语统一。**术语以[项目目标](project-goals.md#3-核心术语)第 3 节为准。需要新术语时，先加到那里，再在设计文档中使用。

**编号可追溯。**设计文档引用目标时使用编号：能力 C1–C9、边界 A1–A4、不变量 G1–G12、场景 S1–S8、专项验收 V1、V3、V4（V2 已撤销，编号不复用）、依赖规则 R1–R7。

**状态如实。**设计文档描述的是目标设计，不代表已经实现或验证。任何"已达成""已验证"的说法都必须附上运行证据。

**修订有记录。**每篇文档开头保留修订表，记录日期和改动原因。

**约束用语。**设计文档用以下用语表达要求的强度。本目录借鉴 RFC 2119/8174 的分级思想，但不采用其正式关键词语义。

| 用语 | 含义 | 例子 |
| --- | --- | --- |
| 必须／不得 | 实现必须遵守的要求或禁止事项；违反即为缺陷，能够写成测试 | 执行管理不得把超时记为"未生效" |
| 建议／不建议 | 默认选择；偏离时说明理由和影响 | 建议首批使用 PostgreSQL |
| 可选 | 实现可以选择是否提供的能力 | 可选的定向诊断 |

另有三条用法：

- "不能""无法"只陈述事实或逻辑上的不可能，例如"超时不能证明请求未执行"，不表达要求；
- 不使用"应""应当""应该"，按实际强度改为上表中的用语；
- 正文中描述系统行为的陈述句（例如"执行管理保存尝试"）就是要实现的目标行为。关键规则用"必须／不得"标出，便于测试和评审。

**区分事实、推断、建议和待验证事项。**引用外部来源的事实附链接；由事实推出的设计判断写明理由；没有实测依据的数值和前提标为"待验证"，集中列在"待定事项"中。

**读者。**模块、适配器、平台服务和专题文档的读者，是实现和评审该部分的开发者。这些文档先给出本设计的要点，再展开细节。

**结构与句子。**先给结论，再给依据、条件和例外；先讲整体，再展开细节。一句话尽量只表达一个主要意思，用明确的主语和具体的动词。关键前提、风险和例外紧挨相关结论，不藏在后面的章节里。

**一条规则只写一处。**跨模块的规则只在一个权威位置完整写出，其他文档引用它，只补充本模块怎样实现。例如四道门禁（准入、开始、重试、完成）各检查哪些条件，只在[核心契约 2.6](core/contracts/README.md#26-四道门禁)写；任务编排、出口闸门、授权等文档只写自己负责的那几项怎样落实。修改这类规则时，先改权威位置，再检查引用它的文档。

**字段名以核心契约为准。**公共对象的字段名和状态以[核心契约 2.3、2.5](core/contracts/README.md#23-对象一览)为准。模块文档的字段表默认是本模块的内部记录或读取视图，同名字段与契约同义，不得为契约已有的字段另起名字；状态如果是几个维度的组合，标明它是展示值。

**评审来源不写进正文。**某项设计来自哪一轮评审，记在修订表和评审处理记录里；正文只写现行规则，不加"〔评审 …〕"之类的标注，以免读者被历史打断。

**持久化点的编号。**"P1–P8"只指[出口闸门 4.1](core/egress/README.md#41-正常调用)中一次调用的持久化点，其他文档说"P4""P5"时都指它（P4 即开始门禁，P5 即写下"可能已发出"）。其他流程的持久化点叫"持久点 1、持久点 2……"，也可以在一篇文档内用字母前缀区分几条流程（例如评测的 E1–E11），编号只在本文内有效。跨文档引用和故障注入清单一律写成"文档或流程名/编号"，例如"数据与存储/D5""记忆接口/D3"，不要求各文档的前缀互不相同。分层原则 P1–P5 和评审优先级 P1、P2 是另外的编号，引用时写全称。

**图示。**状态转换、跨模块时序、组件关系和数据归属，优先用图表达：

| 要表达的内容 | 图的类型 |
| --- | --- |
| 一个对象有哪些状态、怎样转换 | Mermaid `stateDiagram-v2` |
| 多个模块按什么先后交互、持久化点在哪里 | Mermaid `sequenceDiagram` |
| 模块、事务域和存储归属 | 简单关系用 Mermaid `flowchart`；需要固定分区与连线路由时用 SVG |
| 判断与恢复流程 | Mermaid `flowchart`，长流程按阶段拆图 |
| 字段、属性和规则对照 | 表格，不画图 |

图写在正文里，前面用一两句话说明它画了什么、读者该注意什么。图只表达正文已经写明的规则，不得借图新增或改变规则；图与正文冲突时以正文为准，并修正图。图的标签用简短的中文，提交前校验 Mermaid 语法。一个图只回答一个主要问题；过长的时序按准备、执行、恢复等阶段拆分，合并或省略的模块在图注中说明。

SVG 和对应的自包含 HTML 源图放在 `assets/`，文件名描述主题，正文用相对路径嵌入 SVG。同一结构在不同文档中复用同一个文件。修改图时先改 HTML，再导出 SVG；检查文字溢出、连线和节点遮挡、中文字体回退以及 `title` / `desc` 无障碍说明。HTML 源图提供局部横向滚动；Markdown 中的 SVG 缩放过小时可打开原图。SVG 使用字体栈，离线或以图片嵌入时可能回退到本机中文字体。

**图内用语自明。**节点和连线先写具体职责、交付内容或发生的行为，不用规则编号代替说明。例如将“R7 交接”写为“交付动作并确认接纳”；规则编号及其含义放在图注中，链接到对应条款。

**整体方案随上游同步。**修改 `layers.md`、核心模块的职责或主线流程时，同步检查[整体方案](overview.md)。整体方案只描述机制之间的关系并链接上游，不复制字段表和状态枚举，以减少过时的内容。
