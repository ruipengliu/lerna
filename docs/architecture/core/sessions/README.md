会话持有**用户和系统之间的交互事实**：消息的顺序、用户的每一条输入要交给谁、系统向用户提的问题和确认、用户对它们的回应，以及会话和任务之间的关联。

它和其他模块的分工，用一句话说：**会话持有输入和交互，任务编排持有目标和推进，授权持有许可，动作账本持有效果。**四者通过稳定的标识相互关联，而不是通过"聊天进行到了哪一条"来推断彼此的状态。

本设计的要点：

- 会话内的顺序是**核心的提交顺序**，不按端点时间排序；任务另有自己的输入序；
- 每条输入都有**明确的类别和目标**，不存在影响所有端点的隐式"当前任务"；
- **确认在准入事务中一次性消费**。界面显示过、用户读过、本地回显过，都不等于确认；
- 编辑已提交的消息会**产生分支**，不改写历史，也不撤销已发生的效果；
- 离线时可以先在端侧记录输入，重连后**逐条核验**再追加；离线期间不得消费确认，也不得产生新的准入。

## 1 职责与边界

| 会话持有的事实 | 职责 |
| --- | --- |
| 消息顺序 | 分配会话提交序，记录消息身份、因果引用和所属分支 |
| 用户输入 | 保存类别、目标、提交时看到的版本、投递结果 |
| 输入请求 | 保存系统提出的问题和确认事项，按请求标识匹配回应 |
| 确认 | 保存批准、拒绝、撤回和一次性消费 |
| 任务关联 | 保存会话、分支和任务之间的关联及其角色 |
| 交互历史 | 提供带持久水位的视图 |

| 相邻模块 | 分工 |
| --- | --- |
| 任务编排 | 创建任务、接纳任务输入、更新条件和输入版本、控制、准入、关闭。会话不改写任务状态 |
| 授权 | 检查主体和用途、管理许可和撤销。会话里的确认不会自动产生或扩大授权 |
| 预算 | 在准入事务内给出预算结论。会话不按消息数自行计费 |
| 持久工作 | 持有命令回执、待办工作和领取 |
| 内容治理 | 持有正文、附件、版本、来源、用途和派生关系。**会话原则上只保存内容引用** |
| 动作账本 | 持有效果和核对状态；会话只呈现它的回报 |
| 交互适配器 | 收集用户事件、显示状态、保存端侧待发送记录。不得根据"已显示"或"已读"生成确认 |
| 网关与 SDK | 认证连接、传输、重连和补拉。业务幂等由持久工作和核心事实保证 |

会话、任务编排、授权和预算在同一个裁决事务域。共享事务不改变各自的唯一写入责任（R3）。

## 2 对象与状态

### 2.1 通用字段

所有持久对象带 `user_id`、对象标识和契约版本，可变对象带修订号。时间字段用于展示、诊断或明确的到期判断，不得代替业务顺序。

| 字段 | 语义 |
| --- | --- |
| `command_id` | 调用前生成的稳定标识，重试时复用，在用户范围内唯一 |
| `endpoint_id`、`endpoint_generation` | 输入来自哪个端点；代次跨连接保持，只有明确封存时才失效 |
| `client_command_seq` | 端点上单调递增的整数，用来辅助证明命令身份和清理范围，不是服务端的显示顺序 |
| `depends_on` | 显式的因果前提（命令或消息标识）；不依赖网络到达顺序 |
| `observed_session_seq` | 用户提交时看到的会话水位，用于诊断和解释冲突 |
| `expected_requirements_version`、`expected_input_version` | 按输入类别必填；防止基于旧任务上下文的修改或回答被静默套用 |
| `content_ref` | 内容标识和版本；正文和附件归内容治理，保存和同步必须有相应许可 |
| `payload_commitment` | 规范化参数的摘要，用于检查同一命令的参数是否一致；摘要本身也受 G8、G9 约束 |

`user_id` 和主体身份来自经过验证的调用上下文。交互适配器自己报告的"这是用户确认"不被接受。

### 2.2 核心对象

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 会话 | `session_id`、`status`、`last_committed_seq`、`revision` | 独立于任务创建和关闭 |
| 分支 | `branch_id`、`parent_branch_id`、`fork_message_id`、`fork_snapshot_seq`、`head_message_id`、`revision` | 父链无环；历史前缀固定到具体的消息版本 |
| 消息事件 | `event_id`、`session_seq`、`branch_id`、`message_id`、`parent_message_id`、`event_kind`、`content_ref` | 身份和已有顺序不改写；正文可以被内容治理撤回 |
| 用户输入 | `input_id`、`message_id`、`kind`、目标引用、提交时看到的版本、`routing_status` | 投递后目标不可静默改变 |
| 任务关联 | `association_id`、`session_id`、`branch_id`、`task_id`、`role`、`revision` | 角色为"控制"或"引用"；关联不转移任务负责方，也不是授权 |
| 输入请求 | `request_id`、`kind`、来源会话/分支/任务、请求版本、正文引用、有效期、状态 | 独立 UI 中的问题可以不关联任务 |
| 确认绑定 | 准入事项标识、条件集版本、输入版本、关联版本、事项摘要、相关授权版本 | 由核心固定，回应方不得修改 |
| 回应与消费 | 回应输入、决定、回应主体、`consumed_by_admission`、动作标识集合 | 回应和消费分开记录；消费只能发生在准入事务里 |
| 任务输入记录 | `task_id`、`task_input_seq`、`input_version`、来源输入、处理状态 | 由任务编排写；会话读取接纳结果。它不是第二份正文 |

### 2.3 输入的类别

| 类别 | 必要引用 | 被接纳后的含义 |
| --- | --- | --- |
| 新目标 | 目标内容；可选的历史上下文引用 | 任务编排创建任务和初始条件，会话保存关联 |
| 修改任务 | 明确的 `task_id`、看到的条件集版本和输入版本 | 任务编排接纳修改，基于旧输入的快照立即失效；文本内容不会直接扩大授权 |
| 回答问题 | `request_id`、请求版本、答案 | 只回答这一个问题；请求必须仍然有效 |
| 确认 | `request_id`、绑定摘要、明确的批准或拒绝 | 记录确认回应；批准不等于已准入或已执行 |
| 仅记录 | 内容引用，可以不关联任务 | 会话保存，但不创建任务，也不投递给任意的"当前任务" |
| 控制（暂停、取消等） | 明确的 `task_id` 和控制种类 | 由任务编排裁决；不得伪装成普通聊天文本 |

一条输入默认只投递给一个任务。将来如果支持显式广播，必须展开成分别可追溯的任务命令。

推理可以帮助判断一条模糊输入属于哪一类、指向哪个任务，但它的判断只是提议；有歧义时，输入先作为"仅记录"保存，等用户明确指向。自然语言的"好""继续"，只有明确引用了一个有效的确认事项时，才能成为确认回应。

### 2.4 状态

| 对象 | 状态转换 | 规则 |
| --- | --- | --- |
| 会话 | 活跃 ↔ 归档；活跃或归档 → 删除处理中 → 已删除 | 归档不取消任务；删除完成以内容治理的清理结果为依据 |
| 输入投递 | 已记录 → 待指向 / 待依赖 / 任务已接纳 → 已处理 / 处理被拒绝 | "已记录"不等于"任务已接纳"；失败不自动改投其他任务 |
| 普通问题 | 待回答 → 已回答 / 过期 / 撤回 / 被替代 | 第一个有效回答生效；修改答案使用新的输入 |
| 确认 | 待回应 → 已批准 / 已拒绝 | 显示、已读、回显都不改变状态 |
| 已批准的确认 | → 已消费 / 已撤回 / 过期 / 被替代 | 消费与准入原子提交；其他状态都不得被消费 |
| 已消费的确认 | 保持已消费 | 执行失败、取消、分支、进程重启都不会恢复它的消费资格 |
| 端侧待发送记录 | 本地已保存 → 提交中 → 核心已记录 / 冲突 / 失效 | 这是端侧状态，不得冒充核心状态 |

到期、授权变化和任务版本失效，必须在回应时和消费时检查，不得只依赖后台定时器更新状态。

### 2.5 顺序与版本

1. **会话提交序。**事务锁定会话头记录，分配连续的事件序号，把事件、会话头和回执一起提交。回滚不推进会话头；迟到的输入只追加在尾部，不插入旧序号。
2. **分支历史。**分支由固定的父链加本分支的消息组成；会话事件序负责同步，分支头版本负责编辑冲突检查。
3. **任务输入序。**任务编排为来自所有会话的输入统一分配 `task_input_seq`。
4. **任务输入版本。**修改或有效答案被任务接纳后，输入版本递增。提议同时绑定条件集版本、输入版本和上下文快照，准入时全部核验。如果只有条件版本，一条已被接纳、尚未被解释的修改或答案，就可能被基于旧上下文的提议忽略。
5. **确认回应是例外。**批准回应只更新确认事实，不递增输入版本，否则批准会立刻让它所确认的事项失效。普通的修改、答案和相关的控制变化，才会让旧事项失效。
6. **端点焦点。**"当前任务""当前分支"只是某个端点的视图选择；提交时转成明确的引用，不存在一个影响所有端点的全局焦点。

Lamport 证明了因果上的先后能推出逻辑时钟的大小，反过来却推不出；加入进程标识可以得到一个全序，但这个全序不是唯一的（[Lamport 1978](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)）。所以端点时间、逻辑时钟和提交序都无法单独恢复"用户在各个端点上真正的先后意图"。本设计的做法是：用核心提交序提供稳定的历史，用显式依赖表达确实存在的因果关系，对真正并发的输入采用提交顺序，不去猜测全局发生顺序。

## 3 接口

所有改变状态的接口都使用稳定的命令标识，成功回执只在相应事务持久提交之后返回。

| 接口 | 输入 | 成功含义 | 主要错误 |
| --- | --- | --- | --- |
| 创建会话 | 用户上下文、命令标识、允许保存的元数据 | 会话已持久创建 | 授权不足、参数不符 |
| 提交输入 | 通用字段、类别、目标、版本、内容或明确的决定 | 返回输入标识、事件序、投递或确认状态；**明确区分"已记录"和"任务已接纳"** | 依赖未满足、目标无效、版本冲突、请求已失效、已被回应 |
| 指定待投递的输入 | 输入标识、原投递版本、明确的类别和目标 | 新的投递决定和任务接纳引用 | 已投递、并发冲突、目标不属于该用户 |
| 设置任务关联 | 会话、分支、任务、角色、预期关联版本 | 关联已保存 | 用户不符、权限不足、版本冲突 |
| 发布输入请求（核心调用） | 核心已接纳的提问或确认事项、来源、版本、有效期 | 事项已保存，可以呈现 | 来源失效、内容不可用、同来源不同参数 |
| 消费确认（裁决域内调用） | 当前准入事务、准入事项和完整绑定 | 消费关联；**只有整个准入事务提交时才生效** | 未批准、已过期、已撤回、绑定不符、已用于其他准入 |
| 撤回尚未消费的确认 | 确认标识、预期版本 | 已撤回，之后不可消费 | 已消费、并发冲突 |
| 建立分支、编辑历史 | 固定的源消息版本、预期分支版本、编辑内容引用 | 新分支和新消息已建立 | 来源不可用、版本冲突、尚未支持 |
| 设置会话状态 | 归档、恢复或请求删除，预期版本 | 状态和清理跟踪引用；删除请求成功只表示清理责任已被接下 | 冲突、授权不足 |
| 追加任务呈现事件（核心调用） | 唯一的来源事件、原会话/分支/任务、内容和状态引用 | 呈现记录已保存 | 来源不合法、正文已撤回；按来源事件去重 |
| 查询视图、事件或原回执 | 会话或命令标识、游标、可选的最低提交水位 | 带水位的视图、增量或原决定 | 无权限、游标过旧、权威不可用 |

| 错误类别 | 调用方怎样处理 |
| --- | --- |
| 参数或绑定不符 | 保持原命令参数不变重试；确有新意图时，提交新的明确命令 |
| 版本冲突 | 保留原输入，展示冲突；用户重新审视后指定投递或提交修正 |
| 依赖暂时故障 | 用原标识重试或查询；不得改建任务 |
| 提交结果未知 | 查询原命令；不把网络超时当作未接纳 |
| 请求过期、代次已封存、已撤回 | 不自动换个请求或代次重新提交 |
| 游标过旧 | 取一个带水位的新快照，再从该水位补拉 |

对于获准保存的输入，版本冲突时可以返回"已记录、未投递"，避免丢失用户写的内容；没有保存许可的正文不得这样处理。

## 4 关键流程

### 4.1 输入的记录与任务接纳

| 步骤 | 处理 | 持久化 |
| --- | --- | --- |
| 1 | 交互适配器生成稳定的身份，保存允许保存的待发送输入 | 端侧持久记录，只承诺本地已保存 |
| 2 | 内容治理接纳正文和附件，核验保存和同步用途 | 内容治理持久接纳；跨域交接按 R7 |
| 3 | 核心验证用户、会话、类别、依赖、目标和版本 | 不产生外部调用 |
| 4 | 会话追加事件；任务编排创建任务或接纳输入；持久工作记录决定和待办 | **一个裁决域事务**：事件、会话头、关联、任务接纳、回执、待办一起提交 |
| 5 | 提交后返回准确的状态，并发出通知 | 通知丢失可以从第 4 步的记录恢复 |
| 6 | 任务编排处理输入、固定新的上下文；需要修改条件时另外持久裁决 | 推理只给提议 |
| 7 | 后续进展经过内容治理和来源事件去重后进入会话 | 原任务、原分支的引用不因界面切换而改变 |

第 2 步之后、第 4 步之前崩溃，可能留下尚未关联的内容。内容治理按原保存命令和保留策略处理它，不当作已投递的任务输入。

区分"已记录"和"已接纳"很重要。Temporal 的 Update 分 `Accepted`（已持久化）和 `Completed`（处理器已返回）两个阶段，而且阻塞的消息处理器可能交错执行（[Temporal 消息处理](https://docs.temporal.io/handling-messages)）。按顺序收到，不代表按顺序生效。Lerna 要分别表达"会话已保存""任务已接纳""确认已消费""效果已确定"。

### 4.2 确认与准入

1. 任务编排固定准入事项，包括资源、动作、重要参数、内容版本、条件集版本和输入版本；会话持久保存确认请求；
2. 交互适配器呈现该事项。**呈现本身不产生任何回应记录**；
3. 用户明确批准或拒绝。会话核验主体、事项绑定和当前有效性，在事务中保存第一个有效回应及回执；
4. 对已批准的事项，任务编排在**同一个准入事务**中检查：任务允许推进、版本和事项仍有效（任务编排）；当前授权有效且覆盖该事项（授权）；预算足够（预算）；确认已批准、未消费、未过期、未撤回且绑定一致（会话）；同一事项还没有其他准入决定（任务编排、持久工作）；
5. 原子写入确认消费、准入决定、动作意图、预算预留、待办和回执。**任一检查失败，确认都不被消费**；
6. 动作意图按 R7 交给动作账本；执行端点在出口闸门处再核验；之后的效果由动作账本负责；
7. 第 5 步已提交但回执丢失时，恢复原准入决定，不恢复确认的消费资格，也不生成新动作。

OWASP 的交易授权指南要求：用户能识别确认事项中的重要数据；状态转换由服务端控制；参数变化后重新授权；设置执行前检查、有限的有效期和每个操作唯一的凭证（[OWASP 交易授权](https://github.com/OWASP/CheatSheetSeries/blob/6b6a66bae11c9e001c3576bcc3de55cc0dc5e449/cheatsheets/Transaction_Authorization_Cheat_Sheet.md)）。本设计用"核心固定事项 + 准入事务内一次性消费"落实这些要求。签名令牌或随机令牌可以作为请求的句柄，但在有效期内仍可被重放，不得代替消费记录。

M1 中一次确认对应一个准入事项。将来确认有限计划时，必须冻结完整的动作集合；新增或替换动作不得复用原来的确认。

### 4.3 回答按请求标识寻址

回答必须按稳定的 `request_id` 匹配到具体问题，不得匹配到"最新的那个问题"或列表中的某个位置。LangGraph 1.0.2 的 `interrupt()` 按节点内的索引匹配已保存的恢复值，官方文档警告：恢复时会重跑节点，中断的顺序一旦变化就可能错配回答，节点里位于中断之前的副作用也可能重复执行（[中断规则](https://docs.langchain.com/oss/python/langgraph/interrupts#rules-of-interrupts)）。Lerna 的恢复工作也不得重新产生授权，或直接执行动作。

### 4.4 分支、编辑与任务关联

| 操作 | 处理 | 对运行中任务的影响 |
| --- | --- | --- |
| 建立分支 | 在固定的消息版本处保存父关系、历史前缀和新分支 | 不创建或重跑任务 |
| 编辑已提交的用户消息 | 在被编辑消息之前建立分支，保存新内容版本及其派生关系 | 原任务继续依据原记录承担责任 |
| 更正当前任务 | 作为指向该任务的新修改输入被接纳，推进输入版本；条件改变时再推进条件集版本 | 基于旧快照的提议不得准入 |
| 关联已有任务 | 验证同一用户和控制权限，保存"控制"或"引用"角色 | 不改变任务负责方 |
| 在新分支中查看历史确认或效果 | 只作为带来源的历史引用显示 | 不复制消费资格、出口凭据或执行责任 |

草稿可以在本地覆盖。已提交的消息不得用同一身份替换正文，以免改写已有准入的依据。删除正文走内容治理流程，"历史不可变"不得成为拒绝 G9 的理由。

LangGraph 的 `add_messages` 会用相同的消息标识替换内容；它的"时间旅行"保留原历史，不回滚原运行，从检查点继续会重跑后续节点（[分支说明](https://docs.langchain.com/oss/python/langgraph/use-time-travel)）。这类消息合并器和运行检查点不得充当授权和效果账本，分支也撤不回现实中已发生的效果。

会话和任务是**多对多**关系：会话可以不关联任何任务，一个会话可以先后关联多个任务，一个任务也可以被多个会话引用或控制。关联既不是授权，也不是广播规则。

### 4.5 离线与重连

离线时，端侧可以先持久记录用户的输入。但默认部署中，确认的消费和新的准入都在云端的裁决域，所以离线期间**不得消费确认，也不得产生新的准入**。

重连按以下顺序处理：

1. **先恢复当前的权威状态**：核对端点身份与代次、授权、内容治理状态、任务状态、条件和输入版本、未决的确认；
2. **查询已有的提交**：用原命令标识消除回执丢失造成的不确定；
3. **按显式依赖补送**：缺少前驱的等待；引用了离线时创建的新目标的，通过原创建命令解析出任务标识，不另建任务；
4. **逐条单独裁决**：普通文本可以追加；修改可能冲突；答案可能已失效；批准必须仍然绑定着当前事项；
5. **对齐本地回显**：按输入或命令身份匹配服务端事件，不依赖回执和通知的到达顺序；
6. **持久推进游标**：只有完整处理了某个提交前缀之后才保存新的游标；有缺口就显式补拉。

| 离线时的输入 | 重连后的结果 |
| --- | --- |
| 两个端点各自提出的新目标 | 分别创建任务，按核心提交顺序记录 |
| 两个端点基于同一版本修改同一任务 | 第一个被接纳；另一个保留并报告冲突，不静默覆盖 |
| 回答一个已被替代的问题 | 不作为当前答案投递；授权允许时保存为迟到的记录 |
| 批准了基于旧条件或旧输入版本的事项 | 不准入，也不自动绑定到新事项 |
| 暂停或取消已有任务 | 交给任务编排按当前状态处理；本地只显示"等待送达" |
| 端侧专有内容 | 只同步获准同步的引用或结果；正文和敏感元数据不得借补送外流 |

明确的任务控制可以优先发送，不必等待无关文本补送完；但它仍按真实的核心提交顺序生效，不得回填成"云端早就取消了"。

Matrix 的做法提供了参照：transaction ID 用于识别重传，作用域包括设备，访问凭据刷新不改变作用域；本地回显和服务端回显要区分，后者可能早于发送回执到达；同步时受限的时间线可能有缺口，需要补拉（[Matrix v1.18](https://spec.matrix.org/v1.18/client-server-api/#transaction-identifiers)）。但它的服务端实现 Synapse v1.114.0 会清理超过 24 小时的事务标识映射（[events_worker.py](https://github.com/element-hq/synapse/blob/5eec67b6ef4b76caa2324a80e01e361bfa84a929/synapse/storage/databases/main/events_worker.py)）。所以"有幂等键"不能等同于"任意长的离线重试都安全"，见 4.6。

### 4.6 去重的保留期限

按正文或参数哈希去重，会误合并用户有意重复提交的两个相同目标；"固定期限后清理回执，过期后重新接纳"，则可能在长时间离线后重复创建任务或重复批准。本设计采用**稳定命令标识 + 参数一致性检查 + 旧代次封存**：同一标识不同参数被拒绝；重连和认证刷新时复用原标识；端点代次被封存之后，它未提交的输入只能保留为草稿，不得自动换新身份补送。这样回执可以安全地压缩，旧命令也不会被重新接纳。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | SDK、持久工作；会话解释业务结果 | 查询或重发原命令，返回原输入、任务或确认的决定 |
| 进程崩溃 | 持久工作、会话、任务编排 | 未提交的事务没有决定；已提交的记录和待办由新工作者恢复，不改变任务或动作的负责方 |
| 重复请求 | 持久工作、会话 | 同身份同参数返回原决定，不同参数拒绝；正文相同但命令不同的，可以是两个目标 |
| 并发修改 | 会话、任务编排 | 会话序号原子分配；任务或分支的版本冲突明确返回，不采用"最后写入覆盖" |
| 并发的批准、拒绝、撤回 | 会话、任务编排 | 第一个有效回应生效；撤回与消费串行裁决。消费先提交时，撤回不得被误报为动作已撤销 |
| 数据库不可用或持久提交失败 | 所属裁决域 | 不返回核心接纳成功；端侧保留待发送记录 |
| 内容治理不可用 | 内容治理、会话 | 没有可证明有效的内容引用就等待；不得把正文临时复制到会话或日志来绕过治理 |
| 迟到的任务输出或效果回报 | 任务编排、动作账本；会话呈现 | 按原来源和原任务保存，不投给当前焦点；会话归档或解除关联不会丢弃效果和费用 |
| 旧提议迟到 | 任务编排 | 条件或输入版本不符就不得准入；会话不得把它显示为当前的完成结论 |
| 通知丢失、重复、乱序 | 网关、交互适配器 | 按持久事件补拉和去重；通知不承担接纳责任 |
| 端点重装或旧代次封存 | SDK、持久工作 | 旧命令查询原结果或被明确拒绝；不自动换新身份重新接纳 |
| 断网期间发生撤回或删除 | 授权、内容治理 | 重连先核对；旧输入和缓存不会自动恢复使用；没拿到全部清理回报前，不宣布清理完成 |

## 6 不变量落实

| 不变量 | 本模块怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 提交超时显示"结果待查"；动作未知来自动作账本，不得转成失败后新建任务重试 | 回执丢失、迟到效果之后，原命令和原动作身份不变 |
| G2 | 输入已处理、消息已显示都不产生任务成功；完成只引用任务编排的 Result | 伪造完成文本、只有工具应答、存在未收尾动作时，任务不得成功 |
| G3 | 输入、投递决定、回执和待办原子提交；端侧保存和核心接纳分开 | 在各持久化点前后崩溃，检查是否虚报接纳或丢失责任 |
| G4 | 确认消费绑定条件集版本、输入版本和事项，与授权、预算和准入在同一事务 | 任一前提变化都无法消费；消费和准入不会出现只有一边的记录 |
| G5 | 会话不直接调用模型或工具；将来的分类、摘要等辅助调用也经准入和出口闸门 | 替换交互适配器，检查它无法借会话接口形成外部调用的旁路 |
| G6 | 推理的分类、提问和行动提议都必须经核心接纳；正文不得被解析成核心的确认事实 | 注入"已批准"、伪造系统角色，都不产生批准或准入 |
| G7 | 关联和分支不授予权限；确认不扩大授权；扩展不得自称用户来确认 | 跨任务、跨分支、扩展主体、扩大参数范围的重放都被拒绝 |
| G8 | 保存、读取、同步和行动分别检查；历史中的内容引用不得绕过当前授权 | 允许读取但禁止保存或同步；撤回后，分支、缓存和迟到输入都不得继续使用 |
| G9 | 正文、摘要和派生关系归内容治理；会话只保留不含正文的必要身份和阻用状态 | 旧分支、回执、缓存和离线补送都无法复活已撤回的正文 |
| G10 | 重复输入不会重复触发待办；费用引用预算记录 | 重复提交、关闭会话后到达的费用，都按实际计费来源只计一次 |
| G11 | 断线、分支和解除关联都不会创建替代任务；确认的消费不因执行失败而恢复 | 超时、取消、重启和编辑之后，原任务和动作仍可追溯 |
| G12 | 身份、查询、关联、内容和命令去重都带用户范围 | 猜测他人标识、命令身份碰撞、错误关联和过载都不影响其他用户 |

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 核心提交序，不按端点时间回填 | 历史稳定，游标可以恢复 | 迟到的输入出现在尾部；需要另外显示端点时间 |
| 会话序和任务输入序分开 | 支持多个任务和跨会话的输入 | 多一组任务侧的顺序和来源关联 |
| 明确的请求和目标引用 | 避免多端焦点和多个问题造成的误投 | 交互适配器要携带更多上下文 |
| 确认与准入原子消费 | 防重放，能恢复原决定 | 确认不能拆成独立的最终一致事务域 |
| 编辑历史产生分支 | 原始依据和现实后果都可追溯 | 不提供"编辑消息即撤销动作"的体验 |
| 内容引用和逻辑事件分开 | 删除、用途和派生关系统一治理 | 读取和呈现依赖内容治理 |
| 离线记录、重连核验 | 支持端侧输入，同时保持权威归属 | 会出现需要用户处理的冲突和失效输入 |
| 回执清理后仍阻止旧身份 | 长期恢复不会变成重复任务 | 需要明确代次的寿命和清理协议 |

被否决的方案：每用户一条全序日志（所有会话共享一个排序热点，而多数消息并不需要全序）；以多端 CRDT 作为权威历史（合并规则不能解决确认、授权和任务状态的裁决，而且 Automerge 在并发删除和更新同一键时保留更新，各副本达成一致并不意味着"删除优先"，见 [Automerge 合并规则](https://automerge.org/docs/reference/under-the-hood/merge-rules/)）。CRDT 可以用在草稿上。

确认消费事务、"分支不克隆执行责任"、去重清理规则，正式采纳前必须写成 ADR。

## 8 待定事项

| 事项 | 验证或决策方式 |
| --- | --- |
| 单用户负载下，会话头短事务和任务输入串行接纳的吞吐 | 测量热点会话、跨会话修改同一任务、离线积压时的吞吐和尾延迟 |
| "第一个有效回应生效"的多端体验 | 测试另一个端点能否准确显示原决定、冲突原因和撤回入口 |
| 确认的有效期 | 按事项类别评估风险和响应时间，不直接套用登录会话的超时 |
| 端点代次和回执保留的上限 | 明确支持的最长离线时间、封存流程和连续前缀清理的证明 |
| 用户事件来源能否可靠区分 | 明确网关、端点、交互适配器和扩展的信任与凭据边界（见[交互适配器接口](../../ports/interaction/README.md)） |
| 到期判断所依赖的时钟 | 定义裁决域时钟和异常处理；时间不可信时阻止依赖它的消费 |
| 长历史和多分支的读取成本 | 测量父链深度、分页、快照和内容撤回的传播 |

## 9 M1 范围

| 项目 | M1 实现 | 推迟 |
| --- | --- | --- |
| 会话与关联 | 可以创建不关联任务的会话；一个会话可以先后关联多个任务；任务关闭不关闭会话 | 丰富的多会话控制界面 |
| 输入 | 明确的新目标、修改、回答、确认和任务控制，带准确的目标和请求引用 | 高级的自然语言分类、复杂广播 |
| 顺序与并发 | 会话事务序、稳定身份、依赖和版本检查；模拟并发下不误投、不丢输入 | 真实的多端网络和离线积压：M3 |
| 确认 | 事项绑定、明确回应、一次性消费、到期检查、撤回、与准入原子提交 | 有限计划的确认 |
| 持久回执与恢复 | 完整；重启和回执丢失时都查询原命令 | 不得推迟，不得用内存实现代替 |
| 内容与来源 | 正文引用、版本、来源和派生关系从第一天记录 | 完整的用途限制和删除传播：M2 |
| 任务输入版本 | 修改和回答被接纳后，基于旧上下文的提议无法准入 | 不得作为 UI 优化推迟 |
| 分支与历史编辑 | 定义语义；接口明确返回"不支持"，不原地覆盖 | M2 |
| 离线与重连 | 同一宿主重启后恢复待办和命令；不宣称真实端云离线已通过验收 | 端侧待发送记录、同步、授权核对和缺口恢复：M3 |

M1 的最低退出标准：重试不重复创建任务；恢复不丢失已接纳的输入；确认不被重复消费；确认消费与准入不脱节；基于旧上下文的提议无法执行；取消和未知效果被如实呈现。

## 10 测试要点

从公开接口观察结果，用状态模型检查整段历史，而不只断言某个内部函数被调用。

| 用例 | 注入或并发 | 必须观察到 | 对应 |
| --- | --- | --- | --- |
| 输入原子接纳 | 在事件、任务接纳、回执、待办提交的前后崩溃 | 要么全部存在，要么全部不存在 | G3、R7 |
| 持久提交失败 | 磁盘满、写入失败、同步失败 | 不返回核心接纳成功；原输入可恢复 | G3 |
| 输入回执丢失 | 提交成功后断开，反复重试 | 同一输入、同一任务、同一原决定 | G3、G11 |
| 同标识不同参数 | 修改目标、正文、请求标识或确认范围后重试 | 参数不符；原决定不变 | A4、G4 |
| 正文相同、意图不同 | 用不同命令标识提交两个相同目标 | 两个独立任务，不按正文去重 | C1 |
| 序号空洞 | 延迟一个较小序号的事务，让其他操作先完成 | 游标不越过未证明完整的前缀 | G3 |
| 多会话修改同一任务 | 两个会话基于同一输入版本修改 | 不发生覆盖丢失；冲突明确；任务输入序可查 | C5、G4 |
| 多个问题乱序回答 | 同时发布多个问题，倒序提交答案 | 按请求标识匹配，绝不匹配"最新的问题" | C6、C7 |
| 呈现不等于确认 | 呈现、已读、回显、重连重绘，但没有明确回应 | 确认保持未批准、不可消费 | C7、G6 |
| 两端同时批准和拒绝 | 同时提交相反的决定，再重复提交 | 只有一个有效回应；后到的一方能查到原决定 | G3、G4 |
| 撤回与准入竞争 | 批准后并发撤回和消费 | 撤回在先则无准入；准入在先则消费保留，不得伪报撤销效果 | C7、G11 |
| 准入事务中途失败 | 依次在版本、授权、预算、消费和意图写入处注入失败 | 不会出现"消费成功但没准入"或"没消费却已准入" | G4、G6 |
| 消费后崩溃 | 准入提交之后、交给动作账本之前崩溃 | 原准入继续交接；不重建确认或动作 | G3、G11 |
| 事项失效与重放 | 改条件、输入、参数、授权；跨任务、分支、用户使用 | 旧确认无法消费；原任务记录仍在 | G4、G7、G12 |
| 取消与迟到效果 | 取消后才到达动作效果和费用 | 未知不被改为"未发生"；效果和实际费用保持原归属 | G1、G2、G10、G11 |
| 分支与编辑 | 在已有确认、动作和未知效果的历史处编辑 | 新分支没有消费资格，也不重放执行；原责任不消失 | G4、G11 |
| 离线时的旧批准 | 端侧批准后，另一端修改任务或撤销授权，然后重连 | 不自动映射到新的确认或准入 | C5、C7、G4、G8 |
| 回显先于回执 | 通知重复、乱序，且早于发送回执 | 最终只显示一条输入；状态可以从核心恢复 | C6、G3 |
| 超过去重保留期 | 清理回执后重放旧命令和旧代次 | 明确拒绝或返回墓碑；不会重新创建任务 | G3、G11 |

状态模型持续检查：每个命令最多一个决定；每个确认最多被消费一次，每个准入事项最多一个准入决定；已消费的确认必然有同一事务的准入记录；修改或答案被接纳之后，基于旧输入的提议无法准入；分支、删除、断线和归档都不会抹掉原动作的责任或实际费用。
