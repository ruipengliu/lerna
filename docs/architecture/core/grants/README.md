授权回答一个问题：**这个经过验证的主体，现在能不能在这个任务、这个端点、这个时间、为了这个用途，对这个实际资源做这件具体的事；如果能，占用的是哪一份授权。**

本设计的选择：

- 授权事实由核心持有，用**有版本的许可子句**表达。子句的范围是有限的，所以"委派只收缩"可以被机器判定；
- 一次性授权在**准入成功时**消费，而不是在凭据核验时或外部效果成功后；
- 凭据只承载受限的权限证明，**每次使用都检查当前状态**。M1 使用不透明的凭据引用；
- 撤销分两个阶段：**被接纳**时立即拒绝一切新使用，**各执行端点确认停止**后才算完成；
- 断网时，无法证明当前授权有效就等待。

授权**不负责**证明任务完成、推断效果、决定能否重发、自动补偿，也不负责实际的内容清理。

## 1 职责与边界

授权持有：许可、使用记录、委派关系、凭据签发记录、撤销及其封闭进度、用户—端点—密钥绑定、扩展的权限上限、设备控制权代次。

| 相邻模块 | 分工 |
| --- | --- |
| 任务编排 | 持有任务、条件和准入决定；在准入事务中调用授权核验并占用 |
| 会话 | 持有用户输入和确认；授权只能请求消费确认，不得自行制造确认 |
| 预算 | 持有额度和用量；授权不签发预算，也不结算费用 |
| 动作账本 | 持有执行尝试、效果、核对和迟到可能性 |
| 内容治理 | 持有内容来源、版本、用途限制和删除状态；授权的判断与它的限制取交集 |
| 出口闸门 | 核验实际调用并控制出口；使用事实写回授权，尝试写回账本 |
| 扩展管理 | 持有安装包和版本；扩展声明的权限只构成**上限**，由授权持有并据此裁决 |
| 推理、记忆策略、适配器 | 提交提议、检索请求或执行回报；不得写授权事实 |

**用户控制和任务权限是两回事。**经过验证的用户可以直接撤销自己的授权，不需要先拥有被撤销的那份授权。推理和扩展都不得继承这个用户控制身份。

## 2 对象与状态

### 2.1 授权记录

授权一经创建，其许可范围不得扩大。需要更大的范围时，由用户明确授予一个新的根授权；不得修改旧记录，然后让子授权自动获得新权限。

| 字段 | 含义与约束 |
| --- | --- |
| `user_id`、`grant_id` | 用户隔离；授权标识永不复用 |
| `issuer_ref` | 根授权指向可信的用户事件；派生授权指向来源和委派决定 |
| `subject_ref` | 经过验证的主体：任务运行主体或扩展实例，包含适用的配置和版本 |
| `parent_grant_id` | 派生来源；默认是单来源的委派树，不得成环 |
| `clauses` | 许可子句列表，见下表 |
| `semantic_version` | 动作、用途、资源范围和规范化规则的语义版本；不使用隐式的"最新" |
| `valid_from`、`valid_until` | 半开的有效时间窗；持续授权也有明确期限 |
| `use_mode`、`max_admissions` | 单次（上限为 1）或持续（不限次数或明确上限，仍受期限和预算约束） |
| `use_pool_id` | 消费来源；后代授权共享它，不得复制出独立的次数 |
| `delegation` | 能否再委派、合法的接收主体、剩余深度 |
| `extension_ceiling_ref` | 扩展安装时声明的范围和版本，只构成上限 |
| `confirmation_policy` | 是否需要逐个动作再确认；不得绕过许可范围 |
| `status`、`revocation_completion`、`state_version` | 状态和并发控制版本，见 2.5 |

一个**许可子句**包含：

| 维度 | 表达方式 |
| --- | --- |
| 资源 | 类型、稳定标识或受控的选择器；所属用户和目标系统明确 |
| 动作 | 语义版本内的显式枚举；新增的动作默认不包含 |
| 用途 | 读取、保存、同步、行动的显式集合 |
| 参数范围 | 精确值、有限集合、有界区间；金额带币种，接收方使用稳定标识 |
| 运行范围 | 任务、端点、执行宿主、接收方、处理位置 |
| 内容限制 | 来源内容的引用和版本、允许的派生用途、允许的输出目标 |

一份授权是**若干完整子句的并集**，子句内部的各项限制取交集。不得先把所有资源合在一起、所有动作合在一起，再形成笛卡尔积。例如父授权允许"读取 A"和"写入 B"，子授权不能由此得到"写入 A"。缺省值不解释为无限权限；需要"全部"时，必须明确授予一个有定义的范围。

### 2.2 委派只收缩：可判定的条件

把一份授权允许的所有（用户、资源、动作、用途、参数、任务、端点、接收方、时间）组合记为 D(g)。委派要求：

```text
D(子授权) ⊆ D(父授权) ∩ D(扩展安装上限)
```

主体的变化由委派关系单独核验，不当作普通的集合包含问题。

一般的策略包含关系难以判定，所以本设计采用一组**可判定的充分条件**：

1. 子授权的每个子句都对应父授权的某一个子句；
2. 枚举、资源集合、接收方集合只能取子集，区间只能变窄；
3. 时间窗不得延长，委派深度不得增加；
4. 祖先的限制不得删除；不支持判定的包含关系一律拒绝；
5. 消费来源沿委派链共享，不得复制次数。

一次派生需要多项许可时，分别保留各自的来源，不得把几个来源拼起来得到一份新的权利。M1 和 M2 不提供"组合多个来源"的派生。

实际使用时：

```text
允许(请求) = 叶子授权匹配
           ∧ 全部祖先当前有效
           ∧ 符合扩展安装上限
           ∧ 符合内容限制
           ∧ 符合用户设置的限制
```

"当前有效"来自权威状态，不得由模型或凭据持有者自己声明。

RFC 9396 明确说明，不存在一种通用机制来比较任意两个授权对象谁"更大"，比较语义只能由资源类型定义（[RFC 9396 §6.1](https://www.rfc-editor.org/rfc/rfc9396.html#section-6.1)）。所以本设计为每类资源定义包含规则，JSON 对象之间的包含关系不得当作收缩的证明。

### 2.3 授权使用记录

| 字段 | 含义 |
| --- | --- |
| `use_id`、`use_key` | 一次授权使用；动作使用的唯一键是"用户、消费来源、动作标识"，只读检索绑定检索请求标识 |
| `grant_chain_ref` | 实际使用的叶子授权、各级祖先和语义版本 |
| `operation_id` 或 `retrieval_id` | 对应的动作或只读检索，两种类型分开 |
| `request_digest` | 核心生成的规范化对象摘要 |
| `admission_ref`、`confirmation_ref` | 准入决定；已消费的确认（确认的状态仍由会话持有） |
| `auth_revision` | 做出这次使用决定时的权威修订 |
| `state` | 已占用、已封闭；**不表示动作已生效** |

**一次性授权在准入成功的事务中被占用。**同一动作的重新查询、交接或安全重发都不会再次占用；两个不同动作争同一来源，只有一个能成功。超时、取消、未生效或未知都**不会自动退还次数**。

为什么选在准入时消费：

| 候选时机 | 问题 |
| --- | --- |
| 每次核验凭据时消费 | 重复核验或重试会误消耗；无法与准入原子结合 |
| 外部效果成功后消费 | 两个并发请求可以在第一次成功之前同时执行；效果未知时无从决定 |
| **准入成功时绑定到唯一的动作** | 与确认和其他准入事实一起提交；重复请求返回原动作 |

"单次"指一次逻辑上的动作准入，不是一次网络尝试，也不承诺只产生一次外部效果；重试仍由动作账本按 G1 决定。次数耗尽只禁止新的准入，已经绑定的动作仍要检查撤销、期限和当前控制状态。

### 2.4 凭据

| 字段 | 出口凭据 | 只读检索凭据 |
| --- | --- | --- |
| 类型、签发方、密钥代次 | 出口类型 | 检索类型 |
| 主体绑定、受众 | 指定主体、执行宿主、出口类型 | 指定推理主体、记忆策略实例 |
| 用户、任务 | 必须精确匹配 | 必须精确匹配 |
| 来源 | 实际使用的授权链 | 允许读取的来源 |
| 使用引用 | 已准入动作的使用记录 | 检索许可；每次实际使用另留记录 |
| 请求绑定 | 条件集版本、动作、参数摘要、目标、内容版本 | 读取的资源、用途、任务、结果范围 |
| 有效期 | 不晚于任何来源的限制 | 同左 |

凭据不携带第三方的长期密钥。第三方密钥由可信的出口持有，从不下发给推理或扩展；秘密材料不进入推理上下文、普通运行记录或命令日志。MCP 2025-11-25 授权规范要求校验受众，并禁止把为其他资源签发的令牌透传出去（[MCP 授权](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)），这里采用同样的原则，防止"被利用的代理人"问题。

**凭据承载方式的比较：**

| 方式 | 当前有效性与消费 | 结论 |
| --- | --- | --- |
| **不透明引用加主体绑定** | 每次查核心记录，撤销和消费容易落实 | M1 采用 |
| 标准签名凭据（JWT、COSE 等） | 可以本地验证完整性，但当前有效性和单次消费仍需查状态 | 需要跨进程独立传递时再用 |
| 可派生的能力凭据（Macaroons、Biscuit、UCAN） | 可以携带委派证明，但撤销和消费仍需外部状态 | 将来接入外部 Agent、跨保护域时再验证 |

能力凭据各有前提和陷阱：Macaroons 的限制是"与"的关系，适合收缩，但默认是持有者凭据，论文也指出服务新增动作时，没有限定动作的旧凭据可能意外覆盖新动作（[NDSS 2014](https://www.ndss-symposium.org/wp-content/uploads/2017/09/04_3_1.pdf)）。Biscuit 显式信任第三方块时可以**扩展**令牌，只有受限的配置才符合 G7（[Biscuit v3.3 规范](https://github.com/eclipse-biscuit/biscuit/blob/c5697d4e41660d5ed461adf0caaaa132c9f29437/SPECIFICATIONS.md)）。UCAN 0.10 中多个 caveat 是"或"的关系，规范还允许应用定义权限放大（[UCAN v0.10.0](https://github.com/ucan-wg/spec/blob/bd908c6bab74ad6d5bf18d1a66d88ac1136fe516/README.md)），不能直接套用 Macaroons 的语义。另外，密码学验证通过不等于授权通过：go-macaroon 的 `VerifySignature` 只验证签名，返回的 caveat 需要应用再检查（[go-macaroon v2.1.0](https://github.com/go-macaroon/macaroon/blob/1679699b0b723e05f9f16c45b4c6cbd46adb2c78/macaroon.go#L240)），而且它的重复检查只在一次验证内有效，保证不了同一凭据跨两个请求只用一次。

### 2.5 状态

状态沿用[核心契约](../contracts/README.md#25-状态模型)的定义：

```text
授权：ACTIVE → REVOKED（撤销完成状态 PENDING → COMPLETE）
      ACTIVE → CONSUMED（一次性授权已被占用）
      ACTIVE / REVOKED → EXPIRED（未解决的出口责任仍然保留）
      终态不再回到 ACTIVE

授权使用：未建立 → 已占用 → 已封闭（效果由动作账本另行记录）

凭据：待交付 → 已签发 → 已撤销 / 已过期
```

界面把 `REVOKED + PENDING` 显示为"撤销处理中"，`REVOKED + COMPLETE` 显示为"已撤销"。

是否过期在每次核验时判断，不依赖定时清理。时钟不可信时，拒绝需要证明时间有效性的新使用。祖先被撤销后，后代的新使用通过链检查**立即**受限；异步遍历后代只是清理工作。另一份独立的根授权不受某条链撤销的影响，界面必须说明撤销的范围。

## 3 接口

### 3.1 共同约定

- 写命令带用户、经过验证的主体、命令标识、规范化请求摘要和必要的预期版本；同标识同摘要返回原结果，同标识异摘要报冲突；
- **诊断查询和真正的授权使用分开。**诊断查询返回"允许"不产生可执行的许可；
- 调用方提供的 `confirmed=true`、用途、关系、时间或身份字段，都不得代替可信事实；
- 所有成功回执都先持久化（G3）。

| 接口 | 输入 | 成功含义 | 主要错误 |
| --- | --- | --- | --- |
| 签发授权 | 授权表达、用户事件或确认引用 | 许可已持久成立 | 身份不符、确认不匹配、范围不支持 |
| 派生授权 | 来源、接收主体、子范围、安装上限、预期版本 | 子授权和收缩证明已持久建立 | 来源无效、无法证明收缩、禁止委派、深度超限、成环 |
| 核验并占用 | 动作描述、条件集版本、来源、确认引用；**由准入事务调用** | 使用记录随整个准入事务一起成立 | 范围不符、已撤销或过期、次数耗尽、确认已消费、版本冲突 |
| 签发凭据 | 已持久的准入或检索许可、主体和受众、有效期 | 凭据和交付材料，签发事实已保存 | 缺少准入、来源失效、受众错误、密钥不可用 |
| 核验出口使用 | 凭据、实际请求、尝试标识、执行端点身份 | 本次实际出口获准，并建立有界的使用临界区；**不证明效果** | 凭据错误、参数不符、当前状态无法证明、控制已封闭、执行端点不符 |
| 核验只读使用 | 检索凭据、读取请求、内容引用和当前限制 | 本次读取或结果交付获准 | 包含写入或外发用途、来源已撤回、内容不可用 |
| 撤销授权 | 授权及其子树、用户事件 | 撤销已被持久接纳；返回当前阶段和未解决的出口 | 无控制身份、范围不符、版本冲突 |
| 查询记录与撤销进度 | 用户、记录标识 | 原决定、来源、消费和封闭进度 | 无权限、无此记录 |
| 确认封闭 | 原交接标识、出口身份、证明 | 封闭事实已持久接纳 | 游标缺口、实例陈旧、用户错误、证明不完整 |

"核验并占用"必须和条件版本检查、预算预留、确认消费在**同一事务**提交，不得先远程拿到"允许"，再另外写准入。"核验出口使用"只供受信的出口闸门调用，它的结果不得被普通调用方保存起来、稍后拿去任意执行。

### 3.2 错误语义

| 类别 | 行为 |
| --- | --- |
| 明确拒绝 | 返回稳定的原因：已撤销、已过期、用途不符、范围不符、次数耗尽等 |
| 条件缺失或无法证明 | 停止依赖它的使用，说明缺少什么 |
| 权威不可达或状态陈旧 | 返回 `AUTHORITY_UNREACHABLE`；关闭新的使用，保留责任，等待恢复 |
| 并发冲突 | 重新读取后按原命令重试事务，不重建外部动作 |
| 回执结果未知 | 查询原命令或原交接，不当作失败 |
| 未知的语义版本或资源类型 | 拒绝；不忽略字段后继续允许 |

## 4 关键流程

### 4.1 确认与授权成立

1. 核心生成完整的授权表达或动作描述，交互适配器展示其可读视图；会话保存确认请求和**核心生成的规范化对象摘要**；
2. 用户确认，可信的交互入口记录身份和确认对象，会话保存确认事件；
3. 签发根授权，或在动作准入中消费确认，与许可或准入、回执在裁决域中原子提交。

确认绑定的是核心生成的规范化对象摘要，而不是"以后允许这个工具"或一段自然语言摘要：参数、条件、用途或主体有任何改变，旧确认就失效。持钥证明和确认摘要职责不同，前者确认是谁在调用，后者绑定用户批准的具体内容。

确认分两种：**授权确认**批准一个持续范围或一个精确的单次范围，在授权成立时消费；**动作确认**按授权的规定批准某个具体动作，在准入时消费。同一个确认不得被两处分别消费。

### 4.2 动作准入、签发与出口

| 步骤 | 处理 | 持久化 |
| --- | --- | --- |
| 1 | 任务编排取得提议，构造绑定条件版本的实际动作描述 | 任务编排保存准入命令 |
| 2 | 检查当前条件、授权链、确认和预算，占用消费来源 | **裁决域单个原子事务**：准入、使用记录、确认消费、预算预留、待办工作 |
| 3 | 授权保存出口凭据记录，然后交付 | 签发事实；交付材料可恢复 |
| 4 | 意图交给指定的动作账本 | 按 R7 |
| 5 | 账本建立尝试；闸门核验实际资源、参数、当前授权和控制状态 | 账本保存尝试；授权保存本次出口使用 |
| 6 | 在受信的临界区内记录"可能发送"，然后打开真实出口 | 闸门持有隔离约束，直到发送开始或确定取消 |
| 7 | 保存回报和费用 | 效果由账本写，用量由预算写；授权不推断结果 |

模型调用、摘要生成、嵌入、文件操作和各种辅助请求适用同一规则（G5、R2）。一个工具内部有多个独立的外部行动时，每个都需要自己的准入依据，不得凭顶层工具的凭据获得任意的嵌套权限。

### 4.3 委派

1. 任务编排或扩展接入方提出接收主体和所需范围；
2. 授权验证主体、来源链、安装版本、能否委派和范围包含；
3. 在裁决域事务中保存子授权、收缩证明和共享的消费来源；
4. 子任务或外部 Agent 的派发按 R7 交接；
5. 后代每次使用仍检查祖先的当前状态。

### 4.4 只读检索与用途

只读检索凭据只开放 R4 这一个例外：推理可以直接查询指定的记忆策略。

| 阶段 | 必须检查 |
| --- | --- |
| 请求进入 | 主体、用户、任务、受众、范围、期限和当前授权 |
| 读取内容 | 内容治理中的当前版本、来源和读取限制 |
| 缓存命中 | 同样检查当前权限；缓存不是新的授权来源 |
| 交付结果 | 再查来源是否已撤回、用途是否仍允许；撤回期间产生的结果不得继续输出 |
| 之后的保存、同步、行动 | 按对应用途和目的地重新检查；检索凭据不适用 |
| 检索中需要网络、模型或嵌入调用 | 另走动作准入和出口，不得从 R4 派生行动权限 |

用途按**实际行为**判定，不按工具名或 HTTP 方法推断。GET 请求也可能把私有查询内容上传出去；调用模型同时涉及数据处理和数据外发。

| 实际行为 | 至少需要的许可 |
| --- | --- |
| 在允许的位置读取内容 | 读取 |
| 持久化原文、摘要、索引、嵌入或跨任务的记忆 | 保存 |
| 数据离开当前允许的位置或持有方，包括交给云端模型、外部嵌入服务等远端做临时处理 | 同步（外发），并限定接收方和处理位置 |
| 发消息、写文件、调用模型、改变设备状态 | 行动；涉及内容时，另外检查该内容的读取、保存或同步用途 |
| 为诊断或评测读取运行记录 | 读取，并受场景和来源限制；运行记录不是默认开放的系统数据 |

一个动作可能同时需要多种用途，缺一项就拒绝。"行动已获授权"不意味着输入内容可以随意外发。对标记为严格删除的内容，同步许可只能指向能验证删除的接收方（G9）。可替换部分不得自称输出"不含敏感来源"；它产生的派生内容由内容治理保守地继承输入的限制。

**资源范围核验针对实际被访问的对象。**文件核验针对真正打开的那个对象，网络核验覆盖实际目标、重定向和代理接收方，不得只核验提议里写的名字。MCP filesystem 服务器曾先后披露符号链接越界和目录前缀碰撞漏洞（[符号链接](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-q66q-fx2p-7w4m)、[前缀碰撞](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-hc55-p739-j48w)），说明字符串前缀不是文件系统包含关系的证明。

### 4.5 撤销、与出口的竞争、离线

撤销的"被接纳"和"完全生效"分开：

| 阶段 | 行为与含义 |
| --- | --- |
| 接纳（`REVOKED`，`PENDING`） | 持久进入撤销处理中，立即拒绝新的准入、派生、签发和出口临界区，保存封闭工作 |
| 封闭 | 按 R7 请求相关出口关闭尚未开始的执行，处理已进入临界区的请求 |
| 完成（`COMPLETE`） | 所有未开始的出口都已封闭，或有可信证据表明它们不可能再开始 |
| 后续核对 | 已开始的动作可能迟到生效，由原账本继续负责；撤销不删除这些责任 |

一次权威检查返回"允许"之后、真正发送之前，存在一个竞争窗口。所以：受信的闸门把实际发送的开始放进一个有状态、受隔离约束的临界区；只要还有未解决的临界区可能继续发送，撤销就不得宣布完成；失联时显示"撤销请求已保存，出口封闭待确认"，不根据超时猜测已停止。

**核对也需要许可。**核对未知效果本身是一次读取。如果原来的行动授权已被撤销、又没有独立的核对许可，就停止新的查询，保留未知，并请用户单独授予一个精确的核对许可；不得悄悄保留原来的行动权。

**缓存什么。**可以缓存不变的权限表达、密码学验证结果和明确的拒绝结果；**不缓存可以跨次复用的"当前允许"**。失效通知只用于加快封闭和清理，不是正确性的依据。RFC 7662 明确指出，允许缓存令牌内省结果会在撤销之后留下一个残留使用窗口（[RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)）。

**离线：**

| 情况 | 行为 |
| --- | --- |
| 当前授权或控制状态由远端持有，现在无法核验 | 暂停新的出口和内容使用 |
| 完整的裁决域和必要事实从创建时起就归本地持有 | 本地核验后可以继续；仍检查期限、确认、预算和控制 |
| 手里只有以前的准入记录和签名凭据 | 不足以证明远端的当前授权 |
| 重新连上 | 先核对撤销修订、任务控制、原动作结果和交接，再推进；不接管远端的任务 |

只把云端授权复制到端侧，并不会让端侧获得独立的裁决权。故障时也不转移任务或授权的归属（G11、A3）。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 持久工作、授权；动作准入由任务编排负责 | 查询原命令、原签发或原交接，返回原决定；不会再次消费确认或次数 |
| 进程崩溃 | 各事实写入方 | 未提交的事务整体无效；已提交的恢复交付。出口临界区未解决时，先隔离旧实例，效果交账本核对 |
| 重复请求 | 持久工作、授权 | 唯一幂等键加摘要校验；同请求复用记录，摘要不同则拒绝 |
| 并发冲突 | 裁决域 | 授权修订和消费来源上的锁或比较交换，形成与撤销一致的顺序；冲突时重读重试事务，不重发外部动作 |
| 依赖不可用 | 授权、出口闸门、内容治理 | 权威、时钟、内容限制或密钥无法证明时停止新使用；已承接的责任保留，重试原工作 |
| 迟到的结果 | 授权处理交接；账本处理效果 | 旧的封闭回执按原标识归并，旧实例不得覆盖新状态；迟到的效果不会重新激活授权 |
| 失效通知丢失或乱序 | 授权、持久工作、闸门 | 用持久游标检测缺口，补发或取快照；是否允许仍查权威，不依赖通知是否送达 |
| 一次性动作的结果未知 | 动作账本、授权 | 次数保持占用；授权不会把次数"退还"，也不批准重发 |
| 撤销后没有核对许可 | 任务编排、授权、动作账本 | 停止新的查询；保留未知和负责方；用户可以另外授予精确的核对许可 |
| 从旧备份恢复 | 授权、持久工作、闸门 | 撤销记录不得丢失；用恢复隔离版本封闭旧凭据和旧工作者，核对完成前停止新使用 |
| 可替换部分丢失状态 | 任务编排、内容治理 | 从持久记录重建输入；不补发更大范围的凭据，不信任它"已确认""已完成"之类的声明 |

"隔离旧实例"由可信的宿主和闸门落实，不依赖插件自觉遵守一个失效标志。

## 6 不变量落实

| 不变量 | 本模块怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 不因超时退还一次性次数或批准重试；保留原使用记录 | 出口回报丢失后次数不恢复，未经账本判断不得重发 |
| G2 | 授权通过、撤销完成都不证明任务效果；未解决的出口责任对任务编排可见 | 撤销已完成但旧动作仍可能迟到生效时，任务不会被错误关闭 |
| G3 | 许可、消费、签发、撤销和回执都先持久再确认 | 在每个提交和返回点崩溃，恢复后决定仍可查询 |
| G4 | 使用绑定条件版本、授权来源和准入；出口核验实际参数和当前状态 | 改了收件人、金额、内容版本或执行端点后，旧凭据被拒绝 |
| G5 | 行动凭据只签发给指定出口；检索凭据无法通过出口 | 覆盖模型、辅助调用、重定向、文件、GUI、自动渲染等出口 |
| G6 | 推理无法制造许可、确认或可信关系；查询结果不产生执行权 | 恶意内容自称"用户已同意"，不得改变任何授权事实 |
| G7 | 子句包含证明、全部祖先限制、安装上限、共享的消费来源 | 多层委派、兄弟竞争、新版本和新动作都无法扩大来源 |
| G8 | 每次使用检查当前许可和用途；保存、同步、行动分别授权；失联时等待；撤销分阶段 | 缓存、派生摘要、云端模型输入、迟到的检索结果逐项验证 |
| G9 | 撤回后关闭相关使用，配合内容治理沿派生关系停止访问；严格删除的内容不外发给无法验证删除的接收方 | 原文、索引、摘要和缓存在清理期间都不得继续使用 |
| G11 | 使用和凭据绑定原动作、原执行端点；断网和重启不改派 | 接替的工作者只能继续原责任；旧实例和其他执行端点被隔离 |
| G12 | 所有标识、缓存、凭据、查询和交接都带用户维度 | 相同的局部标识跨用户无法读写、消费或复用凭据 |

## 7 取舍

### 7.1 用什么模型表达授权

| 候选 | 问题 | 结论 |
| --- | --- | --- |
| RBAC | 角色变更可能扩大既有任务或扩展的权限；角色模型本身不定义任务有效期、用途、单次消费和委派守恒 | 只用于用户能理解的授权模板 |
| 通用 ABAC | 表达力强，但属性的可信度和任意策略的收缩难以证明 | 不用通用脚本作为权限事实 |
| ReBAC（Zanzibar、OpenFGA、SpiceDB） | 擅长共享和继承，但关系变化不天然满足"委派只收缩"；增加图查询、一致性和迁移的负担 | 出现复杂共享需求后，作为核心内部实现引入 |
| **显式授权记录 + 受限的属性约束** | 能直接绑定责任、消费和撤销 | 默认方案 |

将来如果引入关系引擎，它只能是经过审查的核心内部实现或受限的投影，它的"允许"结果不得绕过准入事务，也不得作为可替换的裁决插件。还要注意它的一致性语义：Zanzibar 论文专门讨论了撤销后的"新敌人"问题，即用旧的访问控制列表保护新内容会造成泄漏（[Zanzibar §2.2、§2.4](https://storage.googleapis.com/gweb-research2023-media/pubtools/5068.pdf)）；SpiceDB 区分"有权限""无权限"和"缺少上下文的条件权限"，条件权限不得当作允许（[SpiceDB v1.40.1](https://github.com/authzed/spicedb/blob/5e7c22386cab6cdb1f26b20af984451f66072b67/internal/services/v1/permissions.go#L56)）。

### 7.2 Agent 场景下的教训

| 案例 | 对本设计的影响 |
| --- | --- |
| AgentDojo 在工具返回内容里注入攻击指令，评估 Agent 的安全违规（[论文](https://arxiv.org/html/2406.13352v3)） | 工具结果只能作为内容进入推理，不得签发授权、消费确认或改变核心事实（G6） |
| Invariant 演示：公开 issue 诱导 Agent 读取私有仓库，再通过公开 PR 泄露。前提是 Agent 本来就有两个仓库的访问权（[披露](https://invariantlabs.ai/blog/mcp-github-vulnerability)） | 这是授权组合问题，不是绕过权限。任务权限要限定仓库、动作、接收方和内容用途，"读私有数据"和"发布公开内容"必须分别检查 |
| EchoLeak（CVE-2025-32711）：Copilot 的 AI 命令注入导致信息泄露，验证链经过内容检索、URL 和自动加载图片（[发现者说明](https://www.catonetworks.com/blog/breaking-down-echoleak/)） | G5 必须覆盖交互适配器里的图片、预览、自动加载、重定向和代理，只管显式工具调用不够 |
| CaMeL 从可信请求形成控制流，对不可信数据的依赖施加能力策略（[论文](https://arxiv.org/html/2503.18813v2)） | 授权裁决独立于模型能否识别提示注入。本设计不承诺消除所有提示注入或侧信道 |

### 7.3 其他取舍

| 决定 | 得到 | 付出 |
| --- | --- | --- |
| 授权事实留在不可替换的核心 | 不变量不依赖可替换策略或模型判断 | 新规则需要核心代码审查 |
| 有限范围的表达 | 收缩可判定，容易审计和测试 | 不支持任意业务脚本，表达不了就拒绝 |
| 单次在准入时消费，未知不退还 | 避免并发放大和故障后重复行动 | 被封闭但从未执行的单次授权可能需要重新确认 |
| 每次检查权威 | 严格的当前授权语义 | 多一次交互的延迟；远端失联时可用性下降 |
| 撤销有"处理中"阶段 | 如实处理执行竞争和失联 | 用户可能需要等待，界面和恢复更复杂 |
| 默认不透明凭据 | M1 容易与事务和撤销结合 | 不能仅凭凭据离线证明当前权限 |
| 版本固定，新动作默认拒绝 | 插件升级和自进化不得悄悄扩权 | 升级可能需要新授权或兼容声明 |

授权的权威归属、消费语义、撤销生效的时刻和离线权限模型，正式采纳前必须各写一篇 ADR。

## 8 待定事项

| 编号 | 假设 | 验证方式 | 验证前的行为 |
| --- | --- | --- | --- |
| H1 | 同用户事务和每次权威核验的延迟可以接受 | 按 S2、S3、S4 测量准入、检索和撤销的延迟及冲突 | 不启用"允许缓存"来降低保证 |
| H2 | 有限范围的表达能覆盖首批 API、文件和模型出口 | 逐类资源验证规范化、包含关系和实际对象的一致性 | 不支持的范围一律拒绝 |
| H3 | 宿主隔离、时钟和临界区封闭能证明旧实例无法继续发送 | 注入崩溃、暂停、时钟回退、分区和恢复 | 未证明前保持"撤销处理中" |
| H4 | 保守继承输入用途足以覆盖首批内容派生 | 私有数据经摘要、编码、拼接、索引和模型输出的测试 | 来源不明的内容不得保存或外发 |
| H5 | 用户能理解持续范围和精确确认的视图 | 接收方、内容来源、期限和委派范围的交互测试 | 使用较窄的范围和逐动作确认 |
| H6 | Biscuit、UCAN 的受限配置能与核心语义一致 | 固定版本的互操作、撤销、资源耗尽和恶意证明链测试 | 不用于默认授权裁决 |

## 9 M1 范围

| 项目 | M1 实现 | 推迟 |
| --- | --- | --- |
| 授权对象 | 单次、持续；明确的主体、资源、动作、范围、期限、用户和语义版本 | 复杂关系、广泛的资源层级 |
| 准入 | 与任务、会话、预算检查在同一事务；单次授权原子绑定动作 | 完整的用途组合和委派规则 |
| 用户确认 | 绑定核心生成的描述，只消费一次；参数改变后旧确认失效 | 高级的交互和确认策略 |
| 出口凭据 | 不透明引用，绑定准入、主体、出口、请求摘要和期限 | 独立签名格式、能力证明链 |
| 出口核验 | 覆盖 API、文件、模型和辅助调用；在实际出口再次检查 | GUI、外部 Agent、插件沙箱 |
| 撤销 | 同一裁决域内立即关闭新准入；同进程内的出口竞争；可查询进度 | 分布式封闭和重连后的传播：M3 |
| 用途 | 字段从第一天保留，未知值拒绝；只支持明确的 M1 流程 | 完整的读取、保存、同步、行动控制：M2 |
| 只读检索凭据 | 没有记忆策略，不开放 R4 直连检索 | M2 |
| 委派 | 不开放，返回"不支持" | 授权关系和收缩：M2；真实子任务和外部 Agent：M4 |

**推迟用途细分，不得实现成"读取自动包含保存、同步和行动"。**M1 只用于受控测试，测试数据的使用处于明确批准的有限范围；没实现的能力直接拒绝，不宣称已满足完整的 C7 和 G7–G9。

## 10 测试要点

测试的依据是持久记录和真实的出口观察，不得只断言返回值。

| 用例 | 必须成立 | 对应 |
| --- | --- | --- |
| 两个动作并发消费同一个一次性授权 | 只有一个准入；失败的事务不消费确认或其他事实 | G3、G4 |
| 两个子授权共享同一个单次来源 | 兄弟和全部后代加起来只能准入一次 | G7 |
| 多层随机委派 | 子权限始终被来源覆盖；过深、成环、未知范围都被拒绝 | G7 |
| 资源与动作的组合 | "可读 A、可写 B"推不出"可写 A" | G7 |
| 条件、参数或内容版本变化 | 旧提议、旧确认、旧凭据都无法批准新行为 | C1、G4 |
| 插件升级、新增动作、回滚 | 旧授权不会自动获得新动作；已撤销的版本不会复活 | C6、C9、G7 |
| 用检索凭据调用写入或模型出口 | 拒绝；不得从 R4 派生行动 | G5、G6、R4 |
| 缓存命中后撤回 | 缓存的结果不得继续读取、输出或派生 | G8、G9 |
| 私有来源流向公开目标 | 即使"读"和"写"分别被允许，缺少对应的数据用途仍然拒绝 | G8 |
| 实际资源发生变化 | 符号链接替换、目录前缀碰撞、重定向或代理都无法越界 | G4、G5 |
| 凭据的主体、任务、受众或执行端点不符 | 全部拒绝；诊断查询也不泄露其他用户的事实 | G11、G12 |
| 提示注入伪造确认或关系 | 不产生授权，不改变消费和身份 | G6、R3 |
| 回执丢失（授权、准入、签发、撤销提交后丢响应） | 原命令可查；重发不复制权限或消费 | G3 |
| 撤销与准入、派生、检索交付并发 | 得到一致的顺序；撤销被接纳后不会出现新的有效使用 | G8 |
| 撤销通知丢失、重复、乱序 | 游标缺口可检测；拒绝不依赖通知送达 | G8 |
| 远端分区期间云端撤销 | 端侧无法证明当前状态时不发送；不把短有效期当成正确性 | G8 |
| 工作者暂停后恢复 | 已被隔离的实例无法用旧凭据继续出口 | G11 |
| 从旧备份恢复 | 撤销不会复活；旧恢复版本的凭据不得再用 | G3、G8 |
| 不可信输出自动加载资源 | 图片、预览、代理和重定向都由闸门控制 | G5 |
| 未知动作遇到授权过期或撤销 | 次数不恢复；没有核对许可时继续保持未知 | G1、G8 |
