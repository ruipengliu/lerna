# 动作账本

| 日期 | 修订说明 |
| --- | --- |
| 2026-10-04 | 初版：动作接纳、执行尝试与外部键、效果与迟到可能性、能力驱动的恢复策略、核对调度、取消竞争、端侧补传。 |

- 状态：草稿
- 负责满足：C4、C5；直接负责 G1、G2（动作收尾部分）、G3、G11；协同落实 G4、G5、G8–G10、G12
- 涉及场景：S2、S3、S4、S5、S7
- 上游：[项目目标](../../project-goals.md)、[分层与模块](../../layers.md)、[核心契约](../contracts/README.md)、[持久工作](../durable/README.md)

动作账本是 Lerna 最核心的一块。它记录每个会影响外部世界的动作：是否已被接纳、发出了几次、实际效果是什么、还会不会迟到生效、核对进行到哪一步、凭什么说它已经收尾。

本设计的要点：

- 账本只有**一个负责方**，接纳之后执行端不再改变；
- 每个动作有**稳定的执行尝试标识**，结果未知后的重发沿用原标识和原外部键，每次物理发送另记序号；
- **效果**和**迟到可能性**分开记录；
- **能不能重试由证据和目标系统声明的能力决定**，不由超时、租约或用户取消决定；
- 端侧账本是本机动作的唯一写入方，云端只接收它补传的事实，不重新执行。

Lerna 能保证的是"责任和记录在故障后可恢复"。效果能否自动收尾，取决于第三方系统是否提供幂等、查询和终局证明。这一点在设计上必须诚实：远程过程调用在通信异常时，调用方原则上无法区分"调用过"和"没调用过"（Birrell 和 Nelson 早在 1984 年就指出了这一点，[论文 §3.1](https://www.cs.cmu.edu/~15712/papers/birrell84.pdf)）。只在 Lerna 一侧持久化意图，不可能给任意第三方调用增加"恰好一次"的保证。

## 1 职责与边界

动作账本是以下事实的唯一写入方：动作意图已被接纳、执行尝试、出口记录、效果裁决、迟到可能性、核对进度、收尾依据。

| 相邻模块 | 分界 |
| --- | --- |
| 任务编排 | 持有准入决定、条件版本、任务控制和 Result。账本接纳已准入的意图，回报事实和阻塞原因；不修改任务状态，不裁决任务成功 |
| 持久工作 | 持有命令回执、待办工作、领取和租约。账本决定业务上怎样恢复；租约过期不改变效果，也不改变执行端 |
| 授权 | 裁决权限，签发出口凭据。账本引用授权，不能自行扩权；执行、核对读取、保存证据、同步分别检查许可 |
| 预算 | 持有额度和实际用量。账本关联并转交计费证据，不自行结算，也不按动作标识合并不同的实际费用 |
| 出口闸门 | 在实际出口核验凭据，并要求账本先持久记录这次出口。闸门不保存第二份效果事实 |
| 执行适配器 | 声明能力、连接目标、回报证据。效果由账本按契约裁决；适配器不得自行重试有外部效果的调用 |
| 内容治理 | 持有参数和证据的内容、来源、用途和删除关系。账本只保存引用和必要的元数据 |
| 运行记录 | 关联任务、动作、尝试、出口、授权和费用，不能替代效果事实 |

## 2 对象与状态

### 2.1 关键字段

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 动作意图 | `operation_id`、`task_id`、`admission_ref`、`requirements_version` | 动作标识在准入时生成；不从参数哈希推导 |
| 交接关联 | `handoff_id`、`command_id`、`intent_digest` | 同一交接只能对应同一意图；同标识不同内容明确拒绝 |
| 负责方 | `ledger_domain_id`、`executor_endpoint_id` | 接纳后固定；工作者替换不能改派 |
| 参数与目标 | `parameters_ref`、`request_digest`、`target_scope` | 固定账户、目标、区域、资源身份和前置条件；参数正文归内容治理 |
| 授权与预算依据 | `grant_refs[]`、`budget_basis`、`credential_ref` | 记录准入依据，不能代替出口处的当前检查 |
| 能力依据 | `adapter_version`、`provider_api_version`、`capability_snapshot` | 保存当时的能力声明；恢复时与当前声明取两者都能保证的部分 |
| 动作状态 | `lifecycle`、`dispatch`、`effect`、`late_effect`、`reconcile_state`、`ledger_revision` | 派发封闭不可逆；每次改变递增修订 |
| 执行尝试 | `attempt_id`、`attempt_no`、`phase` | 结果未知后的重发复用原尝试；禁止用新尝试规避未知 |
| 外部键绑定 | `external_key`、`key_scope`、`key_valid_until?`、`first_possible_send_at` | 在第一次出口前持久保存；无法证明的窗口不允许自动重发 |
| 出口记录 | `attempt_id`、`send_seq`、`purpose`、`claim_epoch`、`provider_request_id?` | 每次物理发送一条记录 |
| 效果证据 | `observation_id`、`source`、`evidence_ref`、`resource_version`、`observed_at`、`terminality_proof?` | 时间戳不能作为跨来源的排序依据；终局证明必须覆盖原尝试 |
| 核对记录 | `policy_version`、`next_check_at`、`check_count`、`limits`、`pause_reason?` | 调度和暂停原因持久保存；暂停不改变效果 |
| 补传记录 | `writer_stream_id`、`stream_epoch`、`event_seq`、`event_digest`、`acknowledged_prefix` | 流身份不复用；只推进已被持久接纳的连续前缀 |
| 费用关联 | `billing_source_ref`、`budget_delivery_ref` | 计费来源由预算去重，不能用尝试标识代替 |

**外部键的传递。**账本保存的外部键必须显式传给目标系统，例如 Stripe 的 `Idempotency-Key`、AWS 各 API 的 `ClientToken`。恢复时禁止依赖 SDK 自动生成键：stripe-python v12.0.0 在调用方未提供键时会为相关请求生成随机键，HTTP 客户端还会按配置在内部重试（[请求构建](https://github.com/stripe/stripe-python/blob/v12.0.0/stripe/_api_requestor.py#L500)、[重试](https://github.com/stripe/stripe-python/blob/v12.0.0/stripe/_http_client.py#L182)）。跨进程恢复时这两个行为都会制造新请求，所以必须显式注入已保存的键，并关闭有副作用调用的 SDK 自动重试。不支持幂等键的目标不虚构去重能力；尝试标识仍用于账本关联和目标支持的查询。外部键是不含敏感信息的稳定标识。

### 2.2 状态维度

状态维度沿用[核心契约](../contracts/README.md#25-状态模型)，本模块补充各维度的裁决条件。

| 维度 | 取值 | 裁决条件 |
| --- | --- | --- |
| 动作生命周期 | `ACCEPTED → ACTIVE → SETTLED` | 意图、接纳决定和待办工作在账本域持久提交后为 `ACCEPTED`；收尾依据成立后为 `SETTLED` |
| 尝试阶段 | `REGISTERED → DISPATCH_POSSIBLE → OBSERVED` | `DISPATCH_POSSIBLE` 表示可能发生了发送；崩溃恢复时不能据此断言已发送或未发送 |
| 效果 | `NOT_APPLIED`、`UNKNOWN`、`APPLIED` | 没有任何尝试可能发出时为 `NOT_APPLIED`；进入 `DISPATCH_POSSIBLE` 时转为 `UNKNOWN`；有充分证据才能转为 `APPLIED` 或 `NOT_APPLIED` |
| 迟到可能性 | `RULED_OUT`、`MAY_OCCUR` | 出口开放后默认 `MAY_OCCUR`；只有覆盖相关尝试的终局证据才能排除 |
| 派发控制 | `OPEN → SEALED` | 取消、收尾、授权约束都可以封闭；不能重新打开 |
| 核对进度 | 待核对、核对中、等待、暂停、结束 | 由调度和证据更新；次数或费用耗尽只让核对暂停 |

几个容易误解的点：

- **已生效**要求所声明的效果有充分证据。HTTP 200、异步接口的"已接受"回执、适配器的一句"完成"，都不自动满足这一点。
- **未知**包括只知道部分效果、回报丢失和证据冲突。
- **可能迟到生效**指仍有请求、执行流程或目标系统的恢复流程可能新增或改变外部效果。仅仅是响应消息迟到，不一定意味着效果会迟到。
- 一个动作产生多个效果、其中部分已知时，保存已知部分，整体保持未知。能拆开的行动应该在准入时就拆成独立的动作。
- 效果记录的是**历史事实**。之后资源被别人删除，不会把原动作改写为未生效；当前条件是否仍满足，由任务编排核验。

### 2.3 收尾依据

```text
动作可以 SETTLED ⇔
    派发已封闭
    且 迟到可能性为 RULED_OUT
    且 不存在未处理的证据冲突
```

这个定义防止一次成功回报掩盖其他仍在途中的发送。历史效果仍为未知、但确定不会再迟到生效的动作也可以收尾；这时任务能否成功，取决于必要条件有没有证据，Result 必须披露这个遗留的未知。已准入但尚未被账本接纳的意图，同样不能从完成门禁中消失。

## 3 接口

所有改变状态的命令都携带契约版本、用户、命令标识和指纹，通过持久工作的命令回执去重。查询当前状态使用独立的查询接口。

| 接口 | 输入 | 成功含义 | 主要错误；幂等 |
| --- | --- | --- | --- |
| 接纳意图 | 原交接标识、完整意图、准入依据、指定的账本和执行端 | 责任已持久接纳；**不表示已经执行** | 无有效准入、负责方不符、版本不支持、同标识异内容；按交接标识幂等 |
| 查询交接 | 用户、原交接标识 | 原接纳决定，或"尚无接纳记录" | "尚无记录"只允许补交原意图，不允许换端或新建动作 |
| 开放出口 | 动作、尝试、发送序号、领取依据、出口凭据、预期修订 | 本次出口已持久记录，可能发生 | 派发已封闭、领取过期、授权失效、预算不足、重发不安全、修订冲突；重复请求不授权再次物理发送 |
| 接纳回报 | 动作、尝试、发送序号、来源身份、证据和第三方标识 | 证据已接纳，返回效果修订和后续核对状态 | 来源不合法、关联错误、证据缺失、无保存许可；按观察标识幂等；**不因领取过期而丢弃合法的迟到证据** |
| 封闭派发 | 动作或原准入范围、控制修订、原因 | 封闭回执，以及尚未收尾的尝试清单 | 无控制权限、范围错误；幂等。封闭回执不能用来断言原动作未生效 |
| 申请核对 | 动作、原因、核对上限 | 已持久安排核对工作，或明确的暂停原因 | 当前读取授权不足、预算不足、目标不支持查询；同一修订上的重复唤醒合并 |
| 查询动作与收尾依据 | 用户、动作集合 | 效果、迟到可能性、证据引用、核对状态、收尾依据 | 缺失的动作明确列出，不能当作已收尾；只读 |
| 补传事实 | 负责方身份、流身份、序号、事实批次、同步许可 | 逐项接纳结果、连续确认前缀、缺口 | 来源不符、同身份不同内容、无同步许可；按事实身份去重 |
| 变化通知 | 动作修订、效果摘要、阻塞原因 | 通知已被任务编排持久接纳 | 回执丢失时查询原通知；重复通知不会重复推进任务 |

执行适配器一侧的约定（完整定义见[执行适配器接口](../../ports/executor/README.md)）：

| 适配器接口 | 输入 | 返回与边界 |
| --- | --- | --- |
| 执行 | 原尝试标识、固定参数和目标、外部键、出口凭据 | 效果主张和证据。返回只表示拿到了回报；超时回报为无法确定；适配器自身不重试 |
| 查询 | 原尝试标识、已保存的第三方关联、核对用凭据 | 三态效果主张、观察范围、目标状态、终局依据。"暂时没看到"必须保持未知 |
| 取消（可选） | 另行准入的取消动作、原动作关联、相应权限 | 取消请求本身的回报；原动作是否终止仍需账本裁决 |

向外部发出取消请求本身也是一个动作，同样经过准入和出口闸门（G4、G5）。退款、撤回已发送消息等补偿动作必须重新准入和授权，不会自动执行。

## 4 关键流程

### 4.1 正常执行

| 步骤 | 处理 | 持久化 |
| --- | --- | --- |
| 准入 | 任务编排原子检查条件版本、输入版本、授权、预算和确认，固定动作标识和执行端 | 裁决域：准入决定、意图、待交接记录 |
| 接纳 | 账本校验原交接并接纳责任；若控制范围已被封闭，接纳为"禁止执行" | 账本域：意图、接纳决定、命令回执、待办工作 |
| 准备尝试 | 固定尝试标识、外部键、参数、作用范围和能力依据 | 账本域：执行尝试和外部键绑定，必须早于第一次出口 |
| 开放出口 | 闸门检查当前凭据、派发控制和重发安全条件，账本记录"可能发送" | 账本域：出口记录，效果转为 `UNKNOWN`，迟到可能性转为 `MAY_OCCUR`；**提交之后才允许发生 I/O** |
| 调用目标 | 执行适配器经闸门调用目标；关闭有副作用调用的 SDK 自动重试 | 这一步无法和第三方效果原子提交，故障窗口必须保留 |
| 接纳证据 | 证据内容交内容治理登记，账本裁决效果，转交费用，安排核对 | 内容域按 R7 交接；账本域：证据引用、效果修订、核对工作、通知和费用的待交接记录 |
| 收尾或恢复 | 有终局证据就封闭并形成收尾依据；否则核对或安全重发 | 账本域：收尾依据，或恢复决定和原因 |
| 更新任务 | 任务编排持久接纳变化，核验全部已准入动作和必要条件 | 裁决域：进展、阻塞项；通过完成门禁后固定 Result |

"准备尝试"和"开放出口"可以合并为一个事务，但顺序不能省略：**外部键和出口风险先持久，然后才发送。**

### 4.2 结果未知后：由能力组合决定策略

适配器声明的能力分为五个维度（见[核心契约 2.4](../contracts/README.md#24-能力声明)）。动作账本根据这些声明的组合决定恢复策略：

| 能力组合 | 结果未知后的策略 |
| --- | --- |
| 无外部效果，且重复读取安全 | 当前授权、预算和派发控制允许时可以重发；不同时间读到的结果各自保留版本；费用仍单独记录 |
| 幂等且可查询 | 先查询；必要时在幂等保证范围内，用原尝试和原键重发 |
| 幂等但不可查询 | 只有作用范围、参数、并发条件和有效期都能证明时才重发；目标缓存的错误响应不构成终局证据 |
| 不幂等但可查询 | 查询确认已生效就收尾；只有确认未执行，**并且**排除原请求迟到生效，才允许新的尝试 |
| 不幂等且不可查询 | 禁止自动重发，保持未知，通知任务编排等待外部证据或人工核对 |
| 未声明、声明冲突、版本不兼容 | 按最保守的能力处理；不用新出现的乐观声明解释旧请求 |

用原键重发还必须同时满足：

1. 原请求确实使用了所声明的幂等机制；
2. 当前授权和预算允许，派发没有被封闭；
3. 参数、资源身份、作用范围和前置条件仍然有效；
4. 幂等有效期覆盖重发请求**到达目标并被去重判断**的时刻。

第 4 条不能仅凭"客户端在有效期内开始发送"来推定。目标没有过期拒绝机制、也给不出可证明的到达边界时，有限的保存期只能算有条件的能力；无法证明安全就不重发。

只有当旧尝试确定未生效、迟到可能性已排除、原准入仍然允许时，才能创建**新的尝试**。修改参数则必须形成新的提议并重新准入，不能覆盖原动作。

几个真实的反例说明了这些规则为什么必要：

- **"查不到"不等于"不存在"。**EC2 是最终一致的，刚创建成功的资源可能暂时返回 `InvalidInstanceID.NotFound`（[EC2 最终一致性](https://docs.aws.amazon.com/ec2/latest/devguide/eventual-consistency.html)）。
- **缓存的错误不是终局。**Stripe 要求把 500 视为结果不确定；故障修复后原请求可能继续推进，产生对象和 webhook，而之前缓存的 500 响应不会改变（[Stripe 错误处理](https://docs.stripe.com/error-low-level#server-errors)）。
- **幂等有作用范围。**EC2 的 `ClientToken` 只在区域或可用区内有效，同一 token 换个区域可能创建另一份资源；ECS `RunTask` 的 token 有效期是"24 小时"和"资源生命周期加一小时"中的较小值（[EC2 幂等](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html)、[ECS 幂等](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_Idempotency.html)）。
- **重发要绑定资源版本。**Google Cloud Storage 的文档举过这样的例子：一个删除请求延迟了，重试的删除先成功，接着有人创建了同名的新对象，原删除请求迟到后把新对象删掉了。绑定原对象 generation 的前置条件可以避免（[Cloud Storage 前置条件](https://docs.cloud.google.com/storage/docs/request-preconditions#multiple_request_retries)）。
- **"幂等"的写也可能破坏一致性。**RIFL 论文指出，覆盖写虽然满足通常的幂等定义，但如果重试夹在其他客户端的写入之后，仍会覆盖掉新值（[RIFL §2，图 2](https://web.stanford.edu/~ouster/cgi-bin/papers/rifl.pdf)）。

### 4.3 核对调度、退避与暂停

- 账本决定何时核对；计时、领取和恢复由持久工作承载。
- 核对查询本身也要经过准入、授权、预算和出口记录。原来的写入许可不能代替读取或保存许可。为减少往返，可以预先准入一个有上限的核对计划。
- 同一动作的重复唤醒合并处理，并限制同时进行的核对数量。推送只用来提高优先级：Stripe 的 webhook 可能重复、乱序，自动重投最长持续三天（[Stripe webhook](https://docs.stripe.com/webhooks#event-delivery-behaviors)），不能替代主动核对和缺口检测。
- 退避使用"全抖动"指数退避，并把目标要求的最短等待时间作为下界：

  ```text
  等待时间 = Uniform(0, min(退避上限, 初始间隔 × 2^连续无进展次数))
  ```

  重试只在账本这一层集中进行，避免适配器、SDK、传输层各自重试而成倍放大（[AWS 超时、重试与退避](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf)）。下次核对时间持久保存，工作者不靠长时间睡眠来维持调度。

| 情况 | 处理 |
| --- | --- |
| 效果和终局都已证实 | 结束核对，形成收尾依据 |
| 仍在处理、暂时没看到、查询暂不可用 | 保持未知，持久安排下一次核对 |
| 次数、时间或费用上限耗尽 | 暂停主动核对，保留未知和迟到可能性 |
| 当前授权不足 | 停止相关查询或证据保存，记录缺少的许可 |
| 目标不再保留结果，或能力失效 | 暂停，说明无法继续自动核对 |
| 任务被取消 | 派发封闭；许可允许时继续核对，不能直接记为未生效 |

暂停通知至少包含：动作和尝试标识、效果、迟到可能性、最后一次观察、暂停原因、恢复所需的证据或许可、是否已具备收尾依据。暂停的是**自动查询**，不是动作的责任：之后到达的合法证据仍会被接纳。

### 4.4 取消与执行的竞争

取消先在裁决域持久保存、停止新的准入，再按 R7 把封闭命令交给账本。

| 竞争结果 | 账本的处理 |
| --- | --- |
| 封闭先于出口开放 | 禁止发送；没有其他开放过的出口时，效果为 `NOT_APPLIED`，迟到可能性为 `RULED_OUT` |
| 封闭先于意图被接纳 | 保存对原控制范围的封闭；迟到的意图仍会被接纳为责任，但不会被执行 |
| 出口开放先于封闭 | 保留"可能发送"和迟到可能性；停止后续的写入重发，继续核对 |
| 目标支持取消 | 发出经准入的取消请求；只有它提供了充分的终局证据，才排除迟到效果 |
| 效果回报与封闭同时到达 | 两者按序记录；封闭不覆盖已经发生的效果 |
| Result 固定后才收到迟到证据或费用 | 关联到原动作，更新当前视图并追加记录；不改写原 Result |

取消之后不能再用原键发送写请求：即使是同一个键，对目标来说也可能是第一次到达并产生效果。

### 4.5 端侧补传与云端对账

1. 端侧账本保持原账本和执行端身份，在本地事务中同时提交状态变更和待补传的事实；
2. 断网期间，尚未开始的本机动作只有在本地能证明当前授权仍然有效时才启动；需要云端当前事实（例如是否被撤销）而无法取得时，等待；
3. 云端依赖失联端侧的步骤保持等待，不接管原动作；
4. 重连后，先核对授权、任务控制和条件变化，封闭不再允许发送的动作，然后补传事实，处理缺口；
5. 云端按负责方、流身份和事实序号去重，逐项持久接纳；乱序到达的事实可以暂存，缺口补齐之前不能根据不完整的视图宣称收尾；
6. 云端只确认**连续的**已持久前缀；端侧持久记下回执之后，才能按回收规则压缩已发送的记录。CouchDB 的复制协议有同样的教训：批量写入返回 HTTP 201 时，其中的文档可能全部失败，检查点必须在逐项确认之后才推进（[CouchDB 3.4.3 复制协议](https://github.com/apache/couchdb/blob/3.4.3/src/docs/src/replication/protocol.rst#L1371)）；
7. 检查点不一致时，从双方共同确认的位置重传，或使用覆盖范围可验证的快照；不能用覆盖状态来掩盖缺口。

同步范围由当前的同步许可决定。原参数、证据正文、可能泄露内容的摘要不会因为"需要对账"就自动上传；云端可以只拿到获准的状态、关联和端侧证据的引用。

设备重置或账本损坏、原请求身份无法恢复时，旧动作保持未知。新设备不能用新键再执行一次旧动作。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 意图接纳的回执丢失 | 任务编排、持久工作 | 查询原交接，必要时补交原意图；动作和执行端不变 |
| 执行回执丢失 | 动作账本 | 原尝试保持未知；按能力核对或安全重发 |
| 工作者或宿主进程崩溃 | 持久工作接替工作者，账本裁决恢复方式 | 未开放过出口的尝试重新检查后可以执行；开放过的按未知恢复；不改派执行端 |
| 重复请求 | 持久工作、动作账本 | 原命令返回原决定；同身份不同内容拒绝；重复事实不产生新执行或新通知 |
| 并发的领取、封闭、回报 | 持久工作、动作账本、出口闸门 | 领取代次和条件写入保护当前状态；封闭不可逆；旧工作者的证据单独接纳；不能假定本地锁能阻止第三方迟到执行 |
| 存储不可用 | 对应的持久域 | 不确认接纳，不开放新出口；已发生但未记录的效果，恢复时按未知处理 |
| 授权或预算服务不可用 | 授权、预算、出口闸门 | 无法证明出口合法就等待；不因为是重发就跳过检查 |
| 目标或查询接口不可用 | 动作账本、适配器 | 退避并持久安排；达到上限后暂停，保持未知 |
| 迟到的结果 | 动作账本；任务编排接纳进展；预算接纳费用 | 关联原尝试；即使工作租约已经失效，也接纳合法证据；不重新打开派发，不丢弃迟到的费用 |
| 证据相互矛盾 | 动作账本、适配器维护方 | 按目标版本和证据覆盖范围判断；确属冲突就保持未知并停止推进，不按"最后到达"覆盖 |
| 宣称终局之后又出现新效果 | 动作账本、相关能力声明的负责方 | 视为终局依据或能力声明失效：保存反例，通知任务编排，停止使用这条错误的保证，记为一致性失败 |

## 6 不变量落实

| 不变量 | 本模块怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 未知持久保留；重发只依据目标的幂等能力，或确定的否定加终局证据 | 注入超时、弱 NotFound、迟到请求、键过期、部分效果，检查没有不安全的新尝试 |
| G2 | 提供派发封闭和终局依据；覆盖全部已准入动作；本身不裁决任务成功 | 并发的准入与完成、尚未接纳的意图、异步回报、未知且可能迟到时，完成门禁拒绝成功 |
| G3 | 接纳、出口风险、证据、调度和回执都先持久；交接遵守 R7 | 在每个提交点和回执前后注入崩溃，另测掉电和存储恢复 |
| G4 | 保存条件版本、授权和预算依据；每次出口都重新核验 | 条件变更、撤销、预算耗尽、旧凭据、只有核对权限等场景 |
| G5 | 模型、工具、网络、文件、设备和核对都经过闸门；关闭隐藏的重试 | 捕获实际出口，逐个关联到准入记录、尝试和出口记录；检查嵌套调用 |
| G6 | 推理和适配器只能提议或回报；效果由核心写入 | 构建依赖检查；伪造完成主张、越过编排直接调用的测试 |
| G7 | 凭据绑定主体、目标和用途；账本不能签发更大的权限 | 委派、插件或能力升级试图扩大范围时被拒绝 |
| G8 | 执行、读取、保存和同步分别检查许可；失联时无法证明当前授权就等待 | 撤销某一种用途，确认其他用途不会自动顶替；断网期间撤销 |
| G9 | 参数和证据归内容治理；不留旁路副本；删除后不再读取、重发或同步 | 删除、派生引用、缓存清理；迟到消息不能恢复已删除内容 |
| G10 | 费用按实际计费来源交预算去重；取消不会抹掉费用 | 同一账单多次回报只计一次，不同的实际收费分别计入，迟到费用照常接纳 |
| G11 | 负责方固定；恢复原动作和原尝试身份；租约过期不产生替代动作 | 端点失联、工作者替换、回执丢失、设备重置 |
| G12 | 标识、权限、存储查询和调度都带用户范围 | 跨用户的标识碰撞、错误路由、单用户故障风暴 |

## 7 取舍

### 7.1 保证到哪一层

| 保证层级 | 前提 | 定位 |
| --- | --- | --- |
| 只保证持久接纳一次；结果未知的请求一律不重发 | 不需要第三方配合 | 能力不足时的保守分支 |
| **持久接纳 + 目标侧幂等或强核对** | 固定请求身份、参数、作用范围和有效条件 | 通用设计，每个目标单独声明能力 |
| 目标效果和去重记录共同原子提交 | 目标参与事务或等价协议，请求身份和回收规则可靠 | 合作目标的增强能力，可以对限定范围声明"恰好一次" |

RIFL 能实现恰好一次，是因为它要求完成记录与动作造成的变更在**目标侧**原子持久（[RIFL §3、§9](https://web.stanford.edu/~ouster/cgi-bin/papers/rifl.pdf)）。Kafka 的事务也只能协调 Kafka 内部的输出和消费位置，写外部系统仍需目标配合（[Kafka 3.9 投递语义](https://kafka.apache.org/39/design/design/)）。所以 Lerna 采用第二层，并明确声明保证范围：分区持续、目标永久不可用、请求身份无法恢复时，不承诺动作一定能完成。

### 7.2 其他关键选择

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 效果和迟到可能性分开记录 | 能表达取消、部分效果和迟到结果 | 状态组合需要显式校验 |
| 发送之前就记录"可能发送" | 崩溃后不会误判为未执行 | 可能把实际没发出去的请求也保留为未知 |
| 稳定的尝试标识 + 独立的发送序号 | 远端去重和物理调用追踪兼得 | 适配器接入约定更严格 |
| 不幂等的动作要有强否定证据才重试 | 避开"查询—创建"竞争和迟到效果 | 部分目标无法自动恢复 |
| 有上限的主动核对 | 控制费用、负载和长期待办 | 一些动作需要人工提供证据 |
| 端侧唯一写入，云端只保存视图 | 满足 A1、A3、G11 | 端侧失联时可用性下降 |
| 内容和去重身份分开治理 | 既能删除内容，又能安全恢复 | 需要独立的回收规则和过期拒绝规则 |

工作引擎的重试不能代替效果核对。Temporal 的工程文章展示过"查询不存在 → 创建"的竞争：旧尝试超时之后仍可能完成创建（[Temporal：幂等与持久执行](https://temporal.io/blog/idempotency-and-durable-execution)）。在查询和创建之间加本地锁，也终止不了已经进入第三方的请求。

### 7.3 需要记录 ADR 的决定

尝试标识的语义、收尾依据的定义、过期请求的拒绝规则、补传事实的身份方案，正式采纳时应各写一篇 ADR。

## 8 待定事项

验证不足时，不启用依赖它的自动重发能力。

| 编号 | 问题 | 验证方式与保守分支 |
| --- | --- | --- |
| H1 | 首批目标能否提供关联到原尝试的效果和终局证据 | 固定 API 版本和证据规则，在目标沙箱中测试；只能查到当前资源状态的，保持未知 |
| H2 | 有限的幂等有效期能否覆盖重发的到达和处理 | 验证目标是否有过期拒绝机制或明确的时间边界；不能证明就关闭这条路径的自动重发 |
| H3 | 闸门能否阻止过期领取产生新出口，同时保留已进入出口的风险 | 暂停旧工作者、让租约过期后恢复，注入出口竞争；没有终局证据时仍保留迟到可能性 |
| H4 | 存储和文件目标的持久、发布与恢复语义是否满足契约 | 在支持的平台上测试掉电、损坏和恢复；不凭路径或内容相同就声明幂等 |
| H5 | 核对参数、每用户限流和保留策略能否满足成本和容量目标 | 模拟故障风暴、长期未知和大量重连；具体参数通过测量确定 |

## 9 M1 范围

动作账本在 M1 要完整实现故障语义。

| 范围 | M1 实现 | 推迟 |
| --- | --- | --- |
| 接纳与交接 | 持久意图、原命令查询、R7 回执、重复处理；同进程部署也保留事务域边界 | 真实的跨端传输：M3 |
| 尝试与出口 | 稳定尝试、外部键绑定、发送序号、出口前的当前检查、禁止隐藏重试 | 接入更多目标，共同约定不变 |
| 效果与迟到可能性 | 三态效果、部分证据、迟到可能性、收尾依据、取消前后的竞争 | 无 |
| 核对 | 持久调度、退避、核对查询的准入、上限、暂停、恢复、通知任务编排 | 生产环境的 webhook 随具体适配器推进 |
| 模拟目标 | 幂等、可查询、不可查询三类；支持延迟生效、弱查询、回执丢失、键过期等故障注入 | 无，这是 M1 退出测试的基础 |
| API 与文件适配器 | 按具体能力声明；文件追加和任意覆盖不能默认标为幂等 | GUI：M3；外部 Agent：M4 |
| 费用关联 | 保存用量关联并可靠转交预算；取消后仍接纳迟到的用量 | 完整的结算和退款：M2 |
| 端云接口 | 固定事实身份、逐项回执和检查点语义，用模拟的重复、乱序和断线验证 | 实际端侧部署和离线重连：M3 |
| 多用户 | 所有记录和接口带用户范围；M1 单用户运行 | 分片和容量验证：M6 |

**M1 退出标准**：可以查询的未知能按证据恢复；既不能查询也不幂等的未知被持久保留并明确展示；回执丢失、重启、取消竞争和迟到效果都不会造成重复的副作用或虚假的成功。

## 10 测试要点

测试使用能观察到实际效果的模拟目标，独立检查实际调用次数、效果、计费来源和账本记录。

| 编号 | 用例 | 必须满足 | 对应 |
| --- | --- | --- | --- |
| T01 | 接纳成功后回执丢失，重复交接 | 原动作、原负责方、原接纳决定；没有第二个动作 | G3、G11、R7 |
| T02 | 同一标识提交不同参数或目标 | 明确拒绝，不覆盖旧记录，不调用目标 | G1、G4 |
| T03 | 在 4.1 每个提交点和回执前后崩溃 | 责任不丢失；开放过出口的不能恢复成"未执行" | G1–G3 |
| T04 | 存储确认后立即掉电并恢复 | 已确认的责任仍可恢复；持久配置不满足时验收失败 | G3 |
| T05 | 未知后重发、进程重建、SDK 自动生成键和自动重试 | 原键和作用范围稳定；每次实际出口都有记录；没有隐藏的发送 | G1、G5 |
| T06 | 最终一致的 NotFound；旧请求仍在途但查询暂时没有 | 不创建新尝试、不换键，保持未知 | G1 |
| T07 | 缓存的 500，随后目标迟到生效并推送 | 缓存的错误不转为未生效；迟到证据关联到原尝试 | G1、G2 |
| T08 | 幂等键过期、重发到达时已超出有效期、时钟回拨 | 不延长安全窗口；无法证明安全就不重发 | G1 |
| T09 | 原请求已成功，重发因资源版本变化返回前置条件失败 | 这次未执行不被误解为原动作从未生效 | G1、G2 |
| T10 | 原键参数冲突，或目标作用范围改变 | 冲突不清除旧的未知；禁止跨范围重发 | G1、G4 |
| T11 | 旧工作者暂停、租约过期、新工作者恢复后旧请求才返回 | 旧领取不能覆盖当前工作；合法的迟到证据仍被接纳 | G1、G11 |
| T12 | 封闭命令先于意图到达 | 迟到的意图不会产生出口，责任记录仍在 | G3、G11 |
| T13 | 封闭与开放出口交错，包括已开放但实际尚未发送 | 按持久顺序和终局证据分类，不猜测未生效 | G1、G2 |
| T14 | 取消后试图用同键重发写请求；第三方忽略取消 | 新的写入被阻止；原动作继续核对，保留迟到可能性 | G1、G4、C7 |
| T15 | 核对次数、期限或预算耗尽，或授权被撤回 | 持久暂停并说明原因；未知不转为未生效 | G1、G8 |
| T16 | 核对暂停后收到合法的迟到证据，通知回执再次丢失 | 证据仍被接纳，通知可靠补交，不重复推进 | G3、R7 |
| T17 | 推送重复、乱序、伪造，以及真实的证据冲突 | 验证来源并去重；不按到达时间盲目覆盖 | G1、G2、G12 |
| T18 | 多效果动作部分完成；异步接口返回"已接受" | 保存已知部分；整体无法确定时保持未知 | G1、G2、C4 |
| T19 | 完成门禁与新准入竞争；有动作尚未接纳，或端侧事实有缺口 | 完成检查覆盖全部已准入动作，不会遗漏责任而成功关闭 | G2 |
| T20 | 端云批量补传部分成功、重复、乱序、确认丢失 | 连续确认前缀正确；不跳过缺口；补传不会再次执行 | G3、G11 |
| T21 | 检查点回退、设备重置、原身份无法恢复 | 不复用旧的流身份；不用新键执行旧动作 | G1、G11 |
| T22 | 删除证据、撤销同步许可后，旧消息被重传 | 不恢复已删除内容，不上传端侧专有内容 | G8、G9、C2 |
| T23 | 同一费用重复回报；同一动作产生不同的实际费用；取消后到达的账单 | 同一来源只计一次，不同费用分别计入 | G10 |
| T24 | 跨用户碰撞、错误路由、单用户故障风暴 | 没有跨用户的读写、去重或费用串账 | G12 |

此外，把 G1、G2、G3、G11 写成可执行的状态机性质，对"开放出口、封闭、观察、恢复、接纳"这几种事件的交错做小规模穷举。真实适配器仍需验证各自的目标约定；模拟测试不能证明供应商的声明永远成立。
