文件适配器负责在授权范围内读取文件、发布单个文件、读回核验、观察原生版本，以及查询原尝试。

它最重要的一条原则是：**"原子可见""条件更新""结果确定""崩溃后持久"是四种不同的保证**，必须分别声明和回报。"写入成功"不是一个单一的事实。

## 1 职责与边界

动作账本持有发布尝试和效果；内容治理持有来源、版本、派生关系和清理责任。适配器回报文件系统原生的状态，不另建一张权威的"成功表"。发布路径和临时资源也都经过出口闸门。

支持范围分三档：

| 范围 | 可以承诺的前提 |
| --- | --- |
| 受管理的本机目录 | 所有写者都走受控出口；可以串行检查版本；文件系统履行它声明的同步和替换语义 |
| 任意原生文件 | 以原生能力为准；有不合作的写者时只能尽力检测，或者要求目标原生的比较交换 |
| URI 或远程 Provider | 按 Provider 声明的原子性、同步、版本、查询和迟到边界处理 |

## 2 对象与状态

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| 文件能力 | 文件系统或 Provider、原子替换、同步、条件写入、提交查询能力 | 防止平台语义被一个统一的 `ok` 掩盖 |
| 目标身份 | 端点、授权根、相对路径或 URI、原生身份、类型 | 同名文件不自动视为原来的对象 |
| 版本证据 | 原生版本、内容摘要、长度、观察时间 | 描述观察时的内容 |
| 发布输入 | 内容引用、期望版本、发布模式、元数据策略 | 固定这次写入的意图 |
| 临时资源 | 原尝试、独占名称、内容摘要、准备状态 | 恢复和清理只处理本尝试的资源 |
| 提交证据 | 可选的提交身份、实际目标身份、同步结果、读回证据 | 区分发布、持久和归因 |

发布的阶段由动作账本保存：

```text
待准备 → 临时内容已写 → 临时内容已同步 → 可能已发布 → 持久性已确认 → 读回已核验
```

发布窗口内的任何失联、错误或进程中断，都可能让状态进入"未知"。准备完成不代表已发布；读回正确也不能代替目录同步。

**当前内容与预期相同**，能证明观察时的字节相同；**当前内容不同**，也可能是原动作成功之后又被用户改了。两者都不能无条件证明原动作是否执行过。

## 3 接口

| 接口 | 输入 → 输出 | 成功含义 | 错误 |
| --- | --- | --- | --- |
| 读取 | 目标、处理目的、读取凭据、期望版本 → 内容和版本证据 | 拿到声明范围内的字节 | 越界、类型不支持、权限失效、并发变化、Provider 不可用 |
| 发布 | 原尝试、目标、期望版本、内容引用、模式 → 发布回报 | 返回发布、同步和核验的信息 | 版本冲突、短写、空间不足、替换或同步失败、未知；受管理模式下还有"前驱证据未交接"（见 4.2） |
| 核验 | 原尝试、目标和预期摘要 → 实际身份、摘要、格式证据 | 当前读回符合指定的范围；不能恢复旧内容 | 不一致、对象已更换、读取不完整 |
| 查询原尝试 | 原尝试、已保存的提交位置 → 提交证据或缺口 | 找到可以归因的原提交；**不重新发布** | 不支持、历史已清理、证据冲突 |
| 清理临时资源 | 核心的清理命令、资源引用和凭据 → 清理回报 | 指定的临时资源已清理并持久确认；**不删除用户的目标文件来"补偿"** | 仍在使用、身份不符、删除失败 |

结果未知时，发布**不得**重新覆盖。

## 4 关键流程

### 4.1 普通文件的发布

1. 动作账本保存尝试、目标、内容摘要、期望版本和允许的临时资源范围；
2. 出口核验授权根、文件类型、当前权限，取得稳定的资源锁。锁的对象不得是即将被替换的那个目标 inode；
3. 在锁内检查期望版本。受管理模式要求所有写者都遵守这个规则；路径锚定和操作系统的权限隔离共同防止越界；
4. 在**同一个文件系统**中写独占的临时文件，处理短写和错误，然后同步临时文件。同步使用部署层[平台准入表](../topics/data-and-storage.md#54-持久档位)为该平台规定的屏障原语（例如 macOS 上的 `F_FULLFSYNC`），并逐项处理错误；平台不在准入表中时，不声明掉电后的持久性；
5. 发布前重新检查资格、授权和取消状态；执行一次替换，**再同步所在的目录**；
6. 重新打开最终目标，验证身份、长度、完整摘要和条件要求的格式；内容治理保存允许保存的证据；
7. 动作账本持久接纳发布、同步、读回和迟到的信息，之后才确认回报。取消不会自动恢复旧版本。

几个关键的系统语义：Linux 的 `rename` 能原子地替换目录项，跨挂载点会返回 `EXDEV`；`RENAME_NOREPLACE` 只检查目标不存在，不提供"按既有版本替换"的比较交换；在 NFS 上，错误可能在重命名**已经发生之后**才回报（[rename](https://man7.org/linux/man-pages/man2/rename.2.html)）。所以跨挂载时不得用"复制"降级来冒充原子替换。`fsync` 文件不一定会持久化目录项，目录还需要单独同步，同步本身也可能返回 I/O、空间或配额错误（[fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)）。POSIX.1-2024 同样区分了目录操作的原子性和持久性（[POSIX 说明](https://pubs.opengroup.org/onlinepubs/9799919799/xrat/V4_xbd_chap01.html)）。读回正确可能只是来自缓存，所以同步结果和字节读回要分别回报。

### 4.2 受管理的版本布局

需要可以归因的证据时，使用不可变的版本对象加一个原子提交的指针：先同步不可变对象，再原子发布包含动作标识、目标版本、对象引用和摘要的提交指针，并同步指针及其目录。

指针只能证明**当前**的发布，不能单独证明被后续版本覆盖的发布。例如动作 A 发布后、账本保存回报前崩溃，锁随进程退出而释放；写者 B 随后发布，指针只剩 B。此时即使 A 的不可变对象还在，也只能证明内容曾经准备好，无法证明 A 是否真正发布过。因此受管理布局增加**串行交接**规则：

1. 写者在稳定锁内读取当前提交；
2. 覆盖之前，确认该提交的发布证据已被动作账本持久接纳；
3. 前驱没有回报时，先按原尝试核对并补交前驱证据；
4. 账本不可用或核对未完成时，**阻止对该目标的覆盖**，返回"前驱证据未交接"。

这样指针始终保留最后一个尚未完成证据交接的提交，历史由账本负责，不需要第二套效果记录。代价是：账本不可用期间，同一目标不能写入。

其他规则：

- 只有被指针引用过、且证据已交给账本的提交才算发布证据。孤立的不可变对象（未被指针引用）不得判为已发布；
- 不得通过重新发布 A 覆盖 B 来"核对" A；
- 历史回收与责任交接关联：账本接纳前驱证据之前，不得按 TTL 删除最后的提交依据。

允许前驱核对未完成时继续发布的"持久提交链"方案（每个提交对象保存前驱身份，从 HEAD 可达才算发布）已评估，M1 不采用：它需要历史遍历和回收，M1 不需要更高的并发恢复能力（见[评审 RV8](../../review/archive/round-1/README.md#rv8-受管理文件覆盖前先交接前驱证据)）。

普通文件没有等价的能力，所以**不承诺消除**发布与回执之间的未知窗口。这个保证也不能推广到任意文件，多文件的对外发布也不在单文件保证之内。

### 4.3 条件写入

| 方式 | 适用范围 |
| --- | --- |
| 所有写者遵守稳定的锁和版本检查 | 受管理的范围（M1 采用） |
| 目标原生的比较交换或事务 | 有不合作写者的场景，要求强条件写入时 |
| 比较摘要后替换 | 检查和替换之间有竞争窗口，只能声明为"尽力检测" |
| 最后写者覆盖 | 只适用于用户明确授权覆盖的情况 |

`flock` 通常只是建议锁，不合作的写者可以绕过；`openat2` 可以限制相对授权根的路径解析和符号链接（[flock](https://man7.org/linux/man-pages/man2/flock.2.html)、[openat2](https://man7.org/linux/man-pages/man2/openat2.2.html)），而字符串的路径检查存在竞争。

### 4.4 Android 与 URI Provider

原生路径和 URI Provider 分档实现，逐个 Provider 声明保证。Android 的 `AtomicFile` 不提供锁，`android-15.0.0_r1` 中 `finishWrite` 对部分同步、关闭和重命名失败只写日志（[AtomicFile](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/util/AtomicFile.java)），正常返回不能证明已持久发布。DocumentsProvider 的部分打开模式会返回管道或 socket，SAF 的能力取决于 Provider，重命名可能改变 URI（[DocumentsProvider](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/provider/DocumentsProvider.java)、[SAF 指南](https://developer.android.com/training/data-storage/shared/documents-files)）。文档 URI 并不天然具备普通文件的同步、原子替换、版本或查询语义。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 原端点的动作账本 | 查询提交身份和原尝试；不再次覆盖 |
| 前驱发布后、账本回报前崩溃，随后另一写者要覆盖 | 动作账本、文件适配器 | 后继写者先核对并补交前驱证据；账本不可用时阻止覆盖 |
| 进程崩溃 | 持久工作、动作账本 | 准备阶段：证明发布没发生、旧执行已停止后可以收尾；发布窗口：用提交证据核对，否则保持未知 |
| 重复请求 | 持久工作、动作账本 | 同身份同内容查原决定；不同内容拒绝 |
| 并发冲突 | 本机受控出口、目标 Provider | 稳定锁加版本检查；有不合作写者时，要求原生比较交换或降级声明 |
| 依赖不可用 | 动作账本、授权 | 卸载、Provider 断线、URI 失效时等待；不对同名的新对象继续操作 |
| 旧工作者恢复 | 出口闸门、持久工作 | 旧资格不得发布；暂停的进程可能仍持有锁，不得只因租约到期就启动另一个写者 |
| 发布后同步失败 | 动作账本 | 保存已观察到的内容，持久性记为未知，不回报未生效 |
| 发布后用户修改 | 动作账本、任务编排 | 保留历史效果证据和新的目标版本；不以"当前不同"推断原动作没发生 |
| 临时文件清理失败 | 内容治理、持久工作 | 跟踪限定的资源继续清理；不得按年龄删除仍被未知尝试引用的文件 |

## 6 不变量落实

| 不变量 | 怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 发布窗口是未知的；当前的摘要不能单独决定是否重发 | 发布成功、丢回执、用户改写之后恢复 |
| G2 | 字节、格式、持久性和收尾分别核验 | 读回正确但目录同步失败时，不得报告成功 |
| G3 | 尝试和接纳先持久；逐项检查同步错误 | 在每个写入、同步、替换的边界中断 |
| G4 | 临时资源和最终资源绑定同一个准入范围 | 发布前撤销授权；过期的资格恢复 |
| G5 | 打开、读写、替换、清理都受控 | 路径逃逸、隐藏的备份或自动导出 |
| G6 | 适配器回报文件状态，任务编排判断条件 | "写入成功"不得代替全部任务条件 |
| G7 | 只接受来源范围内的根、路径或 URI | 子授权访问祖先目录、特殊文件，被拒绝 |
| G8 | 读取、历史保存、同步、发布分别检查 | 允许读取但不允许备份 |
| G9 | 临时文件、历史、读回和缓存登记派生关系 | 删除后遍历受管理的副本和索引 |
| G11 | 原端点恢复，不换一台设备重新写 | 端点失联时动作责任保持不变 |
| G12 | 用户的根、临时名称、版本和锁的范围隔离 | 同名路径、恶意硬链接、跨用户并发 |

## 7 取舍

普通文件采用"同步后替换"，保持与应用的兼容，但允许存在无法归因的未知窗口；受管理的内容可以采用不可变版本加提交指针，改善恢复，代价是额外的目录布局和治理成本。有不合作写者时，"比较摘要再替换"不会升级为比较交换。完整读回增加 I/O，这是 C4 和 G2 的必要成本。原生路径和 URI Provider 分档实现，而不是统一成一种路径语义（那样会误用 Provider 的保证）。受管理布局和历史保留策略在正式采纳前必须写成 ADR。

## 8 待定事项

- M1 声明支持哪些文件系统、元数据保留策略和受管理布局；
- 设备和挂载配置是否真的履行同步保证（结果写入平台准入表），需要模拟断电和真实环境测试。SQLite 用故障文件系统模拟部分写、乱序写和断电来检查事务一致性（[SQLite 原子提交测试](https://www.sqlite.org/atomiccommit.html#testing_atomic_commit_behavior)），文件适配器也必须做这类存储故障模型测试，只杀进程覆盖不了未同步写入的丢失；
- 受管理的根及其祖先目录是否确实没有不合作的写者或可以逃逸的别名；
- 各 SAF Provider 是否具备可归因的提交、稳定的身份或可靠的读回；不具备时维持保守声明。

## 9 M1 范围

| M1 实现 | 推迟 |
| --- | --- |
| 受管理本机目录的读取、单文件的创建和替换、串行交接前驱证据、版本冲突、同步错误、读回、原尝试查询、临时资源跟踪 | SAF 多 Provider、任意外部写者下的强条件写入、跨平台完整矩阵、多文件发布 |

追加写入和任意覆盖不得默认声明为幂等。

## 10 测试要点

| 用例 | 核心断言 |
| --- | --- |
| 在短写、同步、替换、目录同步、读回、回报的各个边界中断 | 不出现"半个文件却假装成功"，也不盲目覆盖 |
| 两个受管理的写者基于同一版本并发 | 最多一个按这个前提提交，另一个冲突 |
| 摘要检查之后插入一个不合作的写者 | 这种模式不得宣称是比较交换 |
| 发布成功、丢回执、用户随后编辑 | 恢复时不覆盖用户的新版本 |
| A 发布后、账本回报前崩溃，随后 B 发布；连续 A/B/C 覆盖 | B 在 A 的证据被账本接纳之前受阻；A 的发布可归因 |
| A 只生成对象未推进指针；推进指针后同步失败；账本接纳成功但确认丢失 | 孤立对象不判为已发布；同步失败记为持久性未知；确认丢失时查询原接纳 |
| 未知的 A 遇到历史清理 | 最后的提交依据不被删除 |
| `ENOSPC`、`EIO`、`EXDEV`、目录同步失败 | 保留真实的阶段；发布之后的错误不写成未生效 |
| 断电、未同步数据丢失、乱序写 | 恢复结果符合声明的文件系统保证 |
| 符号链接、祖先目录被移动、硬链接、特殊文件 | 范围之外的访问被拒绝 |
| Provider 返回管道、新的 URI、延迟提交 | 不套用普通原生文件的语义 |
