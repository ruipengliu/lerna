API 适配器把一次已准入的动作翻译成对外部 API 的一次调用，并按统一格式回报结果。它是 Lerna 首选的执行路径（C4）。

本设计的要点：

- **通用编译 + 服务语义补充**：用通用的 OpenAPI / MCP 编译器处理结构；由经过审查的服务补充描述，说明幂等、查询、计费和业务证据的语义。导入一份规范只能得到结构，得不到效果保证；
- **核心先固定幂等身份**：外部幂等键在核心持久保存后才发出，绑定参数指纹和目标账户，由适配器显式传给目标；SDK 自动生成的键和自动重试必须关闭；
- **以查询原动作为主要的核对方式**：webhook 只用于促发查询，搜索接口只算弱证据；
- **外部系统的认证与 Lerna 的授权分别检查**：拿到一个 OAuth scope，不等于获得对应的 Lerna 授权；令牌不进入推理上下文。

## 1 职责与边界

| 本适配器负责 | 相邻核心负责 |
| --- | --- |
| OpenAPI / MCP 的发现与解析、请求编译、单次调用、原请求查询、事件解码 | 核心固定能力材料和版本；推理选择并提议；任务编排准入 |
| 声明认证、幂等、查询、流控和业务证据的解释规则 | 授权裁决权限；预算裁决额度；执行管理决定重试和效果 |
| 回报原始的协议状态和业务证据 | 内容治理保存来源；任务编排执行完成门禁 |

API 适配器**不提供任意 URL 的执行入口**。工具的返回内容作为内容处理，不得改变条件、授权或能力声明。获取远程规范、MCP 初始化、分页、令牌刷新、重定向、下载结果和核对请求，都受 R2 约束。MCP 回调要求的模型调用、用户输入或其他工具行为，回到核心处理，不直接调用另一个适配器（R4）。

## 2 对象与状态

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| 能力描述 | 供应商、环境、能力标识、规范摘要、输入输出 Schema、序列化规则、适配器版本 | 防止同名工具或目录更新改变已准入的调用 |
| 目标绑定 | 服务 origin、账户主体、凭据引用、资源范围 | 恢复和令牌轮换不得改变账户 |
| 幂等声明 | 键的位置和格式、作用范围、最低保证期限、参数约束、并发和响应语义 | 判断能否用原身份重发 |
| 查询声明 | 查询键、终态、保留期、一致性、"否定证据"的条件 | 判断查询结果能否确定效果 |
| 远端绑定 | 请求标识、对象标识、异步句柄、事件游标 | 查询原动作，不新建替代动作 |
| 回报 | 协议状态、业务状态、证据、迟到可能性、限流建议、用量来源 | 分别解释错误和效果 |

状态由执行管理维护（见[执行适配器接口 2.4](../ports/executor/README.md#24-适配器需要支持表达的状态)）。API 特有的一点：收到可靠的接纳或异步句柄后，记为"远端处理中"，效果仍然未知。HTTP 202 只表示"已接收、待处理"（[RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)）；拿到长时间动作的句柄（例如 [Google AIP-151](https://google.aip.dev/151)）也不表示目标已达成。超时、5xx、解析失败都不得直接记为未生效。

## 3 接口

| 接口 | 输入 → 输出 | 成功含义 | 错误 |
| --- | --- | --- | --- |
| 描述能力 | 固定的规范或服务器引用、版本、访问凭据 → 能力快照 | 得到可以审查的材料 | 分页失败、版本漂移、方言不支持 |
| 编译请求 | 能力版本、参数、目标绑定 → 请求描述和指纹 | 序列化检查通过；**还没有调用业务 API** | 参数、编码、媒体类型或认证组合不支持 |
| 执行 | 原尝试、固定的请求、外部键 → 执行回报 | 拿到回报；实际效果另行裁决 | 出口拒绝、限流、连接故障、业务错误、效果未知 |
| 查询 | 原尝试和已保存的远端绑定 → 核对证据 | 拿到原动作的证据；**不重发业务动作** | 不支持查询、资源已过期、授权失效、证据冲突 |
| 接收事件 | 已认证的事件、账户、事件标识 → 核心持久回执 | 核心持久接纳之后，才向供应商确认 | 身份错误、账户错误、未知的绑定 |

## 4 关键流程

1. **选材。**核心安排规范或工具的发现，适配器编译能力描述，内容治理保存来源和版本。候选能力经核心提供给推理（R1、R4）；
2. **正确调用。**按 Schema、资源标识、单位、币种、时间、分页和序列化检查参数；能力不存在或输入有歧义时，返回缺口，不猜；
3. **准入。**裁决域保存条件、授权、预算和动作意图，按 R7 交给执行管理；
4. **固定身份。**执行管理保存请求指纹、目标账户、尝试和外部幂等键，然后才进入流控队列；
5. **实际出口。**取得流控资格后，重新检查权限、取消状态、版本和预算；出口闸门执行一次网络发送；
6. **接纳回报。**内容治理保存允许保存的证据，执行管理保存执行回报，预算接纳用量；之后才确认内部交接；
7. **恢复与完成。**执行管理查询原动作，或在保证窗口内用原身份重发；任务编排按当前条件和全部动作的收尾状态裁决 G2。

### 4.1 OpenAPI 与 MCP 的解释要点

- OpenAPI 3.1.1 中 `operationId` 可以省略；同一个安全要求对象内的多个机制是"与"，安全要求数组中的各项是"或"（[OpenAPI 3.1.1 安全要求](https://spec.openapis.org/oas/v3.1.1.html#security-requirement-object)）。误读认证组合会改变调用语义；
- MCP 的工具注解对不可信的服务器不构成保证，`isError: true` 表示工具执行出错（[MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)）。工具名、结构有效、错误回报都不足以证明实际效果；
- MCP 断线不表示取消，SSE 重放是可选的，取消通知也可能被忽略（[传输](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)、[取消](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)）。恢复"接收结果"和重发"业务请求"要分开；取消之后迟到的响应，可能是唯一的核对材料，要保留。

### 4.2 认证

授权检查之后，使用凭据引用，在出口处注入真实凭据。M1 可以用预配置的密钥，但仍然保持"引用加受控注入"的方式。MCP 的 HTTP 认证要求令牌绑定资源、禁止把服务器的令牌透传给下游；RFC 9700 要求公共客户端使用 PKCE，并提出权限最小化等要求（[MCP 认证](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)）。

### 4.3 流控与 429

重试只由执行管理决定。限流要区分速率、并发和资源冲突：RFC 6585 没有统一规定 429 的计数范围，Stripe 的部分 429 实际上是对象锁超时（[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)、[Stripe 限流](https://docs.stripe.com/rate-limits#rate-limited-responses)），不得统一扔进业务重试循环。M1 在单个宿主内做流控；多宿主之后按供应商账户协调，并为核对工作保留额度，避免核对被业务流量饿死。

### 4.4 千级 API 的扩展路径

"授权过滤 → 候选检索 → 加载完整描述 → 提议 → 编译检查 → 准入 → 效果核验"。先按用户、环境、权限和可用能力过滤，再用关键词加向量的混合检索找候选，保留分类路由作为回退；检索不到时可以扩大范围或向用户要信息，不得编造工具。研究结果不能直接外推：ToolLLM 使用了 16,464 个 API（[ToolLLM](https://arxiv.org/html/2307.16789v2)），StableToolBench 指出在线 API 的变化会让评测不稳定（[StableToolBench](https://arxiv.org/html/2403.07714v5)）。所以 Lerna 必须分别验收目录覆盖、候选召回、能力选择、参数正确性和真实效果，并使用固定的环境和故障模拟器。

## 5 故障与恢复

| 故障 | 负责方 | 恢复方式 |
| --- | --- | --- |
| 回执丢失 | 执行管理 | 查询原尝试、外部键或远端对象；不生成新键 |
| 进程崩溃 | 原端点的执行管理、持久工作 | 接替者读取发送记录；发送窗口不明就核对 |
| 重复请求 | 持久工作、执行管理 | 同身份同指纹返回原决定；不同指纹拒绝 |
| 并发冲突 | 执行管理、目标系统 | 保存目标返回的冲突；是否重发按目标的约定判断；修改参数必须形成新的提议 |
| 依赖不可用 | 持久工作、授权 | 未发出的请求等待；已发出的保持未知；授权恢复不证明旧请求没发生 |
| 迟到的结果 | 执行管理、预算、内容治理 | 核对账户和原绑定后追加证据和费用；不恢复任务推进 |
| 幂等键或查询资源过期 | 执行管理 | 停止自动重发，明确留下核对缺口 |
| 429、5xx、输出解析失败 | 适配器回报，执行管理裁决 | 保留原错误和发送阶段，不统一映射为未生效 |

Stripe 会保存同一幂等键的第一个结果，包括 500，并要求把部分 500 视为结果不确定：原请求可能有副作用，之后才在供应商处生效（[Stripe 幂等](https://docs.stripe.com/api/idempotent_requests)、[错误处理](https://docs.stripe.com/error-low-level#server-errors)）。所以"同一个键得到同一个错误"仍可能无法确定效果；超过幂等期限再重发，可能重复执行。Stripe 的搜索接口也不适合即时的"写后读"（[Stripe Search](https://docs.stripe.com/search#data-freshness)），查不到不证明没执行。

## 6 不变量落实

| 不变量 | 怎样保证 | 怎样验证 |
| --- | --- | --- |
| G1 | 错误与效果分开；重发前检查原身份和保证窗口 | 提交后丢回执、500 之后生效、查询先空后有 |
| G2 | 业务证据和收尾证明分别保存 | 202、结构有效但业务未完成，任务都不得成功 |
| G3 | 核心保存接纳、外部键和回报之后才确认 | 在各持久化点前后终止进程 |
| G4 | 请求绑定条件、授权、预算；排队之后再检查 | 排队期间撤销授权或改变条件 |
| G5 | 获取规范、刷新令牌、重定向、分页和查询全部经过出口 | 实际的网络发送数与允许的调用逐项对应 |
| G6 | 能力选择和完成声明都回到核心 | 工具返回"已完成"不得关闭任务 |
| G7 | 账户、资源和 scope 都限制在来源范围内 | 恶意请求额外的 scope、跨账户恢复 |
| G8 | 读取、保存、同步、行动分别检查 | 可读不可保存；撤回后命中缓存 |
| G9 | 响应、索引、缓存和迟到的内容登记派生关系 | 删除后无法再保存或使用 |
| G10 | 按实际收费来源去重 | 重复通知只计一次；多次真实收费都计入 |
| G11 | 原执行端点、尝试和远端绑定保持不变 | 重启、新的 MCP 会话不创建替代动作 |
| G12 | 用户的凭据、目录视图、队列和证据隔离 | 同名工具、同一个键、账户错误的事件跨用户测试 |

## 7 取舍

| 选择 | 得到 | 付出 |
| --- | --- | --- |
| 通用编译 + 服务语义补充 | 减少逐个 API 手写，又能表达可靠性语义 | 补充描述需要审查 |
| 核心持久固定外部键，执行管理负责重试 | 恢复过程可以解释 | 多一次持久写入和调度延迟 |
| 以查询原动作为主，webhook 只促发查询 | 不依赖推送的完整性 | 核对有额外的查询成本 |
| MCP 注解只作线索 | 不被不可信的服务器误导 | 未认证的目标只能按"不可查询、不幂等"处理 |

被否决：纯通用的 OpenAPI 或 MCP 桥接（接入快，但没有效果约定）；逐个服务手写（维护成本高）；用 SDK 的临时键（恢复时换键）；用参数哈希作为幂等身份（会把两笔内容相同的合法交易合并）；把密钥放进推理上下文（容易泄露和扩权）。

固定身份的规则、旧能力版本的保留策略，正式采纳前必须写成 ADR。

## 8 待定事项

- 首批供应商、支持的 OpenAPI 方言和 MCP 扩展范围；
- 混合检索在个人任务上是否优于分类路由，能否召回跨服务任务所需的能力；
- 目标实现是否真的遵守幂等期限、查询一致性和收费标识的约定；
- 旧查询接口的保留时间能否覆盖长任务；共享账户的流控会不会饿死核对工作；
- "首次调用正确率"和"有限重试成功率"的统计口径（见[项目目标 13](../project-goals.md#13-待定事项)）：区分描述数量、认证能力和实测调用；固定样本、重试次数、时间预算和"未知"的计数规则；评测必须报告不可执行的样本、目标故障、弃权和未知的数量，不得删掉这些样本来提高正确率。

## 9 M1 范围

| M1 实现 | 推迟 |
| --- | --- |
| 固定版本的能力描述、确定性的参数编译、受控的认证、单次请求、原尝试查询、固定的幂等键、未知和迟到的回报、429 反馈和持久等待 | 大目录检索优化、完整的 OAuth 接入、MCP 高级扩展、跨宿主流控、完整的推送网关 |
| 故障模拟 API：幂等、可查询、不可查询三类；覆盖接单或提交后丢回执、迟到生效、取消竞争 | 供应商特有的大量行为组合 |

M1 不以"已经接入了 1000 条描述"宣称达到"1000+ API 准确调用"的目标。

## 10 测试要点

| 用例 | 核心断言 |
| --- | --- |
| 提交成功后丢回执；500 之后生效 | 原键和原查询身份不变；不得换键重发 |
| 幂等窗口过期后恢复 | 自动重发停止 |
| 202 后长期处理中；查询先空后有 | 不假装完成，不因为空结果就重发 |
| SDK 误开重试、自动分页、自动刷新、重定向 | 每次实际出口都有对应的记录和凭据 |
| MCP 目录分页过程中变化、同名工具、新会话恢复 | 不拼接未固定的目录；不重发未知的工具调用 |
| 200 中携带工具错误；结果不符合 Schema | 错误不直接证明未生效 |
| 速率、并发、锁冲突导致的 429 | 分类等待；重试仍由执行管理决定 |
| 千级目录与真实调用 | 分别测量召回、选择、参数、首次效果和有限重试的结果 |
