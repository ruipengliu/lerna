# 端侧 UI 交互与协议扩展

状态：依据用户明确要求补充的协议设计。协议同时承载执行数据与端侧 UI 交互，沿用 gRPC、WebSocket、Protobuf 和动态 Schema 的既定路线。尚无端侧渲染器或互操作测试结果。

关联：[协议方案](03-contracts-and-protocols.md)、[接口与消息目录](03-contract-message-catalog.md)、[标识模型](03-identifier-model.md)。

## 能力范围与职责

协议须允许服务向端侧提供呈现数据和交互请求，也允许端侧主动发送用户意图、输入、界面事件和呈现状态。UI 交互可以关联任务，也可以独立存在；查看通知、修改界面偏好或提交新任务不必先创建一个虚假的执行任务。

在四类基础契约之上提供“用户交互与呈现”契约组，复用能力声明、授权、消息交付及恢复机制。它是跨系统的人机交互接口，不增加第四个逻辑系统，也不把 UI 状态处理塞入端云连接层。

| 责任 | 归属 |
| --- | --- |
| 交互意图、待输入内容和可选操作 | 提出该交互的任务、能力或应用模块；按权限注册交互处理逻辑。 |
| 消息校验、关联、交付和恢复 | Harness 协议与运行基础模块。 |
| 组件呈现、平台导航、输入采集、可访问性和本地草稿 | 端侧 UI Adapter / Renderer。 |
| 用户动作是否允许及其业务结果 | 对应业务模块与授权机制；由界面点击不能直接改写任务终态。 |
| 对第三方应用点击、滑动、截图 | 设备执行能力，继续遵守手机 GUI 的观察—动作—验证契约。 |

本分册的 UI 指 Harness 或接入应用与用户交互的界面。呈现一个表单和操作第三方应用的输入框是不同能力，即使它们运行在同一模拟端。

## 支持的交互形态

下表表示协议应能表达并按能力协商接入的形态，不要求每个端实现全部组件。

| 形态 | 服务/任务到 UI | UI 到服务/任务 |
| --- | --- | --- |
| 对话与流式内容 | 消息、文本增量、引用、状态和最终内容。 | 新消息、编辑、重试意图、取消生成及附件引用。 |
| 表单与选择 | 字段定义、选项、校验约束、默认值和错误反馈。 | 输入提交、选择、修改请求、放弃。 |
| 卡片与结果面板 | 结构化结果、列表、表格、动作入口及版本更新。 | 动作触发、分页、筛选、展开或刷新。 |
| 弹窗与待确认交互 | 提示、问题、选项、期限及明确的交互语义。 | 回答、拒绝、关闭；关闭不默认等同确认或业务取消。 |
| 通知与导航 | 通知内容、可操作入口、已登记路由的跳转请求。 | 打开、关闭、导航结果、操作选择。 |
| 多模态与实时视图 | 图片、音视频或图表的授权引用、受限数据块。 | 录入、选区、播放控制和已声明的实时事件。 |
| 插件自定义 UI | 具名类型、版本、Schema 与数据。 | 同一扩展声明的事件和输入类型。 |

端侧决定组件的原生实现或已有 UI 框架，不要求服务端规定每个像素、CSS 或平台控件类。交互语义、字段约束和动作含义必须保持。导航目标和组件动作使用已登记的标识，由端侧 Adapter 映射到具体平台。

## 扩展机制

固定 Protobuf 定义 UI 核心消息和扩展载荷容器。自定义内容通过统一扩展描述注册，扩展容器复用于 request、response、event；新增普通组件类型不需要改 Envelope 顶层 `oneof`。

| 扩展描述 | 契约要求 |
| --- | --- |
| type_name、type_version | 使用有归属的类型名，例如 `org.example.ui.chart`；版本在支持矩阵中声明。 |
| schema_ref | 标识、版本、摘要对应已登记的 JSON Schema 资源集；消息不触发任意远程 Schema 解析。 |
| payload | 受 Schema 校验的 UTF-8 JSON 或具名核心消息；大内容使用受限块或授权引用。 |
| supported_events | 列出可发送事件、参数 Schema、是否产生业务变更及处理模块。 |
| delivery / persistence | 声明可靠提交、可合并状态或临时事件，明确哪些信息须跨断连恢复。 |
| required_features / fallback | 声明必需能力和语义等价的可选降级；不能在客户端不支持时自动改成“已执行”。 |

声明登记时绑定实现模块、允许方向和权限要求。收到未知的必需组件、事件或主版本返回不支持；只有明确声明为可忽略、且不承载关键操作的装饰性内容才可忽略。缺少表单输入或确认能力时，应选择经过声明的等价交互或保持等待，不能用展示一段文本假装用户已提交。

客户端在连接协商中报告 UI 类型、事件和数据能力。协商、版本和权限三者分别校验，插件注册不能绕过准入。协议传递声明与数据，端侧 Renderer 通过插件机制安装和启用；服务端发来一种类型不等于端侧自动下载并执行代码。

## 核心 UI 消息

这些消息复用既有信封的消息、操作、授权和流元数据。gRPC 通过 UserInteractionService 及 Exchange 绑定，端云通过 WebSocket 绑定。

| 消息或方法 | 主要内容 | 行为语义 |
| --- | --- | --- |
| DescribeUI | 可用呈现类型、事件、Schema、限制和降级能力。 | 可以通过既有 Negotiate/能力发现交换，不再建立独立协议握手。 |
| GetSurface / SurfaceSnapshot | 界面目标、状态版本、组件数据及有效交互引用。 | 提供权威的可恢复快照；端侧可以有独立本地草稿，不反向覆盖权威状态。 |
| SurfacePatch | 界面目标、base_revision、revision、变更集。 | 只在基版本匹配时原子应用；有缺口则获取快照，不能盲目套用补丁。 |
| RequestInteraction | 呈现数据、输入 Schema、interaction_id、有效期、可选任务/操作引用。 | 建立或发布明确的等待项；同一项的更新保留身份，新等待项使用新身份。 |
| SubmitAction | operation_id、目标、事件类型、输入、可选 interaction_id 及预期版本。 | 对产生业务变更或正式交互提交的动作去重、校验后分派至对应处理模块。 |
| EmitUIEvent | 界面目标、事件类型、临时数据。 | 仅用于已声明不产生业务变更的遥测或实时事件；通常不分配 operation_id。 |
| GetActionResult / ActionResult / InteractionState | 对应操作、等待项、受理/校验/处理结果和必要新状态。 | 用户输入无效时返回字段错误；受理不等于业务完成。 |
| PresentationStatus | 已应用的界面版本、呈现失败或组件不支持。 | 只证明 Renderer 报告的状态，不证明用户已看到、理解或同意。 |
| CloseSurface / DismissInteraction | 界面或等待项目标、原因、显式动作。 | 界面关闭与等待项取消分别处理；请求取消业务任务仍走既有任务契约。 |

SubmitAction 是 UI Adapter 到既有处理模块的入口，不额外建立一套独立业务操作。例如表单提交最终调用 TaskService.ProvideInput 时保留同一 operation_id 和 interaction_id；后续实际执行产生新的业务操作时再建立父子关联。授权确认类动作交给权限模块校验，不能因为 UI 上报 `confirmed=true` 就直接增权。

资源接管与恢复可通过 SubmitAction 转交 CapabilityService.RequestResourceControl，保留同一逻辑操作身份及原始受信主体，核对资源范围和预期控制版本。UI 分别呈现接管已受理与已落实；恢复自动化不清除任务已有暂停或取消。控制语义见 [执行接口](07-execution-contracts-and-validation.md)。

运行中正式追加信息或修改任务目标时，登记的处理模块转交 TaskService.SubmitUpdate，保留原 operation_id 并遵守任务版本检查；它与回复特定等待项、编辑本地草稿分别处理。参考大脑默认展示受控进度，完整校验后发布答案；可选答案预览须表达草稿、失效及正式结果状态。完整规则见 [决策准入、交互与协作恢复](06-decision-admission-and-collaboration.md)。

快照、补丁和呈现回报是状态消息，不因发送一条更新就新建业务 Operation；发布命令或正式用户动作是否产生变更由登记的契约决定。由服务或本地模块发布的 UI 状态必须具备可核对的来源及发布权限。UI Renderer 的呈现回报只更新呈现状态，不成为底层任务、授权或执行效果的权威。

## 标识与状态的最小扩展

不增加 ui_task_id、ui_request_id、ui_event_id 或单独的 UI 操作身份。沿用 task_ref（可选）、operation_id（变更时）、message_id/reply_to 及 interaction_id（等待项时）。界面定位采用作用域内的引用：

- `surface_ref = (namespace, endpoint_ref, surface_key)`：定位已有端点上的一个窗口、面板或交互容器。它是路由信息；`surface_key` 由该端点管理，不要求全局 ID 服务。多窗口不能只依靠 task_ref 区分。
- `component_key`：在 surface 内定位控件或动作入口，由对应 Schema/呈现数据定义，不创建全局组件实体。
- `revision`、`base_revision`：表示界面状态版本，不替代业务操作身份或消息序号。surface 关闭后不能复用旧版本空间；重开需新局部键或明确的新状态世代。

`endpoint_ref` 关联既有受认证客户端/节点上下文，不仅凭用户账号定位。具体引用序列化随连接模型确定；相同账号下两个窗口、同机多个模拟端和同一任务在两个端展示均须能区分。

普通交互可以不关联 task_ref。等待项至少绑定发布方的受控作用域和处理模块，并保存来源、输入约束及状态；需要时关联任务或操作，不为等待用户输入而伪造任务。

## 可靠性与恢复

交互提交、授权选择、取消/接管意图和业务结果沿用可靠交付。operation_id、语义输入和目标在重试中保持；message_id 负责消息层关联。输入提交的操作不能复用待处理调用的操作 ID。

悬停、光标移动、临时输入预览等只有在契约明确允许时才合并或丢弃。最终文本或表单提交单独形成可靠操作。UI 草稿不因进入协议通道就自动获得长期存储或跨端同步授权。

界面增量可采用可靠流，也可声明为由快照恢复的状态流；后一种必须在重连及发现版本缺口时补取快照，并通过周期版本核对或可靠版本通告发现“最后一条增量丢失”的情况，不能静默导致界面永久停留旧状态。用于业务判断的呈现数据和提交结果按其业务保留要求保存。控件 UI 缓存不承担唯一业务记录。

完整恢复与窗口过期流程见 [恢复检查表](04-recovery-state-and-failure-matrix.md)。断连重连按以下可观察行为验收：重新校验身份与权限，获取当前界面及有效等待项；核对已提交操作，恢复必要状态。过期、已处理或被撤销的交互拒绝新提交，不能把旧点击用于新的等待点。

同一等待项在多个端展示时，提交须校验其状态和适用版本。一个端已经完成提交，其他端得到明确的已处理结果并刷新；如业务要求多人独立回答，应显式建立多个等待项，不能通过重复消费同一等待项暗中实现。

同一操作的回执丢失后重试返回原处理结果，而非因等待项已完成就误报为全新非法输入。权限校验仍先于结果披露；不同新操作竞争同一等待项时，仅允许契约规定的状态转换生效。

## 验收矩阵

| 维度 | 最低验证要求 |
| --- | --- |
| UI 多样性 | 至少以对话输入、结构化表单/卡片和通知动作证明同一通道可承载不同 UI 形态。 |
| 插件扩展 | 注册一个自定义 UI 类型及事件，接入匹配的 Renderer，无需修改核心 Envelope 或任务调度逻辑。 |
| 独立交互 | 无 task_ref 的 UI 查询、呈现和用户动作能够按权限处理。 |
| 能力差异 | 不同模拟端声明不同组件；缺少必需能力明确拒绝或采用声明的等价降级。 |
| 多端多窗口 | 同一账号多个端、同端多个 surface、同一任务多处呈现均正确路由，不能串发输入。 |
| 状态恢复 | 补丁基版本冲突、丢失最后增量、断连后重开及旧 surface 消息均不会错误应用。 |
| 操作恢复 | 提交后回执丢失、重复操作、多端竞答、过期或撤销等待项分别给出正确结果。 |
| 回执语义 | 消息已收、状态已应用、交互已提交与业务效果已确认可分别验证。 |
| 安全与权限 | 未登记事件、伪造目标、跨窗口/跨用户越权、失效授权和敏感输入存储限制得到执行。 |
| 流控 | 大 UI 资源与高频事件不导致无界队列；重要输入及取消有独立预算和明确背压。 |

以上是能力验收设计，使用多个模拟 UI 端和不同 Renderer 验证，不要求真实手机或绑定某个 UI 框架。具体呈现组件实现及像素外观不属于本次协议设计交付。

用户授权回应由授权模块持有的等待项约束，批准及签发按原请求范围/版本原子记录，任务与 UI 通过幂等交接取得结果。浏览器同源会话、Origin/CSRF 校验及会话失效遵守 [授权生命周期](08-authorization-lifecycle-and-interfaces.md)；UI 展示回报继续不作为用户同意。
