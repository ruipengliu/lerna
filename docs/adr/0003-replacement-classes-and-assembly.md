# 0003 替换资格分三类，公共契约与内部接口分开

- 影响：[分层与模块 P1、R6、第 4 节、第 11 节](../architecture/layers.md#2-划分原则)、[核心契约](../architecture/core/contracts/README.md)

## 背景

分层原则 P1 用"实现写错会不会破坏不变量"判断哪些属于核心，R6 规定核心只依赖核心契约。这两条不足以指导代码组织：

- PostgreSQL 和 SQLite 的存储实现写错都会丢失责任，按 P1 属于核心，但它们必须可以替换；
- R6 没有给出存储、时钟等平台实现和装配代码的位置，事务上下文这类内部对象容易被放进公共契约，进而进入 SDK。

## 决定

1. P1 只判断哪些实现必须受信。替换资格另分三类：核心裁决语义只随受审查版本发布；受信实现（例如存储、时钟、密钥、出口基本操作；之后补充的受信宿主与供应商编码、受信解释规则、核验规则见[分层与模块第 2 节](../architecture/layers.md#2-划分原则)）通过专项契约和平台验证后可以替换；第三方实现只使用被授予的接口和能力。
2. 核心契约分为公共契约和内部接口。公共契约包括跨进程命令、稳定引用、可替换部分的接口和线协议；内部接口包括事务上下文、存储访问和平台时钟，不进入 SDK。（注："内部接口"是语义分类，指不进入 SDK、由受信实现实现的接口，与 Go 的 `internal/` 目录没有对应关系；它在代码中放在哪个包、怎样装配，以[开发规范 3.1](../development.md#31-核心模块的包结构)为准。）
3. 核心模块依赖公共契约和本模块声明的内部接口；受信实现实现内部接口；只有装配入口知道具体实现，装配入口不写业务规则。
4. 裁决域只创建一个事务上下文，各模块通过内部接口加入。不得提供通用的表访问或万能事件总线绕过写入方。

## 后果

- 可以按部署更换存储实现，而不改业务处理器；每种实现各自通过持久性合同。
- 构建检查要拒绝三类依赖：领域代码导入数据库驱动；插件导入内部存储接口；平台直接写任务等模块的私有记录。
- 受信实现和装配入口的目录名在 M1 代码骨架时确定，本 ADR 只固定依赖规则。（后续：目录已由 [ADR 0004](0004-language-and-stack.md) 和[开发规范 2](../development.md#2-目录骨架)确定。）

## 考虑过的备选

- **保持原 R6，把存储实现也放进 `core`。**每换一种存储都要改核心模块，且领域代码会直接依赖驱动。放弃。
- **为每条记录生成一层只做转发的 Repository。**增加代码量，不减少调用者需要知道的内容。放弃。
