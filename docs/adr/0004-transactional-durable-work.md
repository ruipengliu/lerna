# ADR-0004：用本地事务共同提交事实与持久工作

业务记录已提交但后续工作只存在于内存，会在崩溃后丢失责任。因此，默认使用 PostgreSQL 短事务和 JobStore，将声明为同库的领域变更、原命令回执和必要 Job 共同提交；设备执行账本采用 SQLite。通知只加速唤醒，数据库扫描负责遗漏通知后的恢复。

公共 `accept`、`work` 模板统一原键去重、暂时领取和条件提交，领域模块保留发送、核对与关闭阶段。Command 回执一经提交保持不变；提交未知时查询或重传原命令。Job 完成只推进到本次领取的修订，不能覆盖并发新增的工作；过期 epoch 的 worker 不得提交受控数据库事实。

默认采用权威关系记录加追加观察与审计，不要求从全量事件重放重建所有状态。事务范围必须由宿主明确声明，网络、模型和大文件上传放在事务外；不同 owner 同机运行也不自动共享 Tx。租约与 epoch 不能阻止不检查它们的外部目标产生效果，恢复仍需 [效果合同](0005-explicit-effect-uncertainty.md)。

**取舍与代价。** 首版不以独立消息队列、缓存或协调集群保存唯一工作责任，也不把 Temporal、LangGraph 设为全局必需引擎。这样减少部署及端侧适配成本，但需要维护数据库扫描、索引、锁竞争、定时器和故障恢复。第三方组件可以采用其他持久引擎，前提是满足相同公开行为合同。

**重新评估条件。** 实测队列维护、定时器、历史恢复或运维成本不可接受，且替代方案能保留原身份、事务和效果合同，才重新选择引擎。多数模块必须绕开模板时，先收缩模板，不强迫领域阶段适配错误抽象。

**依据。** [共用持久工作机制并保留领域阶段](../architecture/decisions.md#共用持久工作机制并保留领域阶段)、[公共模板](../architecture/runtime.md#两个公共模板)、[领取与完成竞争](../architecture/runtime.md#领取与完成竞争)、[事务与数据库装配](../architecture/data-model.md#事务与数据库装配)。
