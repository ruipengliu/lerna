# 生产分布式为主线，按本地事务范围收敛持久基础设施

单体只作为开发调试装配，生产从首版将 WSS 接入、Orchestrator 应用与工作池分开部署，保留必要的同库短事务。用户确认单地域三可用区、托管优先且不绑定厂商：单区故障下已确认账本 RPO=0、控制与查询恢复目标≤60秒，整地域使用异地灾备；同步提交、备用容量和平台隔离能力的成本由生产部署承担，目标须运行验收。

PostgreSQL 保存各数据库分片的业务事实及持久工作责任，对象存储保存不可变字节；有界数据库扫描保证恢复，可丢通知只加速唤醒。相比立即加入独立消息、缓存和协调集群，这减少跨系统故障交接，但保留数据库领取、维护与扫描成本；只有测量及运维比较证明收益后才增加组件。固定 Orchestrator 是逻辑负责方，不绑定某个进程或永远固定的物理数据库位置。

网关持有端云连接，业务实例退出或内部委托轮换优先重建内部绑定，避免普通服务发布迫使端侧重新握手。原业务决定仍按原命令或对象标识查询，旧流输出隔离，订阅无法证明连续时要求新快照；这引入有限绑定状态和快照恢复流量，不能以保持 socket 宣称业务没有中断。完整方案见[生产部署](../architecture/deployment-production.md)与[存储和中间件](../architecture/storage-and-middleware.md)。

2026-09-28 用户补充：生产接入公司自有平台，项目先预留配置、发现、健康、排空和退出等接入边界；开发阶段使用单体及本机 PostgreSQL 多进程装配，不建设复杂部署设施。开发验收不依赖公司平台就绪，首次生产上线仍须满足本决策的进程分工、耐久、隔离及恢复条件；本机验证不能代替跨可用区实验。
