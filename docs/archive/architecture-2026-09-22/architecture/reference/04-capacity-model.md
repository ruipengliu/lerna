# 附录 04 容量演算与存储预算

本篇维护当前规格；归档链接只用于来源追溯。规范缺口和实质冲突见[设计缺口](../maintenance/open-questions.md)，不能以历史文件覆盖当前条款。

本附录把用户规模换算为连接、任务、模型、数据库和存储需求，再用故障后的剩余能力检查部署余量。它提供一套可复算的教学配置和实际测量的填写入口；部署职责见[4.2 部署、存储与规模扩展](../main/04-engineering/02-deployment-and-storage.md)，恢复资格与处理顺序见[4.3 故障恢复与运行保障](../main/04-engineering/03-reliability-and-recovery.md)。

千万注册、百万日活、十万同时在线及个人用户隔离是已确认目标，依据见[项目目标基线](../../harness-project-goals.md#11-用户规模与最终服务状态)。本篇的行为参数、体量、提交数、保留窗口和单机能力均为教学假设。所有推导结果继承其输入的证据等级，当前没有本系统的实测容量、费用或生产放行结论。

本篇以云侧容量为主，端侧另列。用摘要任务 T 解释记录归属：手机提出任务，电脑执行保存操作 S，以外部作业 J 跟踪保存，再由 R 读回；摘要 D 留在电脑。用于总量演算的“每任务 4 次执行、3 次模型、12 条消息”来自通用负载假设，并非对 T 的真实轨迹计数。

## 1. 先固定输入与计数边界

实际使用时，先确定统计的是顶层任务、某类操作还是某条恢复队列，再固定时间窗与端云位置。随后计算到达率、并发、写入和存量，最后加入故障余量。改变输入时沿这些依赖重算，不能只替换最终实例数。

### 1.1 目标与基准负载

下表沿用[原容量模型](../../archive/architecture-v1/13-distributed-deployment-and-storage.md#1-设计输入与容量模型)。基准按一日 86,400 秒计算，峰值系数作用于相应时间窗内的到达率；计算日增长时使用每日总量，不再乘峰值系数。

| 输入 | 符号与数值 | 状态及口径 |
| --- | --- | --- |
| 注册用户 | `N = 10,000,000` | 已确认规模目标；用于账户、路由及已有数据存量。 |
| 日活用户 | `A = 1,000,000` | 已确认规模目标。 |
| 同时在线用户 | `U = 100,000` | 已确认规模目标；多端连接另乘系数。 |
| 每日顶层任务 | `q = 5` 项／日活用户／日 | 沿用教学值；明确为用户发起的根任务，不含内部子任务。 |
| 峰值系数 | `k = 10` | 沿用教学值；基准假设各任务驱动负载同时达到该系数。 |
| 每根任务执行／模型／可靠消息 | `e = 4`、`m = 3`、`b = 12` | 沿用教学值；基准无委派，排除额外重试、补投、后台处理和多端扇出。 |
| 任务平均活跃时长 | `t_task = 120 s` | 沿用教学值；从接纳到终态，包含等待，用于活跃状态数量估算。 |
| 模型平均占用时长 | `t_model = 8 s` | 沿用教学值；实际发起至调用结束，不含发起前的排队。 |
| 每在线用户连接数／心跳间隔 | `d = 1`、`h = 30 s` | 沿用连接基准；手机与电脑同时在线等情况另测 `d > 1`。 |
| 单层执行记录／示例保留窗 | `1 KiB`／`30 天` | 沿用教学值；只是一个记录层，保留窗须满足实际恢复和数据策略。 |

本篇使用 `1 KiB = 1,024 B`、`1 MiB = 1,024 KiB`、`1 GiB = 1,024 MiB`、`1 TiB = 1,024 GiB`。带宽若换成 bit/s，要再乘 8；云服务的十进制计费单位另作换算。数值先用未舍入输入计算，最后显示近似结果。

### 1.2 云侧、端侧和共同记录分别计算

以下教学假设固定各类工作的处理位置，使后续预算可以分别计算云侧和端侧消耗。比例不表达用户授权；实际比例必须从获准轨迹测得。

| 分配对象 | 本篇教学配置 | 对计算的影响 |
| --- | --- | --- |
| 顶层任务的 Owner | 云侧比例 `p_owner = 1` | 基准根任务的运行状态与工作均在云侧；端侧 Owner 分支另算。 |
| 模型请求 | 云模型比例 `p_model = 1` | 基准模型额度全计云模型；本地推理需另测端侧计算与内存。 |
| 执行操作 | 云侧比例 `p_exec = 0.25`，端侧 `0.75` | 按执行权威的位置分配 ExecutionStore、执行提交和资源占用。 |
| 可靠消息 | 一半云↔云、一半云↔端 | 每条消息各有发送 Outbox、接收 Inbox；平均云侧 `1.5` 份、端侧 `0.5` 份记录。 |
| 任务正文 | 每根任务另产生 `32 KiB` 获准云侧暂存正文 | 按明确获准的副本计量；受限原文不进入该数字。 |

云侧推进 T 时，仍需要保存端侧操作 S 的映射、结果引用和交接责任；电脑另外保存 S／J 的执行事实。这是两个位置承担不同责任的记录，存储按实际份数累计，业务操作计数仍只有一个 S。Owner 比例也不能代替模型、执行、正文各自的位置比例。

以下计数约定贯穿各表：

- 顶层任务、子任务和后台作业各有独立入口。每个调用、事务和字节按实际责任归入一个明细项；父任务的汇总数若已含子任务，便不再追加同一批子任务消耗。
- `b` 计一次从发送方到接收方的逻辑可靠消息。原消息补投增加传输及去重查询，不自动新增业务操作；广播给新增接收者则增加相应交付责任。
- 消息条数、Inbox／Outbox 记录份数、事务提交数分别计算。随业务一起提交的 Outbox 已在那次事务中，不另加一次提交。
- 120 秒、8 秒和“到达率 × 平均时长”只支持相应稳定窗口的估算。实际报告同时记录长尾、排队、长期等待及未知在途；等待任务无需各占一个常驻 Worker。

<a id="rates"></a>
## 2. 从每日任务推到模型配额与工作能力

### 2.1 基准到达率

令 `n_root_day = A × q` 为每日根任务数，`λ = n_root_day ÷ 86,400 × k` 为峰值根任务到达率。基准没有额外拒绝或积压，假设这些到达均可接纳并按声明流程推进；过载时须分别报告到达、接纳和完成速率。

| 负载 | 推导 | 教学结果 |
| --- | --- | --- |
| 根任务 | `n_root_day = 1,000,000 × 5` | 5,000,000 项／日；平均 `57.87/s`，峰值 `578.70/s`。 |
| 活跃根任务状态 | `λ × 120` | 约 69,444 份；包含等待，另列超出基准时长的未决集合。 |
| 执行操作 | `n_root_day × 4`；`λ × 4` | 20,000,000 次／日；峰值 `2,314.81/s`。 |
| 云侧／端侧执行 | 上项分别乘 `0.25`／`0.75` | 云侧 5,000,000 次／日、`578.70/s`；端侧合计 15,000,000 次／日、`1,736.11/s`。 |
| 模型请求 | `n_root_day × 3`；`λ × 3` | 15,000,000 次／日；峰值 `1,736.11/s`。 |
| 模型在途 | `λ × 3 × 8` | 约 13,889 次调用；调用结束未知时保留相应占用。 |
| 可靠消息 | `n_root_day × 12`；`λ × 12` | 60,000,000 条／日；峰值 `6,944.44/s`。 |

端侧合计表示许多设备上的工作总量。它不能直接换成一个云执行池，也不能证明任意一台手机或电脑能承接其中的热点流量；单端仍受 CPU、内存、I/O、前台资源串行和授权范围约束。

### 2.2 token 与费用需要另一本账

本节假设每次模型调用平均输入 6,000 token、输出 1,000 token。基准使用一种计量口径，不计缓存折扣；它不代表某个供应商的实际限额或计费方式。RPM 表示每分钟请求数，TPM 表示每分钟 token 数，输入与输出分别计量。

| 维度 | 推导 | 教学结果 |
| --- | --- | --- |
| 每分钟请求 | `1,736.111… × 60` | 约 104,167 RPM。 |
| 输入 token 速率 | 请求率 × `60 × 6,000` | 625,000,000 token／分钟。 |
| 输出 token 速率 | 请求率 × `60 × 1,000` | 约 104,166,667 token／分钟。 |
| 每日输入／输出 | `15,000,000 × 6,000`／`× 1,000` | 900 亿输入、150 亿输出 token／日。 |

若相应供应商配置分别给出请求、输入 token、输出 token 和在途限额，安全请求率的估算上界为：

```text
模型请求率上界 = min(
  可用 RPM / 60,
  可用输入 TPM / (60 × 平均输入 token),
  可用输出 TPM / (60 × 平均输出 token),
  可用在途槽 / 平均调用占用秒数
)
```

“可用”指扣除其他工作、未知占用和所需余量后，当前池可使用的份额。实际 Adapter 按供应商声明的窗口、合并／独立 token 计量和预留规则映射这些维度；平均 token 用于规划，单次准入按适用的保守预留执行。请求、token 或费用任一维度不足，都要排队、限制新接纳或明确拒绝。多个 Cell 共享同一供应商额度时，其总分配仍受同一上限约束。

令输入、输出单价分别为 `P_in`、`P_out`，单位均为货币／百万 token，则本例模型日费用为 `90,000 × P_in + 15,000 × P_out`。实际账单单列缓存、其他计费项、失败调用和未知待结算费用，并附供应商、日期与价格来源。每成功交付任务成本使用同一任务集合的全部消耗除以实际成功交付数量，保留失败和恢复消耗。

### 2.3 Worker 与外部等待分开测量

持久工作池要测每根任务产生的可领取轮次数 `a`、每轮本地 CPU 时间 `c`、内存及持有处理槽的时长 `w`。在相同工作混合下，`λ × a × c` 给出 CPU 秒／秒需求，`λ × a × w` 给出处理槽占用估算；实例数再除以单实例的实测安全能力，并加入故障余量。外部等待能否释放处理槽由实现决定，8 秒模型占用不能直接当作 8 秒本地 CPU。

这些变量要覆盖上下文组装、工作领取、授权、结果处理和序列化。基准没有提供这些耗时，报告模板保留待测项；完整机器规格与 Worker 数量须据此补齐。设备 GUI 的单资源串行限制和本地模型推理能力另列，增加云 Worker 不改变该限制。

## 3. 连接、网关和缓冲怎样预算

### 3.1 先按连接与故障后的余量计算

连接总量为 `C = U × d`。单实例在声明消息率和时延下的连接能力为 `c_conn`，目标利用率为 `u`，故障后存活比例为 `s`，连接维度的实例下界为 `ceil(C ÷ (c_conn × u × s))`。

使用教学输入 `c_conn = 5,000`、`u = 0.6`，并假设应用实例均衡分布于三个可用区，损失一区后 `s = 2/3`：

| 在线连接场景 | 原始下界 | 均衡分布于三个可用区 |
| --- | --- | --- |
| 每用户一个连接，`C = 100,000` | `ceil(100,000 ÷ 2,000) = 50` | 向上取 51 个实例，每区 17 个。 |
| 每用户两个连接，`C = 200,000` | `ceil(200,000 ÷ 2,000) = 100` | 向上取 102 个实例，每区 34 个。 |

5,000 连接／实例尚未实测，上表只完成连接这一维的推导。最终实例数需同时满足消息率、带宽、TLS 握手、文件描述符、缓冲和 CPU 限制，并核对逐区放置后的实际存活量。若单实例能力已经含目标余量，不再重复折减；模型供应商等共享限额也不能随应用副本增加而倍增。

### 3.2 心跳、消息与内存另算

| 项目 | 教学输入与计算 | 结果及范围 |
| --- | --- | --- |
| 心跳 | `100,000 ÷ 30` | 约 3,333 组往返／秒；请求与响应各一帧时约 6,667 帧／秒，不逐条写业务数据库。 |
| 经过网关的可靠消息 | 基准云↔端占一半，`6,944.44 × 0.5` | 约 3,472 条／秒；基准每条只有一个目标端点。 |
| 可靠消息载荷带宽 | 新增平均线上大小 `2 KiB`，上项乘大小 | 约 `6.78 MiB/s`，为双向载荷合计；链路收发方向、协议与 TLS 开销另计。 |
| 每连接缓冲 | 新增上下行合计上限 `64 KiB` | 十万连接约 `6.10 GiB` 缓冲预算；不含连接对象、TLS、运行时、缓存及进程基础内存。 |

逻辑流在连接上复用，不必各占一条物理连接。token 预览、临时进度、控制回执和额外订阅扇出按各自速率与大小追加；可靠、可合并和临时消息采用[3.4 端云协同与离线运行](../main/03-coordination/04-edge-cloud-coordination.md#4-连接中断后哪些消息需要补齐)的不同恢复方式。慢客户端达到缓冲上限时执行背压、合并或关闭连接，可靠责任继续由持久记录承接。

扩容主要承接新连接，已有长连接不会自动均摊；缩容、可用区故障和重新认证必须连同[重连场景](#reconnect)验证。数据库连接池另有总预算，不能一条客户端连接占一个数据库连接。

## 4. 事务次数、写入字节与 WAL 分别推导

### 4.1 一次业务操作会跨越几次局部提交

以下提交次数是教学输入，按互不重叠的事务集合归类。每类实际次数须从提交追踪取得，不能根据方法名或表行数猜测。原子组仍遵守[附录 01](01-data-model.md#atomic-retention)；端云及跨 Store 的独立提交分别计数。

| 提交类别 | 教学次数 | 每根任务的云侧提交 | 每根任务的端侧提交 |
| --- | --- | --- | --- |
| 运行状态、工作、预算、领取与随附 Outbox | 云侧 `10` 次／根任务 | `10` | `0` |
| 执行与资源控制 | `4` 次／执行操作 | `4 × 4 × 0.25 = 4` | `4 × 4 × 0.75 = 12` |
| 额外消息接收、消费、发送进展 | 扣除已合并提交后，平均云侧 `1.5`、端侧 `0.5` 次／消息 | `12 × 1.5 = 18` | `12 × 0.5 = 6` |
| UI、授权与获准记忆变更 | 合计 `3` 次／根任务 | `3` | `0` |
| 独立诊断元数据写入 | `1` 次／根任务 | `1` | `0` |
| 合计 | 业务权威记录云侧 `35` 次，诊断另 `1` 次 | `36` | `18` |

这里的消息提交次数与记录份数恰好取相同均值，是两个独立教学输入；批量接收、业务合并提交及耐久确认会改变前者。查询原操作本身还可能触发耐久确认事务，须从实际路径补入，不能只计作裸读取。

另外假设每天接纳 500 份外部评测报告，每份一次云侧提交；报告生成工作属于另行计量的评测资源池。该报告接纳负载也按峰值系数 10 演算。于是：

```text
云侧业务提交 = 5,000,000 × 35 = 175,000,000 次/日
云侧全部示例提交 = 5,000,000 × 36 + 500 = 180,000,500 次/日
云侧峰值提交率 = 180,000,500 / 86,400 × 10 ≈ 20,833.39 次/秒
其中业务权威记录 ≈ 20,254.63 次/秒
端侧提交合计 = 5,000,000 × 18 = 90,000,000 次/日
```

基准将已有账户、目录和配置作为存量；新增登记、独立 UI 输入、管理变更、后台处理和故障核对按[增量表](#increments)追加。上述云侧合计可跨多个独立存储池，不能将其理解为一张全局队列表或共同事务。

### 4.2 更新流量不等于数据净增长

新增教学假设：每次云侧提交平均产生 `4 KiB` 表与索引修改字节，WAL 生成量为该修改量的 `1.5` 倍。前者包含原位更新和索引修改，后者是独立测量指标；此处的字节不等于设备实际 I/O，也不等于新增记录大小。

| 维度 | 计算 | 教学结果 |
| --- | --- | --- |
| 表与索引修改流量 | 云侧提交次数 × `4 KiB` | 约 `686.65 GiB/日`；峰值 `81.38 MiB/s`。 |
| WAL 生成流量 | 上项 × `1.5` | 约 `1,029.97 GiB/日`；峰值 `122.07 MiB/s`。 |
| 一小时峰值的本地 WAL 空间 | `122.07065… MiB/s × 3,600` | 单份数据库合计约 `429.15 GiB`；是本例空间预留窗口。 |

一天中的一小时峰值与其余时段共同构成每日轨迹，全天并非始终按峰值运行。一个小时也不是允许直接删除 WAL 的期限：复制、归档或备份需要更早的位置时继续保留并限制新负载。[4.3 故障恢复与运行保障](../main/04-engineering/03-reliability-and-recovery.md#5-大量任务同时恢复时怎样避免再次压垮系统)说明空间压力下的处置。

一主两备复制同一份数据。表修改、WAL、复制网络、归档网络和存储占用分别报告，不把三个副本算成三倍业务写吞吐；重建副本、备份扫描、检查点与索引整理还会增加 I/O。IOPS、fsync 延迟、热索引命中和跨区同步等待必须在实际布局上测量。

### 4.3 读取与数据库连接同样可能成为瓶颈

按访问路径分别填写 `业务到达率 × 每次访问数`，覆盖任务列表、工作领取、上下文／记忆、权限／路由、原操作查询、消息补读和后台扫描。缓存命中率要附新鲜度与授权条件；缓存失效时的回源峰值单测。副本缺记录不能用于证明操作未接纳，当前权限、额度和操作接纳仍按所属权威读取。

每分片连接池上界为所有客户端服务实例的最大连接数之和，另留控制、核对、复制和运维所需份额。扩 Worker 或 Gateway 前先重新求和；并发事务也可用“事务率 × 平均持有连接时间”估算，再测长尾和锁竞争。报表中的连接预算不得以短平均事务掩盖阻塞事务或恢复期间的占用。

## 5. 按数据族建立云侧主账和端侧分账

### 5.1 先算单份逻辑存量

下表补齐本篇的教学数据配置。当前记忆、授权、UI 和预算按预测时点的存量估算，假设本例预测窗内当前集合大小稳定；其历史变化另计。实际新增长期记忆、账户和关闭水位需要单列增长曲线。

全系统单层执行记录按“每天 2,000 万操作 × 1 KiB ≈ 19.07 GiB”计算，30 天约 572.20 GiB。本表只计云侧四分之一，即 143.05 GiB；其余约 429.15 GiB 在端侧。云侧操作映射是另一份责任记录，另外列项。

### 5.2 加上索引、复制、WAL、备份和迁移空间

新增教学输入：数据库表页、索引与空间开销合计为逻辑数据的 `1.5` 倍；每个数据库数据集保留三份副本；迁移与重建临时空间取三份当前占用的 `20%`；磁盘规划利用率为 `75%`。这些比例分别处理布局、复制、临时重叠和剩余空间，不能合成一个含义不明的“安全系数”。

令单份本地 WAL 预留 `W = 429.15 GiB`，其推导见[数据库写入](#database)，则：

```text
单份数据库占用 P = 1.5 × L + W ≈ 3,333.97 GiB
三副本、迁移余量与磁盘水位下的总空间
  = 3 × P × 1.2 / 0.75 ≈ 16,003.04 GiB
```

这是云侧各数据库池的合计空间下界。身份／归属目录、业务分片和观测评测仍按各自故障范围放置；各池的实例数、卷规格及取整分别计算。该合计不是一台数据库或一种物理布局的容量结论。

数据库外的教学预算如下。各行已列明自身副本和开销，不再统一乘数据库的三副本系数。

| 存储池 | 教学配置及计算 | 结果与口径 |
| --- | --- | --- |

本配置只为在线位置启用缓存，未启用诊断正文采集；其他缓存、正文调试和额外对象历史版本在启用前另填增量。检索窗口只描述这批投影条目，不决定原长期记忆的保留期；对象暂存比例也不授予更长的正文保存权限。

备份基线、WAL 归档和对象版本需要组成可恢复的时间范围。上表假设备份目录能使用这些材料恢复到声明位置，实际须验证基线年龄、连续 WAL 和全部受控对象引用，独立报告缺口；“两份基线＋一天归档”本身不能证明恢复目标。对象池的容量预算与底层物理磁盘字节属于不同层次，费用估算按对应服务的计量口径展开。

### 5.3 端侧按设备与用户另算

端侧总执行层为 `15,000,000 × 1 KiB ≈ 14.31 GiB/日`，消息接收／发送元数据为 `60,000,000 × 0.5 × 1 KiB ≈ 28.61 GiB/日`。它们分散于设备，端侧备份、SQLite 文件布局和本地索引按实际实现附加，不采用云侧 PostgreSQL 的放大系数。

用一个**每天持续发起 5 项任务的用户**演示单用户量级，假设相关端侧工作集中在一台电脑：

<a id="placement"></a>
## 6. 用最紧的资源约束推导 Cell 与分片

一个用户的原子组须完整落在所属事务分区。分片上限取决于相同混合负载下的提交、读写 I/O、热索引、存量、WAL／复制带宽、连接池和恢复扫描；对每个维度求所需分片数，再取最大值，最后按用户分布检查热点。

下面只计算业务分片，身份／归属目录和观测评测单列资源池。业务负载为 `175,000,000` 次提交／日、峰值 `20,254.63/s`。从上一节总逻辑存量中扣除账户／目录 `19.07 GiB` 及诊断／评测 `290.39 GiB`，业务逻辑存量约为 `1,627.07 GiB`；加布局系数与自身一小时峰值 WAL 后，单份约 `2,857.84 GiB`。

| 维度 | 新增教学能力假设 | 分片下界 |
| --- | --- | --- |
| 业务提交 | 每分片在单可用区故障后仍可持续 `2,000/s`，目标利用率 `60%` | `ceil(20,254.63 ÷ 1,200) = 17`。 |
| 数据与本地 WAL | 每份副本卷 `512 GiB`，磁盘水位 `75%`，迁移重叠 `20%` | `ceil(2,857.84 × 1.2 ÷ (512 × 0.75)) = 9`。 |
| 读取、热索引、复制、连接、恢复 | 没有现成实测上限 | 按各自峰值需求除以可用能力，结果可能使分片数继续增加。 |

2,000 次／秒是教学输入，尚未在同步提交、切换和对应读负载下验证；因此 17 只是已赋值维度的下界。数据库的能力假设已经使用故障后口径，不再机械乘一次 `2/3`；网关的 `2/3` 则反映应用实例真的损失了三分之一。

进一步假设采用四个 Cell 且用户负载均匀，每个 Cell 约 25 万 DAU、2.5 万在线，业务峰值约 `5,063.66` 次提交／秒。每个 Cell 向上取五个分片，共 20 个分片；每分片一主两备，共 60 个数据库实例。若每份副本使用前述 512 GiB 卷，仅业务卷即分配 `30,720 GiB`。提交维度和固定卷规格造成的取整，会使实际分配超过聚合空间下界。

此例没有确定物理主机数、CPU、内存或其他资源池规格。各 Cell 均须验证单区损失、备份与恢复叠加时的能力；失去整个 Cell 时，该 Cell 的用户依恢复流程等待或受控迁移，其他 Cell 的空余容量不自动产生任务拥有权。共享身份、目录和模型供应商仍有独立的共同故障范围。

### 热点用户不能用平均分片数消掉

沿用《部署、存储与规模扩展》的正常用户 A 与批量用户 B。若 B 一人提交 `100` 项根任务／秒，按本例会产生 `3,500` 次业务提交／秒，已超过单分片 `1,200/s` 的规划份额。即使整个 Cell 尚有空闲，该用户也可能持续积压。

先按用户控制到达率、公平领取并限制增长。若其他用户在同一分片已占用 `W_other` 次提交／秒，B 在这一维的份额上界为 `(1,200 − W_other) ÷ 35` 项任务／秒，仍须满足模型、存储与端侧约束。迁到独立分片只能移除与其他用户的竞争；它不会把同一分片的处理能力从 1,200 自动变为 3,500。更高能力需重新验证，原子组不能为了均摊而任意拆开。

<a id="backlog"></a>
### 7.3 积压只有在剩余处理能力为正时才会缩小

设某恢复队列已有积压为 `B`，同类新工作每秒增加 `λ_new` 项，该队列每秒实际处理并完成责任交接 `μ` 项。在工作构成与速率稳定时，队列每秒净减少 `μ − λ_new` 项，因此清空时间约为 `B ÷ (μ − λ_new)`。只有 `μ > λ_new` 时，积压才会持续缩小。

沿用[《故障恢复与运行保障》的独立演算](../main/04-engineering/03-reliability-and-recovery.md#5-大量任务同时恢复时怎样避免再次压垮系统)：`B = 30,000` 项、`μ = 300` 项／秒、`λ_new = 200` 项／秒，约需 300 秒。这里计的是这条队列的同类工作项，未把全系统根任务到达率改为 200／秒。若处理率降到 220／秒，清空约需 1,500 秒；若不超过 200／秒，则持续到达下无法清空。

`μ` 是分配给这条队列的总有效处理率，已扣除其他资源池的占用，并受最慢依赖约束；同队列新增工作已通过 `μ − λ_new` 扣除，不再减一次。异质工作的项数需分组或按实测服务需求换算；未知效果、外部未停止和授权不满足的工作单列，不能靠出队或丢弃把它们记作完成。长时间中断还会增加 Inbox／Outbox、回执、WAL 和对象的实际保留量。

清空时间不包含故障检测、权威恢复、等待外部效果和最终用户交付。RTO 需定义业务恢复终点，RPO 需明确故障模型及取得耐久确认的写入范围，沿用[生产恢复断言](03-state-and-failure-matrices.md#operations)；容量演算不扩大这些保证。

<a id="retention"></a>
## 8. 保留窗口必须与恢复责任一起预算

为每个数据族填写“正常保留量＋超过正常窗口仍未履约的量＋清理传播中的量”，并核对这些集合不重复。容量模型中的窗口是一项输入；实际可否删除仍由所属模块的状态与策略裁决。

| 数据族 | 窗口或清理前提 | 容量报告必须保留的量 |
| --- | --- | --- |
| 活跃任务、工作与执行事实 | 工作结束且相关恢复、核对和控制责任已履行；未知效果不能按天数消失。 | 各状态数量、最老年龄、在途占用及超窗未决量。 |
| 操作／提交回执与接纳窗口 | 先持久关闭窗口，再确认恢复义务结束，最后清理明细；旧身份仍可被明确拒绝。 | 有效账本、超窗待处理明细、窗口／流世代及关闭水位的长期增长。 |
| Inbox／Outbox 与消息代理 | 各自确认位置及业务交付责任满足；代理日志期限不替代未结交接。 | 已接收、未消费、待交付、最老缺口及唯一载荷位置。 |
| 记忆修订、墓碑与派生索引 | 副本已应用，或旧同步世代已关闭且重返需重建；当前来源和用途仍有效。 | 当前记录、历史、删除积压、覆盖水位与尚未清理的副本／索引。 |
| 正文、截图与产物 | 分别满足用途、驻留、有效引用及删除要求；暂存、历史版本、备份分别推进。 | 当前对象、孤儿、旧版本、合法保留与删除传播量；端云分列。 |
| WAL 与备份 | 仍能覆盖声明恢复位置；复制、归档及对象依赖完整后按策略清理。 | 最早需要的位置、生成率、滞后、基线年龄及恢复缺口。 |
| 诊断与评测 | 诊断元数据 30 天，获准诊断正文最多 7 天；评测／发布报告及允许的最小证据元数据 90 天。 | 元数据与正文分别计量；私有评测正文默认不复制，必要副本最多 7 天且服从更短授权。 |
| 旧实现、Schema 与扩展资产 | 原工作、结果核对或获准回滚不再依赖它们，才可按策略清理。 | 在途版本数量、依赖资产、镜像／缓存与归档体量。 |

观测评测期限来自[《评测、比较与发布》的既定配置](../main/04-engineering/04-evaluation-and-release.md#7-谁能批准改进证据怎样留存)，其余完整规则见[附录 01 的保留表](01-data-model.md#retention)与[附录 03 的清理水位](03-state-and-failure-matrices.md#retention)。本篇不设覆盖所有记录的统一 TTL，也不因转入冷层而取消原操作核对入口。

磁盘告警要结合剩余时间：在相同数据池中，若净增长率 `g` 为正，则“距离安全水位的剩余字节 ÷ g”可估算可处置时间。净增长应纳入实际清理能力、复制／归档阻塞及恢复流量；不能假定到期记录都会及时删除。水位、扩容提前量与重新开放条件由基准试验提出并冻结，教学中的 60%／70%／75%／80% 不自动成为运行告警配置。

<a id="report"></a>
## 9. 用实际轨迹替换假设并提交容量报告

实际报告以同一候选版本、拓扑、负载轨迹和故障范围为单位。每个输入都带数值、单位、采样窗口、位置／任务范围、来源和状态；无法取得的值写“待测”，不填零。下面的字段是报告模板，不是新增公共协议或实现 Schema。

| 输入组 | 必填内容 | 当前状态 |
| --- | --- | --- |
| 候选与环境 | 代码／配置版本、Adapter 与数据库版本、CPU／内存／磁盘／网络、区域和可用区、实例及分片放置。 | 实现与具体测试环境待填。 |
| 用户与任务 | 注册、DAU、在线、多端分布；根任务与子任务计数；日轨迹、峰值窗口、任务类别及实际接纳率。 | 规模目标已定，行为分布待测。 |
| 位置与权限 | Owner、模型、执行、消息及各类正文的端云比例，数据驻留、用途和允许副本。 | 本篇比例为教学值。 |
| 调用与处理 | 各类操作／查询／模型次数、输入输出 token、占用与排队分布、Worker CPU／槽位、设备串行约束。 | 既有及新增教学值待替换。 |
| 配额与费用 | 各供应商和各池的 RPM／TPM／并发份额、未知预留、价格来源与日期、失败及恢复成本。 | 实际配额与单价待填。 |
| 连接与读取 | 单实例混合连接能力、消息大小与扇出、缓冲、握手、补读、缓存命中与回源、逐分片连接池。 | 上限及故障期间表现待测。 |
| 写入与净增 | 不重叠的提交分类、表／索引修改、WAL、设备 I/O、逐数据族的新增、更新、删除和存量。 | 教学预算与实测分栏。 |
| 生命周期 | 正文及元数据保留、超窗未决量、水位增长、备份／对象版本、索引清理和实际回收速率。 | 保留规则既定，体量与完成时间待测。 |
| 故障与增量 | 单区损失、热点用户、重连、后台、子任务和 GUI 占比；积压初始集合、恢复份额及停止条件。 | 演练计划须冻结后执行。 |

逐资源的结果使用同一行式记录，至少包含下列维度：

| 结果字段 | 填写要求 |
| --- | --- |
| 需求与供给 | 正常／故障后的需求，单实例或单分片能力，已扣除的份额与余量，计算下界、取整及最终放置。 |
| 业务表现 | 到达／接纳／完成／拒绝速率，队列长度与年龄、P50／P95／P99、原任务首次有效推进与最终交付。 |
| 资源表现 | CPU、内存、磁盘和增长率、I/O／WAL、连接、带宽、模型配额及每个池的未知占用。 |
| 安全余量 | 约束最紧的维度，单区损失后的可用能力，恢复与正常流量共同占用，扩容或背压触发条件。 |
| 数据与责任 | 原操作、已完成步骤、未决效果和交接缺口；账户隔离、当前权限、清理水位及 RPO／RTO 适用范围。 |
| 证据与结论 | 原始轨迹／指标／故障注入记录、可复现命令、配置、未覆盖范围；分别记录推算、实测和验收判断。 |

测量时先用单实例、单分片定位各资源瓶颈，再在相同候选拓扑中运行任务、记忆、UI 与恢复混合负载，叠加热点用户和单区故障。全量测试同时覆盖千万账户元数据、百万 DAU 日轨迹、十万在线及多端放大；某一维通过不替代其他维。分片查询计划、热索引、复制与恢复扫描须随增长后的数据量重新核对。

[4.2 部署、存储与规模扩展](../main/04-engineering/02-deployment-and-storage.md#7-怎样证明部署方案满足目标)已有局部时延建议：正常在线、单区域、额度可用且未背压时，提交至 `ACCEPTED` 的 P95 ≤ 300 ms，业务提交至网关发出更新的 P95 ≤ 1 s。报告同时列出条件之外的请求、排队、模型、外部执行及公网端到端耗时；这些建议尚非实测 SLA。恢复门槛按《故障恢复与运行保障》由首轮基准提出并冻结，正式验收配置与追溯见[附录 05](05-validation-profiles-and-traceability.md#production)，教学值不自动成为验收阈值。
