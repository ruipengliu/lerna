<a id="records"></a>
## A. 记录责任与覆盖

记录分为三层，保存责任和完整性要求不同：

| 记录 | 由谁负责 | 丢失或滞后时怎样处理 |
| --- | --- | --- |
| 业务权威事实 | 原模块保存任务、执行、授权、记忆及版本事实。 | 原子提交失败按该模块规则阻止新变更；观测系统不能补写业务成功。 |
| 正式评测证据 | 评测侧保留首份提案、全部尝试、操作事实、效果与评分依据的受控引用。 | 必需证据不能按临时 Trace 采样；无法判定时明确报告不完整。 |
| 诊断视图与临时信号 | Observation 汇集可查询记录、指标及调用轨迹（Trace）。 | 关键来源可补投、去重和重建；临时性能信号可采样，须标明丢失与覆盖。 |

观测沿已有任务、操作、主体作用域、节点、版本和因果关系关联记录，来源身份经验证。持久变更按来源位置与项次去重；跨端墙钟或 Trace 展示顺序不决定业务先后。`GetCoverage` 分别报告来源接纳位置、投影应用位置、采样和不可恢复缺口，查询无结果不代表没有动作。

开发期使用 SQLite 诊断索引和受控文件即可，观测后端通过 Adapter 替换。诊断导出失败不把已确认的业务成功改成失败；是否具备评测或发布证据则另行判断。

<a id="statistics"></a>
## B. 配对比较方法及失效条件

正式比较还要处理样本相关性。同一意图的两种表达不能当作两个完全独立来源：既定方法按 API 分层，每次把整个意图／状态族及两侧配对结果一起重采样，保持 API 权重和族内变体，计算差值区间。参考配置为 10000 次重采样、固定并记录随机种子、双侧 95% 百分位区间；推断范围限于当前目录及计划所定义的任务分布。

该方法须先做统计仿真和边界验证。来源族不独立、存在未处理的跨 API 相关，或小样本与高成功率导致推断失效时，标为 `INFERENCE_UNAVAILABLE`，只报告固定集得分；不能改用逐行独立的计算来获得一个看似有效的区间。

<a id="retention"></a>
## C. 证据保留期限

首版保留配置为：诊断元数据 30 天，获准诊断正文最多 7 天，评测／发布报告及允许的最小证据元数据 90 天。私有评测正文默认不复制，必要副本最多 7 天并服从原授权更短期限；公开非私有夹具可随版本保留。这些期限不清理任务恢复、原操作去重和授权消费所需的权威记录。

<a id="persistence"></a>
## D. 接口、持久化与通知

Evaluation 与 Evolution 各自经内部 Store 保存状态及待交接责任，事实记录与输入内容引用分开，默认不复制完整运行数据库。提交结果未知时查询原提交，管理操作沿稳定身份恢复；方法与 Store 入口见[接口目录](02-api-and-message-catalog.md#evaluation-service)及[组件接口](02-api-and-message-catalog.md#component-interfaces)。

Observation 查询同时限制分页和范围，原始任意遥测不作为端云必需的可靠业务流。动态指标和评分结果使用登记 Schema；完成、失败和发布变更沿既有 Exchange 通知，查询可补读当前快照。遥测缺失须报告覆盖，不能改写业务事实或将无证据视作通过。
