# 示例 3 · 外部效果与恢复

这组分支分别丢失启动回执、处理进程、数据库可写权威或手机呈现反馈。它们未知的事实不同，查询入口也不同。目标始终是保存、读回核验并交付摘要；不能统一处理成重新生成和保存。

## 1. 电脑可能已写入，启动回执丢失

起点是 S／R 已准入且 S 的调用可能发出，J 的回执没有收到。工具在故障发生前已声明可按原幂等键或可靠业务关联核对，执行系统保留原身份和固定输入。这里没有临时更换工具或新增其不支持的保证。

执行系统先查原 S 的启动与外部关联，再按已声明能力查原结果。确认是本次保存成功后，保存找回的作业关联或可核对结果，并补齐效果记录及结果报告，内核据此继续已准入的 R。若只是发现同名文件，仍不能证明本次 S 已生效；需要新的取证动作时，该动作也要通过准入。

若记录覆盖不足，或旧请求仍可能执行，就保留未知。只有证据足以确认未发出，或目标端仍有效的幂等保证与当前条件允许时，才按原操作契约再次发送。无法核对时不能新建一次保存绕过未知。详细分支见[执行核对](../main/02-subsystems/04-tools-and-devices.md#4-保存已经启动作业号却丢了怎么办)。

## 2. 外部作业继续运行，云侧 Worker 退出

起点改为 S／R 已准入，电脑已经持久保存 S 与 J 的关联，J 仍在进行；云侧 Worker 退出，权威数据库完好。两份资料获准在任务范围内进入云侧，原材料、固定实现、核对依据及当前授权、控制、期限和预算均允许继续。这个分支不继承原文留端限制。

新 Worker 取得有效领取，从 RunStore／WorkStore 找到任务进展和未决责任，经执行系统查询原 S；电脑协调器沿 J 调用 Driver 核对。模型无需重新生成 D，执行端也不重新启动保存。确认成功后回报原结果，内核推进 R 和手机交付。

若旧 Worker 迟到，旧领取不能直接更新任务；其带来源报告由当前合格处理者核对。租约过期不证明旧调用已停止。可观察结果是原任务、原操作与原作业继续关联，已完成工作未重复。依据见[原任务恢复](../main/04-engineering/03-reliability-and-recovery.md#2-处理进程退出后摘要任务从哪里继续)。

## 3. 数据库切换发生在派发之前

重新从准入变更 C 在旧主本地可见、同步耐久确认未知且 S 尚未派发开始。生产参考配置使用一主两备、三个可用区和仲裁服务；这是待验证方案，不是已经测得的保证。

扫描器不派发未取得耐久确认的工作。HA 先取得仲裁、候选完整性与旧主隔离证据，再提升合格副本。应用重新连接后按原 change_id 核对 C；确认原记录及耐久条件，再取得当前工作资格、复核控制与权限，才允许派发原 S。

若查不到 C，须进一步确认旧请求无法继续提交及恢复记录覆盖范围，不能直接重做整个意图。无法判定则等待。数据库切换不自动改变任务 Owner 世代，也不接管端侧独立任务。规则见[数据库恢复与派发](../main/04-engineering/03-reliability-and-recovery.md#4-数据库恢复后什么条件下才允许派发)。

## 4. 文件已核验，手机尚未呈现

重新从 S 已成功、R 已读回核验而手机反馈未到开始。保存与内容核验事实仍成立，本例要求的完整交付尚未完成。

交互系统核对原发布操作与显示版本，重连后恢复快照和未决转交。内核取得相应呈现事实后，再核对任务完成条件。补交付不能触发重新保存；手机已呈现也不证明用户已经阅读或同意。

这一分支验证业务完成依据和界面恢复，不能代替手机第三方应用 GUI 专项。相关行为见[应用与交互](../main/02-subsystems/05-interaction.md#surface)。以上过程尚未取得运行或故障演练证据。
