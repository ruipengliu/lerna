# 01 任务运行内核详细设计

本设计规定 Core、Scheduler／Worker、RunStore／WorkStore 的内部组织及默认 Go／SQLite 实现。输入来自[内核架构](../main/02-subsystems/01-runtime-kernel.md)和现行契约；本轮确认了规则集中、目标更新冻结旧工作、单任务单有效决策、人工处置入口和单机有界写入等选择。文档与配套规格是实现基线，尚无运行内核实现或耐久性验收结果。

按下列顺序阅读，接口与表结构分别只维护一份：

| 文件 | 回答的问题 |
| --- | --- |
| 本篇 | 谁处理输入，状态如何变化，一次推进如何提交，故障后如何继续？ |
| [接口与类型](01-runtime-kernel-contracts.md) | 调用顺序、Go 签名、变更类型、错误与版本如何约束实现？ |
| [持久化与调度](01-runtime-kernel-storage.md) | SQLite 怎样保存原子组、领取工作、隔离旧处理者并恢复？ |
| [验证与实施](01-runtime-kernel-validation.md) | 哪些测试证明合同成立，哪些事项仍需实现和测量？ |

本篇覆盖完整的内核运行语义，详写单机默认实现。bbolt、生产数据库、端云移交需要满足相同接口和验收约束；其完整物理实现归各自详细设计。执行端的外部作业查询、资源接管和效果核验仍归 ExecutionCoordinator，不能因为同样使用 Worker 就移入内核。

<a id="structure"></a>
## 1. 内部组织与依赖方向

从一次请求看，调用链是：受信 TaskService／报告入口 → Core 协调层 → 纯规则计算 → RunStore 条件提交。Scheduler 只选候选，Worker 通过 Core 执行一段有限处理；它们不能直接指定任务终态。

[图 1：内核分工与运行原子组](diagrams/runtime-kernel-structure.html)（独立 HTML）展示协调层、纯规则、事务外依赖和持久化单元的调用方向。

| 内部职责 | 输入、输出与封装的复杂性 | 可替换位置 |
| --- | --- | --- |
| Core 协调层 | 验证命令；读取快照；在事务外获取必要授权、来源与能力证明；协调上下文及 Brain；构造受约束提交。 | 对外是一个运行模块；不把每种状态判断做成插件。 |
| 状态规则 | 当前快照、已验证输入、显式时间及分配好的局部键 → 变更计划或拒绝。无数据库、网络、随机数及系统时钟调用。 | 规则版本随内核版本发布；内部可分文件，共享不变量。 |
| 准入检查 | 检查完整提案、精确能力版本、依赖图、权限、来源、预算及旧工作复核清单。 | 调用现有 Authorizer、ContextAssembler、CapabilityCatalog 接口。 |
| 调度策略 | 从有限候选中按工作通道、用户和到期顺序选取，返回有界列表。 | SchedulerPolicy；替代策略仍必须经过存储领取。 |
| Worker | 领取、续租、事务外调用、提交进展或保留核对责任；统一处理提交未知。 | 处理机制可替换，业务规则归 Core。 |
| 运行持久化单元 | 快照、受约束变更、工作领取、Inbox／Outbox 和提交核对；封装锁、索引及耐久条件。 | 同一实例同时实现 RunStore、WorkStore 和运行消息存储端口。 |

`runtime/` 声明调用方需要的接口，`runtime` 内部实现协调与纯规则，`adapters/sqlite/` 实现持久化。适配器可导入规则所需的纯校验帮助函数；内核不导入 SQL、驱动或启动入口。组装器注入存储、授权、上下文、大脑、执行及交互端口、时钟和 ID 分配器。没有实际替换需求的规则检查器保留为内部函数。

纯规则先在事务外形成变更；Store 在短事务内检查规则依赖的版本、资格、控制、期限、额度与唯一约束，再应用变更。不得把事务外检查结果视为永久许可。跨模块授权或来源不具备共同事务：携带有界有效证明及修订，实际处理端再检查当前权限；本地提交无法承诺与远端撤销全局同时发生。

<a id="invariants"></a>
## 2. 实现必须守住的不变量

既有对象、标识和六个任务主状态仍由[对象附录](../reference/01-data-model.md#runtime)维护。以下编号供实现与验证定位内核义务：

| 编号 | 不变量 | 落实位置 |
| --- | --- | --- |
| K1 | 任务变化、相关预算、稳定操作映射、待办、Inbox 消费、必要 Outbox 和回执一次提交。 | RunStore.Commit。 |
| K2 | 一个任务只有当前 Owner 能推进；同一工作只有当前有效领取能提交本轮进展。 | Owner 世代、工作领取代次与活动启动代次分别检查。 |
| K3 | 新提案只能按它读取的任务版本准入。 | 决策领取和预留完成后的版本，不能换成返回时的最新版本。 |
| K4 | 同一任务至多一轮拥有有效准入资格的决策；旧调用未知用量仍占预算。 | 决策局部序号、唯一活动记录、预留账本。 |
| K5 | 操作的目标、参数、能力／实现版本及原始语义不因重规划而改变。 | 不可变操作摘要，KEEP 引用，DROP 留痕。 |
| K6 | 扫描、通知、网络送达和租约过期都不能直接授权外部动作。 | 条件领取、持久派发准备、处理端检查。 |
| K7 | 未知提交查原 change_id；未知效果查原 operation_id。 | 两类恢复各自有入口，禁止用新动作覆盖未知。 |
| K8 | 终态需满足目标／失败／取消证据和在途处置条件，关键效果未知则不终结。 | 统一终态评估；保留实际效果及交付证据。 |
| K9 | 控制、额度、期限、删除与接纳窗口不因重启、换 Worker 或换后端而重置。 | 持久事实、保留水位及迁移合同。 |

任务事实的变化推进 `state_version`；纯领取元数据、续租和重复回执不必推进。决策领取包含预算预留，因此必须推进；普通工作首次领取若同时改变主状态，也推进。任务版本、Owner 世代、Worker 代次、决策局部序号和启动代次各自回答不同问题，不互相替代。

<a id="commands"></a>
## 3. 输入怎样进入同一个规则入口

| 输入 | Core 的处理 | 后续责任 |
| --- | --- | --- |
| Submit | 按受信 namespace、接纳窗口和原操作去重，建立任务、预算与首次工作。 | 首次决策或已确定的输入等待。 |
| SubmitUpdate／ProvideInput | 比较预期版本或消费指定等待项，保存正式输入及来源。 | 目标更新冻结旧目标工作；普通结果输入按依赖触发后续。 |
| Pause／Resume／Cancel／AdjustLimits | 使用现有 TaskService 合同，更新控制来源或限额，保存传播及落实责任。 | 即使目标预算耗尽，也可接纳合法控制；远端落实另行核对。 |
| 执行、子任务、交付报告 | 验证生产者、原操作、报告修订与证据；消费已持久 Inbox。 | 更新事实、结算用量、解除对应依赖或安排决策。 |
| 决策返回 | 对照原决策资格、基线版本及完整提案执行准入。 | 一次提交全部准入记录；不做部分批次成功。 |
| 到期、领取失效、恢复提示 | 读取当前记录，决定核对、重新领取或升级处理。 | 不因为扫描到记录而自动重发外部动作。 |

`Submit` 的唯一接纳检查位于任务创建事务内：即使另一个并发入口拟分配了不同 task key，同一原操作仍只能关联原任务。`ProvideInput` 沿有效 `interaction_id` 消费；新操作争答与原操作重试分开判断。身份与原结果披露权限先于去重返回。

消息先持久接收后再应用时，Inbox 及其消费工作必须原子建立。应用报告时，业务变化、消费标记、后续工作及必要回复一起提交。相同报告修订、不同内容为冲突；较旧修订不覆盖新事实。跨修订的用量按调用／预留的累计值或唯一用量项结算，不能每条报告重复加总。

<a id="decision"></a>
## 4. 一轮决策及其失联恢复

### 4.1 正常生成与准入

1. 先应用一批已持久的正式事实，并优先恢复已经准入的责任。需要新判断时，以唯一活动键登记 DECIDE 工作；连续唤醒合并为一个需要决策标记。
2. 领取 DECIDE，在同一事务分配递增决策序号、预留生成额度、记录固定 Brain／模型／上下文策略版本，形成唯一 ACTIVE 决策。获取提交后的任务版本 `v`。
3. 以 `v` 对应快照组装上下文并在事务外调用 Brain。过程中的模型请求分别计量，不能超出本轮预留和调用限制。上下文来源、准确配置及规范化输入摘要随本轮保存；这些审计元数据不重新改变决策基线。
4. 新事实照常接纳，不能为保住旧提案延迟必要控制或隐瞒结果。旧轮次可请求中止；新的决策唤醒保留为待处理标记。
5. 返回完整提案后做结构和外部证明校验。在 Commit 内复核 ACTIVE 决策序号、工作代次、Owner、`v`、控制及额度。成功时原子固定操作映射、依赖、预留和派发责任，关闭本轮资格并结算已知生成用量。
6. 版本冲突时不接纳任何新操作。把生成用量作为独立幂等事实按最新快照提交，结束旧决策，再按剩余额度安排新轮次。用量未知部分继续保留。

动作／委派／等待／结果四种主提案互斥；格式修复仍属本轮并计预算。计划文字不是持久工作。仅因某项保存仍在进行而查询进度，走执行系统原操作核对，不调用 Brain。

### 4.2 失联并不永久占住有效决策资格

[图 2：失联决策的资格裁决与恢复](diagrams/runtime-kernel-decision-recovery.html)（独立 HTML）展示恢复领取、原准入查询、旧资格退休及重新预留的分支。

恢复者先获得当前恢复领取，在当前唯一可写存储权威上处理原决策。若原准入回执存在，恢复原工作，禁止重新生成。若原准入提交仍可能在旧权威上成功，保持等待并先解决存储权威隔离。

在原提交与撤销能串行裁决的事务中，重新检查回执；仍未准入时把旧决策置为 RETIRED，并撤销原领取资格。该事务与迟到准入竞争同一决策行、任务版本及资格：准入先赢则返回原结果；撤销先赢则旧提案永远失去准入资格。查询一次“未找到”本身不完成这一步。

撤销提交耐久确认后，有剩余额度即可预留新一轮决策。旧供应商调用可能尚未结束，原预留不能释放；迟到结果进入受控报告入口，核对后结算用量，输出不执行。`RETIRED` 表示准入资格结束，不表示物理调用停止或账单已结清。若无法预留新额度，保存预算等待及人工处置入口。

<a id="updates"></a>
## 5. 目标更新后的冻结与保留

### 5.1 冻结边界必须能与派发竞争

正式修改目标、输出要求或约束时，增加 `goal_revision`，它是任务内部的语义修订，不替代 `state_version`。默认冻结所有尚未派发的目标工作；暂停、取消、原结果接收、效果核对、必要处置和重新决策不被这一冻结阻断。只增加事实或改变用量不自动增加 goal_revision。

准入创建 Outbox 时先置为 HELD，不能交给通用发送器直接发送。派发 Worker 在事务内复核目标修订及全部条件，将操作的派发阶段从 UNSENT 改为 MAY_HAVE_SENT，并把对应 Outbox 改为 READY。随后才允许事务外交接。此处保存的是内核的交接准备，执行端仍须独立完成自己的启动准备。

更新事务与派发准备事务竞争同一任务版本。更新先提交，未准备的操作被冻结且旧领取失效；准备先提交，更新把该操作视为可能发出，转入取消或核对。即使进程实际上在发包前崩溃，也不能仅凭没有回包把它改回 UNSENT。准备后收到控制变化应尽力抑制尚未发送的请求，但不承诺跨进程或跨库的瞬时停止。

[图 3：目标更新与派发准备的提交竞争](diagrams/runtime-kernel-dispatch-race.html)（独立 HTML）对照两个互斥提交顺序；实际网络发送发生在准备事务之外。

目标更新不直接删除 HELD 消息，也不释放 MAY_HAVE_SENT 操作的预留。派发准备过的旧消息恢复时优先查询原操作；需要补投时仍按原消息和原操作交接，并遵守当前控制，不能开启一次新业务动作。

### 5.2 新提案怎样复核旧操作

在行动或委派提案中增加 `reviewed_operations`，条目为 `(operation_id, KEEP|DROP, 原意图摘要, 原 goal_revision)`，绑定本轮最新决策基线。主类型不增加；仅复核时新动作列表可为空，但复核列表必须非空。结果或等待提案不能附带解冻目标工作的 KEEP。

| 条目 | 原子准入时的处理 |
| --- | --- |
| KEEP | 必须属于本任务、被冻结、仍为 UNSENT，摘要及绑定完全相同；复核当前能力、来源、权限、依赖及预算，更新其适用 goal_revision 并解除目标冻结。复用原预留，不重复收费或分配操作身份。 |
| DROP | 同样要求 UNSENT，且旧领取及所有发送入口已被隔离；关闭 HELD 消息及尚未派发工作，留下废弃原因，释放可证明未消费的预留。 |
| 未列出 | 保持冻结，不默认保留或废弃。 |
| 已可能交接 | 拒绝 KEEP／DROP，改用原操作查询、取消或结果核验。已知结果始终保留。 |

复核清单与新动作共同进行有界图校验及整体准入。重复条目、跨任务引用、摘要不符或同一操作同时 KEEP／DROP 都拒绝整批。保留动作若依赖已废弃的动作，不能自动满足该依赖；本轮必须同时废弃受阻后继，否则后继继续显式阻塞。保留原操作不允许修改旧依赖；需要换参数或换依赖时，废弃确定未发出的旧操作，另提新操作。

例如，旧提案的 S“保存全文”和 R“读回 S”已准入，更新先于 S 的派发准备提交。两项冻结，新提案可以 DROP S、DROP R，再请求新的“保存结论”和相应读回；旧身份及预算释放依据留存。若 S 已进入 MAY_HAVE_SENT，则先核对 S，不能用 DROP 加一次新保存跳过不确定性。

<a id="work"></a>
## 6. Work 表达责任，领取表达一轮资格

任务状态、操作事实、工作生命周期和领取资格分别保存。内核工作不替执行端查询外部作业 J；其核对工作调用执行服务查询原操作 S。

| Work 种类 | 负责的有限步骤 | 执行分类 |
| --- | --- | --- |
| DECIDE | 组装、生成、校验和尝试准入一轮提案。 | 目标决策；需要唯一有效决策与预留。 |
| DISPATCH | 准备并交接已准入操作。 | 目标工作；受目标冻结、控制、依赖及期限约束。 |
| APPLY_INBOX | 消费一条或有界一批持久报告／正式输入。 | 事实接收；不能被目标暂停完全阻断。 |
| RECONCILE | 查询原操作、核对原交接及已知结果。 | 处置；当前核验权限与有限处置预算。 |
| PROPAGATE_CONTROL | 交接已接纳的暂停、恢复或取消子操作。 | 控制；持久来源和既有权限。 |
| DELIVER | 发布已获准的结果或状态并核对交付。 | 标记 TARGET 或 CONTROL；目标交付受控制，控制通知走处置份额。 |
| RECOVER | 核对未知提交、退休失联决策、恢复已有责任。 | 处置；不能自行生成新目标动作。 |

Work 的 `state` 为 `PENDING / BLOCKED / LEASED / DONE / DROPPED`。等待条件和目标冻结为独立 gate；LEASED 的在途工作也可能后来被 gate 阻止。`DROPPED` 只关闭未派发责任，不能表示外部动作已取消。

| 转换 | 条件与结果 |
| --- | --- |
| PENDING → LEASED | 到期、依赖成立、gate 开放、资格及配额允许；原子增加 claim_epoch、保存 Worker 与有限租约。 |
| BLOCKED → PENDING | 对应条件被正式事实满足；仍检查其他 gate，保存到期时间并发出可丢失的唤醒提示。 |
| LEASED → LEASED | 原 Worker 有效续租；不得复活已到期或已被隔离的领取。 |
| LEASED → DONE＋后续 Work | 一轮责任完成，业务变化与下一轮责任共同提交；正常等待主动释放槽位。 |
| LEASED → BLOCKED／PENDING | 有界重试或条件等待，同步保存原因、次数、下次时间及用量。 |
| LEASED 过期 → 新 LEASED | 当前恢复者取得新代次；先核对旧进展及原提交，再决定处理。 |
| 未派发的 PENDING／BLOCKED／LEASED → DROPPED | 确认旧资格已隔离且不可能交接，完成 DROP 事务。 |

普通完成没有独立的“先 Ack，再提交”入口。RunStore.Commit 共同结束领取及持久责任；若只有工作元数据变化，也提交一个明确类型的工作变更。SQLite 写入队列、Worker 槽和外部执行配额分别管理；释放 Worker 不释放外部作业占用。

<a id="commit"></a>
## 7. 单任务提交的确定过程

这是原[内核细则 A](../reference/runtime-details.md#commit)提交算法的维护位置。RunStore 与 WorkStore 共享同一持久化单元，运行 Inbox／Outbox 也在这一事务内；其他模块账本不参与。

```text
Commit(change):
  经有界队列进入写事务
  校验受信调用主体、namespace、任务与原结果披露权限
  查 (namespace, task_key, change_id) 的已持久回执或关闭记录
  若已有回执: 同语义返回原结果；不同语义拒绝
  若接纳窗口已关闭: 返回恢复边界，不作为首次请求
  核对活动启动代次、Owner/epoch/管理阶段
  核对预期 state_version，以及适用的 Work/claim_epoch/租约
  核对决策资格、goal_revision、控制、依赖、期限及本地证明有效期
  核对预算预留/结算、唯一操作映射和受约束变更的结构不变量
  原子应用状态、操作、依赖、工作、预算、输入/控制及恢复记录
  原子标记适用 Inbox 已消费，保存必要 Outbox 和 change 回执
  达到声明的耐久条件后，返回 Committed
```

先查回执再比较新提交版本，使成功重试仍取得原结果；返回的是原版本和原回执，不重新应用变更，也不授予今天重新执行的权限。`change_id` 绑定同一规范化意图；时间戳、已分配键、变更内容在重试间固定。以新状态重新计算的变更使用新 change_id，业务 operation_id 可继续不变。

Store 返回 `Committed / Rejected / Unknown`。只有已知没有应用且事务结束，才返回 Rejected；调用超时、连接中断、I/O 不明确均可为 Unknown。核对分为已提交、当前未见、已封闭且未提交、超出恢复边界。只有在当前权威下已隔离旧提交者、关闭原变更继续提交的可能后，才可认定未提交。原样重试仍使用原 change_id 和变更；若前提已失效，先完成旧请求核对／封闭，再构造新变更。

<a id="control"></a>
## 8. 控制、终态与人工处置

控制来源的合并规则继续由[控制细则](../reference/interaction-and-task-control-details.md#control)维护。Core 的统一资格函数接收工作执行分类，计算能否“接收事实”“进行处置”“推进目标”，不能用一个 `task == RUNNING` 代替全部判断。暂停与取消禁止适用的新目标动作，但可靠控制传播、用量结算和效果核对继续。

终态评估读取目标验收、必需依赖、交付、在途操作、子任务处置及关键未知效果。只有相关条件已知且满足才提交终态。因取消前既有工作已完成而进入 COMPLETED 的特殊规则仍见[状态矩阵](../reference/03-state-and-failure-matrices.md#task-transitions)。终态不重开；迟到报告若含异常或审计信息，可持久保留并升级处理，但不能偷偷改变终态或产生新目标工作。

自动核对达到次数、时长或处置额度上限时，结束当前领取，保存 `DISPOSITION_EXHAUSTED` 等待原因、原操作和缺失证据，并建立一次升级通知。去重键为本任务该次等待的局部键；可靠发送可以重试，但同一事件不反复创建通知。任务存在其他可推进分支时不必整体 WAITING。

| 用户动作 | 复用入口 | 能改变什么 |
| --- | --- | --- |
| 申请追加有限处置额度 | TaskService.AdjustLimits，指定处置预算维度。 | 有权限才增加上限；不清除已用／未知预留，不自动改目标额度、硬期限、暂停或取消。 |
| 提交外部核验材料 | 有任务收集等待项时用 ProvideInput；获准恢复方也可调用 CapabilityService.Reconcile。 | 输入接纳只证明材料已收到；经原执行权威验证后，才形成效果报告。 |
| 查看未知影响 | Get／LookupOperation 及获准的原操作查询。 | 显示最后确认事实和未知事项，不以人工点击替代实际成功／停止。 |

材料收集等待项与效果核对等待项分开。提交材料会消费前者，但保留后者；Core 持久转交材料引用与原 operation_id，ExecutionCoordinator 沿固定 Driver／关联核验并保存执行事实及报告，Core 再消费。材料涉及的读取、工具动作或对外披露仍须授权和预算，不从 Reconcile 绕过准入。处置不足时依然接收有权的迟到结果，但有成本的主动核验继续受限。

<a id="recovery"></a>
## 9. 恢复、移交与停止

启动入口先确认唯一活动存储配置及启动代次，恢复授权、扩展绑定、接收入口与原账本，再开放有界扫描。任何仍可写的旧进程都必须被排除；两个数据库文件各自上锁不能证明迁移后唯一活动。启动代次隔离进程配置，Owner 世代隔离任务权威，二者不混用。

按顺序核对未决提交、失效领取、唯一有效决策、未知交接、Inbox 和已到期 Work。索引可重建，操作、预留、接纳水位和回执不能从模型或观测重建。文件数据库不可写时停止新的目标交接，保留最后确认状态的陈旧标识，不声称已持久切换 WAITING。

Owner 移交复用 ACTIVE → PREPARING → SEALED → 唯一目标 ACTIVE 的既有协议。PREPARING 禁止新目标决策／派发，允许获准的收束、报告应用与检查点准备；源 SEALED 后不再修改任务快照，只通过受控中继保存／转交迟到消息，目标激活后沿原操作恢复。检查点包含本设计的工作、决策资格、未知预留、控制来源、Inbox／Outbox、回执、关闭记录和准确绑定。未解决提交未知或无法固定持久切点时不能封存；旧 ACTIVE 决策在切点退休或按明确恢复映射处理，不把旧 Worker 租约带成目标可用资格。

普通关闭停止接纳新目标工作与新派发，排空或中止事务外调用并保存未完成责任；先关 Worker，再关连接，最后关持久化。关闭超时不证明外部动作停止。SQLite／bbolt 停写迁移还须涵盖其他模块和共同维护屏障，完整过程见[组装与迁移](../main/04-engineering/01-implementation-and-technology.md#6-sqlite-与-bbolt-怎样带着原任务切换)。

## 10. 用一次保存与读回核对整体流程

| 时点 | 持久事实与下一步 | 条件变化后的处理 |
| --- | --- | --- |
| 提交 T | 创建回执、QUEUED、目标预算和 DECIDE。 | 创建回包丢失，按原操作返回 T。 |
| 领取决策 | 决策 d1、生成预留、版本 v1 与领取同事务。 | 崩溃先核对 d1 准入，再退休资格；未知用量保留。 |
| 提案准入 | S、R、R 依赖 S 效果成功，S 的 HELD Outbox 与派发工作。 | 提交未知先查原 change_id，不交接。 |
| 准备 S | S=MAY_HAVE_SENT，消息 READY，派发责任可恢复。 | 更新先赢则冻结；准备先赢则原 S 进入核对／取消。 |
| 执行端接纳 | 内核记录接纳，执行端拥有 S／J 的实际事实与查询责任。 | 接纳回包丢失，查 S；不再次创建保存。 |
| S 成功报告 | Inbox 消费、效果投影、用量、依赖满足和 R 的工作共同提交。 | 重复报告返回原处理，不重复解锁或结算。 |
| R 与交付 | 原 R 在当前权限／控制下派发，核验读回，交付反馈被正式接纳。 | 手机离线保留交付责任，不能仅因文件存在宣告完成。 |
| 终态 | 目标、交付及在途处置条件满足，提交 COMPLETED。 | 迟到旧 Worker 不能重开任务。 |

本设计以短事务、持久责任和有限决策换取可追溯恢复，代价是更多持久记录及条件检查。吞吐、模型冲突率、恢复延迟和存储增长须按[验证计划](01-runtime-kernel-validation.md)实测；接口、DDL 可静态检查不构成这些运行结论。
