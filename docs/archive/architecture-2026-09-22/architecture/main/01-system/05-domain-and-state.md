# 1.5 对象与状态归属

<a id="核心对象与状态归属"></a>

实现一个模块前，需要先知道它能改变什么事实，以及哪些事实必须向其他模块查询。本篇把任务、行动、上下文、记忆和显示放到同一对象关系中；完整字段由[对象与标识参考](../../reference/01-data-model.md)维护。

## 从目标到实际结果

用户目标建立 Task。大脑依据任务事实和 ContextSnapshot 提出有限工作，内核准入后登记 Operation 及待处理工作。执行类操作由 ExecutionRecord 记录启动、外部关联和效果；外部系统可另外返回作业标识。内核核对报告后推进任务，界面保存和呈现获准结果。

一次任务可以有多个操作，一次操作可以经历多次消息交付与内部提交。独立能力调用、记忆修改和界面自有操作也可以没有 Task。业务操作身份、消息身份和内部提交身份因此分别管理。

| 对象或记录 | 保存什么 | 谁负责写入与核对 |
| --- | --- | --- |
| Task、任务版本、控制与预算 | 目标、当前进度、准入工作和后续责任 | Core 通过 RunStore／WorkStore 的运行持久化单元提交；只有当前资格有效的推进者能改变任务事实。 |
| Operation、ExecutionRecord | 稳定行动身份、启动准备、外部作业关联、资源与效果 | 执行协调器经 ExecutionStore 保存执行事实；内核消费报告，不能把自己的提交当作外部效果。 |
| ContextSnapshot、Evidence、Artifact 引用 | 本轮采用的信息、来源修订与可核验产物 | ContextAssembler 按当前许可和用途组装；内容来源与产物各有保存位置，不成为第二份任务状态。 |
| MemoryRecord、集合修订与墓碑 | 获准跨任务复用的信息及修改历史 | MemoryService 经集合修改权威提交；索引和同步副本不独立裁定正式修订。 |
| UIState、ActionRoute | 显示快照、用户输入及持久转交责任 | UIStateManager 经 SurfaceStore 保存；任务或授权等待项仍由所属业务模块消费。 |
| 授权记录与实际消费 | 策略、有限许可、撤销及原操作占用 | 管理端保存授权决定，实际处理端在自身原子组内复核与登记消费。 |
| Evaluation、Evolution 记录 | 评测计划、独立评分、比较和发布决定 | 各管理模块保存自己的状态与交接责任；运行完成、评分通过、发布获准、节点生效分别成立。 |

## 哪些变化必须一起保存

内核准入时，任务变化、操作关联、预算、后续工作和必要交接责任属于局部原子提交。RunStore 与 WorkStore 需要共同满足这一要求。ExecutionStore、MemoryStore 和 SurfaceStore 各有自己的原子组；部署在同一数据库不自动建立全系统事务。

跨模块交接依靠持久记录、稳定操作身份、Inbox／Outbox 和重复消费恢复。以保存文件为例：内核接纳保存工作、执行端接纳操作、外部文件实际写入、内核收到结果，是需要分别核对的事实。调用超时不能消除任何一方已经保存的责任。

## 版本和资格分别保护什么

任务版本用于判断提案是否仍适用；Owner 世代约束任务推进权威；Worker 领取代次和期限约束一轮处理资格；来源修订表达上下文依据是否仍有效。这些标识不能互相替代，连接在线也不代表拥有推进资格。

如果模型生成期间用户删除偏好，既有文件或已确认执行事实不会因此自动消失，但依赖该偏好的上下文和未准入提案需要重新检查。若保存回执丢失，则沿原操作核对效果；不能用新的任务版本或新操作身份绕过未知结果。
