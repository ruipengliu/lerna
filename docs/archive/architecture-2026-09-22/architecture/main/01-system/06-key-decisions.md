# 1.6 关键选择与代价

<a id="架构选择收益假设与代价"></a>

本方案面向需要多次决策、调用工具、等待外部结果和跨端使用个人数据的任务。模型提出有限工作，持久内核保存已经接纳的责任，执行端核对实际效果。选择的价值取决于这些机制是否降低重复工作、错误动作和恢复成本，也取决于维护这些机制的工程代价。

Go 核心、无独立基础设施的单机开发、三系统可替换及端云灵活部署属于既有设计输入。下文的收益主张、优化优先级与对照方案仍需实现验证；目录完整、接口可替换和静态检查均不证明收益。

## 需要共同接受的取舍

| 选择 | 理由 | 代价与适用条件 |
| --- | --- | --- |
| 准入工作持久保存，再交给执行端 | 进程退出后可以找回已承担的责任，沿原操作核对 | 增加短事务、去重记录、结果交接和保留成本；简单请求也有固定开销。 |
| 权限、控制与效果核对优先于新增动作 | 避免通过重复执行制造表面成功 | 未知效果可能需要等待，核对能力不足时不能承诺自动续跑。 |
| 新决策与已知工作的推进分开 | 等待外部作业时无需反复让模型重建计划 | 需要维护状态、依赖和触发规则，过期提案的重算仍消耗预算。 |
| 一项任务由唯一逻辑 Owner 推进 | 支持权威明确的端侧运行及跨端交接 | 失联时云侧不能任意接管；需要封存、激活及控制传播。 |
| 生产按用户归属分治，资源分别准入 | 将热点与部分故障限制在较小范围 | 增加 Cell 余量、路由、迁移与共享依赖治理成本，是否采用取决于实际负载。 |

## 四条待验证的收益主张

| 主张 | 机制与预期作用 | 成立条件与限制 | 机制解释 |
| --- | --- | --- | --- |
| H1 复用已经确认的工作 | 任务进度脱离 Worker，恢复时读取当前状态并查询原操作 | 已确认工作仍须有效；外部未知效果没有通用恢复时限，不能承诺恰好一次或最多损失一步。 | [内核](../02-subsystems/01-runtime-kernel.md)、[恢复](../04-engineering/03-reliability-and-recovery.md) |
| H2 将模型用量用于必要判断 | 分阶段发现能力、受控上下文和按原因决定后续动作 | 截断候选可能损失召回；准备、补查和压缩也计预算，减少 token 不证明质量提高。 | [决策](../02-subsystems/03-planning-and-decision.md)、[参考策略](../../reference/decision-details.md) |
| H3 部署与替换保留任务语义 | 共同契约保存权威、权限和原操作，在本地齐备时继续运行 | 依赖云模型或云工具的工作可能等待；替换有适配与验证成本。 | [端云](../03-coordination/04-edge-cloud-coordination.md)、[开发组装](../04-engineering/01-implementation-and-technology.md) |
| H4 缩小增长与故障影响范围 | 用户归属、持久状态与资源池分开扩展，历史退出调度热路径 | 共享服务故障仍可能扩大影响；单用户原子组过热不能任意拆散。 | [部署存储](../04-engineering/02-deployment-and-storage.md) |

H1 的等待资源收益可以用本地槽位演算理解：稳定到达率为 λ，实际占槽时间为 a，外部等待为 w，则全程占槽约需要 λ(a+w)，释放等待槽约需要 λa，另付持久调度开销。λ=10 任务／秒、a=10 秒、w=90 秒时是约 1000 与 100 个槽。这不代表机器数或吞吐提高十倍，模型和外部作业并发配额仍需保留；异步或持久工作流也可能获得同类收益。

## 自建与复用如何比较

| 可行路线 | 适用情况 | 需要比较的成本 |
| --- | --- | --- |
| 简单异步 Agent 循环与业务记录 | 任务短、等待少，端云状态要求有限 | 增加恢复与控制后是否逐渐重建同样的运行内核。 |
| 持久工作流承载运行，Harness 提供领域行为 | 引擎能够适配共同契约，并通过相同故障与离线用例 | 语义映射、部署、升级、端侧适配与持续维护。 |
| 当前 Go 内核与当前状态持久化 | 需要直接表达单机嵌入、端侧权威和任务控制 | 调度、公平性、故障用例、Schema 迁移及运维责任。 |
| 云端统一 Owner、设备远程执行 | 稳定联网，配置不要求端侧自主 | 云依赖、传输约束及未来增加自主运行的代价。 |

现有持久工作流应进入强对照，不能把恢复能力本身当作本项目独有优势。当前保留自建基线，并不预先排除验证后替换运行实现；数据库、传输、模型 SDK 和生产 HA 可以复用适合的实现。历史机制研究见[持久运行研究](../../../research/harness-durable-runtime-options.md)，版本依据不因本次整合而更新。

收益比较必须计入建设工作、故障用例、发布迁移、告警与人工处置负担。按[架构主张验证](../04-engineering/06-architecture-comparison.md)冻结强对照、预算和推翻条件后取证，再决定保留、修改或放弃选择。完整业务验收仍采用[既定验收配置](../../reference/05-validation-profiles-and-traceability.md)。
