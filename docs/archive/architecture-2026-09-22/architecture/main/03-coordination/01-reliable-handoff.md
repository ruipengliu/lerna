# 3.1 持久交接与结果确认

任务状态、执行记录、记忆、界面和评测管理状态各有自己的提交边界。一次调用跨过这些边界时，发出方与接收方可能分别重启，消息也可能重复。系统通过稳定的操作身份、可恢复的发送与接收责任，以及对原结果的核对继续处理。

## 1. 先判断未知发生在哪里

| 边界 | 谁保存依据 | 回执说明什么 |
| --- | --- | --- |
| 本地原子提交 | 所属 Store 的变更记录与回执。 | 本次本地变更是否已提交。 |
| 消息持久接收 | 接收模块的 Inbox 与待处理责任。 | `PERSISTED` 表示接收责任已持久保存。 |
| 业务接纳 | 目标模块的操作与业务记录。 | `ACCEPTED` 表示目标模块已接纳相应工作。 |
| 外部实际效果 | 执行系统、Driver 及外部目标可取得的证据。 | 请求进展与效果分别报告，调用成功不能笼统代替效果确认。 |
| 任务交付 | 内核的目标核验与必要呈现事实。 | 只在目标、在途责任及交付条件满足时确认任务完成。 |

`change_id` 关联一次存储变更，`message_id` 关联一条应用消息，`operation_id` 关联一次逻辑意图。同一操作可以跨过多次提交和消息；改变目标或内容则形成新的意图。完整身份规则见[对象与标识](../../reference/01-data-model.md#identity-version)。

## 2. 从本方提交到对方消费

以任务内核向执行系统转交一项已准入操作为例。内核先把任务变化、操作关联、工作和 Outbox 放进同一任务事务。达到适用耐久要求后发送；未收到结果时，待发送责任仍可恢复。

执行端持久保存接收责任，再按业务规则接纳操作。持久接收和业务消费可以分阶段，但接收后必须能找回尚未处理的记录。消费时把业务变化、消费标记及必要回复共同提交；重复消息沿原身份返回，不重复推进。

执行端随后按当前条件启动或核对原操作，将结果与待回报责任共同保存。内核幂等消费结果，更新事实和后续工作。任务事务并不覆盖执行数据库或外部工具；可靠交接保留的是恢复责任，外部效果是否可安全重试仍取决于工具契约。

[内核的交接过程](../02-subsystems/01-runtime-kernel.md#5-模块怎样可靠交接)给出两端提交图及局部记录，[执行系统](../02-subsystems/04-tools-and-devices.md)解释准备、启动、查询与效果核对。

## 3. 回执丢失后查询原事实

若本方提交结果未知，沿原 `change_id` 查询所属 Store。未查清前不派发依赖该提交的新动作；一次未查到不能证明旧提交永远不会成功。

若目标接纳回执丢失，沿原操作查询。目标已经接纳而发出方尚未记账时，发出方补齐原关系，不创建第二次操作。若外部效果未知，执行系统核对原调用或作业；只有确认未发送，或目标端仍有效的幂等保证与当前条件允许时，才按契约再次发送。

例如，电脑已完成写入但报告尚未到内核。内核保留等待，执行系统补发原结果；电脑文件存在本身未必能证明是这一次写入，需要原操作关联与适用证据。完整切点见[状态与故障矩阵](../../reference/03-state-and-failure-matrices.md)。

## 4. 恢复责任也约束清理

去重记录、操作记录和提交回执各有恢复义务。清理关键明细前，先确认相关义务已结束，并持久保存关闭水位或相应恢复边界，停止首次受理已关闭范围内的旧请求。收到过旧请求时明确报告边界，不能把“记录已清理”解释为“从未执行”。

记忆、交互、协作、授权、Evaluation 与 Evolution 在自己的业务原子组中应用这些原则；具体共同写入哪些字段由[原子组与保留规则](../../reference/01-data-model.md#atomic-retention)及所属细则维护。原始观测遥测不因此成为必须逐条可靠交接的业务记录。

本章只连接既有提交与恢复规则，不新增全局事务或统一成功状态。下一章说明控制与来源变化怎样影响尚未完成的交接。
