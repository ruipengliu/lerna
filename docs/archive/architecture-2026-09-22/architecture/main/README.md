# 架构正文阅读顺序

正文按“整体关系 → 子系统行为 → 跨模块协作 → 工程实现与验证”展开。首次阅读时沿下表推进；查阅某个组件时可以直接进入第二部分，各章会给出必要角色、输入及条件。

| 部分 | 读者需要建立的认识 | 下一层入口 |
| --- | --- | --- |
| [一、系统整体](01-system/README.md) | 系统解决什么问题，组件如何连接，谁保存哪类事实，关键取舍是什么。 | 全景中的组件对应第二部分，系统过程引出第三部分。 |
| [二、子系统设计](02-subsystems/README.md) | 每个子系统接收什么、负责什么判断、交付什么结果，以及内部主要职责如何分工。 | 跨模块行为进入第三部分，精确规格进入契约参考。 |
| [三、协作机制](03-coordination/README.md) | 独立提交的模块如何可靠交接，如何落实控制、委派、所有权移交与离线运行。 | 部署位置和失效处理进入第四部分。 |
| [四、工程实现与验证](04-engineering/README.md) | 如何组装实现、部署与恢复，如何取得质量、替换和发布证据。 | 对照参考资料形成实现与验证工作包。 |

章节编号使用“部分.章”，仅用于阅读顺序。示例独立编号，参考附录保留各自编号；图示文件名中的旧数字是稳定资产标识，不再表示章节位置。

## 正文怎样使用示例

局部例子只承担当前机制的解释工作，首次使用时说明初始状态、权限和对象。不同章节可能观察同一教学任务的不同阶段；读者不需要拼接这些片段才能理解通用行为。完整顺序在[任务正常过程](../examples/01-task-lifecycle.md)展开；删除、确认、撤销、故障等分支有独立起点。

架构正文中的“组件”表示逻辑职责，不自动规定进程或代码包。第二部分说明组件对外行为和主要分工；[详细设计目录](../design/README.md)预留内部数据结构、算法与实现选择。现有字段、方法、状态和故障组合仍在[契约参考](../reference/README.md)维护。
