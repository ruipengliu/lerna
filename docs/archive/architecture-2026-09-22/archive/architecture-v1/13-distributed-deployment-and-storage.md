## 1. 设计输入与容量模型

### 已确认输入与待验证换算

| 输入 | 数值或约束 | 对设计的影响 |
| --- | --- | --- |
| 注册用户 | 10,000,000 | 身份、用户路由和长期数据规模；不按每个用户分配进程、数据库或消息主题。 |
| 日活用户 | 1,000,000 | 以每用户任务数、调用数、正文体量推导吞吐与增量存储。 |
| 同时在线 | 100,000 | 连接基准至少覆盖十万长连接；多端连接、多个逻辑流和广播扇出分别计入，不能将其视为十万执行 Worker 或模型并发。 |
| 隔离边界 | 个人用户 | 身份绑定用户级 namespace；任务、记忆、UI、对象引用、配额和订阅均按该边界隔离。 |
| 端云数据策略 | 受限原文可仅留端 | 云侧容量不假定收集所有原文；端侧检索和推理不足时等待或说明覆盖限制，不自动上传。 |

先以每在线用户一个活跃连接形成连接基准；若实际多端系数为 d，则连接预算按 `100,000 × d` 增长，不能通过少测端点来宣称满足在线用户目标。

### 示例业务负载：用于暴露瓶颈，不作为业务预测

假设每 DAU 每天创建 5 个任务、峰值系数 10、每任务 4 次执行操作、3 次模型调用、12 条持久业务消息；活跃任务平均持续 120 秒，一次模型调用平均占用 8 秒。消息数暂不含 token 预览、心跳、重投与额外多端扇出。各参数须由业务轨迹和压测替换。

| 负载 | 换算 | 示例结果 |
| --- | --- | --- |
| 任务接纳 | DAU × 每日任务数 ÷ 86,400 × 峰值系数 | 500 万任务/日；平均约 58/s，峰值约 579/s。 |
| 活跃任务状态 | 峰值任务到达率 × 平均活跃时长 | 约 6.9 万份活跃状态；等待状态不占一个常驻执行线程。 |
| 执行操作 | 任务数 × 每任务执行操作数 | 2,000 万次/日，峰值约 2,315/s；查询、核对和每操作多次提交另计。 |
| 模型请求与并发 | 峰值任务率 × 3；再乘 8 秒 | 峰值约 1,736 次请求/s、约 1.39 万并发；还须满足模型供应商 RPM/TPM 和成本约束。 |
| 持久业务消息 | 任务数 × 12 | 6,000 万条/日，峰值约 6,944 条/s；另加补投、同步、订阅扇出和控制流量。 |
| 心跳 | 10 万连接 ÷ 30 秒 | 约 3,333 组心跳往返/s；若请求和响应各一帧，则约 6,667 帧/s，不逐条写业务数据库。 |
| 操作记录净增 | 2,000 万 × 平均 1 KiB | 约 19.1 GiB/日；仅为一个简化记录层，未含索引、WAL、副本、其他状态和正文。 |

到达率乘平均占用时长仅用于稳定负载下的并发估算；应补测长尾、突发和排队。模型并发很可能先受到配额与费用限制，架构必须能明确排队、限额或拒绝，不能靠扩容连接网关宣称模型吞吐已经满足。

持久存储预算按 `Σ(各类每日写入量 × 有效保留天数 × 索引/副本等放大) + 存量 + 备份 + 迁移余量` 计算。例如上述单层操作记录保留 30 天约 572 GiB，30 天只是演算参数，不覆盖既定操作恢复、隐私删除或评测证据保留契约。

## 2. 生产部署单元与用户路由

![图 S01：用户归属 Cell 的生产部署与故障隔离](diagrams/review-s01-production.svg)

本图展开一个用户的云侧归属路径，应用资源池跨三个可用区放置；其他 Cell 采用相同部署模板并独立管理业务存储与恢复负载。实例数由实测容量和失去一个可用区后的余量确定。数据库 HA 与业务恢复职责见 14 分册；共享目录、身份及模型供应商仍是显式共享依赖，Cell 不能隔离这些依赖的全局事故。

### 两类部署配置共用逻辑契约

| 部分 | 单机开发配置 | 分布式生产配置 |
| --- | --- | --- |
| 运行与调度 | Go 内核、本地工作领取及模拟端 | Kubernetes 上的 API、Task/Brain Worker、Execution Worker 等独立资源池；任务状态外置，按负载扩缩。 |
| 可靠数据 | SQLite 及本地存储 Adapter | 按用户分片的 PostgreSQL，跨可用区同步副本、受控主备切换及连接池。 |
| 交互与消息 | 进程内调用、本机 gRPC/WebSocket | 长连接网关、用户归属路由、持久 Inbox/Outbox；Kafka 承接区域内异步投递和派生消费。 |
| 大内容与检索 | 本地文件和本地索引 | 对象存储保存获准正文；独立可重建检索索引；端侧私有数据仍由端侧管理。 |
| 缓存与运维 | 可省略独立服务 | Redis 缓存/在线位置、集中指标、凭证与密钥托管；均不成为业务事实的替代权威。 |

采用区域内 **Cell（独立服务与存储分区）** 隔离故障和容量。一个 Cell 含应用资源池、消息交付责任和一组数据库分片；一个用户的云侧可变数据默认归属一个 Home Region / Home Cell。Cell 间不共享一张需要全局竞争的任务领取表。

逻辑模块不强制一模块一微服务。初始可将 Task API 与监督逻辑合部署，将 Context/Brain 与模型调用资源池合部署；执行、长连接、批处理按资源和信任边界分开。扩容依据连接、队列年龄、内存、吞吐和外部配额等指标，而非仅看 CPU。Kubernetes 支持自定义指标扩缩容，具体指标组合及容量水位属于本方案设计。[HPA 文档](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)

### 路由和身份不混用

| 状态 | 权威和用途 | 不代表什么 |
| --- | --- | --- |
| 账户 → namespace | 可信身份绑定；普通客户端不得通过请求体切换其他用户作用域 | 不是任意选择数据库的客户端参数。 |
| namespace → home_region / cell / shard / route_epoch | 高可用 NamespaceDirectory；数据分区内另保存可写状态与世代栅栏 | 不是任务 owner_epoch，不赋予动作执行资格。 |
| endpoint → connection generation / gateway | SessionRegistry 持久化新连接世代；Redis 缓存当前在线位置 | 网关断开不使任务失去拥有者；同一用户多个端点可同时在线。 |
| task_ref → owner / owner_epoch | RunStore 管理单任务唯一推进权；Worker 另有短期领取代次 | 不是一个用户只有一个 Worker，也不是每次重连迁移任务。 |

路由使用稳定虚拟桶和可调整目录；不能直接对实时节点数取模，否则扩容会无控制地改变大量用户数据归属。按用户迁移为首选粒度，热点用户可搬至专用分片/Cell；不默认拆散一个任务、记忆集合或资源控制原子组。

路由缓存允许过期，但存储 Adapter 每次写入必须检查本地 namespace 可写状态及 route_epoch。更新目录不是封禁旧写入的充分条件：迁移必须先使旧分区持久封存，再激活新分区。原任务 Owner 位于端侧时，云侧数据路由不能夺取它的推进权。

### 分片、扩容和热点处理的具体路径

用户身份先映射为 namespace，再由稳定虚拟桶及显式用户覆盖项查到 Home Cell / shard；桶数量在一个路由版本内固定，新增物理分片通过迁移改变映射，不对实时实例数重新取模。普通请求只访问该用户归属分片；跨用户分析使用获准派生数据，不能在同步请求内扫描全部分片。

扩容分为三类：增加无状态应用实例承接计算，增加数据库分片承接写入/存量，增加 Cell 承接故障范围与独立容量。它们分别受模型配额、数据库迁移速度和共享控制面能力限制。只加 Worker 不会增加一个热分片的写入容量。

热点用户先按用户额度和公平队列限速，再依据持续写入、存量、锁等待和恢复积压迁移到独立分片/Cell。单个任务、集合或资源控制原子组不能因热点直接切成跨库事务。确有超大用户时，拆分不同独立集合/任务的方案作为新 profile 验证；跨组操作仍用持久交接，不能扩大原子承诺。

读路径按一致性选择：任务接纳回执、未决操作查询、当前授权/额度和变更准入读取权威主库；允许滞后的列表或诊断可读副本并返回来源版本/覆盖信息。读副本查不到记录不证明未接纳，不能触发首次重做。页面刚提交后读进度应使用权威读或满足指定版本的读，避免呈现倒退。

## 3. 十万在线的交互与可靠交付

### 长连接接入和下行路由

生产配置明确采用**登记的受信 Gateway 代理**：在网关终止客户端连接，Gateway 到 Home Cell 使用服务 mTLS；这是一项显式新增的代理信任配置，不沿用开发配置的“默认节点直连”。身份和授权交接按以下规则闭合：

- 原生节点仍在专用入口出示 mTLS 证书；Gateway 校验证书、节点登记、用户关联及原授权的持有者绑定。经登记的认证职责产生受保护的原始主体证明，由有权签发方验证代理资格、原授权与祖先限制后，签发绑定 Gateway 实际出示证书及目标服务 audience 的更窄材料。后端核对当前 mTLS 对端与 `cnf.x5t#S256`，同时保留原发起主体、namespace、端点和连接世代。
- 浏览器使用独立同源会话入口，验证会话、Origin 和变更请求的 CSRF 保护；可信 IdentityVerifier 将会话解析为用户主体，再经同一受控签发路径产生代理材料。浏览器 Cookie 不转交给任意后端，不允许节点认证失败退回浏览器入口。
- 签发方不能仅凭客户端可改写的用户头或 namespace 签发；后端也不能只信任 `X-User-ID` 等头部。材料限定目标、动作/资源范围、原操作关联及有限期限，代理链不得增权；实际数据/动作处理时仍复核授权。Gateway 进入受信计算边界，代理资格和签发密钥分别管理。
- 换 Gateway 或轮换证书需重新取得绑定新出示者的材料，原 operation_id 和不可变业务意图不变；不能原样转发绑定上一跳证书的授权。身份签发、撤销检查和重连洪峰也计入容量验证。

该选择落实既有 [证书绑定与代理转发约束](08-authorization-lifecycle-and-interfaces.md#短期签名授权与转发)。不支持此代理配置的节点只能走保留端到端 mTLS 的直连/透传路径，不能降低身份检查来接入网关。

1. 负载均衡将新连接分配给 Gateway；按上述代理配置完成认证、协议与能力协商，绑定 namespace、endpoint 和新连接世代。原生节点与浏览器使用互斥的认证入口。
2. Gateway 只保有有界连接缓冲、协议状态和在线位置；会话世代与恢复责任不能仅存在该 Pod 内。新连接替换同一端点/连接槽的旧会话，不挤掉同用户其他合法端点。
3. 上行变更路由至 Home Cell 的可靠接收与业务入口；持久接收后才发 PERSISTED，业务模块本地接纳后才发 ACCEPTED。若尚未持久接收即过载，则明确背压/拒绝，不作已收承诺。
4. 业务提交产生 Outbox，区域交付层找到目标端点，按当前权限和订阅下发。离线时保留约定的可靠交付或状态补读责任，不在网关内无限堆积。
5. Gateway 故障后客户端带抖动重连，重新鉴权和取得当前连接世代，恢复流位置并查询未决操作。任务、操作和 Surface 身份不随连接更换。

旧连接发来的业务消息必须验证当前会话资格；不能只相信缓存的用户标签。撤销与离线资格遵守授权分册的新鲜度边界，不能声称全球实时撤销。心跳可只更新暂态在线信息，重要变更仍需经过正式准入。

### 可靠、可合并、临时消息分流

| 类别 | 示例 | 存储与背压规则 |
| --- | --- | --- |
| 可靠业务流 | 正式输入、控制请求、执行结果、授权失效、待输入项 | 持久 Inbox/Outbox 和业务记录；按窗口补投/查询，队列满时阻塞接纳或明确拒绝。 |
| 可恢复状态流 | UI 快照/补丁、任务进度投影、同步视图 | 可合并中间状态；最终状态和版本边界可恢复，版本缺口或游标过期重新取快照。 |
| 临时流 | token 预览、光标、非业务遥测、心跳 | 仅在契约允许时丢弃/合并；丢失不能改变最终业务结果或永久阻塞可靠流。 |

可靠与临时流使用独立序号/额度，避免可丢弃内容造成可靠补读假缺口。控制、结果核对和普通生成各有有界预算；用户目标额度用尽不阻断取消的接纳。

恢复游标必须绑定 namespace、端点/订阅视图、流世代、授权范围和保留窗口。游标只是补读位置，不是读取授权。重放时再次检查当前披露权限；过期返回 CURSOR_EXPIRED，客户端取权威快照并按原 operation_id 核对，不能把旧输入重建为新操作。

对慢客户端限制待确认消息数、总字节数和保留时长；大文件改用授权对象引用/分块。连接被关闭时仍保留业务恢复入口。多端推送只发向登记的受控订阅，不能按“同一个用户在线”向其所有窗口发送所有秘密内容。

### 网关容量与连接风暴

网关规模按 `N ≥ 连接总量 ÷ (单实例压测容量 × 目标利用率 × 故障后存活比例)` 计算。若暂以 5,000 连接/实例、60% 利用率、三可用区损失一区为演算，则十万连接需要至少 50 个实例，均衡分布可向上取 51 个；**5,000 未经实测，51 不是资源采购结论**。还须同时满足带宽、缓冲、TLS、文件描述符及消息处理限制。

扩容主要承接新连接，已有长连接不会因增加 Pod 自动均摊。缩容先停止接新连接，发有界排空/重连提示，保留足够终止时间；失败时通过上述恢复流程兜底。[Pod 终止流程](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

演练同时失去一个可用区、大批端点重连与未决操作查询。握手、恢复补读、快照和普通新任务分别限流，缓存目录并合并相同状态读取，避免十万客户端同时穿透数据库。限流仍遵守受理与未知结果语义。

## 4. 存储结构与用户隔离

### 存储分工

| 存储 | 保存什么 | 一致性与边界 |
| --- | --- | --- |
| PostgreSQL 用户分片 | RunStore、ExecutionStore、MemoryStore、AuthorizationStore、SurfaceStore 及其回执/变更/交付记录；云侧用户预算账本 | 各 Store 原子组保留本地事务；共用分片不等于跨模块/端云事务。 |
| PostgreSQL 控制数据 | 身份绑定、namespace 路由、连接世代及管理配置；评测/发布按各自管理范围分区 | 控制读可缓存；签发、路由激活、用户隔离和发布资格不能靠最终一致缓存单独决定。 |
| 对象存储 | 获准上云的附件、截图、证据正文、不可变产物及备份 | 业务数据库保存受控元数据、摘要、版本和可见状态；对象存在不代表获准对外发布。 |
| 检索索引 | 记忆、证据和能力的可重建检索投影 | 从来源修订派生，按 Cell/分片组织；不能作为权限、来源是否删除或业务提交的唯一判断。 |
| Kafka | 区域内 Outbox 投递、变更分发和异步派生 | 消费可重复；按聚合键维持需要的顺序，不宣称跨分区总序或外部副作用 exactly-once。 |
| Redis | 目录/查询缓存、在线位置、非权威快速限流 | 丢失后可重建；不得唯一保存授权、去重、待执行工作、付费额度或任务拥有权。 |
| 端侧存储 | 受限原文、端侧索引、端侧拥有任务及执行记录 | 与云侧各有事务；同步、披露和备份均遵守数据策略，不因生产扩容自动复制。 |

Kafka 的分区顺序和事务不能扩展成数据库与外部设备的共同事务；本方案使用 Outbox 加幂等消费维持交接责任。[Kafka 设计说明](https://kafka.apache.org/40/design/design/)

Redis Pub/Sub 是至多一次交付，故不承接唯一可靠通知；它至多作为加速唤醒，漏通知时仍可扫描持久工作或读取状态。[Redis Pub/Sub 文档](https://redis.io/docs/latest/develop/pubsub/)

### PostgreSQL 物理设计约束

- 用户数据的主键/唯一键和同域外键包含 namespace，如 `(namespace, task_ref)`、`(namespace, operation_id)`、`(namespace, collection_ref, record_ref)`。查询和缓存键同样带该范围，不依赖 ID 难猜保证隔离。
- 以用户归属分片实现横向扩展；分片内根据任务列表、待处理工作、操作核对和记忆访问建立复合索引。历史变化记录可按时间分区，但分区裁剪不能破坏全恢复窗口的操作唯一性：长期接纳/关闭水位与可清理的明细分开保存。
- 同一个原子组的状态、回执、预算和 Outbox 必须共分片。资源控制与受其保护的启动准备提交在同一权威事务内完成；不能先读一个分片的锁再无条件写另一个分片。
- 长列表使用受作用域约束的稳定键集分页；待处理工作用部分索引缩小扫描范围，避免反复扫描所有终态历史。为热/冷访问路径分别提供 EXPLAIN、索引体量、锁等待和写放大证据。
- 连接池按每个数据库分片的连接预算设置总上限，纳入所有服务副本和故障冗余；客户端长连接不能一对一占数据库连接。采用事务池时不依赖跨事务会话状态；namespace 等上下文在每个事务由可信服务以事务局部方式设置。

RLS 作为纵深防御：运行角色不是表所有者，不具有 superuser/BYPASSRLS，适用表启用并按需 FORCE ROW LEVEL SECURITY；读策略和写入 WITH CHECK 均覆盖 namespace。迁移/运维角色独立受控，应用仍做资源级和用途级授权。PostgreSQL 明确存在表所有者及特权角色绕过情形，不能把“开启 RLS”写成无条件隔离证明。[行级安全文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

跨用户调度扫描是受信内部操作，采用最小权限的工作领取接口，只返回已选定 namespace 内的执行上下文；普通 API 不持有任意跨域 SQL 能力。共享公开能力目录使用单独只读范围，默认不出现其他个人用户数据；任何跨用户共享都需要显式资源授权。

### 数据族、访问路径和保留方式

下表是生产物理设计建议，名称表示表族，不是新增公共协议对象或已经存在的 DDL。每个 Store 的表由所属模块管理；共同数据库不授权模块绕过彼此 Interface 直接改表。

| 数据族 / 建议表族 | 主要键与读写路径 | 分布与索引 | 生命周期与恢复要求 |
| --- | --- | --- | --- |
| 当前任务 `task_current` | `(namespace, task_ref)`；按版本/owner 条件更新，按用户列任务 | Home shard；用户、状态、更新时间及稳定引用组成适用索引 | 活跃状态保持紧凑；历史正文外置，终态保留摘要及仍需核对的关联。 |
| 持久工作 `work_items` | 任务内局部工作键；ready 时间、优先级、领取代次/期限 | 与 RunStore 共事务；ready/待恢复状态的部分索引，选定用户后短事务领取 | 完成前不得归档唯一工作；过期领取进入核对，不重新创造动作。 |
| 操作/提交回执 | namespace、接纳窗口、operation_id；提交另按对象及 change_id 查询 | 各接纳权威内唯一索引；活跃账本不按日期拆散唯一性 | 语义摘要、接纳状态、结果引用和有效范围至少覆盖允许恢复期；关闭水位先持久化再清理明细。 |
| 执行与资源控制 | 原 operation_id；资源范围、控制版本、启动准备/效果 | 同一受控资源与启动原子组共分片；未决状态索引 | 启动和许可消费一起提交；未决效果保留至核对或明确处置。 |
| 用户及任务预算 | 用户账本、原额度分配、任务内预留/消费 | 用户归属分片；条件更新和分配唯一键 | 未知消耗不能归零；用户到任务的分配按原操作交接。 |
| 记忆与来源依赖 | collection/record 引用、revision；来源到派生对象的反向引用 | namespace 和集合内查询；按可见修订建索引 | 当前记录、墓碑、变更日志同事务；删除进度和派生清理单列。 |
| 授权与界面 | Grant/Policy revision；Surface revision、ActionRoute | 各自 Store 的局部原子组；等待项及原操作索引 | 权限/界面快照可恢复，业务等待项仍在其原权威消费。 |
| Inbox / Outbox | 流世代/seq、message_id、operation_id 和聚合修订 | 与对应业务原子组共库；待发送/未处理部分索引 | 可靠消费及连续水位持久保存；Kafka 保留期不能替代未结交接责任。 |
| 追加历史与诊断 | namespace、聚合引用、局部项次/时间；按对象和时间查 | 每个物理分片内按时间分区；具体粒度由体量/查询验证 | 到期前确认恢复、评测及隐私条件；正文不进入无界热表。 |
| 附件、截图、产物与归档 | 受控对象引用、内容摘要、版本、驻留策略 | 对象存储；元数据仍在所属 Store，下载独立授权 | 先暂存并验证再发布引用；孤儿清理、历史版本和备份删除分别推进。 |

**用户分片与时间分区分别解决不同问题。** 前者将负载放到不同数据库，后者控制单库内历史表体积和清理成本。不能以“每天一张操作表”替代稳定操作账本：PostgreSQL 分区表的全表唯一约束需要包含分区键，简单按创建时间分区不能直接保证 `(namespace, operation_id)` 在整个恢复窗口唯一。[分区与唯一约束限制](https://www.postgresql.org/docs/current/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)

参考布局将仍有效的接纳/回执头和窗口关闭水位保存在不按时间切分的账本中；历史载荷按时间归档，账本保留受控结果引用。若账本本身过大，先增加用户物理分片；在单库内可按 namespace 哈希分区并保持唯一键包含该分区键。任务从创建日跨到结束日不迁移其权威操作身份。

核心检索键、状态、版本、期限、领取信息和金额/用量维度使用明确列与类型；动态参数及扩展内容保存在有 Schema 的载荷中。大段模型输出、截图和完整上下文以受控引用保存，不能依赖扫描 JSON 正文来领取工作或检查权限。

### 热冷分层、投影更新与存储预算

热层保存当前状态、有效回执、未决工作和恢复水位；历史层保存仍获准保留的变化记录；对象层保存大正文和不可变产物。搬到冷层不意味着可以失去查询承诺：原操作核对应仍能得到明确状态或契约规定的回执过期结果。

索引/缓存使用“获准快照 + 变更增量”重建，应用时比较来源修订，删除/失效参与同一版本规则。消费者落后时报告覆盖水位；回放旧变更不能把新墓碑覆盖掉。对象清理前核对权威引用、暂存期限及未完成交接，防止误删事务尚未发布的唯一正文。

存储容量分别估算账户存量、活跃状态、每类每日变化、正文体量、保留期及放大系数。数据库写入峰值还需计算 `任务率 × 每任务运行提交数 + 执行率 × 每操作执行提交数 + 消息消费/投递更新 + 记忆/UI/授权/恢复更新`；不把每任务一次接纳等同于一次数据库写入。

将每分片实测可持续写入、热索引大小、IOPS、复制/WAL 带宽、连接预算和恢复扫描能力共同作为分片上限。达到预警水位先限制增长并规划迁移，留出失败重试、备份和单区故障余量；不从千万注册数直接推出固定数据库台数。

### 数据库之外的隔离

| 边界 | 必须验证 |
| --- | --- |
| 对象与下载 | 对象键、元数据和下载许可绑定 namespace/资源/期限；不按客户端提交路径直接返回内容；跨用户去重不能泄露对象存在性。 |
| 索引与向量检索 | 在候选搜索阶段限定获准范围，返回前复核来源版本与权限；不是全库 top-k 后才过滤；隐藏命中数量和覆盖信息也不可泄露。 |
| 缓存 | 缓存键、回填、负缓存及失效均带 namespace 和适用策略/来源版本；命中缓存不自动跳过权限校验。 |
| 消息与 UI | topic/路由键只是投递信息，订阅和重放另验权限；不同 namespace、端点、Surface 不可串发。 |
| 扩展与执行 | 插件运行上下文、临时文件、凭证引用、模型输入和结果出口均受用户范围约束；共享 Worker 不能复用上一个用户的会话或缓冲。 |
| 观测与评测 | 默认记录去敏的引用和指标，不把完整提示、记忆、凭证作为公共日志；原文调试与评测复用需单独获准。 |

正文写入采用“暂存对象 → 校验摘要和可读性 → 业务事务发布引用”。事务失败产生的孤儿由保守清理流程回收；不得先对外宣布成功再异步补写唯一正文。删除先使权威记录不可继续使用，再推进索引、副本、对象历史版本和备份到期清理；未完成的维度分别报告，不以删除一个当前对象冒充所有副本已清除。

## 5. 分布式工作领取、消息和资源配额

### 工作领取与过期 Worker

Scheduler 在本地分片的短事务中选取 ready 工作，检查用户额度、任务控制/拥有者前提，更新领取代次和有效期，提交后才调用模型或执行端。PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 可用于并发队列领取；它只解决本次行锁竞争，不提供持久租约、任务所有权或外部动作的唯一执行。[SELECT 锁定条款](https://www.postgresql.org/docs/current/sql-select.html)

领取事务必须和暂停/取消更新遵守一致的锁定或版本竞争顺序。完成提交同时校验 owner_epoch、state_version 和领取代次；过期 Worker 不得覆盖新状态。租约续期使用权威存储时间和条件更新，时钟/存储不可确认时停止发新资格。

Worker 租约到期只允许新的 Worker 承接恢复责任，不证明旧模型请求、工具调用已经停止。已准备/可能发出的操作先核对原 operation_id；ExecutionCoordinator 保存启动事实并复核当前执行资格，不能因 Worker 重启而重新分配一个动作 ID。数据库栅栏能拒绝旧写入，不能撤销已经发往外部的副作用。

### Outbox 与消费恢复

Outbox 与产生它的业务状态同事务提交。发布方取得消息系统约定的持久接纳后可推进投递位置，但业务操作记录和未结交接责任仍保留；消息代理故障模型必须与承诺的可靠性匹配，不能因短保留期让未完成交接失去唯一载荷。

消费者保存 Inbox/去重与待处理工作后再确认相应消费位置；跨 Store 处理采用独立事务加原操作查询。事件键使用 namespace、聚合引用及 revision；只要求任务、集合或 Surface 自己的必要顺序。重复可忽略、缺口可补读、乱序需按版本核对，不能按消费者到达时间覆盖权威状态。

不按千万用户创建千万 topic。按 Cell 和业务流分区，通过稳定键分配；热点键需限额或迁移，不能随机打散同一聚合后继续声称有序。Kafka 不可用时已持久工作保留，恢复扫描和控制流有独立处理预算，Outbox 到达容量上限后停止扩大新接纳。

### 公平调度与模型调用

采用“用户 → Cell → 区域/供应商”分层准入。用户维度限制新任务速率、活跃任务、并行操作、模型 token/调用预算、存储和上传体量；Cell 限制连接、工作槽、队列年龄和数据库压力；供应商维度限制 RPM、TPM 和实际并发。

用户账本是持久权威，向任务预分配有限额度；任务预算继续与准入工作同事务保存。跨节点/端侧额度先在上游保留，再由接收方独立扣减，同一分配不可重复获得。超时、连接断开或租约到期不能自动退还未知消耗或仍可能占用的并发槽。

Redis 快速限流是第一道减压，不是精确扣费依据。多副本额度采用有上界的预分配和结算，禁止失联时每个节点都使用完整余额。供应商不可提供保守消耗上界时，金额只能报告估算和待结算，不承诺无法落实的硬费用上限。

公平队列先按用户轮转/加权，再按该用户任务优先级选取，避免一个用户的大量后台任务占满 Cell。交互任务、后台记忆/评测和控制恢复分池；权限校验、取消和结果核对不依赖目标执行预算尚有余额。全局共享服务还需限制重用户对其他 Cell 的影响。

## 6. 故障域、主备和用户迁移

### 区域内高可用与跨区域恢复

数据库与业务恢复的完整执行步骤、PostgreSQL + Patroni + etcd 参考组合、旧主隔离、同步提交可见性屏障及逐故障自愈矩阵，见 [分布式故障自愈](14-distributed-recovery-and-operations.md)。在途任务按持久检查点续跑，依赖故障不直接批量判败，恢复时先核对原外部操作再分批放行；硬期限、授权与预算仍约束后续执行。生产配置新增的是受控恢复职责，不改变端侧任务拥有权。

生产参考为区域内三个可用区，应用副本分散部署，关键数据库使用跨可用区同步复制。对外声明已确认写入 RPO=0 的前提是提交确实达到规定同步 WAL 持久化、提升的副本包含全部已确认记录、旧主已被可靠隔离；同步条件不满足时不能静默改为异步后继续原承诺。[PostgreSQL 同步复制](https://www.postgresql.org/docs/current/warm-standby.html)、[故障切换与旧主隔离](https://www.postgresql.org/docs/current/warm-standby-failover.html)

基础设施主备切换、Worker 重新领取与任务拥有权移交是三种不同过程。即使数据库无数据丢失，外部动作也可能处于未知状态，仍需核对。只因心跳缺失不能让另一个独立数据副本自行成为任务拥有者。

默认不采用同一用户跨区域多主写入。跨区域灾备若用异步复制，必须报告实际复制滞后和不确定窗口；切换后先冻结可能丢失的操作、额度消费和撤销/删除记录，隔离旧区域并核对外部事实。不可从旧备份恢复后直接重放所有动作、复活已删除内容或重新花费旧余额。跨区域 RPO/RTO 需要另行实测和验收，不能复用区域内结论。

### 用户分片迁移

首选有限停写的单用户迁移，牺牲该用户短时间写可用性以降低双写冲突风险；不中断其他用户。状态在 NamespaceDirectory 和源/目标分区均有可恢复记录。

1. **PREPARE**：固定目标及新 route_epoch，停止该用户云侧新调度和新接纳，排空或明确挂起所有 Store 的后台写入；已发操作继续核对。端侧自主子任务不自动迁移，其结果交接责任必须保留。
2. **QUIESCE**：取得各原子组稳定边界；把任务、操作、授权、预算、Memory 修订/墓碑、Surface、Inbox/Outbox、回执与窗口水位一并复制。记录各 Store 检查点和摘要，目标仅可校验，不可处理业务。
3. **SEALED**：源分区持久化不可写栅栏并核对生效，旧 route_epoch 不能接受提交或发新资格；源端封存结果未知时先查询，不能两边都恢复运行。封存前允许安全中止，封存后不能仅因超时自动解封。
4. **ACTIVATE**：目录以预期版本 CAS 绑定唯一目标及新世代；目标验证源封存证据、完整检查点和目录绑定后激活。激活消息丢失可向同一目标补发；不允许另一目标自行接管。
5. **VERIFY / CLEANUP**：新分区恢复待处理交接，旧路由拒绝或重定向，校验记录和业务对账。保留恢复期后才清理旧副本。已在新分区产生写入后，回退也是新的迁移，不能直接启用旧快照。

数据库内分区栅栏必须覆盖所有业务写路径；暂停调度但漏掉 Memory 修订、UI 输入或异步结果写入，不算完成静止边界。冻结期间新到的可靠消息须在明确的持久缓冲中承接并纳入交接，或在未接纳前返回暂不可用，不能在复制边界之后向源端遗漏写入。

无法证明旧执行资格停止启动新动作时，只迁移数据而不重新发放执行资格；未决外部效果仍按原操作核对。端侧受限数据不因云分片迁移复制上云。

## 7. 评审门槛与实施验证

以下为建议验收目标和试验设计，不是现有 SLA。正常在线、单区域、未触发背压且额度可用时，任务提交至 ACCEPTED 建议 P95 ≤ 300 ms；业务提交至网关发出可见更新建议 P95 ≤ 1 s。分别统计排队、模型首响应/完成和第三方执行耗时，不能从口径中隐藏主要等待；公网端到端时延另测。

| 验证项 | 必须形成的证据 |
| --- | --- |
| 全量与混合负载 | 千万账户元数据、百万 DAU 对应的日轨迹、十万并发在线基准及多端放大；同时运行任务、记忆、UI 和恢复，报告吞吐/分位时延/队列年龄/资源与费用用量。 |
| 性能瓶颈定位 | 实测每实例连接容量、每分片事务/存储上限、模型 RPM/TPM；区分容量目标、测试假设和实测值，推导部署数量而非凭经验列机器。 |
| 用户隔离 | 对数据库、API、缓存、搜索、对象下载、订阅、游标、日志和共享 Worker 做跨用户读写反例；合法多端协作不得被误拦。 |
| 单区故障与重连 | 丢失一个可用区、网关批量重启、连接风暴、慢消费者；已受理工作可恢复且其他用户仍有服务，记录真实 RTO 和不确定操作数。 |
| 在途任务连续性 | 按故障前各执行阶段固定任务集合，核验同一任务续跑、已完成步骤保留、父子等待不级联失败；测量实际推进时间与最终完成比例，保留真实过期/取消/未恢复结果。 |
| 存储与消息故障 | DB 提交回执丢失、旧主/旧 Worker 迟到、Redis 清空、Kafka 重放或不可用；无重复外部动作、无额度凭空恢复、无可靠请求静默丢失。 |
| 迁移与灾备 | 在准备、封存、目录切换和激活处中断；仅一个可写分区，原操作/删除/预算可核对；跨区域按实际 RPO/RTO 声明能力。 |
| 生命周期 | 生成中删除来源、对象发布失败、索引滞后、缓存旧授权、备份恢复；不能绕过来源和用途限制，未完成清理明确可见。 |
| 公平性与成本 | 单用户突发、后台评测高峰、模型限流、未知用量；队列有界、正常用户不被持续饿死、控制可接纳、配额不重复消费。 |

数据库、消息系统和编排平台的具体发布版本须在实现时锁定并记录兼容测试。本文引用官方机制用于论证设计边界，不将官方功能或上面的演算当作本系统已达到千万用户容量的证据。

生产交付还需提供：可复现的部署配置、表与索引迁移、保留/删除策略、容量模型、按故障域的告警与运行手册、备份恢复报告、按原身份对账的自愈证据，以及已知不能自动恢复的范围。每项须对应同一候选版本和拓扑；业务模块验收通过不自动构成生产放行。
