# Lerna Harness 架构总述

> 归档资料：本文件保存整合前的设计来源，不再维护现行规则。请从[当前架构文档](../../architecture/README.md)阅读；历史状态与当时的选型表述仅供追溯。

面向架构评审与研发 · 2026-09-17

本方案面向需要调用工具、等待外部结果、跨端使用个人数据的多步骤任务。核心选择是：**让模型提出下一步，让持久内核保存已经接纳的工作，让执行端确认实际效果。** 由此争取减少故障后的重复工作、无效模型决策和集中式运行的故障影响；端侧任务在本地条件齐备时可以独立推进。

整体机制将一次模型生成、长期任务进度、短期 Worker 领取和外部作业寿命分别管理。模型返回、Worker 退出或连接重建，都不必重建已经接纳的任务意图；已经发出的外部动作仍沿原身份核对。生产分片再围绕这份持久工作分配容量与恢复责任。每个边界都有独立记录和交接成本，后文检验这些成本是否换来了值得的收益。

这些收益有适用条件。短问答可能用简单调用链更经济；已有持久工作流同样能提供恢复能力；端侧独立运行会牺牲失联时的云端接管便利。本文先解释为什么选择当前路线，再给出可推导的收益、代价和推翻主张的试验。

**证据状态：**Go、无独立基础设施的单机基线、三系统可替换、端云灵活部署及千万注册／百万日活／十万在线是既有输入。下文的优化优先级、参考策略和比较方案是本轮设计建议；没有业务实现、性能实测或优势对照结果。公式和数值示例用于推导，不表示达标。

## 1. 先决定优化哪类任务，以及愿意付出什么

优先分析以下负载：一个个人用户任务需要数次决策和工具动作，中间会等待第三方作业、用户输入或设备上线；用户可能改意图、暂停或取消；运行跨过进程寿命，部分数据受端侧驻留约束。这是检验方案的代表场景，不排除问答、GUI 等已确认能力，也不把所有请求都强制编排成复杂工作流。

| 目标冲突 | 本方案的选择及优先级 | 主动接受的代价 |
| --- | --- | --- |
| 快速返回与动作可核对 | 已接纳工作和外部效果可追溯，优先于省掉必要持久提交 | 多次短事务、结果交接和核对延迟；简单请求也有固定开销。 |
| 完成更多任务与不可撤销的错误动作 | 先满足授权、用户控制及效果核对，再在原预算内争取完成 | 效果未知时可能等待，不能用重复执行换取表面成功率。 |
| 模型自由规划与可恢复执行 | 已准入工作由确定规则推进；模型只处理需要新判断的部分 | 要维护状态机、计划与事实的映射；过期提案会消耗重算预算。 |
| 云端统一调度与本地自主／隐私 | 一个任务只有一个逻辑 Owner；端侧 Owner 在本地条件齐备时独立运行 | 断网时云侧不能直接接管；需要封存、激活和控制传播。 |
| 全局资源利用率与故障影响范围 | 生产按用户 Home Cell 分治，持久工作与执行资源分离 | Cell 容量余量、热点迁移和共享依赖治理增加成本。 |

在这些硬边界内，首先比较任务正确完成比例与成功任务总成本，其次比较用户等待、恢复时间和容量。不能通过少测困难任务、停止计入故障等待或放宽权限得到更好数字。

验收目标保持不变：超过 1000 个 API；首次调用正确率至少 90%；有限预算后的任务成功率至少 95%；单步、多步、联网问答和 GUI 分别按 [既定基准](10-evaluation-contracts-and-release-gates.md) 与 [专项验收](11-specialized-validation-and-handoff.md) 检验。架构让这些目标可实现、可诊断的程度需要实测，组件齐全本身不构成证据。

## 2. 四条核心主张：收益如何发生，什么情况下不成立

| 主张 | 机制改变的行为 | 当前能够论证的收益 | 尚不能宣称的结论 |
| --- | --- | --- | --- |
| H1：故障恢复复用已确认工作 | 任务进度脱离 Worker；原操作核对后续跑 | 重算范围可限制到未持久确认或已失效的工作；外部等待可释放本地执行槽 | 任意外部动作恰好一次、零恢复开销、优于所有持久工作流。 |
| H2：模型只处理必要的新决策 | 分阶段发现工具、受控上下文、错误归因和局部重规划 | 减少注入无关 Schema、对已知执行状态反复推理的机会 | 仅凭候选截断或重试即可达到 90%／95%。 |
| H3：部署与模型替换不丢失任务语义 | 任务权威、授权和操作身份由共同契约管理 | 本地齐备的端侧任务不必等云恢复；更换决策实现不必重建已准入工作 | 任意断网都能继续、任意实现无适配成本地替换。 |
| H4：增长与事故在较小范围内处理 | 用户归属分片／Cell，按资源分别限流和扩容 | 局部事故的直接影响与恢复积压可限制到归属用户；历史和正文退出调度热路径 | Cell 数翻倍就吞吐翻倍、共享服务故障不会全局传播。 |

<a id="claim-continuity"></a>
### 2.1 H1：把恢复工作缩小到未完成部分，而不是重新执行整个任务

**场景与对照。** 五步任务完成前两步、第三步外部作业仍在运行时 Worker 崩溃。对照包括“仅保存对话、由模型重新推断进度”的实现，以及同样具备持久检查点的工作流实现。前者用于定位业务进度持久化的价值；后者才用于判断自建内核是否值得，不能只挑弱对照。

**执行机制。** Core 将已准入工作、预算与交接责任原子提交；ExecutionStore 保留启动准备、原 operation_id、外部作业引用及效果证据。等待时持久保存唤醒条件／下次检查时间，Worker 释放不必占用的本地执行槽。重启后读取当前状态和未决工作，查询原作业，合并结果，再推进符合条件的后续工作。故障不会把整个父子任务树批量改成 FAILED。

**收益推导。** 已确认且仍有效的第 1、2 步无需重新规划或执行，第 3 步使用原作业继续核对。恢复成本主要来自当前状态读取、未决操作核对、失效内容重建和后续必要决策；协议不要求重放全部历史才能知道当前进度。数据库、索引和外部查询仍有成本，不宣称恢复是常数时间。

稳定到达率为 λ，本地执行槽实际占用为 a，外部持久等待为 w。若对照在整个任务期间占槽，则占槽并发约为 λ(a+w)；释放等待槽后约为 λa，另外承担持久调度开销。**演算示例：**λ=10 任务/秒、a=10 秒、w=90 秒，对应约 1000 与 100 个槽。这里比较本地调度槽，不是机器数；模型供应商和外部作业的并发配额仍需保留，不能据此宣称系统吞吐提升十倍。异步或持久工作流对照也可能获得同类收益。

**代价与边界。** 每次跨越不可丢失的工作边界都要提交记录；核对可能慢于重新请求。未准入的模型输出可以丢失后重算，已发动作必须先查明；并行执行时可能有多个未确认窗口，不能声称最多损失一个步骤。记录丢失、唯一产物不可用、硬期限／授权到期或外部效果不可核对时，续跑受限；支持 Task 恢复不等于外部 Driver 支持任意断点续传。

**验证／推翻条件。** 同一任务集、预算和故障窗口下，对比重做的已完成步骤、重复副作用、恢复模型调用数、首次有效推进时间、槽位／内存及数据库写放大。固定未决工作量而增加历史长度，检查是否仍扫描全部历史。若持久工作流对照具有相同恢复质量且总成本更低，H1 只能证明采用持久执行的价值，不能证明自建更优。

<a id="claim-decision"></a>
### 2.2 H2：按失败原因选择下一步，把模型用量花在能改变结果的地方

**场景与对照。** 目录有千级 API，名称近似、参数依赖先前结果，任务又有较长历史。比较同一模型与预算下的目录／上下文策略，以及“每次反馈都重新规划”和“保留已准入工作、必要时再决策”。全目录只有在模型输入限制内才作为有效对照；同时纳入具备检索和工具路由的方案，不能把输入溢出当作对照质量差。

![图 K02：分阶段能力发现与执行路径选择](diagrams/review-k02-capability-selection.svg)

**默认机制。** 先用权限、位置和资源约束过滤目录，再召回候选摘要，按确切版本加载必要 Schema。ContextAssembler 优先放入目标、硬约束、未决动作和必要证据，长期历史以可核对引用参与。模型提出有限行动；Core 检查当前版本并准入，已准入且前提有效的工作由运行规则推进。工具返回原作业仍在运行，只更新等待／核对进展，不因每次轮询都重新调用 Brain。

| 观察到的失败或变化 | 应改变的环节 | 为什么这样处理 |
| --- | --- | --- |
| 正确能力未进入候选 | 在查询／时间预算内扩大召回或澄清 | 同一候选集上重复生成，不能补回缺失能力。 |
| 能力正确但参数缺失、对象歧义 | 取得必要信息或询问用户，再构造提案 | Schema 合法不能证明实体和业务参数正确。 |
| 原作业进行中、回执丢失或依赖故障 | 查原操作、持久等待、受控退避 | 外部执行状态已有查询路径时，增加模型推理并不能确认实际效果。 |
| 用户目标、授权、来源或关键事实改变 | 废弃不再成立的提案，对受影响的未准入工作重新决策 | 保留旧输出会把“少调用模型”变成执行过期意图；已准入动作仍须按原操作核对和处置。 |
| 所有必需效果已确认 | 规则核验可机械判定的条件；开放回答再做有证据的综合 | 动作 ACK 与用户目标达成分开，避免模型过早宣布完成。 |

**收益与风险的数量关系。** 设 C 为候选含至少一条正确路径，S 为选对能力／版本／资源，A 为必要参数正确，则首次行动正确率可按条件概率拆解为 `P(C) × P(S|C) × P(A|C,S)`，不假定各环节独立。缩小候选可能节省 token，却降低 P(C)；后两项再强也无法修补召回漏项。每例记录首个错误来源及其他错误标签，不能只报告整体分数。

模型输入由“候选摘要 + 必要 Schema + 当前证据”构成，其预算随实际候选和必要事实增长；它仍包含检索、Describe、压缩及重规划的总开销。候选 8／16 和连续 3 次无进展是 [参考配置](review-reference.md#55-智能参考策略从可替换接口到可比较实现)，并无最优性证据。预算不足时报告覆盖缺口，不能把准备步骤排除在费用之外。

记忆只在存在适用的有效经验时有望减少重复探索：来源、修订、用途与适用条件不符即停止使用。将“无记忆／有效经验／过期或错误经验”成对比较，观察成功率与错误沿用率。多 Agent 也不默认更优：独立子工作、有可判定交付物且资源允许并发时，才可能将串行时间 `Σtᵢ` 换成 `拆分 + max(tᵢ) + 汇总 + 协调`；调用费用和子任务失联成本另计。单纯固定流程可以并行调度工具，无需为每步增加 Agent。

**代价、验证与替换条件。** 检索增加一次发现链路，严格版本检查会废弃已付费输出；错误记忆或过度裁剪会伤害质量。在同一模型、目录、初始状态和总预算下，逐项替换召回、上下文、记忆、重规划策略，再测试最终组合。成功任务成本定义为全部尝试总费用除以成功任务数，并同时报告失败费用、首次正确率、多步成功率、延迟和错误副作用。只有在既有质量门槛达标且预先规定的质量比较通过时，成本下降才算收益；达不到时应扩大／替换检索策略，而不是宣传“更省 token”。

<a id="claim-placement"></a>
### 2.3 H3：把任务进度留在有权推进它的位置，降低对云连接和某个模型的依赖

**场景与对照。** 用户设备有不允许上传的资料，本地已有能够完成相关步骤的能力，云连接中断。对照是云端管理同一任务、设备仅执行远程指令的路线；两者都遵守相同的数据和授权限制，不用违反隐私要求的实现充当低成本对照。

**机制及收益。** 若任务原 Owner 在端侧，且本地模型／工具／资料／持久库与有效授权齐备，其状态提交和下一步调度不必依赖云端响应。原文经本地检索和处理，仅按权限提供必要结果；云侧索引缺失不被解释成零命中。重连后交接事实，仍使用原任务、操作及所有权世代。已经由云侧拥有的任务不能凭断网自行复制到端侧接管。

任务契约由 Core 持有，Brain 只返回提案。因此替换适用的新决策所用模型，不必改写已经准入的操作、预算和固定 Driver 版本。这里的可替换性是有边界的：输入输出、语义、版本、授权和恢复都要通过共同验证，模型质量仍可能变化。

**代价和不适用场景。** 本地存储、模型包、同步和权限过期需要维护，设备永久损坏时可能无法恢复唯一数据。端侧 Owner 失联时云侧等待或完成有排他性证据的移交；“两端都立即接管”不在承诺内。若业务始终联网、数据允许云端处理且无需本地自主，云端统一运行能减少端侧状态与升级负担，是合理替代路线。

**验证。** 将任务预先分为本地齐备、依赖云模型、依赖云工具三组，断云并重启端进程；只对本地齐备组预期继续，其余应保持等待。测量本地可完成比例、资源占用、获准传输字节、重连核对时间及冲突数。若需要上传更多数据或越过授权才能完成，本主张不成立。替换模型／Store／Driver 时分别测契约通过率和改动范围，不以“实现了 Interface”代替互操作证据。

<a id="claim-scale"></a>
### 2.4 H4：按用户拆分热状态和故障范围，使扩容与恢复有明确对象

**场景与对照。** 十万在线中，部分用户有大量等待任务；一个热点用户突发，或一个数据库分片失效。对照是具有 HA、配额和异步队列的共享资源池，不是假定单节点、无隔离的弱实现。两条路线固定总资源及故障余量，再比较利用率和受影响用户数。

![图 S01：用户归属 Cell 的生产部署与故障隔离](diagrams/review-s01-production.svg)

**机制。** namespace 经稳定目录定位 Home Cell／分片；任务原子组在单个事务分区内，跨模块通过持久交接。Gateway、模型调用、执行与恢复分别限额；共享业务领取表退出跨 Cell 路径。当前任务和未决工作使用紧凑热表及待处理索引；历史按时间分区，截图／正文放受控对象存储，恢复义务结束后才清理回执。增加应用实例、数据库分片和 Cell 是三种不同扩容动作。

**收益推导。** 单 Cell 故障直接涉及其归属用户与工作量。若纯粹用于演算，10 个均匀分配且业务依赖独立的 Cell 中损失 1 个，直接归属用户约为 10%；真实影响应以故障前路由和请求轨迹计数，不能从这个比例推出 90% 请求仍成功。共享身份、目录、模型供应商或恢复流量可扩大影响。相对于共享池，收益主要是把局部资源耗尽和恢复积压限制在较小范围；共享池也能通过分区／配额实现部分隔离，须公平比较。

稳态积压清空时间的容量下界可近似写为 `B / (μ - λ)`：B 是待恢复工作量，μ 是包含核对、重投成本后的有效服务率，λ 是同单位的新工作率，要求 μ > λ。**演算示例：**B=30,000 项、μ=600 项/秒、λ=500 项/秒，需要至少约 300 秒；这不包含故障检测、权威恢复和不可查询的外部等待。实际任务成本不等时应换成加权工作量并测长尾。μ ≤ λ 时，重启成功也无法清空积压，必须限新流量、增加有效容量或延长恢复目标。

千万注册不直接决定 Worker 数。生产分册的示例负载为每 DAU 每日 5 任务、峰值系数 10、每任务 3 次模型调用、平均占用 8 秒，对应约 579 任务/秒、1,736 模型请求/秒和 1.39 万模型并发。首先检查模型配额／费用与数据库写放大，增加网关不能解决这些瓶颈；完整参数见 [容量模型](13-distributed-deployment-and-storage.md#1-设计输入与容量模型)。

**代价、验证与退出条件。** Cell 分治降低资源自由共享程度，增加空闲余量、路由和迁移工作。单用户原子组过热不能靠任意打散解决。采用同步 HA 时，还接受副本条件不足导致停写的代价。在相同资源预算下测试倾斜用户、历史增长、单区／Cell 故障及恢复叠加新流量，记录实际受影响用户、健康 Cell 延迟、迁移写停顿、每成功任务费用与积压下降速度。若目标负载在共享池已满足隔离和恢复要求且成本更低，暂不增加 Cell；跨区域主动多主也不因扩容自动成为需要。

<a id="flows"></a>
## 3. 用一次完整执行说明：检查点在哪里，恢复省下了什么

代表任务是“取得获准输入 → 确定目标资源 → 启动异步处理 → 核验产物 → 交付结果”。五步是用于故障分析的业务依赖，不要求所有任务有固定 DAG，也不预先承诺每步都调用模型。

![图 A00：有限决策、原子准入与外部效果闭环](diagrams/review-a00-mechanisms.svg)

A00 中，模型调用与外部动作均在数据库事务外。R 为 RunStore 局部事务，E 为 ExecutionStore 局部事务。以下 R1／E1／E2／R2 是本例的提交位置说明，不新增协议 ID。

| 第 3 步的关键位置 | 已持久化的内容与下一动作 | 在此崩溃后需要做什么 |
| --- | --- | --- |
| R1：Core 接纳有限提案 | 检查任务版本／控制／授权，保存原操作、工作、预算及必要 Outbox | LookupCommit 确认原接纳；未准入输出可重新决策，已经接纳则继续原工作。 |
| Worker 领取 | 条件更新领取代次／期限；生产路径等待约定耐久确认 | 过期领取允许新的恢复者，不能由此推断旧外部调用停止。 |
| E1：ExecutionCoordinator 启动准备 | 原操作、语义指纹、固定实现、资源／许可消费及“可能发出”一起提交，然后 Driver.Start | 查询原操作与效果；不因缺 ACK 换新 ID 重试。 |
| 异步作业已接纳，进入等待 | 保存外部作业关联与下次核对条件，释放可释放的本地槽；外部在途配额保留 | 用 Driver.Inspect 查原作业。作业引用回执丢失时需可用的原幂等键／业务关联，否则保持未知。 |
| E2：效果核清 | 保存结果与证据、报告 Outbox | 补交原结果，不重新启动作业。 |
| R2：Core 合并结果 | 按原操作幂等合并第 3 步事实，提交待推进工作或新的决策需求 | 保留第 1–3 步已确认效果；第 4、5 步仍需当前资格，才继续。 |

R1、E1、E2、R2 是四类业务持久边界，此外还有领取、外部作业引用、Inbox／Outbox 更新及长任务续租；一次工具调用不等于一次数据库写入。它们有些可以在合法原子组内批处理，不能跨独立 Store 假定合并。报价和性能测试按实际提交／WAL／网络往返计数。

本例在模型决定新行动时调用 Brain，在查询已有作业进展和重发已确认结果时无需重新推理；开放式结果综合仍可能需要模型。跨端部署会增加模块交接往返，同机部署可以进程内调用，但持久与授权语义相同。

如果故障发生在 E1 与 E2 之间，恢复收益是复用第 1、2 步和原第 3 步作业；代价是恢复领取、Inspect 和交接提交。未确认的外部效果没有通用的时间上界，不能把这个阶段算成零重做、零等待的完成保证。

![图 R01：有前提的故障自愈与业务恢复](diagrams/review-r01-self-healing.svg)

大规模事故期间按依赖归并故障、停止无效派发、保留结果与控制资源；恢复后先核清在途配额，再公平地分批放行。用户 PAUSE／CANCEL、硬期限和授权仍有效。验收的是同一任务首次有效推进及最终结果；实例存活、任务重新领取或 UI 显示 RUNNING 均不足够。分阶段细则见 [在途恢复](14-distributed-recovery-and-operations.md#32-检查点执行阶段与续跑方式)。

## 4. 组件、协议和存储如何支撑这些主张

组件图用于定位责任。每项抽象都应能追溯到前面的收益或不可违反的边界；没有独立职责的框不应直接变成一个微服务。

<a id="l2-components"></a>

![图 A03：组件职责与依赖索引](diagrams/review-a03-components.svg)

| 责任组合 | 实现上的关键选择 | 支撑的主张与边界 |
| --- | --- | --- |
| Core + RunStore／WorkStore | 状态、工作、预算及交接责任局部原子提交；按版本与领取代次更新 | H1/H3：Worker 与模型可变化，已经接纳的工作仍有权威依据。 |
| Brain + ContextAssembler + Memory／Catalog | 检索和上下文提供受控事实；Brain 返回有限提案；错误可分段归因 | H2：按需决策并比较策略；模型输出本身不成为实际执行事实。 |
| ExecutionCoordinator + ExecutionStore + Driver | 准备、原操作核对、资源控制与结果交接；Driver 声明 Start／Inspect／Cancel 的实际能力 | H1：恢复原动作；Driver 无法核对的效果不能由 Core 猜测。 |
| Authorization + UI + Connection | 权限／控制在处理端落实；输入、控制及正式结果沿原操作交接 | H1/H3：重连恢复既有任务和有效控制，不重新授予权限。 |
| Cell 路由 + 分片 Store + 独立资源池 | 用户数据局部化，持久工作与连接、模型、执行槽分别扩容 | H4：隔离范围和瓶颈可定位；缓存不成为任务、额度或授权权威。 |
| Extension + Evaluation + Observation | 绑定确切实现版本，采集分段证据，用共同用例验证替换和升级 | 四项主张可比较；扩展可接入不等于实际效果已等价。 |

<a id="protocol"></a>
### 4.1 协议选择改变哪些运行行为

同步命令先区分接纳／拒绝，长任务通过原操作查询与正式结果交接完成；因此连接超时不会直接重新创建任务。交付采用持久 Inbox／Outbox 和重复可恢复消费，换取丢回执后可核对的责任；接收端支付去重和保留成本。查询返回来源版本／覆盖，流使用快照与增量补读，避免把缺口解释成完成。委派绑定原有子任务关系与预算预留，子任务失联不会触发新的重复委派。

gRPC、WebSocket 和编码只承载这些语义；选用传输库本身不会带来任务连续性。命令、查询、事实、流、委派的完整规则见 [协议参考](review-reference.md#protocol)。

<a id="data"></a>
### 4.2 存储选择如何缩短调度路径，又增加哪些负担

![图 D04：事务事实、持久交接与可重建数据的存储分工](diagrams/review-d04-storage.svg)

当前状态／未决工作／有效操作回执留在权威热层，以 namespace 和稳定对象键查询；历史和大正文退出工作领取扫描；索引、缓存和 UI 为可重建投影。单机用 SQLite，生产建议按用户分片 PostgreSQL；每个模块仍只提交自己的原子组，模块共库不扩张跨模块事务承诺。

这能把主要调度访问限定在活跃集合，却要求维护索引、对象引用、墓碑、保留水位和跨 Store 交接。未决操作持续增长时热层仍会膨胀，必须背压和处置，不能按固定天数清掉来维持容量。分片按用户解决横向负载，历史按时间分区解决单库保留；两者不能互相代替。物理表族、索引和清理依据见 [存储分册](13-distributed-deployment-and-storage.md#数据族访问路径和保留方式)。

<a id="alternatives"></a>
## 5. 为什么保留自建内核，又在哪些地方优先复用

**当前保留已确认的 Go 自有状态机与当前状态持久化基线，主要理由是单机可嵌入、端侧独立任务权威和共同契约可以直接表达。** 这不是已证明的性能优势；项目同时接下了调度、公平性、故障恢复、Schema 迁移和生产运维的维护责任。

| 可行路线 | 在相同目标下怎样实现 | 相对收益／负担及采用条件 |
| --- | --- | --- |
| 简单异步 Agent 循环 + 持久业务记录 | 用现有服务保存任务与结果，必要处增加幂等和控制 | 短任务、少等待和少端云状态时实现较少；随着恢复、控制和跨端需求增加，应比较是否正在逐步重建同一内核。 |
| 持久工作流承载任务，Harness 提供授权、工具与端侧 Adapter | 引擎承担调度／恢复，工具副作用和端侧拥有权按本项目契约适配 | 可以复用运行机制；代价是语义映射、部署与升级兼容。若相同故障与离线用例通过且总维护成本更低，应评估替换运行实现。 |
| 当前自建 Go 内核 | 当前状态 + 追加记录 + 原子工作交接，模型和工具通过 Interface 接入 | 可按既定本地与端云语义组织实现；正确性与运行工具由项目负责，生产验证成本可能高于复用。 |
| 云端统一 Owner，设备作为远程执行端 | 云侧持久调度，端侧只执行受限命令，私有数据按策略提供获准结果 | 适合稳定联网、无需端侧自主的配置；端侧任务独立运行能力要另行实现，不能靠重连自动获得。 |

成熟运行机制必须进入强对照：Temporal 文档说明基于事件历史恢复 Workflow，并使用 Worker 缓存避免每次从头读取与重放；LangGraph 提供基于检查点的持久化。因此，“能续跑”“不用每次读完历史”不能直接当作本项目独有优势。具体版本的兼容和成本还需实现比较。[Temporal 执行与缓存](https://docs.temporal.io/workflow-execution)、[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)。

自建范围应集中于任务语义、授权／控制、效果核对与端云权威的结合；数据库、传输、模型 SDK 和生产 HA 使用适合的现有实现。PostgreSQL + Patroni + etcd 是待验证的生产组合，其角色是保护数据与单写权威，不负责证明外部任务效果。既有接口允许替换，不代表更换持久运行引擎已经是无成本操作。

<a id="decisions"></a>
## 6. 怎样验证优势，并决定保留、修改或放弃某个选择

先冻结对照实现、版本、数据集、故障模型、资源预算和比较门槛，再执行试验。所有结果保留原分母；真实过期、取消、失败、未知、无输出和设施事故分别报告，评分口径沿用既有规范。下表是待交付的证据，不是测试通过记录。

| 主张 | 最小对照试验 | 必须共同报告 | 不支持主张时的动作 |
| --- | --- | --- | --- |
| H1 连续性与等待资源 | 同任务集比较业务检查点方案和持久工作流；在 R1/E1/外部接纳/E2/R2 注入故障，包含长等待与历史增长 | 原任务续跑／完成比例、重复副作用、重做步骤、恢复模型费用、首推进时间、槽位／内存、提交及 WAL 量 | 修正检查点或核对能力；若强对照更经济，不把自建当成恢复优势。 |
| H2 质量与决策成本 | 固定模型／目录／预算，分别替换召回、上下文、记忆和规划触发，再测试最终组合；保留近义、缺参及错误经验样本 | 首次错误归因、单步／多步质量、错误副作用、全部尝试费用、成功任务成本、延迟 | 召回不足则增强检索；质量下降不能用 token 下降抵消；无多 Agent 收益则保持单 Agent。 |
| H3 端云与替换 | 本地齐备／依赖云的不同任务，断网 + 重启 + 重连；分别替换模型、Store、Driver 并保持在途工作 | 本地可完成比例、获准数据传输、端侧资源、恢复冲突、适配改动和契约／业务质量 | 缺能力则等待或明确缩小支持范围；不要求自主的配置可使用云端 Owner。 |
| H4 隔离与容量 | 共享池与 Cell 固定总资源和故障余量，叠加热点、历史增长、单区／Cell 故障、恢复与新流量 | 受影响用户／请求、健康用户延迟、有效 μ 与 λ、积压清空、每成功任务成本、迁移停顿 | 先解决实际瓶颈；共享依赖传播则补隔离，规模不需要时不提前增加 Cell。 |

收益评估同时包含建设与持续维护成本：记录自建／适配模块、必须维护的故障用例、发布与迁移步骤、告警和人工处置负担；不把尚未估算的工程量写成“轻量”或“易维护”。

实施顺序先跑通第 3 节的完整执行与恢复链，再做 H2 的质量归因和策略比较；随后验证端侧断网／替换，最后在同一生产候选拓扑验证负载与故障叠加。容量、失败率和成本没有实测前，本方案的结论是“这些机制值得验证”，不会给出虚构的百分比提升。

设计保留可推翻性：H1/H3 的契约不成立则该实现不能交付；H2 未达到既定质量目标则继续改策略；H4 的隔离收益不足以抵消成本则采用更简单部署。这使总体选择由任务结果和工程证据决定。
