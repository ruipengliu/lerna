# 分布式故障自愈、恢复控制与运行验收

> 归档资料：本文件保存整合前的设计来源，不再维护现行规则。请从[当前架构文档](../../architecture/README.md)阅读；历史状态与当时的选型表述仅供追溯。

前置契约：[运行内核](02-runtime-and-state.md)、[端云所有权](04-edge-cloud-and-recovery.md)、[执行核对](07-execution-contracts-and-validation.md)、[数据原子组](12-data-path-and-protocol-semantics.md)、[生产部署与存储](13-distributed-deployment-and-storage.md)。

## 1. 自愈的目标与四层责任

自愈的完成条件是：合法请求重新得到服务、故障前已接纳且仍满足续跑条件的任务使用原身份继续推进、已完成步骤保留、未决效果被核对或明确隔离、权限与预算没有回退。**在途任务连续性是验收目标，不能以实例重启成功或重新提交一批任务代替。** 自动化只能使用预先配置的运维权限和业务恢复接口；不能用新的任务或操作身份掩盖未决工作。

| 层次 | 执行者与依据 | 可以自动做什么 | 不据此推导的保证 |
| --- | --- | --- | --- |
| 实例与连接 | 编排控制器、Gateway；实例健康和会话世代 | 移出流量、重建实例、重连、恢复受控订阅 | Pod 存活不代表数据库可写；重连不转移 Task Owner。 |
| 数据库高可用 | PostgreSQL HA 管理器、仲裁存储及旧主隔离设施 | 在数据完整性和排他性前提满足时提升副本、切换写入口 | 数据库主备切换不证明外部动作未发生。 |
| 持久工作恢复 | Scheduler、所属模块的恢复扫描器 | 重新领取恢复工作、查提交/操作、补投 Outbox、补齐投影 | Worker 租约到期不证明旧调用已停止。 |
| 业务效果收敛 | Core、ExecutionCoordinator、Memory/UI 等原权威模块 | 按原身份核对效果，重新校验后继续或保留等待 | 连接成功、消息回执、模型声称完成均不证明业务成功。 |

云侧同一逻辑 Owner 的进程故障可由新的 Worker 使用同一权威库恢复，前提是领取代次和执行资格受约束；它不是把任务转交给另一份独立副本。端侧 Owner 不可达时，仍遵守原拥有者恢复或协作封存/激活的规则。

## 2. 生产恢复组件与依赖

以下是生产配置增加的运行职责，可与既有模块合部署。它们不把 A03 的逻辑组件一一变成微服务。

| 组件 | 输入与输出 | 权威记录 / 依赖 | 写入边界 |
| --- | --- | --- | --- |
| CellRouter / NamespaceDirectory | 可信 namespace → 区域、Cell、分片、route_epoch | 控制数据库；存储分区内另有可写栅栏 | 修改路由需条件更新和迁移证据，缓存不决定新分区可写。 |
| Gateway / SessionRegistry | 已认证消息、连接世代、恢复游标 | 持久会话登记、Home Cell 可靠接收入口 | 仅在持久接收后报告 PERSISTED；业务 ACCEPTED 由原模块返回。 |
| HA Manager | 数据库复制/主角色、仲裁租约、隔离证据 | PostgreSQL、Patroni、etcd 及主机隔离设施 | 管理数据库角色，不改写任务、操作或授权事实。 |
| RecoveryController | 持久工作积压、故障范围、恢复策略 → 有界恢复扫描 | Cell 内的恢复管理记录、模块恢复接口、运维授权 | 编排查找和核对；业务更新必须经所属模块契约提交。 |
| 模块 Reconciler | 过期领取、未决操作、未完成交接 → 核对结果 | Run/Execution/Memory/Surface 等所属 Store | 保持原操作和版本前提，不直接调用私有 Driver 绕过准入。 |
| Observation / 告警 | 恢复阶段、积压年龄、失败与覆盖缺口 | 最小受控诊断记录 | 诊断投影不成为业务恢复的唯一依据。 |

RecoveryController 是本册建议的运维编排职责，不拥有第二份任务状态机。其管理记录只保存故障范围、配置修订、阶段、领取代次、重试时间、扫描游标及证据引用；不复制完整业务状态。按 `(Cell, 资源范围, 故障代次)` 条件接纳恢复工作，多副本竞争领取，接管者从已持久阶段继续。

控制器自身故障时，各模块仍可从业务 Store 找到待恢复工作。管理记录不可用时不新发破坏性的角色切换或迁移；正常业务是否继续由自己的数据库、权限和执行前提决定。避免把整个系统恢复依赖于一个常驻单点进程。

## 3. 自愈控制闭环

![图 R01：有前提的故障自愈与业务恢复](diagrams/review-r01-self-healing.svg)

恢复阶段只用于运维管理，不增加任务公共状态枚举。

1. **DETECT：检测与归并。** 结合就绪状态、数据库角色/复制、领取超时、Outbox/Inbox 年龄及用户可见错误率定位范围。单个心跳超时只形成怀疑；同一范围事件归并为一项恢复工作，避免每条告警启动一次切换。
2. **CONTAIN：限制影响。** 从新流量中摘除故障实例，暂停受影响分区的新资格签发，保留已有结果接收和核对入口。仅冻结受影响的用户、资源或 Cell；未持久接收的新请求明确背压或拒绝。
3. **ESTABLISH：恢复可信权威。** 验证数据库候选完整性、旧主隔离及当前可写分区；按角色条件重新取得工作领取资格。数据库健康不自动授权端侧任务接管。
4. **RECONCILE：按原身份核对。** 查询提交和业务接纳，重放允许交付的消息；外部效果必须 Inspect/Reconcile。同步核对授权、来源修订、资源接管、固定版本及未结预算。
5. **RESUME：原任务分批续跑。** 保留已完成步骤，恢复尚未满足的依赖和原在途操作，重新准入具备条件的后续工作。优先恢复取消、核对和正式结果交接；按用户公平调度和分片水位控制速率，避免积压一次性压垮数据库或模型供应商。
6. **VERIFY：核验与退出。** 检查原工作继续推进、未知效果年龄下降、可靠交接无缺口、旧资格被拒绝、配额无重复使用。阶段事实持久化后才结束恢复；失败按受控退避重试，超过次数/期限或缺少排他性证据时进入显式等待并告警。

暂不可用可自动等待依赖恢复；数据损坏、永久失去仲裁、无法隔离旧主和不可判定的外部写入须升级处理。人工处置也不能直接把未知效果改成未执行；处置记录必须说明实际证据和保留的未知事项。

### 3.1 在途任务连续性与状态映射

基础设施暂时不可用表示当前无法推进，不直接表示用户目标已经失败。主状态沿用 QUEUED / RUNNING / WAITING / COMPLETED / FAILED / CANCELLED；“恢复中”是运行进展说明，不新增公共任务状态。连续性要求覆盖已接纳的排队、执行和等待任务，按 [状态契约](04-recovery-state-and-failure-matrix.md) 处理：

- Worker、数据库、网络或供应商故障时，保留 task_ref、已完成工作、原 operation_id、控制意图与额度账本。仅受影响的分支等待；有其他可执行分支则任务仍可 RUNNING，全部受阻才 WAITING。依赖不可用使用 DEPENDENCY，效果未知使用 RECONCILIATION；原 INPUT / AUTHORIZATION 等待继续保留。
- 依赖恢复后，Scheduler 重新取得合法领取，Core 核验当前拥有者、版本、权限、用户控制、预算和期限，按持久工作及依赖关系继续。用户 PAUSE / CANCEL、授权撤销和资源接管均不能被自动恢复清除。
- 父任务看到的是子任务的依赖等待或核对进展；不将失联等同于子任务失败并向所有祖先传播。父子关系与预算预留保持原记录，恢复结果交接后再决定后续工作。
- 权威数据库不可用时无法提交 WAITING，保留最后已确认状态，查询端明确标注其版本、陈旧性和“依赖不可用、等待恢复”；不能伪称已经完成状态转换。权威恢复后逐项核对，不通过批量改成 FAILED 或重置 QUEUED 来清理积压。
- 只有确认目标无法完成、必要在途处置完成且关键效果已核清，才满足 FAILED 条件。取消、真实业务期限届满及不可恢复的数据丢失按各自规则处置；即使不能继续，也须保留已发生效果和原因。已进入终态的任务不重开。

### 3.2 检查点、执行阶段与续跑方式

续跑恢复的是持久业务进度，不要求保存进程栈或模型的每个生成 token。检查点由原 Store 和工作账本组成：RunStore 保存任务/计划修订、已准入及已完成工作引用、依赖与父子关系、有效等待项、控制来源、预算预留和期限；ExecutionStore 保存输入语义指纹、固定能力/Driver 版本、原操作与外部作业引用、执行阶段和效果证据。跨 Store 交接仍通过原操作及 Inbox/Outbox 核对；不能假定两库快照属于同一事务。来源、产物和恢复记录在履约前保留，权限及删除要求变化时按现有规则阻止继续使用。

| 故障时所处阶段 | 持久依据 | 恢复后的推进方式 |
| --- | --- | --- |
| 任务已接纳，尚未调度 | 原任务、工作项、提交回执 | 重新领取原工作；不要求用户重新提交任务。 |
| Brain 正在生成，提案尚未准入 | 当前任务快照、已预留生成额度 | 先核对是否已有准入提交；确无准入时，可在剩余预算内重新生成。丢失的输出不能执行，未知用量仍占用，不承诺模型输出完全相同。 |
| 提案已准入，工作尚未开始 | 准入版本、原操作、固定实现及工作项 | 保留原准入工作，在当前资格和耐久条件满足后继续派发，不重新创建整份计划。 |
| 启动已准备，请求可能发出 | ExecutionStore 启动记录、语义指纹、原操作 | 查原提交并 Inspect/Reconcile；没有发出回执不等于未执行。仅在可证明的安全重试前提下再发。 |
| 外部异步作业 IN_PROGRESS | 原作业引用或可核对的原幂等键 | 通过 Driver.Inspect 重建查询/受控回调，等待原作业完成；Worker 重启不重新 Start。Driver 没有通用 Resume，外部作业自身能否断点恢复须由能力声明和实测证明。 |
| 效果已完成，结果交接尚未完成 | 效果证据、原结果与 Outbox | 补交原结果，Core 幂等合并后继续依赖它的步骤；不再次产生外部效果。 |
| 等待用户、授权或子任务 | 原等待项版本、子任务引用及未结预留 | 恢复原等待和界面，核对期间到达的结果；不重建子任务，不将旧回答绑定到新的等待项。 |
| GUI 工作在动作之间中断 | 原动作记录、当前控制权与最新可获准观察 | 先核对旧动作，再重新观察界面并决定剩余步骤；不能沿旧截图坐标盲目点击。 |
| 多步骤任务部分完成 | 已完成工作及证据、尚未满足的依赖 | 保留已完成效果，从下一项符合前提的工作继续；后续动作需当前条件，不能机械重放整条流程。 |

例如五步任务的第 1、2 步已经完成，第 3 步是仍在外部运行的异步作业，第 4、5 步尚未开始。Worker 或可用区故障后，新 Worker 读取同一任务，查询第 3 步的原作业：仍运行则等待，已完成则合并原结果，再执行第 4、5 步。第 1、2 步不重做，第 3 步不重复创建。若其效果无法查明，相关分支保持核对等待；其他无依赖分支可以继续。

部署升级也必须保留在途工作所固定的实现及恢复 Schema，直到完成交接或兼容迁移。丢失固定版本、唯一正文或外部作业核对依据时，不能声称支持自动续跑；应明确能力缺口和处置方式。

### 3.3 期限、预算与故障等待

大量失败常来自把每次调用超时直接升级为任务失败，或恢复后统一重试耗尽额度。生产策略应在接纳时固定适用的期限和预算配置，并分别处理：

| 约束 | 故障期间与恢复后的规则 |
| --- | --- |
| 连接 / 单次调用超时 | 结束本次等待或返回结果未知；保留原操作和核对责任，不据此直接结束整个任务。 |
| Worker 领取租约 | 允许其他 Worker 竞争恢复责任；不证明旧外部工作停止，也不自动释放在途执行配额。 |
| 依赖故障退避 | 保存下次检查时间，释放不必占用的 Worker；已知依赖不可用时暂停新派发，避免每个任务持续实际调用失败。恢复扫描与业务模型纠错分别计数。 |
| 用户 / 业务硬期限与授权有效期 | 按原时间到期，不因系统事故自动延长。期限届满后停止新增目标工作，在有界处置额度内核对已有动作；授权或期限修改须由有权主体明确提交。 |
| 运行时长与费用预算 | 默认沿既有墙钟和总额度规则，等待不隐式扣除；已消费与未知预留不重置。若产品另提供可暂停的有效执行时长，须在接纳时声明、持久计时并另有最长保留期限，不能事后改口径。 |
| 自动恢复上限 | 达到恢复次数/处置期限后转显式等待并升级，保留原工作和未决事项；不靠无限轮询占用资源，也不把“停止自动尝试”写成“业务效果已失败”。 |

基础设施恢复不能保证任务跨过任何长度的中断都能完成。硬期限、授权、外部状态、固定实现和预算仍需满足；要提高中断后的完成比例，生产任务需提前配置符合业务需求的恢复窗口与资源余量。所有真实调用仍计费用和额度；业务端到端耗时包括故障等待。既有评测的 120 / 600 秒墙钟时限及评分口径保持不变，不能用暂停计时或重新提交样本掩盖失败。

## 4. 数据库自动切换的参考配置

### 4.1 选型、放置和耐久性

建议首个自托管生产验证采用 **PostgreSQL + Patroni + etcd**：每个业务数据库分片一主两备，分布在三个可用区；Cell 内的 etcd 使用三个成员、每区一个。应用资源池由 Kubernetes 管理；数据库使用可落实主机隔离的专用 Linux 节点/VM。一个 Cell 的 HA 仲裁与其他 Cell 分开；区域目录等共享控制数据库使用独立 HA 组，其故障范围单列。

参考配置使用 `synchronous_mode=on`、`synchronous_mode_strict=true`、`synchronous_node_count=1`，业务变更保持 `synchronous_commit=on`。同步副本不满足时阻塞该分片新写入；提升候选须满足 HA 管理器的同步状态与资格约束。三副本不等于任意两个故障都可用，不把落后的剩余副本提升成满足原耐久承诺的主库。该取舍以写可用性换取已确认提交的耐久边界。[Patroni 复制模式](https://patroni.readthedocs.io/en/latest/replication_modes.html)

etcd 用于数据库 HA 仲裁，不保存任务、去重账本或用户正文。三个成员形成的多数派可容忍一个成员故障；失去多数派时不能凭本机缓存重新签发数据库领导权。[etcd 仲裁与故障说明](https://etcd.io/docs/v3.6/faq/)

旧主隔离采用已验证的 Linux watchdog／独立主机断电隔离能力；使用 Patroni watchdog 时要求 `mode=required`，验证超时和安全余量覆盖进程暂停等故障。环境无法提供适用的隔离证据时，不开放无人值守提升；只删除 Kubernetes Pod 或修改服务地址不能代替旧主停止写入的证明。[Patroni watchdog](https://patroni.readthedocs.io/en/latest/watchdog.html)

这些参数表达验证起点，不是可直接投产的完整配置。连接入口、证书、复制槽/WAL 空间上限、超时组合、备份与恢复版本均需在实际环境锁定。托管数据库可以替换该组合，但必须提供相同故障模型和验证证据。

### 4.2 本地可见与可对外执行之间的耐久屏障

**读取到一条数据库记录，不总能证明它已经达到同步耐久条件。** PostgreSQL 在等待同步复制确认期间被取消的事务，可能在主库上可见，却在提升副本后消失。因此，不能只通过“查到了 Outbox / 工作 / 启动记录”便发出外部动作。[同步提交取消的限制](https://patroni.readthedocs.io/en/latest/replication_modes.html)

Store Adapter 的参考实现应满足以下顺序，具体实现在故障试验中验证：

- 正常提交只有在要求的同步提交成功返回后，才向调用者报告耐久成功并开放对应后续动作。
- 从扫描器读取的工作、Outbox 或启动准备，先在**同一权威数据库和当前写入资格下**完成条件领取/确认事务，并等待该事务满足同步耐久条件，再调度、发布或启动动作。不能把裸 SELECT 的可见性作为发布许可。
- 原提交结果未知而记录已经可见时，`LookupCommit` 需要建立相应的耐久确认。可由同一数据库上的后续小型确认事务构成 WAL 顺序屏障；确认结果未知则继续返回未知。确认与原记录的语义/版本绑定，数据库角色切换后重新查当前权威。
- 屏障只解决局部记录的复制耐久性。执行端仍复核操作身份、当前资格、授权和资源控制；已发外部请求仍按效果核对，不能从 WAL 或数据库角色推断其未发生。

必须注入“原事务本地提交 → 等待复制时取消 → 扫描器看见记录 → 主库故障”的窗口。验收断言是未达到约定耐久边界的工作不会被当成已获准的新外部动作；已经发生的动作始终有可恢复的原操作依据。

### 4.3 切换顺序及退出条件

1. 故障被 HA 管理器确认后，写入口停止向不可写节点分配新连接，应用保留未确认提交身份。
2. 仲裁和隔离机制确认旧主不能继续接受有效写入；无法满足则保持该分片不可写，不强制提升。
3. 仅提升满足同步资格和完整性要求的候选；更新写入口。已有连接失效后，客户端重建连接并查询原提交，不盲目重放事务里的业务意图。
4. Store 复核 namespace 可写栅栏、当前任务/Worker 资格及耐久确认；先恢复核对，再开放新工作。
5. 旧主重新加入前以新时间线重建/同步并验证，不能带着原数据和旧写入口直接恢复主角色。

自动切换期间，未收到成功回执的提交可能已经生效，也可能在当前权威上未成立，统一从原身份核对。RPO=0 只可用于经验证故障模型中、确实获得规定耐久确认的写入；未知提交和外部效果单独报告。

## 5. 故障与自愈矩阵

| 故障 / 检测信号 | 恢复执行者与动作 | 开放工作的前提 | 不满足时的状态 |
| --- | --- | --- | --- |
| Gateway 崩溃 / 大量断连 | 编排恢复实例；客户端抖动重连，SessionRegistry 建立新世代，按游标和原操作补读 | 重新认证、当前披露权限、可靠接收入口可用 | 排队或明确暂不可用；旧会话无新资格。 |
| Worker 崩溃 / 领取超时 | Scheduler 条件领取新的恢复代次，读取原工作和固定版本，核对提交/调用 | 当前逻辑 Owner、控制意图、领取代次、预算有效 | 等待；不重置预算或生成新动作身份。 |
| 数据库主节点故障 | HA Manager 按第 4 节隔离旧主、提升合格副本、切换入口 | 仲裁、耐久数据和排他性证据齐备 | 分片停写；不提升无法证明完整性的副本。 |
| 网络分区 / etcd 失去多数派 | 停止无资格的领导权与受限新工作，依既定隔离时序自降级；等待仲裁恢复 | 当前权威可验证，旧资格失效 | 明确不可写；不能让两侧各自继续。 |
| Kafka 暂不可用 / Outbox 年龄增长 | 发布器按原消息补投；恢复扫描继续处理本地已持久工作；限制新接纳 | 未结交接载荷与回执仍保留、消费者可去重 | 有界积压，跨模块后续工作等待，不静默丢失。 |
| 消费者失败 / 单条内容持续报错 | 条件重领、退避；隔离坏消息并保留原载荷引用和原因 | 原操作可核对；有序聚合的缺口已解决或进入快照恢复 | 该聚合暂停，其他聚合继续；不能跨过缺口伪造连续确认。 |
| Redis 清空 / 索引损坏或滞后 | 按受控快照和增量重建；限制回源并标记覆盖缺口 | 当前权限/来源版本复核通过 | 降速、部分结果或等待；不从缓存恢复余额或拥有权。 |
| 对象存储写失败 / 引用不可读 | 持久保存暂存状态，重试获准上传；校验后由业务事务发布引用 | 正文和摘要可核验，来源及用途有效 | 不发布缺失的唯一正文；孤儿按保守规则清理。 |
| API 已生效但回执丢失 | ExecutionCoordinator 用原 operation_id Inspect/Reconcile | 效果已确认，或目标仍有效的幂等机制 / 旧请求不会再执行的证据 | 保留效果未知；不换新 ID，也不切 GUI 重做。 |
| 模型限流 / 超时 / 格式错误 | 区分依赖故障与输出纠错，有界退避，当前配置允许时换模型；保持预算与位置限制 | 新请求仍获准且有预留额度 | 暂不可用等待；确认无法继续时按终态条件处置，未知模型用量不归零。 |
| 端侧 Owner 失联 | 本地在有效资格内继续；云侧查询等待，能协作时封存/激活移交 | 有排他性移交证据，或原 Owner 自行恢复 | 保留相关等待，不把云数据库切换当作端侧接管。 |
| 单可用区故障 | 存活应用承接、数据库按条件切换、重连/扫描限速 | 剩余容量、仲裁与同步条件满足 | 按 Cell 降级或背压，核对与控制优先。 |
| 整个 Cell 不可用 | 区域入口隔离该 Cell，其他 Cell 继续；原 Cell 恢复或按灾备流程重建 | 当前可写分区和业务事实可以证明 | 受影响用户等待；不会自动散发给多个空 Cell。 |
| 区域灾难 / 恢复旧备份 | 隔离旧区域，建立恢复范围和丢失窗口，核对操作/额度/授权/删除，分阶段开放 | 数据与执行资格收敛；未决事项明确隔离 | 人工升级和受控恢复；不承诺跨区域零数据损失。 |

## 6. 恢复风暴、重试和背压

恢复工作按用户与聚合分组，以 Cell 为容量隔离单位。扫描采用稳定游标、小批次和下一次重试时间；唤醒消息只加速调度，持久扫描保证漏通知后仍可恢复。不得用全库轮询每个终态任务来实现恢复。

恢复策略作为版本化配置，至少包含退避上限、抖动、最大次数、期限、每用户/分片并发、每批条数、依赖熔断和重新开放水位。单项操作在同一时刻只由一个恢复领取者推进；不同聚合不因一个坏消息共用全局阻塞锁。

控制与效果核对保留独立但有界的槽位、连接池份额和处置预算。数据库容量、外部服务或处置预算不足时明确保留未决，不能靠无限重试满足表面上的自愈。对重连、补读、对象回源、索引重建和新任务分别限流，恢复速率以最慢依赖的安全容量为上限。

同一依赖故障按 Cell/分片/供应商归并，调度入口熔断并以少量探测确认恢复，不让每个在途任务各自消耗一轮失败调用。熔断用于限制派发，不能代替任务自己的执行资格。依赖恢复后，先核对仍在外部执行的工作及其配额占用，再从小批次逐步放量；通过率、延迟、队列年龄或剩余容量恶化则收紧。已经接纳的恢复工作与新工作使用有上限的独立份额及用户公平调度，防止恢复长期饥饿或挤垮正常服务。依赖不可用、等待和效果未知分别统计，不触发逐层的批量 FAILED。

数据库磁盘/WAL 逼近上限时先阻止新负载增长，查明复制槽、Outbox 和归档积压。不能自动删除尚承担恢复责任的操作回执、WAL 或交接载荷；空间恢复与恢复窗口必须一并验证。

## 7. 备份恢复与生命周期

副本提供故障切换，备份提供独立的恢复来源；两者分别验收。每个分片保存可恢复基线、连续 WAL 归档及备份目录，正文/产物有对应版本与摘要。备份目录记录 Schema/扩展版本、检查点、对象引用、操作/窗口水位、策略与删除进度，以及可用密钥版本。

恢复到隔离环境后，先验证可读性和业务引用完整性，再处理路由、旧执行者和恢复水位。已清理来源、撤销授权或已消费额度可能晚于备份，必须根据仍可取得的后续记录/外部事实核对；缺少证据的范围保持不可披露或不可新执行。备份恢复不是把任务数据库回滚到某一时刻后直接继续运行。

索引和缓存从当前获准权威重建。跨 Store 没有全局事务快照时，备份记录各局部一致点，恢复利用原操作、Outbox 和来源版本补齐交接；不能假定所有模块的同一墙钟时间代表共同一致点。需要整体维护快照时应单独配置停写和检查点流程。

## 8. 可观测性、恢复目标与故障演练

记录 `T_detect`、`T_contain`、`T_authority`、`T_reconcile`、`T_service` 和积压清空时间，区分数据库可用、业务可接纳和业务已收敛。RTO 统计从故障发生到约定业务服务恢复；不能仅用 Pod 启动耗时替代。RPO 以丢失的已确认事实及其范围核对，效果未知数另报。

| 观测维度 | 关键指标 | 触发的处理 |
| --- | --- | --- |
| 用户可用性 | 接纳成功率/延迟、等待年龄、控制请求受理与落实差值 | 定位 Cell/依赖，限制新负载，保留控制路径。 |
| 在途任务连续性 | 原任务续跑比例、故障后首次有效推进时间、最终完成比例、误判终态数 | 对照故障前任务集合及阶段，查丢失工作、重复动作和恢复饥饿。 |
| 恢复进度 | 各阶段持续时间、未决效果数及最老年龄、恢复失败率 | 超时升级；不能让长期未知藏在普通重试队列。 |
| 数据完整性 | 复制滞后、同步确认等待、缺口、水位、旧资格拒绝数 | 阻止不合格提升/派发，核对原身份。 |
| 积压与资源 | Outbox 年龄/字节、待领取年龄、WAL/磁盘、连接池排队 | 背压、限流、扩容或迁移；保持保留窗口。 |
| 公平性与费用 | 每用户队列等待、模型请求/用量、未知预留、恢复资源占比 | 限制热点，冻结未结额度，调整获准配置。 |

首版演练必须覆盖：杀 Worker、杀 Gateway、数据库提交回执丢失、同步确认期间取消、旧主进程暂停、单区网络隔离、仲裁失去多数派、Kafka/Redis 不可用、毒消息、对象写入失败、端侧失联、删除后恢复旧备份，以及恢复流量与正常流量同时达到设计峰值。

每次演练固定配置、数据集、负载、注入时刻、预期不变量和停止条件，保留提交/操作/实际效果的对账证据。注入期间继续发送正常用户请求，检查故障范围没有扩散。故障结束后的“队列最终清空”不能抵消期间的重复副作用、越权披露或已确认记录丢失。

在途任务演练在故障前固定队列、模型生成、调用已发、外部作业运行、结果交接、用户等待和子任务等待等阶段的任务集合。分别测量原 task_ref 下的首次有效推进（包含核对到原作业完成）、最终完成及未决效果；单纯领取成功或显示 RUNNING 不计续跑。连续性子集按预先声明的耐久、可核对、权限/期限和预算条件划定，不能将恢复失败的任务事后剔除；同时保留初始全集的完成、取消、真实过期、未知及丢失数量。测量从故障开始到推进的用户等待，也测量依赖恢复到推进的调度延迟。

验收至少断言：在声明的可恢复故障与负载边界内，符合条件的任务在预设恢复期限内用原身份继续；已完成工作不重做，未知动作不重复启动，瞬时设施错误不被误判为任务终态，父子任务不因失联发生级联失败。另注入故障期间 PAUSE/CANCEL、授权过期、预算不足、短硬期限、旧 Worker 迟到和恢复时二次故障，验证应等待/处置的任务不会被强行续跑。恢复成功率不能替代业务成功率，未完成任务和真实期限损失须在报告中可见。

当前仅确定测量方法；恢复时间门槛、容量水位、退避与租约参数需由首轮基准试验提出并冻结，再用于故障验收。生产放行要求同一候选拓扑完成容量、单区故障、迁移及备份恢复验证；单机契约测试和官方组件功能不能替代这些证据。
