## 1. 逻辑对象、写入权威与依赖

下表是逻辑模型，不要求一对象一张表。所有个人业务对象均处于受认证身份绑定的 `namespace`；跨作用域引用必须显式且经过授权。修订、拥有者世代、工作领取代次各有用途，不能互相替代。

| 对象 | 最小关键数据 | 生产者、写入权威与主要消费者 |
| --- | --- | --- |
| Task / Owner / Work | task_ref、目标和约束、state_version、状态、控制来源、owner_ref/owner_epoch、工作依赖/领取代次、预算预留 | Task Core 经 RunStore 提交；Scheduler 领取工作，Brain 只读取版本化快照，执行报告由当前 Core 接纳。 |
| Operation | operation_id、不可变种类/目标/语义摘要/业务期限、接纳状态、关联任务和结果引用 | 对应业务处理模块接纳；执行、记忆、授权等分别持有专有状态。UI、转发节点和恢复逻辑引用同一身份，不重复创建另一层业务操作。 |
| ExecutionRecord | 执行类 operation_id、能力与版本、输入引用、执行资格、阶段/结果/效果维度、观察和核对证据 | ExecutionCoordinator 经 ExecutionStore 写入；Driver 报告事实，Core 将获准的事实纳入任务。 |
| Message / Inbox / Outbox | message_id、reply_to、业务引用、交付类型、流位置、交付/处理进展 | 发送方持久交付责任，接收方保存去重和待处理项；Message 不是业务完成的权威。 |
| ContextSnapshot / Dependency | task_ref、任务版本、组装版本、来源 Ref 和修订、用途、允许处理/披露位置、有效性 | ContextAssembler 组装并验证；Brain 消费，Core 在准入时复核。可重建内容不充当唯一运行记录。 |
| MemoryRecord / Collection | 集合和记录 Ref、revision、类型、内容引用、来源/时间/置信度、用途/驻留策略、删除状态 | MemoryService 通过集合单一修改权威提交 MemoryStore；查询、同步、索引及上下文读取获准投影。 |
| Evidence / Artifact | 受控 Ref、内容摘要、来源、产生时间、版本、数据策略 | 获准采集或执行模块产生；元数据由所属模块管理，正文可在对象存储或端侧。引用可见不等于正文可读取。 |
| Grant / Policy / ResourceControl | 主体、资源/动作/范围、修订、有效期、撤销/消费进展；资源控制世代 | AuthorizationStore 管理授权和策略；ExecutionStore 管理执行资源控制。处理端复核，缓存和 UI 不具签发或恢复权限。 |
| Interaction / Surface / ActionRoute | interaction_id、处理模块、输入约束、期限/状态；surface_ref、revision、来源版本；原操作引用、原输入摘要、固定映射/Schema 版本、规范化摘要与目标 | 等待项归提出它的 Task、Authorization 或登记应用模块；SurfaceStore 只管理呈现状态与可恢复转交。 |
| Evaluation / Candidate / Activation | 不可变计划、样本/证据/报告引用、比较结果、候选精确版本、发布阶段、节点激活修订 | EvaluationStore、EvolutionStore、ExtensionStore 分责写入；运行结束、评测通过、发布获准、节点生效四者分开。 |

关键基数：一个 Task 可以关联多个 Operation；一次 Operation 可以经历多条 Message 和多次内部 Commit；一个等待项可以被多端呈现，但只按业务约束消费；一个 ContextSnapshot 可以依赖多个来源修订，同一来源修订也可以支撑多个上下文或索引。

### 操作身份如何跨模块保持唯一含义

沿用操作 ID 内部绑定接纳窗口的设计。窗口登记必须确定 `namespace`、允许的操作种类、唯一接纳权威和有效范围；同一 ID 的首次接纳不能被路由到两个可独立定义其含义的业务权威。端侧自主运行使用已获准、由该端持有的接纳窗口，不逐次依赖云端分配 ID。

接纳权威持久化规范化的种类、目标、语义摘要和期限，相同 ID 携带不同语义一律返回 `IDENTITY_CONFLICT`。操作路由到错误领域或错误权威时拒绝或转交原权威，不能在另一张模块表中悄悄接纳为新操作。移交时一并迁移操作记录、窗口关闭水位及路由责任，旧权威不能再次首次接纳。

UI 先根据登记的事件绑定规范化为具体业务意图，再建立 ActionRoute；例如输入框提交规范化为 `TaskService.ProvideInput`。UI 包装类型不构成另一种业务 Operation。持久化转交记录和业务模块最终接纳记录引用同一规范化意图，重复转交返回原结果。

## 2. 原子提交组与跨组交接

| 原子组 | 同一本地事务必须包含 | 事务之外及恢复方式 |
| --- | --- | --- |
| RunStore：单任务 | owner/epoch、任务版本及控制前提校验；状态、准入操作映射、待处理工作、预算预留/结算、提交回执、必要 Outbox | 模型、工具、子任务、记忆和 UI 调用均在事务外；提交未知先 LookupCommit，跨组受理未知先 LookupOperation。 |
| ExecutionStore：操作及相关资源控制 | 操作去重、输入与资格、资源控制前提、启动准备记录、局部状态和结果 Outbox；效果报告另一次提交 | 必须在外部调用前保存“已准备、可能发出”的恢复事实；调用结果丢失先 Inspect/Reconcile，不以重新发动作代替查询。 |
| MemoryStore：集合内变更 | 当前修订/权限前提、记录或墓碑、操作回执、变更日志及必要失效通知 | 索引重建、派生清理、远端副本应用分别推进；不能宣称全球同步删除。 |
| AuthorizationStore：授权管理 | 授权/策略修订、原操作回执；交互批准时包括等待项消费和签发结果；必要通知 | 任务/UI 通过幂等交接取结果；权威撤销、执行端知悉与已经发生的动作分别记录。 |
| SurfaceStore：单 Surface | 预期 revision、来源版本、呈现快照或可重建引用、动作路由记录、提交回执及必要 Outbox | 原任务/授权等待项不搬入 UI 事务；转交成功但 UI 未记账时查询原业务操作并补齐投影。 |
| Evaluation / Evolution / Extension | 各自管理对象的版本、操作回执、证据引用或阶段/本地激活绑定、后续工作和 Outbox | 评测任务、跨模块发布和各节点激活均分别核对；不存在跨节点全局激活事务。 |

物理上共用数据库也不自动扩大上述契约。一个原子组必须完整落在一个事务分区；拆分存储时先持久化交接责任，再做远程调用。消息系统承接投递，不充当任务、额度、授权或执行事实的唯一存储。

### 所有链路共用的恢复骨架

1. 当前认证和权限检查先于操作结果披露；原操作重试先查既有接纳结果，再对真正的新操作检查预期版本。
2. 接收可靠消息并持久化 Inbox 后才能回复 `PERSISTED`；待处理项必须可扫描恢复，不能回执后仅留在内存队列。
3. 业务处理模块完成准入和本地持久提交后报告 `ACCEPTED`。队列位置、资源实际取得和外部效果仍单独报告。
4. 跨组交接以同一 operation_id 查询、补投和对账。观察到传输超时只说明本次等待失败，不足以断言未提交或未执行。
5. 关键记录清理前先持久化关闭水位；旧操作记录不可得时报告 `RECEIPT_EXPIRED` 等明确边界，不能重新首次接纳。

原生报告继续分别表达执行阶段 `NOT_STARTED / IN_PROGRESS / FINISHED / UNKNOWN`、结果 `SUCCESS / FAILURE / UNKNOWN`、效果 `NOT_APPLICABLE / UNVERIFIED / CONFIRMED / CONTRADICTED`。`ACCEPTED`、`FINISHED`、`SUCCESS` 均不能单独证明整个任务完成。

## 3. 补齐任务暂停、恢复和子任务控制

### 对外接口

| 方法 | 请求 | 接纳与结果语义 |
| --- | --- | --- |
| TaskService.RequestPause | operation_id、task_ref、expected_state_version、原因、scope=`SELF` 或 `SUBTREE` | 默认 `SUBTREE`，创建一个有来源的暂停意图；提交控制来源、有效控制状态及传播 Outbox。返回受理结果和可查询的落实进展，不承诺所有节点立即停止。 |
| TaskService.RequestResume | 新 operation_id、task_ref、expected_state_version、target_pause_operation_ref | 明确解除指定暂停来源；传播范围沿用该暂停，不允许借恢复扩大范围。其他暂停、取消、授权等待或资源接管继续有效。 |

请求需有目标和范围内的控制权限；`SUBTREE` 只覆盖受该任务管理的委派树，不覆盖无关独立任务。新操作版本冲突返回 `VERSION_CONFLICT`；同一原操作重试返回原受理结果，不因任务版本后来变化而误报新冲突。终态不重开；恢复不撤销已受理取消。

### 控制来源与合并规则

在 Task 的运行状态中保存暂停来源集合，每项至少包括：`origin_task_ref`、`origin_pause_operation_ref`、来源控制修订、传播范围、`ACTIVE / CLEARED`、接纳及落实进展。使用既有对象引用，不引入新的全局控制 ID。

有效控制意图按以下规则计算：已接纳取消优先；否则存在任一有效暂停来源即为 PAUSE；否则为 RUN。RUN 只表示暂停/取消不再阻止调度，不代表输入、权限、资源或依赖已经满足。

父任务恢复只把对应的来源标为 CLEARED。子任务用户另行发起的暂停、其他祖先的暂停、资源接管以及取消均不得被清除。暂停后的恢复应以新的操作提交，不能修改原暂停操作的不可变意图。

### 传播与乱序恢复

1. 父任务接纳暂停时，RunStore 同时保存来源和针对已委派子任务的传播工作。暂停有效期间不创建新的自主子任务；提交未知的旧委派仍须核对，并将该来源传给确认存在的子任务。
2. 传播携带受信委派关系、根暂停来源及单调的来源控制修订。对子任务的控制是新的、目标明确的子操作，分配并持久保存稳定 operation_id；重投不换 ID，也不把根操作改写为另一个目标。
3. 子任务在自己的事务内去重并校验委派链和权限，保存来源，继续向受辖后代传播；父子之间没有共同事务。
4. CLEARED 可以先于 ACTIVE 消息到达：子任务保存该来源的关闭修订，后到的旧 ACTIVE 不生效。关闭记录按照控制恢复窗口保留，清理后仍须能拒绝过期接纳。
5. 每层分别记录本地接纳、下游待送达、已接纳和实际落实。`SUBTREE` 只有相关后代都已停稳/处置且无关键效果未知，才可报告整个范围已落实；不可达后代不算成功。

暂停只阻止新工作；已开始工作按能力声明暂停、取消或核对。没有通用的“冻结外部副作用”能力。任务可能在暂停处理中仍为 RUNNING，停稳后为 WAITING；恢复后重新判定可调度工作，不清空其他等待原因。

## 4. 补齐独立 UI 的状态权威与存储

### 模块和接口

新增逻辑模块 `UIStateManager`，作为 `UserInteractionService` 的状态实现；它可嵌入进程，不要求独立部署。参考实现使用 SQLite 适配的 SurfaceStore，生产实现遵守用户分片规则。

| Interface | 必须保持的契约 |
| --- | --- |
| SurfaceStore.Load | 按 surface_ref 返回快照、revision、受控来源引用和有效路由；调用前由服务检查权限，查询不是远程任意读库。 |
| SurfaceStore.Commit / LookupCommit | 在预期版本下原子提交呈现状态、动作路由、回执及必要 Outbox；提交未知按原 change_id 核对。 |
| SurfaceStore.ReadChanges | 返回以快照边界为基准的有界变更；游标绑定 Surface 世代，过期需重新取快照。 |
| SurfaceStore.ListRecoverable | 扫描待转交、结果待核对及状态待发布记录；不得依赖重启前内存订阅才能发现工作。 |
| UIStateManager.SubmitAction / GetActionResult | 规范化登记事件、保存转交责任并调用目标处理模块；查询原业务结果后更新 UI 投影，不自行判定业务成功。 |

`surface_ref=(namespace, endpoint_ref, surface_key)` 沿用现有模型。SurfaceStore 的权威是“该界面该显示哪个已知版本”，并非底层任务、授权或效果的权威。快照保存完整可恢复内容，或保存能在权限和保留期内重建内容的受控引用；关键引用不可重建时明确显示不可用，不能编造旧状态。

一个正式等待项只在提出它的 Task、Authorization 或登记应用模块中权威保存和消费；UI 保存其引用及已知版本。无 task_ref 的界面也可以通过授权或应用模块完成独立交互；仅改变界面偏好且登记为 UI 自有业务的操作，可以由 SurfaceStore 接纳。

### 输入与恢复顺序

1. 先验证认证端点、namespace 及原操作查询/结果披露权限，再按 operation_id 查既有 ActionRoute。已存在时校验原输入摘要，使用持久保存的目标、映射/Schema 版本与规范化意图查询原业务结果；不因 Surface 后来关闭、事件升级或等待项已消费而把原重试当成新输入。披露仍遵守当前删除和用途约束。
2. 只有尚未接纳的新操作才验证当前 surface/component、登记事件、输入 Schema、权限及预期版本，规范化后原子保存 ActionRoute 与待转交记录，固定原 operation_id、原输入摘要、目标和映射/Schema 版本、规范化语义摘要及可选 interaction_id。并发创建同一路由按唯一键裁决；相同 ID 不同输入拒绝。持久转交不等于目标业务已受理。
3. 目标模块原子检查等待项/版本并接纳，返回业务回执。UI 再提交呈现状态；此处允许短暂投影滞后。
4. 任一步崩溃后查询原操作，恢复转交或更新投影。同一操作重试返回原结果；不同操作争用同一等待项时只允许合法的首次消费。
5. 重连重新鉴权、取快照与有效等待项、查未决操作。旧 Surface 世代、过期输入和旧连接不能重开界面或消费新的等待项。

token 增量、光标和心跳不逐条存为正式状态。最终结果、正式输入、控制意图和关键状态必须持久化；可合并预览通过快照及版本通告补齐，已被策略禁止披露的内容不因缓存或重放再次返回。PresentationStatus 只表示 Renderer 报告的应用状态，不代表用户同意。

## 5. 五条关键链路的完整性检查

评审正文给出时序，以下列出每条链路不可遗漏的持久责任与故障验收点。

| 链路 | 关键数据和责任交接 | 必须覆盖的反例 |
| --- | --- | --- |
| 任务决策与执行 | Task 版本 → Context 来源 → Proposal → RunStore 工作/预算 → ExecutionStore 启动事实 → Driver 效果 → Core 结果接纳 | 准入提交成功但响应丢失；外部动作成功但结果丢失；新输入使旧提案失效。 |
| 端云多 Agent | 父委派操作/预留 → 子任务唯一接纳 → 子 Owner 自主推进 → 带来源结果 → 父汇总/结算 | 委派重投不产生第二个子任务；离线暂停/取消不虚报落实；父恢复不清除子独立暂停；未知消耗不重复分配。 |
| 记忆与上下文 | 获准来源 → 集合权威修订 → 受控查询投影 → Context 依赖 → 模型前后与行动准入复核 → 失效/删除传播 | 模型生成中来源被删除；端侧不可达不等于零命中；云端无权读取时不能通过索引或摘要绕过。 |
| UI 与控制 | Surface 版本/等待项引用 → 同一规范化操作 → 业务模块消费 → UI 结果投影 → 重连补读 | 转交成功但 UI 未提交；两端竞答；恢复旧快照不复活已关闭等待项；呈现回执不作为授权批准。 |
| 评测与改进发布 | 不可变计划 → 隔离任务和证据 → 独立评分/比较 → 候选及阶段 → 各节点激活 | 运行结束但证据不足；发布受理但节点失联；升级后旧任务仍固定旧版本；回滚不抹除已发生事实。 |

所有反例先在脚本化 Brain、多个有状态模拟端及真实进程边界下执行，再验证生产存储和消息适配器。本文是实现契约与测试设计，不把静态检查视为运行验收通过。
