# 整体设计审查：待决项与缺漏

审查日期：2026-09-24。基准提交：`764138174b87cbf5dd8057e56c9b1ab23286adbb`，审查开始时工作区干净。

范围为 `docs/architecture` 下原有 51 篇 Markdown、系统全景图、协议 Schema／注册表／示例及校验器；以[项目目标](../../../harness-project-goals.md)为需求基线，不继承归档方案中的接口或选型。本报告只记录评审结论与建议，不将尚未采用的提案改写为生效契约。

**阅读说明。** 第 1～6 节保留初次审查快照，所引行号均对应上述基准，其中包含实现准备建议。后续修订范围收窄为技术文档质量：契约与示例一致性、职责和异常交接、验证设计及导航；代码、具体部署配置、数据集与运行实测不作为本次文档缺陷。当前处理状态见[第 7 节](#resolution)，原报告的缺项描述不表示修订后仍然缺失。

## 1. 总体判断

模块职责和局部可靠性设计已经较完整，可以开始实现本地参考闭环。任务核心裁决推进与完成，执行系统保存实际效果，授权服务裁决许可，各模块通过原身份、持久责任和原操作查询恢复；这一主线在正常、取消、重启及结果未知场景下基本一致。本轮未发现可确认的首期核心安全性缺陷。

整体方案尚未达到“按共同配置装配即可验收”的程度。主要缺口集中在三处：通用模块依赖的默认策略与基础提供方尚未具体化；跨端领域合同尚未统一；模块验收尚未落实为固定的系统验收计划。协议的截图示例与 UI 首期限制、回退成功的定义还存在可直接判定的衔接问题。

建议保留现有模块划分，优先补齐交接及参考配置。当前没有证据要求新增通用编排层、全局状态机或独立内容服务集群。源码、SDK、适配器和故障证据未交付，应分别记录“本地契约已有设计”“跨端契约未定”“实现待完成”，不能合并成整体 L1–L4 已通过。

| 设计层面 | 审查结论 | 对下一阶段的影响 |
| --- | --- | --- |
| 职责与事实归属 | 整体一致；消息接收、业务接纳、效果和任务完成分别裁决 | 沿现有分工实现，避免重新集中业务裁决 |
| 本地异常闭环 | 未知提交、幂等、取消、预算占用、迟到事实和旧实例隔离已有明确规则 | 主要转入实现与故障注入，不能仅凭文档认定保证成立 |
| 默认应用闭环 | 缺默认目标策略、具体能力包及内容／来源提供方合同 | 通用接口完成后仍可能没有一类可完整运行的任务 |
| 跨端互操作 | WSS／JSON 已有静态资产，领域授权、准确目录、记忆、委派等合同不齐 | 不能把已有消息 Schema 当作 A3／A4 已满足 |
| 用户控制与数据治理 | 本地取消、接管、纠正、逻辑禁用有设计；跨模块副本清理未闭环 | 可以如实显示限制，不能承诺全链物理删除 |
| 评测与发布 | 计分与隔离机制明确；默认验收计划和发布前回退证明不足 | 不能由各团队自行选择的测试计划汇总出统一达标结论 |

## 2. 需要补齐或修正的事项

本节 P2 表示应在相应闭环交付前解决的设计问题或整合缺口，P3 表示文档维护问题；不将它们解释为已发生的运行故障。跨端、离线等已明确关闭的能力另在第 3 节排序。

### R1 · P2：首个协议运行用例依赖当前关闭的中间成果预览

**依据。** [协议总览](../endpoint-communication/README.md)第 70–103 行、[任务与 UI](../endpoint-communication/task-and-ui.md)第 48–82 行以“先查看截图，再选择是否保存”串联正常链路；[协议运行验收](../endpoint-communication/validation/README.md#runtime)第 46 行指定它为首个完整链路。但[交互投影](../application-and-interaction/interaction-and-recovery.md#projection)第 31–35 行明确：ReadTask／ReadResult 不能恢复执行中截图，没有 UI-P3 时关闭需要中间预览的输入。

**触发与影响。** 截图生成后 UI 管理器重启，任务尚未终态。默认适配器无法从核心读取该截图及其与输入请求的完整关系；按 UI 方案应禁止提交，协议用例却要求用户查看后回应。协议能编码 content 引用，不能补足呈现事实的提供方。因此当前默认装配无法完成被指定的首个运行用例。

**建议。** 首个本地集成基线先采用“不依赖中间预览的澄清 → 执行 → 正式成果”链路；截图预览例保留为 UI-P3 完成后的条件用例，并在协议入口、图示说明和验收入口标明依赖。如果首期产品明确需要先看截图再确认，则先完成[UI-P3](../application-and-interaction/validation.md#proposals)：受控中间投影、来源／用途、输入与必需预览的结构化绑定及可重读版本。不要让 UI 直接读取执行存储拼装任务事实。

**验收。** 截图已生成但输入未消费时重启 UI，分别注入来源撤权、内容清理和请求替换；应能恢复正确预览，或明确禁止回应并显示缺口。

### R2 · P2：停用与旧版恢复共用“回退成功”，发布前缺回退可行性门槛

**依据。** [持续监测与回退](../observation-and-improvement/improvement.md#monitoring)第 74–76 行要求回退时检查旧版能否读取当前格式，但又把采用旧版或停用均称为“回退成功”。[扩展切换](../extensions-and-runtime/installation-and-isolation.md)第 85 行允许经验证的私有格式迁移；[发布记录](../observation-and-improvement/contracts.md#release)固定回退范围，没有要求激活新版本前验证旧版读取升级后数据。与此同时，[C9 验收](../observation-and-improvement/evaluation.md)第 82 行要求分别证明旧版本恢复。

**触发与影响。** 新版本合法迁移私有格式，上线后出现退化，旧版无法读取当前数据。安全设计会拒绝回退并停用，这能阻止继续运行坏版本，却未恢复旧版服务。现有措辞容易让管理界面或验收把停用计入回滚成功。

**建议。** 为每个目标分别记录停用、旧版已恢复及仍受阻的结果；批次管理状态可以继续汇总为 stopped，旧版恢复验收必须读取具体结果。首期默认只接纳与指定回退目标兼容的格式变更，发布前验证“新版写入后的当前账本 → 旧版读取和运行”。确需不可逆迁移时单独声明恢复方案与保证变化，不能用旧数据库覆盖当前授权、预算或业务事实。

**验收。** 新版写入后触发回退，检查旧版能否实际恢复所支持任务；旧版不可读而停用的场景，只通过停用验收，不通过 C9 旧版恢复验收。

### R3 · P2：内容与来源提供方尚缺统一合同和明确的实现归属

**依据。** [HTTPS 内容通道](../endpoint-communication/transport.md#content)第 169–196 行规定上传、读取、摘要与访问约束；[执行依赖](../capability-and-execution/validation.md#dependencies)第 17 行进一步要求证据提交、保留与删除回执；[记忆依赖](../memory-system/validation.md#dependencies)第 13、22 行要求精确来源版本、当前状态、完整来源与用途／驻留／保留约束，并明确外部来源适配器尚未具体交付。[MS-P2](../memory-system/validation.md#proposals)和[OI-P2](../observation-and-improvement/validation.md)仍引用“内容服务未来方案”。

**触发与影响。** 执行端上传截图或获取网页，核心需要引用它完成验收，UI 要呈现，记忆要提取。协议已有“持久性与摘要检查后返回引用”和孤立临时内容清理的成功／失败语义；尚缺的是共同实现归属，以及领域引用登记、来源状态证明、保留约束、清理竞争和删除回执的具体合同。缺这些保证时，各模块按现有规则拒绝或等待；本地任务、V1 取证和接入内容记忆均会受限。

**建议。** 先为同宿主内置内容提供方及来源适配器定义合同，并指定所属实现；不要求增加独立部署模块。内容提供方负责字节、完整性、引用生命周期和清理回执，来源权威负责精确版本及当前可用条件，授权服务负责用途许可。共同合同至少落实下列交接。

| 交接 | 必须明确的规则 |
| --- | --- |
| 生成／上传到引用发布 | 将已有耐久发布与孤立清理语义落实到具体提供方，定义临时对象固定、领域引用登记及其与清理的竞争 |
| 来源解析到任务使用 | 来源权威、精确版本／摘要、派生来源、当前状态与允许用途；静态公开来源的新鲜度边界 |
| 引用保留到成果交付 | 未完成验收、正式结果保留、临时 UI 缓存分别依赖哪些字节；到期后返回何种缺口 |
| 禁用到清理 | 先停止使用，再处理受管副本；清理回执区分逻辑禁用、载体清理和不可撤回披露 |
| 宕机与存储压力 | 字节和元数据提交顺序、重启修复、配额、未交接引用与清理的竞争 |

**验收。** 注入上传成功但答复丢失、结果已发布但内容不可取、引用期间到期／撤权、清理中崩溃，分别核对字节、领域记录和后续责任。

### R4 · P2：默认任务策略、能力包和模型配置尚未具体化

**依据。** [核心完成核验](../task-kernel/lifecycle.md#completion)第 135–141 行依赖受信策略固定目标条件；[内核缺口](../task-kernel/recovery-and-validation.md#gaps)第 97 行仍要求应用配置提供策略及验证器。[默认驱动边界](../capability-and-execution/execution-and-recovery.md#gui)第 150–156 行提供 API／文件原则和 GUI 能力名称，尚未给出首个完整能力包。应用和评测消费这些策略、证据与环境，没有补上默认实例。

**触发与影响。** 实现“联网核实并保存答案”或“操作模拟手机”时，各团队仍需自行决定支持哪些目标、如何将目标绑定为条件、取证结果格式、采用哪个验证器及何时确认成功。通用接口都能实现，合在一起仍可能只能等待缺失策略，或使用不兼容的证据格式。

**建议。** 将下列三种参考任务配置与能力、证据和验收一并固定，优先完成一条再展开下一条。任务策略属于核心加载的应用配置；能力声明属于能力与执行；评测环境提供独立真值，避免另造一层裁决者。

| 参考任务 | 最小设计资产 | 首个异常验证 |
| --- | --- | --- |
| 文件保存与读回 | 路径／内容绑定规则，写入与读回准确声明，验证器版本和证据结构 | 写入成功、答复丢失，恢复后不重复写入 |
| 有来源联网问答 | 搜索、正文获取、时间与来源证据；答案条件、语义评估能力及费用；固定内容回放与实际联网两种计划 | 取证失败、来源冲突、资料撤权后不以缺失证据完成 |
| 多模拟设备 GUI | 设备身份、初始状态、观察及四种动作的准确参数／结果；任务侧观察和判定侧真值接口 | 旧观察、错误设备、动作未知、取消及本地接管 |

配置还须固定 draft→fixed 的条件建立规则、unknown 的后续行为，以及“验收规则固定”和“运行中绑定新生成成果版本”的关系。[模型适配方向](../brain-system/contracts-and-runtime.md#model-profile)已选择云端 Claude 原生结构化输出与本地 llama.cpp 两类；待完成的是沿该方向固定首个可验证的部署 profile，具体模型、硬件及数据策略依据评测选择，并落实既定的用量、终结／取消、成本类别和不可核对行为。

**验收。** 默认配置的完整正常链与异常链均能通过共同接口运行，再用另一实现替换其中一个系统，证明无需改写其他模块的完成规则。

### R5 · P2：尚无固定的系统验收与交付基线

**依据。** [项目验收目标](../../../harness-project-goals.md)要求独立记录 C1–C9、A1–A4、V1／V2 与成熟度；[评测设计](../observation-and-improvement/evaluation.md#metrics)已定义计数、分母、未知结果、有限重试和比较方法，但当前方案未实例化项目共同采用的 Dataset／EvaluationPlan。各模块给出了容量观测与限额要求，尚未汇总为选定部署的工作负载、目标阈值及容量验证计划。

**触发与影响。** 两个实现团队选取不同难度、预算和部署的合法测试计划，都可能报告 90%／95% 达标，结果却不可比较；单模块“保证成立”也不能直接组合为端云、替换或灾后恢复通过。1000 API 的计数口径已有定义，缺的是接入清单、业务分类、接入维护方式与分阶段证据，而非再补一套计分公式。

**建议。** 新增一份系统验收计划，实例化既有评测合同并链接各模块用例，不复制测试矩阵。首版固定：支持的平台与部署、默认实现／配置、C／A／V 的目标等级、数据集与样本分层、专项阈值、总期限／费用／重试预算、故障位置、观察账本和证据索引。明确系统级用例由谁维护，哪些模块共同提供观察依据。

容量计划另固定任务到达率、同时活跃任务、模型调用并发、内容字节、消息保留与故障积压，并给出接纳、控制、恢复的延迟目标。先测本地参考部署，再设计云端用户路由／分区、共享资源配额和故障域；不能直接从十万在线数推导数据库、模型或恢复吞吐。备份连续性和旧实例隔离应列明默认提供方、可恢复故障范围与演练，缺少这些实现时仍只允许受限恢复。

**验收。** 同一冻结计划能对默认实现和替换实现输出可比较结果；一次跨模块故障有统一的输入、原身份、独立效果与责任存续证据。运行结果与文档／Schema 检查分别登记。

### R6 · P3：架构入口和邻接依赖状态滞后

**依据。** [架构入口](../README.md)第 13–21 行只列出八项方案，遗漏已经存在的[应用与交互](../application-and-interaction/README.md)和[协作与端云](../agent-coordination/README.md)。[内核缺口表](../task-kernel/recovery-and-validation.md#gaps)仍要求协作模块展开部分合同和消息存储职责，[扩展 ER-P1](../extensions-and-runtime/validation.md)仍称观测改进方案为未来方案；实际相邻文档已有设计。

**影响与建议。** 当前入口不能完整遍历方案，也会使实施者把“合同已有、实现待验”误读为“尚未设计”。将 UI-P0、CO-P0 合并为一次导航与依赖状态维护；补连续阅读顺序，并把已存在的本地契约链接到权威位置，跨端载荷未定和运行证据缺失继续保留。此项不需要新的架构选择。本文仅记录问题，未修改原方案。

## 3. 将分散待决项合并为决策包

以下是已有提案的依赖排序建议，不代表本次已批准扩大首期范围。“必须完成”均以启用相应能力为前提；保留本地闭环时，无需同时解决全部跨端与自动化问题。

| 决策包／现有提案 | 需要决定的内容与推荐 | 未采用时的准确边界 | 牵头与联动 |
| --- | --- | --- | --- |
| 跨端授权与执行：身份 P1、CE-P1、UI-P2 的相关部分 | 先固定身份恢复／确认的默认传输、受信主体及来源绑定、连续切点与应用证明，再落实准确目录和执行依据。优先让“固定云任务权威＋端侧执行”成为第一种跨端组合 | 本地授权／执行可实现；不能声称通用独立端点互操作。普通 UI 同意不签发许可 | 身份与协议牵头，执行、核心、UI、协作共同落实；[身份提案](../identity-and-authorization/validation.md#proposals)、[执行提案](../capability-and-execution/validation.md#proposals) |
| 执行事实与结算：CE-P2、取消答复超窗恢复 | 明确生产者修订、事实查询切点、可信累计用量与固定取消答复查询；优先在跨端硬预算或要求完整恢复时完成 | 保守合并与可信账单适配可先运行；未知费用保留，超窗不承诺还原某次取消完整答复 | 执行与核心、协议、协作；[CE-P2](../capability-and-execution/validation.md#proposals)、[内核缺口](../task-kernel/recovery-and-validation.md#gaps) |
| 远程三系统与委派：MS-P1、CO-P1、BS-P1 | 共享已确定的授权／来源语义，各领域保留自己的操作、版本与恢复合同。按实际部署逐项开放；远程大脑只在确需独立大脑服务时设计 | 本地记忆、本地内部委派、同进程大脑可先实现；云模型适配不等于独立远程 Brain 服务 | 各领域负责自己的 profile，协议维护共同约束；[MS-P1](../memory-system/validation.md#proposals)、[CO-P1](../agent-coordination/validation.md#proposals)、[BS-P1](../brain-system/validation.md#proposals) |
| 内容治理：MS-P2＋OI-P2 | 先决定同宿主受管载体，再定义持有者登记、停止使用、物理清理回执及离线关闭窗口；与 R3 共用提供方合同 | 使用前复核和本模块逻辑禁用继续有效；不能承诺外部副本全链擦除，评测拒绝需要持续撤回却无法关闭的持久导入 | 记忆／来源权威牵头，核心、大脑、UI、内容、观测持有者配合；[MS-P2](../memory-system/validation.md#proposals)、[OI-P2](../observation-and-improvement/validation.md) |
| UI 中间预览与目录：UI-P3、UI-P1 | 中间预览按 R1 单独决定；任务／surface 目录仅在需要新设备恢复未知 ID 或跨端全量列表时补齐。两者不是同一个前提 | 默认只能恢复宿主已知任务；具备完整请求即可作答的输入可用；需要先看中间成果的输入关闭 | 应用牵头，核心和协议联动；[UI 提案](../application-and-interaction/validation.md#proposals) |
| 自动发布与远程管理：OI-P1＋ER-P1、ER-P2 | 先定义同宿主精确批准、撤回与激活前复核，再扩展到逐节点回执；不要以可靠交付替代激活结果。R2 的回退定义须先统一 | 受信人工核验、有限批次、逐目标处置可先实现；不保证自动及时停用或离线节点同步生效 | 改进、扩展与身份；[OI-P1](../observation-and-improvement/validation.md)、[ER-P1／P2](../extensions-and-runtime/validation.md) |
| 终态自动化：MS-P3＋OI-P3 | 将自动提取与改进触发合并讨论：适用任务、幂等触发、用途、费用和独立任务责任；已有显式入口足以支撑首期 | 不自动从任务终态或日志启动隐藏模型循环；显式提取、Propose 和普通生成任务继续可用 | 应用策略与核心、记忆、改进；[MS-P3](../memory-system/validation.md#proposals)、[OI-P3](../observation-and-improvement/validation.md) |
| 高可用与在线替换：CO-P2、ER-P3、直连／离线增强 | 有明确停机、迁移或离线需求后分别设计。保持固定用户写权威；在未证明收益前不引入全局操作目录或多写者。首期升级优先保持格式兼容 | 权威不可达时依赖它的新决定等待；长任务／未知效果可能阻塞升级；缺可信时间、防回滚或隔离证明就关闭离线／接替 | 协作、宿主、身份及所属领域；[CO-P2](../agent-coordination/validation.md#proposals)、[ER-P3](../extensions-and-runtime/validation.md)、[协议范围](../endpoint-communication/README.md#scope) |

跨端传输目前存在专属 HTTPS 与领域消息两种候选，本轮没有足够实际部署约束替项目确定其中一种。建议先比较首次身份恢复、可靠命令、连续变更、浏览器接入和复用成本，再固定一条默认路径；不能让每个模块分别选择后再补互操作。

来源删除也需先明确要求的保证强度。逻辑禁用已有机制；跨模块受管副本清理需要新交接；不可撤回的外部披露不能通过增加删除回执变成可撤回。三类结果应持续分别表达。

## 4. 模块覆盖与实施前置条件

| 模块／方案 | 本轮主要结论 | 实施前最近的一项工作 |
| --- | --- | --- |
| 端云协议 | 结构、可靠交接和领域状态边界较完整；跨端语义尚不齐 | 修正截图验收前提，选择首个跨端组合与领域合同 |
| 任务内核 | 准入、预算、取消与完成核验规则一致 | 固定默认任务策略与验证器，更新邻接依赖状态 |
| 身份与授权 | 身份绑定、单次消费、撤销和离线失败行为明确 | 实现本地授权账本与受信入口；跨端先完成身份 P1 |
| 能力与执行 | 原操作、资源门禁和未知效果处理完整 | 提交准确的默认能力包、证据及内容提供方合同 |
| 大脑 | 单轮生成、过期提案、未知调用和用量责任清晰 | 固定首个模型 profile，与任务策略共同跑通真实调用 |
| 记忆 | 单权威修改、来源继承与受控视图规则明确 | 实现来源适配器；将 MS-P2 与 OI-P2 合并治理 |
| 应用与交互 | 本端意图、输入转交和呈现恢复明确 | 确定中间预览范围，补导航；不将已知 ID 索引当全量目录 |
| 协作与端云 | 本地委派、收发账本及恢复实现合同已有 | 验证受限子配置真正进入 Submit 事务，再扩大跨端范围 |
| 扩展与运行保障 | 引导、排空、隔离和旧账本恢复规则较完整 | 固定默认平台适配器及格式兼容政策；需迁移时另补持久迁移命令与失败恢复 |
| 观测、评测与改进 | 计分、隔离和受控推广机制较完整 | 固定系统 EvaluationPlan；区分停用与恢复旧版 |

这些前置条件不都属于新的架构决策。可信时钟、监督器隔离、持久账本和防旧备份复活已经有失败处理规则，主要缺实现及平台证据；不能将其重复记录为“设计未考虑恢复”。反之，来源合同、默认验收策略、跨端 profile 和统一测试计划需要先补设计资产，不能仅登记为“等开发”。

## 5. 建议推进顺序

| 顺序 | 交付物 | 通过后可以证明什么 |
| --- | --- | --- |
| 1．统一设计基线 | 处理 R1／R2／R6；固定首期部署、支持范围和系统验收入口 | 文档、示例和启用条件一致；不再让实施者隐含决定首期范围 |
| 2．本地最小闭环 | 完成 R3／R4 的文件任务配置、内容／来源合同、默认提供方和必要 SDK 类型；用户输入→核心→大脑→执行→独立读回→正式成果 | 正常链与写入响应丢失、取消、重启、未知结算均有可重复的运行证据 |
| 3．V1／V2 专项 | 固定联网数据与模拟设备、规则及参考答案；独立验证问答、个性化和 GUI 接管 | 专项能力达标，明确模拟与真实平台范围，不用一次组合演示替代独立结果 |
| 4．首个跨端组合 | 身份 P1、CE-P1 及所需 CE-P2；固定云核心与端执行，注入断线／撤权／迟到事实 | A3／A4 的特定部署成立；随后按需求扩展 MS-P1、CO-P1、BS-P1 |
| 5．治理与规模 | 受管副本清理、C9 旧版恢复；需要时自动发布与迁移；冻结工作负载后容量测试 | 分别取得数据治理、回滚、替换及规模证据，不扩大未测试的保证 |

1000 API 接入目录可以并行建设，但必须沿同一准确声明、来源／效果证据与验收规则入库；数量增长不应阻塞先证明少量能力的完整可靠链路。
