# 通用 Harness 项目目标与能力验收基线

状态：目标基线已确认。确认日期：2026-09-09。

本文汇总已对齐的项目定位、能力要求、系统边界、扩展规则和验收方式，作为后续架构设计与实施计划的依据。能力重整经 Q18–Q20 对齐：原 G1–G7 的要求保留，按九项通用能力、架构约束和强制专项能力重新组织，并补入任务上下文管理以及可复用的运行观测与能力评测机制。

文中的能力和验收证据是建设要求，实际实现状态由后续里程碑报告记录。技术实现条件及后续选型见 [设计输入与硬约束](architecture/00-design-constraints.md)；具体协议标准、量化测试门槛和发布时间在后续设计与实施计划中确定。

术语以 [CONTEXT.md](../CONTEXT.md) 为准。

## 1. 项目定位

构建一套长期作为开源项目维护的通用 Harness 架构及可运行实现，连接记忆、大脑和执行三大系统，在授权范围内完成信息获取、上下文组织、任务决策和行动执行，支持端云与多 Agent 协作、个性化和生态扩展，并通过运行观测、能力评测和受控自进化持续改善能力。联网问答和手机 GUI 操作是必须完整验收的专项能力。

从系统能力出发定义架构与里程碑。业务场景作为验证材料；手机与电脑协作可以成为参考用例。里程碑按系统能力维度验收，场景成功只是其中一项证据。

## 2. 通用能力目录

通用能力描述可提供、可组合、可独立验收的行为；一项能力可以由多个系统共同实现。架构约束规定实现必须遵守的结构与规则，专项能力规定若干通用能力组合后必须达到的完整效果。

新版使用 C1–C9 标识通用能力，原 G1–G7 保留在第 7 节作为需求来源。能力数量不决定系统、进程或部署节点的数量。

| 编号 | 通用能力 | 核心责任 | 主要输出 |
| --- | --- | --- | --- |
| C1 | 任务理解、规划与决策 | 理解目标与约束，结合上下文制定和调整计划，选择行动或委派工作，综合结果形成应答或完成判断。 | 计划、行动与委派请求、应答及任务完成判断。 |
| C2 | 上下文、记忆与个性化 | 组织当前任务的工作信息，管理跨任务记忆，并让适用的个性化信息影响应答与执行。 | 任务上下文、受控的记忆读写结果及来源信息。 |
| C3 | 信息获取与证据处理 | 从声明支持且已授权的信息源取得内容，表达来源、获取时间、获取结果及证据缺口。 | 可供任务使用的证据，以及冲突、缺失或获取失败信息。 |
| C4 | 工具调用与设备操作 | 执行工具与设备动作，提供环境观察、调用反馈和可确认的实际结果。 | 工具结果、设备观察、动作执行与效果确认状态。 |
| C5 | 任务运行与端云协同 | 持久化任务状态与执行记录，调度节点与 Agent 协作，处理超时、重试、取消、离线运行和恢复。 | 任务状态、执行记录、协作结果及恢复状态。 |
| C6 | 扩展接入与协议互操作 | 通过共同契约接入插件、Skill、内部与外部 Agent，管理能力、版本与依赖声明并验证兼容性。 | 可使用的扩展与能力声明、适配结果及一致性验证结果。 |
| C7 | 授权与用户控制 | 统一表达和落实主体、资源、动作、范围与有效期，控制委派权限并承接用户对数据和任务的控制。 | 授权约束、准入判断与可落实的用户控制指令。 |
| C8 | 运行观测与能力评测 | 关联运行记录以支持诊断，依据测试集与基线评价行为和效果，测量质量、耗时与成本。 | 关联记录、诊断依据、评测结果与基线比较。 |
| C9 | 受控自进化 | 从经验提出改进，使用评测结果决定是否按授权规则发布，监测效果并支持回滚。 | 改进提案、版本化产物、发布与回滚记录。 |

### C1：任务理解、规划与决策

接收任务目标、用户约束、可用能力与任务上下文，完成理解、规划和行动决策。支持选择工具或 Agent、拆分与委派工作，并根据实际反馈调整后续计划、综合结果形成应答或任务完成判断。

**边界与协作：** C1 决定要做什么，输出计划与请求；C5 负责调度和维持任务运行，C4 负责与工具和设备交互。C1 的完成判断需要依据实际结果；节点连接成功或动作请求已发出本身不构成任务完成证据。授权由 C7 约束。

### C2：上下文、记忆与个性化

任务上下文管理负责选择、组织和更新当前任务所需的目标、进展、工具结果、相关证据与记忆。长期记忆负责跨任务复用，支持用户显式提供、授权接入和交互提取，区分事实、偏好、推断和任务经验，保留来源、时间、置信度与适用范围。

用户可以查看、纠正、删除与限制用途。读取、提取、保存和跨端同步分别受策略控制。个性化信息需要在适用范围内实际影响应答或执行。

支持端云结合的记忆访问：重要隐私数据可保留在端侧，并在允许范围内被检索和使用，不以原始数据全部上云为前提。支持端侧数据挖掘与记忆提取，明确原始数据、索引、派生记忆和返回结果的端云存储及处理策略。

**边界与协作：** 进入任务上下文的信息不自动成为长期记忆，读取权限本身不授予长期保存权限。任务的运行状态由 C5 管理，提供给 Agent 的工作信息由 C2 组织；外部新信息可由 C3 提供。C2 处理记忆访问与更新，C9 处理以经验为依据的改进提案及其效果验证。

### C3：信息获取与证据处理

根据任务的信息需求，通过可替换的搜索与内容获取实现取得实际内容，向任务提供带来源与获取时间的证据。明确表达证据不足、来源冲突和获取失败，支持上层判断信息是否适用于当前问题。

**边界与协作：** C3 负责信息与证据的取得及表达；具体工具交互由 C4 完成，当前任务如何使用证据由 C2 与 C1 协作处理，长期保存受 C2 与 C7 约束。最终回答及其结论由 C1 形成，回答与引用是否成立由 C8 评测。信息源和连接方式按适配器声明的支持范围提供。

### C4：工具调用与设备操作

接收行动请求，在执行端校验权限后与工具、设备或外部系统交互，按能力契约返回调用结果与观察信息。手机 GUI 操作形成观察、动作、再次观察与结果验证的闭环，必须覆盖点击、滑动、输入、返回，并支持任务中断与用户接管。

主要执行路径是 API 接口调用；GUI 用于第三方应用没有可对接的 API 能力及适用的兜底情况。执行路径的优先级不降低手机 GUI 的完整专项验收要求，各路径均遵守统一授权、结果核对与恢复约束。

支持 1000 个以上 API 的准确调用：首次调用正确率至少 90%，有限重试后的任务成功率至少 95%。该要求同时涉及能力接入规模和实际调用效果，不能仅以注册数量或请求发送成功证明达标；API 计数口径、指标计分、有限重试预算和测试覆盖由技术方案及能力评测明确。

分别报告动作是否执行以及其效果是否得到确认；无法确认时保留不确定状态。驱动声明其支持的观察与动作能力以及适用设备条件。

**边界与协作：** C4 承担具体行动与反馈，C1 决定行动目的，C5 管理任务调度、取消、重试与恢复。动作结果不明时，恢复流程需要先核对实际状态，不能直接把未收到回执视为未执行。手机 GUI 的整体效果仍需通过 V2 专项验收。

### C5：任务运行与端云协同

提供任务状态与执行记录的持久化，以及调度、超时、重试、取消和恢复能力，覆盖一次问答及长时间、多 Agent、跨设备任务。节点声明能力，任务安排结合能力与用户策略；Agent 协作覆盖任务委派、状态传递、取消和结果收集。

所需能力在本地可用且授权仍有效的任务可以继续；依赖失联节点的步骤进入等待状态。重连后核对授权、任务状态与执行结果。对于可能已经改变外部状态、但结果不明的动作，先核对再决定是否重试；无法核对时进入待处理状态。

**边界与协作：** C1 负责计划与委派决策，C5 负责实际调度、协作过程和运行保障。C6 负责节点及 Agent 的协议接入，C7 限定可委派的权限，C8 关联运行记录并提供诊断依据。连接恢复与任务恢复分别验收。

### C6：扩展接入与协议互操作

通过共同接口契约与 SDK 接入扩展，支持能力声明、版本与依赖声明、适配和兼容性验证。同类实现接受共同的一致性测试；协议覆盖任务协作、能力调用、记忆访问和端云连接等接口领域，并可扩展承载端侧 UI 呈现、用户事件、输入请求和交互结果。不同 UI 类型通过能力声明与版本化契约接入，不绑定某个场景或界面框架。

| 扩展对象 | 责任与边界 |
| --- | --- |
| 插件 | 提供可安装的实现，例如记忆后端、模型适配器、搜索工具和设备驱动。 |
| Skill | 提供用户可自定义的操作知识与流程，调用工具时沿用执行系统的权限与记录机制。 |
| Agent | 持有目标、上下文和决策循环，通过任务契约参与协作。内部 Agent 的生命周期由 Harness 管理；外部 Agent 保留独立运行时。 |

**边界与协作：** C6 解决扩展能否接入、能否理解共同契约的问题；接入后的决策由相应 Agent 或 C1 负责，运行由 C5 协调，行动受 C7 约束。一个协议可以覆盖多个接口领域。具体标准、版本兼容细则与分发方式在后续设计中确定。

### C7：授权与用户控制

统一策略表达主体、资源、动作、范围与有效期，支持单次和持续授权。任务委派只能在已有授权范围内收缩权限；内核管理授权检查，执行端落实动作准入。大脑、插件、Skill、内部与外部 Agent、自进化产物遵守同一边界。

承接用户对信息查看、纠正、删除、用途限制以及任务中断和接管的控制，交由相应能力落实。读取、提取、保存、同步和行动权限按照各自适用范围检查。

**边界与协作：** C7 管理和判定授权约束，C2 落实记忆控制，C4 与 C5 落实执行和任务控制，C8 记录相关行为，C9 遵守改进发布权限。授权不能由任务委派、扩展接入或自进化过程自行扩大。

### C8：运行观测与能力评测

关联跨端任务、工具调用、授权检查与结果记录，使运行情况可用于诊断。提供可复用的测试集、基线比较和评测结果，测量能力的质量、耗时与成本，供运行诊断、能力验收和自进化共同使用。

一致性测试检查输入输出与可观察行为是否符合契约；效果评测检查实际结果是否满足任务目标。两类证据分别记录，测量需说明环境、实现版本、测试集与方法。运行记录的使用沿用统一授权和用途限制。

**边界与协作：** C5 维护任务运行状态和执行记录，C8 负责关联、诊断与评价。C8 提供改进前后的比较依据，C9 负责提出、发布和回滚改进；评测结果本身不扩大发布权限。

### C9：受控自进化

形成经验采集 → 改进提案 → 隔离评测 → 版本发布 → 效果监测与回滚的闭环。使用 C8 的评测和基线比较证明效果改善，保留来源、版本、评测结果与回滚依据。

| 改进对象 | 默认生效规则 |
| --- | --- |
| 记忆 | 授权范围内的更新可以自动生效。 |
| Skill、执行策略、Agent 配置 | 通过评测后逐步启用。 |
| 插件与内核代码 | 生成可审查补丁，经维护者确认后发布。 |

**边界与协作：** C9 负责改进过程与产物生命周期，C8 负责评价依据，C7 约束发布权限，产物由相应能力接入和使用。常规记忆更新沿用 C2 的规则；声称改进已取得效果时需要评测证据。自进化不能自行扩大权限或降低评测门槛，仅生成新内容不构成成功。

## 3. 架构约束与开源交付

### 3.1 开源交付范围

项目交付以下六类成果：

1. 架构规范：定义三系统的职责、关系与扩展边界。
2. 标准协议：定义组件之间可共同遵守的接口契约。
3. 可运行内核：统一管理任务状态、调度、授权检查、超时、重试、取消、恢复和执行记录。
4. 参考实现：三系统均具备可用的默认实现，并允许独立替换。
5. 扩展 SDK：帮助社区实现组件与适配器。
6. 一致性测试：检查实现是否遵守所声明的接口契约。

### A1：三系统的逻辑边界

记忆、大脑和执行表达逻辑职责，Harness 内核为三系统协作提供公共运行保障。能力目录可以跨系统描述行为；具体模块划分在架构设计中确定。

| 组成部分 | 责任 |
| --- | --- |
| 记忆系统 | 承载个性化信息与经验，并提供受策略控制的访问和更新能力。 |
| 大脑系统 | 理解请求，结合可用信息进行规划与决策，提出行动请求。 |
| 执行系统 | 与工具、设备和外部系统交互，校验行动权限并返回执行结果。 |
| Harness 内核 | 为三系统提供任务生命周期、调度、授权检查与运行记录等公共保障。 |

### A2：默认实现与独立替换

三系统均提供可用的默认实现，并允许独立替换。替换大脑或其他组件后，内核提供的任务生命周期、授权和运行保障仍然成立。各能力通过契约定义与一致性验证约束实现，SDK 支持社区扩展。

### A3：端云灵活部署

三系统可以部署在端侧、云端或两者之间；协议不把某个逻辑系统永久绑定到某个位置。部署位置、节点可用能力与实际运行状态分别表达。C5 提供跨端任务运行、离线行为和恢复保障。

### A4：共同契约与统一授权

端云与模块接口遵守明确的共同契约；插件、Skill 和 Agent 沿用相应契约及授权边界。协议标准化通过 C6 的接入和互操作机制落实，授权通过 C7 及执行端校验落实。架构方案需说明两类约束在各组件和节点上的执行位置。

## 4. 接口契约

### 4.1 为什么要标准化

组件通过共同接口交换请求和结果。共同规则让实现方知道需要接受什么输入、返回什么结果，以及如何表达失败，使组件可以在同一接口下替换或组合。

### 4.2 接口领域

| 接口领域 | 共同规则覆盖的内容 | 示例 |
| --- | --- | --- |
| 任务协作 | 分派工作、报告进展、返回结果和取消任务。 | 一个 Agent 把部分工作交给另一个 Agent。 |
| 能力调用 | 声明可用动作、动作输入及执行结果。 | 请求联网搜索，或请求手机执行一次点击。 |
| 记忆访问 | 在允许的范围内读取和更新记忆。 | 读取用户偏好的应答语言。 |
| 端云连接 | 识别设备、建立连接及处理连接中断。 | 手机断网后重新连接；任务层另行处理任务恢复。 |

这四项描述需要统一规则的基础接口领域。在其上通过用户交互与呈现契约组支持各种端侧 UI；UI 交互可以关联任务，也可独立存在，具体设计见 [UI 交互契约](architecture/03-ui-interaction-contracts.md)。一个协议可以覆盖多个领域；端云连接可以承载其他领域的消息。具体采用哪些现有标准、在哪里需要适配器，留待协议设计阶段确定。

### 4.3 一致性测试

同一接口的不同实现接受同一套契约检查。例如：

- 接受契约要求的输入。
- 动作被拒绝时，返回契约定义的错误。
- 动作失败时，不将结果报告为成功。

一致性测试验证约定的输入、输出与可观察行为。C6 用这些证据判断接入与兼容性，C8 将契约检查与实际效果评测分别记录，任务实际效果需要独立证据。

## 5. 必须验收的专项能力

专项能力表达完整的对外效果，归入通用能力后仍保留单独验收。下列两项是原始诉求中的强制要求。

### V1：联网问答

通过可替换能力完成搜索与内容获取，由大脑综合证据形成回答。关键事实关联实际取得的来源与获取时间；证据不足、来源冲突及获取失败需要明确表达。

由 C3 获取证据、C4 完成工具交互、C2 组织任务上下文及适用的个性化信息、C1 形成回答，C5–C8 提供运行、接入、授权和评测保障。

专项验收覆盖答案正确性、引用是否支持结论、信息时效性，以及检索失败和证据冲突时的行为。用户个性化信息的使用沿用 C2 与 C7 的规则。仅搜索接口可调用或组件通过一致性测试，不足以证明联网问答达标。

### V2：手机 GUI 操作

形成观察界面、执行动作、再次观察与验证结果的闭环，覆盖点击、滑动、输入和返回，并支持任务中断与用户接管。

设备驱动声明其支持的观察与动作能力。参考验收使用多个模拟设备，不要求真实设备验证；模拟设备须提供界面观察及动作引起的可核对状态变化，完整覆盖上述闭环。分别报告动作已执行与结果已确认；无法确认时保留不确定状态。模拟结果不代表已支持真实手机平台，未来真实设备 Adapter 另行声明和验证支持范围。

由 C1 决定行动目标与步骤、C2 提供任务上下文、C4 进行界面观察和操作，C5–C8 提供调度恢复、驱动接入、授权与用户控制、记录及效果评测。

专项验收依据包括动作执行记录和动作后的实际结果，并覆盖中断、接管、权限限制和结果不明的处理。能力声明与适配器边界用于表达不同平台的支持范围。连接中断后的行为还需满足 C5 的核对与恢复要求。

### 5.3 跨能力组合验证

手机与电脑协作作为组合测试之一，用于验证任务在不同节点和能力之间流转。组合测试结果与 C1–C9 的独立验收、V1–V2 的专项验收分别记录，具体业务场景不限定通用架构的适用范围。

## 6. 能力里程碑与验收矩阵

### 6.1 验收原则

按系统能力维度定义里程碑。每项能力分别给出契约、参考实现、测试证据及已知边界。通过不同实现的替换与能力组合检验通用性。

联网问答同时验证答案及其依据；个性化验证信息是否正确影响执行或回答，以及用户控制是否生效；手机 GUI 验证动作后的实际结果；自进化比较改进前后的效果，并验证恢复旧版本的能力。

除通用能力的成熟度外，还需记录架构约束 A1–A4 的满足情况，以及专项能力 V1–V2 的整体结果。场景测试用于验证能力协同，各项通用能力仍需独立证据。

### 6.2 成熟度定义

以下 L1–L4 是每项通用能力的成熟度标识。发布里程碑需要逐项列出 C1–C9 的目标等级、实际等级和证据；不同能力可以按依赖关系分别推进。能力成熟度与模块数量、业务场景数量分别记录。

| 等级 | 成熟度 | 所需证据 |
| --- | --- | --- |
| L1 | 契约定义 | 职责、输入输出、可观察行为、错误、权限与能力声明均有明确约定。 |
| L2 | 参考实现可用 | 可运行的参考实现按契约完成能力，提供可重复执行的验证方法及结果记录。 |
| L3 | 替换与互操作验证 | 不同实现通过同一接口使用，并完成适用的跨组件或跨 Agent 协作验证。 |
| L4 | 异常恢复与治理验证 | 验证该能力适用的失败处理、恢复、权限与用户控制；自进化另需验证评测、发布和回滚。 |

### 6.3 通用能力验收矩阵

本表展开已确认目标在四级成熟度中的验证重点。表内内容是验收要求；实际完成情况由里程碑报告填写。

| 能力 | L1：契约定义 | L2：参考实现可用 | L3：替换与互操作 | L4：异常恢复与治理 |
| --- | --- | --- | --- | --- |
| C1 任务理解、规划与决策 | 定义任务目标、约束、计划、行动请求、委派请求与完成判断。 | 结合上下文规划行动、综合结果，并根据反馈调整后续步骤。 | 更换大脑实现后仍能通过共同契约参与任务运行。 | 验证信息不足、行动失败或结果不明时的决策与完成判断。 |
| C2 上下文、记忆与个性化 | 定义任务上下文、记忆类型、来源、适用范围及访问与更新策略。 | 组织和更新任务上下文，使适用的个性化信息影响应答与执行。 | 替换记忆实现，并验证上下文使用与跨端同步遵守共同契约。 | 验证纠正、删除、用途限制，区分事实与推断，检查上下文使用与长期保存的授权边界。 |
| C3 信息获取与证据处理 | 定义信息需求、获取结果、来源与时间信息及失败表达。 | 获取实际内容，提供可供任务使用的证据。 | 替换搜索或内容获取实现后仍遵守共同契约。 | 验证获取失败、来源冲突、证据不足和时效性信息。 |
| C4 工具调用与设备操作 | 定义观察、动作、调用结果与效果确认的表达。 | 在声明支持的工具与设备上执行动作，返回契约约定的结果或观察信息；手机 GUI 验证完整闭环。 | 不同工具适配器与设备驱动通过共同接口使用，并表达能力差异。 | 验证执行端授权检查，以及适用的中断、接管和不明结果处理；手机 GUI 须覆盖全部专项要求。 |
| C5 任务运行与端云协同 | 定义任务生命周期、节点能力、Agent 协作与连接状态。 | 运行问答与长任务，支持端云和多 Agent 协作并保留记录。 | 验证不同节点实现、部署位置和兼容 Agent 之间的任务协作。 | 验证任务状态与执行记录持久化、超时、重试、取消、离线条件、断连等待、重连校验和不明结果处理。 |
| C6 扩展接入与协议互操作 | 定义接口领域以及插件、Skill、Agent 的版本、依赖与能力声明。 | 通过 SDK 接入扩展，运行用户 Skill，并接入内部及外部 Agent。 | 同类实现通过一致性测试，不同组件与 Agent 完成互操作。 | 验证依赖、版本和调用失败的契约行为，并检查接入后的授权边界。 |
| C7 授权与用户控制 | 定义主体、资源、动作、范围、有效期和用户控制的表达。 | 落实单次与持续授权、行动准入、记忆控制和任务控制。 | 授权约束经任务委派和跨节点协作后仍然成立。 | 验证权限拒绝、有效期与委派收缩，确认扩展和自进化不能自行提权。 |
| C8 运行观测与能力评测 | 定义运行记录关联、测试集、基线、评测结果及测量方法。 | 关联跨端运行记录以支持诊断，输出契约检查、效果评测和质量、耗时、成本数据。 | 用同一契约测试与可比较基线评价不同实现的适用行为。 | 核查失败记录、证据不足、评测结果及访问限制，确保比较依据可追溯。 |
| C9 受控自进化 | 定义改进对象、生效权限、评测依据、版本与回滚约定。 | 展示经验采集到评测、发布、监测和回滚的完整流程。 | 改进产物通过所属能力的契约检查，并在兼容组件中使用。 | 以基线对照证明改善并验证回滚；代码改动经维护者确认，不自行提权或降低门槛。 |

### 6.4 里程碑证据与量化评估

每个里程碑报告逐项记录能力目标、实际成熟度、测试集、基线、结果及已知边界。一致性测试结果与能力效果评估分别记录。报告还需关联架构约束的验证证据与专项能力的整体结果，避免将组件通过测试直接等同于专项能力达标。

性能、成本和质量的量化门槛在测试计划中确定，并说明测试环境、实现版本、数据或任务集及测量方法。自进化评测保留改进前后可比较的基线与结果。目标文档保留用户明确指定的目标门槛；这些数值是验收要求，不表示已经取得对应实测结果。其他数值不预填。

本次调整中的职责重组与新增范围如下：

- 将三系统结构、默认实现与独立替换、端云部署位置从行为能力中提取为架构约束。
- 将联网问答与手机 GUI 保留为强制专项能力，并明确其通用能力组合及整体效果要求。
- 将原文已确认的任务决策、任务运行、多 Agent 协作与统一授权明确归属到通用能力中。
- 在 C2 中新增明确的任务上下文管理责任，与长期记忆区分；具体组织和压缩方式留给后续设计。
- 将已有记录与验收要求扩展为 C8 的可复用观测与评测能力，服务运行诊断、能力验收和自进化。该项增加了公共能力的交付责任。

## 8. 后续架构设计与实施计划

以下内容属于已确认目标之下的后续设计决策：

- 运行时与模块设计：在已确认的技术实现条件下，设计模块接口、状态机、任务调度、持久化、重试与恢复机制。
- 协议与生态设计：现有标准的选择与适配、消息与接口规范、能力发现、版本兼容、依赖及扩展发布机制。
- 记忆与大脑设计：模型适配、任务上下文的组织与更新、记忆存储与检索、来源追踪、跨端同步及授权策略的具体实现。
- 设备与执行设计：多模拟设备的状态与故障模型、观察与动作适配器、能力声明和实际支持范围；真实设备接入保留扩展边界。
- 观测、评测与自进化设计：记录关联、诊断接口、测试集与评测门槛、逐步启用、效果监测与回滚机制。
- 实施与测试计划：各发布里程碑的能力目标等级、交付时间、资源安排、量化指标和测试环境。

这些选择应满足本文的能力与验收要求。需要改变目标或默认权限时，应明确提出目标变更并更新基线。
