本文规定项目要提供的能力、必须遵守的边界和验收目标，作为按[系统分工](architecture/README.md#2-系统分工与事实归属)逐个模块设计的依据。以下是建设要求，实际完成情况由实施与验收结果证明。

## 1. 项目定位与交付

构建一套面向个人智能应用开发者、长期维护的开源 Harness 框架及可运行实现。框架组织大脑、记忆和执行能力，在用户授权与预算内持续推进任务，交付有依据的结果，并在中断、失败或效果未知时保留可恢复的进展和明确的处理责任。

首批使用者是公司内部的个人智能应用团队，以具体应用的接入和反馈验证项目价值。同时兼顾外部开源开发者的交付要求，保持开源实现可独立运行。

项目首先证明任务执行可靠：长任务能够持续推进，中断后能够恢复；效果未知时不盲目重做，完成声明有依据。规划、记忆和多 Agent 协作带来的任务能力提升，必须通过独立对照实验逐项证明；应用接入是否容易，必须通过真实接入过程验收。工期与成本冲突时，优先取得任务执行可靠的证据。

完整项目交付架构规范、共同接口协议、可运行内核、三系统默认实现、扩展 SDK 和一致性测试，支持问答、工具操作、长时间任务及端云、多 Agent 协作。联网问答与手机 GUI 操作是必须单独验收的专项能力。

同一用户可以拥有多个端点、任务和 Agent。用户之间的数据访问、任务运行和资源消耗必须隔离；局部故障或高峰负载下，系统应准确报告任务的接纳、等待、执行效果与恢复状态。

### 首阶段交付

首阶段交付内部应用团队能实际接入的最小完整版本，以[研究报告任务](#首阶段代表场景)验收。首阶段范围与完整能力要求分别成立，不以一个场景通过宣称全部能力已具备。

| 范围 | 首阶段要求 |
| --- | --- |
| 可用交付物 | 可独立运行的内核、报告场景所需默认组件、必要 SDK、示例界面及该范围的一致性与故障测试。 |
| 真实应用接入 | 至少一个内部应用完成接入，验证提交任务、补充要求、查看进展、中断、取消和取得结果。 |
| 随场景交付的保障 | 任务上下文与进展持久化、授权、费用记录、效果核对和故障恢复。 |
| 后续阶段 | 跨任务个性化、复杂多 Agent 协作、受控自进化、完整离线任务及手机 GUI；保留其最终能力要求。 |

任务上下文与进展持久化不能替代跨任务长期记忆的验收。后续能力的具体开放顺序由真实应用需要和运行证据决定；开放时必须满足对应授权、恢复与评测要求。

## 2. 能力要求

C1–C9 用于追踪完整能力要求。一项能力可以由多个模块共同提供，具体分工以[现行架构](architecture/README.md)为准。首阶段按上述范围实现，逐项记录已支持的部分与仍待交付的部分。

### C1：任务理解、规划与决策

结合任务目标、用户约束、上下文和可用能力制定计划，选择工具或 Agent，拆分与委派工作。根据实际反馈调整后续步骤，综合结果形成回答或完成判断。信息不足、行动失败或结果不明时，应明确说明当前判断及缺口。

### C2：上下文、记忆与个性化

组织和更新当前任务所需的目标、进展、工具结果、证据与记忆。长期记忆支持跨任务复用，来源包括用户提供、授权接入和交互提取；区分事实、偏好、推断和任务经验，保留来源、时间、置信度与适用范围。个性化信息应在适用任务中实际影响回答或执行。

支持端云结合的记忆访问、端侧数据挖掘与记忆提取。重要隐私数据可以留在端侧并受控使用，原始数据、索引、派生记忆和返回结果分别遵守存储、处理与同步策略。

### C3：信息获取与证据处理

通过可替换的搜索和内容获取能力，从声明支持且已授权的信息源取得实际内容，提供来源与获取时间。明确表达证据不足、来源冲突和获取失败，供任务判断信息的适用性。

### C4：工具调用与设备操作

按行动请求操作工具、设备或外部系统，提供环境观察、调用反馈和实际结果。主要执行路径为 API；GUI 用于没有适用 API 的应用及合适的兜底情况。工具与设备应声明支持的能力和适用条件，手机 GUI 的验收范围见 V2。

分别报告动作是否执行、效果是否得到确认；无法确认时保留不确定状态。请求已发出或节点已连接不能作为任务完成的依据。

### C5：任务运行与端云协同

持久保存任务状态和执行记录，提供调度、超时、重试、取消与恢复能力，支持问答和长时间任务。根据节点能力与用户策略安排工作，支持 Agent 之间的任务委派、进展传递、取消和结果收集。

本地能力齐备且授权有效的任务可以离线继续，依赖失联节点的步骤等待。重连后核对授权、任务状态与执行结果。可能已产生外部效果的动作，应先核对再决定是否重试；无法核对时保留待处理状态。

### C6：扩展接入与协议互操作

通过共同接口和 SDK 接入扩展，支持能力、版本与依赖声明，以及适配和兼容性验证。

| 扩展对象 | 要求 |
| --- | --- |
| 插件 | 提供可安装、可替换的组件或适配器。 |
| Skill | 支持用户自定义操作知识与流程。 |
| Agent | 支持持有目标、上下文和决策循环的内部及外部 Agent；内部生命周期由 Harness 管理，外部 Agent 保留独立运行时。 |

共同接口覆盖任务协作、能力调用、记忆访问和端云连接，并支持各种端侧 UI 的呈现、用户事件、输入请求和交互结果。UI 可以关联任务，也可独立存在，不绑定具体界面框架。一个协议可以覆盖多个接口领域。

### C7：授权与用户控制

统一表达主体、资源、动作、范围和有效期，支持单次与持续授权。内核管理授权检查，执行端落实行动权限；任务委派只能在已有权限内收缩，大脑、插件、Skill、Agent 和自进化产物均不得自行扩大权限。

用户可以查看、纠正、删除信息、限制用途，以及中断任务或接管设备。读取、提取、保存、同步和行动分别受授权约束；读取或进入任务上下文不自动获得长期保存权限。运行记录的使用也遵守授权和用途限制。

### C8：运行观测与能力评测

关联跨端任务、工具调用、授权与结果记录，支持运行诊断。提供可复用的测试集、基线比较和评测结果，测量质量、耗时与成本，服务能力验收和自进化。

分别记录契约符合性与实际任务效果，确保结果可追溯到测试环境、实现版本、测试集和测量方法。

### C9：受控自进化

从经验提出改进，经过隔离评测后发布，持续监测效果并支持回滚。保留来源、产物版本和评测依据，用改进前后的基线比较证明效果提升。

| 改进对象 | 默认生效规则 |
| --- | --- |
| 记忆 | 授权范围内的常规更新可以自动生效；声称效果改善时需提供评测证据。 |
| Skill、执行策略、Agent 配置 | 通过评测后逐步启用。 |
| 插件与内核代码 | 生成可审查补丁，经维护者确认后发布。 |

评测结果不扩大发布权限，自进化不能自行降低评测门槛。

## 3. 系统边界

| 编号 | 要求 |
| --- | --- |
| A1 逻辑分工 | 记忆系统管理信息与经验，大脑负责规划决策，执行系统负责行动与反馈；Harness 内核提供任务生命周期、调度、授权检查和运行记录等公共保障。 |
| A2 独立替换 | 三系统均提供可用的默认实现，允许独立替换；替换后共同的任务、授权和运行规则仍须成立。 |
| A3 端云部署 | 三系统可以部署在端侧、云端或两者之间，逻辑职责不固定绑定某个位置。 |
| A4 共同契约 | 模块、节点和扩展遵守共同的接口与授权规则，明确输入、输出、失败和权限限制，并通过一致性测试验证。 |

## 4. 验收目标与范围

### 首阶段代表场景

首阶段以研究报告任务验证应用价值：用户给出研究问题和约束，系统取得真实来源，形成带引用的报告，保存到指定位置，并核验保存结果。过程中接受用户补充要求、中断与取消；效果未知时核对原操作，不盲目重做。

该场景同时验证信息质量、目标变更、实际写入和中断恢复，与[首条工程验证路径](architecture/engineering/README.md#工程实现与交付顺序)衔接。手机 GUI 保留为独立专项。一个代表场景通过，不替代全部能力与专项验收。

报告完成必须同时满足已确认要求、重要事实有来源支持、保存结果得到核验。证据不足时必须明确缺口，不得宣称相关要求已经满足。正式评测使用独立依据判断实际成果，不能只看系统自身的完成声明。

运行时的开放质量判断继续遵守[分级准入决策](adr/0005-evaluator-evidence-eligibility.md)：允许的评估依据及其限制必须明示。运行时接受一份成果，不自动证明它通过正式质量验收；用户验收也不能替代必要效果的核验。

### 4.1 量化目标

| 维度 | 目标 |
| --- | --- |
| 最终服务规模 | 千万注册用户、百万日活用户、十万同时在线。 |
| API 覆盖 | 支持 1000 个以上 API 的准确调用。 |
| 首次调用质量 | 首次调用正确率至少 90%。 |
| 有限重试效果 | 有限重试后的任务成功率至少 95%。 |

API 接入数量与调用效果分别验收。在线用户规模还需结合任务吞吐、活跃任务、模型并发和存储负载验证。上述数值是目标，不代表已实测达标。

规模和 1000 个以上 API 覆盖作为最终目标。首阶段先覆盖研究报告任务所需能力；首次调用正确率至少 90%、有限重试任务成功率至少 95% 保留为质量目标，按冻结的任务集、尝试次数、期限和费用预算验收。未知结果必须保留在统计分母中，不得通过删除未完成样本提高成功率。

恢复、授权和完成依据必须随首阶段开放的能力一起验收。开发阶段的小规模验证不替代生产验收；首次生产上线仍须满足[既定分布式部署要求](adr/0003-production-distributed.md)。每阶段分别说明能力范围、负载与证据，不以局部通过宣称最终目标达成。

#### 人工参与与成功率

| 参与方式 | 验收口径 |
| --- | --- |
| 正常澄清与授权 | 允许用户说明研究范围、补充目标约束或批准行动；评测计划必须预先固定允许的交互和判定方式。 |
| 人工纠错或代做 | 用户纠正错误结论、补写报告或代做必要步骤后取得的成果单独统计，不计入 95% 任务成功率的成功数；对应样本仍留在分母。 |

评测必须记录人工参与及其影响，不得把人工提供正确答案包装成正常澄清。正常授权也不允许评测向系统泄露答案或替系统完成任务。

#### 耗时与费用上限

先用代表任务测量耗时和费用基线，再在正式验收前冻结耗时、费用及尝试次数上限。内部应用已有硬性成本或等待时间要求时，优先采用该要求。试运行本身也必须设置上限，不能无限运行以寻找可接受参数。

正式统计计入失败、恢复和核验成本，报告耗时分布及超时情况；不得为达到成功率临时增加预算或放宽期限。未知费用保留其不确定性，不能以尚未收齐的账单证明低成本。达到限制时按任务策略停止新增行动，已经发生或仍未知的效果与费用继续核对。

### V1：联网问答

完整验收答案正确性、引用对结论的支撑、信息时效性，以及检索失败、证据不足和来源冲突时的行为。依据必须来自实际取得的内容；个性化信息的使用应符合 C2、C7。

### V2：手机 GUI 操作

完整验收“观察界面 → 执行动作 → 再次观察 → 验证结果”，覆盖点击、滑动、输入、返回、中断与用户接管，并验证权限限制和结果不明时的处理。

参考验收使用多个有状态模拟设备，须提供界面观察及动作引起的可核对变化，不要求真机测试。模拟结果不代表真实手机平台已经受支持；真实设备接入后另行声明和验证支持范围。

### 4.2 验收证据

按能力推进里程碑，分别记录 C1–C9 的完成情况、A1–A4 的满足情况及 V1–V2 的整体结果。手机与电脑协作可作为组合验证场景；场景通过不替代各项能力的独立验收。

能力成熟度保留四个层次，用于说明已具备的证据：

| 等级 | 完成标准 |
| --- | --- |
| L1 契约定义 | 职责、输入输出、可观察行为、错误、权限和能力声明有明确约定。 |
| L2 参考实现可用 | 参考实现可运行，提供可重复的验证结果。 |
| L3 替换与互操作 | 不同实现遵守同一接口，完成适用的跨组件、跨节点或 Agent 协作验证。 |
| L4 异常恢复与治理 | 验证适用的失败处理、恢复、权限与用户控制；自进化另须验证发布和回滚。 |

每项能力分别记录目标等级、实际等级、结果与已知边界。一致性测试覆盖约定的输入输出、错误和可观察行为；实际效果验收还须证明任务目标达成。连接恢复与任务恢复分别验证，个性化须验证实际影响和用户控制，自进化须验证效果改善与旧版本恢复。

具体测试矩阵、样本、重试预算、计分方法和性能门槛，在基线测量后按[验收设计](architecture/validation/README.md)与[正式评测合同](architecture/evaluation/README.md)冻结。冻结必须发生在正式运行前；本文件不预设未经测量的单份报告耗时或价格。

## 5. 后续工作与依据

下一步按首阶段范围编制实现与验收计划，选定内部接入应用、代表任务和试运行上限，取得运行基线后冻结正式验收计划。开发语言、存储、部署与协议已有[工程方案](architecture/engineering/README.md)和[架构决策](adr/)；本轮目标梳理不将已确定选择重新列为待定事项。

本轮优先级参考[系统边界](architecture/system-model.md)、[研究建议的建设顺序](research/ai-report-2026-09-project-implications.md#5-建设顺序与暂缓项)和[五项目比较](research/agent-harness-comparison/architecture-optimization.md)。这些材料支持设计取舍与实验方向，不证明本项目已经实现、达到质量或容量目标，或优于参考项目。

本文件持续维护目标；模块文档维护设计，测试计划维护验收方法，实施报告记录实际结果。目标或默认权限发生变化时，应明确更新本基线。历史能力映射、讨论记录和旧方案保留在归档中。
